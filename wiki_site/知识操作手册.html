1.1 先按职责选，不让一个模型背三种指标

3
组件 负责什么 不负责什么 本库默认/起点
Embedding 第一轮召回：把 query 与 chunk 映射到可检索空间 精排、生成、补足缺失语料 中文、私有化、dense+sparse 一体优先 bge-m3
生成模型 根据证据组织答案、遵循格式与风格 挽回未召回的证据；保证事实自动为真 先按任务质量、上下文、并发和部署约束选，再用业务题验收
Reranker 将 query 与候选一起编码，做第二阶段精排和证据门控 扩大第一轮召回范围 多语言本地精排优先 bge-reranker-v2-m3

bge-m3 适用边界：源篇记录为 1024 维、8192 上下文、100+ 语言，可同时输出 dense、sparse 和 multi-vector；本库当前使用 dense+sparse。中文开源私有部署可先从它起步，但不要仅凭榜单替换模型：先在至少 100 条领域 query 上比较 Recall@5。法律、医疗等窄领域若通用模型召回差，应构造 (query, relevant_doc) badcase 对微调编码器，而不是先换更大的生成模型。

生成模型选型顺序：

  1. 先判断问题是否只是缺知识：缺最新/私有知识走 RAG，换生成模型不能补回未检索到的事实。
  2. 明确质量合同：任务正确性、格式遵循、引用忠实度、上下文长度、延迟、并发、成本与隐私。
  3. 单机低并发可用 Ollama 快速验证；多人服务端用 vLLM 等连续批处理引擎。引擎选择与模型权重选择是两件事。
  4. 固定同一批业务题做 before/after；报告实际生成模型、是否回退、是否命中缓存，不能把回退模型成绩写成目标模型成绩。

Rerank 选型与预算：标准折中是先召回 top-30 左右，再用 cross-encoder 精排到 top-4/5。源篇给出的定位是：bge-reranker-v2-m3 作为多语言默认；更大的 Gemma reranker 追求质量但延迟更高，Jina/mxbai 一类小模型追求低延迟。候选池、上下文块大小和 rerank 延迟要一起测，不能只比较模型榜单。

1.2 换模型前后的硬规则3 个重点▾ 点开看本节重点
本节重点
  • 换 Embedding 必须全量重建索引：不同模型的向量空间不兼容；sparse 头变化后 sparse 索引也要重建
  • 先修管线再换 Embedding：推荐排查顺序是 chunking + metadata → hybrid → candidate size → 最后才是换 Embedding
  • 查询与入库必须同源：同一模型、同一 snapshot、同一 dense/sparse 配置；否则两路看似运行，实际空间已错位
3
  • 换 Embedding 必须全量重建索引：不同模型的向量空间不兼容；sparse 头变化后 sparse 索引也要重建。
  • 查询与入库必须同源：同一模型、同一 snapshot、同一 dense/sparse 配置；否则两路看似运行，实际空间已错位。
  • 先修管线再换 Embedding：推荐排查顺序是 chunking + metadata → hybrid → candidate size → 最后才是换 Embedding。
  • RRF 分数不是可信度：dense 距离、BM25/sparse 分、RRF 分和 rerank 分不可共用一个阈值。
  • ** rerank 不能救召回**：正确文档没进候选池时，精排无货可排；先看各单路 rank，再调 rerank。
  • 维度不是越高越好：更高维会增加存储和计算成本，是否值得必须由本领域 Recall 与成本共同决定。

2. 模型微调（LoRA / QLoRA / SFT / DPO）

2
2.1 先决定“该不该训”，再决定“怎么训”3 个重点▾ 点开看本节重点
本节重点
  • 微调改行为，RAG 供知识
  • 固定格式、语气、领域任务流程可考虑微调；频繁变化、需要引用的知识用 RAG；少量样本或偶发任务先用 Prompt/Few-shot
  • 源篇的常见门槛是至少约 500–1000 条高质量样本再认真考虑微调，另一篇给出的保守提醒是少于 300–500 条先不要微调
3

微调改行为，RAG 供知识。 固定格式、语气、领域任务流程可考虑微调；频繁变化、需要引用的知识用 RAG；少量样本或偶发任务先用 Prompt/Few-shot。源篇的常见门槛是至少约 500–1000 条高质量样本再认真考虑微调，另一篇给出的保守提醒是少于 300–500 条先不要微调。它们都是经验门槛，不是质量保证；数据去重、覆盖真实分布、train/eval 隔离比堆数量更重要。

路线 核心动作 适用 主要代价/风险
全量 SFT 更新全部参数 算力充足、确需极限任务表现 显存高，易灾难性遗忘
LoRA SFT 冻结基座，只训低秩 adapter 多数行为/格式/领域适配 仍需容纳较高精度基座与激活
QLoRA SFT 4-bit 冻结基座 + LoRA 单卡显存受限，先跑通流程 源篇记录训练通常更慢；不是默认必选项
DPO 用同一提示的 chosen/rejected 直接做偏好优化 SFT 后还需调整回答偏好 偏好数据偏差、长度偏差、通用能力退化

LoRA 常用起点：r=8~16、alpha≈2r、dropout=0.05~0.1、学习率约 1e-4~2e-4、epoch=1~3。简单任务可先只挂 q_proj,v_proj；需要更强适配时覆盖 attention+FFN 的线性层。QLoRA 的 quantization_bit=4 只控制基座加载量化，不等于 adapter、梯度和所有计算都变成 4-bit。

2.2 数据契约与完整流水线

3

SFT 两种格式：

{"instruction":"把这段周报改写成汇报口径","input":"本周修了3个bug...","output":"本周完成质量治理..."}
{"conversations":[{"from":"human","value":"..."},{"from":"gpt","value":"..."}]}

DPO 配对格式：chosen 与 rejected 必须回答完全相同的 instruction/input；LLaMA-Factory 注册表中要有 ranking: true。不要让“长答案”自动等于 chosen，也不要只给错误答案做无意义扰动。

完整流水线固定为：

业务基线 → 数据清洗/去重/长度检查 → train/eval 切分
→ LoRA 或 QLoRA SFT → 业务评测 + 通用能力回归
→（确有需要才做）DPO → 再评测
→ 用未量化基座合并 adapter → 量化 → 对最终量化模型复跑评测
→ 部署与真实负载验收

DPO 不是 SFT 的自动下一步；没有明确偏好目标与配对验证集就不加。源篇给出的 DPO 学习率起点为 5e-6、pref_beta=0.1、先跑 1 轮小实验，明显低于 LoRA SFT 的学习率。

2.4 验收与高频坑

3
  • 只看 train loss 无效：train loss 降而 eval loss 升是过拟合；业务测试集必须训前跑基座、训后跑同题对比。
  • 通用能力必须回归：防止模型只会领域话术；必要时在训练集中混入少量通用指令 replay。
  • 模板/字段优先于调 lr：loss 不降先查非空答案、chat template、columns 映射、截断后是否只剩提示、target module 是否存在。
  • adapter 目录不等于完整训练检查点：恢复训练需要匹配模型、数据、配置和优化器状态。
  • 微调结束不是验收结束：合并后、量化后、服务后都要复跑业务与通用能力测试。
  • 训练 OOM：先降每卡微批量并配合梯度累积，再缩 cutoff、开 gradient checkpointing，最后才改 QLoRA/ZeRO/offload；具体命令见第 6 节。

3.1 三种路线不是三个可互换的文件后缀3 个重点▾ 点开看本节重点
本节重点
  • GPTQ/AWQ 属训练后量化（PTQ）路线，校准数据必须代表真实业务
  • 工具维护状态（源篇 2026-11-02 核对）：AutoGPTQ 不再是新项目的推荐入口；AutoAWQ 已于 2025-05-11 归档弃用
  • GGUF 是格式，不是与 GPTQ/AWQ 同义的算法；不同格式和工具产物不能凭文件名混用
3
路线 原理/性质 主要场景 工具与默认起点
GPTQ 用校准数据估计逐层二阶信息，量化后补偿同层其他权重 GPU 服务端 INT4，愿为质量做代表性校准 新项目用 GPTQModel 或 llm-compressor；4bit、group size 128 起步
AWQ 按激活分布保护重要通道，通过缩放降低关键权重量化误差 GPU 服务端 INT4，面向 vLLM/SGLang 面向 vLLM 优先 llm-compressor；不要为新项目安装 AutoAWQ
GGUF llama.cpp 的模型文件格式，可承载不同量化权重 本地、CPU、边缘、Ollama Q4_K_M 起步；代码/数学可比较 Q5_K_M/Q6_K

GPTQ/AWQ 属训练后量化（PTQ）路线，校准数据必须代表真实业务。GGUF 是格式，不是与 GPTQ/AWQ 同义的算法；不同格式和工具产物不能凭文件名混用。量化只直接压缩权重，KV cache、激活和并发占用不会按同一比例消失。

工具维护状态（源篇 2026-11-02 核对）：AutoGPTQ 不再是新项目的推荐入口；AutoAWQ 已于 2025-05-11 归档弃用。量化与 vLLM 服务建议分虚拟环境，避免 torch/transformers 依赖互相降级。Marlin 是推理 kernel，不是量化工具；同为 AWQ/GPTQ，是否走到优化 kernel 会显著影响吞吐。

以下来自 L12-GPTQ 源篇摘录的官方 README 示例，源篇明确标注“本机无 GPU 未实跑”。先核对已装版本；README 使用 GPTQConfig，部分 vLLM 文档仍写 QuantizeConfig。

pip install -v gptqmodel
python -c "import gptqmodel; print(gptqmodel.__version__)"

from datasets import load_dataset
from gptqmodel import GPTQModel, GPTQConfig

model_id = "meta-llama/Llama-3.2-1B-Instruct"
quant_path = "Llama-3.2-1B-Instruct-gptqmodel-4bit"
calibration_dataset = load_dataset(
    "allenai/c4",
    data_files="en/c4-train.00001-of-01024.json.gz",
    split="train",
).select(range(1024))["text"]

quant_config = GPTQConfig(bits=4, group_size=128)
model = GPTQModel.load(model_id, quant_config)
model.quantize(calibration_dataset, batch_size=2)  # 按显存调整
model.save(quant_path)

  2. 质量不只看 perplexity：至少复跑业务任务、代码/数学等敏感任务和通用能力；比较 FP16/BF16 基线与最终量化产物。
  3. 性能不只看格式名：记录引擎、kernel、GPU、上下文、并发，比较 TTFT、TPOT、输出吞吐和峰值显存。
  4. 不要默认超低 bit：Q4 是常见起点，Q2/3bit 只在明确容量约束且质量回归可接受时考虑。
  5. 不要二次叠加旧量化权重：需要重新量化时从原始高精度权重出发；旧 AutoGPTQ/AutoAWQ 产物与新工具 API、格式可能不兼容。

关键参数：

  • --gpu-memory-utilization：控制 KV cache 池预算，不是“权重量化率”。源篇记录 vLLM 0.6.x 起默认 0.85，旧资料常写 0.9；以当前 vllm serve --help 为准。
  • --max-model-len：单序列 KV 随长度线性增长；按真实 p99 长度设，不盲目开模型上限。
  • --max-num-seqs：并发序列上限；低延迟可从 8–16 起步，批吞吐再逐步增加。
  • --tensor-parallel-size：源篇要求使用 2 的幂；多卡还会增加通信开销，不等于吞吐必然线性增长。
  • --enable-prefix-caching：只有前缀逐字节一致且确有重复时才可能获益；重启不保留，不能假设跨用户自动命中。

压测至少记录 Output token throughput、TTFT、TPOT/ITL、并发和请求长度分布。不同工具的同名指标测量点可能不同，不能仅按名称横向比较；至少复跑两轮，并同时观察 swap/抢占和质量回归。

4.4 部署高频坑

3
  • 服务能 curl ≠ 业务能用：还要跑真实长度、真实并发、流式输出、异常输入与模型质量回归。
  • 低吞吐先确认 GPU 利用率和排队：不要盲目加一堆开关；提高并发会同时增加延迟和 KV 压力。
  • 长上下文 OOM 不一定是权重太大：优先区分权重、KV cache、激活和其他进程占用。
  • 量化后仍需压测：格式相同但 kernel 不同，吞吐可能相差很大。
  • 模型升级要重查参数语义：默认值和参数名会随版本变化，旧教程不能替代当次 --help 与启动日志。

CUDA_VISIBLE_DEVICES=0 llamafactory-cli train configs/qwen_qlora_sft.yaml \

# 仅碎片场景尝试；不会增加物理显存

torch.cuda.empty_cache() 只释放未使用缓存，不释放仍被引用的张量；评测 OOM 要降评测 batch/生成长度，保存 OOM 要查权重聚合，不能只改训练 batch。ZeRO-3/offload 还会增加主存与通信压力，使用前单独规划。

6.5 部署防 OOM：Ollama 与 vLLM 分别调

3

Ollama：context × parallel × 每 token KV 是乘法关系。显存紧张先缩上下文和并发、只驻留一个模型，再评估 q8_0 KV；不要同时开 32K 和 8 并发后才发现权重之外还缺几十 GB。

# 保守起点，作用于当前 shell 中随后启动的 Ollama 服务
export OLLAMA_CONTEXT_LENGTH=4096
export OLLAMA_NUM_PARALLEL=1
export OLLAMA_MAX_LOADED_MODELS=1
export OLLAMA_FLASH_ATTENTION=1
export OLLAMA_KV_CACHE_TYPE=q8_0

ollama ps

vLLM：按“确认权重还是 KV → 降 utilization → 缩 max-model-len → 降 max-num-seqs → 再评估量化/并行”的顺序。诊断模式如下：

vllm serve MODEL \
  --gpu-memory-utilization 0.70 \
  --max-model-len 4096 \
  --max-num-seqs 16 \
  --enable-log-stats

注意：源篇 OOM 链把降低 gpu-memory-utilization 作为释放预留/稳定性的排查步骤；它改变的是 KV 池预算，不是权重本身。若权重已装不下，仅调这个参数不够，应量化、换更小模型或重新规划并行。
