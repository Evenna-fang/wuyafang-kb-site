RAG 三层评估与数据集：先定位检索、生成还是端到端问题

本篇是本层“RAG 三层评估与数据集”的唯一正文。“检索层—生成层—端到端”是本库用于工程归因的三层框架，不是 RAGAS 原论文规定的官方三层分类。历史阈值与历史评测数字均不当成本次实测。

WHY：为什么端到端低分不能直接怪生成模型

2

同一个“答案错了”，至少可能来自四条路径：

  1. 正确材料根本没有被检索到。
  2. 正确材料被检索到，但排名太靠后或被上下文预算截掉。
  3. 最终上下文包含正确材料，生成器却没有使用或误用了它。
  4. 检索与生成单独看都正常，但问题本身无答案、金标缺失，或系统超时、拒答。

如果只跑端到端评分，团队会反复换提示词和模型，却看不到真正故障层；如果只跑检索指标，又可能把“找到了相关段落”误当成“用户得到正确、完整答案”。

三层评估的价值是归因而不是多报几个数字：

  • 检索层回答“证据有没有来、是否排前、上下文是否足够”。
  • 生成层回答“给定实际送入的上下文，回答是否忠实、相关、完整”。
  • 端到端回答“从用户问题到最终响应，任务是否成功”。

没有稳定的金标与证据 ID，三层数字看似精确，实际无法比较。尤其当标注覆盖变化时，检索器完全没变，Recall 也可能变化。

WHAT / WHYT：三层指标、数据契约与适用边界

2

1. 检索层：Recall、HitRate、MRR 与排序精度不是同一件事

3

设某题金标证据集合为 (G)，前 (k) 个检索结果为 (R_k)：

  • Recall@k：(|G \cap R_k| / |G|)。关心金标证据找回了多少；多证据问答尤其重要。
  • HitRate@k：只要 (G \cap R_k) 非空即为 1。关心是否至少命中一条，不代表证据齐全。
  • MRR：每题取首个相关结果排名的倒数再平均。关心第一条证据是否靠前，不反映后续证据覆盖。
  • Context Precision：对前 k 个位置的相关/不相关序列计算 AP 型排序指标。关心相关项是否靠前，不能替代 Recall。
  • Context Relevance：上下文与问题的相关程度。相关不等于足以支持正确答案。

例如相关序列为 [1, 0, 1, 0, 1]，三个命中位置的 precision 分别是 1、2/3、3/5，AP 为：

(1 + 2/3 + 3/5) / 3 = 0.755555...

即使该例 Recall@5 为 1，AP 仍只有约 0.7556，因为不相关项插在相关项之前。两个指标揭示不同问题，不应互相替代。

2. 生成层：必须使用“最终送模上下文”

3

生成层不是只保存检索器原始输出。重排、去重、截断、权限过滤和模板拼接后，模型实际看到的上下文可能已不同。评估记录至少要保留：

query_id + ranked_evidence_ids + final_context_ids + answer + reference_answer + metric_status

否则无法区分“检索没找到”与“找到了但没送模”，也无法复查裁判是否读到同一材料。忠实度、答案相关性、答案正确性的具体口径见 03-RAGAS核心指标。

3. 端到端：正确性、覆盖率与失败状态一起看

3

端到端参考答案 reference_answer 应包含关键事实、可接受变体和禁止事实。无答案问题还要标记 unanswerable，把“应当拒答”与“答错”分开。空输出、超时、检索空结果、裁判异常和正常低分分别记录，不能统一塞成 0 分。

建议每条结果都有：

{"query_id":"q-017","slice":"policy/unanswerable","retrieval_status":"scored","generation_status":"scored","judge_status":"scored","faithfulness":1.0,"answer_correctness":null}

null 必须配套原因，例如 not_applicable；报告中的指标分母只包含该指标有效样本，同时公开缺失率和原因。不能因为“忠实”就推断“回答完整”。

4. 论文怎么说，我们怎么用

3

金标覆盖会改变检索评分（arXiv:2610.31606）。本地摘要报告：在一个含 18 篇文档、18 个查询的小开发集上，标注扩充使 evidence spans 从 25 增至 37、accepted chunk targets 从 36 增至 51，而检索排名不变。这是小规模开发集证据，不能外推成所有数据集的同幅度变化。

我们的用法：看到检索分数上升，先检查 qrels/manifest 是否变化；新增金标时保留数据集版本，并使用同一版本重跑基线与候选。报告把“检索器变化”和“标注覆盖变化”拆开，禁止把后者包装成模型收益。

5. 历史阈值与结构性假象的边界

3

旧稿保存的是 2026-10-19 历史快照：当时 rerank.threshold=0.45，正负样本分离窗记为 (0.0211, 0.4943]；还曾出现 R@5=R@10，原因是 top_k=4 加图谱槽使结果列表最长只有 5。它们说明如何诊断，不是 2026-11-04 重新测得的当前真值。

因此：

  • 不把 0.45 复制成其他模型、版本或业务的默认阈值。
  • 计算 Recall@k 前先看实际返回长度与上游 top_k，否则增大 k 只是名义变化。
  • 阈值必须同时看正负样本，单独用正例调低阈值可能显著增加误检。

HOW：从金标审计到三层可复跑评估

2

第一步：建立版本化 qrels 与查询集

3

查询集建议字段：

{"query_id":"q-001","query":"退款期限如何计算？","gold_evidence_ids":["doc-7#p3","doc-7#p4"],"reference_answer":"……","slice":"refund","unanswerable":false,"qrels_version":"2026-11-04-v1"}

操作顺序：

  1. 领域人员先标问题是否可答，再标所有足以回答的证据，不是只点一条看似相关的 chunk。
  2. 多证据题记录证据组合，避免只命中一条就宣称信息完整。
  3. 冲突材料、过时材料和重复 chunk 单独标记，不能只凭文本相似度自动并入金标。
  4. 将数据集分为调参开发集与只读测试集；阈值和提示词只在开发集上选择。
  5. 每次改标注生成新 qrels_version，基线和候选在同一版本上配对重跑。

第二步：用确定性实现计算检索指标

3 
import math


def recall_at_k(gold_ids, retrieved_ids, k):
    gold = set(gold_ids)
    return len(gold & set(retrieved_ids[:k])) / len(gold) if gold else math.nan


def hit_rate_at_k(gold_ids, retrieved_ids, k):
    gold = set(gold_ids)
    return float(bool(gold & set(retrieved_ids[:k]))) if gold else math.nan


def reciprocal_rank(gold_ids, retrieved_ids):
    gold = set(gold_ids)
    for rank, doc_id in enumerate(retrieved_ids, start=1):
        if doc_id in gold:
            return 1.0 / rank
    return 0.0


def average_precision(relevance):
    hits = 0
    precision_sum = 0.0
    for rank, relevant in enumerate(relevance, start=1):
        if relevant:
            hits += 1
            precision_sum += hits / rank
    return precision_sum / hits if hits else math.nan

无金标的查询不应被强行记 0；它应进入 not_applicable 并报告数量。average_precision 的输入是真实逐位置相关性，不是只根据是否命中生成的简化标签。

第三步：保存足以归因的检索轨迹

3

每次运行至少写：

manifest_hash / retriever_version / query_id / requested_k / actual_returned_n
ranked_ids_with_scores / final_context_ids / latency_ms / error_type

然后按以下顺序定位：

  1. requested_k 是否大于实际可能返回的数量。
  2. 金标是否在原始候选、重排后列表、最终上下文三个位置分别出现。
  3. 相似度分布是否因嵌入模型或分数归一化变化而整体平移。
  4. 空结果是个别查询失败，还是全批数据/配置错误。

第四步：双端标定阈值，而不是照搬历史值

3

设正样本为“应保留的证据对”，负样本为“不应保留的证据对”：

  1. 在开发集同时采样正、负与困难边界样本，检查标签独立性。
  2. 分别画出正负分布，按业务代价选择漏检/误检权衡。
  3. 若存在干净分离窗，可把候选阈值放在窗内并做扰动测试；若分布高度重叠，不要虚构“完美阈值”。
  4. 在冻结测试集只验证一次最终方案，并按领域、语言、查询类型分桶。
  5. 保存阈值、打分器版本和数据版本；任何一项变化都重新标定。

可复用判定逻辑：

def candidate_window(positive_scores, negative_scores):
    if not positive_scores or not negative_scores:
        raise ValueError("正负样本都不能为空")
    lower = max(negative_scores)
    upper = min(positive_scores)
    return (lower, upper) if lower < upper else None

返回 None 表示当前样本没有简单的一维干净分离窗，不代表系统无可用工作点；此时应结合成本函数、分桶阈值或改进入股特征，而不是只报最好看的阈值。

第五步：汇总三层结果

3 
检索：Recall@k / HitRate@k / MRR / AP + 有效样本数
生成：Faithfulness / Relevancy / Correctness + 各指标缺失率
端到端：任务成功率 / 拒答正确率 / 延迟 / 成本 + 失败类型
归因：无证据、未送模、未使用证据、遗漏、幻觉、裁判失败

只有同批 query、同一 manifest、同一数据版本和同一评分协议的结果才能做 paired delta。基线失败时重新运行基线，不允许把缺失基线自动记为候选通过。
