核心论点

2

不成功的 LLM 产品几乎都有同一个根因——没建起稳健的评测系统，评测不是流程装饰而是产品地基：Hamel 的三级体系（代码断言→人工+模型评测→A/B）里，便宜确定的 Level 1 该先做够再上模型评测，且断言要按 feature × scenario 组织而非按代码函数。对 RAG 必须把检索失败和生成失败拆开测——只测端到端分数会把"检索变差但生成变强"的对消放过去，RAGAS 分项指标的全部价值就在定位故障层。方法论的边界条件同样硬：LLM judge 是元问题（要持续追踪与人的对齐，类别不平衡时用 precision/recall 而非 raw agreement），golden set 以 50–200 条真实 query 起步且每条生产失败都要进集，通过率 100% 不是目标。本库的现状正好卡在缺口上：检索侧 Recall@k 闭环已跑（run_eval.py），但生成侧 faithfulness 无测量、golden set 26 条低于行业下限、错误分析制度缺位——补齐这三项，才谈得上评测闭环。

  • 动机（WHY）：不成功的 LLM 产品几乎都有同一个根因——没建起稳健的评测系统；大部分团队把精力全花在改 prompt/改代码（迭代）上，跳过了「评测」和「调试看数据」两环（Hamel 一手判断）。评测不是流程装饰而是产品地基：没有评测，每次改动都是"盲改"（不知道改好还是改坏），积累不出"什么有效"的判断。三级体系（代码断言 → 人工+模型评测 → A/B）的动机是把评测成本按确定性排序：便宜确定的 Level 1（代码断言）先做够再上贵的模型评测，而不是一上来就 LLM-as-judge。

分级与节奏

3
级别 是什么 节奏 成本
Level 1: 单元测试 代码断言（pytest 风格）：len(listing_array)==1、输出不含 UUID 的正则断言 每次代码变更都跑 最低
Level 2: 人工 + 模型评测 先记 trace → 人看数据标 good/bad（二元）→ LLM judge 自动化并对齐人工 按固定节奏（如每周），覆盖全部测试用例 + 生产采样 中
Level 3: A/B 测试 线上实验，验证 AI 改动是否真驱动了用户行为/业务结果 只在重大产品变更后 最高

原文节奏建议：先做完相当一部分 Level 1 再上模型评测——断言便宜、快、确定性强；模型评测贵且需要对齐工作。

2.1 指标定义（📰 Redis / DataAIHub 检索评测指南，二手但定义标准）

3
指标 公式 用途
Recall@k top-k 命中相关文档数 / 相关文档总数 检索主指标；行业经验目标 0.80+（DataAIHub 口径）
Precision@k top-k 中相关数 / k 看噪声占比
MRR@k 首个命中位置的倒数均值 看排序质量（本库 hybrid+rerank 实测 0.605，见 arXiv:2604.01733）
2.2 golden set 工程规范3 个重点▾ 点开看本节重点
本节重点
  • 规模：50–200 条真实 query–doc 对起步（DataAIHub 建议 50+；Confident AI 建议 50–100 条人工复核案例）
  • 纪律：一次只改一个检索组件再复测（DataAIHub）；聚合指标告诉你「差多少」，失败案例告诉你「为什么」——逐条看 miss（本库 run_eval.py 的 MISS 打印就是这个用法）
  • 据[一手源]：raw/rag-arch/RAG进阶调研-6方向-Top3落地方案-20260928.md（混合检索方向），另一组经验数字：recall@10 纯向量约 78%、纯 BM25 约 65%、RRF 融合约 91%，纯向量在精确匹配/缩写/产品 ID 类 query 上 miss 30–40%
3
  • 规模：50–200 条真实 query–doc 对起步（DataAIHub 建议 50+；Confident AI 建议 50–100 条人工复核案例）。
  • 构成：按真实流量比例覆盖常见查询 + 边界 case + 每一条已确认的生产失败（Confident AI）。
  • 来源：生产 trace 是第一来源（Braintrust：真实查询的措辞是开发者想不到的）；合成数据只用来 bootstrap 覆盖面，必须抽样人工验证（生成的 question 可能答非所问）。
  • 门禁：每个组件改动（embedding 换型/chunking/检索参数/索引重建）都跑 golden set，per-metric 阈值当合并门禁；检索指标和生成指标分别 gate（Confident AI）。
  • 纪律：一次只改一个检索组件再复测（DataAIHub）；聚合指标告诉你「差多少」，失败案例告诉你「为什么」——逐条看 miss（本库 run_eval.py 的 MISS 打印就是这个用法）。

参考线：检索侧 Recall@5 0.80+；RAGAS 侧 Context Recall <0.8 意味着生成端拿不到必要信息、会开始编（📰 Redis）。

据[一手源]：raw/sources/RAG优化-外部调研-20260929.md（方向 4）：这条 0.80 线有一份大样本参照，arXiv 2604.01733（23,088 queries / 7,318 docs / 10 种检索策略）实测 hybrid+rerank Recall@5=0.816，dense-only 0.587（hybrid+rerank 相对 +39%），hybrid-only 0.695（相对 dense +18.4%；hybrid+rerank 相对 hybrid-only 再 +17.4%），MRR@3 从 0.433 升到 0.605。召回不够时的修复顺序是 chunking+metadata → hybrid → candidate size → 最后才换 embedding。据[一手源]：raw/rag-arch/RAG进阶调研-6方向-Top3落地方案-20260928.md（混合检索方向），另一组经验数字：recall@10 纯向量约 78%、纯 BM25 约 65%、RRF 融合约 91%，纯向量在精确匹配/缩写/产品 ID 类 query 上 miss 30–40%。

3.1 四类核心指标2 个重点▾ 点开看本节重点
本节重点
  • 完整清单还含 context utilization / noise sensitivity / summarization score 等（📄 RAGAS Metrics 文档）
  • 「context_entities_precision」 在 v0.2 移除，被 LLM-based context_precision/recall 取代
3
指标 测什么 计算方式
Faithfulness（忠实度） 答案是否忠于检索到的上下文（防幻觉） LLM 先把答案拆成陈述句，再逐句判定是否被 context 支持，取支持比例（📄 LangChain 官方博客）
Answer Relevancy 答案是否切题 LLM 由答案反推问题再比对
Context Recall 检索是否捞全了答对所需的信息 用 ground truth 答案逐句问「这句能在 context 里找到吗」，找不到 = 检索缺失（同上）
Context Precision 相关 chunk 是否排在前面 按位置加权的相关性

四者的调和均值 = 单一 ragas score（📄 LangChain 官方博客）；分项的价值在于定位故障在检索还是生成（📰 QASkills 教程）。完整清单还含 context utilization / noise sensitivity / summarization score 等（📄 RAGAS Metrics 文档）。

据[一手源]：raw/rag-arch/RAG业内最高标准-20261009.md（官方 docs 逐字核对）：本表四类之外，Context Relevance 由 LLM 判每个 chunk 与 query 相关再取均值，不需要 ground truth（检索层唯一 reference-free 指标）；Noise Sensitivity 打乱/删除 chunk 后重新生成，看正确性下降；Topic Adherence 看答案是否停留在预定义主题内；Hallucination = 1 − 不受支持 claims / 总 claims。context_entities_precision 在 v0.2 移除，被 LLM-based context_precision/recall 取代。另据[一手源]：raw/sources/RAG优化-外部调研-20260929.md：RAGAS 的 RAG 专属指标共 8 个（faithfulness / answer relevancy / context precision / context recall / context utilization / noise sensitivity / answer correctness / answer similarity）。

from ragas import evaluate
from ragas.llms import LangchainLLMWrapper
from ragas.metrics import LLMContextRecall, Faithfulness, FactualCorrectness
from langchain_openai import ChatOpenAI

evaluator_llm = LangchainLLMWrapper(ChatOpenAI(model="gpt-4o-mini"))
result = evaluate(
    dataset=evaluation_dataset,
    metrics=[LLMContextRecall(), Faithfulness(), FactualCorrectness()],
    llm=evaluator_llm,
)

4.1 离线 vs 在线

3
  • 离线评测：对 curated dataset 跑，像 LLM 应用的单元测试，部署前拦回归；在线评测：对生产流量实时打分，抓质量漂移（📄 LangSmith Evaluation 产品页）。

4.2 评测器类型与关键技巧2 个重点▾ 点开看本节重点
本节重点
  • 「exact_match」 会因空白/大小写静默失败，真实输出用语义相似度或 LLM judge
  • 据[一手源]：raw/rag-arch/反面教材-踩坑Top10-20260928.md（Top3）：评测结论不采信自报，只测正例的"通过"无效，验收要正例 + 负例误报 + 文档与实测一致三件套
3
类型 用法
启发式/代码断言 校验格式、能否编译——快但覆盖窄
LLM-as-judge 按你定义的 criteria 打分，可自定义 Python/TS evaluator
Pairwise 对比 evaluate_comparative(["exp-a","exp-b"], evaluators=[evaluate_pairwise])——比单独打分区分度高得多：单标准打分对两个模型常常拉不开差距，成对比较才能看出偏好（📄 LangChain 官方博客《Pairwise Evaluations with LangSmith》）
人工 annotation queue，把不确定样本路由给评审，结果回流 dataset

回归测试的工程坑（📰 The Neural Base LangSmith 实战，⚠️二手经验）：
- exact_match 会因空白/大小写静默失败，真实输出用语义相似度或 LLM judge
- CI 里 evaluate() 要包 try/except，大数据集跑一半 API 超时会导致静默部分失败——跑完核对 len(results.runs) == len(dataset) 再宣布成功
- 自定义 evaluator 签名按当前版本文档（0.1.0+ 用 @evaluate 装饰器模式，返回顶层 {'key','score','comment'}）
- 据[一手源]：raw/sources/RAG优化-外部调研-20260929.md（方向 4）：CI 与线上的工具分工口诀是 "DeepEval catches regressions at PR time, RAGAS monitors drift over time"——DeepEval 是 pytest-based CI runner，RAGAS 做定时采样（CronJob 每小时采样 1–5% traces，Grafana 看 7 天滚动平均），faithfulness < 0.80 触发告警。
- 据[一手源]：raw/rag-arch/外部调研-雷点知识学习-20260925.md（主题 5）：门禁里的断言要可重放，不依赖墙钟或上轮残留的计数器；失败先智能重跑判可复现，可复现直接红，盲目自动重跑会把红洗成绿（调研引用 47% 重启即过的失败 job 掩盖了真问题）；flaky 检查进 quarantine，必须带 owner 和 deadline。
- 据[一手源]：raw/rag-arch/反面教材-踩坑Top10-20260928.md（Top3）：评测结论不采信自报，只测正例的"通过"无效，验收要正例 + 负例误报 + 文档与实测一致三件套。

1. 记 trace（LangSmith/任意）           ← 一切的原料
2. 人工看 trace 做错误分析（频次分类）     ← Hamel: 最高 ROI 的一步
3. 沉淀 golden set（50–200 条，含生产失败）
4. 检索侧: Recall@k/MRR → 门禁           ← 本库已做（run_eval.py）
5. 生成侧: RAGAS faithfulness/context recall + LLM judge（对齐人工后才可信）
6. 改动 → 重跑 4/5 → 逐条看 miss → 定位是检索还是生成
7. 线上: A/B + 在线评测 → 新失败回流 step 2

与本库 golden-q 的差异：本库只做 step 4（检索 Recall@k，26 条 golden-q，5 方向），缺 step 5 生成侧评测（faithfulness 无）、缺 step 2 的错误分析制度、golden set 规模（26 条）低于行业建议的 50–200 条下限。

  • 三层评测的标准执行序列（先检索层、再生成层、最后端到端）：
    bash source ~/ai-stack/bin/activate cd /mnt/c/MyData/Documents/wuyafang-l python3 rag/eval/eval_recall.py # 检索层 Recall@1/@5/@10 python3 rag/eval/eval_recall_fast.py --mode hybrid # 快速版（可 --no-sparse/--no-graph 消融） cd rag && ~/ai-stack/bin/python eval_ragas.py # 生成层 + context 四指标 cd rag/eval && python3 -u _e2e_eval.py # 端到端（retrieve_node→rerank_node 真实生产口径）
  • golden set 维护：rag/eval/golden-q.jsonl 每行 {id, question, relevant_source, category, answer_keywords, qtype, is_no_answer}（56 条，含 Q052–Q056 域外负样本）；新增题补 relevant_source 用库内相对路径（如 wiki/L4-RAG工程/xxx.md），eval_recall.py 按前缀匹配判定命中。
  • “找到≠答对”复现路径：rag/eval/run_baseline.py 一次拿全 6 指标（Recall@k / P@1 / Rel / Faith / AnsRel），对比 Recall=100% 而 faithfulness<1 的样本就是 Q004 型生成层被旧值带偏案例；答案侧答案正确性另看 _e2e_eval.py 输出。
  • 动库门禁 = 三层联合不降：改库（去重/重灌/加 contextual 前缀）前先留三层基线（eval/baseline-*.json 系列是历史留档样式），改后同命令重跑逐项对比；任一层掉线即回滚，禁止只看 Recall@5 放行。
  • badcase 回流：_e2e_eval.py 自动把 Recall@5 失败题 append 到 rag/eval/badcase.jsonl（status=open），语义档走“生成改写草稿→人审→改 wiki/raw→sync 重灌→本集合回归”，机械档（缺 chunk）自动触发 ingest 重跑。
  • 指标换算口径：Answer Correctness = 0.75×F1事实重合 + 0.25×语义相似度；R@5=R@10 在 top_k=4 下是结构性假象，报告里别把 R@10 当独立指标（见 rag/config.yaml top_k=4）。
