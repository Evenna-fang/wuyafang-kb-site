Faithfulness 只回答一个问题：答案里的每个说法，检索到的上下文撑不撑得住。它由 RAGAS 论文（arXiv:2309.15217）第 3 节定义，是论文三个原始指标之一（另两个是 Answer Relevance 和 Context Relevance），也是论文里与人工标注吻合度最高的一个：在 WikiEval 上成对比较的准确率 0.95，对比 GPT Score 的 0.72 和 GPT Ranking 的 0.54。

但"最可靠的指标"不等于"最全面的指标"。本库的实测暴露出三件事：①Faithfulness 完全看不到漏答，10-15 那轮 RAGAS 库评测 5 题 Faithfulness 全是 1.0，其中两题的答案自己写着"语料中只给出 N3–N6 四个节点""第六个成员语料中没有相关信息"，对照标准答案是漏了一半；②零 claim（拒答）时分数没有定义，官方实现返回 NaN，而本库 10-10 基线脚本硬编码成 1.0，把它平均进总分后总分失去意义；③裁判一旦失效（输出被截断、解析把空输出当 NO），分数会静默地变成随机数，本库 10-28 的裁判自一致率曾经只有 40%。所以 Faithfulness 必须和检索层、端到端指标联合读，不能单独当成"质量分"。

为什么要单独测 Faithfulness（动机与代价）

2

动机：RAG 的卖点是"答案有据可查"。检索层指标（Recall、Context Precision）只证明材料找到了，不证明模型用对了材料。模型可能在材料之外自由发挥（脑补一个数字、混入训练记忆里的旧知识），也可能把材料里的矛盾内容拼在一起。这类问题在检索指标上完全不可见。Faithfulness 把"生成是否越界"变成一个 0 到 1 的数，并且不需要标准答案，因此线上流量也能测，这是它在生产评估里最便宜好用的原因。

代价：每条样本至少两次裁判调用（抽取 claim、逐条验证），上下文越长、claim 越多越贵；分数依赖裁判模型，换裁判后绝对值不可比；且它的取值范围天然偏乐观，因为拒答和空洞回答也可以拿高分（见局限一节）。

是什么（定义与边界）3 个重点▾ 点开看本章重点
本章重点
  • 官方定义：官方文档写道："A response is considered faithful if all its claims can be supported by the retrieved context."分数范围 0 到 1，越高越好
  • 论文第 3 节的说法是答案是 faithful 的，当且仅当答案里的 claims 能够从上下文推断出来
  • S 是从答案中抽出的 statement 总数，V 是裁判判定为"被上下文支持"的 statement 数
2

官方定义：官方文档写道："A response is considered faithful if all its claims can be supported by the retrieved context."分数范围 0 到 1，越高越好。论文第 3 节的说法是答案是 faithful 的，当且仅当答案里的 claims 能够从上下文推断出来。

公式：F = |V| / |S|。S 是从答案中抽出的 statement 总数，V 是裁判判定为"被上下文支持"的 statement 数。

边界：
- ✅ 管：答案相对检索上下文的一致性，即"有没有越界"。
- ❌ 不管：答案对不对（上下文本身可能是错的或过时的）、答案全不全（漏答不扣分）、答案切不切题（那是 Answer Relevancy）、检索得好不好。
- ⚠️ "忠实"针对的是送进生成模型的那几段文本，不是整个知识库。把文档全文当 retrieved_contexts 传入会让分数虚高。

  1. 抽取 statement：用一个 LLM 提示词把答案拆开。论文给出的提示词是："Given a question and answer, create one or more statements from each sentence in the given answer."
  2. 逐条验证：把上下文和 statement 列表一起给 LLM，要求判断每条 statement 是否被上下文支持，先给简短解释再给 Yes/No。

WikiEval 与吻合度

3

论文自建了 WikiEval 数据集：选取 50 个涵盖 2022 年初以来事件的维基百科页面，由两名标注员对三个维度标注。Faithfulness 的标注方式是让标注员比较两个候选答案，其中一个带上下文生成、一个不带上下文生成，选出更忠实的那个。标注员一致率：Faithfulness 和 Context Relevance 约 95%，Answer Relevance 约 90%。

论文表 1 报告各方法与人工判断的吻合准确率：

方法 Faithfulness Answer Relevance Context Relevance
Ragas 0.95 0.78 0.70
GPT Score（让 ChatGPT 直接打 0 到 10 分） 0.72 0.52 0.63
GPT Ranking（让 ChatGPT 直接选更优的） 0.54 0.40 0.52

读这张表要注意三点。第一，任务形式是成对比较：给两个答案，看指标是否选中人选的那个。它证明指标的相对排序能力，不证明"0.85 以上就安全"这类绝对阈值。第二，GPT Ranking 只有 0.54，接近随机，说明"直接让大模型整体评判"远不如"拆 statement 再逐条验证"。这是 Faithfulness 设计的核心价值：把一个模糊的整体判断拆成一组更容易判的小判断。第三（我的推断，论文未讨论），WikiEval 里的两个候选答案差异很大（有上下文 vs 无上下文），比线上"两个都有上下文、只差一点"的情形容易分辨，所以 0.95 不宜直接外推到细微差异的场景。

源码行为（读自 collections/faithfulness/metric.py）：

局限一：漏答不扣分3 个重点▾ 点开看本节重点
本节重点
  • Faithfulness 只统计答案里出现了的说法
  • 仅看 5 题全是 1.0，会得出"生成层完美"的错误结论
  • 答案只回答一半，只要那一半有据，就是满分

Faithfulness 只统计答案里出现了的说法。答案只回答一半，只要那一半有据，就是满分。

本库 10-15 的 RAGAS 库评测（rag/eval_ragas_report.csv，5 题）是现成例子：

题目 Faithfulness Context Recall 答案实际情况
总地图工作流有哪六个节点 1.00 0.00 答案开头写"语料中只给出了 N3–N6 四个节点，N1、N2 的内容语料中没有相关信息"
六员指的是哪六个智能体 1.00 0.00 答案写"明确提到的只有五个角色分层，第六个成员的名称与职责在语料中没有相关信息"

两道漏答题的 Faithfulness 都是满分，因为模型老实地只说了检索到的内容。病根在检索（Context Recall 为 0），Faithfulness 对此毫无反应。这类问题必须靠 Context Recall 和 Answer Correctness 发现。仅看 5 题全是 1.0，会得出"生成层完美"的错误结论。

局限二：忠于错误的上下文

3

如果检索到的片段本身是旧版本或错误的，模型原样复述它，按定义这些说法都是"被上下文支持"的，Faithfulness 不会扣分。本库的 Q004 型案例（据 RAG评测三层方法论 记录：上下文含正确值 0.45，答案却被同文档旧值 0.465 带偏）Faithfulness 为 0.667，说明只有"夹带的 1 条无据说法"被抓到，而"答成旧值"这个错误本身是否被扣分，取决于旧值是否出现在上下文里。这类错误最终要靠 Answer Correctness 暴露。该案例的原始报告 /tmp/ragas_answer_eval_report.md 已被清理，我无法复核其 claim 明细。

局限三：拒答与空答案的取值3 个重点▾ 点开看本节重点
本节重点
  • 答案是"语料中没有相关信息"时，几乎抽不出可验证的事实声明
  • 原则：拒答是一个独立的行为，要单独统计拒答率，不要用一个人为设定的 1.0 掺进 Faithfulness 的均值
  • 官方实现这时返回 NaN，也就是没有定义
3

答案是"语料中没有相关信息"时，几乎抽不出可验证的事实声明。官方实现这时返回 NaN，也就是没有定义。本库 10-10 基线脚本（rag/eval/run_baseline.py）的处理是：负例题（qtype=N）只要判定为拒答，Faithfulness 直接写死为 1.0；正例题抽取不出 claim 时也写 1.0。

后果见下一节的数字核对。原则：拒答是一个独立的行为，要单独统计拒答率，不要用一个人为设定的 1.0 掺进 Faithfulness 的均值。

局限四：粒度影响分数

3

一句话里塞三个事实，抽取时拆不拆、拆几条，都会改变分母。同一个答案在不同裁判下可能得到不同的 claim 数。答案越是"一句一事实"，分数越稳定。这也是为什么对比两个版本时必须用同一个裁判、同一套提示词。

  • 裁判能力不够、输出被截断、解析逻辑有 bug，都不会报错，只会让分数偏离

分数的每一步都是 LLM 在判断。裁判能力不够、输出被截断、解析逻辑有 bug，都不会报错，只会让分数偏离。这是本库实际踩过的，下一节展开。

本库实测与核对

实测一：10-10 基线的 28.1% 和 47.0% 都不能当 RAGAS 分数引用3 个重点▾ 点开看本节重点
本节重点
  • 所以 28.1% 不能和 RAGAS 论文或官方文档的分数直接对比
  • 结论：引用这组基线时只能说"14 条正例、自写流水线、no-rerank 配置下的 Faithfulness 为 28.1%"，并且不要引用 47.0% 的 「all」 数字
  • 注意"忠实复述无关内容"在 Faithfulness 的定义下会得高分而不是低分；低分意味着答案里出现了上下文不支持的说法
3

baseline-report-20261010.md 报告生成层 Faithfulness = 28.1%。核对后有三个口径问题：

  1. 不是 RAGAS 库算的。run_baseline.py 用的是本库自写的流水线（eval_faithfulness.py 的 extract_claims + 自写的 verify_all_claims，提示词是自己写的"YES=编号/NO=编号"格式），不是 ragas 包。所以 28.1% 不能和 RAGAS 论文或官方文档的分数直接对比。
  2. 样本数标注矛盾。报告明确写"成功跑通的正例：14 条"，28.1% 对应这 14 条；但同批产物 baseline_summary.json 把同一个 0.2811 标在 pos 组下，且 n 字段写 51。同一份汇总里的 all 组 Faithfulness = 0.4703，我重新核算：(0.2811 × 14 + 1.0 × 5) / 19 = 0.4703，说明它其实是 14 条正例加 5 条负例共 19 条的加权均值，而不是 56 条。汇总文件里的 n 是错的。
  3. 负例的 1.0 是硬编码。5 条负例的 Faithfulness 100% 来自 faith = 1.0 if refused else 0.0（run_baseline.py:159），没有经过任何裁判判断。它把 all 组均值从 28.1% 拉到了 47.0%，抬高了将近 19 个百分点，但这 19 个点反映的是"拒答了"，不是"忠实"。

结论：引用这组基线时只能说"14 条正例、自写流水线、no-rerank 配置下的 Faithfulness 为 28.1%"，并且不要引用 47.0% 的 all 数字。

这个 28.1% 的归因，报告里写的是"--no-rerank 召回了无关 chunk，LLM 把无关内容也'忠实复述'"。注意"忠实复述无关内容"在 Faithfulness 的定义下会得高分而不是低分；低分意味着答案里出现了上下文不支持的说法。所以这条归因与指标定义对不上，更可能的原因是检索到的材料不含答案、模型靠自己的知识补全，或者裁判过严（context_text[:2000] 把上下文截到 2000 字，后面的片段裁判看不到）。这是一个待验证的疑点，需要拉 claim 明细确认，本文不下结论。

实测二：自写实现里的三个静默失败口

3

读 run_baseline.py 和 eval_faithfulness.py 发现：
- extract_claims 调用 LLM 失败时 return []（eval_faithfulness.py 的异常分支），随后正例分支走到 faith = 1.0（run_baseline.py:156）。裁判一出故障，分数就变成满分。
- verify_all_claims 失败时返回全部 False，对应分数 0。方向相反，同样不报错。
- 验证时 context_text[:2000] 截断，长上下文的后半部分不参与判定，会系统性压低分数。

这三处和官方实现的取舍不同：官方在抽取不出 statement 时返回 NaN，让后续统计能把它单独剔出来并计失败率。

实测三：裁判自一致率 40% → 100%2 个重点▾ 点开看本节重点
本节重点
  • 「_g2_judge_rerun_report_20261028.md」 记录了生成层裁判 mimo-v2.6-flash 的自一致率重测
  • 对 Faithfulness 来说，"能判出 NO"恰恰是核心能力（要识别无据说法），所以这个裁判在 Faithfulness 上的可靠性目前没有被证明
3

_g2_judge_rerun_report_20261028.md 记录了生成层裁判 mimo-v2.6-flash 的自一致率重测。根因：mimo 是推理模型，推理 token 计入 max_tokens，原先设成 10，结果推理没写完配额就用光，content 为空；解析代码又把空输出一律当 NO，判定变成随机的截断结果。修复后（max_tokens 调到 2048，只解析 content 里最后一个 YES/NO，空输出记 ERROR 不计票，网络错误重试 2 次）自一致率 5/5 = 100%，准确率 5/5 = 100%。

这份报告自己写明了局限：样本只有 5 条且全部应判 YES，测不出裁判能否正确判 NO；30 次调用里仍有 1 次 finish_reason=stop 但 content 为空。对 Faithfulness 来说，"能判出 NO"恰恰是核心能力（要识别无据说法），所以这个裁判在 Faithfulness 上的可靠性目前没有被证明。

官方 collections 接口（按文档，未在本机运行）

from openai import AsyncOpenAI
from ragas.llms import llm_factory
from ragas.metrics.collections import Faithfulness

client = AsyncOpenAI(base_url="<云端 OpenAI 兼容端点>", api_key="<从环境变量读取>")
llm = llm_factory("<强模型名>", client=client)

scorer = Faithfulness(llm=llm)
result = await scorer.ascore(
    user_input="爱因斯坦在哪里、哪天出生？",
    response="Einstein was born in Germany on 20th March 1879.",
    retrieved_contexts=["Albert Einstein (born 14 March 1879) was a German-born theoretical physicist."],
)
print(result.value)   # 文档示例此类答案得 0.5；抽不出 statement 时为 nan

要点：密钥走环境变量，不写进代码或日志；裁判用云端强模型，temperature 设 0，max_tokens 留足（推理模型尤其要大）；逐条保存分数和 claim 明细，不只存均值。

3

处理 NaN、单独统计失败率、对拒答单独计数：

import math

def faithfulness(verdicts):
    """verdicts: 每条 claim 是否被上下文支持；无 claim 返回 nan，与官方实现一致"""
    if not verdicts:
        return math.nan
    return sum(verdicts) / len(verdicts)

def summarize(scores):
    ok = [s for s in scores if not math.isnan(s)]
    return {"mean": sum(ok) / len(ok) if ok else math.nan,
            "n": len(scores), "n_nan": len(scores) - len(ok)}

print(faithfulness([True, False]))        # 0.5，对应官方 Einstein 示例
print(faithfulness([]))                   # nan
print(summarize([1.0, 0.5, math.nan, 0.0]))  # {'mean': 0.5, 'n': 4, 'n_nan': 1}

用法：均值只在有效样本上算，n_nan 作为独立的健康指标一并报告（占比高说明裁判失败或拒答多，要分开看）；拒答率另算。

Faithfulness 在动库门禁里的角色是护栏：改检索、去重、换模型之后，同一份 golden set、同一个裁判、同一套提示词前后各跑一遍，逐题对比，不降才放行。注意三点：

  1. 逐题配对比较，不要只比均值。LLM 裁判有噪声，均值掩盖不了个别题的突变。
  2. 本库目前没有为 Faithfulness 标定过阈值。RAG管线现状与阈值标定.md 里只有检索和 rerank 的阈值，没有生成层指标。三层评测落地篇给出的"0.85 放行"是经验值，生产级篇的"跌超 0.05 阻断"是规则设定，二者都没有本库的校准数据支撑。采用前应先用 20 到 30 条带人工判断的样本，测出本库裁判在"有据/无据"上的实际准确率，再定线。
  3. 基线本身要先可信：先解决上面三个静默失败口，再谈对比。
