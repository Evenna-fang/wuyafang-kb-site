阈值不是拍出来的，是双端校准出来的：0.45 的 rerank 拒答线之所以维持不动，是因为它落在干净分离窗 (0.0211, 0.4943] 内——抬到 0.87 虽能拦住 Q056 这类 reranker 假阳，却会误拒 3/19 正样本，得不偿失；这类假阳该用域外第二道校验（生成端引用核查）解决，而不是动阈值。每个数字都有实测背书且回退即翻车：top_n=4 时 simple_fact R@5 仅 36%、dense_top_n=200 曾把 dist=0.28 的 wiki 挤出候选池，所以 top_n/dense_top_n 一律不动，timeout 60→180 也只是兜底（compute_score 阻塞跑完才判超时，不省一秒）。当前真正的短板不是阈值而是结构：图谱槽霸占 multi_hop top1（23 题中 20 题），把该路由 R@1 压到 1/23；R@5=R@10 是 top_k=4 下的结构性假象，R@10 不是独立指标。修法已定位待批（after_top1 档 / 判据置顶 / 剔图谱口径考核），属于布局问题而非调参问题。

为什么阈值要"双端校准"（动机与代价）

2
  • 动机（WHY）：RAG 管线的阈值（rerank 拒答线、relevance 阈值、gate 分数）不是拍出来的，而是双端校准出来的——既要拦住假阳（reranker 假相关的域外内容），又不能误拒正样本（真答案被拒答）。0.45 的 rerank 拒答线维持不动，是因为它落在干净分离窗 (0.0211, 0.4943] 内：抬到 0.87 虽能拦住 Q056 这类 reranker 假阳，却会误拒 3/19 正样本，得不偿失。单端调阈值（只看拒答率或只看通过率）必然偏科——阈值的本质是"假阳 vs 假阴"的取舍点，必须两端实测数据同时看。
  • 代价与权衡：双端校准要积累两端样本（正样本 + 域外负样本）、跑 51+ 条 e2e 评测（约 31 分钟），成本不低。但反面代价更贵：阈值拍脑袋要么"该拒的没拒"（假阳泄漏进答案），要么"不该拒的拒了"（正样本误拒，用户体验直线下降）。校准的产出是"干净分离窗"——一个阈值区间，落在里面两端都安全；找不到干净窗时才考虑加第二道校验（域外第二道校验是处理假阳的正确姿势，不是无脑抬阈值）。

核心结论

2

本地 RAG 已上线：Chroma 持久化（集合 wuyafang_kb，18085 chunks，2026-10-19 实测），bge-m3 本地 embedding（dense 1024 维 + sparse，BGEM3FlagModel 统一加载），bge-reranker-v2-m3 本地精排，生成走小米 MiMo（mimo-v2.6-flash，TokenPlan 端点）。管线为 Adaptive RAG 路由（simple_fact / multi_hop / complex_reasoning）+ 混合检索（dense top-1000 + sparse top-100 → RRF）+ CRAG 纠错环 + 全路由 rerank 门禁 + 图谱槽（graph_slot_mode）。阈值必须用下表新口径（旧 README 的 0.465 / 0.75 均已过时）。

rerank 输入修订与双端校准（2026-10-19，含审查发现的坑）

3

本轮按独立审查意见（~/.hermes/cache/scratch/claude_rerank_review.log）修订 rerank 实现：

  1. _rerank_text 改为「子块 + heading_path 拼接」只送 rerank；generate / explain 两处作答上下文改用 parent_text——若只改 rerank 侧，生成上下文会同步退化成 ~384 字子块，检索修好、作答变差（审查致命点 A5）。
  2. 单变量实测（同 query 各 3 次）：父块均 42.43s vs 子块均 28.25s，真实倍率仅 1.50x（剔除首次调用波动后约 1.1x）。「子块提速 4 倍」不成立——本库父块普遍仅 ~670 字，削短空间有限。验收线按实测定，不拍脑袋。
  3. timeout 60→180 只是兜底：compute_score 是一次性阻塞调用，超时判在跑完之后，改 timeout 不省一秒，只保证慢结果不再被白算后丢弃。
  4. threshold 0.45 双端重校（19 正 + 5 域外负，新输入下）：正端 16/19 ≥ 0.9165，低位 Q030=0.8371 / Q016=0.4943 / Q001=0.0697；负端 Q052-Q055 = 0.0026~0.0211，Q056=0.8641 是 reranker 假阳（Snowflake 问题命中 FDE交付方法论，文中并无 Snowflake 内容，语义近邻误打 0.86）。干净分离窗 (0.0211, 0.4943]，0.45 落在窗内 → 维持；抬到 0.87 虽能拦 Q056 但会误拒 3/19 正样本，得不偿失。校准数据 ~/.hermes/cache/scratch/threshold_calib_20261019.json。
  5. top_n / simple_fact_top_n / dense_top_n 一律不动（分别有 2026-10-15 召回实验、2026-10-14 挤出实验背书）——这是方案作者没读 config 修复史注释最容易踩的回退坑。
  6. 冷测验证（--no-gen）：正例 simple_fact rerank 47.1s / best=0.9878 放行；正例 multi_hop rerank 52.7s / best=0.9914、图谱槽按 multi_hop_only 置 #1；域外"咖啡机除垢剂" best=0.0004 被 gate 拒答。三条均 exit 0。

  • 改任何阈值前先跑双端校准，别拍数字：现行值全在 rag/config.yaml——retrieval.dist_threshold: 0.60、gate.dense_threshold: 0.50、rerank.threshold: 0.45（干净分离窗 (0.0211, 0.4943]）、rerank.top_n: 30、rerank.timeout: 180.0、rrf_k: 60、source_max_per_query: 3；改后同命令重跑 cd rag/eval && python3 -u _e2e_eval.py --json-out /tmp/e2e_new.json 与基线 eval/e2e_final.json 逐项对比。
  • 图谱槽布局问题的验证/回退（本条目“修法已定位”部分的落地）：

    回退开关全在 config 一行：graph_slot_mode: multi_hop_only（恢复旧置顶）/ linked_chunk.enabled: false / high_key.enabled: false，不用回滚代码。
