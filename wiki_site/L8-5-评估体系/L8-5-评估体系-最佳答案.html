评测体系不是 RAG 的附属品而是产品地基——没有稳健评测系统的 LLM 产品几乎必然失败，这是 Hamel 一手结论而非行业传闻。 评测必须把检索失败和生成失败拆开测（只测端到端分会放过"检索变差但生成变强"的对消），并按 Hamel 三级（单元断言→人工+模型评测→线上 A/B）配节奏：断言每次跑、模型评测按周、A/B 只在重大变更。落地的最小闭环是"golden set（50-200 条含生产失败）+ 检索/生成分层指标 + LLM judge 与人工对齐"，缺任何一环的评测系统只是跑分脚本。

WHY：这个能力域为什么重要

2

Hamel Husain 的判断："不成功的 LLM 产品几乎都有同一个根因——没建起稳健的评测系统"。大部分团队把精力全花在改 prompt/改代码（迭代）上，跳过了"评测"和"调试看数据"两环。对 RAG 来说，评测必须把检索失败和生成失败拆开测——只测端到端分数的管线，会把"检索变差但生成变强"的对消变化放过去。MIT 数据：95% 企业 AI pilot 无可测回报——差异在工作流逻辑 / guardrails / retrieval architecture / audit layer。

Hamel 三级评测体系

3
级别 是什么 节奏 成本
Level 1: 单元测试 代码断言（pytest 风格）：输出不含 UUID 的正则断言、格式校验 每次代码变更都跑 最低
Level 2: 人工 + 模型评测 先记 trace → 人看数据标 good/bad（二元）→ LLM judge 自动化并对齐人工 按固定节奏（如每周），覆盖全部测试用例 + 生产采样 中
Level 3: A/B 测试 线上实验，验证 AI 改动是否真驱动了用户行为/业务结果 只在重大产品变更后 最高

关键操作细节（Hamel 一手）：
- 断言要按「feature × scenario」组织，不是按代码函数组织
- 测试用例可以 LLM 合成，但执行后断言真实结果
- 通过率 100% 不是目标——pass rate 是产品决策，取决于你能容忍哪些失败
- 二元标注优于打分：good/bad 比 1–5 分好管得多
- LLM judge 要用你能负担的最强模型，且它是"元问题"——必须维护迷你评测系统持续追踪 judge 与人的对齐度；类别不平衡时别用 raw agreement，要用 precision/recall 分开看
- 停止条件：一直读 trace 到"不再学到新东西"；成熟系统每两周复盘 10–20 条离群 trace
- 错误分析频次计数：spreadsheet 每行一条对话写开放式笔记 → LLM 归纳失败分类法 → 每行贴标签 → 按频次排序修复（NurtureBoss 案例：日期处理成功率 33%→95%）

RAG 评测三层方法论3 个重点▾ 点开看本节重点
本节重点
  • 关键认知：找到 ≠ 答对
  • 结论：检索命中是必要非充分条件
  • 只看 Recall@5 会系统性高估 RAG 端到端质量 7.5~20 个百分点
3
层 指标 测什么
检索层 Context Recall / Context Precision / Context Relevance 找得全不全、排得准不准
生成层 Faithfulness / Answer Relevancy 答案忠不忠于上下文、切不切题（不编造）
端到端 Answer Correctness / Answer Similarity 答案最终对不对

最小充分集 = 6 指标：Context Recall + Context Precision + Context Relevance + Faithfulness + Answer Relevancy + Answer Correctness。

关键认知：找到 ≠ 答对。 本地实测（5 条 golden-q 真跑）：
- 检索层 Recall@5 = 100%（全命中）
- 端到端 answer_correctness = 0.787，严格答对率 = 80%
- 同题内差 20 个百分点
- 典型失败 Q004：检索 top-5 已含正确值 0.45，但生成层被同文档旧值 0.465 带偏，答成 0.465，且夹带 1 条 context 无据的幻觉 claim（faithfulness=0.667）

结论：检索命中是必要非充分条件。只看 Recall@5 会系统性高估 RAG 端到端质量 7.5~20 个百分点。

指标机制详解

3
指标 计算方式
Faithfulness 被 context 支持的 claims / 答案总 claims（LLM 拆句→逐条 NLI 判）
Answer Relevancy LLM 从答案反推 N 个问题，算与原问题 embedding 余弦相似度均值
Context Recall 被检索 context 覆盖的参考句数 / 参考句总数（需 ground truth）
Context Precision 相关 chunk 的加权 precision@k（测排序质量）
Answer Correctness 0.75×F1事实重合 + 0.25×语义相似度
Recall@k top-k 命中相关文档数 / 相关文档总数（行业经验目标 0.80+）
MRR@k 首个命中位置的倒数均值

据[一手源]：raw/rag-arch/RAG业内最高标准-20261009.md（RAGAS 官方 docs 逐字核对）：最小充分集之外还有四个官方指标可按需加。Context Relevance 由 LLM 直接判断每个 chunk 与 query 是否相关取均值，无需 ground truth（所以线上流量也能跑，检索层唯一的 reference-free 指标）；Noise Sensitivity 通过打乱/删除 context chunk 后重新生成，看答案正确性下降幅度，量"生成对检索噪声有多敏感"；Topic Adherence 判答案是否停留在预定义主题清单内，算命中率；Hallucination = 1 − 不受支持 claims / 总 claims，是无 ground truth 版的忠实度判据。版本变迁：context_entities_precision 在 RAGAS v0.2 移除，被 LLM-based 的 context_precision/recall 取代，旧教程里的指标名要先对版本。

评测工具栈

3
工具 角色
DeepEval pytest-based CI gate，拦 PR 回归（golden-question 套件）
RAGAS scheduled job 采样生产流量，算 faithfulness / context precision / answer relevance，监控 drift
Langfuse 捕获生产 trace（question / retrieved context / answer / metadata）
LangSmith 离线评测（curated dataset，像 LLM 应用的单元测试）+ 在线评测（生产流量实时打分）

LangSmith 评测器类型：启发式/代码断言（快但覆盖窄）、LLM-as-judge（可自定义 criteria）、Pairwise 对比（比单独打分区分度高得多——单标准打分对两个模型常常拉不开差距，成对比较才能看出偏好）、人工 annotation queue。

from ragas.llms import LangchainLLMWrapper
from ragas.metrics import LLMContextRecall, Faithfulness, FactualCorrectness
from langchain_openai import ChatOpenAI

result = evaluate(

    llm=evaluator_llm,

- 无错误分析制度（Hamel 最高 ROI 的一步：人工看 trace 做频次分类）
