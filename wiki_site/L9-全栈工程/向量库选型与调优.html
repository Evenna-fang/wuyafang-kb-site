RAG 向量检索：选型、过滤、混合检索与可复现调优

RAG 答不上来时，向量库只是候选原因。数据清洗失败、chunk 切断语义、embedding 与业务语言不匹配、过滤把候选筛空、生成端拿到太多噪声，都能表现为“检索不行”。书籍把数据准备、向量库创建、检索与生成协同调优放在连续章节，课件也把向量存储放在摄取管道中，而不是孤立 benchmark，这说明优化对象应是整条检索链。

旧文里的固定规模上限、统一 p95 延迟和“100k 行就必须建某索引”不能作为通用事实：结果随维度、数据分布、过滤选择性、硬件、并发和参数改变。正确问题是：

  1. 在自家 golden set 上，Recall@k、nDCG/MRR 与答案忠实度是否提高？
  2. 在业务过滤条件和并发下，p95/p99 是否仍满足 SLO？
  3. 新增一套数据库的备份、权限、升级、监控成本是否值得？
  4. 是否必须近似索引？pgvector 默认精确检索提供完全召回，近似索引是用部分召回换速度。

HNSW、IVFFlat 与过滤的真实语义3 个重点▾ 点开看本节重点
本节重点
  • HNSW：图索引；官方口径是相对 IVFFlat 有更好的速度—召回权衡，但构建更慢、内存更多，可在空表上创建
  • IVFFlat：倒聚类索引；构建更快、内存更少，但查询性能/召回权衡通常较弱
  • 应在表已有数据后建索引，并用代表性数据选择 lists、查询时调 probes
3
  • HNSW：图索引；官方口径是相对 IVFFlat 有更好的速度—召回权衡，但构建更慢、内存更多，可在空表上创建。
  • IVFFlat：倒聚类索引；构建更快、内存更少，但查询性能/召回权衡通常较弱。应在表已有数据后建索引，并用代表性数据选择 lists、查询时调 probes。
  • 过滤发生在近似索引扫描之后：若只扫描少量候选再按 tenant/category 过滤，返回数可能少于 LIMIT。pgvector 0.8.0 起可用 iterative index scans 继续扫描。
  • strict_order 保证距离顺序；relaxed_order 允许轻微乱序以提高召回，需要严格顺序时可按官方建议用 materialized CTE 再排序。iterative scan 会访问更多 tuple，必须同时测延迟和召回，不能只开参数就宣布修好。
  • 过滤值种类少时考虑部分索引；租户种类多时考虑分区。先给普通过滤列建 B-tree/GIN 等索引，也可能让 PostgreSQL 选择精确检索路径。

混合检索与重排不是同一步

3
  • 语义检索适合同义表达；全文检索保留专有名词、编号和精确词项。
  • RRF 只使用各路排名，不直接比较余弦距离与 BM25/FTS 原始分数：单篇得分可写为 Σ weight_i / (k + rank_i)。k 是平滑参数，不是召回文档数。
  • “大候选 → RRF → rerank → 少量上下文”把召回率与最终上下文预算分开。rerank 后的 top-n 应通过 golden set 和成本共同决定，不预设 3、4 或 8 永远最好。

论文证据怎样改变评估口径

3

《How Ground Truth Shapes Retrieval Scores》（arXiv:2610.31606）在一个小型临床 RAG 开发集上，将证据 span 映射到所有包含该证据的 chunk；扩充标注后，被接受的相关 chunk 目标从 36 增至 51，而检索排名并未改变。作者同时明确样本小、标注受检索结果影响，需要独立验证。论文不是证明“384 token + 20% overlap 普遍最佳”，而是证明 Recall、MRR、nDCG 会被 ground-truth 覆盖方式改变。

我们的落地规则因此改成：先标证据 span，再生成所有等价相关 chunk；保留标注版本与检索快照；由未参与调参的人复核证据充分性；调 chunk、混合检索和 rerank 时固定同一标注版本。报告指标必须附 golden set 规模和覆盖方式，不能把标注扩充造成的分数变化误报为算法提升。

以下示例以 1024 维 embedding 为例；实际维度必须和模型输出一致：

CREATE EXTENSION IF NOT EXISTS vector;

CREATE TABLE documents (
  id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  tenant_id bigint NOT NULL,
  content text NOT NULL,
  embedding vector(1024) NOT NULL,
  fts tsvector GENERATED ALWAYS AS (to_tsvector('simple', content)) STORED
);

CREATE INDEX documents_embedding_hnsw
  ON documents USING hnsw (embedding vector_cosine_ops);
CREATE INDEX documents_fts_gin ON documents USING gin (fts);
CREATE INDEX documents_tenant_idx ON documents (tenant_id);

先灌入代表性数据、建索引并刷新统计信息。语义查询示例（$1 为 query embedding，$2 为 tenant）：

SET hnsw.iterative_scan = relaxed_order;
SET hnsw.max_scan_tuples = 20000;  -- 官方默认值示例，不是调优目标

WITH nearest AS MATERIALIZED (
  SELECT id, content, embedding <=> $1 AS distance
  FROM documents
  WHERE tenant_id = $2
  ORDER BY embedding <=> $1
  LIMIT 20
)
SELECT id, content, distance
FROM nearest
ORDER BY distance;

权限过滤不能只藏在应用代码里：多租户场景同时考虑 PostgreSQL RLS，并用“ tenant A 的凭证查询 tenant B 专属文档”做负例，确保引用与 chunk 都不会泄露。

2. 用 RRF 合并两路排名

3 
def reciprocal_rank_fusion(rankings, k=60):
    """rankings: [[doc_id, ...], ...]；只融合排名，不混合异构原始分。"""
    scores = {}
    for ranking in rankings:
        for rank, doc_id in enumerate(ranking, start=1):
            scores[doc_id] = scores.get(doc_id, 0.0) + 1.0 / (k + rank)
    return sorted(scores, key=scores.get, reverse=True)

执行顺序：关键词取 20～50 个候选、语义取 20～50 个候选 → RRF → 可选 cross-encoder rerank → 只把最终 top-n 送进生成器。候选数和 k 都是待网格搜索变量；每次实验记录 embedding 版本、chunk 版本、索引参数和数据快照。

def recall_at_k(golden):
    """golden: [(ranked_doc_ids, relevant_doc_id_set), ...]"""
    hits = [bool(set(ids) & relevant) for ids, relevant in golden]
    return sum(hits) / len(hits) if hits else 0.0

同一批数据依次比较：精确检索基线、HNSW 默认参数、调参后的 HNSW、混合检索、混合 + rerank。报告 Recall@k、MRR/nDCG、p50/p95/p99、最终上下文 token；生成侧另测 faithfulness，避免“召回提高所以答案一定更好”的假推断。

4. 用业务负载做迁移决策

3 
固定数据快照与查询集
  → 单并发测正确性/召回
  → 逐步提升到生产峰值并发
  → 加入真实 tenant/category 过滤与最长向量维度
  → 记录 p95/p99、CPU、内存、索引构建时间
  → 加备份恢复与节点故障演练
  → 只有质量或 SLO 明显收益覆盖迁移成本时才换库

不引用厂商“快 N 倍”作为验收值；不同 benchmark 的维度、距离、过滤和并发不可比。上线后保留失败 query，经人工确认 relevant 文档再回流 golden set。

5. 把检索链做成可交付的文档问答项目

3

原《项目实战—RAG 问答》的价值在于给出上传、父子分块、会话、引用和删除的完整业务闭环；其中固定 P95、固定 Top-K、模型切换收益和“代码已验证”的表述不作为本机实测结论保留。最终项目只采用下面的可验收路线，示例均未在本轮启动数据库或模型实跑。

功能与数据契约：文档表保存 document_id/tenant_id/source_uri/version/status；chunk 表保存 chunk_id/document_id/parent_id/content/embedding/metadata。子块负责召回，父块负责提供完整上下文；所有父子行都带租户与文档版本。删除文档时同事务删除元数据和向量行，对象存储原文另按生命周期删除，避免“列表已删但向量仍可检索”。

rag-doc-assistant/
├── app/api.py                 # 上传、问答、删除；鉴权与输入上限
├── app/ingest.py              # 解析、父子分块、embedding、批量写入
├── app/retrieve.py            # 租户过滤、混合召回、RRF、可选 rerank
├── app/generate.py            # 仅依据上下文生成，返回引用 ID
├── sql/schema.sql             # pgvector 表、索引、RLS
├── tests/golden.jsonl         # 证据 span 与 relevant chunk 标注
└── tests/test_permissions.py  # 跨租户与删除后检索负例

  1. ** ingestion 先落证据关系**：解析 PDF/DOCX/TXT 后按标题、段落和条款边界切父块，再切子块；每个子块保存 parent_id 与原文页码/偏移。embedding 模型和维度写入数据版本，入库与查询必须使用同一模型 revision。
  2. 问答先检索、后生成：两路各取候选，RRF 后可选 rerank；按最终 parent_id 去重回捞父块。上下文只包含当前租户、当前文档版本；模型输出引用 chunk_id，API 再校验这些 ID 确实属于本次已授权候选。
  3. 无答案与删除是主流程：检索低于经校准的阈值时返回“不确定/需要补充材料”，不硬答。删除后用被删文档的独有编号再查一次，候选、答案和引用都不得出现该编号。
  4. 验收用同一套证据链：先跑 schema 和权限负例，再跑 Recall@k/MRR/nDCG，最后跑 faithfulness 与端到端引用正确性；记录 p95、最终上下文 token 和每成功任务成本。任何“Top-K 降低成本”的结论必须同时给出质量变化。

最小端到端检查不是 curl 返回 200，而是：上传一份含独有编号的文档 → 提问能返回正确编号与引用 → 用另一租户身份查不到 → 删除后原租户也查不到。上述四步本轮未实跑，是交付时的功能验收脚本口径。

    | 后端 | 位置 | 特点 |
    |---|---|---|
    | Chroma（本地） | rag/query.py L2593 chromadb.PersistentClient(path=index_dir) | 索引 1.3G 落盘，离线可用 |

    配置 rag/config.yaml 的 cloud.enabled: true，凭证走环境变量名（ZILLIZ_URI/ZILLIZ_TOKEN），代码里不落 key。
  • 选型的最实际判据是「能不能不连网就检索」：cloud_backend.py 的模块 docstring 写的是「替代本地 Chroma+bge-m3, 把检索算力搬到云端, 省本地约2GB内存」——换向量库的第一驱动力是内存，不是性能。
  • 本地调优在本库集中在四行配置（rag/config.yaml 检索段）：dense_top_n: 1000、sparse_top_n: 100、top_k: 4、source_max_per_query: 3。dense 召回放到 1000 是拿事故换的（注释：「之前 dense_top_n=200 时 chroma 内部返回 top-200 dist 下限=0.496，把真实 dist=0.28 的 wiki 挤出」）。
    向量库的「候选池」参数会改变「最终看到的距离分布」，调它必须重看门禁阈值。
  • 和课件讲法的差异：课件对比 Milvus/pgvector/Chroma 多讲 HNSW 参数与 QPS；本库的调优笔记全是「召回池大小 + 层权重 + 门禁阈值」这三者的联动。
  • 本库暂无：没有 Zilliz 与本地 Chroma 的 A/B 结果落盘（verify_cloud_ingest.py 存在，但没有结果文件进库），也没有 HNSW 参数调优记录。
