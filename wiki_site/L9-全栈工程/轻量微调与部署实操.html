很多“模型不懂业务”的问题其实是知识缺失、检索失败或输出没有约束。微调擅长学习稳定的格式、语气、任务映射和行为模式；不适合充当需要频繁更新、逐条溯源的知识库。先用 prompt + few-shot 和 RAG 建基线，只有错误稳定复现且属于可学习行为时，微调才有明确收益。

训练 loss 下降也不等于业务变好：模型可能记住模板、损害通用能力，或在训练集格式上过拟合。课件把模型推理效果评估单列为框架，书籍的公开划线还提醒“只调 rank 并不存在普适最优值”。因此必须否定旧文中“r=16 是通用阈值”“1000 条一定胜过多少条”“某格式必然快 N 倍”这类绝对口径。

微调与部署必须共用一个验收集：基座、adapter/合并模型、量化后模型都在同一批 held-out 任务上比较。否则训练得到的提升可能在量化或推理引擎切换时消失。

方法 更新对象与显存特征 适用与主要风险
Prompt/few-shot/RAG 不更新权重 先建基线；知识需更新/溯源时优先
LoRA 冻结基座，训练低秩 adapter；仍需保存基座与反向激活 稳定行为/格式；多 adapter 易管理

r、lora_alpha、target modules、学习率与 epoch 都是待验证超参，不是跨模型定律。先用小数据和短训练暴露格式/显存问题，再扩大；保留独立验证集和通用能力回归集。

2. 数据契约比样本截图更重要

3

每条 conversational 样本统一为：

{"messages":[{"role":"system","content":"按指定JSON格式回答"},{"role":"user","content":"业务输入"},{"role":"assistant","content":"{\"label\":\"...\",\"evidence\":\"...\"}"}]}
  • 使用基座对应的 chat template；不要一部分样本手工拼特殊 token，另一部分由 Trainer 自动套模板。
  • train/validation/test 按文档、用户或时间去重分组，避免同一源文切块同时出现在训练与测试造成泄漏。
  • 覆盖正常、边界、拒答、无答案和安全负例；输出格式必须可被确定性 parser 校验。
  • 保存数据版本、来源授权、清洗规则和样本哈希；训练代码、依赖、基座 revision、随机种子一并记录。

论文怎么说 → 我们怎么用：AutoSFT（arXiv:2610.22194）把 SFT 数据研究拆成比例调整、剪枝、修复、替换和合成等动作，并在每轮从同一基座重新训练以归因各组件收益。论文说明“自动改数据”需要多种动作与受控对照，不说明多 Agent 在任何数据集都必然增益。我们的数据流水线相应保留 proportion/prune/repair/replace/synthesize 五类变更记录；每轮固定基座、训练器和预算，只改一类数据动作，使用同一 held-out 集比较，禁止一边改数据一边换基座再把收益记给清洗策略。

2. QLoRA + TRL 训练模板

3 
import torch
from datasets import load_dataset
from peft import LoraConfig
from transformers import AutoModelForCausalLM, AutoTokenizer, BitsAndBytesConfig
from trl import SFTConfig, SFTTrainer

BASE = '你的基座模型或本地路径'  # 生产固定到已审核 revision
OUT = './artifacts/qloora-adapter'

tokenizer = AutoTokenizer.from_pretrained(BASE)
quant = BitsAndBytesConfig(
    load_in_4bit=True,
    bnb_4bit_quant_type='nf4',
    bnb_4bit_compute_dtype=torch.bfloat16,
)
model = AutoModelForCausalLM.from_pretrained(
    BASE,
    quantization_config=quant,
    device_map='auto',
)
peft = LoraConfig(
    r=16,                       # 起点，不是通用最优值
    lora_alpha=32,
    lora_dropout=0.05,
    target_modules=['q_proj', 'k_proj', 'v_proj', 'o_proj'],
    task_type='CAUSAL_LM',
)
args = SFTConfig(
    output_dir=OUT,
    per_device_train_batch_size=1,
    gradient_accumulation_steps=8,
    learning_rate=2e-4,
    num_train_epochs=1,
    logging_steps=10,
    eval_strategy='steps',
    eval_steps=50,
    save_strategy='steps',
    save_total_limit=2,
    report_to=[],
    seed=42,
)
ds = load_dataset('json', data_files={
    'train': 'train.jsonl', 'validation': 'validation.jsonl'})
trainer = SFTTrainer(
    model=model,
    args=args,
    train_dataset=ds['train'],
    eval_dataset=ds['validation'],
    peft_config=peft,
    processing_class=tokenizer,
)
trainer.train()
trainer.save_model(OUT)       # 默认保存 adapter；不是完整合并模型
tokenizer.save_pretrained(OUT)

不同 TRL 版本对数据列、chat template、评估参数有差异。若安装版本与示例不一致，先运行 python -c "import inspect; from trl import SFTConfig,SFTTrainer; print(inspect.signature(SFTConfig)); print(inspect.signature(SFTTrainer))" 并按官方对应版本文档调整，不静默猜参数。

合并 adapter 时不要用仍量化加载的训练对象硬合并。常见做法是以合适精度重新加载基座，再加载 PeftModel adapter、执行 merge_and_unload()、保存合并模型与 tokenizer，并重新跑结构/生成冒烟；也可以保留基座 + adapter 部署以减少重复权重。

固定同一测试集、上下文、解码参数和 judge 版本：

对照 必看指标 阻断条件示例
基座 vs adapter 任务正确率、格式通过率、指令遵循、拒答 目标任务无显著提升则不进入部署
adapter vs 通用回归 通用问答、安全、多语言/长上下文 关键能力明显下降则回滚
合并模型 vs adapter 输出一致性与格式 合并引入异常则保留 adapter 路线
高精度 vs 量化 上述全部 + TTFT/TPOT/显存 质量损失超过业务容忍度则换量化方案

LLM judge 只负责开放质量维度；JSON、数值、引用 ID 和分类标签优先用确定性代码。人工抽查必须覆盖 judge 高分但答案错误的样本，防止假绿。

4. 部署并做端到端压测

pip install vllm
vllm serve ./artifacts/merged \
  --max-model-len 4096 \
  --gpu-memory-utilization 0.9 \
  --port 8000

curl http://127.0.0.1:8000/v1/chat/completions \
  -H 'Content-Type: application/json' \

随后按《安全、容量压测与成本治理》中的 vllm bench serve 流程，使用业务真实输入输出长度逐级加压，记录 p95/p99 TTFT/TPOT、goodput、KV 和失败率。保留上一版模型与配置，流量切换后仍能回滚。

上线检查：模型/adapter/数据 revision 可追踪；chat template 一致；测试无泄漏；量化质量回归通过；服务健康检查、超时、取消、日志脱敏和容量门禁均已实测。未满足时只能说“训练脚本完成”，不能说“模型可生产交付”。

若评估 speculative decoding，不能只看 accepted tokens/round。《Acceptance Is Not Speed》（arXiv:2610.23818）在其实验的 relaxed/lossy 设置中发现接受率提高伴随输出变长，墙面时间与准确率未必受益。我们将完成长度、verifier rounds、端到端 wall-clock、任务准确率和 SLO 内 goodput 一起纳入部署对照；lossless 与 lossy 验证分开报告，不用单一接受率宣称部署提速。
