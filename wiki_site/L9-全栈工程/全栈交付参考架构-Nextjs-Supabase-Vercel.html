WHY：为什么两周交付需要一套收敛的默认栈

2

2026 年"两周给客户交付一个带 RAG 与引用来源的 AI 应用"已有一套收敛的默认栈：Next.js App Router + Vercel AI SDK useChat + Vercel Functions（Fluid compute）+ 同区域向量库（Supabase Postgres/pgvector）+ 按用户权限过滤检索（Vercel 官方 KB 的生产 RAG 三层）。三个选型判断最值得记住：其一，语言分工已定型——Python 管训练/研究/数据管线，TypeScript 管生产应用与 UI，Vercel AI SDK 是这套栈的事实默认（GitHub 约 23.6k stars、614+ 贡献者）；其二，向量层用 pgvector 而不是专用向量库——已在 Postgres 上就别引入新组件，Supabase 把 Postgres + pgvector + Auth + Storage 打包，交付现场少装三个组件；其三，结构化输出一律 Zod inputSchema，不用 JSON mode。真正的坑在版本与检索细节：AI SDK v7 于 2026-06-25 发布、要求 Node 22+ 与 ESM，v4→v5→v7 每一跳都有破坏性变更（v5 改了 inputSchema/stopWhen 词汇，useChat 不再管理输入状态），所以客户项目必须先钉版本再抄文档；向量侧 100k+ 行就必须建 HNSW 索引，且带过滤的向量查询在 pgvector 0.8.0 起有 iterative scan 的延迟代价，开之前先测。

三、可跑代码骨架（官方 cookbook 形态）

3

建表与索引（100k+ 行就必须建索引）：

create extension vector;
create table embeddings (
  id bigserial primary key,
  content text,                 -- 文本 chunk
  embedding vector(1536)        -- 与所选 embedding 模型维度一致
);
create index on embeddings using hnsw (embedding vector_cosine_ops);

切块 + 批量 embedding（官方 embedMany；示例按句切块，生产要换成 token 级/分层切块）：

import { embedMany } from 'ai';
const embeddingModel = 'openai/text-embedding-ada-002';   // 示例；生产换成你的模型
const generateChunks = (input: string): string[] =>
  input.trim().split('.').filter(i => i !== '');
export const generateEmbeddings = async (value: string) => {
  const chunks = generateChunks(value);
  const { embeddings } = await embedMany({ model: embeddingModel, values: chunks });
  return embeddings.map((e, i) => ({ content: chunks[i], embedding: e }));
};

检索（Drizzle 写法，1 - cosineDistance 即相似度，阈值 0.5 是示例值）：

import { cosineDistance, desc, gt, sql } from 'drizzle-orm';
const similarity = sql<number>`1 - (${cosineDistance(embeddings.embedding, userQueryEmbedded)})`;
const results = await db.select({ name: embeddings.content, similarity })
  .from(embeddings)
  .where(gt(similarity, 0.5))
  .orderBy(t => desc(t.similarity))
  .limit(4);

Supabase 侧等价物（官方 match_documents SQL 函数）：

select * from documents
where documents.embedding <=> query_embedding < 1 - match_threshold
order by documents.embedding <=> query_embedding asc
limit least(match_count, 200);

流式生成 route handler：

// app/api/chat/route.ts
import { streamText, tool } from 'ai';
import { z } from 'zod';
export async function POST(req: Request) {
  const { messages } = await req.json();
  const result = streamText({
    model: /* provider model */,
    system: '仅根据提供的上下文回答。',
    messages,
    tools: {
      getInformation: tool({
        description: '从知识库检索相关信息',
        inputSchema: z.object({ query: z.string() }),   // v5+ 用 inputSchema
        execute: async ({ query }) => findRelevantContent(query),
      }),
    },
    stopWhen: ({ stepCountIs }) => stepCountIs(5),       // v5+：控制 agent 循环上限
  });
  return result.toUIMessageStreamResponse();
}

Hybrid 检索升级（Supabase 官方 hybrid_search：FTS(GIN) + 语义(HNSW) 两路 → RRF 融合，rrf_k 默认 50）：

create or replace function hybrid_search(
  query_text text, query_embedding vector, match_count int,
  full_text_weight float = 1, semantic_weight float = 1, rrf_k int = 50
) returns setof documents language sql as $$
  with full_text as ( ... ts_rank_cd ... ),          -- 关键词 CTE（GIN 索引 on fts）
       semantic as ( ... embedding <=> ... limit ... ) -- 语义 CTE（HNSW 索引）
  select ... 1.0 / (rrf_k + rank) 融合 ...
$$;
create index on documents using gin(fts);
create index on documents using hnsw (embedding vector_ip_ops);
四、生产检查清单（交付验收用）3 个重点▾ 点开看本节重点
本节重点
  • 建 HNSW 索引（生产默认；IVFFlat 只在 build 内存受限/静态数据时选）
  • 「maxDuration」 按最长答案配（Fluid 默认 300s / Pro 800s），长天花板必须配上游 abort，否则卡住的 provider 流会占住请求
  • 混合检索：FTS(GIN) + 语义(HNSW) → RRF，权重可调
3

检索质量
- 建 HNSW 索引（生产默认；IVFFlat 只在 build 内存受限/静态数据时选）。
- 过滤 + HNSW 的坑：选择性 filter 会让 HNSW 返回不足 match_count 条——pgvector 0.8.0 起开 iterative index scan（hnsw.iterative_scan 取 strict_order 或 relaxed_order，hnsw.max_scan_tuples 默认 20,000）；strict_order 保序但更慢（AWS 实测：过滤查询从 20ms → 197ms，开之前先测延迟）。
- 混合检索：FTS(GIN) + 语义(HNSW) → RRF，权重可调。
- 检索权限隔离：按请求者权限 scoping，别让用户拿到他打不开的文档引用。

流式与超时
- 每一跳（反代/CDN）关缓冲。
- maxDuration 按最长答案配（Fluid 默认 300s / Pro 800s），长天花板必须配上游 abort，否则卡住的 provider 流会占住请求。
- 首字节前错误走 HTTP 状态码，首字节后错误走 stream error event，保留部分文本。

结构化与工具
- Zod inputSchema 做结构化输出与工具入参校验，不用 JSON mode。
- stopWhen 给 agent 循环设硬上限防 runaway（v5+；v6 默认 stepCountIs(20)）。

模型接入与账单
- AI Gateway：单 key、按列表价无 markup、BYOK 同价、自动 fallback（故障转移到同模型的另一 provider）。
- 成本归因按 gen_ai.* span 属性记。

评测门禁
- golden set 50+ 条，检索侧 Recall@k 与生成侧 faithfulness 分别 gate。

五、与本库（Chroma + bge-m3）现状对照

3
栈环节 本库对应 异同
向量存储 Chroma（rag/index/chroma.sqlite3，bge-m3 1024 维 dense+sparse） 交付栈用 Postgres/pgvector：多租户权限（RLS）、事务、SQL 生态是 Chroma 没有的；本库单机单用户场景 Chroma 够用
检索 Python 侧 dense(20)+sparse(20) → RRF → bge-reranker(阈值 0.45) Supabase hybrid_search 是 SQL 侧 FTS+语义 → RRF(k=50)，同构可对照；本库多了 rerank 一步（交付栈可用 pgvector + 外部 rerank 补齐）
切块 384/80 分层（parent/child）+ contextual 前缀 官方 cookbook 示例是按句切块（示例级）；交付时要上本库的分层方案
前端/流式 无（本库是离线管线 + query.py CLI） 交付栈补齐 UI 层；useChat parts + source-url 引用是交付演示的加分项
成本 模型路由/步级档位（省 Token 三件套） 交付栈侧对应 AI Gateway 统一账单 + OTel span 记账
评测 golden-q 26 条只测检索 交付验收需要双侧门禁——当前本库还没有生成侧评测
