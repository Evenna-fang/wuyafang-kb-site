Agent 项目实战：有界多智能体、MCP 工具与可验证交付

本篇重写原《项目实战—Agent 智能体》。课件提供 LangGraph + MCP 内容生成原型，书籍摘录用于工具安全、状态和生产运维框架，论文补足记忆与“任务成功但产生副作用”的评测盲区。下列代码与命令均为实施模板，本轮未安装依赖、未连接真实模型/搜索服务、未启动 MCP 或 LangGraph，全部未实跑。

WHY：为什么“多角色能跑”仍不是可交付 Agent

2
  1. 突破单轮问答：RAG 只"检索+回答"，Agent 能规划、拆解任务、调用外部工具、多步推理，处理"查资料→分析→产出→自检"这类复合任务。
  2. 工具即能力：通过 MCP/Tool Calling 把搜索、数据库、API、文件系统接进来，让大模型从"会说"变"会做"。
  3. 多智能体分工提质量：研究/分析/写作/审核各司其职，审核环节带评分与重写，形成自我纠错闭环，显著降低幻觉与跑题。
  4. 协议标准化：MCP 统一工具接入、A2A 统一智能体间通信，工具与智能体可复用、可插拔，工程上可长期演进。
  5. 跨行业通用：客服、办公、数据分析、内容生产、面试、旅行规划……凡"目标可拆解、步骤可工具化"的场景都能套用。

旧稿把“多智能体分工”直接写成质量提升，这在没有对照实验时证据不足。多角色会增加模型往返、提示词注入面、状态交接和成本；如果单个 Agent + 确定性工具已能完成，就不应为展示架构而拆成五个角色。真正需要解决的是：每一步是否有结构化输入输出，循环是否有预算，工具是否最小权限，失败是否可恢复，最终是否同时通过任务正确性与无副作用测试。

WHAT / WHYT：系统是什么，何时用/不用

2

一个能自主规划、调用工具、多角色协作完成复杂任务的智能体系统。以课件中可直接复现的 多智能体内容生成系统（LangGraph + MCP + FastMCP）为主干：用户给一句需求（如"写一篇 AI 发展趋势文章"），系统自动走完 意图识别 → 研究（联网搜索）→ 分析 → 写作 → 审核（不达标重写） 的完整流水线，输出高质量成果。

同一套骨架在项目库里有多种行业形态：
- 智扫通 / ReAct 智能客服（To C 扫地机器人客服，博学谷）——ReAct + RAG 工具 + 报告生成；
- SmartVoyage 旅行智能助手（博学谷）——A2A 协议多智能体 + MCP 工具服务器 + LLM 路由；
- HeiMaClaw / AgentCenter 智能体服务中台（黑马）——Routing Agent、Tool Calling、A2A/MCP 协议、会话记忆；
- 基于 Coze 的智能面试助手（低代码快速落地）。

本篇覆盖代码框架（LangGraph+MCP） 与 低代码平台（Coze/Dify） 两条落地路线，做到"看完能复现一个多智能体 Agent"。

适用边界与相似概念区别

3
  • RAG 与 Agent：RAG 负责找到并引用知识；Agent 负责选择步骤和调用工具。只需文档问答时不应强行加 Agent。
  • 工作流与自主 Agent：本项目的研究→分析→写作→审核主要是显式状态图，可控性高于自由循环；不要把它宣传成无限自治系统。
  • MCP 与业务 API：MCP 标准化工具/资源接入，不替代鉴权、租户隔离、参数校验、审计和副作用审批。课件 README 曾将 MCP 展开为 Model Control Protocol，本篇按官方规范统一为 Model Context Protocol。
  • 多智能体与评审器：多智能体是角色/上下文隔离方式，评审器是质量检查节点；两者可以独立使用，评审分数也不等于事实正确。

论文怎么说 → 我们怎么用

3

《Beyond Downstream QA》（arXiv:2610.22209）指出只用下游 QA 评估记忆，会把记忆写入、检索和生成混为一体，可能掩盖错误的 create/update/supersede 操作。项目因此增加记忆内省测试：构造“偏好首次出现→更新→作废”的小轨迹，每步直接检查存储中的事实状态与来源，再测最终回答；不只凭一次答对认定记忆正常。

《VeriHarm-Bench》（arXiv:2611.03575）把“harmful success”定义为任务目标完成但伴随非预期伤害，并要求正确性测试与伤害测试同时通过。项目验收相应改成 safe_success = task_pass AND harm_tests_pass：例如“生成周报”成功但不能读取任务范围外文件，“调用搜索”成功但不能外发本地提示词或凭据。论文数值只属其基准，不作为本项目安全率。

3.1 需求分析

功能需求（FR）
- FR1 意图识别：区分"普通对话"与"内容生成工作流"，带置信度。
- FR2 研究：调用联网搜索工具（web_search）获取最新信息。
- FR3 分析：提炼搜索结果关键信息，产出分析报告。
- FR4 写作：基于分析结果生成结构化文章。
- FR5 审核：评估质量并打分，低于阈值自动重写（可设最大迭代次数）。
- FR6 MCP 工具管理：web_search、extract_key_points 等工具统一注册与调用；动态提示词、写作指南等资源管理。
- FR7 会话与记忆：支持多轮对话、上下文记忆。

非功能需求（NFR）
- NFR1 质量可控：审核分数阈值可配（默认 75 分通过），迭代上限可配（默认 3 次）。
- NFR2 可扩展：新增工具只需在 MCP server 注册；新增智能体只需加节点。
- NFR3 可观测：日志记录每步输入输出、工具调用、token 消耗。
- NFR4 异步并发：AsyncIO 高效并发处理工具调用与 LLM 请求。

角色/状态设计：5 个智能体（意图识别/研究员/分析师/作家/审核员）+ 共享 State（用户需求、检索结果、分析报告、草稿、评分、迭代次数）。

关键设计决策
- 状态图（StateGraph）而非链式：用 Node（步骤）+ Edge（流转）+ Conditional Edge（条件分支）+ Loop（审核重写）表达复杂流程，可控、可可视化、可回放。
- 条件循环做自我纠错：审核员打分 → 条件边决定"重写"还是"通过"，把质量控制内置进流程。
- MCP 解耦工具：工具在 MCP server 里标准化注册，Agent 通过 client 调用，工具可被多个智能体/项目复用，替换不影响编排。
- 意图识别前置分流：避免简单对话也走全流程，省成本、降延迟。

（4）mcp_integration/client.py——调用 MCP 工具

# 通过 stdio 连接 MCP server，列出并调用工具（示意）
import os
from mcp import ClientSession, StdioServerParameters
from mcp.client.stdio import stdio_client

MCP_SERVER_SCRIPT = os.environ["MCP_SERVER_SCRIPT"]

async def call_tool(name: str, args: dict):
    params = StdioServerParameters(command="python", args=[MCP_SERVER_SCRIPT])
    async with stdio_client(params) as (read, write):
        async with ClientSession(read, write) as session:
            await session.initialize()
            result = await session.call_tool(name, args)
            return result.content

（5）workflow/graph.py——LangGraph 状态图（核心编排）

from langgraph.graph import StateGraph, START, END
from workflow.state import AgentState
from agents.intent_recognizer import intent_node
from agents.researcher import research_node
from agents.analyst import analysis_node
from agents.writer import write_node
from agents.reviewer import review_node

def route_intent(state: AgentState) -> str:
    return "chat" if state["intent"] == "normal_chat" else "research"

def route_review(state: AgentState) -> str:
    if state["review_score"] >= PASS_SCORE:
        return "pass"
    if state["iteration"] >= MAX_REVIEW_ITERATIONS:
        return "fail"      # 达到预算仍不达标则显式失败，不静默放行
    return "rewrite"

g = StateGraph(AgentState)
g.add_node("intent", intent_node)
g.add_node("chat", lambda s: {"final_output": "（普通对话回复）"})
g.add_node("research", research_node)
g.add_node("analysis", analysis_node)
g.add_node("write", write_node)
g.add_node("review", review_node)
g.add_node("failed", lambda s: {"final_output": "未达到质量门槛，请人工处理"})

g.add_edge(START, "intent")
g.add_conditional_edges("intent", route_intent, {"chat": "chat", "research": "research"})
g.add_edge("research", "analysis")
g.add_edge("analysis", "write")
g.add_edge("write", "review")
g.add_conditional_edges(
    "review", route_review,
    {"pass": END, "rewrite": "write", "fail": "failed"},
)
g.add_edge("failed", END)
g.add_edge("chat", END)

graph = g.compile()

3.4 部署与运维

部署
1. 本地/容器：python main.py 起 CLI；对外服务时用 FastAPI + 流式接口（SSE）暴露，前端用 Streamlit/Vue/Next.js 消费。
2. 服务中台化（AgentCenter 模式）：把 Agent 封装为服务，前端 + Gateway（认证/限流/熔断/负载均衡）+ Agent Router（FastAPI+LangChain+LangGraph）+ Business Connectors（对接业务系统 API）。
3. 协议能力：
- MCP：封装通用工具服务（搜索、数据库、文件），供多 Agent 复用；
- A2A：跨智能体/跨服务协作与通信（如 SmartVoyage 的天气代理、票务代理、LLM 路由服务器）。
4. 会话与记忆：PostgreSQL/Redis 做 checkpointer，存对话历史与上下文，支持多轮与多租户隔离。
5. 沙箱与安全：工具执行放沙箱（Docker/Podman）；API Key 走密钥服务；对工具调用做权限与审计。

运维与评估
- 日志：以结构化 JSON 记录节点名、迭代次数、工具名、参数校验结果、审核分数和 token 消耗；完整输入输出与敏感参数默认不记录，确需采样时先脱敏、审批并设置保留期。
- 质量评估：审核通过率、平均迭代次数、端到端延时、工具成功率、成本/token；badcase 回流调提示词与阈值。
- 可观测：接入 Tracing（Langfuse/Phoenix/OpenTelemetry）看每个 Agent 节点的耗时与失败点。
- 成本控制：意图识别前置分流；缓存高频工具结果；控制最大迭代与 Top-K；按需路由强/弱模型（详见 L9《安全、容量压测与成本治理》）。
- 兜底：MCP 连接失败、LLM 超时要有降级路径与可解释错误；审核始终有最大迭代上限防止死循环。

5.1 Agent 架构模式怎么选

单 Agent 适合目标单一、步骤少的任务；多 Agent 适合可并行、需专业分工、要互相校验的任务。常见模式：流水线（研究→分析→写作，串行分工）、监督者/路由（一个主 Agent 分派子 Agent）、辩论/评审（多 Agent 互相挑错取共识）、层级（主 Agent 孵化子 Agent 处理子问题）。选型看任务耦合度与质量要求，别为了"多智能体"而多智能体——能用一个 Agent 干完的，拆成五个只会更慢更贵。

5.2 提示词与上下文工程

Agent 的失败多数不是模型不行，而是提示词与上下文没喂对。每个节点的系统提示词要明确角色、输入、输出格式、约束；用少样本示例锚定输出结构；长任务做上下文压缩与摘要，避免把全部中间结果塞回窗口；给模型"思考时间"（让它先列计划再执行）能显著提升多步任务成功率。工具描述要写清参数、返回、副作用，模型才知道何时调、怎么调。

5.3 工具设计与安全

工具是 Agent 的手脚，也是最大的风险面。设计原则：单一职责、幂等、可观测、最小权限。破坏性工具（写库、发消息、删文件）必须加确认/沙箱/审计；外部调用要限速、超时、熔断、兜底；工具返回要控制长度并标注错误。用 MCP 把工具标准化后，可在网关统一做鉴权与限流，避免每个 Agent 自己裸调。

5.4 可靠性与成本

防死循环：给循环设最大迭代上限、最大 token 预算、超时熔断；审核重写要有退出条件。可观测：用 Langfuse/Phoenix/OpenTelemetry 追踪每个节点的输入输出、工具调用、耗时、token，定位失败点。成本：意图分流省掉无谓全流程；缓存高频工具结果；按任务难度路由强/弱模型；控制迭代与检索 Top-K。质量评估看任务完成率、审核通过率、平均迭代次数、端到端延迟与单任务成本。

5.5 记忆与状态

短期记忆放会话 checkpointer（PostgreSQL/Redis），支持多轮与断点续跑；长期记忆存用户偏好、历史结论（向量库 + 时间衰减）。多租户必须隔离记忆，避免串数据。状态设计要可序列化、可回放，方便调试与审计。

六、常见踩坑与排错

3

MCP 连接失败：检查 MCP_SERVER_SCRIPT 路径是否为绝对路径、Python 环境变量是否配好、MCP server 能否独立启动。LLM 调用失败：API Key 无效或网络不通，看 logs/ 详细报错；DashScope 记得用 compatible-mode 的 base_url。死循环/无限重写：审核条件没设最大迭代上限，或"重写"分支没接回正确节点；务必有 iteration < MAX 的退出条件。意图识别不准：给意图分类加少样本示例与置信度阈值，低于阈值走默认流程。工具返回被截断：控制工具返回长度、分页、只回关键字段，否则塞爆上下文。异步报错：AsyncIO 里别用阻塞 IO，工具与 LLM 调用都要 async；事件循环记得 asyncio.run。多智能体状态丢失：State 字段没声明在 TypedDict 里导致流转丢数据，节点返回要覆盖正确 key。
