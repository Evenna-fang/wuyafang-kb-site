WHY

2

项目价值与适用场景

3
  1. 支撑高并发与弹性：单体扛不住流量洪峰。微服务按域拆分、独立扩缩容，配合限流、缓存、异步削峰，才能应对秒杀/大促/早高峰。
  2. 故障隔离与高可用：一个服务出问题不拖垮全站；Sentinel 熔断降级、多级缓存、消息重试保证整体可用。
  3. 团队与迭代效率：服务边界清晰、独立部署、独立演进，多团队并行开发不互相阻塞。
  4. AI 落地的天然载体：传统业务系统智能化升级（风控、智能派单、推荐、AI 客服）需要在微服务里挂 AI 服务（SpringAI / LangChain / LangGraph），这是"业务 + AI 双能力"的核心体现。
  5. 大厂生产标准对标：分布式事务、幂等、全链路追踪、灰度发布、容量压测——这些是面试与实际交付的硬通货。

WHAT

2

系统定义与适用边界

3

一个生产级、分布式的微服务业务系统：把单体应用按业务域拆成独立服务（订单、运单、骑手/派单、支付…），用 Spring Cloud Alibaba 做服务治理（注册/配置/网关/限流熔断/远程调用/消息/分布式事务），并在关键业务环节注入 AI 能力（风控、智能派单、推荐、问答）。

以本知识库 微服务实战系列（物流系统）为骨架，它覆盖了企业级微服务的全部硬骨头：
- 架构治理：Nacos 注册/配置、Gateway 网关、Sentinel 限流熔断、OpenFeign 远程调用；
- 高并发核心：秒杀抢购（Redis 库存预热 + Lua 原子扣减 + RocketMQ 异步下单 + 一人一单）；
- 分布式业务：派单调度（GEO 检索 + 评分 + 分布式锁 + 条件更新）、支付（异步通知 + 验签 + 幂等 + 状态机 + Seata AT）。

在黑马项目库中对应 智链云途（智能物流）/ 云岚到家（家政 O2O）/ 四方保险（保险 SAAS）/ 天机学堂（在线教育） 四选一的"AI 工程化-微服务智能体实战"阶段。换业务域即换行业，骨架通用。

实施路径

3.1 需求分析

业务需求（以物流系统为例）
- 订单域：下单、取消、状态流转。
- 运单域：运单创建、状态跟踪、轨迹。
- 骑手/派单域：位置上报、智能派单、接单、超时重派。
- 支付域：支付单创建、支付、退款、对账。
- （AI 升级点）登录风控、智能派单推荐、运费/路线优化、AI 客服问答。

功能需求（FR）
- FR1 服务注册发现：各服务启动注册 Nacos，调用方按服务名发现实例。
- FR2 配置中心：Nacos Config 动态刷新配置（开关、阈值），支持多环境 namespace。
- FR3 网关：统一入口、鉴权、路由、限流、跨域、审计。
- FR4 高并发秒杀：库存预热、原子扣减、防超卖、一人一单、异步下单、削峰。
- FR5 智能派单：GEO 半径检索骑手、多维评分、抢占接单锁、条件更新、超时重派。
- FR6 支付：异步通知、验签、幂等、状态机、最终一致、分布式事务。

非功能需求（NFR）
- NFR1 高并发：秒杀目标 QPS 万级，DB 不被打垮（缓存 + 异步 + 限流）。
- NFR2 高可用：限流降级、熔断、重试、死信兜底、幂等防重。
- NFR3 一致性：跨服务写操作幂等键 + 补偿任务；支付/扣库存最终一致。
- NFR4 可观测：traceId 全链路、结构化日志、指标告警。
- NFR5 安全：JWT/网关鉴权、防刷风控、密钥不落库。

领域与数据：每服务独占数据库（订单库/运单库/支付库）；Redis 存库存/缓存/GEO/分布式锁；RocketMQ 传递领域事件。

治理组件分工
| 组件 | 职责 | 关键点 |
|---|---|---|
| Nacos | 注册 + 配置中心 | namespace 分环境、group 分领域；心跳续租 |
| Gateway | 统一入口 | 鉴权早于路由；限流（令牌桶）；lb:// 路由 |
| Sentinel | 流控/熔断/降级 | 阈值来自压测；热点参数；规则持久化到 Nacos |
| OpenFeign + LoadBalancer | 声明式远程调用 | 超时小于上游；重试只用于幂等 GET |
| RocketMQ | 异步解耦/削峰/延迟消息 | 消费幂等、死信、事务消息 |
| Seata AT | 分布式事务 | 下单扣库存、派单等跨服务写 |
| Redis | 热点/库存/GEO/锁 | 多级缓存、原子操作、分布式锁 |

关键设计决策
- 缓存抗并发、DB 保一致：Redis 挡住读写洪峰，DB 乐观锁 + 唯一索引兜底，绝不产生负库存/重复单。
- 原子操作优先：库存扣减用 Lua 脚本"检查+扣减+标记"一步完成，避免"先查再减"竞态。
- 异步削峰：下单等重操作写 RocketMQ，消费者异步处理，主链路快速返回。
- 幂等贯穿：接口幂等键、消息消费幂等、支付通知幂等，数据库唯一索引做最后防线。
- 锁只降竞争、不保正确：Redis 接单锁减少并发，但最终靠 DB 条件更新（status='已派单' AND rider_id=?）保证正确。

-- lua/seckill.lua  返回 1成功 / 0库存不足 / -1重复购买
local previous = redis.call('GET', KEYS[3])
if previous == 'RESERVED' then return 1 end
if previous == 'RELEASED' then return -3 end
local stock = tonumber(redis.call('GET', KEYS[1]) or '-1')
if stock <= 0 then return 0 end
if redis.call('EXISTS', KEYS[2]) == 1 then return -1 end
redis.call('DECR', KEYS[1])
redis.call('SET', KEYS[2], ARGV[1], 'EX', ARGV[2], 'NX')
redis.call('SET', KEYS[3], 'RESERVED', 'EX', ARGV[2])
return 1

@Service
public class RedisStockService {
    private final StringRedisTemplate redis;
    private final DefaultRedisScript<Long> script;
    public RedisStockService(StringRedisTemplate redis) {
        this.redis = redis;
        this.script = new DefaultRedisScript<>(new ClassPathResource("lua/seckill.lua"), Long.class);
    }
    public long reserve(long goodsId, long userId, String requestId) {
        String tag = "{" + goodsId + "}";                 // 同 hash tag 保证同槽
        String stockKey   = "seckill:stock:" + tag;
        String userKey    = "seckill:order:" + tag + ":user:" + userId;
        String requestKey = "seckill:request:" + tag + ":" + requestId;
        Long r = redis.execute(script, List.of(stockKey, userKey, requestKey), requestId, "1800");
        return r == null ? -2 : r;
    }
}

异步下单超时不能直接回补库存（消息可能已到达）：标记 UNKNOWN，后台核对 MQ 投递与 DB 订单后，才带幂等号回补。

（4）智能派单：GEO 检索 + 评分 + 抢占锁 + 条件更新

@Service
@RequiredArgsConstructor
public class AcceptService {
    private final StringRedisTemplate redis;
    private final WaybillMapper waybillMapper;

    @Transactional
    public boolean accept(long waybillId, long riderId, String requestId) {
        String key = "rider:accept:" + waybillId;               // 锁只降竞争
        Boolean locked = redis.opsForValue().setIfAbsent(key, requestId, Duration.ofSeconds(10));
        if (!Boolean.TRUE.equals(locked)) return false;
        int changed = waybillMapper.accept(waybillId, riderId);  // DB 条件更新保正确
        if (changed != 1) { redis.delete(key); return false; }
        return true;
    }
}

@Mapper
public interface WaybillMapper {
    @Update("UPDATE delivery_order SET status='已接单', updated_at=NOW() " +
            "WHERE id=#{waybillId} AND rider_id=#{riderId} AND status='已派单'")
    int accept(long waybillId, long riderId);   // 影响行数=1 才算成功
}

派单评分：先过滤（在线、位置 90s 内、未超载、无锁），再按 0.5×距离分 + 0.3×负载分 + 0.2×服务分（归一化到 0~1）取前 N；候选空则扩大半径或进人工池。超时用 RocketMQ 延迟消息（delayLevel）触发重派。

（5）支付幂等与最终一致
- 支付单状态机：待支付→支付中→成功/失败/关闭，状态单向流转。
- 异步通知：验签 + 幂等（以支付单号 + 通知序号去重）+ 本地消息表。
- Seata AT：下单扣库存、派单等跨服务写纳入分布式事务；不可逆迁移走"新增字段→双写→回填→切读→删除"。

（6）AI 智能化升级点（业务 + AI）
- 登录风控：SpringAI/LangChain 做身份认证风控 + Token 刷新。
- 智能派单/网点推荐：LangGraph 多节点智能体产出推荐方案。
- AI 客服/问答：接 RAG（项目一）做业务问答；接 Agent（项目二）做智能助手。
- 运费/路线优化：XGBoost/BERT 等模型微服务化后被 Feign 调用。

3.4 部署与运维

部署
1. 容器化 + 编排：每服务一个镜像，Docker Compose（开发）/ Kubernetes（生产）编排；Nacos、Redis、MySQL、RocketMQ 独立部署并数据卷持久化。
2. CI/CD：Jenkins/Gitee Go 流水线——构建→漏洞扫描→契约测试→镜像→灰度发布。
3. 灰度：Nacos metadata 标记版本，网关/LoadBalancer 按灰度 Header 导流小流量；观察错误率、P95、线程池、GC 达基线再放量。
4. 服务拆分原则：每服务独占数据；跨域只读视图走 API/事件；同步链路不超过 2~3 个核心服务，其余走事件异步。

运维与监控
- 全链路追踪：traceId 由 Gateway 生成/透传，Feign、MQ 生产/消费者继续传递；接入 SkyWalking/OpenTelemetry。
- 指标告警：注册实例数、配置拉取失败、网关 4xx/5xx、Sentinel block、Feign 超时、MQ 积压、DB 连接池、缓存命中率；告警分入口成功率/依赖成功率/资源水位三类。
- 日志：结构化 JSON（service、instance、traceId、userId 脱敏、orderId、errorCode）。
- 容量压测：用 JMeter/Gatling 压出 DB 连接池、线程池、下游安全上限，再据此设 Sentinel 阈值（Warm Up、排队等待按场景选）。
- 故障演练：Nacos 短暂不可用、Redis 主从切换、MQ 消费延迟、DB 连接池耗尽、实例 Full GC；目标是"能限流、能降级、能重试、最终一致"。
- 发布与回滚：回滚不仅回镜像，还要确认配置、DB 迁移、消费者版本兼容。

踩坑要点（速查）
- Nacos 账号密码用环境变量/密钥挂载；namespace 用实际 UUID；2.x 通不通查 9848/9849 gRPC 端口。
- Gateway lb:// 依赖 LoadBalancer starter；WebFlux 网关别引 Servlet MVC 过滤器；请求体只读一次。
- Sentinel 资源名要稳定；fallback 只返回可解释降级，不能吞掉扣库存异常。
- Feign 超时 < 上游网关超时；重试只用于幂等 GET，支付/扣库存禁用无脑重试。
- RocketMQ 延迟消息用 delayLevel（非任意毫秒）；消费幂等 + 死信；Redis Keyspace Notification 不做唯一超时机制。
- 金额用 BigDecimal/最小货币单位整数；时间统一 UTC 存储、展示层转换。

五、企业级进阶与调优（深度）

3

5.1 服务怎么拆、边界怎么定

拆分按业务域能力而非技术分层：订单、运单、支付各自拥有数据与生命周期。判定标准是"高内聚低耦合、可独立扩缩容、能由一个小团队全权负责"。避免两种极端——拆得过细导致分布式开销大于收益、拆得过粗回到单体。数据所有权一旦确定就别跨服务直连对方数据库，只通过 API 或领域事件交换只读视图，否则边界名存实亡。

5.2 高并发三板斧：缓存、异步、限流

缓存抗读：多级缓存（本地缓存 + Redis）挡热点，注意缓存一致性（延迟双删、失效订阅）与缓存穿透/击穿/雪崩（空值缓存、互斥重建、随机过期）。异步抗写：把重操作丢进 RocketMQ 削峰，主链路快速返回，消费者慢慢处理。限流保命：Sentinel 按总 QPS、用户、IP、并发数分层设阈值，超出就降级排队或快速失败，绝不让流量打穿数据库。

5.3 一致性与幂等的工程底线

分布式下没有免费的一致性。同步调用链要短，跨服务写用"本地消息表 + 最终一致"或 Seata AT。幂等三件套：接口幂等键（请求指纹去重）、消费幂等（业务唯一键 + 唯一索引）、支付通知幂等。重试必须指数退避 + 最大次数 + 死信队列；只对幂等操作重试，扣库存、支付这类禁用无脑重试。记住：锁只降低竞争，数据库条件更新与唯一索引才是正确性的最后防线。

5.4 可观测性与稳定性

traceId 全链路透传是排障的前提。指标要覆盖入口成功率、依赖成功率、资源水位三类，而不是只盯 CPU。日志结构化并脱敏。故障演练常态化：Nacos 不可用、Redis 切换、MQ 积压、连接池耗尽、Full GC 都要演练过，验证目标是"能限流、能降级、能重试、最终一致"，而不是"没有报错"。

5.5 演进：从微服务到 AI 化业务系统

微服务是 AI 落地的载体。把模型能力封装成独立 AI 服务（SpringAI/LangChain/LangGraph），通过 Feign/MCP 被业务服务调用：风控、智能派单、推荐、RAG 问答、Agent 助手。AI 服务要单独做超时、降级、成本控制与灰度，不能让一次模型调用拖垮主交易链路。业务服务保持无状态、可水平扩展，AI 服务按 GPU/并发独立伸缩。

  • 本库真正在跑的「多服务协作」是另一种形态（本次实测）：
    | 组件 | 位置 | 角色 |
    |---|---|---|
    | Hermes 网关 | ~/.hermes/gateway、gateway.pid | 消息/会话调度 |
    | 六员 Agent 进程 | DSH / Claude / Codex / OC / Qwen / Hermes | 执行者 |
    | 任务总线 | ~/.hermes/shared-state.db（tasks + inbox） | 类「注册中心 + 任务队列」 |
    | 知识库服务 | rag/serve.py（OpenAI 兼容） | 数据服务 |
    它没有 Nacos/网关路由/Dubbo，但「服务发现靠表、调用靠契约、失败靠状态机」这三个微服务核心问题都在。
  • 最接近微服务的真实配置文件是 projects/agent-service-toolkit/compose.yaml：postgres + agent_service + streamlit_app 三服务，用 depends_on: condition: service_healthy 表达启动依赖，用 healthcheck 表达「就绪」——单机 Compose 就是小规模微服务。
  • 和课件讲法的差异：课件微服务重点在 Spring Cloud 组件；本库的现实是「Agent 即服务」——服务之间的契约是 OpenAI 兼容的 JSON，注册中心是 SQLite 表。
  • 本库暂无：服务网格、链路追踪、限流熔断（rag/query.py 的熔断是函数级超时，不是服务级）。
