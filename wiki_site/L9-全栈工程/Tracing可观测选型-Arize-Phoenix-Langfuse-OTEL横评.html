WHY：为什么在 7.8G WSL 约束下重做 Tracing 选型

2

在 7.8G WSL + 本地自托管 + 轻量 + 能串"检索→rerank→生成"全链路的约束下，Arize Phoenix（单容器，官方 2GB RAM + 1 vCPU）是唯一在该内存下无压力、且带完整 UI 的方案；Langfuse 功能最全但 v3+ 自托管需 5 容器（Web 4G + Worker 4G + PG 4G + Redis 1.5G + ClickHouse 8G ≈ 15GiB 基线），在 7.8G WSL 上偏重；OpenTelemetry+Jaeger 最轻（~200-500MB）但需手写 span 无开箱 UI；LangSmith 自托管仅 Enterprise 付费 + K8s，本地直接排除。

选型动机的机制拆解

3
  • 四方案内存实测 vs 本机约束（关键决策点）：本机 WSL 内存 7.8G，且 query.py 本身要跑 torch（bge-embedding + bge-reranker，RAG_TORCH_THREADS=4）已占可观内存。实测对比：
  • Langfuse 自托管 v3+：官方 production 最低 Web 2C/4G + Worker 2C/4G + PG 2C/4G + Redis 1C/1.5G + ClickHouse 2C/8G ≈ 21.5G（推荐），最小 Docker Compose 可砍到 8-12G 但 UI 慢、ClickHouse 吃紧 → ⚠️ 勉强/高风险，与 RAG 模型抢内存，低负载个人用可跑但需盯 OOM。
  • LangSmith 自托管：需 K8s 集群 + Enterprise 许可 → ❌ 不可行（门槛 + 重量级）。
  • OpenTelemetry + Jaeger all-in-one：Jaeger 单容器 ~200-500MB → ✅ 极轻，无忧。
  • Arize Phoenix：官方内部 2GB RAM + 1 vCPU，单容器 + SQLite → ✅ 轻，最推荐的"完整 UI"方案。
  • 接入成本的"基线"逻辑：LangSmith 的 5 个 @traceable 已经在 query.py 里跑通（L45-52 导入，L499/535/634/714/1949 打点），所以任何新方案的接入成本都应对照"替换这 5 个装饰器"来评估，而不是从零打点——这是判断"改多少代码"的锚点。
  • Langfuse 被收购的背景：2026-01-16 被 ClickHouse 收购（MIT 许可承诺不变），~35k stars，90 天 ~1550 commits，最近 release v4.50.0（2026-10-02）——社区活跃度是四方案中最高的，但内存门槛也是最高的。
  • Phoenix 的定位差异：~12k stars，v20.26.x（2026-10-25 仍在发版），Apache 2.0 + ELv2（部分），Arize 商业公司背书；OpenInference SpanKind（retriever/reranker/llm/chain/tool）原生支持 RAG 各环节分类，trace 树 + eval（retrieval evals、response evals）内置——RAG 场景是 Phoenix 的主打场景，与本项目 golden/e2e eval 体系天然契合。

现状、代价与切换权衡

3
  • 现状：query.py（2116 行）是 LangGraph 状态机 + CRAG 纠错环的 Adaptive RAG，链路为
    user_query → route_question(路由) → retrieve_node(检索) → grade_documents(CRAG评分) → [rewrite_node(重写)?] → rerank_node(rerank) → generate_node(LLM生成)。
    已通过 from langsmith import traceable 在 5 个关键函数上打点（retrieve / retrieve_hybrid / rerank / ollama_chat / query，run_type 分别为 retriever/llm/chain）——但 LangSmith 云端免费档仅 5k traces/月、1 席位、14 天保留，长期本地方案需替换。
  • 不做的代价：检索→rerank→生成这条链路上任一环节的延迟/错误无法定位，生产排障靠猜；LangSmith 免费额度撞顶后直接断数据。
  • 权衡：切换成本 = 替换 5 个 @traceable 装饰器（约 5-8 处改动，30 分钟量级）+ 可选 span 属性增强。LangSmith 的 @traceable 本身就是"改多少代码"的基线——任何方案的接入成本都应对照这个基线评估，不是从零打点。

WHAT / WHYT：Tracing 的定义、职责与内存边界

2
  • Tracing 可观测：对 RAG 管线每个环节（检索/重排/生成/全链路）打 span，记录耗时、token、命中文档，用于生产排障与质量归因。
  • ✅ 管什么：span 树结构、检索/rerank/生成的业务语义分类（OpenInference SpanKind）、LLM 成本/token 统计、数据主权（本地存储）。
  • ❌ 不管什么：向量库本身调优、embedding 模型选型、chunk 切分策略——这些是 RAG 检索层的事，不在 tracing 范围。
  • ⚠️ 红线：RAG_TORCH_THREADS=4 的 torch（bge-embedding + bge-reranker）已占可观内存，任何 tracing 方案都不得再挤占这 7.8G 的剩余空间导致 OOM。

四方案横评矩阵（核心维度）：

维度 Langfuse（自托管） LangSmith OpenTelemetry + Jaeger Arize Phoenix
自托管/本地 ✅ MIT，Docker Compose 一键起；但 v3+ 需 Postgres+ClickHouse+Redis+MinIO 5 容器，~15GiB ❌ 自托管仅 Enterprise 付费 + K8s（Helm）；SDK MIT 平台闭源 ✅ 协议/SDK，零存储；配 Jaeger all-in-one 单容器 ~200MB 或 Tempo ✅ 单容器 docker run arizephoenix/phoenix，官方 2GB RAM + 1 vCPU，SQLite/PG 可选
接入成本 低：from langfuse.langchain import CallbackHandler + config={"callbacks":[langfuse_handler]} 一行接 LangGraph；自定义函数 @observe() 替 @traceable（1:1） 极低（现状已接好 5 个 @traceable）；但云端免费档 5k traces/月 中-高：tracer.start_as_current_span() 手动包每个环节，无现成装饰器 低：arize-phoenix-otel 的 register(auto_instrument=True) 自动 instrument；检索/rerank 仍需手动 span
串全链路 ✅✅ 最强：LangGraph CallbackHandler 自动串 StateGraph 全节点为嵌套 trace；@observe(as_type=...) 显式标注 ✅ 自动串，但业务语义分层靠 run_type 命名，不如 Langfuse 丰富 ✅ GenAI Semantic Conventions（gen_ai.operation.name、gen_ai.usage.*）+ 自定义 retrieval.*/rerank.*；最规范但最费手 ✅ OpenInference SpanKind（retriever/reranker/llm/chain/tool）原生支持 RAG 各环节分类
社区/维护 ✅✅ ~35k stars，90 天 ~1550 commits，2026-01-16 被 ClickHouse 收购（MIT 不变） ⚠️ 活跃但闭源；2026-05 起存储引擎 SmithDB（闭源替代 ClickHouse） ✅✅ CNCF 标准，永不消失，厂商中立 ✅ ~12k stars，2026-10-25 仍高频发版，Apache 2.0，Arize 商业背书
数据主权 ✅ 完全本地（ClickHouse/PG） ❌ SaaS 或 Enterprise 自托管 ✅ 完全本地 ✅ 完全本地（SQLite/PG）

推荐结论（按本机约束排序）：
- 🏆 首选 Arize Phoenix：单容器 + SQLite，2GB/1vCPU，唯一在 7.8G WSL 上无内存压力且带完整 UI；接入约 5-8 处改动、30 分钟量级；RAG 检索/响应 eval 是 Phoenix 主打场景，与本项目 golden/e2e eval 体系契合。
- 🥈 备选 Langfuse：功能最全（OTEL 原生、LangGraph 一行接入），但 5 容器 + ClickHouse 内存基线在 7.8G WSL 上偏重——未来迁到 ≥16G 机器且需 prompt 管理 + LLM-as-judge + 成本核算时再选。
- 🥉 第三 OpenTelemetry + Jaeger：协议永不消失、~200MB 极轻；代价是检索/rerank 属性要手写、无 LLM 成本/eval 开箱能力。
- ❌ 不推荐 LangSmith 自托管：Enterprise 付费 + K8s，个人/本地场景直接排除；云端免费档可临时调试，注意额度撞顶。

接入步骤概要（以首选 Phoenix 为例，⚠️ 概要设计，执行需另开实施单，本条目不改配置）：
1. 起 Phoenix：docker run -d --name phoenix -p 6006:6006 -p 4317:4317 arizephoenix/phoenix:latest（UI: http://localhost:6006）
2. 装 SDK：pip install "arize-phoenix-otel>=0.16.0"
3. 注册 tracer（query.py 顶部替换现有 langsmith import 块）：
python from phoenix.otel import register tracer_provider = register(project_name="wuyafang-rag", auto_instrument=True)
本地无需 API key：export PHOENIX_COLLECTOR_ENDPOINT="http://localhost:6006"
4. 替换 5 个 @traceable 为 OpenInference span：
- retrieve / retrieve_hybrid / rerank → tracer.start_as_current_span(name, attributes={OpenInferenceSpanKindValues.RETRIEVER/RERANKER})，属性挂 retrieval.top_k、retrieval.query、命中 document.id/text/score
- ollama_chat → span kind LLM，属性 gen_ai.request.model、gen_ai.usage.input_tokens/output_tokens
- query() 顶层 → span kind CHAIN 作为 root，天然串起子 span
5. （可选）LangGraph 全自动：若走 LangChain/LangGraph CallbackHandler 路线，Phoenix auto_instrument=True 自动抓 StateGraph 各节点，检索/rerank/生成自动成嵌套 span。
6. 验证：跑一次 python query.py --question "..." → 打开 http://localhost:6006 看 trace 树是否含 检索→rerank→生成 三层。

若选 Langfuse（备选）接入差异：起服务 git clone https://github.com/langfuse/langfuse && cd langfuse && docker compose up（5 容器，注意内存）；LangGraph 一行接入 from langfuse.langchain import CallbackHandler; config={"callbacks":[CallbackHandler()]}；自定义函数 from langfuse import observe → @observe(as_type="generation"/"retriever") 替换 5 个 @traceable。
