WHY：为什么流式、取消与并发治理是生产基线

2

流式不是"优化项"而是基线：LLM 逐 token 生成，等完整响应再渲染要面对 3–10 秒死等，把每个 chunk 立刻追加能把感知延迟（time-to-first-token）从几秒压到几百毫秒；2025–2026 主流前端 AI 产品（ChatGPT / Claude / Cursor / Vercel AI Playground）全部默认 streaming，不流式已被视为反模式。前端只有一条正确路线——fetch() + response.body.getReader() + TextDecoder 手动解析 SSE 帧，因为浏览器原生 EventSource 只支持 GET，而 LLM 的 prompt 往往要放 POST body（长度、鉴权、隐私）。框架层直接用 Vercel AI SDK 把约 50 行手写 SSE 压到约 2 行：useChat() 管 messages/status，服务端 streamText() 一行切 provider。后端的关键不是"能返回"，而是"能把上游流原样转发"：FastAPI 用 async generator + StreamingResponse，绝不能用同步 def 堵死 uvicorn worker；再叠一层 asyncio.Semaphore 并发闸（示例 64）、按上游 RPM/TPM 限额的 70–80% 设闸值、超时退避重试、客户端断开即时 cancel 上游。三条最硬：EventSource 不要用于聊天；后端满闸宁可 503 快速失败、也不要无限排队把内存打爆；用户关掉标签页后继续烧 token 是 2026 年被反复强调的浪费来源。

一、传输层：两条路线怎么选2 个重点▾ 点开看本节重点
本节重点

  • signal: controller.signal, // 打断

维度 EventSource（原生 SSE） fetch + ReadableStream
请求方法 只支持 GET 支持 POST（可带 JSON body）
实现复杂度 极低（一行 new EventSource） 需手动解码 chunk、处理边界
取消 内置 close() 配合 AbortController
适用 简单通知流 LLM 聊天（推荐）

生产一律 fetch + ReadableStream，服务端以 Content-Type: text/event-stream 推送：

const res = await fetch('/api/chat', {
  method: 'POST',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({ messages }),
  signal: controller.signal,          // 打断
});
const reader = res.body.getReader();
const decoder = new TextDecoder();
while (true) {
  const { done, value } = await reader.read();
  if (done) break;
  for (const line of decoder.decode(value).split('\n')) {
    if (line.startsWith('data: ')) appendToUI(line.slice(6));
  }
}

二、框架层：Vercel AI SDK 是事实标准

3

手写上面那套（解析 SSE、管 message state、provider 切换、错误处理、工具调用）约 50 行起，AI SDK 压到约 2 行，是 2025–2026 React/Svelte/Vue/Angular 接 LLM 的事实标准。

抽象 作用
useChat()（@ai-sdk/react） 自动管理 messages / sendMessage / status（'streaming'、'ready'、'error'），自动把服务端 stream 追加到 UI
streamText() / generateText() 一行切 provider（OpenAI / Anthropic / Google / 本地 Ollama 统一接口）
generateObject + Zod 结构化输出（provider 差异在框架层抹平）
parts 模型（v4/v5 起） message.parts 区分 {type:'text'} 与 {type:'tool-...'}，前端分别渲染文本块与工具块
AI Elements / Streamdown 预封装流式 chat UI 组件 + 为流式 markdown 优化的渲染器（边打字边渲染代码块/公式/表格不闪烁）
  • 对比直调 OpenAI SDK：streaming 搭建约 50 行 vs 2 行；换 provider 全量重写 vs 一行；tool calling 手写 JSON 解析 vs 原生 Zod 支持。
  • OpenAI SDK 前端直连（new OpenAI({ dangerouslyAllowBrowser: true })）仅限内部/演示；生产必须前端 POST 到自家 /api/chat，由服务端持有 key、注入 system prompt、做鉴权限流，再把 provider 的 stream 原样 relay（SSE 透传）——key 不出服务器，也能统一计费。
  • Vue 侧：AI SDK v5 已官方支持 @ai-sdk/vue 的 useChat 与 Angular；无专属库时自己包一层 fetch + ReadableStream 的 composable 也很快，模式与 React 一致。

HOW：流式 UI、异步转发、并发闸与模型路由

三、流式 UI 的四个要点

3
  1. 打字机效果要批处理：不要每个 token 都 setState（React 会狂渲染）。用 useSyncExternalStore 或 buffer 合并——攒 16ms 内的 chunk 批量 flush；流式 markdown 渲染器要容忍"半截代码块"。
  2. 打断必须接 AbortController：用户点"停止"就 abort 请求、终止 reader，后端收到断开要停止向 LLM 发请求。进阶是 resumable stream——刷新/关标签页后能续接（producer 写日志、reader 从 offset 回放），Vercel resumable-stream 与 Upstash Redis Streams 模式都为此设计。
  3. 工具调用分块渲染：用 parts 模型区分文本与工具块——工具进行中显示"正在搜索资料…"旋转卡片，完成后折叠成引用，而不是把 function_call 的 JSON 直接打给用户。
  4. 错误态优雅收尾：上游 429/500 要在流中途收尾并给"生成中断，点击重试"，别白屏；别把 provider 原始错误体透给浏览器（会泄漏请求细节）。
四、后端：StreamingResponse + async 是底线3 个重点▾ 点开看本节重点
本节重点
  • 后端接 LLM 第一件事不是"能返回结果"，而是"能把上游流原样转发"
  • @router.post("/api/chat")
  • yield "data: [DONE]\n\n"
3

后端接 LLM 第一件事不是"能返回结果"，而是"能把上游流原样转发"。FastAPI 用 StreamingResponse + async generator，把 .stream() 逐个 yield 成 SSE 帧（末尾 data: [DONE]）：

@router.post("/api/chat")
async def chat(req: ChatRequest):
    async def gen():
        stream = await openai.chat.completions.create(
            model="gpt-4o", stream=True,
            messages=[m.model_dump() for m in req.messages])
        async for chunk in stream:
            delta = chunk.choices[0].delta.content
            if delta:
                yield f"data: {delta}\n\n"
        yield "data: [DONE]\n\n"
    return StreamingResponse(gen(), media_type="text/event-stream")
  • 必须用 async 而非同步 def：LLM 调用是 IO 密集，同步会把 uvicorn worker 整个堵死。
  • 不要 await 完整响应再返回；逐 token yield 才能降感知延迟。

五、并发闸与可靠性：别被压垮

3

LLM 后端被压垮的典型方式：几十上百并发同时打上游 → 429，或自己进程被占满。

机制 做法（含具体口径）
并发闸 asyncio.Semaphore(64) 限制在途调用；满了宁可快速失败（503 + 前端退避重试），不要无限排队打爆内存；闸值按上游 RPM/TPM 限额的 70–80% 设，留缓冲
超时 上游必须设 timeout（总超时 60–120s，首 token 超时更短），LLM 卡住时不能让连接一直挂着
重试 只重试幂等可重试错误：429（带 Retry-After）、5xx、网络抖动；400 绝不重试；指数退避 + jitter（用 tenacity 或 SDK 自带 max_retries）；流式断到一半不要盲目重发（会重复计费），给"重新生成"按钮或走 resumable
断开止损 检测 request.is_disconnected() 就 cancel 上游 stream，别在用户关标签页后继续烧 token
限流 按用户/API key 用 token bucket（Redis + slowapi/limits）；还要估算本次输入+输出 token 按 TPM 排队；超闸请求进有上限、有超时的队列而非立刻 503
六、多模型路由与 Node 侧3 个重点▾ 点开看本节重点
本节重点
  • return "gpt-4o-mini" 小模型，便宜快
  • return "o4-mini" 推理模型
  • return "claude-haiku" 免费档走便宜模型
3

生产后端几乎都不接单一模型，而是按请求类型路由：

def route(req):
    if req.task in ("classification", "extract"):
        return "gpt-4o-mini"          # 小模型，便宜快
    if req.task == "reasoning" and req.needs_quality:
        return "o4-mini"              # 推理模型
    if req.stream and req.user_tier == "free":
        return "claude-haiku"         # 免费档走便宜模型
    return "claude-sonnet"            # 默认主力
  • 路由层与调用层解耦：统一封装 call_model(model, messages, stream)，内部按 model 名分发到 OpenAI/Anthropic/本地 Ollama 的 client。
  • fallback 链：主模型 429/超时自动降级到备用模型；用 Zod/Pydantic 定义 schema 抹平各 provider 结构化输出差异。
  • 纯路由一个 if/else + 字典足够，别为简单路由引入重型框架；带工具、带检索的复杂编排才用 LangChain/LangGraph。
  • Node/Express 侧模式一致：用 Readable/Transform 把 async iterator 转成 text/event-stream，用 p-limit/bottleneck 限流，AbortController 透传上游；Vercel AI SDK 的 streamText 在 Node/Edge 运行时直接产出标准 Response，是最省事的 Node 后端方案。

本库真实落地（源码核对，2026-11-04）

  • 本库的「流式」是声明了但没实现——这是最容易误导客户端的地方（rag/serve.py L288 / L323，本次读源码）：
    python class ChatCompletionRequest(BaseModel): model: str = MODEL_ID messages: list[ChatMessage] temperature: float | None = None max_tokens: int | None = None top_p: float | None = None stream: bool = False
    stream 字段只是声明，chat_completions() 里没有任何 stream=True 分支，始终返回完整的 chat.completion 对象。客户端传 stream: true 不会报错，只是没有增量输出——这类「静默降级」比直接 400 更难查。
  • 真正的流式实现样本在 projects/agent-service-toolkit：src/service/service.py 顶部 import 了 from collections.abc import AsyncGenerator 与 from fastapi.responses import StreamingResponse，用 async def + 生成器逐 token 推送。
  • 同步服务也不是没好处：本库单问题耗时约 3 分钟（本次实测），用户等的是「一个完整答案」；流式会把「检索+重排+门禁」这段静默等待暴露成「首字延迟很高」。先想清楚等待发生在哪，再决定要不要流式。
  • 和课件讲法的差异：课件讲流式几乎都是「SSE 逐 token」。本库的教训是：在 RAG 里，首 token 之前的检索链才是等待主体，应当流式推送「正在检索/正在重排」这类阶段事件，而不只是 token。
  • 本库暂无：没有 SSE 阶段事件、没有取消语义（客户端断开后后端仍跑完），/v1/completions 同样是整段返回。
