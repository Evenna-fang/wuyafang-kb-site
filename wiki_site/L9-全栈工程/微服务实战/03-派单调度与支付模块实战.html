本文以智链云途物流为背景，把运单从创建、派送到支付结算串成一条可落地链路。示例基于 Spring Boot 2.7.18、Spring Cloud 2021.0.8、Spring Cloud Alibaba 2021.0.5.0、Nacos 2.2.3、RocketMQ 4.9.7、Redis 6/7 和 JDK 17。代码使用标准 Spring Boot API，可直接放入对应服务工程；本文没有连接真实中间件做联调，接入时需要替换环境变量中的地址和商户配置。

2.1 业务模型与数据表

运单至少包含运单号、订单号、取货点、送货点、状态、指定时间窗和当前骑手。骑手记录服务区域、在线状态、当前单量、最大并发量以及最近上报时间。位置数据放 Redis GEO，业务属性仍放 MySQL；不要把 GEO 当作完整的骑手主数据。

2.2 位置上报与 GEO 检索

Redis GEO 的 member 没有独立 TTL，GEOADD 写入后不会自动过期。因此服务需要把最后上报时间写到 Hash 或数据库，查询后过滤超过阈值的骑手，并用定时任务清理离线 member。Redis 6.2 提供 GEOSEARCH，旧版本可使用 GEORADIUS，生产环境应确认服务器版本。

package com.wuyafang.delivery.location;

import lombok.RequiredArgsConstructor;
import org.springframework.data.geo.Circle;
import org.springframework.data.geo.Distance;
import org.springframework.data.geo.GeoResult;
import org.springframework.data.geo.Metrics;
import org.springframework.data.redis.connection.RedisGeoCommands;
import org.springframework.data.redis.core.StringRedisTemplate;
import org.springframework.stereotype.Service;

import java.util.List;

@Service
@RequiredArgsConstructor
public class RiderLocationService {
    private static final String GEO_KEY = "rider:geo:online";
    private static final String LAST_KEY = "rider:last-location:";
    private final StringRedisTemplate redis;

    public void report(long riderId, double longitude, double latitude, long epochSecond) {
        redis.opsForGeo().add(GEO_KEY,
                new RedisGeoCommands.GeoLocation<>(String.valueOf(riderId),
                        new org.springframework.data.geo.Point(longitude, latitude)));
        redis.opsForHash().put(LAST_KEY + riderId, "epoch", String.valueOf(epochSecond));
    }

    public List<GeoResult<RedisGeoCommands.GeoLocation<String>>> nearby(
            double longitude, double latitude, double radiusKm) {
        return redis.opsForGeo().radius(GEO_KEY,
                new Circle(new org.springframework.data.geo.Point(longitude, latitude),
                        new Distance(radiusKm, Metrics.KILOMETERS)),
                RedisGeoCommands.GeoRadiusCommandArgs.newGeoRadiusArgs()
                        .includeDistance().sortAscending().limit(50));
    }
}

对应的 Redis 命令如下，顺序始终是经度、纬度，反过来会把位置写到错误半球。GEOSEARCH 可按圆心半径检索并返回距离。

GEOADD rider:geo:online 121.4737 31.2304 10001
GEOSEARCH rider:geo:online FROMLONLAT 121.4737 31.2304 BYRADIUS 5 km ASC COUNT 50 WITHDIST
GEOSEARCH rider:geo:online FROMMEMBER 10001 BYRADIUS 3 km ASC

2.3 派单策略与评分

第一层先过滤：骑手在线、最近上报小于 90 秒、当前单量小于最大并发、没有同一运单锁。第二层按距离排序，距离相同再比较负载。综合评分可采用 0.5×距离分 + 0.3×负载分 + 0.2×服务分，所有分数归一化到 0 到 1，避免不同量纲直接相加。服务分来自近 30 天准时率和取消率，不能用一次评价决定结果。

flowchart TD
  A[创建运单] --> B[读取取货点]
  B --> C[GEOSEARCH 半径检索]
  C --> D[过滤离线/超载/过期位置]
  D --> E[计算距离与负载评分]
  E --> F{候选为空?}
  F -- 是 --> G[扩大半径或进入人工池]
  F -- 否 --> H[按评分取前N]
  H --> I[抢占接单锁]
  I --> J{DB条件更新成功?}
  J -- 是 --> K[发送派单通知]
  J -- 否 --> L[尝试下一候选]

接单锁只用于减少并发竞争，不能替代数据库条件更新。推荐使用 rider:accept:{waybillId}，值为请求幂等号，短 TTL 例如 10 秒。数据库更新必须约束 status='已派单' AND rider_id=?，成功行数为 1 才算接单成功。

package com.wuyafang.delivery.assignment;

import lombok.RequiredArgsConstructor;
import org.springframework.data.redis.core.StringRedisTemplate;
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;

import java.time.Duration;

@Service
@RequiredArgsConstructor
public class AcceptService {
    private final StringRedisTemplate redis;
    private final WaybillMapper waybillMapper;

    @Transactional
    public boolean accept(long waybillId, long riderId, String requestId) {
        String key = "rider:accept:" + waybillId;
        Boolean locked = redis.opsForValue().setIfAbsent(key, requestId, Duration.ofSeconds(10));
        if (!Boolean.TRUE.equals(locked)) return false;
        int changed = waybillMapper.accept(waybillId, riderId);
        if (changed != 1) {
            redis.delete(key);
            return false;
        }
        return true;
    }
}

package com.wuyafang.delivery.assignment;

import org.apache.ibatis.annotations.Mapper;
import org.apache.ibatis.annotations.Update;

@Mapper
public interface WaybillMapper {
    @Update("UPDATE delivery_order SET status='已接单', updated_at=NOW() " +
            "WHERE id=#{waybillId} AND rider_id=#{riderId} AND status='已派单'")
    int accept(long waybillId, long riderId);
}

2.4 超时重新调度

派单成功后发送 RocketMQ 延迟消息。RocketMQ 4.9.x 使用固定 delayLevel，不能把任意毫秒数直接传给消息；例如 level 4 约 10 秒，具体映射以 broker 配置为准。消费者读取运单状态，仍为已派单才回滚到待派单并重新选择骑手。Redis Keyspace Notification 受配置、重启和集群影响，适合补偿提醒，不应作为唯一超时机制。

package com.wuyafang.delivery.assignment;

import org.apache.rocketmq.client.producer.DefaultMQProducer;
import org.apache.rocketmq.common.message.Message;
import org.springframework.stereotype.Component;

import java.nio.charset.StandardCharsets;

@Component
public class AssignmentTimeoutProducer {
    private final DefaultMQProducer producer;
    public AssignmentTimeoutProducer(DefaultMQProducer producer) { this.producer = producer; }
    public void send(long waybillId) throws Exception {
        Message message = new Message("waybill-timeout", "timeout", String.valueOf(waybillId),
                String.valueOf(waybillId).getBytes(StandardCharsets.UTF_8));
        message.setDelayTimeLevel(4);
        producer.send(message);
    }
}

package com.wuyafang.delivery.assignment;

import lombok.RequiredArgsConstructor;
import org.apache.rocketmq.spring.annotation.RocketMQMessageListener;
import org.apache.rocketmq.spring.core.RocketMQListener;
import org.springframework.stereotype.Component;

@Component
@RequiredArgsConstructor
@RocketMQMessageListener(topic = "waybill-timeout", consumerGroup = "dispatch-timeout")
public class AssignmentTimeoutConsumer implements RocketMQListener<String> {
    private final WaybillMapperExt mapper;
    @Override public void onMessage(String body) {
        long id = Long.parseLong(body);
        mapper.resetIfWaiting(id); // UPDATE ... WHERE status='已派单'
    }
}

3.1 支付架构与支付单

支付单独立于订单，保存支付号、订单号、金额（分）、渠道、状态、第三方交易号、通知次数和最后通知时间。金额使用整数分或 BigDecimal，禁止 double。创建支付单时校验订单归属、金额和可支付状态，返回渠道所需参数；绝不把支付宝私钥返回前端。

密钥从环境变量或密钥管理服务注入，示例只展示属性绑定，不读取、打印或提交真实密钥。

package com.wuyafang.pay.api;

import com.alipay.api.AlipayClient;
import com.alipay.api.request.AlipayTradePagePayRequest;
import lombok.RequiredArgsConstructor;
import org.springframework.web.bind.annotation.*;

@RestController
@RequiredArgsConstructor
@RequestMapping("/pay")
public class PayController {
    private final AlipayClient client;
    private final PayProperties properties;

    @PostMapping("/alipay/page")
    public String page(@RequestParam String paymentNo, @RequestParam String subject,
                       @RequestParam String totalAmount) throws Exception {
        AlipayTradePagePayRequest request = new AlipayTradePagePayRequest();
        request.setReturnUrl(properties.returnUrl());
        request.setNotifyUrl(properties.notifyUrl());
        request.setBizContent("{\"out_trade_no\":\"" + paymentNo + "\"," +

正式代码应使用 JSON 序列化构造 bizContent，并对 subject 做长度与字符校验。沙箱联调时配置网关地址、appId、回调地址和支付宝公钥；回调地址必须可被公网访问，内网环境可用受控隧道。

3.2 异步通知、验签与幂等

通知接口先验签，再核对 app_id、seller_id、商户订单号、金额和交易状态。TRADE_SUCCESS 才能完成支付；TRADE_FINISHED 还要根据业务是否允许退款后完成。验签通过后，在本地事务中锁定支付单、比较状态并写入第三方交易号，提交成功后返回 success。如果业务更新失败，返回非 success 让渠道重试。原始通知参数可脱敏落库，便于审计。

package com.wuyafang.pay.notify;

import com.alipay.api.AlipayApiException;
import com.alipay.api.internal.util.AlipaySignature;
import jakarta.servlet.http.HttpServletRequest;
import lombok.RequiredArgsConstructor;
import org.springframework.web.bind.annotation.*;

import java.util.HashMap;
import java.util.Map;

@RestController
@RequiredArgsConstructor
public class AlipayNotifyController {
    private final PayProperties properties;
    private final PaymentService paymentService;

    @PostMapping("/pay/alipay/notify")
    public String notify(HttpServletRequest request) throws AlipayApiException {
        Map<String, String> params = new HashMap<>();
        request.getParameterMap().forEach((k, v) -> params.put(k, v[0]));
        boolean valid = AlipaySignature.rsaCheckV1(params, properties.alipayPublicKey(),
                "UTF-8", "RSA2");
        if (!valid || !properties.appId().equals(params.get("app_id"))) return "failure";
        if (!properties.sellerId().equals(params.get("seller_id"))) return "failure";
        if (!"TRADE_SUCCESS".equals(params.get("trade_status"))) return "success";
        if (!paymentService.amountMatches(params.get("out_trade_no"), params.get("total_amount"))) return "failure";
        paymentService.markPaid(params.get("out_trade_no"), params.get("trade_no"), params.get("gmt_payment"));
        return "success";
    }
}

markPaid 必须带条件 WHERE status IN ('WAIT_PAY','PAYING')，重复通知更新行数为 0 时仍返回 success。金额比较使用分转 BigDecimal 后精确比较，禁止字符串包含判断。主动查询任务按支付创建时间和状态扫描，调用 alipay.trade.query；对账文件下载后按商户订单号核对金额和状态，差异进入人工工单，不能自动覆盖已退款记录。

package com.wuyafang.pay.service;

import lombok.RequiredArgsConstructor;
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;

@Service
@RequiredArgsConstructor
public class PaymentService {
    private final PaymentMapper mapper;
    private final PaymentEventMapper eventMapper;

    @Transactional
    public void markPaid(String paymentNo, String tradeNo, String paidAt) {
        int changed = mapper.markPaid(paymentNo, tradeNo, paidAt);
        if (changed == 1) eventMapper.insertIfAbsent(paymentNo, "PAY_SUCCESS");
    }
    public boolean amountMatches(String paymentNo, String amount) {
        return mapper.amountEquals(paymentNo, amount);
    }
}

3.3 支付状态机与最终一致性

支付状态包含待支付、支付中、支付成功、支付失败、已关闭、已退款。支付成功事件不能直接在 HTTP 线程同步调用订单和派单服务，否则任一服务短暂不可用都会导致回调失败。支付单和本地消息表放在同一个数据库事务，后台投递器发送 RocketMQ，消费者以业务幂等键处理订单状态。

stateDiagram-v2
  [*] --> 待支付
  待支付 --> 支付中: 创建渠道订单
  支付中 --> 支付成功: 验签通知/主动查询
  支付中 --> 支付失败: 渠道失败
  待支付 --> 已关闭: 超时关闭
  支付成功 --> 已退款: 退款完成
  支付成功 --> 支付成功: 重复通知幂等

sequenceDiagram
  participant U as 用户
  participant P as 支付服务
  participant A as 支付宝
  participant DB as MySQL
  participant MQ as RocketMQ
  participant O as 订单服务
  U->>P: 创建支付单
  P->>A: pageExecute
  A-->>U: 收银台
  A->>P: notify(签名参数)
  P->>P: 验签/金额/商户核对
  P->>DB: 支付单+本地消息同事务
  P-->>A: success
  P->>MQ: 投递支付成功事件
  MQ->>O: 幂等更新订单
  O-->>MQ: ack

事务消息可以用于需要可靠发布的场景，但不要把支付宝远程支付调用放进 Seata AT；外部支付不受全局事务控制，XID 也不会天然跨异步消息传播。更简单可靠的做法是本地消息表加重试、死信和对账。

3.4 Seata AT 在下单扣库存与派单中的应用

Seata AT 一阶段由各分支事务执行 SQL，同时记录 undo_log，提交前注册分支；二阶段全局提交删除日志，回滚阶段按反向 SQL 恢复数据并检查脏写。订单库、库存库、运单库需要配置同一事务组和 TC 地址，所有表准备主键，数据库隔离级别和时钟保持稳定。

CREATE TABLE undo_log (
  branch_id BIGINT NOT NULL,
  xid VARCHAR(128) NOT NULL,
  context VARCHAR(128) NOT NULL,
  rollback_info LONGBLOB NOT NULL,
  log_status INT NOT NULL,
  log_created DATETIME NOT NULL,
  log_modified DATETIME NOT NULL,
  PRIMARY KEY (branch_id, xid)
);

package com.wuyafang.order.service;

import io.seata.spring.annotation.GlobalTransactional;
import lombok.RequiredArgsConstructor;
import org.springframework.stereotype.Service;

@Service
@RequiredArgsConstructor
public class OrderCreateService {
    private final OrderRepository orders;
    private final InventoryClient inventory;
    private final WaybillClient waybills;

    @GlobalTransactional(name = "create-order", rollbackFor = Exception.class)
    public void create(CreateCommand command) {
        long orderId = orders.insert(command);
        inventory.deduct(command.skuId(), command.quantity());
        waybills.createForOrder(orderId, command.pickupAddress(), command.deliveryAddress());
    }
}

AT 适合短事务和可补偿的数据库写入，长时间等待骑手接单、第三方支付、文件上传等不应放进全局事务。网络超时可能造成分支已提交但调用方未知，业务必须提供幂等键、状态查询和人工补偿。升级 Seata 时同步客户端、服务端和数据库脚本版本，监控锁等待、回滚次数和 undo_log 堆积。

4. 踩坑与最佳实践

3

4.1 可观测性与故障恢复设计

派单和支付都需要统一的业务追踪号。网关生成 traceId，订单号、运单号、支付单号在各服务日志中结构化输出，RocketMQ 消息体携带 eventId 和 traceId。这样可以从一次用户请求追到位置筛选、接单更新、支付通知和订单完成。日志中不要记录身份证号、银行卡号、支付宝私钥或完整回调参数；金额、订单号等敏感字段按审计要求脱敏。

位置上报接口应限制单个骑手的频率，例如每 3 秒一次，超过频率直接丢弃或只保留最新坐标。服务端校验经纬度范围、时间戳漂移和骑手在线状态。Redis 写入失败时不要把旧坐标标成新时间，调度服务应继续使用数据库中的最后心跳并降低候选优先级。对于长时间没有心跳的骑手，先标记疑似离线，再由定时任务确认，避免网络抖动造成大量派单失败。

候选计算可以分两阶段缓存：第一阶段只返回骑手 ID 和距离，第二阶段批量读取骑手负载、服务分和区域限制。不要为每个候选逐个调用远程服务，否则半径扩大时延迟会线性增长。评分结果带计算时间，超过 10 秒的结果不能直接用于接单。对于高峰期，调度线程池要设置有界队列，队列满时进入人工池并告警，而不是无限创建线程。

支付链路应把每一次状态变化写入支付流水表，字段包括旧状态、新状态、事件来源、请求号和发生时间。状态机只允许白名单迁移，例如已退款不能回到支付成功。支付关闭任务和主动查询任务要使用分布式锁，按支付单分片执行，避免多个实例重复查询同一渠道订单。对账差异必须保留原始文件摘要和比对结果，修复动作由有权限的运营人员审批。

对于 RocketMQ 消费者，业务幂等键应使用 paymentNo:eventType 或 waybillId:eventType，而不是消息 ID，因为重投时消息 ID 可能变化。消费者先写消费记录，再更新业务表，或者利用业务表唯一索引保证同一事件只生效一次。处理成功后才返回消费成功；发生数据库死锁或短暂网络错误时抛出异常触发重试，参数校验失败则进入死信并告警。死信处理工具必须支持人工重放和原因备注。

数据库索引也要围绕状态机设计。运单查询通常按状态、区域和更新时间过滤，可建立 (status, updated_at) 联合索引；接单更新通过主键定位后再判断状态，避免对状态列做范围扫描。支付单按 payment_no、out_trade_no 建唯一索引，通知表按 payment_no,event_type 建唯一约束。定时任务采用游标分页，不使用大 offset，以免历史支付单增长后扫描变慢。所有时间统一使用 UTC 存储，展示层再转换为用户时区，跨区域派送时尤其重要。

外部渠道调用必须设置连接和读取超时，并记录渠道响应码、耗时和重试次数。只对明确的网络异常重试，业务参数错误、余额不足或签名错误不应自动重试。支付创建接口使用客户端幂等号，服务端将其映射到支付单；同一幂等号再次请求时返回原支付单，而不是重新创建渠道订单。退款同样需要独立幂等号，并限制退款金额不超过可退余额。

压测场景至少包括一万个骑手同时上报位置、同一运单一百个并发接单、支付通知重复发送十次、支付通知先于订单回调到达、RocketMQ 消费者重启和 Redis 故障切换。验收指标应记录 P99 延迟、条件更新成功率、通知重试次数、死信数量和对账差异。压测数据使用虚拟订单和虚拟商户号，禁止把生产用户数据复制到测试环境。

第一，Redis GEO 只有经纬度和 member，没有 member 级过期时间；必须结合时间戳过滤，并设置离线清理任务。第二，GEO 的参数顺序是 longitude、latitude，移动端常把 latitude 放前面，接入层要统一 DTO 并增加中国城市坐标测试。第三，距离优先不等于最优派单，过载骑手会造成二次超时，评分中必须加入当前单量和准时率。

第四，Redis SETNX 锁丢失、续期或网络分区都可能发生，最终一致性依赖数据库条件更新和状态日志。第五，RocketMQ 延迟消息使用固定 delayLevel，不能假设任意延迟精度；消费失败需要重试和死信监控。第六，支付通知可能乱序、重复或延迟，验签成功也不代表金额正确，必须核对商户、订单、金额和状态。

第七，支付宝回调响应 success 前要确保本地事务提交；否则渠道停止重试会形成漏单。第八，主动查询和对账是通知链路的补偿，不是可选报表。第九，Seata AT 不覆盖支付宝远程调用，也不会自动跨 RocketMQ 异步边界传播 XID，支付场景仍采用本地消息表和对账。

上线前准备指标：派单候选为空率、接单条件更新失败率、位置过期比例、支付通知验签失败率、支付成功到订单完成的延迟、消息重试次数和对账差异金额。压测要覆盖同一运单多人抢单、重复回调、支付回调乱序、Redis 主从切换和 RocketMQ 重平衡。演练结束后检查状态机是否出现非法跳转，并通过补偿任务恢复可重试状态。

5. 小结

3

派单模块用 Redis GEO 做近邻候选，用评分模型选人，用短锁降低竞争，再用数据库条件更新保证唯一接单；超时通过 RocketMQ 延迟消息驱动重新调度。支付模块把支付单、验签、幂等、异步消息、主动查询和对账放在同一条可追踪链路中。Seata AT 能解决数据库短事务的一致性，但不能替代支付渠道的最终一致性设计。掌握这些边界后，智链云途可以在高并发和故障下保持订单、运单和资金状态可恢复。

  • 调度算法的真实约束不是「最短路径」，而是「已派给谁、多久没心跳、谁能收口」——所以本库的任务表有 attempt（被重领次数）与 fail_reason，这两个字段在课件派单模型里通常没有。
  • 和课件讲法的差异：课件的派单调度是「骑手抢单/超时改派 + 支付回调对账」；本库没有支付模块，唯一相关的「对账」是 receipt.py 的完成凭据（执行人声明的产物哈希与验证结果比对）。
  • 本库暂无：无支付链路、无计价规则、无派单的地理/时效优化；sweep() 的 TTL 回收在单机 SQLite 上够用，换成多实例需换成真正的分布式锁。
