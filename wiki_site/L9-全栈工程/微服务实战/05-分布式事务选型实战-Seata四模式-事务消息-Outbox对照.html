WHAT

七种方案先给结论

3

先给结论，细节在后文展开，关键结论后的方括号是文末"官方参考"的序号。

  1. 能用一个本地事务解决的，不要上分布式事务。 接单抢单、骑手单量加一、支付单状态迁移，都在单库内，用条件更新和唯一索引即可。
  2. 需要同步看到"全部成功或全部回滚"，且参与方都是自己控制的关系库：先考虑 Seata AT，因为它对业务代码侵入最小。但 AT 默认隔离级别是读未提交，写冲突靠全局锁串行化 [1]。热点行不适合。
  3. 参与方不是关系库、需要业务级冻结资源，或要避开全局锁：用 TCC。 代价是每个接口写三个方法，并且必须处理空回滚、悬挂、幂等三个问题 [3][4]。
  4. 流程长、有外部系统、无法提供 TCC 三接口：用 Saga。 它不保证隔离性，隔离问题要业务自己设计 [5][9]。
  5. XA 只在"迁移已有 XA 应用"或"必须由数据库保证强隔离"时考虑，分支 prepare 之后要阻塞等待，锁持有时间长，性能较差 [6]。
  6. 只需要"本地事务成功，则下游一定最终收到消息"：用事务消息或 Outbox，不要用全局事务。 这两者只保证上游与下游的最终一致，不保证下游处理成功 [7][10]。
  7. 调用第三方支付渠道的步骤，不放进任何全局事务。 渠道不受 Seata 控制，用本地消息表加重试、查询和对账。这与 03 篇的判断一致。

2. 先把问题讲清楚

3

2.1 什么叫"跨服务一致"

微服务拆分之后，每个服务拥有自己的数据库。microservices.io 对 Saga 模式的定义是：当每个服务有独立数据库、又不能使用两阶段提交（2PC）时，跨服务业务事务要拆成一系列本地事务 [9]。因此选型实际上是在回答三个问题：

  • 一致性强度：是要求任意时刻外部都看不到中间状态（强一致），还是允许短暂不一致、最终收敛（最终一致）。
  • 隔离性：全局事务进行到一半时，别的事务能不能读到或改到中间数据。
  • 侵入性与性能：业务代码要改多少，热点数据上能扛多少并发。

2.2 双写问题

03 篇的支付回调里有一个典型的双写：更新支付单，同时给订单服务发"支付成功"消息。数据库和消息中间件是两个系统，没有一个事务能同时覆盖。microservices.io 的 Transactional Outbox 页把它表述为：如何在更新数据库的同时，原子地向消息代理发送消息；2PC 往往不可行，因为数据库或消息代理可能不支持，并且让服务同时耦合两者通常不可取 [10]。

先更新库再发消息，发送失败或进程宕机，下游永远收不到；先发消息再更新库，库更新失败，下游收到了一个不存在的事实。事务消息、本地消息表和 Outbox 都是对这个问题的不同解法。

2.3 隔离性是 Saga 类方案的短板

没有隔离性意味着并发的全局事务可能互相看到中间状态。Seata 文档给了一个例子：用户 A 先被入账，B 的余额随后被扣减；如果 A 在事务提交前把这笔钱花掉，回滚时就无法补偿 [5]。microservices.io 也把"缺少隔离性"列为 Saga 的主要缺点，并说明需要用对策（countermeasures）来补，但该页面没有列出具体对策，只指向作者的书 [9]。所以后文凡涉及"对策"的部分，都标明是业务设计而非框架提供的能力。

HOW

2

3. Seata AT：对业务最透明，隔离最弱

3

3.1 原理

AT 适用于支持本地 ACID 事务的关系库，并要求 Java 应用通过 JDBC 访问 [1]。

  • 一阶段：在同一个本地事务里提交业务数据和回滚日志（UNDO_LOG），然后释放本地锁和连接。具体步骤是解析 SQL、记录更新前镜像、执行更新、记录更新后镜像、写入 UNDO_LOG、向 TC 申请全局锁、提交本地事务并上报结果 [1]。
  • 二阶段提交：异步快速完成，批量删除 UNDO_LOG [1]。
  • 二阶段回滚：按 XID 和 Branch ID 取出 UNDO_LOG，比对后镜像与当前数据，再由前镜像生成回滚 SQL [1]。

因为一阶段就提交了本地事务，数据库行锁很快释放，这是 AT 比 XA 性能好的原因。代价是它另外引入了一把"全局锁"。

3.2 全局锁与写隔离

一阶段提交本地事务之前必须先拿到全局锁，拿不到就不能提交，并且会重试，超过超时时间则回滚本地事务并释放本地锁 [1]。官方举的例子是两个事务先后更新同一字段：后者因全局锁被前者持有而不断重试，直到前者全局提交并释放全局锁。由于全局锁一直由前者持有，所以不存在脏写 [1]。

回滚路径有一个容易被忽略的细节：前者回滚时需要本地锁来还原数据，而本地锁正被等全局锁的后者持有，于是前者反复重试，直到后者超时回滚并释放本地锁 [1]。这意味着热点行上并发的全局事务会互相等待直到超时。

3.3 读隔离

本地库隔离级别是读已提交或更高，所以全局事务的默认隔离级别是读未提交 [1]。要读已提交，目前靠 SELECT FOR UPDATE：执行时申请全局锁，被占用则释放本地锁并重试，查询阻塞到拿到全局锁。出于性能考虑，只代理 SELECT FOR UPDATE，普通 SELECT 不处理 [1]。

这一条对业务的直接影响是：下单事务进行到一半时，别的请求用普通查询可能读到还没全局提交的库存。如果这个读取会影响业务判断（例如据此展示"已抢完"），就要在读取处加 FOR UPDATE，或者接受读未提交。

3.4 最小代码

03 篇已经给出了 @GlobalTransactional 下单示例，这里补上读已提交的写法。以下代码未实跑。

@Service
@RequiredArgsConstructor
public class InventoryQueryService {
    private final InventoryMapper inventoryMapper;

    // 需要读已提交语义时，走 FOR UPDATE，才会被 Seata 代理并申请全局锁
    @Transactional
    public int availableForUpdate(long skuId) {
        return inventoryMapper.selectAvailableForUpdate(skuId);
    }
}

-- InventoryMapper.selectAvailableForUpdate 对应的 SQL
SELECT available FROM inventory WHERE sku_id = ? FOR UPDATE;

3.5 边界

  • 参与方必须是支持本地事务的关系库，且经 JDBC 访问 [1]。Redis、RocketMQ、第三方 HTTP 接口都不在 AT 的覆盖范围内。
  • 全局事务期间不要有长时间等待，例如等骑手接单。03 篇已经强调这一点。
  • 回滚时如果发现数据已被当前事务之外的操作改动，官方页面只说需要"以不同策略处理"，没有展开 [1]。工程上等于要有人工兜底，所以必须监控回滚失败和 UNDO_LOG 堆积。

4. TCC：自己写三个阶段，换来更细的控制

3

4.1 原理

每个分支事务都必须满足两阶段模型：一阶段 prepare（Try），二阶段 commit（Confirm）或 rollback（Cancel）。TCC 不依赖底层资源的事务能力，三个阶段的逻辑全部由开发者实现 [2]。与 AT 的区别就在这里：AT 的二阶段补偿由框架自动生成，TCC 则由业务自己写 [2]。

用法上，在 Try 方法上标注 @TwoPhaseBusinessAction，参数 name 是全局唯一的 TCC bean 名，commitMethod 和 rollbackMethod 指定另外两个方法；参与者是本地 bean 时，接口上还要加 @LocalTCC；上下文参数用 @BusinessActionContextParameter 标注传入，BusinessActionContext 里能取到 xid、branchId、actionName 和 actionContext [3]。

4.2 库存冻结的业务设计

TCC 的 Try 不能直接扣最终值，而是"预留"。以秒杀之外的普通下单扣库存为例：

阶段 操作 数据变化
Try 条件冻结 available = available - n，frozen = frozen + n，条件 available >= n
Confirm 确认扣减 frozen = frozen - n
Cancel 释放冻结 available = available + n，frozen = frozen - n

Try 提交后，别的事务立刻就能看到 available 已减少。预留资源对外可见，这就是 TCC 隔离性比 AT 的读未提交更可控的原因：中间状态是业务显式建模出来的，不是数据库行的原始中间值。

4.3 三个必须处理的问题

TCC 的二阶段由 TC 驱动，会遇到网络超时、乱序，所以必须面对三类问题。下面的定义和解法来自 Seata 官方博客 [4]。

幂等：提交或回滚阶段，若 TC 没收到分支事务的响应，会重试该操作，因此分支必须支持幂等。Seata 的做法是提交时先查 tcc_fence_log：记录已是 committed 则直接返回成功，无记录则插入新记录供后续重试检测 [4]。

空回滚：Try 阶段在某节点失败（官方例子是两节点集群中一个节点的 Try 没有执行），全局事务仍然对它发起 Cancel。此时没有东西可以回滚。Seata 在 Try 阶段向 tcc_fence_log 插入状态为 STATUS_TRIED 的记录；回滚时若记录不存在，则不执行回滚逻辑；若存在，把状态由 STATUS_TRIED 更新为 STATUS_ROLLBACKED，更新成功后才执行回滚 [4]。

悬挂：网络问题导致资源管理器先收到 Cancel、后收到 Try，Try 随后预留了资源，却再也没人释放。Seata 的做法是：回滚前先查该 xid 的记录，若无记录，则插入状态为 STATUS_SUSPENDED 的记录且不执行回滚；之后 Try 再插入同一主键时会冲突，prepare 失败，预留的资源就不会产生 [4]。

sequenceDiagram
  participant TC as TC
  participant RM as 库存服务
  participant F as tcc_fence_log
  Note over TC,RM: 正常路径
  TC->>RM: Try
  RM->>F: 插入 TRIED(与冻结同一本地事务)

  TC->>RM: Cancel(先到)

4.4 防护机制的开关与代价

这套防护由 @TwoPhaseBusinessAction 的 useTCCFence 属性控制，默认值是 false，即默认关闭 [4]。如果沿用默认值写 TCC，空回滚、悬挂都没有保护，这是实践中很容易漏掉的一点。

使用围栏有两个前提：Try 阶段必须提交本地事务，资源以中间状态落库；业务操作与 tcc_fence_log 的操作必须在同一个本地事务内成功或失败，这靠 Seata 的代理数据源实现 [4]。也就是说，围栏只对"落在关系库里的资源预留"有效；如果 Try 阶段是调用第三方接口，围栏保证不了什么。博客还指出 queryTCCFenceDO 使用 for update，会对记录加锁，其对并发性能的影响文中没有讨论 [4]。围栏表需要维护清理，博客未说明清理机制，需要查阅所用版本的配置 [4]。

围栏表字段为 xid、branch_id、action_name、status、gmt_create、gmt_modified，主键 (xid, branch_id)，状态值 1 到 4 分别对应 TRIED、COMMITTED、ROLLBACKED、SUSPENDED [4]。以下建表语句是按这些字段整理的，具体以所用 Seata 版本 script 目录里的官方脚本为准，未实跑。

CREATE TABLE IF NOT EXISTS tcc_fence_log (
  xid           VARCHAR(128) NOT NULL,
  branch_id     BIGINT       NOT NULL,
  action_name   VARCHAR(64)  NOT NULL,
  status        TINYINT      NOT NULL COMMENT '1:TRIED 2:COMMITTED 3:ROLLBACKED 4:SUSPENDED',
  gmt_create    DATETIME(3)  NOT NULL,
  gmt_modified  DATETIME(3)  NOT NULL,
  PRIMARY KEY (xid, branch_id),
  KEY idx_gmt_modified (gmt_modified),
  KEY idx_status (status)
) ENGINE = InnoDB DEFAULT CHARSET = utf8mb4;

4.5 最小代码

以下代码未实跑，注解及参数名依据官方用户文档和博客 [3][4]。

@LocalTCC
public interface InventoryTccAction {

    @TwoPhaseBusinessAction(name = "inventoryReserve",
            commitMethod = "commit", rollbackMethod = "rollback", useTCCFence = true)
    boolean tryReserve(BusinessActionContext ctx,
                       @BusinessActionContextParameter(paramName = "skuId") long skuId,
                       @BusinessActionContextParameter(paramName = "qty") int qty);

    boolean commit(BusinessActionContext ctx);

    boolean rollback(BusinessActionContext ctx);
}

@Service
@RequiredArgsConstructor
public class InventoryTccActionImpl implements InventoryTccAction {
    private final InventoryMapper mapper;

    @Override
    public boolean tryReserve(BusinessActionContext ctx, long skuId, int qty) {
        // UPDATE inventory SET available=available-?, frozen=frozen+? WHERE sku_id=? AND available>=?
        return mapper.freeze(skuId, qty) == 1;
    }

    @Override
    public boolean commit(BusinessActionContext ctx) {
        long skuId = Long.parseLong(String.valueOf(ctx.getActionContext("skuId")));
        int qty = Integer.parseInt(String.valueOf(ctx.getActionContext("qty")));
        // UPDATE inventory SET frozen=frozen-? WHERE sku_id=?
        return mapper.confirm(skuId, qty) >= 0;
    }

    @Override
    public boolean rollback(BusinessActionContext ctx) {
        long skuId = Long.parseLong(String.valueOf(ctx.getActionContext("skuId")));
        int qty = Integer.parseInt(String.valueOf(ctx.getActionContext("qty")));
        // UPDATE inventory SET available=available+?, frozen=frozen-? WHERE sku_id=?
        return mapper.release(skuId, qty) >= 0;
    }
}

注意：官方用户文档里 doTransactionCommit 示例声明了返回 String 但没有 return，直接复制会编译失败，这是文档示例的小瑕疵 [3]。

5. Saga：长流程与外部系统

3

5.1 原理

Saga 把长事务拆成一串本地事务，每个参与者提交自己的本地事务；任一参与者失败，框架对此前已成功的参与者执行补偿。正向服务和补偿服务都由业务实现 [5]。

Seata 提供两种实现 [5]：

  • 状态机引擎：用 JSON 状态语言定义流程，每个节点可配置补偿节点，支持单选、并发、子流程、参数转换、异常捕获。
  • 注解方式：在业务接口上用 @CompensationBusinessAction，由 compensationMethod 指定补偿方法，再配合 @GlobalTransactional 启动全局事务。

恢复策略有两种：向后恢复是节点异常时路由到补偿触发器，由引擎反向执行已成功节点的补偿，且补偿不会自动触发，是否回滚由 JSON 中的路由决定；向前恢复是对失败的状态机实例调用 forward 接口重新启动，继续执行直到最终一致 [5]。状态机实例记录在本地数据库，崩溃重启后由 Seata Server 触发恢复，提交或回滚失败时 Server 会持续重试 [5]。

5.2 编排与协同

microservices.io 把 Saga 的协调方式分为两类 [9]：

  • 编排（Orchestration）：一个编排器告诉各参与方执行哪个本地事务。
  • 协同（Choreography）：每个本地事务发布领域事件，触发其他服务的本地事务。

派单场景的"创建运单、锁定骑手、通知用户"适合编排，因为状态流转复杂、需要集中看进度；支付成功后"订单置已付款、派单服务开始调度、积分服务发积分"适合协同，各下游独立订阅同一事件。

5.3 适用与缺点

官方列出的适用场景是流程长、环节多，以及参与方是其他公司或遗留系统，无法提供 TCC 要求的三个接口 [5]。优点是一阶段直接提交本地事务、不持有锁，性能高，补偿服务较易实现 [5]。缺点是不保证隔离性 [5]。

microservices.io 还指出，发起 Saga 的同步请求如何把结果告诉客户端也是需要设计的问题，有三种做法：完成后再返回；先返回 orderID 让客户端轮询；先返回 orderID 再通过 WebSocket 或 Webhook 推送 [9]。云岚到家的秒杀查询接口返回"排队中、成功、失败"，就是第二种。

5.4 最小代码

以下注解式示例未实跑。页面只确认了注解名和 compensationMethod 属性 [5]，其他属性以所用版本为准。

public interface RiderLockAction {

    @CompensationBusinessAction(compensationMethod = "unlockRider")
    boolean lockRider(long riderId, String waybillNo);

    boolean unlockRider(long riderId, String waybillNo);
}

补偿方法必须自行保证幂等，并能处理"正向方法没执行过"的情况，原因与 TCC 的空回滚相同。

6. XA：数据库保证强隔离，代价是阻塞

3

Seata XA 利用数据库对 XA 协议的支持管理分支。执行阶段，业务 SQL 在 XA 分支内执行；分支完成后执行 XA prepare，由资源保证结果持久化，之后故障也不影响回滚；完成阶段对各分支执行 XA commit 或 XA rollback [6]。官方称，由资源自身支持 XA 协议可以从任何角度保证数据的有效隔离，从而满足全局一致 [6]。

与 AT 的使用方式几乎一致，区别只在数据源代理类型，XA 使用 DataSourceProxyXA，AT 使用 DataSourceProxy [6]。以下代码未实跑。

@Bean("dataSourceProxy")
public DataSource dataSource(DruidDataSource druidDataSource) {
    return new DataSourceProxyXA(druidDataSource);
}

限制很明确：分支完成 XA prepare 后进入阻塞阶段，必须等 XA commit 或 XA rollback，事务资源长时间不释放，锁周期长；应用层无法介入，官方评价性能较差；适用场景是把基于 XA 协议的旧应用迁移到 Seata，或不适配 AT 的数据库应用 [6]。对秒杀这类高并发场景，基本可以排除。

7. RocketMQ 事务消息：可靠发布，不是分布式事务

3

7.1 机制

RocketMQ 5.x 官方文档描述的流程共七步 [7]：

  1. 生产者向 Broker 发送消息。
  2. Broker 保存消息并标记为不可投递，即半事务消息，返回 ACK。
  3. 生产者执行本地事务。
  4. 生产者发送第二次 ACK，结果为 Commit 或 Rollback；Commit 则消息可投递，Rollback 则丢弃。
  5. 若 Broker 没收到第二次 ACK，或状态是 Unknown（网络断开、生产者重启），Broker 等待一段时间后向生产者集群发起事务回查。
  6. 生产者检查对应本地事务的执行结果。
  7. 生产者按结果再次发送 ACK。

关键参数来自参数限制页 [8]：事务异常检查间隔（回查间隔）默认 60 秒；半消息最大超时时间默认 4 小时，超时仍无结果会被强制回滚；RMQ_SYS_TRANS_HALF_TOPIC 和 RMQ_SYS_TRANS_OP_HALF_TOPIC 是系统保留名，不能用作 Topic 名。最大回查次数在该页没有给出数值。

7.2 它保证什么，不保证什么

官方限制说明得很清楚 [7]：

  • 事务消息只保证生产端与下游分支的事务一致，不保证消费结果与上游结果一致，消费者要自己正确处理并配置消费重试。
  • 只保证最终一致。消息投递给消费者之前，上游与下游状态可能不一致，所以只适用于能接受异步执行的场景。
  • 事务消息只能发送到 MessageType 为 Transaction 的 Topic。

使用注意：本地事务返回未知结果会触发大量回查，拖慢性能；回查时如果事务仍在执行，应保持 Unknown，不要提前返回 Commit 或 Rollback [7]。

8. 本地消息表与 Outbox

3

8.1 做法

microservices.io 的 Transactional Outbox 模式：服务在更新业务实体的同一个本地事务里，把要发送的消息存进同库的 outbox 表，再由一个独立的消息中继（Message Relay）读取并发给消息代理 [10]。保证是"消息当且仅当数据库事务提交时才会被发送"，并且消息按应用写入的顺序进入代理 [10]。

中继有两种实现：事务日志追踪和轮询发布者 [10]。03 篇 3.3 节的"后台投递器"属于轮询发布者。

8.2 缺点必须面对

两个缺点来自官方页面 [10]：一是开发者可能更新了数据库却忘记写 outbox；二是中继可能重复发布，例如它发布之后、记录已发布状态之前崩溃，重启后会再发一次。因此消费者必须幂等，比如记录已处理的消息 ID。

8.3 用 Debezium 代替轮询

如果不想自己写轮询投递器，可以用 Debezium 读取数据库日志并路由 outbox 表。Debezium 的 Outbox Event Router 要求默认列 id、aggregatetype、aggregateid、type、payload；aggregatetype 决定 topic 名，默认路由为 outbox.event.${routedByValue}，aggregateid 作为消息 key 以保证分区内顺序 [11]。官方说明 outbox 表上的变更预期都是 INSERT，DELETE 事件会被自动过滤，遇到 UPDATE 的行为由 table.op.invalid.behavior 控制，默认 warn [11]。页面提到可用 id 去重 [11]，但没有直接说明投递语义，也没有说明插入后能否删行，这两点需要另行确认。Debezium 通常搭配 Kafka Connect，本库的消息中间件是 RocketMQ，引入前要评估运维成本，本篇不展开。

8.4 最小代码

以下为本库自拟的最小结构，沿用 Debezium 的默认列名以便将来迁移，未实跑。

@Transactional
public void onPaymentNotify(PaymentNotify n) {
    paymentMapper.markSuccessIfPaying(n.getPayNo());           // 条件更新，天然幂等
    outboxMapper.insert(Outbox.of("payment", n.getOrderNo(),   // 同一个本地事务
            "PaymentSucceeded", n.toJson()));
}

// 轮询发布者：按创建时间取待发送，发送成功再标记；崩溃会重复发送，下游以 msg_id 去重
@Scheduled(fixedDelay = 500)
public void relay() {
    for (Outbox o : outboxMapper.listPending(100)) {
        mqTemplate.syncSend("PAYMENT_EVENT", o.toMessage());
        outboxMapper.markSent(o.getId());
    }
}

多实例部署时，listPending 要么加行锁跳过已锁行，要么按分片领取，否则同一条消息会被多个中继重复取走。重复发送无害，但会放大下游压力。

3

只要引入最终一致，就要把"出错后会怎样"当作交付内容。以下清单可直接用作测试用例。

11.1 失败注入

注入点 预期结果 检查什么

AT：回滚前数据被他人改动 回滚校验失败 是否告警并进入人工处理 [1]

11.2 对账清单

  • 库存守恒：初始库存等于已售加冻结加可用加人工调整，TCC 场景下 frozen 长期大于 0 要排查悬挂和未完成的全局事务。
  • 围栏表：tcc_fence_log 中状态长期停在 TRIED 的记录；SUSPENDED 记录数量异常增长，说明乱序频繁。
  • UNDO_LOG：堆积量与存活时间，超过全局事务超时仍存在的记录。
  • 支付单与订单：支付成功单对应订单必须为已付款，不一致的进入补偿队列；渠道流水逐日比对。
  • Outbox：status=0 且创建时间超过阈值的记录数，这个指标是中继是否卡住的第一信号。
  • 消费幂等表：去重命中率突然升高，往往意味着上游在重复发送。
  • 死信队列：每条死信必须有处理人、原因和结论，并有重放脚本。

12. 常见误区

3
  1. 以为事务消息等于分布式事务。 它只保证上游本地事务与"消息可被投递"的一致，下游处理结果不在保证范围内 [7]。
  2. 把 Redis、HTTP 调用放进 @GlobalTransactional。 AT 只管关系库 JDBC [1]。
  3. TCC 忘了开 useTCCFence。 默认是 false [4]，空回滚和悬挂都没有保护。
  4. 在 TCC 的 Try 里调第三方接口并指望围栏兜底。 围栏要求业务操作与围栏表在同一个本地事务 [4]，外部调用不满足。
  5. 认为 AT 没有隔离问题。 它避免了脏写，但默认读未提交，普通 SELECT 看到的是别人未全局提交的数据 [1]。
  6. Saga 补偿只写正向的反操作。 补偿还要处理"正向没执行"和"补偿重复执行"，并且补偿期间别的事务可能已经读到中间状态 [5][9]。
  7. Outbox 只在发送成功后才记录，认为不会重复。 中继崩溃必然产生重复 [10]。
  8. 回查器直接返回 Rollback。 回查时本地事务可能还在跑，应保持 Unknown [7]。
  9. 把 4.x 与 5.x 的参数混用。 回查间隔、超时等数值取自 5.x 文档页 [8]，4.9.7 需另行核对。
  10. 用分布式事务掩盖拆分不当。 两个服务总是要一起改同一份数据，往往说明边界划错了，应先考虑合并或重新划分。

13. 小结

3

选型可以压缩成四步判断：能否单库本地事务；是否涉及外部系统；是否有热点或需要业务预留；是否必须强隔离。绝大多数业务环节落在"本地事务加幂等加 Outbox 或事务消息加对账"，少数同步强要求的环节才用 AT 或 TCC，Saga 承担长流程，XA 基本留给遗留系统。每上一种方案，都同步写失败注入用例和对账指标，否则最终一致只存在于设计文档里。

    os.replace 在同一文件系统内是原子的，不会出现「写了一半的 registry」。这是最小可用的「本地事务」实现，对应课件里 TCC/Outbox 想解决的「中间态不可见」问题。

  • 知识库还有一个需要一致性思考的点：索引与源文件不同步。ingest.py 按 sha256 增量更新（内容变→删旧 chunk→写新 chunk），没有回滚机制——如果 ingest 中途失败，索引可能处于「部分新部分旧」的状态。本库目前的兜底是「重跑 ingest」（幂等），不是事务。
  • 和课件讲法的差异：课件对比 Seata AT/TCC/SAGA/XA 四模式；本库的经验是 在单机场景里「文件原子替换 + 幂等重跑」胜过任何分布式事务框架，上框架的前提是先有真正的多服务跨库写。
  • 本库暂无：多服务跨库写场景尚未出现（任务总线与知识库互不写对方数据），所以「选哪个分布式事务」在本库没有真问题，也没有答案。
