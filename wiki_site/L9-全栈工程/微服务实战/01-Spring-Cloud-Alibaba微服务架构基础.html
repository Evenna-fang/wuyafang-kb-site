WHY

1. 学习目标与版本基线

3

本篇以智链云途物流为背景，搭建一套可以迁移到云岚到家的基础平台。示例统一使用 JDK 17、Spring Boot 2.7.18、Spring Cloud 2021.0.8、Spring Cloud Alibaba 2021.0.5.0、Nacos 2.2.3、RocketMQ 4.9.7 和 Redis 6/7。需要特别说明：Alibaba 2021.0.5.0 的官方依赖管理原始验证组合是 Boot 2.6.13 与 Cloud 2021.0.5；课程将 Boot/Cloud 升到 2.7.18/2021.0.8，生产上线前必须在自己的依赖树和回归环境中验证兼容性，不能只看版本号。

1.1 微服务演进

单体应用把用户、订单、库存和配送放在同一个进程，部署简单但代码耦合、扩容只能整体扩容。SOA 以服务和企业服务总线拆分能力，强调契约、治理和异步集成，不过 ESB 容易成为性能瓶颈。微服务进一步按业务边界拆成可独立发布的小服务，每个服务拥有清晰数据责任，通过 HTTP、消息或 RPC 协作。拆分不是目的，必须配套注册发现、配置管理、网关、熔断、链路追踪、日志和自动化交付。物流系统可把运单、骑手、计价、支付、通知拆开，使高峰期只扩容下单和派单服务。

WHAT

2

1.2 生态全景

3

Spring Boot 提供自动配置和运行时；Spring Cloud Commons 提供 DiscoveryClient、LoadBalancer 等抽象；Spring Cloud Alibaba 将 Nacos、Sentinel、RocketMQ、Seata 接入 Spring 生态。Nacos 负责服务目录和配置，Gateway 做统一入口，Sentinel 负责流控与降级，OpenFeign 声明 HTTP 契约，LoadBalancer 从服务实例列表中选择节点。运维侧还应配合 Prometheus、Micrometer、SkyWalking 或 OpenTelemetry。

2. Nacos 服务注册与发现

3

2.1 原理和实例模型

应用启动时由 Nacos Discovery 自动配置创建 NamingService，向 Nacos 注册 service、group、cluster、ip、port 和 metadata。临时实例默认启用心跳：Nacos 1.x 主要走 HTTP 心跳，Nacos 2.x 在客户端和服务端之间增加 gRPC 长连接（同时保留兼容接口）；连接断开超过超时后实例被摘除。永久实例由服务端持久化，客户端不主动注销，适合数据库等固定节点，不能把短生命周期容器误注册成永久实例。发现调用先从本地缓存读取实例，缓存失效时请求 Nacos，再由 LoadBalancer 按权重、区域或随机策略选节点。

flowchart LR
  A[运单服务启动] --> B[Nacos NamingService]
  B --> C[(服务目录: service/group/cluster)]
  A -- Nacos2 gRPC心跳 --> B
  D[订单服务] -->|查询实例| B
  B --> D
  D --> E[LoadBalancer选择实例]
  E --> F[HTTP调用运单服务]
application.yml 与启动类
# order-service/src/main/resources/application.yml
server:
  port: 8081
spring:
  application:
    name: order-service
  cloud:
    nacos:
      discovery:
        server-addr: ${NACOS_ADDR:127.0.0.1:8848}
        namespace: logistics-dev
        group: LOGISTICS_GROUP
        ephemeral: true
        username: nacos
        password: nacos

package com.example.order;

import org.springframework.boot.SpringApplication;
import org.springframework.boot.autoconfigure.SpringBootApplication;
import org.springframework.cloud.client.discovery.EnableDiscoveryClient;

@SpringBootApplication
@EnableDiscoveryClient

    public static void main(String[] args) {
        SpringApplication.run(OrderApplication.class, args);
    }

永久实例可通过 ephemeral: false 或运维 API 管理，但必须配套实例健康检查和下线流程。命名空间用于环境隔离，group 用于业务分组，cluster 用于机房或可用区；三者任意一项不一致，客户端都会表现为“服务不存在”。

3. Nacos Config 配置中心

3

3.1 dataId、group 与动态刷新

配置读取键通常是 ${spring.application.name}-${spring.profiles.active}.${file-extension}，例如 order-service-dev.yaml。namespace 隔离 dev、test、prod，group 可按团队或业务线隔离。客户端首次从 Nacos 拉取配置并写入本地快照；长轮询监听 dataId 变化，收到变更后刷新 Environment。@RefreshScope 会重建标注 Bean，因此只把可热更新的超时、开关放进去，数据库连接池等对象仍应通过发布流程变更。bootstrap 上下文先于 application 上下文加载，必须引入 spring-cloud-starter-bootstrap。

  B -->|长轮询变更通知| C[客户端Environment]
  C --> D[@RefreshScope Bean重建]
  D --> E[订单服务读取新阈值]

4. Spring Cloud Gateway

3

Gateway 基于 Reactor Netty，在请求进入时依次执行 Route Predicate、局部 Filter 和 GlobalFilter。Predicate 判断路径、方法、Header、时间等条件；Filter 可改写路径、追加 Header、重试或限流。全局鉴权应校验 JWT 签名和过期时间，并把用户 ID 放入下游 Header，不能仅信任前端传来的 X-User-Id。跨域配置要明确允许的来源、方法和凭据，生产禁止 * 与 allow-credentials=true 同时使用。

flowchart LR
  U[用户端] --> G[Gateway]
  G --> P{Path Predicate}
  P --> F[GlobalFilter: JWT/CORS]
  F --> R1[order-service]
  F --> R2[dispatch-service]
  F --> R3[payment-service]

// GatewayRoutes.java；依赖 spring-cloud-starter-gateway、nacos-discovery
package com.example.gateway.config;

import org.springframework.cloud.gateway.route.RouteLocator;
import org.springframework.cloud.gateway.route.builder.RouteLocatorBuilder;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;

@Configuration
public class GatewayRoutes {
    @Bean
    RouteLocator routes(RouteLocatorBuilder builder) {
        return builder.routes()
            .route("order", r -> r.path("/api/orders/**")
                .filters(f -> f.stripPrefix(1).addRequestHeader("X-Gateway", "logistics"))
                .uri("lb://order-service"))
            .route("dispatch", r -> r.path("/api/dispatch/**")
                .filters(f -> f.stripPrefix(1))
                .uri("lb://dispatch-service"))
            .build();
    }
}

// JwtGlobalFilter.java；示例使用已配置的 TokenService，生产应接入成熟JWT库
package com.example.gateway.filter;

import org.springframework.cloud.gateway.filter.GlobalFilter;
import org.springframework.core.Ordered;
import org.springframework.http.HttpStatus;
import org.springframework.stereotype.Component;
import org.springframework.web.server.ServerWebExchange;
import reactor.core.publisher.Mono;

@Component
public class JwtGlobalFilter implements GlobalFilter, Ordered {
    private final TokenService tokenService;
    public JwtGlobalFilter(TokenService tokenService) { this.tokenService = tokenService; }
    @Override public Mono<Void> filter(ServerWebExchange exchange, org.springframework.cloud.gateway.filter.GatewayFilterChain chain) {
        String path = exchange.getRequest().getURI().getPath();
        if (path.startsWith("/api/auth/")) return chain.filter(exchange);
        String auth = exchange.getRequest().getHeaders().getFirst("Authorization");
        if (auth == null || !auth.startsWith("Bearer ")) return reject(exchange);
        String userId = tokenService.verifyAndGetSubject(auth.substring(7));
        if (userId == null) return reject(exchange);
        ServerWebExchange mutated = exchange.mutate().request(r -> r.headers(h -> h.set("X-User-Id", userId))).build();
        return chain.filter(mutated);
    }
    private Mono<Void> reject(ServerWebExchange exchange) { exchange.getResponse().setStatusCode(HttpStatus.UNAUTHORIZED); return exchange.getResponse().setComplete(); }
    @Override public int getOrder() { return -100; }
    public interface TokenService { String verifyAndGetSubject(String token); }
}

# application.yml：Gateway跨域与Redis令牌桶限流的基础配置
spring:
  cloud:
    gateway:
      globalcors:
        add-to-simple-url-handler-mapping: true
        cors-configurations:
          '[/**]':
            allowedOrigins: ["https://app.example.com"]
            allowedMethods: [GET, POST, PUT, DELETE, OPTIONS]
            allowedHeaders: ["*"]
            allowCredentials: true
      routes:
        - id: order
          uri: lb://order-service
          predicates: [Path=/api/orders/**]
          filters: [StripPrefix=1, RequestRateLimiter=redis-rate-limiter]

限流可用 Gateway RequestRateLimiter（Redis 令牌桶）拦住突发流量，再由 Sentinel 在服务内部保护数据库。网关只做粗粒度配额，用户维度和接口维度的细粒度规则放在业务服务，避免所有策略耦合在入口。

5. Sentinel 熔断与限流

3

Sentinel 把受保护方法抽象成资源，规则包含流控、熔断降级、系统保护和热点参数。滑动窗口按时间桶统计 QPS、并发数和异常比例；熔断状态机为 CLOSED、OPEN、HALF_OPEN，OPEN 期间快速失败，等待恢复时间后放少量探测请求。流控效果支持快速失败、Warm Up 预热和排队等待。控制台配置默认只在内存，重启会丢失；接入 Nacos DataSource 后才可持久化，但仍需验证规则序列化和权限。

stateDiagram-v2
  [*] --> CLOSED
  CLOSED --> OPEN: 异常比例/慢调用超阈值
  OPEN --> HALF_OPEN: 熔断等待时间到
  HALF_OPEN --> CLOSED: 探测成功
  HALF_OPEN --> OPEN: 探测失败

// OrderController.java；依赖 sentinel、sentinel-annotation-aspectj
package com.example.order.web;

import com.alibaba.csp.sentinel.annotation.SentinelResource;
import org.springframework.web.bind.annotation.*;

@RestController
@RequestMapping("/orders")
public class OrderController {
    private final OrderService orderService;
    public OrderController(OrderService orderService) { this.orderService = orderService; }
    @GetMapping("/{id}")
    @SentinelResource(value = "order:detail", blockHandler = "blocked", fallback = "fallback")
    public Order detail(@PathVariable Long id) { return orderService.find(id); }
    public Order blocked(Long id, com.alibaba.csp.sentinel.slots.block.BlockException e) { return Order.unavailable("系统繁忙"); }
    public Order fallback(Long id, Throwable e) { return Order.unavailable("服务降级"); }
    public interface OrderService { Order find(Long id); }
    public record Order(Long id, String status) { static Order unavailable(String s) { return new Order(0L, s); } }
}

6. OpenFeign 与 LoadBalancer

3

OpenFeign 以 Java 接口表达远程契约，name 对应 Nacos 服务名，底层由 Spring Cloud LoadBalancer 选实例。接口只放 DTO 和错误码，不把数据库实体直接暴露给跨服务调用。生产应启用超时、重试白名单和 fallback，并给每次调用加 traceId。

// DispatchClient.java；依赖 spring-cloud-starter-openfeign
package com.example.order.client;

import org.springframework.cloud.openfeign.FeignClient;
import org.springframework.web.bind.annotation.*;

@FeignClient(name = "dispatch-service", path = "/dispatch", fallbackFactory = DispatchFallback.class)
public interface DispatchClient {
    @GetMapping("/capacity/{riderId}")
    Capacity capacity(@PathVariable Long riderId);
    record Capacity(Long riderId, int activeOrders) {}
}

// OrderApplication.java 中启用Feign

3 
flowchart TB
  C[用户端/骑手端] --> G[Spring Cloud Gateway]
  G --> O[订单服务]
  G --> W[运单服务]
  G --> R[骑手与派单服务]
  G --> P[支付服务]

  W --> N
  R --> N
  O --> REDIS[(Redis库存/缓存/GEO)]

一次下单请求先经过 Gateway 鉴权和粗限流，订单服务通过 Feign 查询库存和配送能力，关键事件写入 RocketMQ，消费者异步更新运单和通知。Nacos 只保存服务目录与配置，不保存业务数据；Redis 适合热点和短期状态，MySQL 保存最终事实。跨服务写操作应设计幂等键和补偿任务，不能把网络重试当成事务。

8. 踩坑与最佳实践

3

8.1 注册发现的运行细节

注册动作不是一次性的配置读取，而是一个持续租约。客户端启动后先发送实例元数据，随后按照心跳周期续租；服务端维护实例最后更新时间并执行健康检查。临时实例失联达到超时阈值会被标记不健康，超过删除阈值才从目录移除，这段窗口用于网络抖动恢复。调用端本地缓存会造成短暂的“幽灵实例”，因此连接失败时 LoadBalancer 应触发重新拉取并配合有限重试。发布流程应先把实例权重调为零，等待连接排空，再停止进程，避免直接杀进程导致请求失败。

服务名、分组和命名空间共同构成逻辑坐标。建议把环境写入 namespace，把领域写入 group，把可用区写入 cluster；例如 logistics-dev/LOGISTICS_GROUP/order-service。元数据可以记录版本、提交号和灰度标签，网关或自定义选择器据此实现按用户标记路由。不要在业务代码里缓存固定 IP，因为容器重建、弹性扩缩容和跨机房都会改变地址。

8.2 配置变更的安全边界

动态刷新适合开关、阈值和文案，不适合线程池核心数、数据源地址和序列化协议。变更前先在测试 namespace 发布，观察应用日志中的 dataId、group 和版本，再逐步放量。配置内容应该进行字段校验，启动时缺少关键字段要快速失败；对密码、密钥和第三方凭证使用独立密钥系统，Nacos 中只保留引用。回滚通过重新发布上一版本 dataId 完成，并保留审计记录。

bootstrap 配置加载失败时，应用可能退回本地默认值，形成“看似启动成功、实际连接错误”的隐患。建议在健康检查中暴露当前 namespace、group 和配置版本摘要，但不要输出敏感值。多数据中心部署时，每个机房使用本地 Nacos 集群，跨机房只读同步服务目录，避免所有请求依赖单一 Nacos 地址。

8.3 网关过滤链与性能

Gateway 的过滤器按 order 排序，鉴权应早于路由，响应头和审计日志应在后置阶段执行。阻塞式数据库或文件 IO 不能直接放进 Netty 事件线程；必须使用响应式客户端，或明确切换到弹性调度器并设置并发上限。请求体只能读取一次，签名校验需要缓存时要限制最大 body 大小，防止大报文耗尽内存。跨域预检 OPTIONS 请求应在鉴权白名单中，否则浏览器会把正常接口误判为跨域失败。

限流指标需要区分总 QPS、用户 QPS、IP QPS 和并发数。总 QPS 保护服务容量，用户维度抑制单个账号刷接口，并发数防止慢请求占满连接池。限流响应使用统一错误码和 Retry-After，客户端按照退避策略重试，不能立即忙循环。网关日志记录 traceId、路由 ID、状态码和耗时，敏感 Header 只记录哈希或脱敏值。

8.4 Sentinel 规则设计

流控规则的阈值应来自压测而不是经验。先测出数据库连接池、线程池和下游依赖的安全上限，再设置低于上限的保护值。Warm Up 适合刚启动的服务，让令牌速率逐步爬升；排队等待适合短时突发且请求可容忍毫秒级延迟的读接口。写接口通常快速失败并由上层提示稍后重试。熔断降级要区分慢调用比例与异常比例，超时属于慢调用时应同时检查网络、连接池和下游 GC。

热点参数规则可针对运单 ID、用户 ID 设置单独阈值，但参数必须来自可信的解析结果，不能直接信任任意 Header。系统规则用于 CPU、负载和入口总并发的最后一道保护。规则持久化后要做双向验证：在控制台修改，检查 Nacos dataId 是否变化；直接改 Nacos，检查客户端是否收到并生效。发布脚本应校验 JSON 字段范围，避免错误规则导致全量拒绝。

8.5 可观测性和故障演练

每个请求携带 traceId，Gateway 生成或透传，Feign、消息生产者和消费者继续传递。指标至少包括注册实例数、配置拉取失败数、网关路由 4xx/5xx、Sentinel block 数、Feign 超时、消息积压和数据库连接池使用率。日志采用结构化 JSON，字段包含 service、instance、traceId、userId（脱敏）、orderId 和 errorCode。告警分为入口成功率、依赖成功率和资源水位三类，避免只监控机器 CPU。

演练应覆盖 Nacos 短暂不可用、Redis 主从切换、RocketMQ 消费延迟、数据库连接池耗尽和单个实例频繁 Full GC。验证目标不是“没有报错”，而是流量能被限流、请求能被降级、消息能重试且最终数据一致。每次演练记录开始时间、影响范围、恢复动作和改进项，形成可审计的运行手册。

8.6 数据与接口契约

微服务边界一旦确定，数据所有权也必须确定。订单服务只能修改订单表，配送服务维护骑手和运单表，查询其他领域通过 API 或事件获得只读视图。跨服务接口采用版本化路径或兼容字段，新增字段先向后兼容，删除字段经过观察期。金额使用 BigDecimal 或最小货币单位整数，时间统一 UTC 保存并在展示层转换，避免跨时区结算错误。

同步调用链不宜过深。入口请求最多串联两到三个核心服务，其余动作发布领域事件异步完成。对外 API 使用幂等键，服务端保存请求指纹和处理结果，重复请求直接返回同一结果。消息消费者也要记录业务唯一键和消费状态，数据库唯一索引是最后一道重复保护。失败重试采用指数退避并设置最大次数，超过次数进入死信队列，由人工或补偿任务处理。

8.7 发布与容量基线

每次发布先做依赖漏洞扫描、接口契约测试和数据库变更演练，再以小流量灰度。灰度实例通过 Nacos metadata 标记版本，LoadBalancer 或网关只把带灰度 Header 的测试用户导向新版本。观察错误率、P95 延迟、线程池和 GC 指标达到基线后再扩大比例。回滚不仅回滚镜像，还要确认配置、数据库迁移和消息消费者版本兼容；不可逆迁移必须采用新增字段、双写、回填、切读、删除的分阶段策略。

  • 不要把 Nacos 账号密码硬编码进仓库，使用环境变量或密钥挂载；namespace ID 必须是实际 UUID，不是显示名称。
  • Gateway 的 lb:// 路由依赖 LoadBalancer，缺少 starter 时会出现找不到协议处理器；WebFlux 网关不要引入 Servlet MVC 过滤器。
  • Sentinel 资源名要稳定，代码重构时同步规则；fallback 只返回可解释的降级结果，不能吞掉库存扣减异常。
  • 临时实例适合容器，发布前先摘流量再停机；永久实例需要人工下线。Nacos 2.x 客户端网络不通时同时检查 9848/9849 gRPC 端口。
  • Feign 超时要小于上游网关超时，避免请求堆积；重试只用于幂等 GET，支付和扣库存接口禁止无脑重试。
  • 版本升级先跑 mvn dependency:tree、契约测试和压测，确认 Boot 2.7 与 Alibaba 2021.0.5.0 的兼容边界。

9. 小结

3
