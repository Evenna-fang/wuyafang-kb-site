2. 链路追踪与日志关联

3

2.1 Observation 与 Micrometer Tracing 的关系

Spring Boot 的指标和链路都来自 Micrometer Observation：一次 Observation 既产生指标，也产生 span。低基数（low cardinality）的 key-value 同时进入指标和链路，高基数（high cardinality）的 key-value 只进入链路 [2]。这条规则直接决定了标签怎么设计：userId、orderId 这类取值几乎无限的字段只能作高基数标签，放进指标会让 Prometheus 的时间序列数爆炸。

Micrometer Tracing 是 JVM 上的追踪门面，通过 micrometer-tracing-bridge-brave 或 micrometer-tracing-bridge-otel 接入具体 tracer [5]。它为 Micrometer 的 ObservationHandler 提供追踪扩展，每个 Observation 会创建、启动、结束并上报一个 span，要求 Micrometer 1.10.0 及以上 [5]。

自己埋点的写法（Boot 官方示例 [2]）：

Observation.createNotStarted("seckill.deduct", this.observationRegistry)
    .lowCardinalityKeyValue("sku.type", "flash")
    .highCardinalityKeyValue("userId", "42")
    .observe(() -> {
        // 扣库存的业务逻辑
    });

注解方式需要打开 management.observations.annotations.enabled=true，并引入 org.aspectj:aspectjweaver。官方特别提醒：对已经被框架埋点的代码（Spring MVC 控制器、Spring Data 仓库）再加注解，会得到重复的 observation [2]。

2.2 依赖与配置

Boot 4.1.2 提供两套官方组合：OpenTelemetry + OTLP 用 spring-boot-starter-opentelemetry；Brave + Zipkin 用 spring-boot-starter-zipkin [1]。页面同时提示，OpenTelemetry 已弃用 Zipkin 支持，对应自动配置将在 Boot 4.2 移除 [1]，所以新工程直接选 OTLP。

# application.yml（Boot 4.1.2 口径；属性名出自 [1][2][3][4]）
spring:
  application:
    name: seckill-service

management:
  tracing:
    sampling:
      probability: 1.0        # 默认只采 10%；压测和灰度观察期临时调到 1.0，常态按流量下调 [1]
  endpoints:
    web:
      exposure:
        include: health,prometheus   # 默认只暴露 health；prometheus 必须显式开启 [4][3]
  endpoint:
    health:
      probes:
        enabled: true          # /actuator/health/liveness 与 /readiness，供 K8s 探针使用 [4]
  observations:
    key-values:
      region: cn-east          # 对所有 observation 追加低基数标签 [2]
      stack: prod
  metrics:
    tags:
      region: cn-east          # 对所有指标追加公共标签 [3]
      stack: prod

logging:
  pattern:
    correlation: "[${spring.application.name:},%X{traceId:-},%X{spanId:-}] "  # 日志带上 traceId [1]
  include-application-name: false

几个容易踩的点：

  • 采样率默认是 10% [1]。采样率低时，线上单个报错请求恰好没有 trace，排障时就找不到链路。常态方案是低采样率加"错误请求必留"，后者需要尾部采样（tail sampling），在 OTel Collector 侧做，本次未抓取其文档，属未核实项。
  • OTLP 导出地址：官方页面指出使用 management.opentelemetry.tracing.export.otlp.*，但具体的 endpoint 属性名页面没有给出，需查 Common Application Properties [1]。保险的做法是用环境变量：Boot 会把 OTEL_EXPORTER_OTLP_ENDPOINT=http://collector:4318 映射成 http://collector:4318/v1/traces 用于链路，OTEL_EXPORTER_OTLP_TRACES_ENDPOINT 优先且按原样使用 [2]。
  • 手写 new RestTemplate()、RestClient.create()、WebClient.create() 不会传播 trace。必须使用自动配置的 RestTemplateBuilder、RestClient.Builder、WebClient.Builder [1]。这条对 01 篇里 Feign 以外的内部 HTTP 调用尤其重要。
  • 响应式链路（Gateway 是 WebFlux）里，ThreadLocal 默认不会在 reactive 算子中恢复，需要 spring.reactor.context-propagation=auto；@Async 线程池需要 spring.task.execution.propagate-context，自建线程池要注册 ContextPropagatingTaskDecorator [2]。秒杀的异步下单线程池如果自己 new ThreadPoolExecutor，traceId 会在这里断掉。

2.3 trace 如何跨服务传播

OpenTelemetry 的 context propagation 把上下文序列化在发送方、反序列化在接收方，默认传播器用 W3C Trace Context，traceparent 头的格式是 <version>-<trace-id>-<parent-id>-<trace-flags>，例如 00-a0892f3577b34da6a3ce929d0e0e4736-f03067aa0ba902b7-01 [6]。Baggage 可以跨服务携带任意键值对，但官方明确说不要放凭证、API key、个人信息，因为它可能被记录或发给不可信的下游 [6]。Boot 侧：W3C 传播时 baggage 自动跨网络传播，B3 传播时不会，需要配置 management.tracing.baggage.remote-fields [1]。

微服务链路里的传播断点按"Gateway → Feign → RocketMQ → 消费者"逐段检查：

环节 传播方式 本次核实情况
客户端 → Gateway 请求头 traceparent Gateway 是 WebFlux，OTel agent 支持列表含 Spring Cloud Gateway 2.0+ 和 Spring WebFlux 5.3+ [8]
Gateway → 业务服务 同上 同上
服务 → 服务（OpenFeign） 同上 OTel agent 支持列表没有单列 OpenFeign [8]，需靠底层 HTTP 客户端的埋点，必须实测
生产者 → RocketMQ → 消费者 消息属性携带上下文 agent 列表含 Apache RocketMQ Remoting 客户端 4.8+（对应本系列 4.9.7），条目写的是 Messaging Spans，是否自动把上下文写进消息未说明 [8]，必须实测

RocketMQ 这一段是整条链路最容易断的地方，而秒杀的价值恰恰在"下单请求 → 消息 → 订单落库"这一跳。验证方法：压一个带固定 traceparent 的请求，在追踪后端搜索这个 trace id，检查消费者的 span 是否挂在生产者 span 之下。如果消费者 span 是独立的新 trace，说明上下文没传过去，退路是用 OTel 的 Propagators API 手动注入和提取：发送侧把上下文 inject 到消息的用户属性，消费侧 extract 出来再开 span。官方的态度是只有在没有埋点库处理传播时才手动用该 API [6]。

RocketMQ 自带的消息轨迹是另一套机制，与 OTel 的 trace 无关，但对排查消息去向很有用。Broker 配置 traceTopicEnable=true，启动后自动创建系统 Topic RMQ_SYS_TRACE_TOPIC；生产者和消费者构造时传入第二个参数 true 开启；可以用 mqadmin QueryMsgTraceById -n <nameserver> -i <msgId> 按消息 ID 查询 [11]。轨迹记录生产者的发送耗时、是否成功，消费者的投递轮次、消费耗时和是否成功，以及 Broker 的存储位置 [11]。轨迹数据量大时，官方建议用一台专用 Broker 存储，使普通消息与轨迹的磁盘 IO 隔离，此模式要求至少两台 Broker [11]。秒杀高峰期不建议在所有 Broker 上都开轨迹，推荐专用 Broker。

2.4 Boot 2.7 工程的采集路线：OTel Java agent

OpenTelemetry Java agent 是一个 JAR，可以挂到任何 Java 8+ 应用上 [7]。因为它按字节码埋点，对 Boot 2.7 不需要改依赖。agent 的启动参数（-javaagent:）和环境变量（OTEL_SERVICE_NAME、OTEL_TRACES_SAMPLER 等）在其 Getting started 与 Configuration 页面，本次只读到概览页，这些具体参数未核实 [7]，使用前以官方页面为准。

这条路线的取舍：好处是不改代码、覆盖面由 agent 的支持列表决定；代价是与 Boot 自己的 Observation 机制是两套体系，同时开启会出现重复 span，要选一条。agent 对 HikariCP 提供连接池指标 [8]，与 Boot 的 hikaricp 指标 [3] 也可能重复，上线前核对。

2.5 日志与 trace 的关联

日志里带 traceId 是最便宜的关联手段。Boot 启用 Micrometer Tracing 后默认输出 [traceId-spanId] 格式，上面的 logging.pattern.correlation 是自定义成带服务名的格式 [1]。01 篇 8.5 节要求的 JSON 结构化日志，需要把 MDC 里的 traceId、spanId 作为字段输出，具体的 Logback encoder 本次未核实。

排障顺序固定为：监控面板发现异常 → 取一个失败请求的 traceId → 在日志系统按 traceId 查全链路日志 → 在追踪后端看 span 耗时分布。Prometheus 还支持 exemplar，把 trace id 挂到指标样本上，直接从面板跳到 trace。Boot 的 exemplar 需要 SpanContext bean（使用 Micrometer Tracing 时自动配置），由 management.tracing.exemplars.include 控制包含哪些 trace，默认只含已采样的，且 Prometheus 不支持 all 值 [3]。

3. 指标体系：RED、USE 与四个黄金信号

3

Google SRE 书的四个黄金信号是延迟、流量、错误、饱和度 [13]。几个对本篇有直接指导意义的原文要点：

  • 成功请求和失败请求的延迟要分开统计，因为"慢错误比快错误更糟" [13]。
  • 只看平均值会掩盖长尾，一个后端的 99 分位很容易成为前端的中位数 [13]。微服务扇出越多，这条越重要。
  • 延迟分布用直方图记录，桶边界大致按指数间隔，例如每档约 3 倍 [13]。
  • 饱和度要看最受限的资源，很多系统在利用率到 100% 之前性能就已经下降，需要设定利用率目标 [13]。
  • 告警应当可执行：每次呼叫都应引起紧迫感且需要人的判断，而不是机械操作 [13]。

RED（速率、错误、耗时）面向请求型服务，USE（利用率、饱和度、错误）面向资源。这两个缩写的定义不在上述 SRE 页面里，属未核实的通用说法，这里仅作为分类标签：入口和每个服务用 RED，线程池、连接池、Redis、Broker 用 USE。

3.1 开箱即用的指标

Boot 默认提供的指标（出自 [3]）：

  • HTTP 服务端：指标名 http.server.requests，适用于 Spring MVC、WebFlux、Jersey，可通过 management.observations.http.server.requests.name 改名。
  • JVM：jvm. 前缀，含内存与缓冲池、GC、线程、类加载。
  • 系统：system.、process.、disk. 前缀。
  • 线程池：自动埋点所有 ThreadPoolTaskExecutor 和 ThreadPoolTaskScheduler bean，标签是 bean 名。具体指标名页面未列出。
  • 连接池：jdbc.connections 前缀（当前活跃、空闲、最大、最小连接数），HikariCP 用 hikaricp 前缀，按池名打标签，池名由 spring.datasource.name 控制。

Micrometer 指标名到 Prometheus 指标名的转换规则，官方页面没有写 [3]。常见约定是点变下划线、计数器加 _total、计时器以秒为单位加 _seconds，所以下文 PromQL 里的 http_server_requests_seconds_count、hikaricp_connections_active 是按约定推出的写法，务必先访问 /actuator/prometheus 核对实际输出再写规则。

Prometheus 抓取配置的官方示例 [3]：

scrape_configs:
- job_name: "spring"
  metrics_path: "/actuator/prometheus"
  static_configs:
  - targets: ["HOST:PORT"]

注册中心场景下建议用服务发现替代 static_configs，具体写法本次未核实。

3.2 Sentinel 指标

Sentinel 本身把数据写在本地日志里 [10]：

  • 拦截日志 ${user_home}/logs/csp/sentinel-block.log，按秒记录被拦截的情况；拦截原因分三种：FlowException 限流、DegradeException 降级、SystemBlockException 系统保护。没有拦截发生时该文件不会出现。
  • 秒级监控日志 ${user_home}/logs/csp/${app_name}-${pid}-metrics.log，字段依次为：时间戳、格式化时间、资源名、通过数（passed QPS）、拦截数（blocked QPS）、每秒结束的调用数、异常数、平均 RT、占用未来请求数（1.5.0 起）、最大并发（预留）、资源分类（1.7.0 起）。
  • 日志目录可用 csp.sentinel.log.dir 改。

注意文件名不是固定的 metric.log，而是带应用名和进程号 [10]。本次没有找到官方文档里直接把 Sentinel 指标暴露成 Prometheus 格式的方案，常见做法是采集这份 metrics 日志后转成指标，或者在 @SentinelResource 的 blockHandler 里自增一个 Micrometer 计数器。后者是自建指标，见下一小节。

3.3 业务指标：秒杀与派单

框架指标回答"服务健不健康"，回答不了"业务有没有卡住"。下表的指标名是本篇建议自定义的名字，不是任何框架自带的：

链路 自定义指标（建议） 类型 回答的问题
秒杀 seckill_deduct_total{result}，result 取 success / sold_out / duplicate / blocked Counter 流量被谁挡掉了，库存是否正常卖完
秒杀 seckill_order_create_seconds Histogram 消息消费到订单落库的耗时
秒杀 seckill_stock_mismatch_total Counter Redis 库存与数据库对账不一致次数
派单 dispatch_assign_seconds Histogram 从下单到分配到骑手的耗时
派单 dispatch_timeout_reassign_total Counter 骑手超时未接而重新调度的次数
支付 payment_notify_total{result} Counter 异步通知验签通过、失败、重复的次数
支付 payment_pending_orders Gauge 超过阈值时间仍未终态的支付单数

标签只放低基数字段（结果类别、渠道、城市），不放订单号和用户号 [2]。

3.4 消息队列指标

RocketMQ 5.x 文档里的 Broker 端指标（出自 [12]）：

  • rocketmq_consumer_lag_latency（毫秒）：消息从可消费到被消费之间的延迟，按最早一条未确认消息的就绪时间计算。
  • rocketmq_consumer_ready_messages：就绪消息数，即最大 offset 减最新拉取 offset。
  • rocketmq_consumer_inflight_messages：已拉取未确认的消息数。
  • rocketmq_consumer_queueing_latency（毫秒）：最早一条就绪消息的排队时长，反映消费者拉取是否及时。
  • rocketmq_send_to_dlq_messages_total：投递到死信队列的消息数。
  • rocketmq_send_cost_time、rocketmq_process_time：发送耗时与消费处理耗时的直方图。

开启方式是 Broker 配置 metricsExporterType=PROM，Broker 在 http://<broker-ip>:5557/metrics 暴露指标，端口由 metricsPromExporterPort 控制；也可设为 OTLP_GRPC 推送到 OTel Collector [12]。页面里没有 rocketmq_consumer_lag_messages 这个名字，不要想当然地写 [12]。

版本差异：以上是 5.x 文档，而 01 篇基线是 RocketMQ 4.9.7。4.x 的官方做法是单独部署 rocketmq-exporter，本次只在搜索结果摘要里看到它，没有读正文，属未核实。如果集群是 4.9.7，先确认上面这些指标是否存在，不存在就改用 exporter 的指标名。

4. 告警规则与阈值推导

3

4.1 规则格式

Prometheus 告警规则文件的结构 [9]：groups 下每组有 name、可选 labels 和 rules；每条规则有 alert、expr、for、keep_firing_for、labels、annotations。for 是条件持续多久才从 pending 转 firing，省略则首次评估即触发；keep_firing_for 是条件消失后继续保持 firing 的时长，用于防抖；labels 和 annotations 可用模板 {{ $labels.<name> }} 和 {{ $value }} [9]。

# rules/seckill.yml —— 阈值均为示例，必须按第 4.2 节方法用自己的基线推导
groups:
- name: seckill-red
  labels:
    team: trade
  rules:
  - alert: SeckillHighErrorRate
    # 指标名按 Micrometer 约定推出，上线前对照 /actuator/prometheus 核对
    expr: |
      sum(rate(http_server_requests_seconds_count{application="seckill-service",status=~"5.."}[5m]))
        /
      sum(rate(http_server_requests_seconds_count{application="seckill-service"}[5m])) > 0.01
    for: 3m
    keep_firing_for: 5m
    labels:
      severity: page
    annotations:
      summary: "秒杀服务 5xx 比例超过 1%"
      description: "当前值 {{ $value }}，先按 traceId 抽样看失败请求的链路"

  - alert: SeckillOrderConsumerLag
    expr: max by (consumer_group) (rocketmq_consumer_lag_latency) > 30000
    for: 2m
    labels:
      severity: page
    annotations:
      summary: "消费组 {{ $labels.consumer_group }} 延迟超过 30 秒"
      description: "订单落库落后，库存已扣但订单未创建的用户会越来越多"

  - alert: RocketMQDeadLetterIncreasing
    expr: increase(rocketmq_send_to_dlq_messages_total[10m]) > 0
    labels:
      severity: ticket
    annotations:
      summary: "10 分钟内有消息进入死信队列"

- name: resource-use
  rules:
  - alert: DbPoolNearlyExhausted
    expr: |
      hikaricp_connections_active / hikaricp_connections_max > 0.8
    for: 5m
    labels:
      severity: ticket
    annotations:
      summary: "{{ $labels.pool }} 连接池使用率超过 80%"

规则写完需要用 promtool check rules 校验语法，本次未实跑，属未验证项。

4.2 阈值怎么推导

上面所有数字都是示例。推导阈值的步骤：

  1. 取基线。选一段正常流量（包含一次完整的高峰），用 PromQL 取各指标的 P50、P95、P99 和日内最大值。没有基线就先别设硬阈值，只做面板。
  2. 从业务目标反推。例如"点击抢购后 3 秒内看到结果"，扣掉网关和网络，得到订单链路的耗时预算，消费延迟告警值必须小于这个预算，否则告警响起时用户早已超时。
  3. 加余量。常用做法是在基线 P95 上乘一个系数（例如 1.5 到 2 倍），再用最近两周的告警历史校正，目标是"每次告警都需要人处理"，对应 SRE 书的"可执行"原则 [13]。系数本身没有权威出处，是经验值。
  4. 用 for 和 keep_firing_for 控制抖动 [9]。秒杀是脉冲流量，for: 3m 在活动 1 分钟就结束的场景下永远不会触发，活动期间要单独设一组更短 for 的规则，或者活动期间用 recording rule 先做聚合。
  5. 饱和度提前报。SRE 书建议在"接近有问题"时就告警 [13]，所以连接池告警设 80%，而不是 100%。

5. 压测方法

3

5.1 压测要回答什么问题

压测先定问题，再定方案。针对秒杀和派单，常见的四个问题：

  1. 单实例在延迟达标的前提下最大吞吐是多少（容量）。
  2. 流量超过容量时，限流、降级是否按预期生效，核心接口是否还能保住（保护）。
  3. 异步链路（消息、对账）在高峰后多久追平（恢复）。
  4. 持续压若干小时是否有资源泄漏（稳定性）。

5.2 开放模型与封闭模型

k6 的执行器分为按虚拟用户数驱动（constant-vus、ramping-vus，封闭模型）和按到达速率驱动（constant-arrival-rate、ramping-arrival-rate，开放模型）两类 [14]。这个划分页面是用 VU 或到达速率来描述的，"开放/封闭"的对应关系是页面推断，详细定义在其链接的另一篇文章里，未读 [14]。

工程上的结论是：秒杀是"用户不会因为系统慢而减少点击"，应该用开放模型（固定到达速率）。封闭模型下，服务变慢时虚拟用户都卡在等待上，实际施加的压力反而下降，会得出偏乐观的结论。

5.3 k6 脚本

阈值语法 [15]：options.thresholds 以指标名为键；Trend 类指标支持 avg、min、max、med、p(N)，Rate 类支持 rate；abortOnFail: true 让阈值失败时立即中止测试，delayAbortEval 推迟首次评估以避免开局的偶发数据误中止；官方警告同一指标不能重复写同一个对象键，否则后者静默覆盖前者 [15]。

// seckill_load.js —— 开放模型阶梯加压；脚本未实跑
import http from 'k6/http';
import { check } from 'k6';

export const options = {
  scenarios: {
    seckill_spike: {
      executor: 'ramping-arrival-rate',   // 执行器名出自 [14]；下列参数名为 k6 通用用法，本次未在抓取页面核实
      startRate: 100,
      timeUnit: '1s',
      preAllocatedVUs: 200,
      maxVUs: 2000,
      stages: [
        { target: 500,  duration: '1m' },
        { target: 2000, duration: '2m' },
        { target: 2000, duration: '3m' },   // 峰值保持
        { target: 100,  duration: '1m' },   // 回落，观察消息积压追平时间
      ],
    },
  },
  thresholds: {
    // 5xx 率；注意 429（被限流）属于预期结果，不应计入 http_req_failed
    http_req_failed: [{ threshold: 'rate<0.01', abortOnFail: true, delayAbortEval: '30s' }],
    http_req_duration: ['p(95)<800', 'p(99)<1500'],
    checks: ['rate>0.95'],   // checks 要写阈值才会影响退出状态 [15]
  },
};

export default function () {
  const res = http.post(`${__ENV.BASE_URL}/seckill/buy`,
    JSON.stringify({ skuId: 1001, quantity: 1 }),
    { headers: { 'Content-Type': 'application/json',
                 'X-Load-Test': '1' } });          // 压测流量标记，见 5.4
  check(res, { 'status is 200/429': (r) => r.status === 200 || r.status === 429 });
}

脚本里有两点需要处理：一是 k6 默认把 4xx、5xx 都计入 http_req_failed，秒杀被限流返回 429 是预期行为，需要用 http.setResponseCallback 之类的机制调整，具体 API 本次未核实，建议跑通后看结果指标再定；二是用户身份要从参数文件读，避免所有虚拟用户用同一个账号，否则"一人一单"规则会让绝大多数请求命中重复下单分支，压测变成了测重复校验。

5.4 全链路压测、流量标记与影子库

这一节是工程设计思路，没有本次抓取的一手源作依据，仅作方案参考。

压测流量进入真实生产链路时，需要保证三件事：

  • 可识别。入口给压测请求打标记（如上面脚本的 X-Load-Test 头），网关把它写入 baggage 或 MDC，下游所有服务通过 baggage 读取。注意 baggage 不要放敏感信息 [6]，一个布尔标记是合适的。
  • 可隔离。带标记的请求写入影子库、影子 Topic、影子 Redis key 前缀，或者在测试环境整体复制。只在业务代码里 if (loadTest) return 绕过写入，测不到真实写入路径，不推荐。
  • 可清理。压测数据要有统一前缀或独立 schema，结束后批量清理。

没有条件做影子库时，独立的压测环境配套"数据量与生产同量级"的库表，比在生产里做不隔离的压测安全得多。支付类接口必须使用支付渠道的沙箱，不要对真实渠道压测。

5.5 容量估算

给定目标峰值 QPS 与目标响应时间，需要的并发度由 Little 定律给出：并发数 ≈ QPS × 平均响应时间（秒）。例如目标 2000 QPS、平均 200 ms，稳态约 400 个并发请求在飞。这个数字用来核对 Tomcat 或 Netty 线程数、Hikari 连接池大小、Feign 连接池上限是否会先成为瓶颈。上面算出的并发数不是配置建议，只用于识别"理论需要远大于配置"的环节。

逐环节的瓶颈检查：

  1. 先压网关，确认网关自身不是瓶颈。
  2. 再压单个下游服务，记录达标延迟下的最大 QPS，作为单实例容量。
  3. 实例数 = 目标峰值 QPS ÷ 单实例容量，再留出余量（至少应能承受单实例故障时的重新分配），余量比例需要团队自己定。
  4. 消息消费者的容量单独压，因为它决定"高峰过后多久追平"。

5.6 读压测报告

  • 延迟看分位数，不看平均值 [13]。同一次测试里 P50 稳定而 P99 翻倍，通常意味着排队或锁竞争。
  • 看拐点。随着到达速率上升，延迟突然陡增的点就是容量拐点，容量取拐点之前的值，不是测试里的最高值。
  • 错误分类。区分被限流（预期）、超时、5xx，三者含义不同。
  • 同步看资源。压测期间同时看 Hikari 活跃连接、线程池队列、GC、Redis CPU 与慢日志。延迟升高但各项资源都不高，往往是下游依赖或锁的问题。
  • 压测后看恢复。停止加压后消费延迟多久回到基线，是否有消息进死信，库存对账是否一致。
  • 复现性。记录被测版本、配置、数据量、脚本版本，否则报告不能和下一次对比。

6. 灰度发布

3

6.1 基于 Kubernetes 的滚动更新与金丝雀

Deployment 的滚动更新有两个参数 [16]：maxUnavailable 是更新期间允许不可用的最大 Pod 数，maxSurge 是可以超出期望副本数创建的最大 Pod 数，两者都可以是整数或百分比，默认都是 25%；百分比的 maxUnavailable 向下取整、maxSurge 向上取整；两者不能同时为 0。minReadySeconds 指新 Pod 就绪后要持续多少秒无容器崩溃才算可用，默认 0；progressDeadlineSeconds 默认 600，超过后 Deployment 会报告 ProgressDeadlineExceeded，且该值必须大于 minReadySeconds [16]。

spec:
  replicas: 4
  minReadySeconds: 30          # 新 Pod 就绪后再观察 30 秒；数值为示例
  progressDeadlineSeconds: 600
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1
      maxUnavailable: 0        # 业务服务建议先加后减，不降低可用容量

回滚用 kubectl rollout undo deployment/<name>，指定版本加 --to-revision=N；用 kubectl rollout history deployment/<name> 查看历史，--revision=N 看某个版本详情 [16]。官方特别说明：只有 Pod 模板（.spec.template）变化才产生新 revision，扩缩容不产生，所以回滚只回滚模板部分 [16]。这印证了 01 篇 8.7 的提醒：回滚镜像不等于回滚配置和数据库迁移，数据库变更必须用"新增字段、双写、回填、切读、删除"的分阶段方式。

金丝雀的官方做法 [17]：两个 Deployment 共用 app、tier 标签，用 track 标签区分 stable 与 canary；Service 的 selector 去掉 track，因此同时选中两组 Pod；通过调整两边副本数决定流量比例，例子里 3 个稳定副本加 1 个金丝雀副本，比例为 3:1；确认没问题后把稳定版更新为新版本，再删除金丝雀 [17]。

这个方式的局限：流量比例只能近似到副本数，不能精确到 1%，也不能"只让内部用户先用"。页面本身没写局限，这是从机制得出的推论。要按请求头或用户分流，就用下一节的网关方案。

6.2 基于 Nacos 元数据与 Gateway 的请求级灰度

目标：带灰度标记的请求走新版本，其余请求走稳定版本，比例与副本数无关。

第一步，给实例打元数据。Nacos 的 spring.cloud.nacos.discovery.metadata 用 Map 格式配置，默认为空；weight 默认 1，取值 1 到 100，数值越大权重越大 [20]。

# 新版本实例
spring:
  cloud:
    nacos:
      discovery:
        metadata:
          hint: gray
# 稳定版本实例
#   hint: stable

第二步，让 LoadBalancer 按 hint 过滤。Spring Cloud LoadBalancer 会读取请求头 X-SC-LB-Hint（可通过 spring.cloud.loadbalancer.hint-header-name 改名），用它的值去匹配实例 metadataMap 里 hint 键的值；没有请求头时用 spring.cloud.loadbalancer.hint.[SERVICE_ID]，再回退到 spring.cloud.loadbalancer.hint.default [19]。启用需要自定义 ServiceInstanceListSupplier：

public class CustomLoadBalancerConfiguration {
    @Bean
    public ServiceInstanceListSupplier discoveryClientServiceInstanceListSupplier(
            ConfigurableApplicationContext context) {
        return ServiceInstanceListSupplier.builder()
                .withDiscoveryClient()
                .withCaching()
                .withHints()
                .build(context);
    }
}

这里有一个必须处理的坑：官方规则是"没设置 hint 时返回全部实例；有 hint 但没有匹配的实例时也返回全部实例" [19]。所以如果稳定版实例没有标记，且普通请求没有 hint，普通流量也会被分到灰度实例上。解决办法是给所有稳定实例打 hint: stable，并设置 spring.cloud.loadbalancer.hint.default=stable，让没有灰度头的请求默认只走稳定实例。同时要想到另一面：灰度头指向的版本如果没有存活实例，请求会落到全部实例，灰度范围会悄悄变大。

第三步，在网关按条件加 hint 头。Gateway 路由断言支持 Header=<name>, <regexp> 与 Weight=<group>, <weight>；Weight 按 group 分别计算，8 比 2 的两条路由会把约 80% 和 20% 的流量分过去 [18]。下面的 YAML 前缀是 Gateway 5.0.4 的写法 [18]，更早的版本（01 篇用的 2021.0.x 系列）的前缀不同，页面未覆盖，以对应版本文档为准。

spring:
  cloud:
    gateway:
      server:
        webflux:
          routes:
          - id: seckill_gray_by_header
            uri: lb://seckill-service
            predicates:
            - Path=/seckill/**
            - Header=X-Gray-User, true
            filters:
            - AddRequestHeader=X-SC-LB-Hint, gray
          - id: seckill_gray_by_weight
            uri: lb://seckill-service
            predicates:
            - Path=/seckill/**
            - Weight=seckill-group, 5      # 与下一条同组，约 5% 走灰度
            filters:
            - AddRequestHeader=X-SC-LB-Hint, gray
          - id: seckill_stable
            uri: lb://seckill-service
            predicates:
            - Path=/seckill/**
            - Weight=seckill-group, 95
            filters:
            - AddRequestHeader=X-SC-LB-Hint, stable

AddRequestHeader 过滤器和路由顺序的细节本次未抓取到 Gateway 的 filters 页面，属未核实。另外，灰度头只在网关到第一个服务这一跳有效。服务内部再通过 OpenFeign 调用下游时，需要用 RequestInterceptor 把 X-SC-LB-Hint 透传，否则下游又回到默认的稳定集合，灰度链路在第二跳断掉。这是设计层面的提示，透传代码未实跑。

灰度范围的选择顺序建议：内部员工账号（按头或 Cookie，Gateway 也有 Cookie 断言 [18]）→ 1% 到 5% 的随机用户 → 逐级扩大。秒杀这类有时间窗口的活动，不建议在活动当天做灰度，灰度窗口应安排在活动前的低峰期，避免在峰值时验证新版本。

6.3 回滚判据

回滚标准必须在发布前写好，发布中不临时争论：

判据 示例阈值（按基线调整） 动作
灰度实例 5xx 率明显高于稳定实例 持续 3 分钟高出 0.5 个百分点 立即摘除灰度 hint，回滚
灰度实例 P95 延迟 高于稳定版 1.3 倍并持续 5 分钟 暂停放量，定位后再决定
消息消费延迟、死信计数 出现新的死信，或延迟持续增长 回滚消费者版本，先确认消息格式兼容
业务对账 库存、订单、支付对账出现差异 停止放量，保留现场，按补偿流程处理
Deployment 进度 出现 ProgressDeadlineExceeded [16] kubectl rollout undo

对比灰度与稳定的指标，需要指标里有"版本"这个维度。可以通过 management.metrics.tags.version=<发布版本> 给所有指标加公共标签 [3]，这样面板上能直接按版本分组对比。
