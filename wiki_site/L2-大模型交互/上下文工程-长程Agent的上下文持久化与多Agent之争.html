任务跑得足够久，总会超过一个窗口。省 token 只能延缓这个时刻，不能取消它。一手资料给出的共同答案是：把状态放到窗口之外，窗口里只留当前这一步需要的东西。 本文整理这条思路在各家的具体做法，并回答一个有争议的问题：要不要把长任务拆给多个 Agent。

  1. 文件系统是最实用的“窗口外记忆”。 Manus 称它为“终极上下文”：大小不受限、天然持久、Agent 自己可以直接操作。Anthropic 的 memory tool、Anthropic 长程 harness 里的 claude-progress.txt 和 feature list、LangChain Deep Agents 的落盘，都是同一模式。
  2. 压缩必须可恢复。 Manus 不信任不可逆压缩，原因是“你无法可靠地预测，哪条观察在十步之后会变得关键”。网页内容可以删，但要保留 URL；文档内容可以省，但要保留路径。
  3. Anthropic 在 Claude 开发者平台上提供了两个原生机制：context editing 和 memory tool。 内部评测中，两者结合比基线高 39%，只用 context editing 高 29%；在 100 轮网页搜索评测里，context editing 使 token 消耗降低 84%，并让原本会因上下文耗尽而失败的流程得以完成。
  4. 长程任务靠 harness 接力。 Anthropic 的做法是把工作拆成“初始化 Agent 搭环境 + 编码 Agent 逐个功能推进”，每个会话结束留下进度文件、git 提交和 JSON 功能清单，下一个会话读这些东西接上。
  5. 多 Agent 的争议有一个可操作的分界线。 Cognition 主张默认不要多 Agent，理由是上下文无法在 Agent 之间无损传递；Anthropic 的研究系统用多 Agent 比单 Agent 高 90.2%，但消耗约 15 倍于聊天的 token。两方并不矛盾：前者针对要写出一致产物的任务，后者针对可并行的宽度优先检索。

一、问题：窗口有限，任务不限

2

Anthropic 长程 harness 一文开头直接点破：长程 Agent 要分多个会话工作，而“每个新会话开始时，都不记得之前发生过什么”。可以把它想象成轮班的工程师，每个人上班时前一班的人已经走了，手里只有交接文档。

文中有一个重要观察：即使用 Claude Agent SDK 带 compaction 的循环，让 Opus 4.5 只收到“做一个 claude.ai 的克隆”这种高层指令，它也做不出生产级的 Web 应用。失败有两种典型形态：

  • 一口气做完（one-shot）。 试图在一个窗口里做完所有事，上下文耗尽时留下做了一半、没有任何记录的功能，下一个会话要花大量精力猜现场。
  • 过早宣布完成。 项目后期，后来的 Agent 看到已有进展，就认定任务做完了。

这两种失败的共同点是：状态只存在于窗口里，窗口一结束，状态就蒸发。后面所有的做法都是在回答“状态存在哪”。

WHYT：窗口外状态、可恢复记忆与平台原生机制

2.1 以文件系统作为上下文

3

前沿模型的窗口已经到 128K token 以上，但真实任务里仍常不够，甚至成为负担。文中给出三个痛点：

  1. 观察结果可能非常大（网页、PDF）；
  2. 超过一定长度后，模型性能下降；
  3. 即使有前缀缓存，长输入仍然昂贵。

很多系统的应对是截断或压缩。Manus 的看法是，任何不可逆的压缩都有风险，因为你无法预知哪条信息稍后会变得关键。他们的方案是把文件系统当作外部记忆：Agent 按需读写文件，窗口里只保留指针。

“可恢复”是这里的关键词。判断一个压缩方案好不好，只需要问：被压掉的东西，Agent 之后还能不能找回来？删掉网页正文但保留 URL，答案是能；直接删掉并不留痕迹，答案是不能。

作者还有一个推测：如果状态空间模型（SSM）能熟练使用基于文件的记忆，也许会成为新一代 Agent 的基础，并称之为 Neural Turing Machines 的可能继承者。这是作者的推测，不是已验证的结论。

本节重点

  • 末尾位于模型的近期注意力范围内，这样既对冲了 lost-in-the-middle，又减少了目标漂移

3

Manus 处理复杂任务时，会创建一个 todo.md，每完成一项就更新、打勾。文中说一个典型任务平均要约 50 次工具调用，长循环里模型很容易偏题或忘掉最初的目标。

反复改写待办清单，实际效果是把全局计划不断复述到上下文的末尾。末尾位于模型的近期注意力范围内，这样既对冲了 lost-in-the-middle，又减少了目标漂移。本库前一篇讲位置偏置时，给出的工程对策是“最相关的放开头或结尾”；复述是这条对策在 Agent 循环里的动态版本：计划不是放一次，而是每隔几步重新放到末尾。

2.3 保留错误

3

常见做法是出错就隐藏痕迹、重试，或者重置状态再靠 temperature 碰运气。Manus 的判断是：“抹去失败就抹去了证据，没有证据，模型就无法适应。”把错误的路径和堆栈信息留在上下文里，模型会更新自己的内部信念，减少重复同样的错误。作者还认为错误恢复是判断“真正的 Agent 行为”最清晰的指标之一，而学术研究和公开基准大多只关注理想条件下的成功率，对此重视不够。

这条与第一章的“一口气做完”形成互补：不是所有东西都该留在窗口里，但失败信息比成功信息更值得留。

语言模型会模仿上下文里的行为模式。如果上下文里全是相似的“动作—观察”对，模型会沿用这个节奏，哪怕已经不是最优选择。Manus 的例子是用 Agent 批量评审 20 份简历：Agent 很容易陷入重复节奏，出现漂移、过度泛化甚至幻觉。

对策是增加受控的多样性：对动作和观察使用不同的序列化模板、换措辞、在顺序或格式上加少量噪声。作者的总结是：“上下文越统一，Agent 越脆弱。”注意这和第 2.1 节的“只追加、序列化要确定”表面上冲突，实际不矛盾：缓存要求前缀已写入的部分不变，多样性要求新追加的内容别千篇一律。

3.2 Memory tool：窗口外的文件目录

3

定义（原文大意）：让 Claude 通过基于文件的系统，在上下文窗口之外存取信息。Claude 可以对一个专用的记忆目录创建、读取、更新、删除文件。关键设计点是：这个工具完全在客户端通过工具调用运作，目录位于开发者自己的基础设施里，跨对话持久保存。存储后端由开发者管理，所以数据放哪、怎么持久化，开发者说了算。

四、长程 Harness：用环境做接力棒

2

Anthropic 工程博客《Effective harnesses for long-running agents》（2025-11-26）给出了一套完整的接力做法。

4.1 双段设计3 个重点▾ 点开看本节重点
本节重点
  • Initializer agent（只在第一个会话运行）：搭环境
  • 产出 「init.sh」（启动开发服务器）、「claude-progress.txt」（进度日志）、一个初始 git 提交，以及完整的功能清单
  • Coding agent（之后每个会话）：每次只做一个功能，结束时留下结构化更新，并保证代码处于可以直接合并的干净状态
3

两种 Agent 用同一套系统提示、工具和 harness，只有第一次会话的初始提示不同：

  • Initializer agent（只在第一个会话运行）：搭环境。产出 init.sh（启动开发服务器）、claude-progress.txt（进度日志）、一个初始 git 提交，以及完整的功能清单。
  • Coding agent（之后每个会话）：每次只做一个功能，结束时留下结构化更新，并保证代码处于可以直接合并的干净状态。

Anthropic 工程博客《Equipping agents for the real world with Agent Skills》（2025-10-16）给出的结构，是前面所有“按需加载”思路中最规整的一个：

层 内容 何时进入上下文
第一层：元数据 每个 SKILL.md 开头的 YAML frontmatter，含必填的 name 和 description 启动时，所有已安装技能的这两项放进系统提示
第二层：SKILL.md 正文 完整说明 Claude 判断该技能与当前任务相关时才读取
第三层及以上：附加文件 技能目录里被 SKILL.md 引用的其他文件 只在需要时读；例如 PDF 技能里填表说明放在 forms.md，填表时才读

两个细节。其一，技能里的脚本可以直接执行，不必把脚本内容载入上下文，所以文中说技能可打包的内容“实际上没有上限”。其二，博客没有给出元数据和正文的具体 token 量级，不要凭印象写数字。

编写建议：先让 Agent 跑代表性任务，找到它卡住的地方，再针对性加技能；SKILL.md 变笨重时拆分文件，把互斥或少用的内容分开放；特别注意 name 和 description，因为模型凭它们决定是否触发；只安装可信来源的技能，来源不明的要通读其脚本和依赖。

3

作者 Walden Yan，来自 Devin 的开发团队。核心主张是，生产级长时间运行的 Agent 应默认排除违反下面两条原则的架构：

  1. 共享上下文，并且共享完整的 Agent 轨迹，而不只是单条消息。
  2. 动作隐含决策，相互冲突的决策会导致糟糕的结果。

文中的例子是“做一个 Flappy Bird 克隆”被拆成两个子任务。子任务 1 的 Agent 把背景理解成类似超级马力欧的风格，子任务 2 的 Agent 做出的小鸟既不像游戏素材，运动方式也不对。最后主 Agent 只能合并两个相互误解的结果。作者指出，把原始任务复制给子 Agent 并不够，因为真实系统是多轮对话，拆任务之前可能已经调用过工具，每个细节都影响对任务的理解。即使共享了上下文，两个子 Agent 仍可能因为各自基于未事先约定的假设而做出风格不一致的产物。

作者的推荐架构有两种：

  • 单线程线性 Agent：上下文连续，结构最简单。局限是子任务很多的超大任务会耗尽窗口。
  • 加一个压缩历史的 LLM：专门用一个模型把动作和对话历史压缩为关键细节、事件和决策，延长有效上下文。作者承认这很难做好，可能需要微调小模型，Cognition 已经这样做过；局限是最终仍会触及上限。

他对 Claude Code 子 Agent 的评价是：这是符合原则的保守设计，子 Agent 不与主 Agent 并行工作，通常只回答一个明确的问题，不写代码；好处是子 Agent 的调查过程不留在主 Agent 的历史里，主 Agent 因此能承载更长的轨迹。文中注明这一评价基于 2025 年 6 月的实现，当前版本可能已有变化。

6.2 正方：Anthropic 多 Agent 研究系统（2025-06-13）

3

仅晚一天发布的 Anthropic 博客，给出了相反方向的数据：

  • 架构是 orchestrator-worker：主 Agent 规划并协调，把任务分给并行运行的子 Agent。内部评测中，Claude Opus 4 作主 Agent、Claude Sonnet 4 作子 Agent 的系统，比单 Agent Claude Opus 4 高 90.2%。
  • 在 BrowseComp 评测中，三个因素解释了 95% 的性能差异，其中 token 用量单独解释 80%，其余两个因素是工具调用次数和模型选择。也就是说，多 Agent 之所以强，主要是因为它能同时花掉更多 token，在更多窗口里独立思考。
  • 代价：Agent 约消耗聊天的 4 倍 token，多 Agent 系统约消耗聊天的 15 倍。因此只适合任务价值足够高的场景。
  • 适用的任务类型：可大量并行、信息量超出单个窗口、需要对接众多复杂工具；文中举的例子是“列出信息技术类 S&P 500 公司的所有董事会成员”这种宽度优先的查询。
  • 主 Agent 会把计划存入外部 Memory，因为文中提到当上下文超过 200,000 token 时会被截断，计划如果只在窗口里就会丢失。

Anthropic 在 prompt 层面给出的几条原则，也和上下文工程有关：

原则 要点
教会主 Agent 怎么委派 每个子任务需要明确的目标、输出格式、工具与来源指引、任务边界，否则会重复劳动或留下空白
按复杂度分配投入 简单查询 1 个 Agent、3 到 10 次工具调用；复杂研究才动用 10 个以上子 Agent
工具描述要清晰、不重叠 让 Agent 自己重写工具描述后，后续任务完成时间减少 40%
先宽后窄 先用短而宽的查询，再逐步缩小
并行调用 主 Agent 并行启动 3 到 5 个子 Agent，子 Agent 并行使用 3 个以上工具，复杂查询的研究时间最多减少 90%

最值得注意的一条是 artifact 做法：让子 Agent 把成果写入外部系统，只把轻量引用交回主 Agent。原文说法是，这样既减少信息在“转述”中丢失，也降低 token 开销，在代码、报告、数据可视化这类结构化输出上效果好。这恰好回应了 Cognition 的核心担忧——上下文在 Agent 之间传递会损耗——办法是让产物直接落在共享存储里，而不是靠主 Agent 复述。

7.1 三类上下文2 个重点▾ 点开看本节重点
本节重点
  • 三种数据源：Runtime Context（静态配置：用户 ID、密钥、权限）、State（会话级短期记忆：消息、上传的文件、工具结果）、Store（跨会话长期记忆：用户偏好、历史洞察）
  • 很多上下文事故，来自把这两者搞混——想只改一次调用，结果永久改了历史；或者想永久压缩，结果只在单次调用里生效，下一轮又恢复了

类型 控制什么 持久性
Model Context 每次模型调用的输入：指令、消息、工具、模型、输出格式 瞬态——模型在这一次调用里看到什么
Tool Context 工具读取和产生的内容，即对 state、store、runtime context 的读写 持久
Life-cycle Context 模型调用与工具调用之间的步骤：摘要、护栏、日志等 持久——跨轮次保存在 state 里

三种数据源：Runtime Context（静态配置：用户 ID、密钥、权限）、State（会话级短期记忆：消息、上传的文件、工具结果）、Store（跨会话长期记忆：用户偏好、历史洞察）。

这个分类的价值是区分“瞬态”和“持久”：在 Model Context 里裁剪消息，只影响这一次调用，原始历史不动；在 Life-cycle Context 里做摘要，则会写进 state，之后每一轮都只看到摘要。很多上下文事故，来自把这两者搞混——想只改一次调用，结果永久改了历史；或者想永久压缩，结果只在单次调用里生效，下一轮又恢复了。

7.2 Middleware 钩子

3

Middleware 可挂在 Agent 生命周期的任意步骤，做两件事：更新上下文（改 state、store 或对话历史），或者跳转到其他步骤。原文提到的钩子包括 before_model、after_model、wrap_model_call、wrap_tool_call，以及 dynamic_prompt 装饰器。

内置的 SummarizationMiddleware 有三个参数：model（用于摘要的模型）、trigger（触发阈值，例如 {"tokens": 4000}）、keep（保留最近多少条消息，例如 ("messages", 20)）。超过阈值后，它用单独的 LLM 调用压缩旧消息，把摘要持久写入 state。这就是第三章 context editing、以及前一篇文档里“85% 触发压缩”的框架内实现。

下面是按官方 API 精简改写的示意，不是原文照搬：

from langchain.agents.middleware import dynamic_prompt, wrap_model_call, ModelRequest

@dynamic_prompt
def build_prompt(request: ModelRequest) -> str:
    role = request.runtime.context.user_role      # 读 runtime context
    return "You are a helpful assistant." + (" Read-only mode." if role == "viewer" else "")

@wrap_model_call
def route_model(request, handler):
    if len(request.messages) > 20:
        request = request.override(model=large_model)   # 瞬态替换，不改 state

7.4 官方给出的六条最佳实践

3
  1. 从静态提示和工具开始，需要时再加动态逻辑；
  2. 每次只增加一项上下文工程功能，并单独测试；

九、常见误区

2
  1. 只靠压缩续命。 Anthropic harness 一文说明，仅靠 compaction，Opus 4.5 也做不出生产级应用。状态要有窗口外的家。
  2. 压缩了就找不回来。 违背“可恢复”原则，之后某一步需要被压掉的信息时只能重来。
  3. 只记录成功。 保留失败痕迹，模型才会避开同一个坑。
  4. 功能清单用 Markdown 自由书写。 容易被模型改乱，用结构化格式并限制可修改字段。
  5. 模型自述“已完成”就算完成。 要有端到端的验证信号，并写进持久记录。
  6. 看见 90.2% 就全面多 Agent。 同一篇文章写明了约 15 倍 token 的代价和适用边界。
  7. 看见 Cognition 就全面禁用多 Agent。 反方论证针对的是强耦合的产物生成。
  8. 把瞬态改动当持久改动。 在中间件里裁剪消息，只影响当次调用；要永久压缩必须写入 state。
  9. 所有策略一次上齐。 LangChain 官方建议每次只加一项并单独测试。
