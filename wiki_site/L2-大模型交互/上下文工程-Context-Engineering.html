上下文工程是提示词工程的自然升级：Prompt 工程只管"怎么写指令"，上下文工程管的是每一次推理时，模型的上下文窗口里到底应该装什么——系统指令、工具定义、外部数据、消息历史全部在内（Anthropic，2025-09）。它比"把话说清楚"更重要的原因是实证的：模型对上下文的使用并不均匀。相关信息埋在中部时，GPT-3.5-Turbo 多文档问答准确率甚至低于完全不给文档的闭卷基线（56.1%）（arXiv:2307.03172）；Chroma 对 18 个模型的测试显示，同样的信息，约 300 token 的聚焦提示在所有模型上全面胜过约 113K token 的全量历史（Context Rot，2025-07）。因此上下文必须当作有限且边际收益递减的资源来经营。最关键的三条判断：① 卡帕西的定义——上下文工程是"在每一步为上下文窗口装填恰好正确信息"的精密技艺；② Anthropic 的操作准则——"找到实现目标所需的最小高信号 token 集合"；③ LangChain 的落地框架——write / select / compress / isolate 四类策略，今天的好 Harness 本质上就是上下文工程的交付机制。

上下文的四个组成部分

3

LangChain 官方博客把需要管理的上下文归为四类（与 Anthropic 的解剖一致）：

组成部分 内容 管理策略
指令（Instructions） system prompt、few-shot 示例、工具描述 Anthropic：写在"正确高度"（right altitude）——足够具体能引导行为，又不硬编码脆弱逻辑；用 XML 标签/Markdown 标题分节；示例要多样且典型，不要堆边界 case
知识（Knowledge） 检索到的文档、外部数据、注入的事实 不预塞，改用 just-in-time 检索（RAG/搜索），让 Agent 在需要时自己取；检索结果只给轻引用
工具定义（Tools） 工具 schema、MCP 服务描述 工具要自包含、容错、最小且不重叠——臃肿的工具集制造模糊的决策点
历史（History） 消息历史、工具调用结果、Agent 中间产物 最大的失控源：需压缩（compaction）、剔除（offload）、摘要治理

一句话：指令和工具定义是常驻成本，要最小化；知识和历史是动态负载，要按需化。

# 失效模式 实证结论与数字 来源
1 Lost in the middle（位置偏置） 性能呈 U 形曲线：相关信息在开头/结尾最好，埋在中部显著变差；20 篇文档场景下，GPT-3.5-Turbo 中部准确率低于闭卷基线 56.1%——给文档反而不如不给。专为此优化的长上下文模型同样中招 arXiv:2307.03172（TACL 2023）
2 Context rot（整体衰减） Chroma 测 18 个模型（含 GPT-4.1、Claude 4、Gemini 2.5、Qwen3）：任务难度不变、只加长输入，准确率持续下降；LongMemEval 上约 300 token 的聚焦提示在所有模型上胜过约 113K token 的全量历史——多出的 11 万 token 是净负资产 Chroma Research, 2025-07
3 注意力稀释（attention budget） Transformer 让每个 token 两两交互（n² 关系），上下文越长关系捕捉越稀薄；Anthropic 称之为有限的"注意力预算"，且训练分布中短序列远多于长序列，模型对超长依赖缺乏专门参数 Anthropic, 2025-09
4 干扰（distractor / poisoning） Drew Breunig 四分：Poisoning（幻觉进入上下文被当真）、Distraction（上下文淹没训练知识）、Confusion（多余上下文影响回答）、Clash（上下文内部互相矛盾）。Chroma 实测：1 个干扰项就低于干净基线，4 个更差；NoLiMa 基准（非字面匹配）下 32K 处 12 个模型中 10 个跌破短上下文基线的 50%，GPT-4o 从 99.3% 掉到 69.7% LangChain 博客引 Breunig；Chroma 2025-07；arXiv:2502.05167（ICML 2025）
5 成本 上下文即成本：每 token 都计入计费、延迟与 KV cache（见本库 vLLM 笔记）；LangChain 官方提醒"不要把检索全文灌进主上下文，否则 80% token 浪费在搬运" LangChain 官方博客/文档

关键认知：NIAH（大海捞针）基准会骗人——它只测字面匹配检索，各模型近乎满分，让人以为长上下文已解决；换成需要语义关联的 NoLiMa，跌落立刻现形。

实用策略清单

LangChain 把业界做法归为 write / select / compress / isolate 四类，加上 Anthropic 的补充：

策略 做什么 适用条件 一手出处
检索注入（select，just-in-time） 不预塞知识，Agent 用 RAG/搜索按需取 知识库大且动态；Chroma 数据（300 vs 113K token）证明聚焦注入严格优于全量塞入 Anthropic / LangChain
剔除/卸载（offload） 大结果不进窗口：LangChain Deep Agents SDK 对超过 20,000 token 的工具结果立即落盘，只留前 10 行预览 + 文件路径；超长的用户消息（阈值 50,000）同样处理 工具输出大（读大文件、API 拉数据）；Anthropic 也把"清理已消费的工具结果"列为最安全的轻量压缩 LangChain Deep Agents
压缩/摘要（compaction，compress） 上下文用到窗口 85% 时，用另一次 LLM 调用把旧消息压成结构化摘要（含会话意图、已产出、下一步），原文落盘可回查 长会话、长程任务；摘要后 Agent 可通过读文件恢复细节 LangChain Deep Agents / Anthropic
分层（渐进披露） 常驻的只有一行描述，正文按需加载——Skills/CLAUDE.md 的"薄入口 + 专业文档"模式；Anthropic 的系统提示分层（## Tool guidance 等分节） 常驻指令太多互相干扰时；对应本库 Claude Code 条目的"给地图不给说明书" LangChain / Anthropic / 本库 L3
结构化笔记（write，note-taking） Agent 定期把目标、进度、关键发现写到上下文外的文件（如 NOTES.md / todo list），需要时读回 多步骤任务；Anthropic 用 Claude 玩宝可梦演示：跨数千步靠自笔记保持策略连贯 Anthropic
隔离（isolate，子 Agent） 噪音大的活派给干净上下文的子 Agent，主 Agent 只拿浓缩结论——Anthropic 数据：子 Agent 可消耗数万 token，只回传 1,000–2,000 token 摘要 可并行的探索型工作（研究、搜索）；对应本库 Harness"编排"组件的子智能体 Anthropic / LangChain
重排序（re-rank） 把最相关的检索块放在上下文开头、次相关放结尾，其余夹中间 RAG 多路召回时——直接对冲 lost-in-the-middle 的 U 形曲线 arXiv:2307.03172 的工程推论

选择原则（Anthropic）：压缩适合需要连续对话流的任务；笔记适合有清晰里程碑的迭代开发；多 Agent 适合并行探索有收益的复杂研究。

本库 Harness工程到底是什么 里已经记录了三次命名演进：Prompt Engineering → Context Engineering → Harness Engineering。三者的关系是包含而非替代：

  • 上下文工程是 Harness 的核心子系统。LangChain 在 "The Anatomy of an Agent Harness" 中说得很直白："今天的好 Harness 在很大程度上就是良好上下文工程的交付机制"——compaction、tool offloading、Skills 渐进披露、子 Agent 隔离，全是 Harness 组件在替上下文工程干活。
  • 映射到 Harness 五组件：
  • 指令 = 上下文的"指令"部分（system prompt 分层、CLAUDE.md 薄入口）
  • 约束 = 工具定义与输出格式的最小化、不重叠设计
  • 记忆 = 结构化笔记、文件系统外置记忆（Anthropic memory tool 的方向）
  • 编排 = 子 Agent 上下文隔离 + compaction，即"让十匹马各带各的缰绳"
  • 反馈 = 工具调用结果这条最肥的上下文流的治理（offload / 剔除）
  • 衔接本库前沿精读笔记的 Model + Harness 框架：模型是 CPU，上下文窗口是 RAM（Karpathy 的类比），Harness 是操作系统——上下文工程就是操作系统的内存管理器：决定哪个页进 RAM、哪个页换出、哪个页压缩。
  • 分工：本库 L2 提示词工程条目讲"单次调用怎么说"；本条讲"多轮系统每轮窗口里装什么"；L3 Harness 条目讲"整个工程环境怎么设计"。本条是 L2 与 L3 之间的桥梁。

HOW：四类策略的最小可运行实现与 token 账（2026-11-03 补强）

上面回答了 WHY 与 WHAT；这一节把 write / select / compress / isolate 里最适合手写落地的三件（offload、compress、re-rank）给出最小实现，并给出"上下文值多少钱"的算式。代码与算式为本文编写的工程实现；策略与阈值（20K offload、85% compaction）的一手出处见文末 LangChain 链接。

1. offload：大工具结果落盘，只留预览 + 路径

3

对应 LangChain Deep Agents 的做法（超 20,000 token 的工具结果立即落盘、只留前 10 行预览）。手写版：

# context_offload.py —— 工具结果卸载（本文编写，无第三方依赖）
import hashlib, pathlib

STORE = pathlib.Path("./context_store"); STORE.mkdir(exist_ok=True)

def offload_tool_result(text: str, max_chars: int = 2000, preview_lines: int = 10) -> str:
    """超过阈值就把全文落盘，上下文里只留预览+指针；Agent 需要细节时按路径读回。"""
    if len(text) <= max_chars:
        return text
    digest = hashlib.sha256(text.encode()).hexdigest()[:16]
    path = STORE / f"{digest}.txt"
    path.write_text(text, encoding="utf-8")
    preview = "\n".join(text.splitlines()[:preview_lines])
    return (f"{preview}\n...[已截断] 全文 {len(text)} 字符，"
            f"需要细节时用读文件工具读取：{path}")

要点：① 指针必须可操作（给真实可读的路径，不是"内容太长已省略"），否则 Agent 无法自救；② 按内容哈希命名天然去重，同一结果被多个工具反复返回不会重复占盘；③ 这是可逆压缩——与摘要不同，原文一个字没丢。

3. re-rank：对冲 lost-in-the-middle 的两行代码

3

arXiv:2307.03172 的 U 形曲线意味着检索块的摆放位置是免费的准确率：

def reorder_for_context(chunks):          # chunks 已按相关度降序
    """最相关放开头、次相关放结尾，其余夹中间——对冲位置偏置（工程推论，非论文原算法）。"""
    return chunks[::2] + chunks[1::2][::-1]

注意边界：如果检索器相关度排序本身不准，重排救不回来；先保证 top-1 真的最相关，再谈摆放。

4. 上下文成本算式：给"最小高信号 token 集合"一个量化目标2 个重点▾ 点开看本节重点
本节重点
  • 长会话月成本 ≈ 平均单轮token × 轮数 × 会话数 × 30 × 单价 / 1e6
  • 第三行是关键：工具结果一旦进历史，之后每一轮都为它重复付费，所以 offload 的收益随会话长度平方级增长，而不是一次性
3 
单轮输入成本 = (system + 工具schema + 历史 + 检索注入)token × 输入单价 / 1e6
长会话月成本 ≈ 平均单轮token × 轮数 × 会话数 × 30 × 单价 / 1e6
offload 收益 = 被卸载token × 该结果被后续轮次重复携带的次数 × 单价 / 1e6

第三行是关键：工具结果一旦进历史，之后每一轮都为它重复付费，所以 offload 的收益随会话长度平方级增长，而不是一次性。示例占位：一条 8,000 token 的工具结果在后续 20 轮里被携带，卸载它省 160,000 token/会话；日 5,000 会话、输入 2 元/百万 token，则日省约 1,600 元（单价为演示占位，以实际账单为准）。
