1.1 "交互模式"指什么

3

前两篇深挖整合分别讲了"一次调用里怎么写提示词"和"每一轮窗口里装什么"。本篇换一个角度，按人与模型（以及程序与模型）交互的形态来梳理 L2 素材：

  1. 单轮调用：一条 system 加一条 user，得到一次回复；
  2. 多轮对话：用 messages 数组维护历史；
  3. 推理增强：让模型先想后答，或多次采样投票；
  4. 结构化输出：让模型的回复能被程序直接解析；
  5. 工具调用与 Agent 循环：模型在循环里调用工具；
  6. RAG 与检索：把外部知识按需带入；
  7. 服务化接入：通过 OpenAI 兼容接口调用自建或第三方模型；
  8. 安全交互：防注入、二次确认。

素材中这些内容分散在最佳答案、提示词工程、前沿精读笔记里，本文把它们按"交互形态"重新串起来，并在每一种形态里回答三个问题：怎么调用、有什么关键参数、常见的坑在哪。

1.3 贯穿各模式的三个共性

2

精读笔记归纳的三个共性，在每一种交互模式里都会反复出现：

  • 上下文即成本：每一种模式都要考虑窗口里装了多少；
  • 测量先行：Prompt 靠 eval，LangChain 靠 tracing，vLLM 靠真实负载压测；
  • harness 与模型可插拔：换模型不该动业务代码。

2.1 最小调用结构

3

素材中最基础的调用形态是：

messages = [
    {"role": "system", "content": "你是AGI课堂客服瓜瓜，回答课程问题。"},
    {"role": "user", "content": "你们有哪些课程？"}
]

三个要素：system 消息、user 消息、temperature。

  • System 消息负责角色、边界、语气、输出格式，模型对它的服从度高于 user 消息。
  • User 消息是实际输入。
  • Temperature 决定随机性。
2.2 Temperature 的选择1 个重点▾ 点开看本节重点
本节重点

3
取值 效果 适用场景
0 ~ 0.3 确定性，几乎无随机 分类、抽取、代码、数学题
0.4 ~ 0.7 平衡，有变化但不离谱 日常对话、文案生成

数据抽取案例用 temperature=0 减少随机性，多轮对话案例用 0.7 增加日常表达的变化；两者都是起点而非定律。即使 temperature=0，也不能保证跨服务版本逐字节一致，结构化任务仍需 schema 校验。

2.3 单轮调用的三种典型任务

3

客服问答：system 里写职责、边界规则、输出格式，并用 {knowledge_base_context} 注入产品知识库。

数据抽取：要求"严格输出 JSON 格式，不要输出其他内容"，给出字段与示例，temperature=0。

分类：给一个固定类别集合和每类一个示例，再给新输入，让模型输出类别。

三种任务有一个共同点：输出都是短而确定的，所以单轮调用就够用，且 temperature 偏低。

三、模式二：多轮对话——messages 是唯一的记忆

2
3.1 记忆的真相2 个重点▾ 点开看本节重点
本节重点
  • 多轮对话的实现很朴素：每一轮把用户输入以 user 消息追加到 messages，调用模型后把回复以 assistant 消息追加回去
  • 模型本身没有记忆，记忆就是每次请求都带上完整的 messages
3

多轮对话的实现很朴素：每一轮把用户输入以 user 消息追加到 messages，调用模型后把回复以 assistant 消息追加回去。模型本身没有记忆，记忆就是每次请求都带上完整的 messages。

素材里的多轮对话模板是一个 while 循环：读取用户输入，输入"退出"则结束；否则追加 user 消息，调用模型（temperature=0.7），打印回复，再追加 assistant 消息。

3.2 随之而来的两个问题

3

模板里有一行注释非常重要：messages 会越来越长，生产环境需要截断或摘要历史。这背后是两个现实问题：

  1. 成本：每一轮都要重新计费整段历史，对话越长越贵；
  2. 质量：根据上下文工程的结论，历史越长，上下文腐烂越明显。Chroma 的测试显示，300 token 的聚焦提示在所有模型上胜过 113K token 的全量历史。

本节重点
  • LangChain Deep Agents 里压缩的阈值是上下文用到窗口 85% 时触发，摘要包含会话意图、已产出内容与下一步，原文落盘可回查
3

素材给出的治理手段有层次：

做法 说明 适用
截断 只保留最近若干轮 对话短期、早期内容不重要
摘要 用另一次 LLM 调用把旧消息压成结构化摘要 长会话
卸载 大的工具结果落盘，窗口里只留预览和路径 工具输出大

3.4 多轮对话中 system 的稳定性

3

Anthropic 官方的要求是：thinking block 必须原样回传，对话历史保持 append-only；中途改写历史或重建 system，会让 thinking block 失效。这意味着在使用推理模式的多轮对话里，不能随意改动已有历史，要做压缩也要考虑是否会破坏这一约定。

此外，vLLM 的 prefix caching 要求共享前缀逐字节匹配才能命中。所以多轮对话里把稳定的 system prompt 放最前，且不改动，也有利于缓存复用。

四、模式三：推理增强——让模型先想再答

2
4.1 三种推理增强3 个重点▾ 点开看本节重点
本节重点
  • 素材把推理增强归为三个技巧
  • Tree-of-Thoughts（思维树）：让模型同时生成多个候选推理路径，评估每条路径可行性，选最优分支
  • Self-Consistency（自我一致性）：对同一问题用 temperature>0 采样多次，取多数投票的答案
3

素材把推理增强归为三个技巧。

Chain-of-Thought（思维链）：在 prompt 里要求显式解题步骤，或给带步骤的 few-shot 示例。它可能改善部分模型的数学与逻辑任务，也可能只生成看似合理的事后解释；最终答案与推理质量必须分别验证，不能把“有过程”当作“过程忠实”。

Self-Consistency（自我一致性）：对同一问题独立采样多次，再对最终答案做多数投票。课件的 自洽性.py 直观展示了“五条推理链—统计—投票”的目标，但它在单次请求、temperature=0 下要求模型自报五条链，不等于五次独立采样，其中的“置信度”也只是样本内投票比例。生产实现应发起 k 次请求、使用能产生多样性的解码设置，并把调用次数、延迟和投票一致率一起记录；只有自己的验证集证明收益覆盖 k 倍成本时才启用。

Tree-of-Thoughts（思维树）：让模型同时生成多个候选推理路径，评估每条路径可行性，选最优分支。适用于数独、规划等需要回溯的任务。

4.2 交互形态上的差别

3
技巧 调用次数 需要的采样设置 输出形态
CoT 1 次 视任务而定 推理过程加答案
Self-Consistency 多次 temperature>0 多个答案，投票得到一个
Tree-of-Thoughts 多次，含评估 通常需要多样的候选 多分支，选最优

可以看到，推理增强的代价主要体现在调用次数上：CoT 几乎无额外调用，自我一致性翻倍，思维树更多。这让它直接和成本、延迟挂钩，在 L3 的性能调优里要作为权衡项处理。

4.4 输出标签化

3

CoT 模板的补充技巧：复杂问题可以要求把推理过程写在 <think> 标签内，最终答案写在 <answer> 标签内。这样程序可以只提取 <answer>，用户界面也可以选择是否展示推理过程。

4.6 何时不要用推理增强

3

素材的整体精神是"先基线，再加码"。因此对于简单任务，比如翻译、摘要、分类，不必上 CoT，更不必上自我一致性。Anthropic 的建议是先定义成功标准、建 eval 集，延迟和成本问题换模型可能更划算。effort 的使用方式也体现了这一点：low effort 便宜且快，难例再用 high。

6.2 Agent 循环的交互特征

3

一个跑在循环里的 Agent，每一轮都可能产生工具调用，结果又回到上下文里。这带来三类交互层面的问题：

  1. 往返次数：官方建议在 agent 循环里批量发起 tool_use 以减少往返；
  2. 可见性：若要进度可见，需要显式要求模型补充总结；
  3. 上下文膨胀：工具结果是最肥的上下文流，需要卸载或剔除，例如超过 20,000 token 的结果立即落盘，只留前 10 行预览和文件路径。

  • 对主 Agent 而言，与子 Agent 的交互是"发出一个任务，收回一份摘要"，形态上更像一次函数调用

3

十、案例：同一个客服系统在八种交互模式下的样子

2

下面用客服场景把八种模式串一遍，所有元素都来自素材。

单轮：用户问"你们有哪些课程？"，system 设定了客服瓜瓜的职责与边界，temperature 取较低值保证回答稳定。

多轮：用户接着问"那第二门的价格呢？"，messages 里保留上一轮问答。随着对话变长，需要截断或摘要历史，否则成本与质量都会受影响。

推理增强：当用户问一个涉及套餐叠加优惠的计算问题时，可以在 prompt 里要求逐步推理，把过程写在 <think> 内，答案写在 <answer> 内；一般咨询则不用。

结构化输出：客服后台需要把用户反馈归类为功能建议、Bug 报告、咨询、投诉、其他，用 Few-shot 分类模板，temperature=0。

工具调用：客服需要查订单，把"查订单"写成一个带 docstring 的函数当工具；工具返回超大结果时落盘，只留预览。

RAG：产品知识库通过检索注入，不全量预塞；检索块重排序，最相关放开头；回答时先引用原文再作答。

服务化：后端若用 vLLM 自建模型，则通过 OpenAI 兼容接口，--served-model-name 固定逻辑名；监控 TTFT 与 gpu_cache_usage。

安全：用户输入用标签包裹；用户要求"忘记规则"时回复"我无法执行此操作"；退款等敏感事项转人工。

这个案例展示了：同一个业务，在不同的交互阶段会用到不同的模式，而且它们不是互斥的，而是叠加的。

十二、小结

2

L2 的交互模式可以概括为：单轮调用是原子，多轮对话靠 messages 带记忆，推理增强用调用次数换准确率，结构化输出让回复可被程序消费，工具与 Agent 循环把模型接入外部世界，RAG 把知识按需带入，服务化通过 OpenAI 兼容接口让模型可替换，安全三招贯穿全程。

这些模式背后是同一条主线：Model 与 Harness 分开。模型是可替换的件，harness 的各个部分（prompt、工具、检索、历史管理）决定了交互的形态与质量。

三个共性贯穿始终：上下文即成本，测量先行，harness 与模型可插拔。落到实践上，有几个必须记住的要点：temperature 要与任务匹配；多轮对话必须有历史治理；推理增强要按需使用，因为代价是调用次数；工具的 docstring 就是 API 文档；服务化时吞吐与延迟本质冲突，需要实测；凡用户输入和检索文档，都要当作数据而非指令。

素材里还留有几个缺口：多轮截断摘要未实现，RAG 里的防注入未实测，评测脚本缺位。这些是下一步工作的起点。

13.1 单轮 + 结构化输出：schema 校验兜底，不靠模型自觉

# structured_demo.py —— 模式四：结构化输出 + 校验 + 重试（本文编写）
import os, json
from pydantic import BaseModel, ValidationError
from openai import OpenAI

client = OpenAI(base_url=os.environ["OPENAI_BASE_URL"], api_key=os.environ["OPENAI_API_KEY"])

class Person(BaseModel):
    name: str
    age: int | None = None
    skills: list[str] = []

def extract(text: str, retries: int = 2) -> Person:
    prompt = ("从文本提取信息，严格输出 JSON："
              '{"name": str, "age": int|null, "skills": [str]}\n文本：' + text)
    for attempt in range(retries + 1):
        out = client.chat.completions.create(
            model=os.environ["MODEL"], temperature=0, max_tokens=256,
            messages=[{"role": "user", "content": prompt}],
        ).choices[0].message.content
        try:
            return Person.model_validate(json.loads(out))
        except (json.JSONDecodeError, ValidationError) as e:
            prompt = f"你上次的输出无法解析（{type(e).__name__}），请只输出合法 JSON。\n{out}"
    raise RuntimeError("多次重试仍不合规：转人工或记录 badcase，不要让脏数据进下游")

要点：校验失败后的重试 prompt 要带上错误输出与错误类型，让模型知道修什么；重试上限到了必须走兜底，不能无限循环烧钱。
