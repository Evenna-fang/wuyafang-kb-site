Few-shot和Zero-shot怎么选

WHY：在任务效果、示例成本与模型能力间取舍

这个问题的答案是什么3 个重点▾ 点开看本章重点
本章重点
  • 两者没有绝对优劣，选型要看三个维度：任务复杂度、示例成本、模型能力
  • 简单、通用、模型能力强 → Zero-shot，省 Token、可泛化
  • 复杂、有隐性偏好、模型能力不够或输出格式苛刻 → Few-shot，用范例把"默契"一次性对齐
2

Zero-shot（零示例）= 只给指令，不给范例；Few-shot（少示例）= 给 1~N 个输入/输出范例再让模型处理新输入。两者没有绝对优劣，选型要看三个维度：任务复杂度、示例成本、模型能力。

一句话结论：
- 简单、通用、模型能力强 → Zero-shot，省 Token、可泛化。
- 复杂、有隐性偏好、模型能力不够或输出格式苛刻 → Few-shot，用范例把"默契"一次性对齐。
- 二者之间摇摆 → 先 Zero-shot 跑一版，看输出哪里飘，再针对那个点加 1~2 个 Few-shot 示例，不要一上来塞一堆。

WHYT：Zero-shot 与 Few-shot 的判断维度与决策表

详细内容

1. 任务复杂度：先判断"模型能不能靠常识做"3 个重点▾ 点开看本节重点
本节重点
  • 《Prompt魔法》被划了 30 次的一段话点明了关键机制："当你把一个问题，按照思维链的方式，一步步 Prompt 大型语言模型时，往往能够得到正确的答案
  • "——也就是说，对于有明确推理步骤的任务，即使不给范例，只要你在指令里把步骤拆清楚（Chain-of-Thought 式 Zero-shot），大模型自己就能走出来
  • 任务形式通用：翻译、摘要、改写、常识问答、结构化抽取（"把这段话里的人名抽出来"）
3

《Prompt魔法》被划了 30 次的一段话点明了关键机制："当你把一个问题，按照思维链的方式，一步步 Prompt 大型语言模型时，往往能够得到正确的答案。"——也就是说，对于有明确推理步骤的任务，即使不给范例，只要你在指令里把步骤拆清楚（Chain-of-Thought 式 Zero-shot），大模型自己就能走出来。

适合 Zero-shot 的任务特征：
- 任务形式通用：翻译、摘要、改写、常识问答、结构化抽取（"把这段话里的人名抽出来"）。
- 输出格式宽松：不要求严格 JSON、不要求匹配某种企业内部规范。
- 偏好是大众共识：比如"写一封礼貌的邮件"——GPT 类模型默认就懂。

适合 Few-shot 的任务特征：
- 有隐性规则：例如"我们公司的周报要按'本周完成 / 下周计划 / 风险'三段，且每段不超过 80 字"——这种偏好大众不懂，必须用范例告诉模型。
- 输出格式苛刻：要解析、要进下游流水线、要严格 JSON schema，靠"你输出 JSON"这种描述经常飘。
- 边界 case 多：例如情感分析要区分"讽刺"和"反讽"，一个范例比一段解释管用。
- 需要对齐某种风格：品牌语气、特定行话、内部术语。

《如何用提问解决问题》的简介直接把这点写进了方法论："指导用户设计包含 few-shot 示例的提示词，优化模型输出质量。"——作者的立场很清楚：复杂任务不是靠写更长的指令，而是靠补几个真实示例。

2. 示例成本：Few-shot 不是免费的

3

Few-shot 的隐性成本有三类，选型时要算进去：

  • Token 成本：每个示例都是几百到几千 Token，重复塞在每次请求里。在高频调用场景（如批量评估、RAG 流水线），这是真金白银。
  • 上下文挤压：示例占了位置，留给用户输入和检索结果的空间就少了，长文档任务尤其敏感。
  • 示例偏差：模型会被示例"带节奏"。如果你给的 3 个示例都偏长，它就会默认输出偏长；如果示例恰好是某种特殊 case，模型会误以为所有输入都长这样。

《AI提示工程》里被划了 26 次的一句话提供了成本视角："提示信息只管分配'任务'和提出'目标'，具体工作交给大语言模型去执行并完成。"——理想的 Prompt 应该是任务说明书，不是范例集。能用任务描述清楚的事，不要靠示例；只有描述不清的，才用示例兜底。

实操上有个经验法则：示例数量从 1 个开始加。1 个能对齐，就不要 3 个；3 个不够，再补到 5 个。示例之间要覆盖不同类型的输入（正面、边界、反面），而不是同一个 case 的三种写法。

3. 模型能力：不同尺寸的模型吃不同的套路3 个重点▾ 点开看本节重点
本节重点

  • 强模型（GPT-4 / Claude / 国产旗舰）：Zero-shot 能力已经很强，尤其在推理、摘要、代码这些"见过太多"的任务上
  • 中等模型（7B~70B 开源）：Zero-shot 容易飘格式、漏指令
3

《Prompt魔法》的另一句被划 28 次的话值得记住："大语言模型仅仅是通过学习文本数据中的统计规律来产生输出，缺乏真正的理解和情感体验。"——这句话反过来用就是选型依据：

  • 强模型（GPT-4 / Claude / 国产旗舰）：Zero-shot 能力已经很强，尤其在推理、摘要、代码这些"见过太多"的任务上。给示例的边际收益在递减，但给了也不会错。
  • 中等模型（7B~70B 开源）：Zero-shot 容易飘格式、漏指令。Few-shot 是最有效的"对齐补丁"，比写更长的 system prompt 便宜。
  • 小模型 / 边缘模型：Few-shot 也救不了逻辑复杂任务，得回到微调。

《如何用提问解决问题》的 648 人划线句 "提问驱动思考，答案终止想象" 提醒我们一件事：选型不是一次性决定。真正稳定的流水线是——先 Zero-shot 跑基线，看输出错在哪类输入上，针对错的那一类补 Few-shot 示例，再跑一轮。这是一个"提问→验证→迭代"的闭环，而不是一上来就把 Prompt 堆成瑞士军刀。

HOW：把选型从"感觉"变成可复跑的实验（2026-11-03 补强）

前面三节回答"怎么判断"，这一节给出三件可直接落地的工具：一个 A/B 对照评测脚本、一条示例成本算式、一份示例编写清单。判断维度是书里的，评测代码与算式是本文编写的工程实现，可在本库 ollama / vLLM 的 OpenAI 兼容端点上直接跑。

1. 最小 A/B 对照：同一批评测集，只改"给不给示例"1 个重点▾ 点开看本节重点
本节重点
  • 原则来自 Anthropic 官方提示工程文档的"eval 先行"（先定义成功标准与评测集，再动 prompt；见 前沿精读笔记 第一节）
3

原则来自 Anthropic 官方提示工程文档的"eval 先行"（先定义成功标准与评测集，再动 prompt；见 前沿精读笔记 第一节）。把 Zero-shot 与 Few-shot 当成两个候选版本，其余条件（模型、温度、system 其他部分）全部锁死：

# fewshot_ab.py —— Zero-shot vs Few-shot 对照评测（本文编写，需 pip install openai）
# 用法：OPENAI_BASE_URL=http://127.0.0.1:11434/v1 OPENAI_API_KEY=ollama \
#       MODEL=qwen2.5:7b python3 fewshot_ab.py
import json, os
from openai import OpenAI

client = OpenAI(base_url=os.environ.get("OPENAI_BASE_URL", "http://127.0.0.1:11434/v1"),
                api_key=os.environ.get("OPENAI_API_KEY", "ollama"))
MODEL = os.environ.get("MODEL", "qwen2.5:7b")

# 评测集：至少 20 条，覆盖正面/边界/反面三类（此处为示意，换成你的真实 badcase）
CASES = [
    {"text": "希望能增加深色模式", "label": "功能建议"},
    {"text": "App闪退了，iOS 17系统", "label": "Bug报告"},
    {"text": "付费后功能还是用不了，要求退款！", "label": "投诉"},
    {"text": "功能还行，就是这价格是在抢钱吗", "label": "投诉"},  # 边界：带夸但主诉是价格
]
LABELS = "[功能建议, Bug报告, 咨询, 投诉, 其他]"
EXAMPLES = (  # Few-shot 臂唯一的差异变量
    '示例：\n"希望能增加深色模式" → 功能建议\n'
    '"App闪退了，iOS 17" → Bug报告\n'
    '"怎么导出数据？" → 咨询\n'
    '"付费后用不了，要求退款！" → 投诉\n'
    '"今天天气不错" → 其他\n'
)

def run_arm(use_examples: bool) -> float:
    correct = 0
    for case in CASES:
        prompt = f"将用户反馈分类为：{LABELS}\n"
        if use_examples:
            prompt += EXAMPLES
        prompt += f'新输入："{case["text"]}"\n只输出类别名，不要解释。'
        resp = client.chat.completions.create(
            model=MODEL, temperature=0, max_tokens=16,
            messages=[{"role": "user", "content": prompt}],
        )
        pred = resp.choices[0].message.content.strip()
        if pred == case["label"]:
            correct += 1
        else:
            print(f"  错例 [{'few' if use_examples else 'zero'}] "
                  f"输入={case['text']!r} 期望={case['label']} 实得={pred!r}")
    return correct / len(CASES)

if __name__ == "__main__":
    zero = run_arm(False)
    few = run_arm(True)
    print(f"Zero-shot 准确率: {zero:.0%}\nFew-shot 准确率: {few:.0%}")
    print("判读：提升 <5 个百分点就不值得常驻示例（成本见下节）；"
          "错例集中在哪一类，就只给那一类补示例，不要全量堆。")

三条纪律（否则实验无效）：

  1. 温度锁 0、max_tokens 锁小：分类任务输出只允许一个类别名，把随机性和啰嗦都排除，差异才能归因到"示例"这个变量。
  2. 错例必须打印出来看：准确率只告诉你差多少，错例才告诉你差在哪——错例集中在边界类，就补边界类示例；Zero-shot 已全对，就直接收工不加示例。
  3. 评测集与示例集分开：示例不要从评测集里挑，否则测的是"背答案"不是泛化。

2. 示例成本算式：Few-shot 的账单是能提前算出来的

3

设示例区共 E token（用端点返回的 usage.prompt_tokens 实测，不要估算），每次请求的用户输入为 U token，输入单价为 P（元/百万 token），日调用量为 N：

Few-shot 每日增量成本 = E × N × P / 1,000,000
示例占比           = E / (E + U)        # >50% 说明你在为示例打工，不在为用户输入打工

代入一组示例占位数字（单价仅为演示算式，真实单价以你所用平台账单为准）：E=600、N=50,000、P=2 元/百万 token，则每日增量 = 600 × 50,000 × 2 / 1e6 = 60 元/天，约 1800 元/月。这就是"先 Zero-shot 跑基线、提升不明显就不加示例"的量化依据。

两个降本手段（细节见 上下文工程·成本侧实战）：

  • 前缀稳定 + Prompt Caching：示例区放在 system/消息最前且逐字节不变，命中缓存后输入价按缓存价计（Anthropic 缓存读约为常规输入的 1/10，以官方价格页为准），上例可降到约 6 元/天。
  • 自部署端点用 prefix caching：vLLM 对相同前缀跳过重复 prefill，省钱变成省延迟与显存（见 L12 vLLM 推理加速）。
