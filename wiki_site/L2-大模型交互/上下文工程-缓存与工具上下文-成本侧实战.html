本库已有两篇上下文工程文档讲清了“装什么”：窗口里该放哪些信息，位置偏置和 context rot 为什么存在，write / select / compress / isolate 四类动作怎么用。这一篇补的是另一半：装进去的东西怎么装得便宜、装得稳。结论有四条。

  1. 生产环境 Agent 最该盯的指标是 KV-cache 命中率。 Manus 披露其输入与输出 token 比约为 100:1，缓存输入与未缓存输入相差 10 倍（以 Claude Sonnet 计，0.30 对 3 USD/MTok）。Agent 每走一步都要把整段历史重新发给模型，成本主要花在重复的前缀上。
  2. 缓存按前缀逐字节匹配，而且分层失效。 Anthropic 文档规定缓存前缀顺序是 tools → system → messages，改动某一层，这一层和它之后所有层的缓存一起作废。所以“稳定的放前面、变化的放后面、历史只追加”是硬约束，不是风格偏好。
  3. 工具定义是最大的常驻成本，也是最容易被忽略的一块。 Anthropic 的实测里，5 个 MCP 服务器共 58 个工具，仅定义就约占 55K token。Tool Search（按需加载工具定义）把这一块压到 8.7K 量级，同时选工具的准确率还上升了。
  4. 写工具就是写上下文。 工具返回什么、返回多少、出错时怎么说，都直接决定下一轮窗口里有什么。Anthropic 给出的做法包括 response_format 枚举（同一接口详细版 206 token、简洁版 72 token）、分页和截断的合理默认值（Claude Code 默认把工具响应限制在 25,000 token）。

单次问答里，这个问题不明显：输入发一次，输出生成一次。Agent 不同。Manus 的描述是，一个典型任务平均要约 50 次工具调用；每次调用后，模型都要拿到“全部历史加上最新观察结果”，再产出一个很短的结构化函数调用。于是输入远大于输出，Manus 实测约 100:1。这时候真正花钱、真正拖慢首 token 延迟的，是那一大段几乎没变过的历史前缀。

2.1 前缀匹配是怎么回事

3

语言模型是自回归的：每个 token 的表示依赖它之前的全部 token。推理引擎把已经算过的前缀对应的 key/value 张量缓存起来（KV cache），下一次请求如果以完全相同的前缀开头，就可以跳过这一段的预填充。Manus 的原话大意是：只要有一个 token 不同，从这个位置开始往后的缓存全部失效。

这给上下文设计提了一个很具体的要求：前缀里不能有“每次都不一样”的东西。

2.2 实践一：保持前缀稳定3 个重点▾ 点开看本节重点
本节重点
  • Manus 举的反例是把精确到秒的时间戳放在系统提示词开头
  • 这样做看起来无害，实际上让每一次请求的第一个 token 之后就开始分叉，整段缓存永远命不中
  • 如果确实需要给模型时间信息，应放在靠后的位置，或精度降到不影响前缀的程度
3

Manus 举的反例是把精确到秒的时间戳放在系统提示词开头。这样做看起来无害，实际上让每一次请求的第一个 token 之后就开始分叉，整段缓存永远命不中。如果确实需要给模型时间信息，应放在靠后的位置，或精度降到不影响前缀的程度。

2.3 实践二：上下文只追加，序列化要确定

3

两条规则：

  • 不回头修改之前的动作和观察结果。任何对历史的原地修改，都会让修改点之后的缓存全部作废。
  • 序列化要确定。Manus 专门提醒，很多编程语言和库在序列化 JSON 时不保证键的顺序稳定。Anthropic 的缓存文档里也有同样的提示：Swift、Go 等语言序列化工具定义时可能随机化键顺序，导致缓存失效。表面上看工具定义没变，字节序列却变了。
2.4 实践三：必要时显式设置缓存断点3 个重点▾ 点开看本节重点
本节重点
  • 有些服务商不自动识别缓存边界，需要在请求里标出断点
  • 路由是关键：缓存在某个 worker 的显存里，请求被分到另一个 worker 就等于没有缓存
  • Manus 的建议是断点至少包含系统提示词末尾，并考虑缓存过期
3

有些服务商不自动识别缓存边界，需要在请求里标出断点。Manus 的建议是断点至少包含系统提示词末尾，并考虑缓存过期。自托管模型时，可以在 vLLM 里开启前缀缓存，并用 session ID 把同一会话的请求稳定路由到同一个 worker。路由是关键：缓存在某个 worker 的显存里，请求被分到另一个 worker 就等于没有缓存。本库《L2 上下文工程深挖整合》第八章已讲过 vLLM 的 max-model-len、gpu-memory-utilization 和 prefix caching 参数，这里不重复。

三、Anthropic Prompt Caching：官方机制逐项拆解

2

以下内容来自 Anthropic 平台文档（本次抓取日期 2026-11-02）。文档会随模型更新，具体模型名单和价格请以官方页面为准。

3.1 启用方式与前缀结构3 个重点▾ 点开看本节重点
本节重点
  • Messages API 需要显式开启
  • 系统把断点放在最后一个可缓存块上，并随对话增长自动后移
  • 显式断点：把 「cache_control」 放到具体内容块上，精细控制缓存范围
3

Messages API 需要显式开启。有两种写法：

  • 自动缓存：请求顶层加一个 cache_control: {"type": "ephemeral"}。系统把断点放在最后一个可缓存块上，并随对话增长自动后移。多轮对话优先用这种方式。
  • 显式断点：把 cache_control 放到具体内容块上，精细控制缓存范围。目前唯一支持的类型是 ephemeral。

缓存前缀的拼接顺序固定为 tools → system → messages。cache_control 所在块及它之前的全部内容构成缓存前缀。

3.2 断点数量、最小长度与 TTL

3
项目 规则
每个请求的显式断点上限 4 个；自动缓存占 1 个槽位，已有 4 个显式断点再开自动缓存会返回 400
最小可缓存长度 因模型而异，文档列出 512、1,024、2,048、4,096 token 四档；不足最小长度不缓存，也不报错
默认 TTL 5 分钟；每次命中免费刷新
可选 TTL 1 小时，"ttl": "1h"，写入价为基础输入价的 2 倍
计时起点 从发起写入或读取的请求开始算，不是从响应结束算

计时起点这一条容易踩坑。文档举的例子：如果一次响应流式输出用了 4 分钟，那么下一次请求必须在这次响应结束后约 1 分钟内发出，才能复用同一前缀。

选 TTL 的建议是：调用间隔短于 5 分钟的循环，用默认 5 分钟即可，因为每次命中都会免费续期；间隔在 5 分钟到 1 小时之间的任务（比如人在回路里审阅后继续），用 1 小时。同一请求混用两种 TTL 时，长 TTL 的条目必须排在短 TTL 之前。

3.3 计费倍率2 个重点▾ 点开看本节重点
本节重点
  • 断点本身不收费，只为实际写入和读取的 token 付费
  • 把这张表和第一章的 10 倍差价对照：只要一段前缀被读取两次以上，5 分钟写入的 1.25 倍溢价就已经回本
3

以基础输入价为 1 倍：

类型 倍率
5 分钟缓存写入 1.25x
1 小时缓存写入 2x
缓存读取与刷新（多数模型） 0.1x
缓存读取（部分最新模型） 0.05x 或 0.025x

断点本身不收费，只为实际写入和读取的 token 付费。把这张表和第一章的 10 倍差价对照：只要一段前缀被读取两次以上，5 分钟写入的 1.25 倍溢价就已经回本。

3.4 回看窗口：最容易写错的地方

3

读取时系统怎么找缓存：先在当前断点处计算前缀哈希，查有没有条目；没有就逐块向前回退，检查更早位置的哈希；每个断点最多检查 20 个位置，断点本身算第 1 个；20 个位置内找不到就停。

由此引出三条规则，官方文档都明确写了：

  1. 写入只发生在断点处。 断点之前的位置不会自动写入。
  2. 回看只能找到之前请求已经写入的条目，它不会去“发现”稳定内容并缓存它。
  3. 每轮新增少于 20 个块时，在最后一个块上设断点即可；如果会话增长使断点距上次写入超过 20 个块，要在更靠近的位置提前加第二个断点。

文档还给了一个典型错误：块 1 到 5 是静态系统上下文，块 6 含时间戳和用户消息，却把断点设在块 6 上。每次时间戳不同，哈希永远不匹配，结果是每次都写入、从不读取，白付 1.25 倍。正确做法是把断点移到块 5。官方最佳实践里的说法与 Manus 完全一致：断点设在前缀中最后一个跨请求保持不变的块上。

3.5 哪些改动会让缓存失效1 个重点▾ 点开看本节重点
本节重点
  • 实战含义：不要在会话中途切换这些开关
3

文档用一张表列出了各类改动对三层缓存的影响，归纳如下：

改动 影响范围
工具定义（名称、描述、参数） tools 层及其后全部失效
联网搜索开关、引用（citations）开关 tools 层缓存保留，其后各层失效
tool_choice 只使 messages 层失效
图片增删（提示中任何位置） tools 层缓存保留，其后各层失效（逐层细节以官方表格为准）
思考参数（thinking，含 budget_tokens）、effort messages 层失效；部分模型连带更早的层

实战含义：不要在会话中途切换这些开关。 如果需求确实是中途增加指令或工具，官方给了不破坏缓存的通道：较新的模型支持用 {"role": "system"} 消息在对话中追加指令；一个 beta 头支持通过 tool_addition 块增加工具而不改动 tools 数组。具体能力以官方文档当前版本为准。

3.6 用 usage 字段验证

3

响应的 usage 里有四个字段：cache_creation_input_tokens（本次写入）、cache_read_input_tokens（本次读取）、input_tokens（最后一个断点之后、未参与缓存的部分）、以及按 TTL 拆分的 cache_creation。总输入的算法是：

total_input_tokens = cache_read_input_tokens + cache_creation_input_tokens + input_tokens

文档的例子：10 万缓存 token 被读取、0 个新写入、用户消息 50 token，则三个字段分别为 100000、0、50，总计 100,050。如果前两项都是 0，说明这次请求没有被缓存（要么不足最小长度，要么断点位置不对）。命中率不是猜出来的，应该从这几个字段统计。 文档还提供了 cache diagnostics 功能，可以让 API 对比连续请求，指出前缀在哪里分叉。

3.7 预热3 个重点▾ 点开看本节重点
本节重点
  • 把 「max_tokens」 设为 0，API 会读取提示并写入缓存，但不生成输出
  • 适合在用户真正发问之前预先写好大前缀（比如一份长文档加一套工具）
  • 5 分钟缓存需要每 5 分钟至少预热一次，间隔更长就改用 1 小时 TTL
3

把 max_tokens 设为 0，API 会读取提示并写入缓存，但不生成输出。适合在用户真正发问之前预先写好大前缀（比如一份长文档加一套工具）。限制是：预热请求不能同时用流式、扩展思考、结构化输出或强制 tool_choice；它的 thinking 与 effort 配置需要和后续请求一致，否则 messages 层缓存对不上。5 分钟缓存需要每 5 分钟至少预热一次，间隔更长就改用 1 小时 TTL。

4.1 问题3 个重点▾ 点开看本节重点
本节重点
  • 工具越多，模型越容易选错，效率也会下降，Manus 的说法是“重装备的 Agent 反而变笨”
  • 直觉的解法是按阶段动态增删工具，只给当前用得上的
  • 1. 工具定义位于上下文前部，改动它会让其后所有缓存失效（第三章已讲）
3

工具越多，模型越容易选错，效率也会下降，Manus 的说法是“重装备的 Agent 反而变笨”。直觉的解法是按阶段动态增删工具，只给当前用得上的。Manus 的经验是除非必要，不要在迭代中途动态增删工具，原因有两个：

  1. 工具定义位于上下文前部，改动它会让其后所有缓存失效（第三章已讲）。
  2. 历史里的动作和观察如果引用了已不在当前工具集中的工具，模型会困惑，可能产生 schema 错误或幻觉动作。

4.2 Manus 的做法：约束解码

3

Manus 保持工具定义不变，用一个上下文感知的状态机管理“当前允许调用什么”，在解码阶段对 token 的 logits 做掩码，禁止或强制某些动作。文中区分了三种函数调用模式：

模式 含义
Auto 模型自己选择调用还是直接回复
Required 必须调用工具，但选哪个不受限
Specified 必须从指定子集中选一个调用

为了让“指定子集”好实现，Manus 要求工具名使用统一前缀，如 browser_、shell_。这样只要限定 token 前缀，就能把可选范围收窄到一组工具，不需要写有状态的 logits 处理器。

  • 传统方式任务开始前约占 77K token，使用后约 8.7K，原文称保留了 95% 的上下文窗口；
  • 内部 MCP 评测中，Opus 4 的工具选择准确率从 49% 升到 74%，Opus 4.5 从 79.5% 升到 88.1%；
  • 原文对节省幅度有多处表述（85%、191,300 对 122,800 token 等）口径并不一致。按文中 77K 对 8.7K 计算，降幅约 89%。引用时请标明具体口径，不要混用。

适用条件：工具定义总量超过 10K token、工具数 10 个以上、出现选错工具的情况、同时用多个 MCP 服务器。代价是多一次搜索步骤，带来额外延迟。文中称延迟加载不会破坏 prompt caching，因为这些工具本来就不在初始提示里。

这和上一篇文档里的“渐进披露”是同一思路：常驻的只有索引，正文按需取。Tool Search 把这条思路用到了工具定义上。

5.2 Programmatic Tool Calling：中间结果不进窗口

3

问题：每次工具调用的结果都会进入上下文，每次调用还要一轮模型推理。读 200KB 的原始数据只为得出一个汇总数字，窗口被白白撑满。

机制：让 Claude 写一段 Python 编排代码，在代码执行环境里调用工具，对结果做过滤、聚合，只把最终输出返回上下文。工具需要通过 allowed_callers 选择开启。原文的预算核对例子里，原始数据约 200KB，最终只返回约 1KB。

数字：复杂研究任务平均 token 用量从 43,588 降到 27,297（降 37%）；20 多次工具调用合并进一段代码，省去 19 次以上的推理往返；内部知识检索准确率从 25.6% 升到 28.5%，GIA 基准从 46.5% 升到 51.2%。

不适用：单次简单调用，或者模型确实需要看到全部中间结果才能决策的任务。

它是 LangChain Deep Agents“大结果落盘、只留预览”那条策略的另一种实现：一个把结果放到文件系统，一个把结果留在代码沙箱里，目的一样，都是让中间产物不占窗口。

5.3 Tool Use Examples：用示例补 schema 说不清的部分3 个重点▾ 点开看本节重点
本节重点
  • JSON Schema 只能描述结构，说不清“什么时候该填这个可选参数”“两个字段怎么搭配”“日期用什么格式”
  • 内部测试中，复杂参数处理的准确率从 72% 提升到 90%
  • 在工具定义里加 「input_examples」 可以补上
3

JSON Schema 只能描述结构，说不清“什么时候该填这个可选参数”“两个字段怎么搭配”“日期用什么格式”。在工具定义里加 input_examples 可以补上。内部测试中，复杂参数处理的准确率从 72% 提升到 90%。官方建议每个工具 1 到 5 个示例，用真实数据，只为 schema 无法说明的歧义添加。代价是示例本身也占 token，所以要克制。

六、写工具就是写上下文：Anthropic 的工具设计原则

2

Anthropic 工程博客《Writing tools for agents》（2025-09-11）把工具定义为“确定性系统与非确定性 Agent 之间的契约”。其中与上下文直接相关的原则如下。

6.1 选对工具，而不是多给工具3 个重点▾ 点开看本节重点
本节重点
  • 不要把 API 端点逐个包装成工具
  • Agent 的上下文有限，所以应该提供 「search_contacts」 而不是 「list_contacts」（后者把整个通讯录倒进窗口）
  • 把常连用的多步操作合并成一个工具，比如 「schedule_event」、「search_logs」（只返回相关日志及上下文）、「get_customer_context」
3

不要把 API 端点逐个包装成工具。Agent 的上下文有限，所以应该提供 search_contacts 而不是 list_contacts（后者把整个通讯录倒进窗口）。把常连用的多步操作合并成一个工具，比如 schedule_event、search_logs（只返回相关日志及上下文）、get_customer_context。

6.2 命名空间

3

按服务和资源加前缀，如 asana_search、asana_projects_search。原文说前缀或后缀两种风格对效果有“不可忽略的影响”，要靠自己的评测来选。这与 Manus 的 browser_ / shell_ 前缀是同一个做法，只是一个服务于模型选择，一个还服务于解码约束。

6.3 只返回高信号字段2 个重点▾ 点开看本节重点
本节重点
  • 返回 「name」、「file_type」 这类语义化字段，少返回 「uuid」、「mime_type」 这类底层标识
  • 把 UUID 解析成语义化名称或从 0 开始的简单 ID，能显著提高检索精度、减少幻觉
3

返回 name、file_type 这类语义化字段，少返回 uuid、mime_type 这类底层标识。把 UUID 解析成语义化名称或从 0 开始的简单 ID，能显著提高检索精度、减少幻觉。

6.4 response_format：让 Agent 自己选粒度

3

给工具加一个 DETAILED / CONCISE 枚举参数。原文数字：同一个响应，详细版 206 token，简洁版 72 token；Slack 的例子里，简洁模式约用了详细模式三分之一的 token。需要后续调用的 ID（如 thread_ts）放在详细模式里返回，这样 Agent 先用简洁模式扫一遍，真要深入时再拉详细版。

6.5 token 效率：分页、截断、可操作的错误3 个重点▾ 点开看本节重点
本节重点
  • 对可能很大的响应，组合使用分页、范围选择、过滤和截断，并设置合理的默认值
  • Claude Code 默认把工具响应限制在 25,000 token
  • 截断时要给出引导，告诉 Agent 如何改用更小、更有针对性的查询
3

对可能很大的响应，组合使用分页、范围选择、过滤和截断，并设置合理的默认值。Claude Code 默认把工具响应限制在 25,000 token。截断时要给出引导，告诉 Agent 如何改用更小、更有针对性的查询。错误信息要具体可操作，而不是晦涩的错误码或堆栈。

6.6 工具描述也是 prompt

3

像给新员工介绍工具那样写：隐含背景、专用查询格式、资源之间的关系都写清楚；参数名要明确，用 user_id 而不是 user。原文称，对工具描述的精细修改使 Claude Sonnet 3.5 在 SWE-bench Verified 上达到当时的最优水平。

6.7 用评测迭代，别凭感觉3 个重点▾ 点开看本节重点
本节重点
  • 官方流程是：快速做原型 → 用真实多步任务做评测（任务要强，通常需要多次、乃至数十次工具调用；每个任务配可验证的结果）→ 读转录，留意 Agent 没说出口的内容 → 让 Claude Code 批量改工具 → 用保留测试集防过拟合
  • 要采集的指标包括准确率、耗时、工具调用次数、token 消耗和工具错误
  • 大量冗余调用提示分页或截断参数需要调整，大量参数错误提示描述或示例需要改进
3

八、常见误区3 个重点▾ 点开看本章重点
本章重点
  • 1. 把缓存当成自动优化
  • 同一篇文章里出现 85%、89%、95% 三个数，使用时要写清分母
  • 缓存按字节匹配，一个时间戳就能让命中率归零，而且不会报错，只会悄悄变贵
2
  1. 把缓存当成自动优化。 缓存按字节匹配，一个时间戳就能让命中率归零，而且不会报错，只会悄悄变贵。
  2. 断点设在最新一条用户消息上。 用户消息每轮都变，应设在它之前最后一个稳定块。
  3. 会话中途改 thinking 参数或 tool_choice 却不知道要付重写的钱。 见 3.5。
  4. 以为工具越多越灵活。 55K token 的定义换来的是选择困难，Tool Search 实测准确率还更高。
  5. 工具把一切都返回。 窗口里的每个 UUID 都是成本。
  6. 只看单次调用价格。 Agent 的成本是步数乘以前缀长度，命中率才是杠杆。
  7. 引用节省比例不标口径。 同一篇文章里出现 85%、89%、95% 三个数，使用时要写清分母。

本库真实落地（源码核对，2026-11-04）

  • 本库的成本控制不靠提示词压缩，靠「缓存 + 配额 + 降级」三件套（本次读源码）：
    | 手段 | 位置 | 机制 |
    |---|---|---|
    | rerank 缓存 | rag/query.py L893-903 | 键 = md5(query\|"\|".join(d[:50] for d in docs))，命中直接读 data/rerank_cache/<key>.json |
    | 改写日配额 | rag/query.py L1018 inc_rewrite_counter() + data/rewrite_counter.json | rewrite_daily_limit: 100（配置 L166），超了直接跳过改写 |
    | Contextual 前缀缓存 | rag/contextual_llm.py L19 _CONTEXTUAL_CACHE_PATH | 按 chunk 的 sha256 命中缓存，避免重复调 LLM |
    | 实体向量缓存 | rag/config.yaml L86 注释 | graph/entity_emb_m3.npz，图谱扩展不重复编码 |
  • 缓存设计的关键取舍：rerank 缓存键的输入是「query 加 docs 各段前 50 字」，整体 md5 后落盘 （rag/query.py L893，原文见该行 cache_key = hashlib.md5(...)）——docs 只取每段前 50 字，用碰撞风险换「小改动也能命中」。这是刻意的：缓存键越精确，命中率越低、省的钱越少。
  • 成本核算也有代码：rag/contextual_llm.py L170 estimate_cost() 按「Anthropic 官方公式 + DeepSeek-V3 单价」算 no-cache 与 with-cache 两档，返回 savings_percent——上线前先算，再决定要不要为缓存付 LLM 调用费。
  • 和课件讲法的差异：课件讲 KV cache/前缀缓存（推理侧）；本库的缓存全是应用侧（结果落盘），因为生成走的是云端 API，「前缀缓存省的是你自己的钱」在本库体现为「少调用一次」。
  • 本库暂无：生成调用本身没有缓存（同问题问两次就是两次付费），也没有 token 计量台账。
