二、LangChain / Agent 编排（source_tier S，官方文档，2026）

3
  • 认知更新：Agent = Model + Harness。四层工具：LangChain create_agent（最小、可高度定制的 harness）、Deep Agents create_deep_agent（batteries-included，自带上下文压缩、虚拟文件系统、子 agent 派生）、LangGraph（低层编排，确定性 + agentic 混合工作流）、LangSmith（tracing/调试/评估，设 LANGSMITH_TRACING=true）。
  • 工具即函数：普通 Python 函数直接当工具（tools=[get_weather]），类型签名 + docstring 自动转 JSON Schema——docstring 就是给模型的 API 文档，写清参数含义直接提升调用成功率。
  • 切模型只改一个字符串：init_chat_model 的 provider:model 语法（openai:gpt-5.5 / claude-sonnet-4-6 / ollama:devstral-2 / google_genai:gemini-2.5-flash-lite / bedrock_converse:... / openrouter:...）。
  • RAG 通用六步（与框架无关）：load → split → embed → store → retrieve → augment prompt → generate。
  • 2026 官方推荐范式 Retrieve-offload-delegate：检索到的 chunk 不要全塞主 agent 上下文，而是写到虚拟文件系统，再派子 agent 并行分析，主 agent 只拿摘要——解决长文档撑爆上下文。四种 RAG 模式按语料/延迟/grounding 严格度选：Skills-guided / Rubric-checked grounding / Todo-driven investigation / Retrieve-offload-delegate。
  • Memory：checkpointer 持久化 + thread_id 隔离会话（生产用 langgraph-checkpoint-postgres）；长会话靠自动上下文压缩，不手写裁剪逻辑。
  • 坑：不要把检索全文灌进主上下文（否则 80% token 浪费在搬运）；tracing 先开否则工具循环出问题看不见；老教程 LLMChain / ConversationBufferMemory 已被 create_agent + middleware 取代，学新不学旧。
三、vLLM 生产调优（source_tier A，官方文档 + 实测）3 个重点▾ 点开看本节重点
本节重点
  • 「gpu-memory-utilization」：只对 KV cache 预留，权重恒定全量加载；默认 0.85（0.6.x 起从 0.9 下调）
  • 核心机制：PagedAttention + continuous batching
  • 吞吐与延迟本质冲突——高吞吐调大 「max-num-seqs」 + 开 「--enable-chunked-prefill」；低延迟压小并发、开 prefix caching
3
  • gpu-memory-utilization：只对 KV cache 预留，权重恒定全量加载；默认 0.85（0.6.x 起从 0.9 下调）。KV cache 首次请求就贪婪一次性分配，设 0.95 在 80GB A100 会一次预留 76GB。经验区间：H100(HBM3) 可 0.90+，A100/A6000 0.75–0.80，混合负载（推理+微调同卡）≤0.85。
  • max-model-len：线性决定单条序列 KV 占用，4K vs 32K 差 8 倍；max_model_len × max_num_seqs 不能超预留 KV。
  • tensor-parallel-size：必须是 2 的幂（用 4，用 3 启动失败或极慢）；走 NVLink 收益最大、跨机 PCIe 延迟剧增；TP 增大吞吐提升非线性，需实测拐点。
  • 核心机制：PagedAttention + continuous batching。吞吐与延迟本质冲突——高吞吐调大 max-num-seqs + 开 --enable-chunked-prefill；低延迟压小并发、开 prefix caching。
  • Prefix caching：共享前缀（相同 system prompt / few-shot）逐字节匹配才跳过重复 prefill，对 agent/多轮/RAG 提速最明显；前缀差一个字符就不命中，跨进程/重启缓存失效。
  • OOM 排查顺序：确认是权重还是 KV → 降 utilization（0.95→0.85→0.75）→ 压 max-model-len → 压 max-num-seqs → 量化（AWQ/FP8，70B 可压到 ~40GB）。
  • OpenAI 兼容 API：任何 OpenAI SDK 指 base_url 即用；--served-model-name 给稳定逻辑名（换后端模型不用改客户端）；--enable-metrics 抓 /metrics 监控 num_requests_running/waiting、gpu_cache_usage、TTFT/TPOT。

四、三者共性

3
  1. 上下文即成本：Anthropic 长文档前置、LangChain offload、vLLM prefix caching，本质都是压缩或复用上下文。
  2. 测量先行：Prompt 靠 eval、LangChain 靠 LangSmith tracing、vLLM 靠真实负载压测——先能看见，才能调。
  3. harness 与模型可插拔：工具契约、provider 字符串、OpenAI 兼容接口都在把"模型"做成可替换件，换模型不该动业务代码。

HOW：把三条主线落成可跑的动作（2026-11-03 补强）

1. eval 先行：改 prompt 前的 20 行测量仪器1 个重点▾ 点开看本节重点
本节重点
  • Anthropic"不是每个失败都该用 prompt 解决"的操作含义：先有一个能重复跑的评分脚本，再动 prompt，否则无法区分"改好了"和"这次运气好"
3

Anthropic"不是每个失败都该用 prompt 解决"的操作含义：先有一个能重复跑的评分脚本，再动 prompt，否则无法区分"改好了"和"这次运气好"。

# mini_eval.py —— 最小评测：固定用例 + 自动判定 + 版本对比（本文编写）
import os, json
from openai import OpenAI
client = OpenAI(base_url=os.environ["OPENAI_BASE_URL"], api_key=os.environ["OPENAI_API_KEY"])

CASES = json.load(open("eval_cases.json", encoding="utf-8"))  # [{input, expect_substr}, ...]
def score(system_prompt: str) -> float:
    hit = 0
    for c in CASES:
        out = client.chat.completions.create(
            model=os.environ["MODEL"], temperature=0, max_tokens=512,
            messages=[{"role": "system", "content": system_prompt},
                      {"role": "user", "content": c["input"]}],
        ).choices[0].message.content
        hit += c["expect_substr"] in out
    return hit / len(CASES)
# 用法：旧 prompt 跑一遍记分 → 改 prompt → 再跑；分数不升就不合并。
# 完整版（含注入/越界负例）见 System Prompt怎么写才好.md 的 HOW 节。

2. prefix caching：验证"前缀稳定"是否真命中

3

笔记说"前缀差一个字符就不命中"——这条要自己验证才算数。方法：同一长前缀请求发两次，看第二次的 usage 与服务端指标：

# prefix_cache_check.py —— 两次同前缀请求，对比 TTFT 与 usage（本文编写）
import os, time
from openai import OpenAI
client = OpenAI(base_url=os.environ["OPENAI_BASE_URL"], api_key=os.environ["OPENAI_API_KEY"])
LONG_PREFIX = open("system_prompt.txt", encoding="utf-8").read()  # 建议 ≥1024 token

for i in range(2):
    t0 = time.time()
    resp = client.chat.completions.create(
        model=os.environ["MODEL"], temperature=0, max_tokens=8,
        messages=[{"role": "system", "content": LONG_PREFIX},
                  {"role": "user", "content": "你好"}],
    )
    print(f"第{i+1}次: 耗时 {time.time()-t0:.2f}s, usage={resp.usage}")
# 判读：第二次耗时显著下降 / usage 出现 cached_tokens（OpenAI 兼容字段）= 命中。
# vLLM 侧另看 /metrics 的 prefix cache 命中率；Ollama 看日志的 prompt eval 耗时。
# 反例自查：system 里若拼了时间戳/随机request_id，两次前缀不同，永远打不中。

python -m vllm.entrypoints.openai.api_server \
  --model /path/to/model \
  --served-model-name stable-name \      # 稳定逻辑名，换模型不动客户端
  --gpu-memory-utilization 0.85 \        # A100 老卡压到 0.75-0.80；只影响 KV 预留不省权重

  --enable-prefix-caching                # 共享 system/few-shot 前缀的场景必开
