1.1 从"怎么说"到"装什么"

3

提示词工程管的是"怎么写指令"。当任务从一次性问答变成跑在循环里的 Agent 之后，需要管理的对象就不再只是指令文本，而是每一次推理时，模型上下文窗口里到底装了什么：系统指令、工具定义、外部数据、消息历史，全部算在内。这就是上下文工程（Context Engineering）。

素材里引用的 Anthropic 原话是：上下文工程是"在持续演化的可能信息宇宙中，策选出进入有限上下文窗口的内容的艺术与科学"。

本节重点
  • Harrison Chase 的工程化表述是："构建动态系统，以正确的格式在正确的时机提供正确的信息与工具，使 LLM 能合理地完成任务
3

素材给出了三个互相补充的定义，值得并排放在一起：

来源 定义 侧重
Andrej Karpathy "the delicate art and science of filling the context window with just the right information for the next step"，即在每一步为上下文窗口装填恰好正确信息的精密技艺 目标：恰好正确

1.3 为什么这件事比"把话说清楚"更重要

3

理由是实证的，而不是直觉：模型对上下文的使用并不均匀。素材里有两个最有冲击力的数字。

  • 在 20 篇文档的多文档问答里，当相关信息埋在中部时，GPT-3.5-Turbo 的准确率甚至低于完全不给文档的闭卷基线（56.1%）。也就是说，给了文档反而不如不给（arXiv:2307.03172）。
  • Chroma 对 18 个模型的测试显示：同样的信息，约 300 token 的聚焦提示，在所有模型上全面胜过约 113K token 的全量历史（Context Rot，2025-07）。

因此，上下文必须当作有限且边际收益递减的资源来经营。本文接下来依次讲：它与提示词工程的区别、上下文的四个组成部分、长上下文的五个失效模式、七类应对策略、与 Harness 的关系，以及落到具体工具链（LangChain、vLLM）上的做法。

2.1 四个维度的对比

3
维度 Prompt Engineering Context Engineering
管理对象 指令文本（主要是 system prompt） 进入上下文窗口的全部 token：指令、工具定义、MCP、外部数据、消息历史
工作方式 一次性写好、静态复用 每轮推理都要重新策展，迭代式
失败模式 措辞歧义、指令被忽略 上下文腐烂（context rot）、注意力稀释、成本爆炸
类比 考卷上写一个好问题 为决策者准备整套简报包

这张表有两个值得展开的点。

第一，工作方式的差异。提示词是"写一次，复用很多次"；上下文是"每一轮都要重新决定装什么"。前者像出一道题，后者像每天为决策者准备当天的简报。

第二，失败模式的差异。提示词工程的失败通常是措辞歧义，或指令被模型忽略，改文字就能修；上下文工程的失败往往是系统性的：窗口里东西太多、太杂、互相矛盾，模型的注意力被稀释，成本也一同失控，这不是改一句话能解决的。

三、上下文的四个组成部分2 个重点▾ 点开看本章重点
本章重点
  • LangChain 官方博客把需要管理的上下文归为四类，与 Anthropic 的解剖一致
  • 素材把四类概括成一句话：指令和工具定义是常驻成本，要最小化；知识和历史是动态负载，要按需化
2

LangChain 官方博客把需要管理的上下文归为四类，与 Anthropic 的解剖一致。

组成部分 内容 管理策略
指令（Instructions） system prompt、few-shot 示例、工具描述 写在"正确高度"（right altitude）：足够具体以引导行为，又不硬编码脆弱逻辑；用 XML 标签或 Markdown 标题分节；示例要多样且典型，不要堆边界 case
知识（Knowledge） 检索到的文档、外部数据、注入的事实 不预塞，改用 just-in-time 检索（RAG/搜索），让 Agent 需要时自己取；检索结果只给轻引用
工具定义（Tools） 工具 schema、MCP 服务描述 工具要自包含、容错、最小且不重叠，臃肿的工具集会制造模糊的决策点
历史（History） 消息历史、工具调用结果、Agent 中间产物 最大的失控源，需要压缩（compaction）、剔除（offload）、摘要治理

素材把四类概括成一句话：指令和工具定义是常驻成本，要最小化；知识和历史是动态负载，要按需化。

3.1 指令：正确高度

3

"正确高度"是 Anthropic 的一个提法。指令写得太低（硬编码一堆 if-else 式的规则）会脆弱，换一个场景就失效；写得太高（只讲大原则）又给不了具体引导。适中的做法是：给足够具体的行为指引，同时不替模型写死每一步。这与提示词工程里"给为什么，而不是禁止"的黄金法则相通。

3.2 知识：从预塞到按需3 个重点▾ 点开看本节重点
本节重点
  • 传统做法是把可能用到的资料一次性塞进 prompt
  • 上下文工程的做法是 just-in-time 检索：Agent 在需要时自己去取，并且检索结果只回传轻引用，而不是全文
  • 这样做的依据就是前文 Chroma 的数字：聚焦注入严格优于全量塞入
3

传统做法是把可能用到的资料一次性塞进 prompt。上下文工程的做法是 just-in-time 检索：Agent 在需要时自己去取，并且检索结果只回传轻引用，而不是全文。这样做的依据就是前文 Chroma 的数字：聚焦注入严格优于全量塞入。

3.3 工具定义：最小且不重叠

3

工具定义是常驻成本，每一轮都在占窗口。工具集臃肿还有第二个副作用：多个工具功能重叠，会让模型在选择时犹豫、选错，也就是"模糊的决策点"。所以工具设计原则是自包含、容错、最小、不重叠。

3.4 历史：最大的失控源3 个重点▾ 点开看本节重点
本节重点
  • 历史包括消息记录、工具调用结果、Agent 的中间产物
  • 其中工具调用结果是"最肥的上下文流"：读一个大文件、拉一次 API 数据，就可能带来成千上万 token
  • 历史的治理手段是压缩、剔除和摘要，下文第五章详述
3

2

4.1 失效一：Lost in the middle（位置偏置）3 个重点▾ 点开看本节重点
本节重点
  • 性能呈 U 形曲线：相关信息位于开头或结尾时效果最好，埋在中部时显著变差
  • 20 篇文档的场景下，GPT-3.5-Turbo 的中部准确率低于闭卷基线 56.1%，给了文档反而不如不给
  • 出处是 arXiv:2307.03172（TACL 2023）
3

性能呈 U 形曲线：相关信息位于开头或结尾时效果最好，埋在中部时显著变差。20 篇文档的场景下，GPT-3.5-Turbo 的中部准确率低于闭卷基线 56.1%，给了文档反而不如不给。专门为长上下文优化的模型同样会中招。出处是 arXiv:2307.03172（TACL 2023）。

4.2 失效二：Context rot（整体衰减）

3

Chroma 测了 18 个模型，包括 GPT-4.1、Claude 4、Gemini 2.5、Qwen3。任务难度不变、只加长输入，准确率就持续下降。在 LongMemEval 上，约 300 token 的聚焦提示，在所有模型上都胜过约 113K token 的全量历史，多出来的 11 万 token 是净负资产。

4.3 失效三：注意力稀释（attention budget）3 个重点▾ 点开看本节重点
本节重点
  • Transformer 让每个 token 两两交互，形成 n² 的关系，上下文越长，关系捕捉越稀薄
  • Anthropic 称之为有限的"注意力预算"
  • 此外，训练分布中短序列远多于长序列，模型对超长依赖缺乏专门参数
3

Transformer 让每个 token 两两交互，形成 n² 的关系，上下文越长，关系捕捉越稀薄。Anthropic 称之为有限的"注意力预算"。此外，训练分布中短序列远多于长序列，模型对超长依赖缺乏专门参数。

4.4 失效四：干扰（distractor 与 poisoning）

3

Drew Breunig 把干扰分为四种：

  • Poisoning：幻觉进入上下文，被后续推理当作真实信息；
  • Distraction：上下文淹没了训练得到的知识；
  • Confusion：多余的上下文影响回答；
  • Clash：上下文内部互相矛盾。

Chroma 的实测给出了数字：一个干扰项就会让结果低于干净基线，四个更差。NoLiMa 基准（非字面匹配）下，32K 处 12 个模型中有 10 个跌破短上下文基线的 50%，GPT-4o 从 99.3% 掉到 69.7%（arXiv:2502.05167，ICML 2025）。

4.5 失效五：成本2 个重点▾ 点开看本节重点
本节重点
  • 每个 token 都计入计费、延迟和 KV cache
  • LangChain 官方的提醒是：不要把检索全文灌进主上下文，否则 80% 的 token 浪费在搬运上
3

上下文即成本。每个 token 都计入计费、延迟和 KV cache。LangChain 官方的提醒是：不要把检索全文灌进主上下文，否则 80% 的 token 浪费在搬运上。

4.6 关键认知：NIAH 会骗人

3

NIAH（大海捞针）基准只测字面匹配式的检索，各模型近乎满分，会让人误以为长上下文问题已经解决。换成需要语义关联的 NoLiMa，性能立刻跌落。因此评估长上下文能力时，不能只看 NIAH 的成绩。

五、七类实用策略

2

LangChain 把业界做法归为 write / select / compress / isolate 四类，Anthropic 又做了补充，素材整理成七行表格。

5.1 检索注入（select，just-in-time）2 个重点▾ 点开看本节重点
本节重点
  • 不预塞知识，让 Agent 用 RAG 或搜索按需获取
  • Chroma 的 300 对 113K token 数据证明：聚焦注入严格优于全量塞入
3

不预塞知识，让 Agent 用 RAG 或搜索按需获取。适用于知识库大且动态的场景。Chroma 的 300 对 113K token 数据证明：聚焦注入严格优于全量塞入。

5.2 剔除与卸载（offload）

3

大结果不进窗口。LangChain Deep Agents SDK 的具体阈值是：超过 20,000 token 的工具结果立即落盘，只在上下文里留前 10 行预览加文件路径；超长的用户消息（阈值 50,000）同样处理。Anthropic 也把"清理已消费的工具结果"列为最安全的轻量压缩。适用于工具输出大的场景，比如读大文件、拉 API 数据。

5.3 压缩与摘要（compaction，compress）2 个重点▾ 点开看本节重点
本节重点
  • 上下文用到窗口的 85% 时，用另一次 LLM 调用把旧消息压成结构化摘要，摘要包含会话意图、已产出内容和下一步，原文落盘可回查
  • 适用于长会话、长程任务，摘要后 Agent 可以通过读文件恢复细节
3

上下文用到窗口的 85% 时，用另一次 LLM 调用把旧消息压成结构化摘要，摘要包含会话意图、已产出内容和下一步，原文落盘可回查。适用于长会话、长程任务，摘要后 Agent 可以通过读文件恢复细节。

5.4 分层（渐进披露）

3

常驻的只有一行描述，正文按需加载。这就是 Skills 与 CLAUDE.md 的"薄入口加专业文档"模式，也是 Anthropic 系统提示分层（例如 ## Tool guidance 等分节）的思路。适用于常驻指令太多、互相干扰的情况，对应本库 Claude Code 条目里的"给地图不给说明书"。

5.5 结构化笔记（write，note-taking）2 个重点▾ 点开看本节重点
本节重点
  • Agent 定期把目标、进度、关键发现写到上下文外的文件，例如 NOTES.md 或 todo list，需要时再读回
  • Anthropic 用 Claude 玩宝可梦做演示：跨越数千步仍靠自己的笔记保持策略连贯
3

Agent 定期把目标、进度、关键发现写到上下文外的文件，例如 NOTES.md 或 todo list，需要时再读回。适用于多步骤任务。Anthropic 用 Claude 玩宝可梦做演示：跨越数千步仍靠自己的笔记保持策略连贯。

5.6 隔离（isolate，子 Agent）

3

噪音大的活派给一个干净上下文的子 Agent，主 Agent 只接收浓缩结论。Anthropic 给出的数据是：子 Agent 可能消耗数万 token，但只回传 1,000 到 2,000 token 的摘要。适用于可并行的探索型工作，比如研究和搜索，对应 Harness"编排"组件里的子智能体。

5.7 重排序（re-rank）3 个重点▾ 点开看本节重点
本节重点
  • 把最相关的检索块放在上下文开头，次相关的放结尾，其余夹在中间
  • 适用于 RAG 多路召回，直接对冲 lost-in-the-middle 的 U 形曲线
  • 这是 arXiv:2307.03172 的工程推论
3

把最相关的检索块放在上下文开头，次相关的放结尾，其余夹在中间。适用于 RAG 多路召回，直接对冲 lost-in-the-middle 的 U 形曲线。这是 arXiv:2307.03172 的工程推论。

5.8 如何选择

3

Anthropic 给出的选择原则很简洁：

  • 压缩适合需要连续对话流的任务；
  • 笔记适合有清晰里程碑的迭代开发；
  • 多 Agent 适合并行探索有收益的复杂研究。

6.1 长文档（20k 以上）的写法

3

Anthropic 官方指南给出了三条：长文档放在 prompt 顶部；每篇文档用 <document index="n"> 包裹，里面包含 <source> 与 <document_content>；采用 ground in quotes，要求先引用原文再作答，用来抑制幻觉。这三条正好对应前面的失效分析：放顶部与引用，是在对冲位置偏置和干扰。

6.2 多轮对话的截断与摘要3 个重点▾ 点开看本节重点
本节重点

8.5 vLLM：上下文成本在推理侧的体现

3

上下文即成本，在推理引擎里体现得最直接。

max-model-len：线性决定单条序列的 KV 占用，4K 与 32K 相差 8 倍；max_model_len × max_num_seqs 不能超过预留的 KV。这就是"窗口开得越大越贵"的硬约束。

gpu-memory-utilization：只对 KV cache 预留，权重恒定全量加载；默认 0.85（0.6.x 起从 0.9 下调）。KV cache 在首次请求时贪婪地一次性分配，设 0.95 时在 80GB A100 上会一次预留 76GB。素材特别指出一个认知纠正：调低它并不省权重显存。经验区间是：H100（HBM3）可 0.90 以上，A100/A6000 为 0.75 到 0.80，混合负载（推理加微调同卡）不超过 0.85。

Prefix caching：共享前缀（相同的 system prompt、few-shot）逐字节匹配时可以跳过重复 prefill，对 agent、多轮、RAG 的提速最明显。但前缀差一个字符就不命中，跨进程或重启缓存也会失效。这给提示词写作提了一个实际要求：把稳定不变的内容放在前面，把会变化的内容放在后面，并且不要在前缀里夹带时间戳之类每次都变的字符。这是上下文工程与推理优化的交汇点。

OOM 排查顺序：先确认是权重还是 KV；再降 utilization（0.95 → 0.85 → 0.75）；再压 max-model-len；再压 max-num-seqs；最后量化（AWQ/FP8，70B 可压到约 40GB）。

九、案例：一次长任务中的上下文治理

2

下面用素材里的元素，串起一个完整的情境，说明各策略如何配合。注意这不是新增内容，而是把已有的策略按时间顺序摆开。

起点：Agent 接到一个需要阅读大量资料的任务。系统指令走薄入口，常驻的只有一行描述，专业文档按需加载（分层）。工具集保持最小且不重叠。

检索阶段：Agent 不预塞资料，而是用 RAG 按需检索（select）。检索回来的 chunk 先写到虚拟文件系统（offload），再派子 Agent 并行分析（isolate）。子 Agent 可能消耗数万 token，但只回传 1,000 到 2,000 token 的摘要。多路召回的结果做重排序：最相关的放开头，次相关放结尾。

推进阶段：Agent 把目标、进度、关键发现写进 NOTES.md（write）。某次工具调用返回超过 20,000 token 的结果，立即落盘，上下文里只留前 10 行预览和路径。

长会话阶段：上下文用到窗口的 85% 时，触发 compaction：用另一次 LLM 调用把旧消息压成结构化摘要，包含会话意图、已产出内容和下一步，原文落盘可回查。

推理侧：system prompt 与 few-shot 示例作为稳定前缀放在最前，prefix caching 命中，重复 prefill 被跳过。

全程：LangSmith tracing 始终开着，出现问题时能看见每一轮窗口里装了什么。

这个情境把七类策略、LangChain 的 Deep Agents 能力和 vLLM 的 prefix caching 放进了同一条时间线，也说明为什么素材说"好 Harness 就是上下文工程的交付机制"。

十、常见误区3 个重点▾ 点开看本章重点
本章重点
  • Chroma 的数据表明，多出来的 11 万 token 可能是净负资产
  • 80% token 浪费在搬运
  • NIAH 只测字面匹配，NoLiMa 才能暴露语义关联场景下的跌落
2

结合素材，可以归纳出几个典型误区：

  1. 以为窗口越大越好。Chroma 的数据表明，多出来的 11 万 token 可能是净负资产。
  2. 只看 NIAH 的成绩。NIAH 只测字面匹配，NoLiMa 才能暴露语义关联场景下的跌落。
  3. 把检索全文灌进主上下文。80% token 浪费在搬运。
  4. 常驻指令越写越多。常驻成本每轮都要付，且互相干扰，应分层、薄入口。
  5. 工具越多越好。重叠的工具制造模糊决策点。
  6. 调低 gpu-memory-utilization 想省权重显存。它只管 KV cache。
  7. 前缀里放变化的字符。prefix caching 逐字节匹配，差一个字符就不命中。
  8. 不开 tracing。看不见窗口里装了什么，就无法调优。

十一、小结

2

上下文工程是提示词工程的自然升级，核心问题从"怎么写指令"变成"每一轮窗口里该装什么"。三条判断可以记住：Karpathy 的"恰好正确的信息"、Anthropic 的"最小高信号 token 集合"、LangChain 的 write / select / compress / isolate 四类动作。

支撑这套方法的是一组不容忽视的实证：位置偏置让中部信息的准确率低于闭卷基线；18 个模型上 300 token 的聚焦提示胜过 113K token 的全量历史；NoLiMa 下 GPT-4o 从 99.3% 掉到 69.7%。这些数字共同说明：上下文是有限且边际收益递减的资源。

落地上，指令和工具定义是常驻成本要最小化，知识和历史是动态负载要按需化。具体手段有七类：检索注入、卸载（20,000 token 阈值）、压缩（85% 阈值）、分层披露、结构化笔记、子 Agent 隔离（1,000 到 2,000 token 回传）、重排序。它们是 Harness 五组件的内容，也是操作系统式"内存管理器"的职责。

最后别忘了素材反复强调的方法论：先测量，再调优。无论是 Prompt 的 eval、LangChain 的 tracing，还是 vLLM 的真实负载压测，都是同一个原则的不同体现。

12.1 先能测量：一个够用的 token 估算器

3

没有计量就没有"85% 水位"和"20K 阈值"。离线场景用字符近似（中文约 1 token/字、英文约 1 token/4 字符，是粗估不是精确值），在线场景直接用响应里的 usage.prompt_tokens 校准：

def est_tokens(messages) -> int:
    """粗估：中文按 1 token/字，其余按 1 token/4 字符；用于水位判断，不用于对账。"""
    total = 0
    for m in messages:
        text = m["content"]
        cjk = sum('一' <= ch <= '鿿' for ch in text)
        total += cjk + (len(text) - cjk) // 4 + 4   # +4 = 每条消息的结构开销粗估
    return total
12.2 offload：大结果落盘 + 可操作指针2 个重点▾ 点开看本节重点
本节重点
  • 关键不是"截断"而是指针可操作：Agent 后面能按路径读回细节，压缩才是无损工作流
  • 哈希命名顺带解决同一结果被反复返回的去重
3 
import hashlib, pathlib
STORE = pathlib.Path("./context_store"); STORE.mkdir(exist_ok=True)

def offload(text: str, max_chars: int = 2000) -> str:
    if len(text) <= max_chars:
        return text
    path = STORE / (hashlib.sha256(text.encode()).hexdigest()[:16] + ".txt")
    path.write_text(text, encoding="utf-8")
    preview = "\n".join(text.splitlines()[:10])
    return f"{preview}\n...[已截断] 全文 {len(text)} 字符，用读文件工具读取：{path}"

关键不是"截断"而是指针可操作：Agent 后面能按路径读回细节，压缩才是无损工作流。哈希命名顺带解决同一结果被反复返回的去重。

12.3 compress + re-rank：水位触发与免费准确率

3
  • compress：est_tokens(messages) > budget × 0.85 时，把 system 与最近 3 轮之外的旧消息交给便宜模型压成"会话意图 / 已产出 / 下一步"三段摘要，原文落盘（完整函数见 最佳答案篇 模板 5）。验收方法：撤掉原文只留摘要，让 Agent 继续下一步，观察是否重复劳动。
  • re-rank：检索块按相关度降序后 chunks[::2] + chunks[1::2][::-1]，最相关放开头、次相关放结尾，对冲 lost-in-the-middle 的 U 形曲线（工程推论，非论文原算法）。

本库真实落地（源码核对，2026-11-04）

  • 本库的上下文是「双层切分 + 分角色取用」，三个把手各管一段（本次读源码）：
    | 把手 | 位置 | 管什么 |
    |---|---|---|
    | 父块 | rag/ingest.py L613 split_parent_chunks()（800 字符，PARENT_CHUNK_SIZE） | 给生成侧完整语义 |
    | 子块 + 标题 | rag/query.py L1926 retrieve_node() 里 _rerank_text = f"{hp}\n{h['text']}" | 只给 rerank 用，缩短输入 |
    | 父块回灌 | rag/query.py L2689 注释：explain 上下文用 parent_text, 不用子块 _rerank_text | 给生成侧 |
  • 为什么这样切：reranker 吃的是「子块 + 标题」（本次熔断前本应输入 30 条），生成吃的是「父块」——同一个 chunk 在链路上有两个视图。retrieve_node 的注释写死了这条纪律：生成侧不再共享此字段 …… 否则只改这里会把作答上下文也退化成子块(审查 claude_rerank_review.log 致命点A5)。
    这是上下文工程里最实用的一条：上下文不是一份文档，而是按消费者裁剪的多个视图。
  • 上下文污染的防护：①gate_node 在拼上下文之前做质量门禁，不达标直接拒答（不给模型「凑合用的片段」）；②jev_filter_chunks 逐条剔除跑题 chunk；③_validate_citations 在生成后把「引用了不存在的来源」的句子标⚠️——入场、场内、出场三道都管。
  • 和课件讲法的差异：课件讲上下文窗口、压缩、摘要；本库没有做对话历史压缩（无长会话记忆），上下文工程全部服务于「单轮 RAG」——窗口利用率靠切分粒度，不靠摘要。
  • 本库暂无：没有对话记忆/多轮上下文（rag/serve.py 只取最后一条 user 消息），也没有上下文预算计数器（没有「超了多少 token 就裁剪」的机制）。
