第2章 MCP的工作原理

3
  • 基线原文回归：MCP 采用主机—客户端—服务器三层核心架构，主机负责用户交互与权限裁决，客户端负责协议通信，服务器封装具体能力。；三大核心组件职责分明——资源是只读的上下文数据（“万物皆资源”），工具是可能改变外部状态的动态操作，提示模板用于标准化任务输入以保障输出一致性。；传输层支持两种常见方式，适配本地进程与远程服务两类部署形态；安全机制依托 OAuth 流程与令牌机制，避免暴露用户名密码等敏感信息。；主机可对高风险操作实施人工确认拦截（如删除操作弹窗授权），并在工具描述中标注只读/写入属性以辅助风险判断。；通过与 API、Agent、Function Calling、A2A 的逐项对比，MCP 的差异化优势在于协议标准化与生态复用性，而非替代上述任一方案。
  • 核心观点1：MCP 采用主机—客户端—服务器三层架构。主机承载用户交互、模型调用和策略治理；客户端负责与某个服务器建立协议连接；服务器把外部系统能力包装成 MCP 可发现、可调用的对象。
  • 核心观点2：资源、工具、提示模板承担不同职责。资源通常是给模型读取的上下文，工具是可以查询或改变外部状态的动作，提示模板则把常见任务的输入结构固定下来，减少团队成员各写一套提示造成的输出漂移。
  • 核心观点3：资源可以是文档全文、数据库记录、API 返回值、截图、图片或日志；工具则应明确参数、返回格式和副作用。设计时要区分只读查询与写入操作，不能只凭工具名称判断风险。
  • 核心观点4：传输层适配本地进程与远程服务两类形态，本地常用于桌面客户端和开发调试，远程更适合共享服务与集中治理。部署选择需要同时考虑延迟、隔离、身份认证、日志和故障恢复。；核心观点5：主机可以在高风险调用前插入人工确认，并把权限裁决放在模型之外。MCP 与 API、Agent、Function Calling、A2A 并非互相替代：API是服务接口，Function Calling是模型调用机制，Agent是任务执行系统，MCP是连接能力的协议层。

    与资源不同，工具可能会改变外部系统的状态，或者与外界发生交互，所以其操作是动态的。
    当AI应用尝试调用一个高风险操作时，主机完全可以弹出一个确认对话框……只有在得到用户同意后才允许AI应用调用该高风险操作。

第4章 开发与代码执行

3
  • 核心观点1：Semantic Kernel 可以把 MCP 工具编排进既有 AI 应用管线，使工具能力不再绑定某一个聊天界面。编排时要明确工具何时可用、谁负责重试、如何记录调用链以及何时交给人工。
  • 核心观点2：MCP Run Python 借助 Pyodide 在受限环境中执行 Python，权限开关分别影响网络访问和 node_modules 读写。能力越强，沙箱边界越重要，不能把任意代码执行直接等同于安全的自动化。
  • 核心观点3：E2B 把代码运行放入云端沙箱，适合需要隔离、可回收环境的任务；JetBrainsMCP 与 FileScopeMCP 则把 IDE 和文件系统能力工具化，强调开发环境本身也可以成为工具源。
  • 核心观点4：代码执行类工具应采用最小权限、资源配额、超时、工作目录限制和输出截断，并把执行结果与模型生成的解释分开记录，避免把模型的描述当成真实执行证据。

    -N-R=node_modules和-W=node_modules表示分别打开网络权限与对node_modules的读写权限，以便Pyodide下载并缓存Python标准库与第三方包。

第8章 数据库交互

3
  • 基线原文回归：数据库类 MCP 的核心价值是终结“在 Prompt 里手动拼接 SQL”的原始做法，让“数据库+大模型”成为可落地的智能体方案。
  • 核心观点1：Aiven、ClickHouse、Chroma、Confluent 等 MCP 覆盖关系型、列式、向量和流式数据源，说明数据库工具化的重点不是数据库类型，而是把连接、查询、结果和权限统一纳入模型可理解的接口。
  • 核心观点2：genai-toolbox 提供 LangChain 与 SDK 两种 Python 客户端，可把数据库工具注入 VertexAI、Gemini 或 LangGraph 节点。连接管理、安全策略和观测由工具层承担，业务编排仍由应用控制。
  • 核心观点3：数据库 MCP 应优先提供带约束的领域查询，而不是默认开放任意 SQL。只读查询、分页、超时、行数上限和敏感字段脱敏能降低模型生成错误查询造成的风险。
  • 核心观点4：向量库场景要区分文档摄取、相似检索、过滤条件和答案生成；流式数据库则要处理时间窗口、消费位点和重复消息。工具描述越具体，模型越不容易把不同数据源的语义混在一起。

    借助genai-toolbox，我们可以在几分钟内把“数据库+大模型”变成真正可落地的智能体方案……彻底告别“用Python在Prompt里手动拼接SQL语句”的原始做法。

第10章 云平台服务集成

3
  • 基线原文回归：云平台类 MCP 的共性是凭证先行——AWS 需配置 ACCESS_KEY_ID / SECRET_ACCESS_KEY 与 REGION，Cloudflare 需生成 Edit Cloudflare Workers 自定义 Token 并写入环境变量。
  • 核心观点1：aws-kb-retrieval-server 封装 Amazon Bedrock Knowledge Bases，支持列出知识库、列出数据源和自然语言检索，内部通过 Bedrock Agent Runtime 调用 Retrieve API，将跨库语义检索与轻量重排结果返回给模型。
  • 核心观点2：mcp-server-cloudflare 把 Cloudflare API、Workers AI 和自定义 Workers 方法封装为工具，例如 worker_list、worker_get_worker、worker_logs_by_worker_name，并通过 OAuth 或 API Token 完成授权。
  • 核心观点3：k8m 与 kubernetes-mcp-server 暴露 pods_list、pods_log、pods_exec、resources_create_or_update、events_list、namespaces_list 等工具，覆盖日常运维，但执行变更前要核对集群、命名空间、资源版本和回滚方案。
  • 核心观点4：云平台 MCP 的共性是凭证先行。凭证应由环境变量或受控配置注入，工具只获得完成任务所需的范围；任何示例中的密钥字段都只能作为变量名，不能把真实值写入提示或日志。；核心观点5：云边运维适合采用“自然语言查询—生成计划—人工确认—执行—回读状态”的闭环。先读后写、先小范围后全量，比让模型直接执行连续变更更稳健。；mcp-server-cloudflare：把Cloudflare API、Workers AI与自定义Workers方法封装成一组MCP工具（如worker_list、worker_get_worker、worker_logs_by_worker_name），可通过OAuth或API Token完成授权，在1分钟内接入Claude Desktop或其他客户端，让大模型能够以自然语言管理DNS、KV、Vectorize、D1或触发任意Workers逻辑，真正实现“对话式云边运维”。

    aws-kb-retrieval-server：封装了Amazon Bedrock Knowledge Bases的检索能力，支持列出知识库、列出数据源及自然语言检索三大接口，内部通过Bedrock Agent Runtime调用Retrieve API，将跨库语义检索与轻量重排结果直接返回给大模型，实现针对企业文档的“有问即答”。
    服务器暴露的主要工具包括pods_list、pods_log、pods_exec、resources_create_or_update、events_list、namespaces_list等，覆盖大部分日常运维场景。
