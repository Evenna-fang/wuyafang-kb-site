这份文档是FDE客户交付的即拿即用模板库，入库于2026年9月30日，来源为VanGong1999/FDE开源项目的"08-工具箱与清单"系列（发现访谈提纲/POC验收表/生产Go-Live清单/现场勘察与范围文档）+《POC到生产》+ OpenFDE《什么是FDE》4C框架 + Palantir AI FDE自验证清单。文档定位是"客户交付即拿即用模板"——方案书/技术评估清单/POC→生产checklist/交付验收模板，覆盖从Week 1写码前的现场勘察到交付后的验收会全流程。

文档的核心价值在于把FDE方法论拆解成了可填空的模板，而非抽象原则。每个模板都有"何时用"和"完成定义"——例如现场勘察Site Survey在Week 1写码前用，完成定义是"客户技术Owner已阅、开放问题有Owner、Quick Win可演示"；技术范围PRD在进Pilot前当"合同"用，完成定义是"Eval线与Out of Scope书面、双方签字或邮件确认"。这种"模板+完成定义"的设计让FDE新人也能按节奏推进项目，不会在模糊的方法论里迷失。高管周报WES在每周/双周对赞助人，完成定义是"赞助人3分钟读完并知道要不要动作"——这个完成定义看似简单，但实际上很多FDE的周报做不到这一点（写了一大篇赞助人还是不知道要不要动作）。

文档节奏建议非常具体：Week 1 = Site Survey + 问题陈述；Week 2-3 = 技术范围PRD + POC验收表；持续 = 周报/WES；门禁 = POC验收/Go-Live。这个节奏来自VanGong1999/FDE《现场勘察与范围文档》原文，经过实战验证。配套的"常见扯皮与应答"表格更是把客户常见的模糊说法（"领导看了Demo很满意""环境下周一定好""安全太慢"）对应到了具体的门禁卡点和应答话术，非常实战——不是教FDE"讲道理"，而是教FDE"把模糊对话拉回到书面流程上"。

方案书/技术范围PRD模板与Site Survey3 个重点▾ 点开看本节重点
本节重点
  • 原文强调"没有Out of Scope的PRD等于邀请范围蔓延"——这是FDE项目中最常见的陷阱，客户总说"顺便也做一下XX"，如果PRD没有明确的Out of Scope，这些"顺便"就会变成范围蔓延
  • 特别注意"非目标"部分——明确说了"不做自动改写合同和商务谈判建议"，这防止了客户后期说"你们说能做AI合同审查，怎么不能自动改写
  • Site Survey的Week 2 Quick Win原则：Week 2必须能演示一个小胜利——这不是为了炫技，而是为了建立客户信任
3

  • PRD模板七要素：①用户与动作（谁、在什么场景、用系统完成什么动作）②问题陈述（Discover确认版：【用户】在【场景】下需要【结果】，今天通过【现状】完成，主要问题是【痛点】，成功时【指标】从A到B，约束包括【数据/安全/时间/组织】，本次非目标是【】）③Eval通过线（检索/延迟/扎根性等阈值）④分阶段（MVP→Scale每阶段出口条件）⑤Out of Scope（必填）⑥成本与延迟预算⑦风险登记Top3（含负责人）。原文强调"没有Out of Scope的PRD等于邀请范围蔓延"——这是FDE项目中最常见的陷阱，客户总说"顺便也做一下XX"，如果PRD没有明确的Out of Scope，这些"顺便"就会变成范围蔓延。

  • 问题陈述示例（合同初审场景）：【一线法务】在【供应商合同初审】下，需要【标出与模板不符的高风险条款】，今天通过【人工通读】完成，主要问题是【积压与漏标】，成功时【初审人均时长】从45min到20min且【高风险漏检】不高于基线，约束包括【合同不出域、需审计】，本次非目标是【自动改写合同、商务谈判建议】。这个示例展示了好的问题陈述长什么样——每个括号都有具体内容，不是空话。特别注意"非目标"部分——明确说了"不做自动改写合同和商务谈判建议"，这防止了客户后期说"你们说能做AI合同审查，怎么不能自动改写？"

  • Site Survey检查项：①权威源（System of Record）是什么②数据质量问题有哪些③连通性/身份/权限约束（SSO、文档ACL、网络路径）④Delta（产品缺口）与拟议胶水⑤Quick Win（Week 2可演示）⑥开放问题+Owner。好勘察的标志（原文）：有权威源与质量问题不是"数据很多"；有连通与身份约束不是"应该能连"；有产品缺口与拟议胶水；有Week 2可验证的小胜利。Site Survey的实战意义：写码前把"脏现实"写死——客户说"数据很多"不等于"数据能用"，客户说"应该能连"不等于"真能连"。

  • Site Survey的Week 2 Quick Win原则：Week 2必须能演示一个小胜利——这不是为了炫技，而是为了建立客户信任。如果Week 1只做Site Survey，Week 2还在分析数据，客户会觉得"花了两周什么都没看到"。Quick Win的作用是让客户在早期就看到AI的价值，愿意继续投入。Quick Win的选择标准是：小（1-2天能做完）、真（基于真实数据）、可演示（客户能看到结果）。

技术评估清单（模型在客户约束下能否交付）

3

  • 数据与权限Day 0必问五题（VanGong1999/FDE《POC到生产》§4原文）：①数据能否出域？需不需要私有化/VPC？②身份从哪来（SSO）？授权如何映射到文档级？③提示词与日志里是否落PII？保留多久？④工具调用是否可能越权写系统？⑤谁有权看审计记录？红线（原文）：不要用"管理员万能账号"撑过Pilot——那会让门禁2永远过不去。这五题是FDE项目的"生死题"——任何一题答不清，项目后期都会踩坑。特别注意第⑤题"谁有权看审计记录"——很多FDE项目做到最后才发现没人能看审计日志，出了安全问题无法追溯。

  • 可行性与Eval评估矩阵：任务是否有标准答案/可判据（有专家一致率或规则可判→通过；没有→降级为"助手建议"而非自动决策）；golden set可建（能拿到20-50条真实样本分层→通过；拿不到→先做数据/标注战役不承诺指标）；模型能力vs要求（要求99%而模型稳定85%=不可硬上→缩范围为HITL助手）；成本预算（单次推理成本×预估量级可接受→通过；不可接受→模型分级/缓存/路由）。这个矩阵的核心思想是"诚实评估"——如果模型能力不够（99%要求 vs 85%能力），不要硬上，而是降级为HITL助手（AI建议+人工确认）。

  • 组织与变更评估矩阵：业务owner（有人用业务指标背责→通过；只有IT牵头人→红旗）；一线接触（能旁看真实工作流→通过；只有管理层转述→红旗）；否决方（安全/法务已知情→通过；历史上否决过类似项目但未拉齐→红旗）；变更窗口（培训与发布窗口明确→通过；"先上再说"→红旗）。这四项评估确保项目不是"AI能做"就行，还要"组织能接得住"——没有业务owner的项目，上线后没人推广；没有一线接触的项目，做出来的东西不符合真实使用习惯。

本节重点

  • 特别注意"哪怕20-50条"——原文明确说不需要完美的评测集，但至少要有20-50条真实样本，证明"非随机水平"（即不是瞎猜）
  • 门禁1的实战设计：补充门禁条件（《POC到生产》原文）：关键路径在目标网络与数据驻留约束下可运行；权限模型草图过安全初审；初步eval（哪怕20-50条）显示非随机水平；书面试点范围
3

  • 门禁1：PoC→PILOT POC验收表8项：P1问题陈述确认（赞助人邮件/纪要确认）；P2目标环境路径（非仅笔记本，网络/驻留可行）；P3安全初审（数据流与权限草图已阅）；P4初步Eval（冻结集上达到约定线或诚实未达线）；P5试点范围（用户×内容×时间盒书面化）；P6风险与缓解（Top3有负责人）；P7 Owner（客户侧对接人指名）；P8 Go/No-Go（书面决策）。未通过则不得宣称"可推广到全员/生产"。8项证据齐备才放行，任何一项缺失都不进Pilot——这是防止"Demo绑架"的核心机制。

  • 门禁1的实战设计：补充门禁条件（《POC到生产》原文）：关键路径在目标网络与数据驻留约束下可运行；权限模型草图过安全初审；初步eval（哪怕20-50条）显示非随机水平；书面试点范围。这些条件确保Pilot不是"换个大环境继续试"，而是"真的在接近生产的环境验证"。特别注意"哪怕20-50条"——原文明确说不需要完美的评测集，但至少要有20-50条真实样本，证明"非随机水平"（即不是瞎猜）。

  • 试点切片一页纸模板：用户群体/场景/内容范围/时间盒/成功指标（冻结）/非目标/门禁1证据链接/门禁2证据链接/客户Owner/若失败：停/改/缩的默认动作。试点设计原则（原文）：窄、真、可测、可叙事——用户一个团队10-30人（差：全公司）；内容一个产品线文档；自动化先助手/影子模式；时间4周时间盒；指标采纳率/时长/差错（差："大家觉得好"）。这个一页纸模板的价值在于：所有关键信息在一页纸上，客户和FDE都能快速review。

  • 门禁2：Pilot→Production生产Go-Live清单：可靠性与运营（降级与回滚演练过记下时间与结果、看板与告警指向真实值班人、Runbook已交客户并可打开）；安全（SSO/ACL强制验证通过含跨用户用例、密钥与PII策略就绪、审计日志可查）；质量（Eval回归通过线附报告链接、已知限制对用户可见）；采用（培训完成材料可查、支持渠道与升级路径明确、客户侧Owner指名）；决策（Go/有条件Go/No-Go书面记录）。5个维度的检查项确保生产环境不是"凑合能用"，而是"真正可运营"。

  • "有条件Go"格式与时间窗：条件：完成X；负责人：Y；最晚：日期；到期未完成：自动降级为No-Go/维持Pilot。原文金句："没有到期日的条件=永远的灰色生产"。Go-Live当天与之后72小时（原文）：当天变更窗口内发布、验证主路径、公告边界；24h看错误率/成本/负反馈热修或回滚；72h短复盘"是否误判门禁"、补Runbook。72小时复盘的价值在于：即使门禁全过了，上线后72小时内的真实使用数据会告诉你门禁是否误判了——有些问题只有真实流量才能暴露。

  • 交接包最少清单：架构图与数据流；环境与密钥归属；Runbook/故障演练记录；Eval集与如何回归；已知限制与路线图建议；值班与升级路径。这6项是FDE交付的"出院证明"——缺任何一项都不算真正移交。"环境与密钥归属"特别重要——很多FDE项目交付后客户不知道API密钥在哪，出了问题无法排查。"Eval集与如何回归"确保客户能自己跑评测，不依赖FDE远程支持。

交付验收模板（4C维度）

3

  • 4C验收框架（OpenFDE《什么是FDE》）：C1现场Context（问题陈述与真实业务结果的对应关系——谁痛、被什么指标衡量、约束是什么）；C2代码Code（系统在客户基础设施真实运行的证据——非demo/非PPT/非纯配置）；C3校准Calibration（正确率/覆盖率/越权率/人工接管率/采用率——逐项填基线→目标→实际）；C4回流Compounding（现场摩擦沉淀成了什么——连接器/模板/评估集/产品需求）。4C框架的价值在于：它不是"功能清单"，而是"结果证据"——每个C都要求可测证据，不是"系统能跑"就行。

  • C3校准指标的实战意义：五个指标构成FDE的"体检表"——正确率（答得对不对）、覆盖率（能答多少）、越权率（有没有超出边界）、人工接管率（多少场景转人工）、采用率（用户真的用不用）。每个指标都要填基线→目标→实际三列，没有基线的目标是空话，没有实际的目标是自欺欺人。特别注意"越权率"——这个指标在传统软件验收中不常见，但在AI系统中至关重要：AI有没有超出边界回答不该回答的问题？有没有调用不该调用的工具？

  • Palantir AI FDE自验证清单：Running a transform preview to validate transform code；Running a function preview to validate function behavior；Reviewing CI checks to validate code written in Code Repositories；变更评审门（"AI FDE will propose changes in a Global Branch proposal or Code Repository pull request for review"）。这些动作可以直接改写为客户上线检查单——不是"系统能跑"就行，而是"每次改动都经过验证"。Palantir的实践说明：FDE不是一次性交付，而是持续交付——每次AI改动都要经过transform preview、function preview、CI checks、变更评审门。

  • 六组典型扯皮话术与应答：①"领导看了Demo很满意"→Demo≠Eval，补冻结集（POC验收表P4）；②"环境下周一定好"→P2未过就维持PoC不进Pilot；③"安全太慢"→升级赞助人，给最小开通清单；④"先上再补文档"→门禁就是防这个，书面No-Go或缩范围；⑤"竞品已经全自动了"→先比差错与投诉成本，用助手把采用与安全做实再谈分级自动；⑥"先全库接上再慢慢补权限"→否，权限是Day 0。这些话术都是客户项目中真实会遇到的模糊说法，模板给出的应答不是"讲道理"而是"指向具体门禁卡哪一项"——把模糊对话拉回到书面流程上，避免口头承诺的陷阱。
