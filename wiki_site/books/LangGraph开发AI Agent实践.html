第2章 开发环境搭建

3
  • 核心观点1：环境搭建的核心是 API 密钥与依赖的正确配置，.env 文件中的密钥填写错误或含多余空格是调用失败的常见原因；排查时应先核对变量名、加载路径和网络。
  • 核心观点2：依赖版本需精确控制（如 faiss-cpu==1.8.0），版本不符会导致检索组件不可用，应确认安装后再执行后续流程。
  • 核心观点3：排错应遵循分层思路——先查密钥与网络连通性，再排查框架组件，避免把模型调用失败误判为记忆或状态组件问题。
  • 核心观点4：环境验证应以最小调用为准：先让模型返回一条简单结果，再接入图、工具和向量库，逐层增加变量才能快速定位失败环节。
第3章 构建带工具与记忆功能的聊天机器人3 个重点▾ 点开看本节重点
本节重点
  • 核心观点1：记忆功能由检查点存储器实现，MemorySaver 是官方内存版方案，轻量无外部依赖，适合开发调试场景；它保存对话状态，不负责替代模型
  • 核心观点2：记忆与模型调用逻辑解耦——切换模型（如 Qwen-plus）无须改动记忆配置，因为检查点只负责保存对话状态
  • 核心观点3：是否传入 「checkpointer」 决定对话是否有上下文：不传则每轮独立，模型仅基于当前输入回复；传入后即可获得历史上下文，还要用稳定的 thread 标识区分会话

第4章 构建自定义RAG检索Agent

3
  • 核心观点1：LangGraph 通过状态管理与节点决策实现 RAG 流程的智能调度，解决传统 RAG 流程固定、缺乏灵活性的问题；是否检索、检索几次以及何时生成都可以由图控制。
  • 核心观点2：RAG Agent 至少需定义三个核心节点——“判断是否需要检索”“执行检索”“生成最终回答”，每个节点接收状态、执行逻辑、修改状态输出。
  • 核心观点3：文档处理质量决定检索效果，应按文档结构（标题、段落）自定义分割符，避免切断完整语义段落；切分、嵌入、向量搜索和上下文拼装必须作为一条可调试链路观察。
  • 核心观点4：生产化需补齐缓存（如 Redis）、权限控制、批量调用与多格式文档支持，以提升响应速度、降低成本并防止敏感信息泄露；还应对空召回和低置信度回答设置降级。
  • 核心观点5：RAG 的故障定位应区分加载、切分、向量化、检索和生成环节，不能看到答案不佳就只调整提示词。
  • 文本分割优化：根据PDF文档的内容结构（如标题、段落），自定义分割符，避免将完整的语义段落分割开；

第6章 集成外部工具与API

3
  • 核心观点1：外部工具是智能体能力的延伸，集成时需明确工具的输入输出契约与调用边界；参数校验和超时设置应在工具层完成。
  • 核心观点2：工具调用失败应有兜底策略，避免单点故障中断整个智能体流程；可按错误类型选择重试、降级、人工处理或明确告知用户。
  • 核心观点3：RESTful API、数据库和自定义工具都应统一封装，节点只依赖稳定的数据契约而不依赖外部响应的偶然文本格式。
  • 核心观点4：工具返回值最好用字典或 Pydantic 模型表达成功、错误、数据和来源，便于下游节点解析、测试和记录日志。

第8章 智能体(Agent)集成

3
  • 核心观点1：工具执行结果（API 响应、数据库查询结果）需封装为统一格式（字典或 Pydantic 模型），保证下游节点可稳定消费。
  • 核心观点2：结构化封装是智能体集成的基础，统一数据契约可降低节点间耦合、提升可测试性；错误结果也应遵守同一结构。
  • 核心观点3：智能体主管负责拆分任务、调用专长 Agent 并汇总结果，子 Agent 应获得自包含的任务上下文，避免依赖不可见的全局变量。
  • 核心观点4：输出解析不能只依靠字符串截取，应该通过结构化字段、类型校验和失败重试保证结果可被主流程使用。

第10章 构建旅行规划智能体

3
  • 核心观点1：旅行规划属于多约束、多步骤任务，适合用状态图拆分“收集需求—检索信息—生成方案”等阶段；日期、地点、预算和偏好应进入显式状态。
  • 核心观点2：外部工具（如天气、地图、票务 API）的集成质量直接决定规划结果的可用性；实时数据应标注来源和获取时间。
  • 核心观点3：规划结果需要经过约束检查，发现天气、时间或交通冲突时回到调整节点，而不是直接输出看似完整但无法执行的行程。
  • 核心观点4：多工具调用要控制并发、超时与失败分支，保留用户可修改的中间方案，便于重新规划。

第12章 构建股票趋势预测智能分析系统

3
  • 核心观点1：金融分析系统需整合数据获取、指标计算、模型分析与报告生成多个环节，体现 LangGraph 编排复杂分析流水线的能力。
