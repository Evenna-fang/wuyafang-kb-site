FDE 程序性边型 Schema · 五段式链路

版本：v0.1-draft · 2026-10-30
设计参照：Palantir Foundry Ontology Action Types 官方文档；OC 调研报告 §3.2（FDE 程序性链路五段式）
用途：把 FDE 真实交付中的"问题→根因→处置→工具→验证"链路显式建模为图谱边，供 RAG 多跳推理与错误台账回流使用。
与现有 schema 关系：本文件定义程序性（procedural）边族，与 edge-schema.json 的结构性（structural）纵向谓词（IS_A / PART_OF / IMPLEMENTS / USES / HAS_MODULE）正交叠加；不替换、不重命名任何已有谓词。

一、五段式链路总览

2

一条完整的 FDE 程序性案例，必须能在图谱里走出如下五跳路径（缺一跳即视为"程序性不闭合"）：

SYMPTOM ──diagnosed_by──▶ ROOT_CAUSE ──fixed_by──▶ ACTION ──requires──▶ TOOL ──validated_by──▶ EVIDENCE
  (问题症状)               (根因)                  (处置动作)             (工具/权限)          (验证凭据)

对应 Foundry Ontology Action 的语义：每一段都不是"知识陈述"，而是受控动作的输入-输出契约——从"看到症状"出发，经过"诊断→处置→准备→核验"四步动作，最终收敛到可复核的凭据。

二、节点类型（domain / range 前置约束）

2

五段式边型复用并扩展 edge-schema.json 的 entity_types。新增三类程序性节点（全部大写+下划线，与现有 TECH_STACK / LAYER / FRAMEWORK / ... 命名一致）：

节点类型 中文释义 典型实例
SYMPTOM 问题症状 / 客户可感知的异常 "RAG 召回 top-5 命中率 < 30%"、"客户内网模型推理 OOM"
ROOT_CAUSE 根因（经过 5 Why 收敛） "chunk 粒度 512 过小 + 缺全局语境"、"量化到 4bit 后 KV cache 爆显存"
ACTION 处置动作 / FDE 可执行动作 "换 Contextual Retrieval + chunk 升到 1024"、"换 AWQ-GEMM 内核"
TOOL 工具 / 权限 / 资产 "Anthropic Contextual Retrieval 模板"、"vLLM 0.6 FP8 启动参数"、"客户内网 sudo 权限"
EVIDENCE 验证凭据（可被复核的输出物） "复测 recall@5 = 78% 的 eval 报告"、"压测 P99 < 2s 的 Grafana 截图"

存量节点类型（TECH_STACK / LAYER / FRAMEWORK / SUBSYSTEM / PROTOCOL / STRATEGY / IMPLEMENTATION）不动，只在五段式边的 TOOL 段 被引用（一个 TOOL 节点可以同时是 FRAMEWORK 或 IMPLEMENTATION）。

三、五种边型字段定义

2

每种边型给出：名称 / 中文描述 / domain / range / 必填属性 / 示例三元组。所有边强制带两个公共属性：
- strength ∈ [0, 10]（沿用 edge-schema.json 的 relationship_strength 约定）
- confidence ∈ {confirmed, suspected, refuted}（默认 suspected；confirmed 必须有 EVIDENCE 段闭环）

3.1 diagnosed_by —— 症状 → 根因

3
字段 内容
边名 diagnosed_by
中文描述 该症状被诊断为某根因（诊断动作的输出）
domain SYMPTOM
range ROOT_CAUSE
必备属性 method（诊断方法，如 5-Why / 分层排查 / A/B）、diagnosed_by_agent（谁做的诊断：DSH / Claude / 人工）、timestamp
反身 / 多对多 一个 SYMPTOM 允许指向多个 ROOT_CAUSE（疑似并列根因），每个 ROOT_CAUSE 必须能被后续 fixed_by 接住
示例 RAG召回top-5<30% --diagnosed_by--> chunk=512 缺全局语境，[S=8, confidence=confirmed, method=5-Why, diagnosed_by_agent=DSH]

3.2 fixed_by —— 根因 → 处置动作

3
字段 内容
边名 fixed_by
中文描述 该根因由某个处置动作解决（处置动作的输入）
domain ROOT_CAUSE
range ACTION
必备属性 fix_strategy（修复策略类别：code-change / config-tune / data-fix / infra-change / prompt-fix）、applied_by_agent、rollback_available（bool）
约束 ROOT_CAUSE 不允许悬空——必须至少有一条 fixed_by，否则图谱里会出现"诊断完没动作"的死链
示例 chunk=512 缺全局语境 --fixed_by--> 切 Contextual Retrieval + chunk 升 1024，[S=9, fix_strategy=config-tune, rollback_available=true]

3.3 requires —— 处置动作 → 工具/权限

3
字段 内容
边名 requires
中文描述 执行该动作需要哪些工具、权限、资产（前置依赖）
domain ACTION
range TOOL（TOOL 节点可同时是 FRAMEWORK / IMPLEMENTATION / PROTOCOL / 权限实体）
必备属性 required_role（如 dev / ops / customer-admin）、est_cost_min（人分估算）、blocking（bool：缺了能不能干）
复用 与现有 USES（structural）的区别：USES 是静态依赖关系（"LangGraph 用 MCP"），requires 是动作执行时的动态前置条件（"这次修复 requires 客户内网 sudo 权限"）
示例 切 Contextual Retrieval --requires--> Anthropic Contextual-Retriever 模板，[S=7, required_role=dev, blocking=true]

3.4 validated_by —— 工具/动作 → 验证凭据

3
字段 内容
边名 validated_by
中文描述 该动作/工具的效果被哪份凭据复核（验收闭环）
domain ACTION（可放宽到 TOOL）
range EVIDENCE
必备属性 validation_metric（如 recall@5 / P99 / 客户签认）、before_value、after_value、evidence_uri（必须可定位：wiki 路径 / Grafana / eval json）
约束 整条五段链 confidence=confirmed 的必要条件：链上每个 ROOT_CAUSE → ACTION → EVIDENCE 段都必须有 validated_by，且 EVIDENCE 节点本身必须带 evidence_uri（禁止"我觉得修好了"）
示例 切 Contextual Retrieval --validated_by--> recall@5 基线复测报告，[S=10, validation_metric=recall@5, before=0.28, after=0.78, evidence_uri=wiki/L4-RAG/eval-20261030.md]

3.5 公共反向边（用于检索）

3

为了让 RAG 双向都能查到，每条正向边自动派生反向边（写入时由脚本生成，不手填）：

正向 反向 用途
SYMPTOM --diagnosed_by--> ROOT_CAUSE ROOT_CAUSE --explains--> SYMPTOM 从根因反查所有它能解释的症状
ROOT_CAUSE --fixed_by--> ACTION ACTION --fixes--> ROOT_CAUSE 从动作反查它治哪些根因
ACTION --requires--> TOOL TOOL --needed_for--> ACTION 从工具反查它支撑哪些动作
ACTION --validated_by--> EVIDENCE EVIDENCE --validates--> ACTION 从凭据反查它验收了哪些动作

四、与 bfo / skos 谓词族的兼容关系

2

本五段式边族不引入全新本体，每条边都能映射到 BFO（Basic Formal Ontology）上层或 SKOS 词汇表的既有语义：

本边 BFO 映射 SKOS / OWL 映射 说明
diagnosed_by BFO:0000062 (diagnostic process) → BFO:0000040 (objective entity 作为根因) skos:relatedMatch 弱关联升级为带过程属性的边 不是纯陈述性 related，是"诊断过程"指向诊断结论
fixed_by BFO:0000015 (intentional process) 由 agent 执行 → 改变 BFO:0000031 (disposition) dct:references + prov:wasGeneratedBy 动作是带意图的过程，结果是 disposition 被修正
requires BFO:0000130 (role) / BFO:0000129 (material entity) 作为前置 owl:requires / dcat:required 与现有 USES（structural）区别见 §3.3
validated_by BFO:0000261 (evaluation process) 输出 BFO:0000179 (information content entity 作为凭据) prov:wasDerivedFrom / dct:conformsTo EVIDENCE 节点本身是 ICE（可被引用的信息实体）
反向边 一律走 owl:inverseOf 声明 — 不占独立命名空间

命名空间约定：五段式边全部使用命名空间 proc:（procedural），与现有结构性谓词 str:（structural，如 IS_A / PART_OF）横向谓词 hor:（legacy complementary / alternative / ...）三套并列：

@prefix str:  <http://wuyafang-l.local/ontology/structural#>
@prefix hor:  <http://wuyafang-l.local/ontology/horizontal#>
@prefix proc: <http://wuyafang-l.local/ontology/procedural#>

proc:diagnosed_by  a owl:ObjectProperty ;
    rdfs:domain  proc:SYMPTOM ;
    rdfs:range   proc:ROOT_CAUSE ;
    owl:inverseOf proc:explains ;
    rdfs:subPropertyOf bfo:0000062 .

不冲突声明：
- ✅ 不替换 edge-schema.json 的 5 个纵向谓词（IS_A / PART_OF / IMPLEMENTS / USES / HAS_MODULE）
- ✅ 不替换 ontology-triples.csv / wiki-relations.csv 已有的横向谓词（complementary / alternative / orthogonal / specialization / instantiates / depends-on / pairs-with / validates / escalates-to / part-of）
- ⚠️ 注意：存量 wiki-relations.csv 里已有 validates 谓词（如 "Evals validates RAG"），语义偏向"评测体系给整个流程背书"；新 validated_by 偏向单次动作的验收。两者并存不合并，用命名空间区分（hor:validates vs proc:validated_by），抽取脚本时按上下文自动分流。

五、合法边矩阵（kg_validation_schema 风格）

2

与 edge-schema.json 的 valid_edges 同款格式，供抽取脚本硬校验：

{
  "procedural_valid_edges": {
    "SYMPTOM":      ["diagnosed_by"],
    "ROOT_CAUSE":    ["fixed_by", "explains"],
    "ACTION":        ["fixes", "requires", "validated_by"],
    "TOOL":          ["needed_for", "PART_OF", "USES", "IS_A"],
    "EVIDENCE":      ["validates"]
  },
  "procedural_node_types": ["SYMPTOM", "ROOT_CAUSE", "ACTION", "TOOL", "EVIDENCE"],
  "closure_rule": "confidence=confirmed 的五段链必须满足 SYMPTOM→ROOT_CAUSE→ACTION→EVIDENCE 全通；TOOL 段可省略（动作无外部依赖时）"
}

六、示例完整链（可直接当 golden case）

2

摘自 wiki/L4-RAG工程/RAG检索不准怎么排查.md 真实案例：

SYMPTOM:     "RAG 检索 top-5 recall = 0.28（客户验收阈值 0.6）"
  └─diagnosed_by [method=5-Why, agent=DSH, S=8]──▶
ROOT_CAUSE:  "chunk=512 过短 + 缺全局语境补全"
  └─fixed_by [fix_strategy=config-tune, rollback=true, S=9]──▶
ACTION:      "切 Contextual Retrieval，chunk 升至 1024 + LLM 补全局句"
  ├─requires [blocking=true, role=dev]──▶ TOOL: "Anthropic Contextual-Retriever 模板"
  └─validated_by [metric=recall@5, before=0.28, after=0.78, S=10]──▶
EVIDENCE:    "eval-20261030.json + wiki/L4-RAG/复测报告.md"

这条链入图后，RAG 多跳查询（"上次 RAG 召回不准是怎么修好的？"）可以直接顺着 diagnosed_by → fixed_by → validated_by 一跳一跳取到答案，而不是在大段 markdown 里向量召回。

七、迁移与落地建议

2
  1. 不重建旧图：存量 wiki-relations.csv / ontology-triples.csv 不动，五段式边以新增表 ontology/procedural-edges.csv 落地（列：source, predicate, target, strength, confidence, method, evidence_uri, wiki_ref）。
  2. 先打样后批量：先手工录入 5-10 条 golden 案例（如上节 RAG 案例），再交给 Codex 写的三元组抽取脚本在 wiki 全库跑批。
  3. 置信度门禁：抽取脚本默认写 confidence=suspected；只有 evidence_uri 可定位且 before/after_value 齐备时才升 confirmed——避免"我脑补了一条根因"污染图谱。
  4. 错误台账回流：总网流程/错误台账机制.md 里的高频已修复条目，按月批量转写为本五段式边，形成"踩坑→可复用程序性知识"的正循环。
