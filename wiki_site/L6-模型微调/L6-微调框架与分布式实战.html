L6 微调框架与分布式实战

知识网挂接：总地图“四之一知识层”的 L6 模型微调内容，服务 N2 技术选型与 N4 模型工程化执行。

运行边界：本文所有安装、训练、导出、分布式启动命令，以及 YAML、JSON、Python 片段均为“示例，未实跑”。本文没有安装依赖、下载模型、启动 GPU 训练或验证产物。示例只说明流程和排错结构，具体参数名、兼容组合与目录布局必须以所用版本的官方样本和 --help 为准。

微调项目失败，常见原因不是“少知道一个框架”，而是把四个不同问题揉成了一件事：任务该用全参还是 LoRA，数据怎样变成带正确标签的批次，训练状态怎样放进显存，产物怎样保存、恢复和评估。LLaMA-Factory、ModelScope SWIFT、TRL+PEFT 主要解决前两类中的工程组织问题；DeepSpeed 主要解决分布式执行、状态切分和卸载问题。微调框架不等于分布式框架，装上 DeepSpeed 也不会自动完成数据模板、标签掩码和业务评测。

需要先建立一条小而完整的主路径，原因是长训练会放大早期错误。模板错一位、答案全被截掉、LoRA 没有命中目标模块、把适配器目录当完整模型、ZeRO-3 保存时聚合权重导致内存峰值，这些问题都可能在“训练终于启动”之后才暴露。小样本流程的价值是尽早走通“数据—训练—保存—恢复—合并—固定输入回归”，不是用小样本证明业务效果。

本文还要纠正三个资源误区：

  1. 梯度累积只把多次微批次合并成一次更新，不能消除参数、单样本激活或优化器状态本身的占用。
  2. 多卡不天然等于单卡容量增加。普通数据并行会复制模型；ZeRO-1/2 也仍保留完整参数副本。
  3. ZeRO 不是“省所有显存”。激活、通信桶、临时聚合、CUDA 工作区和碎片仍可能占显存，卸载还会引入主存、磁盘和通信成本。

稳定性与超参诊断另见《L6 损失函数与优化器》。

当前功能核对入口应回到官方项目页：LLaMA-Factory、ModelScope SWIFT。需要自行拼装训练链路时，核对 PEFT LoRA 指南与 TRL SFTTrainer 文档。本文不声称任何一个是“事实标准”，也不把旧篇固定版本的参数当作当前版承诺。

一个实用决策顺序是：先确定训练方式，再确定数据与模型适配，最后确定分布式。单卡 LoRA 能清楚完成的任务，不必为了“看起来正式”先上 ZeRO-3；全参模型加载已经失败，也不应只在数据批量上反复试错。

2. LoRA、全参与分布式是三组独立开关

3
  • 全参 SFT：更新全部或大部分模型参数，梯度与优化器状态随之增长，适合有充分数据、算力和回归预算的任务。
  • LoRA：冻结基础权重，训练注入的低秩增量。它显著减少可训练参数及其优化器状态，但仍要加载基础模型并计算激活。
  • QLoRA：在 LoRA 思路上以低比特表示冻结基座，减少基座权重占用；不代表激活、适配器梯度和所有中间计算都变成低比特。
  • 分布式并行：决定参数、梯度、优化器状态和计算怎样跨设备组织。它可以与全参或参数高效训练组合，但每种组合都要核对当前版本支持情况。

课件将 LoRA 放在参数高效微调语境中，强调低秩、模块化和可合并；书摘目录则把“全量参数微调”“低参数量微调”“分布式训练与内存优化”分在不同章节。这个划分比把框架名堆在一起更有助于定位问题。

3. ZeRO 三个阶段切的是什么3 个重点▾ 点开看本节重点
本节重点
  • ZeRO-Offload 主要面向 Stage 2；ZeRO-Infinity 面向 Stage 3，并将分层内存扩展到 CPU/NVMe
  • 可卸载对象、设备和字段必须以当前 DeepSpeed 配置文档为准
  • 卸载不是免费扩容：CPU 卸载消耗主存和主机—设备带宽，NVMe 还依赖本地盘吞吐、容量及异步 I/O 支持
3
阶段 优化器状态 梯度 参数 典型判断
ZeRO-1 按数据并行组切分 每卡完整 每卡完整 参数和梯度的副本尚可接受，先削减优化器状态
ZeRO-2 按数据并行组切分 再按组切分 每卡完整 需要进一步削减梯度状态，但完整参数仍能放入设备
ZeRO-3 按数据并行组切分 按组切分 再按组切分 参数副本本身成为瓶颈，能够接受更多通信和保存复杂度

ZeRO-Offload 主要面向 Stage 2；ZeRO-Infinity 面向 Stage 3，并将分层内存扩展到 CPU/NVMe。可卸载对象、设备和字段必须以当前 DeepSpeed 配置文档为准。卸载不是免费扩容：CPU 卸载消耗主存和主机—设备带宽，NVMe 还依赖本地盘吞吐、容量及异步 I/O 支持。

PyTorch FSDP 也提供参数、梯度和优化器状态分片，适合已有 PyTorch 原生分布式工程、希望减少外部运行时依赖的团队。选型时应比较模型兼容、检查点工具、运维经验和实测吞吐，而不是另起一套“ZeRO 与 FSDP 谁绝对更快”的口号。

步骤 C：检查预期产物，而不是只看进程退出

产物检查清单如下，具体文件名以所用版本为准：

  • 输出目录中有可识别的 LoRA 适配器配置与权重；
  • 至少一个训练检查点包含恢复所需的训练状态，而不是只有最终适配器；
  • 日志或训练状态中有 step、loss、learning rate、grad norm 等记录；
  • 基础模型路径、模板、数据配置和软件版本被一并保存；
  • 日志显示可训练参数数量符合 LoRA 预期，且没有“零个目标模块”一类警告；

3

先保存最早错误 rank 的完整堆栈、当时的序列长度和配置，再判断 OOM 出现在哪个阶段。其他进程占用也要先查清，但不要终止不属于自己的任务。

OOM 时点 优先怀疑 第一轮动作 无效或危险动作
模型加载 参数副本、加载精度、临时双副本 换更小模型做链路基线；核对加载精度；全参场景再评估参数分片 只增加梯度累积；反复调用缓存清理
第一次前向 微批量、序列长度、注意力与激活 微批量降到小实验最小值；缩短异常长样本；确认答案未被截没 把 ZeRO 当成激活压缩器
反向传播 激活、梯度、通信缓冲 开梯度检查点；降低长度或微批量；再检查状态切分 同时改多个变量导致无法归因
第一次优化器更新 优化器状态延迟初始化 全参时考虑 ZeRO-1/2；LoRA 时确认可训练参数范围 以为 LoRA 不需要加载基座
保存或导出 ZeRO-3 权重聚合、CPU 合并中间副本 预留保存峰值；先保存分片检查点，再按官方方式离线导出 把“训练没 OOM”等同于“保存也不会 OOM”

有序处理步骤：

  1. 记录 GPU 真实进程、失败阶段和最长样本，建立不改代码的容量基线。
  2. 减小微批量；如需保持有效批量，用梯度累积补偿。有效批量约为“每卡微批量 × 累积步数 × 数据并行副本数”。
  3. 缩短序列或拆分异常长样本，同时抽查有效答案 token，避免用删除监督信号换训练成功。
  4. 开启梯度检查点，以重算换激活显存，并记录吞吐变化。
  5. 如果任务允许改变训练方式，再比较全参、LoRA、QLoRA；这是新实验，不是同一实验的无损开关。
  6. 多卡且状态确为瓶颈时选择 ZeRO；仍不足才评估 offload。

torch.cuda.empty_cache() 只能处理部分未使用缓存，不能释放仍被引用的张量，也不能让物理上放不下的模型变为可训练。所谓碎片优化同样不增加物理显存。

4. ZeRO 阶段选择与配置衔接

3

Stage 3 的 stage3_gather_16bit_weights_on_model_save 用于保存时聚合完整低精度权重，便于得到可独立加载的模型；聚合会增加额外内存与通信成本。首次排错可把“可续训分片检查点”和“可部署完整权重”分开验收，不要在保存失败时丢失整个训练目录。

若使用 ZeRO-Offload/Infinity，先确认主存、NVMe 挂载点、每节点路径权限和异步 I/O 算子，再增加卸载字段。GPU 利用率下降可能是在等 CPU 或磁盘，不一定还是显卡容量问题。

5. 多卡启动、保存、合并与恢复2 个重点▾ 点开看本节重点
本节重点

  • 两者选一种，不要嵌套两个启动器造成重复进程
3

启动

上层框架可能自行调用 torchrun，手写 TRL/Trainer 脚本则常由用户显式启动。两者选一种，不要嵌套两个启动器造成重复进程。

以下是启动结构的示例，未实跑，不是当前版兼容保证：

# 示例，未实跑：框架自动进入多进程路径时，字段以官方样本为准
CUDA_VISIBLE_DEVICES=0,1 FORCE_TORCHRUN=1 NPROC_PER_NODE=2 \
  llamafactory-cli train configs/lora_sft_smoke.yaml \
  deepspeed=configs/ds_zero2.json output_dir=outputs/lora-z2

# 示例，未实跑：手写 Trainer/TRL 脚本的另一种入口，不与上一条叠加
CUDA_VISIBLE_DEVICES=0,1 torchrun --standalone --nproc_per_node=2 \
  train_sft.py --deepspeed configs/ds_zero2.json

主路径是 LoRA，并不意味着 LoRA 与任意 ZeRO 阶段在所有版本都可直接组合。若为了全参训练选择 ZeRO-3，应另建全参配置并重新估算资源；不要只把 finetuning_type 改一个词就沿用全部学习率、保存和显存假设。

多卡卡住时先找最早失败的 rank。一个 rank 先 OOM 或数据异常，其他 rank 最后才报告 NCCL 超时；单纯延长超时不能修复最初错误。多节点还要核对代码、环境、路径、主节点地址和端口的一致性。

保存与恢复

  • 最终适配器：用于加载或合并，不一定包含优化器、调度器和随机数状态。
  • 可续训 checkpoint：用于从同一实验继续训练，应保留完整目录和各 rank 分片。
  • 合并模型：用于独立部署，应包含完整权重、config、tokenizer 等必要文件。

恢复命令是示例，未实跑：

# 示例，未实跑：替换为真实存在且属于本实验的检查点
llamafactory-cli train configs/lora_sft_smoke.yaml \
  resume_from_checkpoint=outputs/lora-smoke/checkpoint-2

恢复后检查起始 step、学习率、数据推进和随机状态，不能只看进程能启动。跨框架迁移通常先导出普通模型，再在新框架重新建立优化器，不能混用各自 checkpoint 目录。

合并与回归

LLaMA-Factory 合并配置的示例，未实跑如下；当前字段仍须对照官方导出样本：

# 示例，未实跑：基础模型、模板与训练保持一致
model_name_or_path: Qwen/Qwen2.5-0.5B-Instruct
adapter_name_or_path: outputs/lora-smoke
template: qwen
finetuning_type: lora
export_dir: outputs/lora-merged
export_device: cpu

# 示例，未实跑
llamafactory-cli export configs/lora_export.yaml

合并通常需要重新加载未量化基础模型；QLoRA 训练时节省的显存不代表合并也不需要内存。合并后应使用完整模型路径独立加载，不再叠加同一适配器。验证至少包括：文件完整性检查、固定输入下合并前后输出回归、基础模型与微调模型的独立业务测试集对比。

6. 产物、验证、常见坑与回退

3

一次实验应收口的产物：不可变的数据版本、完整配置、环境与模型 revision 记录、训练日志、可续训 checkpoint、最终适配器或合并模型、固定问题回归结果、独立验证集报告。小样本冒烟与正式效果实验分目录保存。

常见坑 最早证据 回退方式
混抄不同版本 CLI/YAML 未知参数、解析失败、同名字段语义变化 回到固定版本官方最小样本，只逐项加入业务配置
模板或数据映射错误 预处理后只剩提示、有效标签为空、角色警告 回退到一条人工构造样本，打印模板化结果与标签
多卡有效批量被悄悄放大 更新步数、warmup 与单卡不可比 固定全局批量重算累积步数，再比较实验
ZeRO 后仍 OOM 激活或通信桶峰值未变、保存时聚合失败 回到最近可运行阶段；分别处理激活、状态和保存
把适配器当完整模型 缺少 config/tokenizer/完整权重或加载报错 回到“基座+适配器”加载，重新按官方流程导出
合并后效果异常 基座 revision、模板或 tokenizer 不一致 保留原适配器，回到合并前固定输入回归
NCCL 超时掩盖根因 其他 rank 最后才报错 查最早 rank 日志，回退到单机两卡短流程

任何失败都保留输出目录和日志，以新目录做下一次单变量实验。回退的优先顺序是：最近可运行配置 → 最近完整 checkpoint → 官方最小样本 → 更小模型。不要用删除旧产物来“解决”无法解释的失败。
