本文面向已经会使用 docker run、docker logs 的工程师。目标是把一个后端 API、数据库、缓存和静态前端组合成可以构建、启动、验证、回退的交付单元。示例适合单机部署的起点；公网生产还要补齐 TLS、认证、备份恢复、漏洞扫描和监控告警。

WHAT / WHYT：从一个镜像到一组服务，及其边界

2

1. Dockerfile、上下文与镜像层

3

Dockerfile 是镜像构建配方。基础镜像、依赖安装、代码复制、运行身份和默认命令都能进入版本控制。docker build -t my-api:1.0 . 最后的点是构建上下文，不是 Dockerfile 路径；构建器只能访问上下文中允许进入构建的文件以及明确提供的其他输入。COPY ../secret /app 不能任意读取父目录。上下文选仓库根目录还是后端子目录，会直接决定可复制范围和缓存失效范围。

镜像由只读文件系统层以及配置元数据组成。RUN、COPY 等通常产生文件系统变化；ENV、CMD 等主要写入配置，不能简单理解成“每条指令都有一份完整文件系统”。各层以内容寻址方式存储，相同内容可以被不同镜像复用；容器启动时再叠加自己的可写层，常见存储驱动通过写时复制处理修改。容器可写层随容器删除而消失，因此业务数据不能依赖这一层。

删除上层文件不会抹去下层已经包含的内容。例如先 COPY 私钥、下一条 RUN rm，私钥仍可能存在于历史层。正确方法是在进入上下文前排除凭据，构建期认证使用 BuildKit secret mount，运行期凭据使用单独挂载。

Compose 用 YAML 描述一个应用的服务集合。服务规定镜像、命令和运行配置；网络规定哪些服务互通；卷负责容器生命周期之外的数据保存。Compose Specification 是持续演进的规范，如今不必再写顶层 version: "3.8"；新插件中该字段仅为兼容而保留，可能提示已经过时。

同一网络上的服务可以用服务名通信。API 访问 PostgreSQL 应连接 postgres:5432，而不是 localhost:5432；容器里的 localhost 指向容器自身。ports 是向宿主机发布端口，服务之间通信不需要发布端口，EXPOSE 也不会自动向宿主机开放端口。

WHY：为什么环境也需要可审查、可重复

2

1. 把环境写成代码，减少手工状态

3

手动进服务器安装依赖，最终得到的是一台难以复制的机器。用 Dockerfile 固定运行时和依赖，用 Compose 声明网络、数据卷、资源限制，代码审查就能覆盖环境变化。所谓不可变基础设施，是把应用更新表达为“构建新镜像并替换容器”，而不是进入旧容器修文件。否则镜像里的代码和实际运行代码分离，下一次重建就把修复覆盖了。

《持续交付 2.0》目录中的部署流水线、软件配置管理、不可变基础设施与低风险发布，为这类环境代码提供了交付背景；公开摘录“质量内建”说明配置检查、集成测试和安全检查应在交付过程中完成，而不是部署后补验。书籍材料只提供原则与章节指引，具体 Compose 字段仍以官方规范为准。

不可变并不意味着数据库不可变。应用镜像负责程序，持久卷负责状态；数据库升级、迁移和备份有自己的生命周期。配置也应区分公共参数与凭据，让同一镜像在开发、预发布和生产使用不同运行配置，而不必重新构建。

2. 分层顺序为什么影响速度3 个重点▾ 点开看本节重点
本节重点
  • 构建缓存会考虑指令及其相关输入
  • 若先 「COPY . .」 再安装依赖，任何一个源文件变化都可能使依赖安装重新执行
  • 正确顺序通常是先复制依赖清单、安装依赖，再复制源码
3

构建缓存会考虑指令及其相关输入。若先 COPY . . 再安装依赖，任何一个源文件变化都可能使依赖安装重新执行。正确顺序通常是先复制依赖清单、安装依赖，再复制源码。这样业务代码频繁变化时可以复用依赖层。.dockerignore 还应排除虚拟环境、日志、前端 node_modules 和本地 Git 数据，减少输入、传输与无关变动。

缓存命中不等于软件已经更新。未改变的依赖清单可能继续命中旧层，基础镜像标签也可能发生变化。应在受控更新任务中使用 --pull、更新锁文件并重新扫描，而不是每次发布都粗暴 --no-cache。本示例钉住直接依赖；严格生产复现还应锁住传递依赖并记录包哈希，避免同一份 requirements 在不同日期解析出不同结果。

3. 多阶段构建为什么缩小交付范围

3

编译器、头文件、包管理缓存只在构建时需要。多阶段构建让 builder 生成 wheel、二进制或前端静态资源，最终 runtime 只复制运行所需产物。它减少最终镜像里不必要的工具，也降低攻击面。收益取决于项目：本例使用预编译 Python wheel，体积收益可能有限；包含 C 编译链、Node 构建依赖的项目通常更明显。

多阶段本身不保证镜像小。如果把整个 builder 文件系统复制回 runtime，体积仍会很大；也不能把不同 Python 版本、不同 CPU 架构或 glibc/musl 环境中的二进制随意混用。本例两个阶段使用相同基础镜像，避免二进制兼容问题。

4. 为什么不用一串 docker run3 个重点▾ 点开看本节重点
本节重点
  • 单条 「docker run」 可以启动一个进程，但多服务还需要记住网络、卷、重启策略、数据库参数和启动依赖
  • Compose 把关系放进一份可校验文件，并按项目名分组，开发和生产可以使用不同项目名形成隔离
  • 启动顺序与就绪状态是两回事：数据库进程刚创建时可能仍在初始化
3

单条 docker run 可以启动一个进程，但多服务还需要记住网络、卷、重启策略、数据库参数和启动依赖。命令散落在历史记录里，换人就难以重建。Compose 把关系放进一份可校验文件，并按项目名分组，开发和生产可以使用不同项目名形成隔离。

启动顺序与就绪状态是两回事：数据库进程刚创建时可能仍在初始化。depends_on 的短语法只保证启动关系；配合健康检查与 condition: service_healthy 才会等依赖报告健康。即使如此，数据库在运行中仍可能重启，应用还要有连接超时、连接池回收和有限重试。依赖条件不是永久保活承诺。

论文落点：Up/healthy 也不能覆盖有害副作用。 VeriHarm-Bench（arXiv:2611.03575）研究带 shell 的编码 Agent“任务完成但同时造成伤害”的情形，主张同时运行任务正确性测试和可执行伤害测试。其模型与数字不能直接外推到 Compose；我们借用双门禁方法：除了验证四个服务健康和 API 返回，还要断言未发布多余端口、未把 secret 打入镜像、未改动无关卷、未放宽权限，清理演示时不误删其他项目资源。

5. 为什么 .env 与 secrets 分开

3

.env 的主要角色是为 Compose 插值提供参数；env_file 才会把指定文件的键值注入容器。环境变量便于传递端口、日志级别，但密码可能通过容器检查信息、调试输出或进程环境暴露。运行期 secret 文件使应用只读取需要的凭据，避免把密码直接写进 YAML、镜像层或 Git。

本地 Compose 的 secrets: file: 主要是受控文件挂载，并不自动带来加密保险库。源文件仍要受宿主机权限、备份和磁盘安全策略保护。Docker Swarm 的 docker secret 是另一套集群能力；普通 docker compose up 不会因此获得 Swarm 的加密分发机制。

import os
from contextlib import asynccontextmanager
from pathlib import Path

import psycopg
from fastapi import FastAPI, HTTPException
from redis.asyncio import Redis


@asynccontextmanager
async def lifespan(app: FastAPI):
    app.state.cache = Redis.from_url(
        os.environ["REDIS_URL"], decode_responses=True,
        socket_connect_timeout=2, socket_timeout=2,
    )
    yield
    await app.state.cache.aclose()


app = FastAPI(lifespan=lifespan)


@app.get("/api/health")
async def health():
    try:
        password = Path(os.environ["DB_PASSWORD_FILE"]).read_text().strip()
        async with await psycopg.AsyncConnection.connect(
            host=os.environ["DB_HOST"],
            dbname=os.environ["POSTGRES_DB"],
            user=os.environ["POSTGRES_USER"],
            password=password,
            connect_timeout=2,
        ) as conn:
            async with conn.cursor() as cursor:
                await cursor.execute("SELECT 1")
                row = await cursor.fetchone()
        cache_ok = await app.state.cache.ping()
        if row != (1,) or not cache_ok:
            raise RuntimeError("dependency check failed")
    except Exception:
        raise HTTPException(status_code=503, detail="dependencies unavailable") from None
    return {"status": "ok", "database": "ok", "cache": "ok"}

必须分开理解两套优先级：

  1. Compose 插值：本例在项目根目录执行，shell 环境变量优先于 .env；显式 --env-file 可以选择插值文件，多次传入时后者覆盖前者，但 shell 仍优先。无 --env-file 时，当前工作目录的 .env 和项目目录的 .env 还涉及查找规则；为避免多目录歧义，CI 固定工作目录并显式指定文件。
  2. 容器环境变量：普通 up 下，服务的 environment 覆盖服务 env_file，再覆盖镜像中的 ENV；多个服务级 env_file 按列表顺序读取，后者覆盖前者。environment 中显式空值也可能覆盖已有值。
  3. 一次性 run：docker compose run -e KEY=value 优先于该服务其他变量来源。environment: KEY: ${KEY} 的最终值先经过上一条插值规则，再参与容器变量优先级，所以不能把 .env、shell、env_file 简化成一个永远固定的单列表。

        os.environ["REDIS_URL"], decode_responses=True,

    )

1. Compose 的适用边界

3

Compose 是声明多容器应用和管理其生命周期的工具；这里说“Compose 不是编排器”，具体指它不是具备跨节点调度、节点故障迁移和滚动更新保证的集群编排器。单台机器、可接受发布短暂停机、团队能管理宿主机恢复时，Compose 可以提供简单交付。需要跨主机高可用、自动迁移、多副本滚动升级时评估 Kubernetes；希望保持 Docker 生态且需求较简单时可评估 Swarm，但应确认团队维护能力和功能边界。

2. 钉住镜像、升级与回退3 个重点▾ 点开看本节重点
本节重点
  • 不要用 latest 发布
  • 基础镜像的补丁 tag 仍可能被重发布，digest 才锁定具体内容，同时也要安排定期更新，避免永久锁住漏洞版本
  • 单机 Compose 的 「up -d」 是容器替换，不承诺零停机滚动升级
3

不要用 latest 发布。每次构建分配唯一版本标签，例如提交哈希，再记录 registry digest；严格不可变引用用 image@sha256:实际摘要，其中摘要必须从真实构建或 registry 获取。基础镜像的补丁 tag 仍可能被重发布，digest 才锁定具体内容，同时也要安排定期更新，避免永久锁住漏洞版本。

单机 Compose 的 up -d 是容器替换，不承诺零停机滚动升级。本例 Nginx 可刷新 API DNS，但替换期间仍可能有短暂 502。需要低停机时设计双实例与代理切流，或迁移到支持滚动更新的平台。回退镜像前确认数据库迁移向后兼容，必要时先恢复备份；不能认为把 tag 改回去就能回退数据库模式。

3. 凭据、健康与只读文件系统

3

不要在 compose、Dockerfile ARG、ENV 中硬编码生产密码。普通 Compose 的 file secret 适合受控单机挂载，生产可以由凭据管理系统在部署时供给；Swarm 场景使用 docker secret，Kubernetes 则有自己的 Secret 与外部凭据集成。不要把 docker compose config 展开的凭据输出到工单。

API 使用非 root、去掉 capabilities 和只读根目录；PostgreSQL 与 Redis 需要各自可写的数据路径，不能盲目给所有服务套同一限制。Nginx 的官方镜像在本例保留其默认运行模型，若组织要求所有容器非 root，应换用适配的非特权镜像，并调整监听端口、PID 与缓存目录后再验证。

健康检查要区分进程存活与业务就绪。本文健康接口把数据库和缓存计入就绪条件，适合启动验收，但数据库故障会使所有 API 容器同时 unhealthy。生产应拆出轻量存活端点和依赖就绪端点，设置告警与重连策略，避免探针加重故障。stop_grace_period 应大于正常请求收尾时间，应用在 SIGTERM 后停止接新请求、关闭连接。

5. 多环境与 CI 的最小流程

3

基础文件保留共同配置，开发与生产覆盖文件只表达差异。CI 显式列出 -f、--env-file、项目名，避免当前目录自动发现开发覆盖文件。生产应消费 CI 已发布的镜像，以 --no-build 禁止在服务器现场构建；本例保留 build 字段便于教学，正式部署时可拆出不含 build 的基础运行文件。

以下是供有授权的 CI 环境使用的模板，会推送镜像；本文写作与校验过程不执行任何推送。预先通过 CI 的凭据管理完成 registry 登录，不将 token 写入仓库或命令日志。CI_COMMIT_SHA、REGISTRY_IMAGE 由平台提供，registry 地址替换为组织自己的仓库。

# 将镜像引用或其 digest 作为发布产物交给部署阶段。
