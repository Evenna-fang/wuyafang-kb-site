WHAT / WHYT：先建立六个概念与适用边界

2

镜像（image）是只读的应用交付模板，包含程序、依赖、用户空间文件以及默认启动设置。python:3.12.8-slim-bookworm 就是一份带 Python 的基础镜像。镜像名通常是 仓库地址/命名空间/名称:标签；省略地址时通常使用 Docker Hub。标签是可移动引用，摘要 sha256:… 才能标识确定内容。

容器（container）是镜像的一次运行实例，由进程、隔离环境、可写层和挂载等组成。同一个镜像可以创建许多容器。停止容器会结束进程，但保留容器可写层；删除容器会删除该可写层。镜像里没有“正在运行的服务”，服务是在创建并启动容器时运行的。

仓库（repository）保存同一应用的多个标签；镜像注册服务（registry）托管许多仓库，例如 Docker Hub 或企业私有 registry。pull 下载镜像，push 上传镜像。本教程只要求本地构建，不需要登录或上传代码。

联合文件系统（UnionFS）把多个只读层与一个可写层呈现成一棵目录树。Linux 容器常见实现是 OverlayFS；实际后端受存储驱动和镜像存储配置影响。写入已有文件通常会触发写时复制；这使多个容器能共享镜像层，也意味着数据库的大量随机写不宜长期放在容器可写层中。删除后续层中的文件，并不能消除早期镜像层中的原始内容，因此“先 COPY 密钥再 RUN 删除”仍会泄密。

比较维度 Linux 容器 虚拟机
隔离边界 namespaces、cgroups 等内核机制 虚拟硬件与独立客户机内核
内核 共享运行环境的 Linux 内核 每台虚拟机有自己的内核
启动 通常启动应用进程，常见为秒级 通常还需启动操作系统，常见为数十秒
内存与存储 可共享文件层，无每容器内核开销 每台有系统镜像和内核开销
兼容性 仍受 CPU 架构、内核接口等约束 可以安装不同客户机操作系统
适合场景 高频交付、测试环境、服务扩缩容 更强隔离、不同内核或完整系统环境

这里的时间只是常见数量级，不是性能保证；应用初始化和下载镜像可能远比启动容器耗时。macOS、Windows 上的 Linux 容器通常运行于 Docker Desktop 管理的 Linux 虚拟环境，宿主仍承担一份虚拟化开销。

论文落点：只读镜像不只用于应用。 Creating SquashFS Images to Support HPC and AI Datasets（arXiv:2610.20578）比较了 11 种把大量小文件制成 SquashFS 数据集镜像的工作流，动机是降低并行访问对中心文件系统元数据服务的压力。SquashFS 不是 OCI/Docker 镜像格式，不能直接替换本文的分层镜像；可借鉴的是“只读数据封装成不可变制品，并按真实输入形态、存储位置和线程数做基准”。若容器要挂载大型只读数据集，应单独测试元数据开销与挂载方式，不要把海量小文件盲目 COPY 进应用镜像。

Docker Engine主要包括后台守护进程 dockerd、API 和 CLI；Linux 服务器通常直接安装它。Docker Desktop包含图形界面、CLI、Compose、虚拟运行环境等，面向 macOS、Windows 以及桌面 Linux。二者不是互不相关的两种容器格式。OCI定义容器镜像、运行时与分发等开放规范，帮助不同实现互操作；它并不承诺任意架构和操作系统的镜像都能直接互换运行。

2.1 “在我机器上能跑”到底差在哪里3 个重点▾ 点开看本节重点
本节重点
  • Python 项目能启动，不只取决于 「app.py」：解释器版本、pip 依赖、系统动态库、当前目录、环境变量和启动命令都参与结果
  • 甲机器有某个系统包，乙机器没有；开发机依赖已升级，测试机还在用旧版本；同事直接启动 Python，服务器却从另一工作目录启动
  • 这些差异很难靠一份“安装说明”长期保持同步
3

Python 项目能启动，不只取决于 app.py：解释器版本、pip 依赖、系统动态库、当前目录、环境变量和启动命令都参与结果。甲机器有某个系统包，乙机器没有；开发机依赖已升级，测试机还在用旧版本；同事直接启动 Python，服务器却从另一工作目录启动。这些差异很难靠一份“安装说明”长期保持同步。

容器把用户空间依赖和启动契约编码到镜像中。团队在持续集成阶段构建一次，再把同一个镜像摘要推广到测试和生产。测试通过的对象与生产运行的对象因此更接近。Dockerfile 本身并不保证完全可重复：浮动标签、未锁定的间接依赖、在线包源变化仍会改变结果。可靠流程还应保留锁文件、固定镜像摘要，并记录构建参数和架构。

《持续交付 2.0》的目录把部署流水线、软件配置管理、不可变基础设施和低风险发布串成实践体系，公开摘录中“一次构建，多次使用”与这里完全同向。它的作用不是证明 Docker 自动等于持续交付，而是提醒我们把镜像构建、测试、制品保管、发布和监测放进同一条流水线；只有 docker run 成功，仍没有形成交付闭环。

容器同样不会把数据库状态、DNS、外部 API 权限或宿主内核一起封进去。因此“多环境一致”应理解为：程序与用户空间依赖一致，环境差异通过显式配置注入，数据和外部服务另外管理。不要为了追求一致而把开发数据库和生产凭据烘焙进镜像。

2.2 对交付、扩展和回滚有什么帮助

3
工程诉求 容器提供的办法 仍需完成的工作
交付 镜像携带运行依赖与启动命令 自动构建、扫描、版本命名和发布审批
扩展 用同一镜像启动多个实例 负载均衡、容量规划、会话外置
回滚 重新启动上一版镜像摘要 数据库迁移向后兼容、流量切换
环境一致 测试与生产使用同一制品 分离配置、检查架构和宿主支持
新人入职 统一启动入口 准备开发数据和访问权限

镜像版本化让回滚从“现场修改服务器文件”变成“选择已知制品”。但如果新版已经不可逆地修改数据库，启动旧镜像也无法恢复旧数据。数据库迁移应采用可兼容的阶段式变更，并建立备份恢复流程。

扩展方面，复制无状态 HTTP 服务很容易；复制数据库却不能自动得到正确的数据复制和一致性。应用若把用户上传文件保存在容器本地，即使新增十个实例，也会因为各实例文件不同而出问题。应把持久状态放到卷、数据库或对象存储，再考虑横向扩展。

2.3 为什么通常比虚拟机轻3 个重点▾ 点开看本节重点
本节重点
  • 在同一 Linux 宿主上，多个容器共享内核，不必为每个应用启动完整操作系统
  • 镜像公共层能够复用，部署更新只需传输变化层
  • 对短任务和频繁启动的服务，这能降低资源浪费与环境准备时间
3

在同一 Linux 宿主上，多个容器共享内核，不必为每个应用启动完整操作系统。镜像公共层能够复用，部署更新只需传输变化层。对短任务和频繁启动的服务，这能降低资源浪费与环境准备时间。比较成本时必须包含镜像拉取、解压、应用启动和 Desktop 虚拟机的资源，而不能只比较 docker run 返回的时间。

容器也不会凭空增加 CPU：--cpus=1 是调度配额，不是独占一个物理核心；--memory=256m 是内存限制，不是已经为应用预留好全部容量。应用吞吐、I/O 和网络仍需测量。把资源限制设得过小，反而会造成限流和内存溢出。

2.4 容器不是银弹

3

隔离方面，共享内核意味着宿主内核漏洞和高权限容器可能扩大攻击面；高风险多租户工作负载可能需要虚拟机或专用沙箱。运维方面，容器停止并不等于数据已备份；卷能跨容器保留，却仍可能因误删、磁盘损坏或应用逻辑错误而丢失数据。安全方面，镜像来源、基础包漏洞、构建脚本、容器权限和开放端口都要管理。

此外，容器增加了网络、存储、镜像供应链与观测层。单人一次性脚本未必值得容器化；当多人协作、部署频繁、依赖复杂或需要批量复制环境时，收益才更明显。学习时先掌握单容器，再使用 Compose 编排多服务，最后按真实需求引入 Kubernetes。

3.1 环境准备与明确版本

3

本教程以 Ubuntu 22.04 LTS / 24.04 LTS、Docker Engine 29.8.2、Python 3.12.8、FastAPI 0.115.6、Uvicorn 0.34.0 为明确示例版本。Engine 29.8.2 是本次官方 Ubuntu 安装页列出的版本，不表示应长期停留在该补丁版。Buildx、Compose 和 containerd 使用官方 apt 源当前兼容稳定包，并用 dpkg-query 记录具体版本。示例所用功能不依赖 Engine 29 的特有接口。

Ubuntu：使用官方 apt 源

以下适用于全新 Ubuntu。先检查系统与现有包；如果已经运行其他 Docker/containerd 服务，先评估迁移，不能直接卸载正在承载业务的组件。

cat /etc/os-release
dpkg --print-architecture
dpkg -l docker.io docker-compose docker-compose-v2 podman-docker containerd runc 2>/dev/null || true

仅在本次准备的练习机器上，移除与官方包冲突的发行版软件包；这一步不主动删除镜像和卷，但会影响现有容器服务。随后安装证书和下载工具。

for conflict_pkg in docker.io docker-doc docker-compose docker-compose-v2 podman-docker containerd runc; do
  if dpkg-query -W -f='${Status}' "$conflict_pkg" 2>/dev/null | grep -q 'install ok installed'; then
    sudo apt-get remove -y "$conflict_pkg"
  fi
done
sudo apt-get update
sudo apt-get install -y ca-certificates curl

创建 keyrings 并导入 Docker 官方 GPG 公钥。这里下载的是公开签名验证密钥，不是个人凭据。

sudo install -m 0755 -d /etc/apt/keyrings
sudo curl -fsSL https://download.docker.com/linux/ubuntu/gpg -o /etc/apt/keyrings/docker.asc
sudo chmod a+r /etc/apt/keyrings/docker.asc

写入 /etc/apt/sources.list.d/docker.sources，这是官方当前采用的 deb822 格式。Ubuntu 22.04 使用 jammy，24.04 使用 noble；下面从系统读取，不必手工猜代号。不要同时保留指向相同地址的旧 docker.list 条目。

. /etc/os-release
case "$VERSION_ID" in
  22.04|24.04) ;;
  *) echo '本教程仅覆盖 Ubuntu 22.04 / 24.04'; exit 1 ;;
esac
sudo tee /etc/apt/sources.list.d/docker.sources >/dev/null <<EOF
Types: deb
URIs: https://download.docker.com/linux/ubuntu
Suites: ${UBUNTU_CODENAME:-$VERSION_CODENAME}
Components: stable
Architectures: $(dpkg --print-architecture)
Signed-By: /etc/apt/keyrings/docker.asc
EOF
sudo apt-get update

安装全部五个组件。先列出源中的版本；若指定补丁已经不在源中，选择列表中可用的受维护版本并同时替换 Engine 和 CLI 的版本字符串，不要从非官方站点下载未知包。

. /etc/os-release
apt-cache madison docker-ce
DOCKER_PACKAGE_VERSION="5:29.8.2-1~ubuntu.${VERSION_ID}~${UBUNTU_CODENAME:-$VERSION_CODENAME}"
sudo apt-get install -y \
  docker-ce="$DOCKER_PACKAGE_VERSION" \
  docker-ce-cli="$DOCKER_PACKAGE_VERSION" \
  containerd.io docker-buildx-plugin docker-compose-plugin
sudo systemctl enable --now docker
dpkg-query -W docker-ce docker-ce-cli containerd.io docker-buildx-plugin docker-compose-plugin

默认 Unix socket 需要管理员权限。学习机可把自己的账号加入 docker 组；它近似于授予宿主 root 权限，只能给可信账号。生产或多人机器优先评估 rootless 模式。执行后退出并重新登录；newgrp 也能临时建立新组会话。

sudo usermod -aG docker "$USER"
newgrp docker

macOS：Docker Desktop

选择 Docker Desktop 4.50.0 或更高、仍受官方维护的稳定版，这是本教程选定的版本基线，不是所有功能的最低历史版本。安装页为 https://docs.docker.com/desktop/setup/install/mac-install/ 。按 Apple Silicon（arm64）或 Intel（amd64）选择 DMG，打开后把 Docker 拖入 Applications，启动 Docker 并完成系统授权，等界面显示引擎正在运行。

官方支持当前及前两个 macOS 大版本，至少需要 4 GB 内存；本教程建议 8 GB 以上。具体组合以下载版本安装页为准，不能认为“任何 macOS 都能装最新版”。默认使用与本机 CPU 一致的镜像；跨架构仿真可能明显变慢。终端可执行下面命令启动应用，然后等待引擎就绪。

open -a Docker

Windows：Docker Desktop + WSL 2

同样选择 Docker Desktop 4.50.0 或更高的受维护稳定版。建议使用受 Microsoft 支持的 Windows 11 64 位版本；官方安装页列有 Windows 11 23H2 / build 22631 及以上的硬件基线，但不同版本是否仍受支持取决于系统版本和支持生命周期。Windows 10 22H2 / build 19045 是旧兼容基线，不应当作长期新装建议。需要 WSL 2.1.5 或更新、至少 8 GB RAM，并在 BIOS/UEFI 中开启硬件虚拟化。

在管理员 PowerShell 中执行；如果尚未安装 WSL，安装后按提示重启电脑。

wsl --install -d Ubuntu-24.04
wsl --update
wsl --set-default-version 2
wsl --version
wsl --list --verbose

从 https://docs.docker.com/desktop/setup/install/windows-install/ 下载并运行对应架构安装器，选择 WSL 2 后端。打开 Docker Desktop，在 Settings → General 启用 WSL 2 engine，在 Resources → WSL Integration 启用 Ubuntu-24.04。进入该发行版终端执行后续 Bash 操作。使用 Desktop 集成时，不要再照前面的 apt 教程在同一个 WSL 发行版安装第二套 Engine，以免 CLI 连接了错误的 socket。Windows Server 不属于 Docker Desktop 的安装目标。

三条统一自检

以下三条在已完成权限处理的 Ubuntu、macOS、WSL 终端中均适用。

docker --version
docker compose version
docker run hello-world

应看到 Docker version ...、Docker Compose version ... 和 Hello from Docker!。版本号可能比示例新。最后一个容器运行结束后显示 Exited 是正常情况。docker --version 只证明 CLI 存在；hello-world 成功才同时覆盖 daemon 连接、镜像拉取和运行链路。现在统一使用带空格的 docker compose，本地旧课件中的 docker-compose 是历史独立程序写法。

3.2 镜像管理：pull、inspect、tag、rmi3 个重点▾ 点开看本节重点
本节重点
  • 先拉取固定标签的小镜像并查看配置
  • 「inspect」 返回 JSON；用格式化选项可以单独查看镜像 ID 或摘要
  • 给同一镜像添加本地名字，再删除这个新标签
3

先拉取固定标签的小镜像并查看配置。inspect 返回 JSON；用格式化选项可以单独查看镜像 ID 或摘要。

docker pull nginx:1.28.0-alpine
docker image ls
docker image inspect nginx:1.28.0-alpine
docker image inspect --format '{{json .RepoDigests}}' nginx:1.28.0-alpine

给同一镜像添加本地名字，再删除这个新标签。tag 不会复制一套完整文件，rmi 删除标签也不一定立即释放底层空间。镜像正被容器引用时，先处理引用关系，不要惯性使用强制删除。

docker tag nginx:1.28.0-alpine local-nginx:lesson1
docker image inspect --format '{{.Id}}' local-nginx:lesson1
docker rmi local-nginx:lesson1

3.3 容器生命周期、端口和资源

3

启动一个有名字的后台容器。宿主仅绑定回环地址，浏览器打开 http://localhost:8080。映射顺序是“宿主 IP : 宿主端口 : 容器端口”；nginx 默认监听容器的 80 端口。

docker run -d --name lesson-web \
  -p 127.0.0.1:8080:80 \
  --memory=128m --cpus=0.5 \
  nginx:1.28.0-alpine
docker ps
curl -fsS http://localhost:8080

预期 run 输出容器 ID，ps 显示 Up，网页包含 Welcome to nginx!。省略 127.0.0.1 的 -p 8080:80 默认会发布到宿主所有地址，可能让局域网甚至公网访问服务。Docker 发布端口与宿主防火墙规则的交互需要单独审查，不能只凭 UFW 表面规则判断安全。

查看日志并进入容器。-i 保持标准输入，-t 分配终端；自动化脚本通常不应加 -t。Alpine 默认有 sh，未必有 bash。进入后执行 exit 退出，不会停止 nginx。

docker logs --tail 30 lesson-web
docker exec -it lesson-web sh

停止、查看、再次启动，最后删除。start 沿用已有端口与挂载设置；要修改这些设置，通常需要重新创建容器。不要把“退出交互 shell”与“停止容器主进程”混为一谈。

docker stop --time 10 lesson-web
docker ps -a
docker start lesson-web
docker logs --tail 10 lesson-web
docker stop lesson-web
docker rm lesson-web
命令 用途 容易误解的地方
docker run 创建并启动新容器 每次都创建，不是重启旧容器
docker ps -a 包括已停止容器的列表 不带 -a 只显示运行中容器
docker stop / start 停止 / 启动已有容器 停止不会删数据层
docker logs -f 跟随标准输出日志 文件日志不会自动出现在这里
docker exec -it 在运行中容器执行命令 已停止容器不能 exec
docker rm / rmi 删除容器 / 镜像引用 二者对象不同
3.4 数据卷与 bind mount3 个重点▾ 点开看本节重点
本节重点

3

命名卷由 Docker 管理，适合数据库数据；bind mount把你指定的宿主路径映射进去，适合本地源码、配置和明确管理的文件。挂载覆盖容器目标路径的视图，原来镜像中的文件不是被物理删除，而是暂时被遮住。

创建命名卷，写入文字，再创建另一个临时容器读取。两个容器都通过 --rm 自动删除，但数据仍在卷里，这就是“数据与容器分离”。

docker volume create lesson-data
docker run --rm --mount type=volume,src=lesson-data,dst=/data \
  alpine:3.21.3 sh -c 'printf "volume survives\n" > /data/note.txt'
docker run --rm --mount type=volume,src=lesson-data,dst=/data \
  alpine:3.21.3 cat /data/note.txt
docker volume inspect lesson-data

预期第二个容器输出 volume survives。卷持久化不等于备份；数据库应采用自身支持的一致性备份或正确停机后的备份流程。

下面将当前目录里的网页只读挂载到 nginx。请在 Bash 执行，Windows 使用 WSL 的 Linux 文件路径；开发项目优先放在 WSL 的 ~/ 下，避免大量小文件跨 Windows 文件系统造成性能下降。

mkdir -p "$HOME/docker-lesson-site"
printf '<h1>Hello bind mount</h1>\n' > "$HOME/docker-lesson-site/index.html"
docker run -d --name lesson-bind \
  -p 127.0.0.1:8081:80 \
  --mount "type=bind,src=$HOME/docker-lesson-site,dst=/usr/share/nginx/html,readonly" \
  nginx:1.28.0-alpine
curl -fsS http://localhost:8081
docker stop lesson-bind
docker rm lesson-bind

--mount type=bind 的源路径必须已经存在；这有助于及时发现路径拼写错误。Linux 上卷里的文件仍受 UID/GID 权限约束，非 root 应用不能因为“挂了卷”就自动拥有写权限。

逐条理解指令，尤其分清“构建时执行”和“运行时执行”。

指令 作用 常见错误及结果
FROM 指定基础镜像，开启构建阶段 用 latest，重建时基础环境悄然变化
WORKDIR 设置后续构建和启动的工作目录 拼成 WORKDOR 会报 unknown instruction
COPY 从构建上下文复制文件 企图复制上下文外的 ../secret，通常被拒绝
ENV 设置后续构建与容器默认环境变量 填入密码，值可通过镜像配置等方式暴露
EXPOSE 声明应用计划监听的端口 以为它会自动发布端口，实际仍要 -p
RUN 构建阶段执行命令并生成文件变化 RUN uvicorn ... 使构建一直占着前台
CMD 容器默认命令或默认参数 写多条期待全部执行，实际只最后一条生效
ENTRYPOINT 固定默认可执行程序 shell 形式未正确转发信号，停机拖延
USER 指定后续 RUN 和运行时的用户 切用户后再往无权限目录安装依赖

JSON 数组使用双引号，不能写成 Python 风格单引号数组。当前 Dockerfile 用 exec 形式的 CMD，Uvicorn 成为容器主进程并可接收停止信号。如果希望“镜像始终执行 uvicorn，而运行参数可替换”，可以把最后一行改成下面两行；这是替代方案，不要同时保留两套 CMD。

ENTRYPOINT ["uvicorn", "app:app"]
CMD ["--host", "0.0.0.0", "--port", "8000"]

在该方案中，docker run 镜像名 --host 0.0.0.0 --port 9000 会替换 CMD 参数；要换程序则用 --entrypoint。exec 数组不经过 shell，因此 $PORT 不会自动展开；若需要环境变量驱动端口，应让程序读取变量，或编写最后使用 exec 的入口脚本。

构建缓存为什么这样安排

层缓存依赖指令、父层与相关输入。复制的文件内容变了，这一步及其后续步骤通常需要重新计算。把 COPY . . 放在安装依赖之前，会让一次普通业务代码修改也触发重新安装所有依赖。这里先复制 requirements.txt、安装依赖，再复制 app.py；只有应用文件改变时，昂贵的依赖层有机会复用。“COPY 放后面”具体指频繁变动的源码后置，依赖清单必须先复制。

构建日志中 CACHED 表示命中缓存；pip --no-cache-dir 只关闭 pip 下载缓存，不等于关闭 Docker 层缓存。docker build --no-cache 则主动绕过层缓存；--pull 只要求检查基础镜像的新版本，不会自动更新被固定的 pip 依赖。

构建参数 用途 使用建议
-t lesson-api:1.0 设置镜像名与标签 给每个发布版本明确标签
-f Dockerfile.multistage 选择 Dockerfile 构建上下文仍由最后的路径确定
--progress=plain 展开构建日志 排查下载与构建错误
--pull 检查更新的基础镜像引用 有意更新时使用，并重新测试
--no-cache 禁用层缓存 用于诊断，日常不必总加
--build-arg NAME=value 传递已声明的 ARG 不传密钥，构建参数不是秘密通道
--platform linux/amd64 指定目标平台 需基础镜像支持，跨架构可能要仿真

最后的 . 是构建上下文，不可遗漏。Dockerfile 在哪里与构建上下文在哪里是两件事：-f 改前者，最后的路径改后者。

多阶段构建：只交付运行需要的产物

保存下面内容为 Dockerfile.multistage。builder 阶段在独立虚拟环境安装依赖，runtime 只接收虚拟环境和应用源码。两个阶段使用相同 Python、Debian 和目标架构，避免复制不兼容的二进制依赖。

FROM python:3.12.8-slim-bookworm AS builder
WORKDIR /build
ENV PIP_DISABLE_PIP_VERSION_CHECK=1
RUN python -m venv /opt/venv
COPY requirements.txt ./
RUN /opt/venv/bin/pip install --no-cache-dir -r requirements.txt

FROM python:3.12.8-slim-bookworm AS runtime
WORKDIR /app
ENV PATH="/opt/venv/bin:$PATH" \
    PYTHONDONTWRITEBYTECODE=1 \
    PYTHONUNBUFFERED=1 \
    LANG=C.UTF-8 \
    PYTHONIOENCODING=utf-8
RUN useradd --create-home --uid 10001 appuser
COPY --from=builder /opt/venv /opt/venv
COPY --chown=appuser:appuser app.py ./
USER appuser
EXPOSE 8000
HEALTHCHECK --interval=10s --timeout=3s --start-period=10s --retries=3 \
    CMD ["python", "-c", "import urllib.request; urllib.request.urlopen('http://127.0.0.1:8000/health', timeout=2)"]
CMD ["uvicorn", "app:app", "--host", "0.0.0.0", "--port", "8000"]

这个小项目没有引入编译器，多阶段版本未必显著小于单阶段版本，因为最终 Python 和依赖仍要保留。多阶段的主要价值是形成产物边界；如果某些依赖必须源码编译，gcc、头文件和开发包仅安装在 builder，运行阶段只安装必要共享库，就能明显减少工具链体积。不要以为多阶段自动删掉被复制目录里不需要的内容。

docker build --progress=plain -t lesson-api:1.0 .
docker build --progress=plain -f Dockerfile.multistage -t lesson-api:1.0-multi .
docker image ls lesson-api

4.2 docker.sock permission denied

3

症状：连接 /var/run/docker.sock 提示 permission denied，而 sudo docker ps 成功。

原因：Linux 原生 Engine 的 socket 由 root/docker 组控制，当前登录会话尚无对应组权限。Desktop 集成异常则应修复集成，不要照搬组权限处理。

修复命令（仅 Linux 原生 Engine；执行后重新登录或进入新组会话）：

sudo usermod -aG docker "$USER"
newgrp docker
docker ps

不要 chmod 666 /var/run/docker.sock，它会把近似宿主 root 的控制面开放给所有本地用户。

4.3 Cannot connect to the Docker daemon3 个重点▾ 点开看本节重点

docker info

4.5 镜像拉取超时、国内网络慢3 个重点▾ 点开看本节重点

症状：docker pull 在请求 registry、下载层时超时。

原因：DNS、代理、出口策略或 Docker Hub 网络链路异常。宿主 curl 的代理不一定自动传给 daemon；pip 下载慢也不等于镜像 registry 慢。

curl -I --connect-timeout 10 https://registry-1.docker.io/v2/
docker info

Linux 原生 Engine 可在 /etc/docker/daemon.json 合并 registry-mirrors。下面是 JSON 结构片段，域名是占位地址，必须替换为所在组织或云厂商分配并验证可用的 HTTPS 镜像加速地址；不提供未经验证的“永久免费公共加速站”。镜像加速通常针对 Docker Hub，不会自动加速所有 registry 和 apt/pip。

{
  "registry-mirrors": ["https://YOUR-MIRROR.example.com"]
}

不要把占位地址原样启用，也不要覆盖已有 JSON 中的其他设置。用编辑器合并并替换后校验；重启 daemon 可能影响业务容器，生产安排窗口。Docker Desktop 在 Settings → Docker Engine 编辑对应 JSON 并 Apply & Restart，代理在其代理设置中配置。

sudo install -d /etc/docker
sudoedit /etc/docker/daemon.json
sudo dockerd --validate --config-file=/etc/docker/daemon.json
sudo systemctl restart docker
docker pull alpine:3.21.3

docker build --progress=plain -t lesson-api:cache-check .
docker build --progress=plain -t lesson-api:cache-check .

3

3

5.1 非 root 与 Docker 组是两层权限3 个重点▾ 点开看本节重点
本节重点

  • 不要把 「/var/run/docker.sock」 随意挂进 Web 服务；也不要用 「--privileged」 解决普通文件权限问题
3

5.2 镜像瘦身与依赖兼容

3

优先减少运行时工具和无关内容，用多阶段构建隔离编译器。Debian slim 通常兼容 Python wheel，适合入门。Alpine 使用 musl，部分依赖没有对应 wheel 时会触发源码编译，最终可能又慢又大；不能只看基础镜像大小。Distroless 通常没有 shell 和包管理器，需设计调试方式，并检查 Python、共享库、证书和健康检查程序是否齐全。把 apt update、安装和清理索引放在同一 RUN，才能避免把索引留在前一层。

5.3 密钥通过运行环境或 secrets 注入3 个重点▾ 点开看本节重点
本节重点
  • 不要把密码写进 Dockerfile、ARG、ENV、源码或镜像层；「.dockerignore」 是辅助边界，不能替代审查
  • 运行时可使用受权限保护的 env 文件，但环境变量仍可能被有管理权限的人读取
  • 更敏感的内容优先使用只读挂载文件或编排平台 secrets
3

不要把密码写进 Dockerfile、ARG、ENV、源码或镜像层；.dockerignore 是辅助边界，不能替代审查。运行时可使用受权限保护的 env 文件，但环境变量仍可能被有管理权限的人读取。更敏感的内容优先使用只读挂载文件或编排平台 secrets。构建访问私有依赖应使用 BuildKit secret mount，不应通过构建参数携带 token。

下面假设你已经在本地安全准备了文件，仅引用路径，不在命令中写真实秘密。应用还必须主动读取 /run/secrets/app_config；挂载文件不会自动变成环境变量。

docker run --rm \
  --mount "type=bind,src=$HOME/.config/lesson/app_config,dst=/run/secrets/app_config,readonly" \
  lesson-api:1.0

5.4 健康检查、日志与只读根文件系统

3

HEALTHCHECK 用于提供服务状态，探针要有超时，并区分存活与就绪需求；依赖数据库短暂故障时，过度激进的存活重启可能放大故障。Docker 原生健康检查不会自动执行“摘流量、重启和告警”，这些需由编排或监控处理。

应用日志写 stdout/stderr，再由日志驱动采集。第 3.7 节已显式设置 json-file 的 max-size=10m、max-file=3。也可以在 daemon 配置中为新容器设置 local 驱动及轮转；改默认值不会自动修改已有容器。长期开启无限制日志会耗尽磁盘，即使镜像本身很小也会出事故。

--read-only 阻止写容器根文件系统；确需写入的目录通过卷或受限 --tmpfs 显式开放。示例在 /tmp 提供 64 MiB 临时空间，并关闭 Python 字节码写入。不要因为启动报只读错误就直接撤掉保护，应先确认程序到底需要写哪个目录。tmpfs 数据随容器停止丢失，不适合保存业务数据。

5.5 资源限制与 OOM3 个重点▾ 点开看本节重点
本节重点
  • 为服务设置合理的 「--memory」、「--cpus」，同时监控压力
  • 超过内存限制可能被 OOM killer 终止；退出码 137 只能说明进程收到 SIGKILL，不能单凭这一项断定 OOM，还要查看 「OOMKilled」 与宿主事件
  • 内存限制并不保证宿主有足够可用内存，多个容器的总配额仍应纳入容量规划
3

为服务设置合理的 --memory、--cpus，同时监控压力。超过内存限制可能被 OOM killer 终止；退出码 137 只能说明进程收到 SIGKILL，不能单凭这一项断定 OOM，还要查看 OOMKilled 与宿主事件。内存限制并不保证宿主有足够可用内存，多个容器的总配额仍应纳入容量规划。

docker stats --no-stream
docker inspect --format 'OOMKilled={{.State.OOMKilled}} ExitCode={{.State.ExitCode}}' lesson-api-e2e

这组命令应在第 3.7 节容器仍存在时执行；已删除则不能 inspect。不要用无限 restart 掩盖 OOM 循环。

5.6 固定镜像版本、扫描与持续更新

3

生产不要用 latest。本文的固定补丁标签便于解释，但标签仍能被发布者重新指向；更强的制品标识是经验证的 digest。通过 docker image inspect --format '{{json .RepoDigests}}' 基础镜像 获取真实摘要，再记录到构建文件中；不要复制网上随手写的假摘要。固定版本也意味着必须主动安排安全更新和回归测试，不能永远不升级。

Trivy 是独立镜像扫描工具，下面使用其官方发布的固定版本容器对本地镜像归档进行扫描，不挂载高权限 Docker socket。扫描前先确认镜像数据库下载可达；它需要下载公开漏洞数据库。--offline-scan 避免依赖识别阶段的外部 API 查询，扫描结果留在终端。

docker image save -o lesson-api-1.0.tar lesson-api:1.0
docker run --rm \
  --mount "type=bind,src=$PWD/lesson-api-1.0.tar,dst=/scan/image.tar,readonly" \
  aquasec/trivy:0.58.2 image --input /scan/image.tar \
  --scanners vuln --offline-scan --severity HIGH,CRITICAL --exit-code 1

该固定扫描器版本用于说明流程，上线时应换成当时受维护的版本。--exit-code 1 会在命中所选严重级别时返回非零，适合 CI 门禁；扫描成功不代表没有未知漏洞或配置风险。检查完按本地文件管理流程删除不再需要的镜像归档，避免重复占用空间。Trivy 的安装和策略以其官方文档 https://trivy.dev/ 为准，它不是 docker scan 子命令。

5.7 优雅停机与发布顺序3 个重点▾ 点开看本节重点
本节重点
  • 「docker stop」 通常先向主进程发送 SIGTERM，超时后再 SIGKILL
  • exec 形式 CMD/ENTRYPOINT 能避免 shell 吞掉信号；入口脚本应最终 「exec」 真正的应用
  • HTTP 服务收到终止信号后应停止接收新流量、等待正在处理的请求、释放连接
3

docker stop 通常先向主进程发送 SIGTERM，超时后再 SIGKILL。exec 形式 CMD/ENTRYPOINT 能避免 shell 吞掉信号；入口脚本应最终 exec 真正的应用。HTTP 服务收到终止信号后应停止接收新流量、等待正在处理的请求、释放连接。生产先摘除流量，再给足应用退出时间，最后删除容器。对长请求或后台作业，30 秒可能仍不够，要按业务设置。

docker stop --time 30 lesson-api-e2e

上线验收至少覆盖：镜像版本可追溯、健康接口可用、只读根目录下可启动、卷权限正确、日志受限、资源峰值可接受、SIGTERM 后能退出、数据库备份和恢复可执行。把这些做成明确检查项，容器才能真正缩短交付时间。
