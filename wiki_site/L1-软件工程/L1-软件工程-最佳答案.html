传统软件工程面对的是确定性系统（输入固定则输出固定，质量用"对/错"衡量）；AI 工程面对的是概率性系统（同一输入跑两次可能不同，质量用"好到什么程度"衡量）。这个根本差异贯穿四个环节：需求从"写清楚要什么"变成"定义什么算好"；开发从"写代码"变成"调提示词+选模型+做评估"；质量从"单测过没过"变成"评测集上的得分分布"；迭代从"改代码上线"变成"改 prompt / 换模型 / 补数据"。当 demo 走到生产，还会撞上五块硬骨头：prompt 版本化、guardrails 分层、streaming 按事件解析、成本按 OTel GenAI 记 span、观测三信号在网关统一打点——共同失败模式是"上线后再补"，出问题时什么都查不到。

环节 传统软件 AI 工程
需求 规格说明（200 或 401） 成功标准：合格阈值 + 必拦的边缘 case；先判断"问题出在内容还是风格格式"
开发 编码 → 调试 → 集成 编排四件事：模型选择 / 提示工程 / 外部知识（RAG）/ 状态管理（OpenAI 默认无状态，历史要开发者自己管）

迭代 改代码 → 跑测试 → 部署 改配方：prompt 模板（极低）→ 调温度（极低）→ 加 RAG 数据源（中）→ 换模型（中）→ 微调（高）

关键架构原则：规划最好与执行解耦——先让 Agent 生成计划，验证后才执行（对应"先评审再合并"，但在 AI 里是运行时动态验证）。

二、30 个案例沉淀的 5 个可复用骨架模式

3

跨场景反复出现的不是"业务功能"，而是共用骨架：

  1. RAG 检索增强：领域文档切块→向量化→用户提问先检索→拼进 prompt 让模型基于证据回答。任何"需要私有/最新/领域知识"的场景都适用。判断口诀："问题出在内容上 → RAG 是下一步"。
  2. Prompt 模板工程：把 prompt 从代码字符串抽成模板变量（{user_input}、{context}、{format_instructions}），同一任务备多套对比。实战细节：ChatGPT 的母语是英文，英文 prompt 更稳。
  3. 多轮对话状态管理：模型无状态，每轮把 user/assistant 消息 append 进 messages 列表；上下文窗口有限，必须设计截断/摘要策略（不能无限追加）。
  4. 结构化输出解析：prompt 里要求 JSON/固定格式，代码解析成字典（如 {"sentiment":"positive","confidence":0.8}）。这是"模型说了一大段话，我只想要几个字段"的标准解法。
  5. 外部工具调用：模型先判断意图，再调用外部 API（图像生成、语音、SQL），最后组织回答。RAG 解决"知识"，工具调用解决"行动"；"规划与执行解耦"本质是工具调用的安全版。
三、生产化五块硬骨头（demo → 生产）3 个重点▾ 点开看本节重点
本节重点
  • 1) Prompt 管理：集中存储 + 版本化（SemVer 或 commit hash，LangSmith Hub 自动生成）+ 分支实验 + 变更审批 + 每次变更自动跑回归 eval + 按版本追踪生产表现
  • 最大坑：把流当纯文本拼接——真实 provider 流是事件交错的（tool-call JSON、reasoning、usage、error 混在一条流里），必须按事件类型解析
  • 工具盘：LangSmith Hub、Portkey（MIT gateway）、Latitude、LaunchDarkly
3

1) Prompt 管理：集中存储 + 版本化（SemVer 或 commit hash，LangSmith Hub 自动生成）+ 分支实验 + 变更审批 + 每次变更自动跑回归 eval + 按版本追踪生产表现。工具盘：LangSmith Hub、Portkey（MIT gateway）、Latitude、LaunchDarkly。

2) Guardrails 分层防御（不存在一个总开关）：

层 工具 职责 延迟
① 快速输入扫描 LLM Guard（MIT，15 输入 + 20 输出扫描器） 模型跑之前拦 prompt injection / 越狱串 / 密钥，fail fast 低
② 对话流控制 NeMo Guardrails（Colang DSL，input/dialog/retrieval/execution/output 五段 rails） 保在题内、工具策略；单检查 <50ms 中
③ 输出校验 Guardrails AI（Hub 50+ validator） 结构合规、PII、毒性、JSON schema、SQL 安全 50–200ms/validator

FPR 成本意识：4% 误报率 = 每百万日活拦掉 40,000 条正常请求；15.2% = 152,000 条——选 guardrail 不能只看 F1，要把"每百万请求误伤数"算给产品看。每次 guardrail 决策必须落日志（违规类型/严重度/动作/耗时），否则合规审计拿不到证据链。

3) Streaming：SSE 是 token 传输默认（Anthropic/OpenAI/Google 都用）；生产混合 = SSE 数据面 + WebSocket 控制面（取消、用户插入反馈）。最大坑：把流当纯文本拼接——真实 provider 流是事件交错的（tool-call JSON、reasoning、usage、error 混在一条流里），必须按事件类型解析。

生产清单：每一跳禁缓冲（否则 TTFT 报废）；错误二分（首字节前失败走 HTTP 状态码 + JSON body；首字节后失败走 SSE error event，保留已渲染部分文本并标记不完整，别清屏）；取消端到端 1 秒内传播；429/5xx 指数退避 1s/2s/4s/8s，4xx 不重试；分类/审核/字段抽取这类短且要整体校验的输出直接返回 JSON（别付流式四份成本）；核心监控指标 = TTFT、TPS、错误率。

4) 成本追踪：不要围着各家 provider 原始字段建 dashboard，归一化或直接上 OpenTelemetry GenAI 语义约定。

关键属性：gen_ai.provider.name / gen_ai.request.model / gen_ai.response.model（二者可能不同）；gen_ai.usage.input_tokens / output_tokens；gen_ai.usage.cache_read.input_tokens / cache_creation.input_tokens（prompt 缓存折扣核算必需）；gen_ai.usage.reasoning.output_tokens（推理 token 单独计价）；gen_ai.response.finish_reasons（stop / tool_calls / length——区分正常结束和被截断）；自定义 llm.request_cost_usd + app.feature / app.environment / user_id 归因。

成本看板两问：spend 归因（总成本/总输入 token/总输出 token/总调用数 + 按 feature/team/模型下钻）；token 效率（cost per successful task、prompt 长度趋势——prompt bloat 是成本失控常见驱动）。

5) 观测三信号：Traces（请求跨 prompt/retrieval/tool/guardrail 完整路径）+ Metrics（聚合性能/成本/质量）+ Events（需人工复核的安全/治理告警）。

一次请求的标准 span 链：

User request → Gateway (user_id, prompt_hash, input_tokens)
  → Input Guardrails (verdict)
  → Retrieval (latency, docs count)
  → Model Provider (model call duration)
  → Tools/MCP (每次调用 = 子 span)
  → Output Guardrails (moderation verdict + cost)
  → Client (全链路带 trace_id 返回)

每请求必记字段：request_id, trace_id, timestamp, model_name + version, provider, full_prompt/full_response(按脱敏策略), latency_ms, ttft_ms, input_tokens, output_tokens, cost_usd, user_id/session_id, feature_flags, A/B variant, retrieval_sources, guardrail_verdicts, finish_reason。

⚠️ prompt/completion 内容采集默认关（OTel 官方警告敏感数据），开启前要有脱敏/访问/留存策略。

对照本库（六员 / RAG 管线）现状：

硬骨头 本库现状 落地动作
Prompt 管理 六员 prompt 散在 config/skill，无版本门禁 复用"口径回写"纪律 → 改成 prompt 版本纪律：变更 → 跑 eval → 记录版本
Guardrails 知识库侧无生产 guardrail（本地 RAG 风险低） 给客户交付时按三层起步，先算误伤成本
Streaming 非本库场景（检索为主） 交付聊天类应用时按 §三.3 清单验收
成本追踪 六员协同终局 管预算分配（模型路由 + token 三档） 接 gen_ai.usage.* 属性到六员路由日志，做逐 span 实测记账
观测 schema 无 批处理管线只需"每请求必记"精简版（query.py 检索日志）
评测联动 run_eval.py 只测检索 生产化后 guardrail verdict 与评测门禁进同一 trace

迭代杠杆使用顺序（便宜优先）：prompt 模板 → 温度 → 补 RAG 数据源 → 换模型 → 微调。先判断问题在内容（模型不知道 → RAG）还是风格格式（模型知道但表达不对 → prompt），再动杠杆。
