L1 数据库设计与 SQL 实战：约束、事务、索引与演进

← 返回总入口
本文以关系数据库为主线。可执行示例使用 Python 标准库自带的 SQLite 内存库，避免依赖外部服务；生产设计同时给出 PostgreSQL 核对入口。SQLite 与 PostgreSQL 在类型、并发和 DDL 事务等方面并不等价，不能把一方测试结果直接当成另一方上线证明。外部数据库、ORM 服务与迁移工具均未实跑。

WHY：为什么表能建出来，数据仍可能不可信

2

数据库首先管理的是业务事实及其一致性，然后才是查询速度。只靠应用代码检查，会在并发请求、后台任务、手工修复和历史版本之间留下缺口：同一个邮箱被两个请求同时注册，订单指向已不存在的用户，金额为负数，库存扣减成功而订单写入失败。此类问题不一定在 demo 中出现，却会破坏报表、计费、权限与恢复。

不做数据库工程的典型代价是：

  1. 无效数据进入系统后再清理。清洗脚本只能处理已知坏数据，无法证明新请求不会继续制造同类问题。
  2. 多步写入只完成一半。应用崩溃或网络中断后，没有事务边界就无法回答“到底扣款没有”。
  3. 靠加索引解决所有慢查询。索引占空间并增加写放大；不符合查询选择性与排序方式的索引可能根本不被采用。
  4. 改表与回滚脱节。应用回滚到旧镜像，数据库却已被新代码不可逆改写，旧版本随即无法运行。
  5. AI 输出替代事实源。模型可以把结构化记录改写得很流畅，但若没有字段约束和证据映射，简化过程可能改变原意。

旧散篇中“好设计让性能提升 10 倍”“80% 性能问题源于设计不当”没有本库可核验证据，本篇不再采用。性能要用具体查询、数据分布、执行计划和基准测试说明。

《持续交付 2.0》的目录把“数据的版本管理”放在软件配置管理中，把“低风险发布”单列一章；公开摘录提出质量应从生产过程内建。对应到数据库，就是约束在写入时生效、迁移进入版本控制、发布与回滚一起设计，而不是上线后靠人工修表。

WHAT / WHYT：设计对象、相似概念与边界

2

1. 表、约束、事务、索引分别解决什么

3
对象 核心作用 不能替代什么
表与列 表达实体、属性和数据类型 不会自动保证业务关系正确
主键/外键/UNIQUE/CHECK/NOT NULL 在数据库边界拒绝无效状态 不代替身份认证与业务授权
事务 给一组读写定义原子性、一致性与隔离边界 不自动处理分布式事务，也不等于备份
索引 为特定查询减少候选行或支持有序访问 不等于全表加速，也不免费
视图 固化查询接口、简化读取 默认不是权限系统或物化缓存
ORM 用程序对象和 API 操作数据库 不会自动设计好事务、索引和 SQL

三大范式可作为异常分析工具：1NF 关注值的原子性，2NF 关注非键属性对整个候选键的依赖，3NF 关注非键属性不应传递依赖于候选键。实际设计应从业务不变量和访问模式出发，不为“满足范式”拆出无意义表，也不为少一次 JOIN 任意复制事实。反规范化是带一致性成本的选择，应说明谁负责同步、冲突以谁为准。

2. SQL、ORM、迁移和向量检索的边界

3
  • SQL声明要读写的集合与关系，适合约束、聚合和集合操作；复杂动态查询可由查询构建器生成，但参数必须绑定。
  • ORM减少对象与关系之间的重复映射，不意味着无需看 SQL。N+1 查询、隐式事务和批量写入仍要检查。
  • 迁移把模式变化变成可审查版本；CREATE TABLE IF NOT EXISTS 不能表达重命名、拆分列、回填和删除约束。
  • 向量索引按嵌入相似性找候选内容，适合语义检索；它不能替代订单、库存等强一致事实。常见架构是关系库保存事实与权限，向量库保存可重建的检索派生物。

本地 Python 课件提供 FastAPI + SQLAlchemy + SQLite 任务 API，包含 ORM 模型、会话依赖、提交和关闭连接。本篇进一步把约束、事务和索引显式化：ORM 示例便于接 Web，但生产验收仍需查看实际 SQL 和执行计划。

3. MySQL 与 PostgreSQL 不是“简单/复杂”的性格标签

3

选型应核对具体版本下的事务与隔离、约束、索引类型、JSON、全文检索、运维工具、托管服务和团队经验。两者都能支撑常见 CRUD；不要用“MySQL 一定快、PostgreSQL 只适合复杂查询”代替基准测试。示例选 SQLite 是因为标准库可离线运行，而不是建议多实例生产服务也使用 SQLite。

4. 论文怎么说，我们怎么用

3

From Structured Records to Patient Narratives（arXiv:2610.31467）研究把结构化健康记录转成患者可读叙述时的语义漂移。论文在 4,500 份生成摘要上评估，发现显式证据约束在其设置下改善临床对齐，尤其是不确定性保留；同时可读性可能变差，遗漏效果依模型而变。

这与通用数据库设计的关系不是“所有系统都要做医疗摘要”，而是：结构化字段是事实源，生成文本是派生视图。我们在 AI 应用中应保存原始值、单位、时间、来源和不确定性，让生成结果能回指记录 ID；评估同时看忠实度、不确定性与可读性，不能只让文案更顺。本文没有复现医疗实验，也不把论文结论外推为所有领域固定收益。

HOW：用约束和事务做一个可离线验证的订单模型

2

第一步：先写业务不变量

3

示例只有用户、商品、订单和订单项，先明确六条规则：

  1. 邮箱不能为空且唯一。
  2. 商品价格非负；订单项数量必须大于零。
  3. 订单必须属于存在的用户，订单项必须引用存在的订单和商品。
  4. 创建订单与写入所有订单项要么一起成功，要么一起回滚。
  5. 常用查询是“某用户按时间倒序看订单”，索引围绕该查询设计。
  6. 金额使用定点整数的最小货币单位，例如分，避免二进制浮点累计误差。

第二步：创建完整 Python + SQLite 示例

3

保存为 db_demo.py。它使用内存数据库，每次运行都是新环境；PRAGMA foreign_keys=ON 必须对每个 SQLite 连接设置，不能假定一次设置全局生效。

import sqlite3

SCHEMA = """
CREATE TABLE users (
    id INTEGER PRIMARY KEY,
    email TEXT NOT NULL UNIQUE CHECK (length(trim(email)) > 3),
    created_at TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP
);
CREATE TABLE products (
    id INTEGER PRIMARY KEY,
    name TEXT NOT NULL,
    price_cents INTEGER NOT NULL CHECK (price_cents >= 0)
);
CREATE TABLE orders (
    id INTEGER PRIMARY KEY,
    user_id INTEGER NOT NULL REFERENCES users(id) ON DELETE RESTRICT,
    status TEXT NOT NULL CHECK (status IN ('pending', 'paid', 'cancelled')),
    created_at TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP
);
CREATE TABLE order_items (
    order_id INTEGER NOT NULL REFERENCES orders(id) ON DELETE CASCADE,
    product_id INTEGER NOT NULL REFERENCES products(id) ON DELETE RESTRICT,
    quantity INTEGER NOT NULL CHECK (quantity > 0),
    unit_price_cents INTEGER NOT NULL CHECK (unit_price_cents >= 0),
    PRIMARY KEY (order_id, product_id)
);
CREATE INDEX idx_orders_user_created
    ON orders(user_id, created_at DESC, id DESC);
"""


def connect():
    db = sqlite3.connect(":memory:")
    db.execute("PRAGMA foreign_keys = ON")
    db.executescript(SCHEMA)
    return db


def create_order(db, user_id, items):
    """items: [(product_id, quantity, unit_price_cents), ...]"""
    if not items:
        raise ValueError("订单至少需要一个商品")
    try:
        db.execute("BEGIN")
        cursor = db.execute(
            "INSERT INTO orders(user_id, status) VALUES (?, 'pending')",
            (user_id,),
        )
        order_id = cursor.lastrowid
        db.executemany(
            "INSERT INTO order_items "
            "(order_id, product_id, quantity, unit_price_cents) VALUES (?, ?, ?, ?)",
            [(order_id, product_id, quantity, price)
             for product_id, quantity, price in items],
        )
        db.commit()
        return order_id
    except Exception:
        db.rollback()
        raise


def main():
    db = connect()
    user_id = db.execute(
        "INSERT INTO users(email) VALUES (?)", ("demo@example.com",)
    ).lastrowid
    db.execute(
        "INSERT INTO products(name, price_cents) VALUES (?, ?)",
        ("键盘", 19900),
    )
    db.commit()

    # 参数绑定：即使字符串含引号，也只作为值处理。
    db.execute(
        "INSERT INTO users(email) VALUES (?)", ("o'connor@example.com",)
    )
    db.commit()

    order_id = create_order(db, user_id, [(1, 2, 19900)])
    total = db.execute(
        "SELECT SUM(quantity * unit_price_cents) FROM order_items WHERE order_id = ?",
        (order_id,),
    ).fetchone()[0]
    assert total == 39800

    # 无效外键必须使整个事务回滚，不能留下空订单。
    before = db.execute("SELECT count(*) FROM orders").fetchone()[0]
    try:
        create_order(db, user_id, [(999, 1, 100)])
    except sqlite3.IntegrityError:
        pass
    else:
        raise AssertionError("无效商品没有被外键拒绝")
    after = db.execute("SELECT count(*) FROM orders").fetchone()[0]
    assert before == after

    # 唯一约束必须在数据库层生效，而不只是应用预检查。
    try:
        db.execute("INSERT INTO users(email) VALUES (?)", ("demo@example.com",))
    except sqlite3.IntegrityError:
        db.rollback()
    else:
        raise AssertionError("重复邮箱没有被 UNIQUE 拒绝")

    plan = db.execute(
        "EXPLAIN QUERY PLAN SELECT id, status, created_at FROM orders "
        "WHERE user_id = ? ORDER BY created_at DESC, id DESC LIMIT 20",
        (user_id,),
    ).fetchall()
    print("订单总额（分）:", total)
    print("无效订单回滚: OK; 重复邮箱拦截: OK")
    print("查询计划:", plan)


if __name__ == "__main__":
    main()

运行：

python3 -I db_demo.py

成功时应输出总额 39800、两项约束检查 OK 和查询计划。查询计划会依 SQLite 版本与数据情况变化，不能只凭出现索引名就证明生产更快；要用真实规模数据对比延迟和写入成本。若要制造负例，可暂时删除 PRAGMA foreign_keys=ON 再运行，观察无效外键不再按预期被拦截；实验后恢复。

第三步：读懂查询与索引，而不是背命令

3

按用户查订单：

SELECT id, status, created_at
FROM orders
WHERE user_id = ?
ORDER BY created_at DESC, id DESC
LIMIT 20;

idx_orders_user_created(user_id, created_at DESC, id DESC) 先支持等值定位用户，再按后续字段提供有序结果。它不一定适合“只按 created_at 查全部用户”或“只按 status 过滤”的查询，因为最左列没有参与相同方式的定位。复合索引不是把每个单列索引简单拼起来。

计算订单总额：

SELECT o.id, SUM(oi.quantity * oi.unit_price_cents) AS total_cents
FROM orders AS o
JOIN order_items AS oi ON oi.order_id = o.id
WHERE o.id = ?
GROUP BY o.id;

订单项保存成交时单价，是因为商品当前价格以后可能变化。这里没有库存表和支付表，不是完整电商模型；高并发库存扣减还需要原子条件更新、隔离级别与幂等设计。

更新必须使用参数绑定：

# 推荐：值与 SQL 文本分开。
db.execute("UPDATE users SET email = ? WHERE id = ?", (new_email, user_id))

# 禁止：把用户输入直接拼接为 SQL。
# db.execute(f"UPDATE users SET email = '{new_email}' WHERE id = {user_id}")

参数绑定防 SQL 注入，但仍要做授权：user_id 合法存在，不代表当前登录者可以修改它。

第四步：从 SQLite 迁移到 PostgreSQL 时重新验收

3
  1. 核对自增主键、时间类型、布尔类型、DDL 事务和 ON DELETE 行为，不机械替换连接串。
  2. 使用 PostgreSQL 官方约束文档逐项验证 PRIMARY KEY/FOREIGN KEY/UNIQUE/CHECK/NOT NULL；约束命名，便于迁移与排错。
  3. 用 EXPLAIN (ANALYZE, BUFFERS) 在脱敏且接近生产的数据上检查实际计划；该命令会真正执行查询，写查询或生产环境须谨慎。
  4. 为连接设置合适事务隔离与超时，验证并发重复提交、死锁与重试；SQLite 内存测试覆盖不了这些。
  5. ORM 打开 SQL 日志做开发诊断，生产日志脱敏并限制开销；重点检查 N+1、隐式全表扫描和事务长期不提交。

第五步：模式演进采用可回退顺序

3

以“把 name 拆成 first_name/last_name”为例，不要在同一发布中删旧列并让新旧代码同时依赖不同结构：

  1. Expand：添加可空新列与必要约束，迁移进入版本控制。
  2. 双写/回填：新版本同时写旧列和新列；分批回填历史数据，校验行数与抽样值。
  3. 切读：确认新旧版本兼容窗口后，把读取迁到新列。
  4. 停止旧写：所有旧实例退出后再停止写旧列。
  5. Contract：经过观察期，在独立变更中删除旧列；删除前保留可恢复备份与回退方案。

数据库回滚不能只看应用镜像。备份也不等于恢复能力：定期在隔离环境恢复并跑约束、行数和关键业务查询，才算验证。

验证边界：上面的脚本只使用 SQLite 内存库，不涉及真实用户数据。PostgreSQL 的并发、执行计划、ORM 和迁移命令未实跑；任何生产性能结论都需要目标环境证据。

本库真实落地（源码核对，2026-11-04）

  • 本库真正在用的业务表是「任务总线」，DDL 全文在 scripts/sql/shared_task_bus_ddl.sql（本次读源码）：状态机、必填字段、取值范围全部交给数据库约束，而不是交给应用层自觉：
    sql state TEXT NOT NULL DEFAULT 'pending' CHECK (state IN ('pending','claimed','done','failed')), ttl_seconds INTEGER NOT NULL DEFAULT 1800 CHECK (ttl_seconds BETWEEN 60 AND 86400), -- 心跳 TTL, 默认 30min
  • 哈希字段的约束写法值得抄（同文件 L34-38）：artifact_hash TEXT CHECK (artifact_hash IS NULL OR (length(artifact_hash) = 64 AND artifact_hash NOT GLOB '*[^0-9a-f]*'))——用 CHECK 把「64 位小写 hex」写进 schema，脏数据进不来就不用在应用层到处校验。
  • 写入面收口：所有六员只经 scripts/task_bus.py 写库，docstring 明写「不直连 SQL 写库」，退出码有契约（0 成功 / 2 状态冲突(已被抢/非本人单) / 3 不存在 / 4 参数或约束拒绝）。把「约束错误」映射成独立退出码，是 SQL 层与应用层协作的好习惯。
  • 索引与查询真实用法：tasks 表建了 ix_tasks_state/ix_tasks_owner/ix_tasks_closer/ix_tasks_heartbeat 四个索引，配合 WHERE owner=? AND state=? 的抢单查询；inbox 表是 append-only（state IN ('unread','read','acked')），结果只追加不改写。
  • 和课件讲法的差异：课件的 SQL 实战以 MySQL 语法（AUTO_INCREMENT、ENGINE=InnoDB）为主；本库是 SQLite，没有引擎/字符集概念，但用到了课件里常被跳过的东西——CHECK 约束、GLOB 取反模式、FOREIGN KEY（DDL 首行 PRAGMA foreign_keys = ON）。
  • 本库暂无：知识库侧的向量数据存 Chroma（rag/index/chroma.sqlite3），没有走业务 SQL；「业务表 + 向量表联查」在本库不存在。
