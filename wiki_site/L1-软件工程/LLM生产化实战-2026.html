生产化的五块硬骨头可以压成一张表：prompt 要版本化、guardrails 要分层、streaming 要按事件解析而非拼字符串、成本要按 OpenTelemetry GenAI 约定记进 span、观测三信号（trace/metric/event）要在网关层统一打点。它们共同的失败模式是「上线后再补」——trace 没记、成本没归因、guardrail 决策没日志，出问题时什么都查不到（📰 Portkey 观测指南 / 📰 OpenObserve 监控最佳实践一致强调每请求必记日志）。

2.3 FPR 成本意识（📰 digitalapplied，一手算式）

3

4% 误报率 = 每百万日活拦掉 40,000 条正常请求；15.2% = 152,000 条 —— 选 guardrail 不能只看 F1/F 拦截率，要把「每百万请求误伤数」算出来给产品看。这与本库「错误台账按频次排优先级」是同一思路。

3

每次 guardrail 决策必须落日志：违规类型、严重度、动作（放行/改写/拦截）、耗时，可导出 SIEM（📰 getmaxim 平台对比）——否则合规审计拿不到证据链。

3.1 协议选型

3

SSE 是 token 传输的默认与主流（Anthropic/OpenAI/Google 均采用）；生产混合架构：SSE 做数据面（token 下发）+ WebSocket 做控制面（取消、用户插入反馈），避免高流量路径背上 WebSocket 的状态成本（📰 Zylos 2026 架构研究）。

3.2 最大的坑：把流当纯文本拼接2 个重点▾ 点开看本节重点
本节重点
  • 真实 provider 流是事件交错的：tool-call JSON、reasoning、usage、error 混在同一条流里
  • 不解析事件类型 → 静默损坏 tool 参数、把 reasoning 渲染进答案、把 「event: error」 当正文显示（📰 metacto 生产流文章）
3

真实 provider 流是事件交错的：tool-call JSON、reasoning、usage、error 混在同一条流里。不解析事件类型 → 静默损坏 tool 参数、把 reasoning 渲染进答案、把 event: error 当正文显示（📰 metacto 生产流文章）。必须按事件类型解析。

项 要求 来源
关缓冲 每一跳（反代/CDN/框架）都要禁缓冲，否则 TTFT 报废 📰 metacto
错误二分 首字节前失败 → HTTP 状态码 + JSON body；首字节后失败 → SSE error event；保留已渲染的部分文本并标记不完整，别清屏 📰 flaviocopes

4.3 成本看板两问（📰 OpenObserve）

3
  1. spend 归因：总成本、总输入 token、总输出 token、总调用数四个头图 + 按 feature/team/模型下钻
  2. token 效率：每次成功任务的成本（cost per successful task）、prompt 长度趋势（prompt bloat 是成本失控的常见驱动）

再配：按 user/tenant/feature 设硬预算与软告警、成本对话级追踪、FAQ 类缓存（📰 OpenObserve 监控最佳实践）。

5.1 三信号模型（📰 Portkey 2026 观测指南）

3
  • Traces：请求跨 prompt/retrieval/tool/guardrail 的完整路径
  • Metrics：聚合的性能、成本、质量
  • Events：需要人工复核的安全/治理告警
5.2 一次请求的标准 span 链（Portkey 模型）3 个重点▾ 点开看本节重点
本节重点
  • User request → Gateway : user_id, workspace, prompt_hash, input_tokens
  • → Input Guardrails : verdict(通过/拦截)
  • → Model Provider : retrieval latency, docs count, model call duration
3 
User request → Gateway          : user_id, workspace, prompt_hash, input_tokens
           → Input Guardrails   : verdict(通过/拦截)
           → Model Provider     : retrieval latency, docs count, model call duration
           → Tools/MCP          : 每次调用 = 子span(tool name, latency, success)
           → Output Guardrails  : moderation verdict + cost
           → Client             : 全链路带 trace_id 返回

5.3 Span 结构建议（📰 kunalganglani OTel agent 实践）

3
  • 一次 agent run = 一条 root trace，子 span 按 llm.generate / retrieval.query / tool.call / retry 分——这样延迟和花费能怪到正确的一步上。
  • span 名保持无聊且一致（一致性比分类学完美更重要，dashboard 依赖它）。
  • 最小自定义属性集：OTel GenAI 约定仍在 Development 阶段、名字可能变——先控制一小套自定义属性（llm.ttft_ms 等），将来再映射到稳定约定，吃 80% 价值只背 20% churn。
  • ⚠️ prompt/completion 内容采集默认关：OTel 官方警告模型内容可能含敏感数据，开启前要有脱敏/访问/留存策略（📄 OTel / 📰 Tsuga）。

硬骨头 本库/六员现状 差距
Prompt 管理 六员的 prompt 散在各自 config/skill 里，无版本门禁 有 skill 化沉淀但无「变更→跑评测→记录版本」链路；本库改动已有「口径回写」纪律可复用为 prompt 版本纪律

Streaming 非本库场景（检索为主） 交付聊天类应用时按 §3.3 清单验收
成本追踪 六员协同终局 管的是预算分配（模型路由 + token 三档） 缺 OTel GenAI 式的逐 span 实测记账；可把 gen_ai.usage.* 属性接到六员的路由日志上
观测 schema 无 本库是批处理管线，只需 Step 2「每请求必记」的精简版（query.py 的检索日志）
