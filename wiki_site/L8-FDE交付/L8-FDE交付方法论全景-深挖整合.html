FDE 是 Forward Deployed Engineer 的缩写，起源于 Palantir。到 2026 年，Anthropic、OpenAI、AWS、微软、Google Cloud 都设了类似的部门。五份素材反复强调同一个定位：售前对方案负责，咨询对建议负责，交付对验收负责，而 FDE 对生产环境里真实发生的业务结果负责。这句话是整套方法论的起点。它决定了 FDE 的工作不止于做出一个能演示的系统，而要一直做到系统在客户基础设施上稳定运行、指标真的变好。

本文把五份素材合并成一张全景图，按下面的顺序展开。

  • 骨架：Discover、Design、Deploy、Review 四阶段（简称 DDDR），每一阶段有入口条件、关键动作、出口产物和出口检查。
  • 微观循环：OpenFDE 的 FDE Loop 五步，在每个阶段内部持续运转。
  • 验收口径：4C，以及九天Hector 讲的三大核心能力。
  • 对标：Palantir 如何发明这套模式，Anthropic 如何改造。
  • 实战提炼：一个智能客服端到端项目沉淀出的三条可迁移原则。
  • 现场节奏与商业模式，以及对转岗求职者的差距清单。

先说明 FDE 和咨询、外包的本质区别，这一点在对标 Palantir 的素材里讲得最清楚。咨询是一次性交付，不影响产品。FDE 的路径叫 Gravel Road 到 Paved Highway 的反馈环：FDE 先为单个客户建一条粗糙但快速的碎石路，总部团队再把跨客户的共同模式提炼成标准功能，也就是高速公路。每个定制方案都成为产品化的原料。这套机制需要纪律，管理不好就会退化成难以规模化的纯定制，素材后面还专门列了几种退化的形态（见第十一节）。

素材也明确区分了来源口径。DDDR 和 FDE Loop 来自 VanGong1999/FDE 和 OpenFDE 的一手 GitHub 与博客原文。Palantir 部分来自 S-1/10-K 口径和官方文档。九天Hector 部分是 B站口述的 ASR 转录，观点是讲师个人的综合，不是官方口径。智能客服案例来自本地一个完整 RAG 项目的复盘。本文的整理性归纳都会标注“本文整理”，不同来源数字口径不同时并列呈现，不做裁决。

五份素材里分散出现了几类“方法被用歪”的警示，本文整理在这里，方便做交付前自查。

价值成立的前提，以及不采用这套方法的后果

2

这套方法的价值链是“找对问题—在约束内实现—证明结果—把经验变成可复用能力”。客户买的不是一个模型调用入口，而是一条可持续运行的工作流；团队要减少的也不只是首版开发时间，还包括上线返工、持续人工兜底和人员撤离后的停摆。缺少 Discover，会实现错问题；缺少 Design 的 Eval，会把演示当能力；缺少 Deploy 的运营与交接，会形成英雄交付；缺少 Review，则既无法证明价值，也无法判断该停还是该扩。

适用对象是需要进入真实组织、接入数据与权限、持续运营并接受业务验收的 AI 项目。对于输入输出已固定的简单脚本，不必照搬全部驻场节奏；对于无业务 Owner、无法建立判据或无法取得合法数据的需求，应先补条件或不做。DDDR 不是“所有项目都要排满同样周数”，4C 不是人才认证标准，FDE Loop 的参考实现也不等于可以直接生产自治的产品。

素材的总览表把四个阶段压缩成一句话和一个核心问题。Discover 是弄清真相，核心问题是谁痛、被什么指标衡量、约束是什么。Design 是把真相变成可执行计划，核心问题是做什么、不做什么、如何证明成功。Deploy 是在约束内实现并上线，核心问题是权限、数据、集成、培训、观测是否齐备。Review 是学习与杠杆，核心问题是有没有效、为什么有效、怎样复用并反馈给产品。

1.1 Discover（发现）

入口条件有两条：有赞助人，或至少有一名业务 champion；能接触到真实用户或一线操作者，而不是只有 IT 转述。第二条看似简单，却是后面失败案例里反复出现的雷区。

关键动作有五项：

  • 画干系人地图，区分出资的、使用的、否决的、维护的。
  • 梳理现状工作流，包括用时、工具、例外情况和失败代价。
  • 弄清数据与权限现实：数据在哪里，能否出域，质量如何，新鲜度如何。
  • 给出成功的可观测定义，并回答“只能选一个指标时选哪个”。
  • 明确非目标。

出口产物是发现纪要，内容涵盖问题陈述、用户、指标、约束、风险和开放问题，再加上初步的范围假设。出口检查有三条：能用一句话说清“为谁、解决什么可测问题”；知道最大的技术风险和最大的组织风险各一条；赞助人认可问题陈述，哪怕方案还没定。

这里有一个细节值得注意。出口检查要求的是赞助人认可“问题”，而不是认可“方案”。本文整理：把确认的对象前移到问题陈述，是为了让后面方案换了再换时，项目的目标不会跟着漂移。

1.2 Design（设计）

入口条件是 Discover 的出口检查已通过，并且已经对数据做过抽样或有等价的了解。关键动作有六项：

  • 方案选项至少两个，其中必须包含“不做 LLM”的选项。
  • 画架构草图，覆盖数据流、权限、人机回环和失败降级。
  • 设计 Eval：golden set 从哪里来，量规是什么。
  • 切出试点切片，由用户群、文档或流程子集、时间盒三个维度共同确定。
  • 做成本与延迟预算。
  • 列出安全与合规审查清单。

出口产物是设计一页纸、可勾选的 POC/Pilot 验收标准、风险登记与缓解措施。出口检查要求成功标准可测并和业务指标挂钩，有明确的非目标和时间盒，安全或 IT 部门至少已经看到权限与数据流。

素材给出了一条原文红线：AI 项目特别容易在 Deploy 之前假装 Design 已经完成，没有 Eval 计划就不算 Design 完成。后面的失败案例分析也反复回到这一条。

1.3 Deploy（部署）

入口条件是 Design 的验收标准已书面确认，环境、密钥、网络路径已经打通，或者有明确的阻塞项并已升级。关键动作包括：

  • 实现与集成，每次迭代都能演示。
  • 评测闭环：改动、跑 eval、看失败案例，循环往复。
  • 权限、审计、日志、告警。
  • 用户培训与 Runbook。
  • 分阶段 rollout，顺序是影子模式、建议模式、自动模式。
  • 交接计划，要回答谁值班。

出口产物是在生产或试点环境中运行的系统、观测看板与 on-call 说明，以及用户启用材料。出口检查有三条：达到书面验收线，或者有明确的“未达线但不扩大范围”的决策；回滚路径可用；至少有一名客户侧人员能独立完成主路径操作。

第三条是能力移交的最低门槛。如果只有 FDE 本人能操作系统，那这个项目离开 FDE 就会停摆，素材的反模式表里称之为英雄交付。

1.4 Review（复盘）

入口条件是试点或生产已经运行了一个约定窗口，素材举的量级是两到四周。关键动作有六项：

  • 对照指标，既看数量也看质量，包括失败案例抽样。
  • 访谈用户，了解采用障碍。
  • 复盘技术债与成本。
  • 模式化，即判断哪些内容可以进入解决方案库。
  • 产品反馈，指出平台缺什么。
  • 做决定：扩大、维持、停掉还是改方向。

出口产物是带数据的复盘文档、更新后的 Playbook，以及给产品或领导层的简报。出口检查要求有“下一轮 Discover”的输入，或者明确结项，并且知识不能只存在于个人笔记本里。

1.5 阶段之间的节奏规则

素材给出的规则很具体。允许的做法是在 Deploy 早期同时补充 Discover 的细节。禁止的做法有两条：用 Demo 的欢呼声跳过 Eval，以及用“先做了再说”跳过安全。时间盒方面，Discover 通常一到两周，窄 Pilot 通常两到六周。

最常见的翻车模式也是两条：Discover 没做完就进入 Deploy；没有 Eval 计划却宣布 Design 完成。这两条在失败案例素材里得到了印证。

这张表的解读如下。DDDR 和六阶段是同一件事的两种切分，素材给出了一一映射：六阶段的 Discover 对应 DDDR 的 Discover，Design 对应 Design，Build 对应 Deploy 里的实现，Deploy 对应 Deploy 里的上线，Prove 对应 Review，Scale 则是 Review 之后进入下一轮 Discover。六阶段在两处比 DDDR 更细。一是把“实现”和“上线”分开，Build 的核心提醒是生产可靠性比 Demo 重要，要能兼容脏 API 甚至没有 API 的系统；Deploy 的核心提醒是私有化或云、合规和文化阻力。二是单独列出 Prove，要求把效果换算成钱、风险或时间，素材称 ROI 是建立信任的关键。Scale 则要求复制到相邻部门、监控漂移与成本，并把模式回流产品。

POC、Pilot、Production 是另一个维度，它描述的是上线范围，不是工作类型。POC 是概念验证，小范围上线 MVP 功能。Pilot 是小范围试点，测试稳定性和真实业务提升。Production 是生产上线并大规模使用。本文整理：DDDR 的每个阶段里，都可以落在这三个梯度上的某一级，所以两者是交叉关系，不是替代关系。

DDDR 是人类 FDE 的项目级流程，FDE Loop 是每个阶段内部都在跑的小循环。它来自 OpenFDE 的 README 与 Agent v0.1 博客，本意是“AI Agent 作为驻场 FDE”的运行时协议，把“向专家学判断”做成机制。五步如下。

  1. OBSERVE（看）：坐在专家旁边看真实工作流。原文的说法是观察只告诉你 what。
  2. ELICIT（问）：在关键时刻追问，比如“你刚才为什么这么判断、看了什么、什么情况下会不这么做”，把 why 引出来。
  3. INDUCE（学）：归纳成判断单元，即 Judgment Unit。
  4. ACT（做）：把判断单元编译成内建治理的 Agent 配置，写操作强制要求审批，即使是 auto 模式也不能越过。
  5. EVOLVE（长）：信任是挣来的，真实结果归因加一之后，判断单元才从 suggest 升到 approve。

判断单元包含几个字段：触发情境与信号、决策、理由、被放弃的备选、反转条件、渐进自主度（suggest、approve、auto 三档），以及归因到的真实结果。素材特别强调反转条件，它只存在于专家的脑子里，不主动引出就拿不到。

循环之外还有两个“面”作为基础设施。DEPLOY 面让 Agent 真正驻进现场，包含连接器、授权、审计。ATTRIBUTION 面负责归因，回答哪一次判断真正推动了业务结果，把判断和生意连起来。

素材给出的诚实边界不能漏掉：OpenFDE Agent v0.1 是能跑、离线、确定性的参考实现，INDUCE 的抽取基于规则，判停、排序、归因都是给护城河留位的简单基线。所以它是一个方法的演示，不是成熟产品的证据。

本文整理：FDE Loop 的“渐进自主度”和 DDDR 的 Deploy 阶段“影子、建议、自动”三步 rollout 是同构的，都在表达“自动化要靠结果来换取”。后面的客服、知识库、代码助手场景全部从助手起步，原因也在这里。

四、4C 验收与三大核心能力

3

4.1 4C 四个面

OpenFDE 的《什么是FDE》把 FDE 的工作分成四个面，可以直接作为交付物的验收维度。

面 内容 验收口径
Context 深入客户真实环境：流程、数据在哪、谁有权限、谁买单、失败成本 问题不是“客户要什么功能”，而是“真正的业务结果卡在哪”
Code 亲手把方案写到生产：接数据、做检索与 Agent、处理权限与审计、部署 不是 demo、PPT 或配置，而是能在客户基础设施上真实运行的系统
Calibration 用真实业务指标和失败模式做 eval 正确率、覆盖率、越权率、人工接管率、采用率；被用起来且指标真的变好才算
Compounding 把现场反复出现的摩擦沉淀成连接器、模板、评估集和产品需求 让下一个客户更快落地

这四个面的排列有内在顺序：先理解环境，再动手实现，然后用指标校准，最后把经验回流。其中 Calibration 的五个指标里，越权率在传统软件验收里不常见，却是 AI 系统必须盯的一项。Compounding 则对应前面说的 Paved Highway：没有这一面，FDE 就只是在重复做定制。

4.2 三大核心能力

九天Hector 的口述给出另一种切法。他的核心主张是，FDE 的能力不在于掌握某几项技术，是否懂 LangChain 的所有 API、是否熟悉工具生态都不重要，重要的是知道用什么工具解决什么问题。三项能力如下。

能力一，业务理解与需求判断。 要回答三个问题：当前场景最核心的问题是什么，能不能用 AI 解决，能解决到什么程度。甲方的需求常常不明确，比如只说“提升问答准确率”，FDE 要靠技术素养和对业务的理解把问题划分清楚，并定义基线、评估指标和成功标准。他的原话大意是，不定成功标准，尾款就收不回来。口述中的示例是营销问答效率从 4 小时降到 1 小时，要先定基线 4 小时，再定成功指标、上线条件和工作范围。

能力二，Agent 开发工程化。 把方案做成完整系统，包括接入真实数据系统、处理权限和运行环境，框架不限。他强调的关键差异是：传统工程师做完功能、测试通过就结束，FDE 开发完还没有结束，还要保障上线运行并创造价值。

能力三，组织落地。 让系统进入真实组织，步骤包括部署上线、引导业务人员使用、内部培训、找试点先用、收集反馈优化、推动组织接受，最终进入真实业务流程稳定运行。交付的是“可持续生产业务价值的系统”。

三项能力不是线性分阶段使用，而是交替使用。理需求时也得懂技术才能合理设计架构。讲师还指出，软性能力同样有对应的工作流，比如“接入真实数据”属于企业集成，可以用 Palantir 的 Ontology 方法把它标准化。

4.3 两套口径怎么对上

本文整理一张对应关系。Hector 的能力一对应 4C 的 Context 加 Calibration 的前置（定基线与成功标准）。能力二对应 Code。能力三对应 Deploy 阶段的培训、交接，以及 Compounding 里的推广与回流。两套口径指向的是同一套工作内容，不同在于 4C 是验收视角，Hector 的三能力是人才视角。

素材里另一个对应点是 Anthropic 的做法：eval 套件与客户共建、门槛归客户，这与能力一里“基线与成功标准要先定”是同一个意思。

《Building Effective Agents》（2024 年 12 月）的核心说法是，最成功的实现使用简单、可组合的模式，而不是复杂框架；建议从直接调用 LLM API 写起，若使用框架必须理解底层代码。文中区分了 workflow 和 agent：workflow 是预定义代码路径的编排，agent 是由 LLM 动态决定过程与工具使用。

《Effective Context Engineering》（2025 年 9 月）的核心说法是，好的上下文工程是找到“尽可能小的一组高信号 token”。上下文是有限资源，存在 context rot 与注意力预算的问题。工具要做到“最小可用集”，原话大意是：如果人类工程师都无法明确说出某个场景该用哪个工具，也不能指望 AI agent 做得更好。

对 FDE 交付的含义，素材总结为：方案阶段先选最简单的可组合模式，包括 prompt chaining、routing、parallelization、orchestrator-workers、evaluator-optimizer，复杂度只在被证明必要时才增加。这与 Design 阶段“方案至少两个、含不做 LLM 的选项”的要求一脉相承。本文整理：二者共同的精神是把复杂度当成需要被论证的成本。

十、对转岗求职者的差距清单

3

素材把 Palantir 四要素（工程深度、领域好奇心、沟通跨度、不躲流程）、Anthropic 三合一、Hector 三能力放在一起，给转岗者（零基础转行、目标是企业 AI 降本增效方向）列了九条自查项。

硬性能力，可以通过项目补齐并展示：

  1. 生产级工程深度。要写全栈生产代码而不是 notebook，素材称这是 Anthropic 的第一道门槛，也是最需要补的课。做法是每个学习项目都按“能上线运行”的标准收尾。
  2. Eval 设计能力。能从模糊需求推导出 eval 套件，这是 Anthropic 面试必考。每个练习项目都写基线、指标、成功标准和上线条件。

软性能力，可以在日常工作和社区中练习：

  1. 客户判断。练习“访谈操作员而非高管”、把访谈限定在工作流、把转录喂回测试用例。

岗位筛选与叙事：

  1. 不要被“FDE 必须驻场、长期出差”劝退。投递时看岗位描述是否要求“对最终业务效果负责”。
  2. 面试叙事锚点：准备 Palantir 起源故事，也就是为什么传统交付在说不清需求的场景里失效；再准备一个自己的“快速交付加定成功标准”的案例。素材提到可以拿 Palantir 的案例题练手：“给你这份乱 CSV，周五交付什么？”

国内落地的两驾马车

Hector 的口述描述了国内现状，分两股力量。一是互联网科技企业，用 AI 改造既有业务流，是生产力驱动，有前沿技术基础、数据和硬件。二是政府与央国企，是更大的一股力量，由政策驱动。素材引述国务院《深入人工智能+行动指导意见》要求 2027 年前 AI 普及率达到 97%，这一数字出自讲师口述的转引。这类客户的难点是数据不能出域、必须本地部署，历史数据和系统改造接入困难。素材认为这是转岗者岗位量最大的方向，且天然要求私有化部署能力。

最典型的三个纠偏如下。

  1. 报税案例必须把个案与总体分开。“180 小时到 15 小时”是一位高级会计师的年度个案，不应改写成所有复杂税单的通用收益。原件整理版还给出试点季 7000 份、准备时间约减少三分之一、吞吐量约提升 50% 等总体口径。更值得关注的是上线初期正确字段完成率只有 25%，6 周内到 86%：成功不是因为第一版完美，而是因为自动化被限制在提取与映射层，会计师持续审核，人工修正被回收成 Eval。这直接印证 Deploy 的“先助手后自动”和 Review 的“错误回流”。
  2. NL2SQL 必须把路径与数字分开。“查询两天到分钟级、自助覆盖率 85%、重复需求减少 60%”在原件中均找不到，且原件明确写 ROI 未公开，不能对客户引用。可借鉴的是渐进路径与治理重点：先限定主题域，补表描述、主外键、枚举和指标口径，采用只读账号、行级权限、超时和扫描上限，再考虑多步分析。六阶段架构属于业界参考，不应写成“B站内部披露”。
  3. 鞋服素材案例不能把 POC 写成商用成功。合集的效率四倍、成本下降 65%、七天到两天与原件“POC、内部试用、尚未给出统一节省金额”冲突。可复用的是跟设计师和运营走流程、素材与商品信息关联、按商品一致性验收，以及“生成量不等于可发布量”。

行业调研也要求同样的口径纪律。Gartner 关于 2027 年底前超过 40% agentic AI 项目可能被取消的是预测，不是所有 AI 项目的实测失败率；S&P Global 的 42% 放弃大部分 AI 项目与 46% PoC 未进生产来自特定样本调研；RAND 的超过 80% 来自 65 名资深从业者访谈；McKinsey 的 88% 使用 AI 与 39% 报告可测利润影响说的是“采用”和“价值”的落差。它们不能平均成一个失败率，却共同支持 DDDR 的两个前置门：业务问题先确认，Eval 与基线先于扩量。

把校准变成每周动作。在每个项目的案例引用登记表中增加六列：claim、source_file、original_locator、population_and_denominator、evidence_level、allowed_use。只有能定位到原件、口径与当前项目一致的数字才可进入客户承诺；只有二手合集支持的降级为待验证假设；与原件冲突或原件明确未公开的禁用。评审时依次问：这是事实还是推演？是个案还是总体？是速度、质量还是业务收益？是 POC、试点还是生产？这四问把“来源诚实”变成方法论的执行门，而不是文末一句免责声明。

三套框架的协同关系与选型顺序

《交付总纲》把现场工作节奏写成五步。

  1. 第一周做 Discover：旁看一线、画流程图、找硬点、定非目标。
  2. 第二到六周做 Design 加窄 Pilot：写 golden set，跑通一条核心工作流，产出“可勾选”的验收标准。
  3. 部署期：分阶段 rollout，把工具嵌进员工已在使用的系统，寻找内部代言人，交付 Runbook。
  4. 运行两到四周后做 Review：对照指标复盘，把案例补回知识库，把可复用的内容沉淀成模板并反馈产品。
  5. 商业模式：第一次以小额收费的 Demo 建立信任，再以项目制交付核心场景，再以 retainer 持续优化。

定价上，素材主张按成果价值，不按工时。依据是《赢利》里的“价是本，量是末”：收多少钱决定利润的正负，做多少单只决定规模大小。素材举了一个设备维修知识库的例子：维修工每单查历史故障要 20 分钟，日耗 140 小时，AI 上线后变成看一眼 AI 提取结果、重点复核标黄项，一年省 200 万人力；若按 3 天工时报价收 2 万，等于报价被工时锚定了，没有被客户价值锚定。

三种定价模型如下。

模型 适用场景 参考逻辑
按成果定价 客户能算清省了多少人力或时间 节省的人力乘以 3 到 6 个月
按项目定价 交付物明确，如知识库搭建、流程改造 行业基准加复杂度系数

实操要点三条。第一次合作用小额 Demo 加后续转化的模式，Demo 本身也收费（素材给出 5000 到 10000 的区间），否则客户不珍惜，也筛不掉白嫖者。报价时把准确率拆成阶段：第一版做到 80%，解决 80% 的场景，后续迭代到 90%，客户预期是“第一版 80%”，做到 83% 就是超预期。中小微客户要把服务拆成标准化小模块，例如知识库梳理一次固定价、流程诊断一次固定价、月度维护月度固定费，不要报“整体 AI 改造方案”，免得被价格吓跑。

八、实战提炼：智能客服端到端的七节方法论

3

《FDE实战方法论》来自本地一个完整的智能客服 RAG 项目复盘，素材标注其性质是“从完整实战案例中提炼的通用方法论”。下面按七节整理。

需求：先划边界，再谈功能。 接到需求的第一个动作不是选模型，而是把“不做什么”写死。案例中客户想要“什么都能答”，实际交付的是只答退货、物流、商品三类，其余转人工。边界外的场景用代码硬编码为转人工，比让 Agent 自由发挥便宜得多，因为一次错误的退货承诺造成的损失，可能超过整套系统一个月的收益。SLA 要可测量：响应时间小于 3 秒、准确率大于 85% 这类指标必须配上测量方式，比如从 token 计时的首包时间、500 条人工标注评测集。RAG 主要解决外部知识与证据供给，微调主要解决经 Eval 证明的行为或任务适配；法律条文、医学指南即使更新慢，只要需要引用、权限和可追溯性，也不能默认把事实知识微调进参数。更新频率只是运营成本因素之一，不能单独决定选型。

选型：用解耦代替追新。 语言能力是通用的，知识是专属的，RAG 把两者解耦，知识更新是分钟级的，微调迭代以周计。是否引入微调要看 Eval 是否证明存在行为或任务适配需求，而不是等“RAG 做到最优”才考虑；需要引用、权限或可追溯知识时仍由 RAG/检索层承担。Embedding 选型三条标准：是否支持 dense 加 sparse 一体化，中文与垂直领域语义强度，能否本地部署。向量库按数据量和过滤需求选，十万级、简单过滤用嵌入式的 Chroma 快速验证，千万级、多条件权限过滤用服务式的 Qdrant。两者的切换应当是预案，不是返工，因为向量本身与库无关。

Demo：三天跑通“问一句、有答、带来源”。 MVP 的价值在三条保守约束：低温（temperature 不高于 0.1），拒绝发散；“资料没有就转人工”，用 prompt 显式划边界，不指望模型自觉；强制标注来源，为评测与溯源留证据链。Demo 暴露的问题，比如 chunk 粒度切散了规则，就是迭代的起点。

部署：流式输出、并发兜底、模型路由。 SSE 流式输出的意义在于主观等待时间取决于首 token 的出现，不是端到端时长。并发要用有界并发、队列上限、超时与背保护住上游，同时依据队列长度和 SLO 扩容；持续超载不能只靠排队，无界队列还会扩大内存与超时风险。模型路由按意图分级：物流查询这类高频模板化问题走小模型，退货规则这类复杂判断走大模型，边界场景根本不调 LLM。路由本身用轻量分类器，延迟小于 200 毫秒。语义缓存对高频重复 query 做 embedding 相似度命中，命中率 30% 到 40% 时能省掉三分之一以上的 LLM 费用。

成本：在架构里省钱。 月活 1 万用户的实测：全量大模型约 9360 元每月；加模型路由，75% 的请求走小模型，降到约 3700 元；再加语义缓存再省 35%，最终约 2400 元每月，合计省 74%。关键认知是省钱设计必须在写第一行 server 代码时就埋进去，等账单爆了再改，线上变更的风险大于收益。

故障复盘：幻觉的根因 80% 在检索。 案例里 AI 错答“掉色能 7 天无理由退”，表面是幻觉，根因是检索层没有召回“质量问题 15 天”那条文档。那条文档的标题是“非人为损坏说明”，不含“掉色”二字，dense embedding 对口语同义词不敏感。定位顺序应当是先查召回，也就是 top-k 里有没有正确答案，再去怪模型。修复手段是 hybrid 检索（dense 加 sparse）加 rerank 精排。性能类故障（超时）则优先查批处理凑批策略、定时任务抢占资源和上游限流，监控告警要盯队列长度，不能只看响应时间。

三条可迁移原则。

  1. 先上线再优化，但边界先划死。真实 query 分布只有上线后才暴露，但“什么必须转人工”第一天就要硬编码。
  2. 评测集优先于模型选型。与其纠结哪个模型更好，不如建一个 500 条真实 query 的标注集，每次改动都回归跑一遍。准确率是磨出来的，不是换出来的。
  3. 架构里埋省钱设计。模型路由和语义缓存是第一天的默认设计，不是事后补丁。

这三条被《交付总纲》收录为“智能客服端到端三原则”，并配上“幻觉根因 80% 在检索层”的结论。

案例一：智能客服端到端项目（本地真实实战）

这是《FDE实战方法论》的来源，也是本篇最完整的一条链路。把它放回 DDDR 框架，对应关系如下。

  • Discover：客户说想要“什么都能答”，FDE 通过划边界把需求收敛成三类问题加转人工。SLA 要求响应小于 3 秒、准确率大于 85%，并配上测量办法。
  • Design：按知识供给、引用权限与行为适配需求划分 RAG 和微调的职责，Embedding 与向量库的选型都留了切换预案。
  • Deploy：三天 Demo 加三条保守约束，之后上 SSE 流式输出、信号量限流、模型路由与语义缓存。
  • Review：用 500 条真实 query 的评测集回归，处理“掉色能 7 天无理由退”这类故障，把根因追到检索层，并以 hybrid 检索加 rerank 修复。

这个案例对方法论的贡献在三处。其一，它把“边界即安全”落到了具体的工程动作上，即边界外硬编码转人工。其二，它给出了一组可复核的成本数字：9360 元降到 3700 元再降到 2400 元，省 74%。其三，它给出了一条诊断顺序：先查召回再怪模型。素材同时标注其来源是本地实战，数字是该项目的实测，客户承诺前必须以自己项目的实测替换。

案例二：远洋保险的流程耗时表（素材转述，未独立核验）

这个案例在素材《FDE交付总纲》中被用来说明定价的锚点，也在其他篇目中用来说明 Discover 阶段如何用一张表找到 AI 的插入点。核对环节占用 20 分钟，约占单案总时长的一半，日总耗时 140 小时。AI 预读环节插入后，理赔员的动作从打开三个系统逐项核对，变成看一眼 AI 提取的结果、重点复核标黄项。

放到方法论里，这个例子说明 Discover 的出口产物应当是“能指出钱该花在哪”的数据，而不是泛泛的痛点列表。本文整理：这张表既是 Discover 的产物，也是后面 Prove 阶段对照 ROI 的基线，并且支撑了定价时的“成果锚定”。需要说明的是，本篇使用的素材对这个案例的转述限于上述数字，更完整的细节在其他篇目，此处不扩写。

案例三：制造业设备维修知识库（素材转述，未独立核验）

素材在多处提到同一个制造业例子：公司想用 AI 整理设备维修记录，初衷是让维修工能秒读历史故障和解决方案，但发现设备编码和故障分类都没有统一，AI 读不懂这些记录。外部团队进来后先做了三件事：统一设备编码和故障分类，把高频问题提炼成标准知识条目，规定提问格式和答案验收标准。

它对方法论的意义是说明 Discover 阶段要包含“数据与权限现实”的核查，而 Design 阶段在选型之前就要先决定数据治理要不要先做。在《交付总纲》里，这个例子又被用作定价案例：维修工每单查历史故障 20 分钟、日耗 140 小时，素材估算 AI 上线后一年可省 200 万人力，对应的定价错误是按 3 天工时报价 2 万。该“200 万”是素材中的价值估算，不是经独立核验的实际节省结果，而且净节省还须扣除上线后的全链路复核耗时。同一个例子在两处用于不同论点，本文原样并列，不做合并裁决。

案例四：Palantir 的起源场景

Palantir 的案例是“组织层面的案例”：客户（情报与国防机构）既说不清需求，又不能共享数据，工作流还常变，传统流程失效，于是把工程师嵌进客户环境。它的价值在于说明：Discover 不是一个可以外包给问卷的环节，在需求说不清的场景里，观察加实验加实时构建才是获得需求的方式。从结果看，素材给出了 FDE 规模超过传统工程师、2024 年营收 28.7 亿美元等公开口径数字，但这些是上市公司披露口径，不等于方法论本身的因果证明。

案例五：Anthropic 的六周节奏与访谈转测试用例

Anthropic 一侧的素材没有给具体客户案例，给的是做法：六周分五段，访谈转录里的引语、摩擦点、未解问题直接变成 eval 用例，门槛归客户。本文把它当作“方法案例”使用，用来对照 DDDR 中 Design 阶段的“Eval 设计”。素材的来源是 Perspective AI 的分析，属于第三方二手解读，使用时需要留意这一点。

小结

3

本篇把五份素材归并为一条主线：FDE 对生产环境的真实业务结果负责，用 DDDR 四阶段做项目骨架，用 FDE Loop 在每个阶段内部沉淀判断力，用 4C 和三大核心能力做验收与人才画像，用 Palantir 与 Anthropic 的做法作为外部参照，用智能客服端到端案例作为落地样本。

几条贯穿全篇的规律，本文整理如下。

  • 红线集中在入口：Discover 的出口检查、Design 的 Eval 计划，是后续所有翻车的最早可拦截点。
  • 自动化靠结果换取：影子、建议、自动的 rollout 与判断单元的 suggest、approve、auto 是同一种思想。
  • 复杂度需要论证：Anthropic 的工程共识与 Design 阶段“含不做 LLM 选项”的要求互相印证。
  • 价值要能被量化：Discover 阶段的耗时表、Prove 阶段的 ROI、定价阶段的成果锚定，三者共用同一份基线。
