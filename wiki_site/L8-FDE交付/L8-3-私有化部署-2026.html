1. 触发离线部署的典型场景

3
  • 金融 / 银行：客户合同、投研材料、风控规则，任何一跳外网都过不了等保 / 银保监。
  • 政务 / 军工：物理隔离网闸，连 HTTPS 出站都没有。
  • 大型制造业：MES / ERP 数据在工厂内网，出站被防火墙拦。
  • 医疗：HIPAA / 个保法要求 PHI 不出院。

据[一手源]：FDE私有化离线部署-外部调研-20261012 §一 / 九天Hector转录（国内落地现状）
离线部署在 2026 年不是边缘需求，三类驱动同时收敛：① 合规（GDPR、等保、金融/医疗/政务监管明确要求数据不出域）；② 客户现场（国企/军工/医院/工厂隔离区天然无外网）；③ 成本（源文引 vLLM 官方数据：7B FP16 约 14GB 显存；on-prem 每 token 成本比云低 8-18 倍；相对 Azure 按需 H100 约 3.7 个月回本。⚠️ 源文未附原始链接，对客户报 TCO 前需复核）。
国内的需求侧印证：九天Hector 口述，政府与央国企是更大一股力量（国务院要求 2027 年前 AI 普及率 97%），难点正是"数据不能出域、必须本地部署、历史系统接入难"。所以私有化不是加分项，是央国企方向 FDE 的入场券。

3. 私有化不是「小一点的云」

3

完整离线栈必须覆盖：
1. Embedding 模型（不能调 OpenAI text-embedding）
2. LLM（不能调 gpt-4o / qwen-max）
3. 向量库（不能调 Pinecone / 阿里云向量库）
4. ASR / TTS（不能调讯飞 / 阿里语音 API）
5. 所有 Docker 镜像（不能从 Docker Hub / GHCR 在线拉）
6. Python 依赖包（不能 pip install）

缺任何一环 = 项目交付不了。

1. Embedding 层：BGE-M3 是 2026 年自托管默认

3
  • 来源：BAAI，MIT 许可。
  • 关键能力：单个 checkpoint 同时支持 dense / sparse（BM25 风格）/ multi-vector（ColBERT 风格）三种检索，不用单独部署稀疏编码器（Tensoria, 2026）。
  • 基准：MTEB 检索平均分 ~54-56，开源模型第一梯队。
  • 硬件：CPU 可跑批量索引（慢但能跑），实时向量建议单卡 A10G / T4 / L4。
  • 备选：bge-reranker-v2-m3 做精排（cross-encoder）。
2. 向量库：Chroma / Qdrant / LanceDB 三选一3 个重点▾ 点开看本节重点
本节重点
  • Chroma：单机零依赖，Python 原生，适合 < 100 万 chunk 的内网知识库
  • Qdrant：要混合检索（dense+sparse）、要分片、要 filter 时升级到它
  • LanceDB：列存 + 磁盘友好，多模态（图 + 文）时选它

  • Chroma：单机零依赖，Python 原生，适合 < 100 万 chunk 的内网知识库。离线文件目录直接拷贝。
  • Qdrant：要混合检索（dense+sparse）、要分片、要 filter 时升级到它。

3. LLM 量化选型：GPTQ / AWQ / GGUF 怎么挑

3

按硬件决策（综合 Spheron 2026、GigaGPU 2026、SitePoint 2026）：

硬件 推荐格式 理由 70B 显存占用
NVIDIA 数据中心卡（A100/H100/L40S/4090） AWQ (INT4) vLLM/SGLang INT4 kernel 快，perplexity 比 GPTQ 好 1-2% ~35 GB
老 NVIDIA / 要 ExLlamaV2 生态 GPTQ (INT4) HuggingFace 上预量化模型最多 ~35 GB
消费级 / AMD / Apple Silicon / CPU GGUF Q4_K_M（llama.cpp / Ollama） CPU+GPU 混合卸载，回退能力强 ~40 GB（CPU offload）
质量敏感（微调 / 评测） FP16 / BF16 参考精度，不算部署格式 ~140 GB
  • 通用经验：AWQ 能跑就别用 GPTQ，速度快、质量好。
  • Ollama 的 q4_K_M 是 GGUF 家族里「质量/体积」甜点，9B 模型 ~5.5 GB，13B ~8 GB，32B ~20 GB。
  • 客户内网常见硬件：1× 4090（24G）或 1× A10（24G），跑 Qwen2.5-14B-AWQ / Qwen3-8B 是甜点配置。

# offline_rag.py —— 全程本地，零外网依赖
from fastapi import FastAPI
from pydantic import BaseModel
import chromadb
from sentence_transformers import SentenceTransformer, CrossEncoder
from openai import OpenAI  # 指向本地 vLLM

app = FastAPI()

# 1. 本地 embedding（CPU/GPU 都行）
embedder = SentenceTransformer("/models/bge-m3", device="cuda")
reranker = CrossEncoder("/models/bge-reranker-v2-m3", device="cuda")

# 2. 本地向量库
chroma = chromadb.PersistentClient(path="/data/chroma")
collection = chroma.get_or_create_collection("kb")

# 3. 本地 LLM（vLLM OpenAI 兼容端点）
llm = OpenAI(base_url="http://127.0.0.1:8000/v1", api_key="EMPTY")

class Query(BaseModel):
    question: str
    top_k: int = 20
    final_k: int = 5

@app.post("/ask")
def ask(q: Query):
    # dense + sparse 混合检索（BGE-M3 原生输出）
    emb = embedder.encode(q.question, return_dict=True)
    res = collection.query(
        query_embeddings=emb["dense"],
        n_results=q.top_k,
    )
    docs = res["documents"][0]

    # cross-encoder 精排
    scores = reranker.predict([(q.question, d) for d in docs])
    ranked = sorted(zip(docs, scores), key=lambda x: -x[1])[: q.final_k]
    context = "\n---\n".join([d for d, _ in ranked])

    prompt = f"""基于以下内部资料回答，不知道就说不知道。
资料：
{context}

问题：{q.question}"""
    out = llm.chat.completions.create(
        model="qwen2.5-14b-awq",
        messages=[{"role": "user", "content": prompt}],
        temperature=0.2,
    )
    return {"answer": out.choices[0].message.content, "sources": ranked}

A. 硬件 sizing 实测参考（tier 2，dev.to GDPR 指南 / iternal.ai on-prem 指南）

3
硬件 模型 速度 判断
CPU（Intel i7） llama3.2:3b ≈10 tok/s 勉强可用
CPU（Intel i7） llama3.1:8b ≈3 tok/s 太慢，不进生产
RTX 3090 24GB llama3.2:3b / llama3.1:8b ≈150 / ≈80 tok/s 流畅
RTX 3090 24GB mistral-small3.2:24b / qwen2.5:32b ≈35 / ≈25 tok/s 32B 适合 coding 类任务
- 选型口诀：没有 GPU 就别谈 8B 以上；小团队起步用二手 RTX 3060 12GB（约 €250），7B FP16 需约 14GB 显存，12GB 卡实际要走 Q4/Q8 量化。
- 量化默认选 Q4_K_M（Ollama 默认；源文引 174,500 个实例的调研，称其为最主流选择）；显存富裕、追求保真用 Q8_0；极限压缩才用 Q4_0/Q4_K_S；4-bit 相对 F16 的精度损失很小（源文举 GLM-5.2 4-bit 保留约 98% 准确率、体积降到约 430GB，⚠️ 该条未标出处，只当方向性信号）。
- 上面的速度是"单用户、单卡"数字，不代表并发吞吐；并发场景以 vLLM 压测为准，本篇验收清单的 ≥30 tok/s 指标要在客户真实硬件上重测。

B. vLLM 的「offline」≠「air-gapped」（2026-04 particula 实测，vLLM 0.19.0 / issue #39039）

3

vLLM 文档里的 "offline" 指不起 server 的批量推理，客户要的是 egress-denied（出口拒绝，不能出站）。两个概念混用，会在客户断网机房里当场翻车：
1. 模型解析链有 6 步：config.json 查找 → config 解析 → model_type 分派 → RoPE 补丁 → AutoTokenizer → 权重加载。把模型指到本地路径只能短路其中几步；较新模型在 tokenizer/processor 分支仍可能去 Hugging Face 拉文件。
2. 必须设置的开关：HF_HUB_OFFLINE=1（禁 huggingface_hub 下载）· VLLM_NO_USAGE_STATS=1（关闭 stats 遥测上报）· --enable-offline-docs（默认 False，不开则 /docs 页面会去 CDN 拉 Swagger 资产）。
3. 验证办法：不要信"本地路径能起来"，要在真实断网环境（或 iptables -A OUTPUT -j DROP）里从冷启动完整跑一遍，并抓包确认零出站。
4. 可抄模板：Elastic 官方文档给出了完整 air-gapped 示例（vLLM 0.9.1 官方镜像 + Nginx 反向代理 + 无任何出站），tier 1，可直接作为客户现场的参考架构。

常见坑

2
  1. 把 vLLM「offline」当成 air-gapped：本地路径起得来，不等于断网起得来；漏设 HF_HUB_OFFLINE / VLLM_NO_USAGE_STATS，现场冷启动会卡在联网或悄悄外发遥测（据[一手源]：FDE私有化离线部署-外部调研-20261012 §五）。
  2. pip wheel 漏包：只导了 pip install 时直接依赖，漏了 transitive。→ 用 pip download 而不是 pip freeze 拷 site-packages。
  3. PyTorch CUDA 版本错位：镜像里 torch 是 cu118，客户机器是 cu121 驱动。→ 从一开始就用官方 vLLM / PyTorch 镜像，不要自己 pip install torch。
  4. GGUF vs AWQ 混用：Ollama 只能吃 GGUF，vLLM 只能吃 AWQ/GPTQ，别想转换。→ 一开始就定推理引擎，再选量化格式。
  5. 向量库索引忘导出：ChromDB / Qdrant 的索引数据要挂载到宿主机目录，镜像重建不丢。
  6. 大镜像 U 盘拷不过：FAT32 单文件 4G 上限。→ split -b 4000M 分包，客户侧 cat part-* > bundle.tar。
