L8 Discover 执行：从现场发现到可证伪试点

三段阅读说明：WHY 先确定业务价值与不做的后果；WHYT 再看方法骨架、模式协同和取舍；HOW 最后按步骤、模板与门禁执行。为完整保留原文，原有章节编号、WHYTF 小标题和历史阅读说明均保留，重组后的顺序以三个一级标题为准。新增教学模板是合成教学案例，不是客户记录或已取得的实测结果。

WHY：以可核对的业务问题降低交付试错成本

2

FDE 项目最危险的时刻，往往不是模型答错，而是所有人对一个错误的问题达成了共识。客户说“我要 AI 客服”“我要自动审合同”“我要一个能问数据的机器人”，这些都是解决方案提议，不是可直接验收的问题。若 FDE 立即选择模型、框架和演示数据，后续每一步都在放大最初的不确定性：访谈对象错，容错标准就错；容错标准错，评测集就错；评测集错，POC 的漂亮数字就无法外推；最后只能靠人工兜底和延期维持“上线”的表象。

行业材料从不同口径指向同一风险。RAND 2024 对 65 名资深数据科学家和工程师的访谈，把业务领导层对问题的理解或传达错误列为首要根因；S&P Global 2025 的调研口径中，42% 的企业放弃大部分 AI 项目，平均 46% 的 PoC 在进入生产前被砍；Gartner 对 agentic AI 项目取消率的判断是面向 2027 年底的预测，不是实测；McKinsey 的 88% 企业使用 AI 与 39% 报告可测利润影响，则说明“用了”不等于“用出价值”。这些数字不能平均成一个失败率，却足以说明：Discover 的任务不是把需求文档写厚，而是尽早消灭会导致项目重来的未知数。

新增失败复盘把这一点进一步落到时间线上。七个失败或半失败样本的“最早检出点”都不晚于 Design/POC 验收：金融合同构造示例在 Discover 就漏掉法务；连锁零售第三方复盘在立项就只盯降本；知识库合成案例在 Design 验收时就能发现测试题由自己精选；权限合成案例在第一周就能发现超级账号；鞋服素材原件在 POC 评审时就该追问审核人手与连续使用标准。样本小，不能外推为行业统计，但操作含义很清楚：越早在现场看到真实动作，越便宜。

公开成功案例也说明了 Discover 的价值。制造业老师傅案例不是先把文档扔给模型，而是跟岗和访谈形成知识地图；律所案例发现最痛的不是找不到法条，而是整理材料；报税案例把自动化限定在提取和映射层，并从会计师修改中持续学习；鞋服案例跟设计师与运营走流程，才发现“生成量”不等于“可发布量”；NL2SQL 的真正难点是表结构、指标口径与权限，而不只是生成 SQL。它们的共同点不是用了同一个模型，而是先改写了问题。

本篇因此把 Discover 定义为一段有入口、有证据、有退出条件的工程工作：在承诺大规模交付之前，用真实用户、真实任务、真实数据和真实约束，证明“为谁解决什么可测问题”，同时证明哪些问题现在不该做。

价值、代价与适用边界

2

Discover 的业务产出不是“多了解客户”，而是让后续预算、设计与验收都锚定同一个问题：谁在真实任务里承担什么损失，现状如何测量，改变后由谁确认。把流程耗时、人工复核、数据可用性和否决权提前显性化，才能决定该投入开发，还是先治理数据、调整流程或停止立项。没有这层发现，团队可能把错误需求实现得很完整，却无法证明业务结果。

适用条件是存在具体岗位、可观察任务和愿意对问题负责的业务方，但关键约束尚未被验证。不适用边界也要写清：已有明确输入输出、可用规则闭环的小任务，不应被强行扩成驻场调研；拿不到合法样本或真实使用者时，只能交付带缺口的发现结论，不能承诺试点效果；存在不可逆动作时，Quick Win 不构成跳过安全与授权的理由。发现“不应做 AI”同样是合格产出，而不是 Discover 失败。

一、三源怎样融合成一条逻辑链

3

课件骨架提供顺序。DDDR 中，Discover 的入口是至少有赞助人或业务 Champion，并且能接触真实用户；关键动作是画干系人地图、走现状流程、确认数据与权限、定义可观测成功、写非目标；出口是发现纪要、问题陈述、指标、约束、风险与开放问题。OpenFDE 的 OBSERVE→ELICIT→INDUCE→ACT→EVOLVE 则提供微观循环：先看，再问，再归纳判断，再做小动作，最后根据真实结果提升自主度。

书籍补上“为什么会议室里的需求不可靠”。《The Mom Test》的既有二手摘要强调：谈对方的生活而非你的方案，问过去具体行为而非未来泛泛意愿，少说多听。它直接纠正“你们想要哪些功能”“你会不会用”这类诱导式问题。《流程！》的既有书摘强调识别少数核心流程、厘清每一步的人、内容、时间、地点与方式，并正视惯性；它解释了为什么 Discover 必须跟岗，而不是只收一张理想流程图。本文未读两书全文，不引用页码或虚构原话。

业内最新材料负责校准证据。Palantir 的起源经验说明，在客户无法明说需求、数据不能直接共享、工作流常变的环境里，观察、实验与实时构建比问卷更有效；Anthropic 的工程共识要求从简单可组合模式开始，工具保持最小可用集，客户访谈中的引语、摩擦点和未解问题应回到 Eval。2026 年 B 站案例对账又补充了引用纪律：22 个量化说法中，只有 2 个获得本库原件支持，4 个冲突，16 个原件无。这说明 Discover 不仅要发现客户事实，还要发现“我们引用的案例究竟能证明什么”。

三源环环相扣：课件告诉你何时做什么，书籍告诉你为什么口头需求会失真，业内材料告诉你哪些方法在现实里经受了约束、哪些数字必须降级。最终产物不是一堆链接，而是一份能指导下一步行动的证据包。

Discover 也不等于无限调研。它的终点不是“所有问题都有答案”，而是关键未知数已有证据，剩余未知数有 Owner 和补证日期，并且能选择一个窄而真的下一步。能在一天内闭环的小问题可以直接做完再复盘；涉及权限、不可逆动作、跨部门责任的大问题，不能用“小步快跑”跳过评审。

四、A-D 证据分级：事实、原话与推演不能混写

3
等级 含义 示例 使用边界
A 观察 FDE 亲眼看到的动作 理赔员在三个系统间复制两次 可进问题陈述，但注明只观察了谁、多久
B 文档 原始系统或制度记录 工单导出、审计日志、版本表 可作基线，必须写时间窗与口径
C 原话 当事人陈述 “漏审后要写情况说明” 标角色，尽量用 A/B 补证
D 推断 FDE 的解释、换算或建议 “所以法务需要 95%” 只能进待验证清单，不能冒充客户要求

常见升级路径是 C→B：对方说“上个月漏审”，就请求看情况说明或工单；A 仍不能直接外推全体：跟岗一个人只能代表这个人，至少覆盖不同资历、班次或业务类型后才能描述分布。D 不是不能写，而是必须显著标出并安排证伪。

公开案例也使用同样的诚实纪律。NL2SQL 的“两天到分钟级、85%、60%”在原件中无出处，只能禁用；报税“180 到 15 小时”必须带“个别高级会计师年度个案”限定；bili-bot 与 Lumine 没有公开 ROI，只能用于架构启发。Discover 的证据表若混入这些数字，后面的 ROI 与合同都会被污染。

五、从事实到判断单元，再到试点假设3 个重点▾ 点开看本节重点
本节重点
  • Discover 不是把观察记录直接交给开发，而要经过 INDUCE
  • 2. 判断层：在什么信号下，专家为什么选择动作 A 而非 B，何时会反转
  • Discover 的产出要把它们拆开，避免一个“准确率 90%”掩盖不同风险

Discover 不是把观察记录直接交给开发，而要经过 INDUCE。推荐固定写四层：

  1. 事实层：谁在什么系统做了什么，证据等级是什么。
  2. 判断层：在什么信号下，专家为什么选择动作 A 而非 B，何时会反转。
  3. 系统层：哪些判断可由规则、检索、模型或人工承担，各自错误代价是什么。
  4. 试验层：用哪个最小任务验证哪条假设，达到什么结果才继续，未达到怎么办。

例如“自动审合同”不是一个判断单元，而是一组异质任务：提取条款、比较模板、识别缺失、解释风险、给出处置、写回系统。提取可能可自动，风险处置可能必须人工。Discover 的产出要把它们拆开，避免一个“准确率 90%”掩盖不同风险。

试点假设必须可证伪。差的写法是“验证 AI 是否能提升法务效率”；好的写法是“两名法务在 30 份覆盖长合同和歧义条款的样本上，比较人工初审与 AI 建议后初审；记录人均时长、高风险漏检、误报和全部重看率；若漏检高于基线或复核时长未下降，则缩为条款定位助手，不进入自动风险提示”。这里没有预设一定成功，却能让下一周产生明确决策。

原文的 Palantir 经验强调从现场观察理解业务对象与动作，Anthropic 相关材料强调把摩擦点转成 Eval；九天Hector 的口述则要求先确认问题、基线和成功标准。这里把三者作为不同的约束视角：现场事实决定做什么，评测判据决定能承诺什么，业务责任决定何时推进。它们不是同一家公司的一套标准，也不能互相替代证据。

六、进场前：把访问权与证据容器准备好

3

进场前先确认四件事：业务赞助人是谁；能观察哪几个岗位；能否接触脱敏真实任务与系统；安全、法务、数据 Owner 谁有权否决。只拿到 IT 联系人，不算具备入口。

建立四个文件或目录，不需要复杂工具：

discover/
  01_stakeholder_map.md       # 角色、诉求、否决权、被考核指标
  02_evidence_register.csv    # A-D证据、来源定位、时间窗、补证Owner
  03_workflow_samples/        # 脱敏任务样本与观察记录，权限按客户要求
  04_problem_statement.md     # 问题陈述、非目标、退出线、开放问题

evidence_register.csv 至少包含：

evidence_id,role,observed_at,fact_or_quote,level,source_locator,scope,inference,next_proof,owner,due
E-001,法务专员,2026-11-03,"十条提示有一条错就全部重看",C,访谈02/第8轮,仅该受访者,"90%可能没有效率价值",调阅近20份复核记录,业务Owner,2026-11-06

示例中的内容用于说明格式，不是实际客户记录。真实项目禁止把密钥、个人信息或未授权合同复制进个人笔记。

七、第一天：跟岗、画流程、量耗时、对齐问题3 个重点▾ 点开看本节重点
本节重点
  • 上午：只观察，不急着演示
  • 》的书摘在这里变成具体检查：是否识别了少数核心流程，而不是试图全企业改造；每一步的人、内容、时间、地点与方式是否清楚；新方案是否要求用户再开系统、再记密码、改变全部习惯

上午：只观察，不急着演示。选择一名真实操作者，请求看最近一次完整任务。记录打开的系统、每次复制粘贴、等待、返工、查阅的例外规则。除安全和澄清外不打断，避免把流程引导成你希望看到的样子。

下午：把流程画成泳道。泳道至少包括一线、业务负责人、IT/数据、安全或审批者。每个节点写“谁、输入、动作、系统、输出、耗时、错误处理”。用三种标记找候选切入点：瓶颈是耗时最长，重复是相同动作多次，易错是返工或后果集中。

傍晚：拿一页纸回去核对。只写流程现状、最痛的三点、证据等级、待补问题和下一步。不要第一天承诺模型或全自动。客户否定你的推断是收益，因为 D 级假设在写码前就被证伪。

《流程！》的书摘在这里变成具体检查：是否识别了少数核心流程，而不是试图全企业改造；每一步的人、内容、时间、地点与方式是否清楚；新方案是否要求用户再开系统、再记密码、改变全部习惯。若答案为是，采用风险必须进 Top3。

三、五种发现路径：观察、追踪、对比、回收、分解

3

3.1 跟岗加知识地图：发现文档外的判断

制造业老师傅案例（Datawhale 案例整理）记载的路径是跟岗观察与主管访谈，梳理新人高频问题、易错知识点和隐性经验。其价值不在“做了 RAG”，而在先识别老师傅何时不机械照标准执行。这类反转条件通常不在手册里，只能问：“最近一次你让新人别照标准做，是什么情况？你看到了什么信号？如果信号变了，你会不会换做法？”

输出不应只有文档清单，而应有判断单元：触发信号、动作、理由、被放弃的备选、反转条件、可由谁审批。它们后续才能转成检索条目、规则或 Eval 题。原件中的带教时长与首次合格率说明，业务指标在 Discover 就已出现，不是上线后才补。

3.2 跟着职能走流程：发现角色目标不一致

鞋服素材案例（原件明确为 POC、内部试用与持续迭代）要求分别观察管理层、设计师和运营。管理层可能关心成本与产量，设计师关心改稿与可控性，运营关心商品一致性与能否发布。把三类人放进一场大会，往往只得到折中后的功能清单；分别跟随真实任务，才能看到素材散落在个人电脑、提示词各自维护、审核队列没人接等硬点。

该案例不能用来证明商用 ROI。合集里的效率四倍、成本下降 65% 与原件“尚未给出统一节省金额”冲突，Discover 阶段若拿这些数字立项，就把证据错误带进了商业目标。正确用法是提出待测指标：可发布素材率、人工审核时长、商品一致性错误率、设计师连续使用率。

3.3 现场对比验证：把口头认同变成真实任务结果

黑湖科技案例（21 世纪经济报道的本地整理）中，客户提供真实图纸，老师傅与 Agent 同场处理。“两小时对五分钟”是速度对比，不是准确率或整体效率证明。Discover 可借鉴的是试验设计：同一批任务、同一时间窗、同一验收人，事先记录质量判据，避免只比速度。

现场对比尤其适合客户无法清楚描述标准的场景。不要问“你觉得 Agent 做得怎么样”，而问“这份结果哪里不能直接用”“你会改哪几处”“哪一处错误会导致整份结果作废”。修改痕迹比赞美更接近真实验收标准。

3.4 回收使用者修正：把上线后工作变成持续访谈

报税案例（OpenAI 官方博客的本地整理版，未回溯原文）把会计师每次修改记录下来：系统提议了什么、专家改了什么、最终提交了什么。反复出现的差异再进入 Eval。上线初期正确字段完成率只有 25%，6 周内到 86%，说明系统不是一次做对，而是在窄边界、人在环和反馈回流中演进。

Discover 要提前设计这条回路：“用户每次修改记录在哪里？谁判断是否反复出现？如何脱敏？哪个版本把差异变成回归题？”如果现场没有反馈入口，Deploy 后就会失去最重要的需求来源。

3.5 按环节分解：发现最痛点不一定是最炫的功能

律所案例（Datawhale 案例整理）把受理、准备、开庭拆开，发现材料整理比法条检索更痛。操作时让使用者分别按“耗时”和“烦人程度”排序，再问“哪一步错了会让后面全部返工”。前者找量，后者找情绪与风险，硬点往往在两者的交叉处。

NL2SQL 也适用这种分解：取数需求从提出、排队、编写、执行、核对到解释，每一段的时延与返工不同。若瓶颈其实是指标口径争议，单做 SQL 生成只会让错误数字产生得更快。

九、基线：用同口径数据证明问题值得做

3

基线优先从系统记录计算，不从印象估计。以取数需求为例，先定义时间窗、任务状态和重复需求，再用 SQL 取原始明细；以下 PostgreSQL 示例需按客户 schema 修改，不可未核对字段直接执行：

SELECT
  request_id,
  requester_team,
  topic_domain,
  created_at,
  delivered_at,
  EXTRACT(EPOCH FROM (delivered_at - created_at)) / 3600.0 AS lead_hours,
  metric_name,
  dimensions,
  time_range
FROM analytics_request
WHERE created_at >= TIMESTAMPTZ '2026-10-01 00:00+00'
  AND created_at <  TIMESTAMPTZ '2026-11-01 00:00+00'
  AND status = 'delivered';

计算中位数和 P90 时保留原始明细与查询版本。若只做汇总，把同一明细查询包成 CTE，避免引用未定义关系：

WITH request_lead_time AS (
  SELECT
    request_id,
    EXTRACT(EPOCH FROM (delivered_at - created_at)) / 3600.0 AS lead_hours
  FROM analytics_request
  WHERE created_at >= TIMESTAMPTZ '2026-10-01 00:00+00'
    AND created_at <  TIMESTAMPTZ '2026-11-01 00:00+00'
    AND status = 'delivered'
)
SELECT
  percentile_cont(0.50) WITHIN GROUP (ORDER BY lead_hours) AS p50_hours,
  percentile_cont(0.90) WITHIN GROUP (ORDER BY lead_hours) AS p90_hours,
  COUNT(*) AS delivered_requests
FROM request_lead_time;

“重复需求”必须先定义，例如“同一指标、同一维度，仅时间范围不同”，再统计；不能把标题相似直接当重复。“覆盖率”必须写分子分母，“准确率”必须写判据与抽样，“平均时长”要同时看中位数和尾部。若数据不足，Discover 的下一产物就是补日志或人工抽样，不是编造一个精确数字。

基线还要包含质量护栏。客服项目不能只测成本，要同时记录投诉率、复拨率、满意度；合同项目不能只测初审时长，要测高风险漏检与误报；NL2SQL 不能只测执行成功，要测结果正确、口径一致与越权拦截。单一效率指标会诱导系统牺牲未测量的维度。

合同初审的构造示例可以这样写：一线法务需要定位与模板不符的高风险条款，当前人工通读，痛点是积压和漏标；成功不只看初审时长下降，还要求高风险漏检不高于基线；合同不出域且需要审计；非目标是自动改写合同和商务谈判建议。示例数字不能用于真实承诺，真实项目必须填自己的基线。

试点切片坚持“窄、真、可测、可退出”：一个团队、一类任务、一个主题域、一个时间盒；样本来自真实分布并含困难与负例；指标冻结；未达线有默认动作。不要用“全公司”“全量知识库”“全自动”“大家觉得好”作为第一期的四个维度。
