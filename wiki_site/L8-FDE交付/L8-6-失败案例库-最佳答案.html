坑 1：目标从立项那天就是错的

症状："项目从立项那天起，目标就是三个月后的那场汇报。"真实目的不是解决业务问题，而是给老板的老板看、给董事会汇报、给行业会议讲案例。成功标准是"有没有汇报出去"，不是"有没有人用"。
- 高层引进 AI 时预期往往很笼统——"提高效率、压一压成本"。这种模糊预期如果 FDE 不帮忙翻译成具体目标，最后就会变成"花了很多钱、做了很多 Demo、没人真用"。
- 避坑：项目启动时问清楚——这个项目要解决哪个业务环节的具体问题？解决完了哪个指标会变好？谁的工作会变轻松还是变快？答不出来的项目宁可不做。

坑 2：数据是乱的，AI 再强也救不了

症状：客户想用 AI 整理设备维修记录，结果连设备编码和故障分类都没统一，AI 根本读不懂这些记录。
- Demo 用的是你精选的 100 条数据，上线面对的是企业里真实的、混乱的、几十年积累的数据——这中间的差距就是项目失败的距离。
- 避坑：做任何 AI 应用之前先做"数据体检"——数据存在哪里？格式统一吗？谁维护？多久更新一次？数据本身脏，FDE 第一件事不是搭模型，是帮客户梳理数据（统一编码、提炼标准知识条目、规定提问格式和答案验收标准）。

坑 3：只加了 AI，没改流程

症状：在现有流程上"加一个 AI 工具"其他都不变，结果员工还是按老习惯工作，AI 工具放在那里没人打开。
- 流程落地最大挑战就是克服惯性。
- 正确姿势：远洋保险案例里，AI 预读环节插入流程后，理赔员从"打开三个系统逐项核对"变成"看一眼 AI 提取的结果、重点复核标黄项"——这才叫真落地，不是加工具，是改流程。
- 用户每天在某个系统里工作八小时，你的工具就应该出现在那个系统里，而不是要求他们再开一个网页、再记一个密码。
- 避坑：FDE 的工作不是"把 AI 塞进去"，而是"重新设计这个环节的工作方式"——哪些动作 AI 做、哪些人做、顺序怎么排、系统怎么串。如果最后员工的工作流程一点没变，这个项目就是失败的。

坑 4：Demo 效果很好，一上线就崩

症状：Demo 用精选数据、特定场景、亲自调的提示词；一到生产环境——数据量上来各种边角情况、不同用户问法五花八门、系统要实时稳定接订单/物流/会员系统。
- 避坑：Demo 只用来证明"这个方向可行"，不要用 Demo 效果直接对客户承诺生产效果。预留足够时间做从 Demo 到生产的工程化——这往往比 Demo 本身还费时。

坑 5：期望管理失控，承诺过度

症状：为了签单把效果吹上天，说"准确率能到 99%"，上线到 85%，客户觉得你失败了。
- Klarna 血的教训：一开始说 AI 能替代多少客服，结果做得过了头，服务质量下降，又重新招人工，转向"AI 处理常规、人工处理复杂"的混合模式。
- 期望值越高满意度越低，胡乱承诺会导致满意度下降。
- 避坑：宁可把效果往保守说——“先做到把物流查询这类问题自动化 70%，复杂的还是人工处理”只能作为分阶段沟通示例，不是通用目标。70%、80%、83% 等数字都必须替换为本项目冻结 Eval 与人工容量实测后的阶段门槛，不能用“超预期”话术替代真实达标。

案例 A：连锁零售 AI 客服，上线即翻车→6 个月重构（对应坑 1、坑 3、坑 4；jimo.studio 复盘）
- 背景：500+ 门店 / 500 万会员，CEO 目标"6 个月降本 40%"。
- 翻车曲线：上线头两周数据亮眼（日均 12000 通、自助解决率 75%）；6 月底客户投诉录音上热搜（播放量 50 万+）；投诉量 500→2100（+320%，源文未写统计口径与单位），满意度 87%→71%，公司反而增员 3 人处理舆情。
- 根因（源文称"三层"，实列四点）：训练数据是 3 年前的 FAQ，和现在的业务错配；情感识别准确率 <60%；流程与 KPI 没有同步重构；决策初衷是"减员"而不是"体验"。
- 修复：投诉场景 50 个关键词强制转人工 → 重新标注 2 万条数据 → "AI 班/专家班"分离 → 立伦理红线（投诉永不让 AI 独立处理）。
- 结果：自助率降到 48%，但满意度升到 94%，投诉降到 580，人员从 200 人优化到 135 人，客单价 +8%。
- 可迁移判断：前两周的漂亮指标是虚荣指标；KPI 定成"降本减员"本身就是坑 1。降自助率换满意度反而更赚钱，说明验收指标要同时盯成本和体验两端。

案例 B：3 个团队的 AI 项目死在生产环境（对应坑 4；53ai 复盘，含银行 AI 机器人）
- 教训 1：意图识别不该用大模型。银行机器人把板球赛的问题塞进利率知识库，自信地胡答 → 用小型分类器做意图识别和拒答。
- 教训 2：缓存的核心是语义匹配，不是键值对（与 FDE 交付方法论全景 的语义缓存讨论同向）。
- 教训 3：AI 应作兜底，不是核心决策者。
- 核心画面：Demo 只要 4 个方框，上线要 12+ 个组件，而且没有一个是 AI（源文未列举这 12+ 个组件；鉴权、限流、监控、降级、审计是常见例子，属自研补充）。这就是坑 4 "从 Demo 到生产往往比 Demo 本身还费时"的具体形状。

案例 C：共享财务智能审核，历史数据只有"通过单据"（对应坑 2；Fabarta 化工/制造业链主现场交付两年复盘，成功但踩坑）
- 客户要"AI 自学习审核，替代人工"，坑在历史数据只有正样本（通过的单据），没有退单、人工意见、修改痕迹，AI 无法倒推出"什么不通过"。
- 调整路径：制度规则打底 → 用通过单据做合规画像 → 人工补典型负样本 → AI 生成候选规则 → 人工确认 → 反馈闭环。验收用混淆矩阵（误拦 vs 漏拦），早期宁可谨慎。
- 经验：场景不能从技术热词里选；AI 要嵌进原工作流，不另开入口；AI-ready = 流程留痕 + 专家参与 + 反馈闭环。

HOW：交付前的失败预防清单

2
  1. 立项前：答不出"解决哪个业务环节的哪个指标"的项目不接。
  2. Discover 阶段：
    - 必须旁看一线真实工作流（不能只听管理层转述）
    - 必须做数据体检（编码/分类/更新频率）
    - 必须找到业务 owner（不是 IT 牵头人）
  3. Design 阶段：
    - 方案至少 2 个，含"不做 LLM"选项
    - 必须有 golden set + 量规 + 验收线，否则不算 Design 完成
    - 明确非目标与时间盒
    - 明确"什么必须转人工"的边界
  4. Deploy 阶段：
    - 分阶段 rollout（影子模式 → 建议模式 → 自动模式），不要一步到位
    - 工具必须嵌进员工已在用的系统（微信/钉钉/企业微信），不要要求开新网页记新密码
    - 找一个内部代言人（老板自己或愿意尝试的员工）先用起来
  5. 沟通阶段：
    - 对高层讲"省多少钱/风险多大/多久见效"，不讲 RAG 召回率
    - 对业务负责人讲"原来 2 小时现在 5 分钟"，不讲 Agent 架构
    - 承诺保守、留有余量、分阶段报指标
  6. 复盘阶段：
    - 每个项目结束必须写"我们踩了什么坑、什么信号早出现过"——回流到这个失败案例库
    - 知识不独享在个人笔记本

以下脚本演示“同排名、不同证据标注版本不得直接比分”的确定性检查，使用合成数据，不调用模型；真实复盘还需逐题人工核对。

python -I - <<'PY'
def recall_at_k(ranked, evidence, k=2):
    return len(set(ranked[:k]) & set(evidence)) / len(evidence)
ranked = ["chunk-A", "chunk-B"]
annotation_v1 = ["chunk-A"]
annotation_v2 = ["chunk-A", "chunk-C"]
r1, r2 = recall_at_k(ranked, annotation_v1), recall_at_k(ranked, annotation_v2)
assert ranked == ["chunk-A", "chunk-B"] and (r1, r2) == (1.0, 0.5)
print(f"同排名不同标注版本：v1={r1:.2f}, v2={r2:.2f}；不得直接归因于模型")
