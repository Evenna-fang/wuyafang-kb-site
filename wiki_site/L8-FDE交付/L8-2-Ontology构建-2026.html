1. 纯 RAG 的三个天花板

3
  • 读得到，改不动：向量库只能回答「文档里写了什么」，回答不了「把这张工单改派给张三会发生什么、需要谁审批、触发哪些下游」。
  • AI Agent 不敢碰真实业务：没有受控的写接口时，大模型直接调业务 API = 让实习生拿 root 连生产库。Ontology 的价值恰恰是「让 raw model 安全地指向一家真实公司」（Elementum, 2026）。
  • Dashboard 是后视镜：仪表盘告诉你「这票货迟到了」，但 Ontology 让你直接在同一张模型上执行「改路线 / 改承运商 / 通知客户」这一动作（BD Emerson, 2026）。

3. 对标

3

Palantir 官方把 Ontology 定义为「组织的数字孪生，把数据集和模型映射为 object types / properties / link types / action types」（Palantir Docs, Core Concepts）。它不是数据湖，也不是语义层 / metrics store——关键差异在 Action 层：语义层只读，Ontology 是「读 + 受控写」的合一操作层。

1. 三大原语（官方定义）

3
原语 含义 举例（物流场景）
Object Type（对象类型） 真实世界实体 / 事件的 schema 定义 Shipment、Asset、Order、Incident
Property（属性） 对象的特征字段（含主键、展示配置、时序列） Shipment.dest_city、Shipment.eta
Link Type（链接类型） 对象对之间的有类型关系 Shipment → Asset（1..N）、Order → Shipment（1..1）
Action Type（动作类型） 一次受控事务：改属性 + 改链接 + 副作用 RerouteShipment、ApproveClaim、TakeAssetOutOfService

要点（来自 Palantir 官方 anti-pattern 文档）：
- Action 是带参数、带提交校验（submission criteria）、带副作用的事务，不是「一个按钮改一个字段」。
- 命名动作要用业务动词：TransferEmployee、ApprovePurchaseOrder、EscalateSupportTicket，而不是 UpdateInventoryStatus 这种技术动作。
- 反模式：CalculateRegionalSales 这类「计算型动作」应改为每日 pipeline 聚合出一个 Summary 对象类型，而不是让用户点击触发计算。

3. 数据如何进入 Ontology

3

Palantir 的路径：Object Data Funnel 从 Foundry 数据源读取 → 索引进对象库 → 源系统更新时保持同步。在我们自建栈里等价做法：
- 业务库（MySQL / ERP / MES）→ Airflow / dbt 清洗 → 同步为对象表
- 文档库（PDF、工单）→ 切分 + 向量化，同时挂到对应的 Object 上（例如所有关于 Shipment#123 的聊天记录，都 link 到这个对象）

# ontology_server.py —— 完整可运行的 FastAPI Ontology 服务
from fastapi import FastAPI, HTTPException, Depends
from pydantic import BaseModel
import psycopg2
from psycopg2.extras import RealDictCursor
import datetime

app = FastAPI(title="Shipment Ontology Service")

DB_CONFIG = {
    "host": "localhost", "dbname": "logistics",
    "user": "ontology_app", "password": "your_password",
}

def get_db():
    conn = psycopg2.connect(**DB_CONFIG, cursor_factory=RealDictCursor)
    try:
        yield conn
    finally:
        conn.close()

class RerouteShipmentParams(BaseModel):
    shipment_id: str
    new_dest_city: str
    reason_code: str  # CUSTOMER_CHANGE / WEATHER / CARRIER_DELAY

class AssignClaimParams(BaseModel):
    claim_id: str
    assignee_id: str

# ---- Object 查询工具（Agent 调用入口）----
@app.get("/objects/{type_name}/{object_id}")
def get_object(type_name: str, object_id: str, conn=Depends(get_db)):
    """查询一个对象类型的完整属性"""
    with conn.cursor() as cur:
        cur.execute(f"SELECT * FROM {type_name.lower()} WHERE id = %s", (object_id,))
        row = cur.fetchone()
        if not row:
            raise HTTPException(404, f"{type_name} {object_id} not found")
        return dict(row)

@app.get("/objects/{type_name}/{object_id}/links/{link_type}")
def get_links(type_name: str, object_id: str, link_type: str, conn=Depends(get_db)):
    """查询对象的所有链接（如 Shipment → Orders）"""
    with conn.cursor() as cur:
        cur.execute("""
            SELECT o.* FROM orders o
            JOIN shipment_order_link l ON o.id = l.order_id
            WHERE l.shipment_id = %s
        """, (object_id,))
        return [dict(r) for r in cur.fetchall()]

# ---- Action 执行（受控写操作）----
@app.post("/actions/RerouteShipment")
def reroute_shipment(p: RerouteShipmentParams, user: str = "demo-user", conn=Depends(get_db)):
    """改运单目的地：带前置校验 + 审计日志 + 事务"""
    with conn.cursor() as cur:
        # 1. 行锁，防止并发冲突
        cur.execute("SELECT status FROM shipment WHERE id = %s FOR UPDATE", (p.shipment_id,))
        row = cur.fetchone()
        if not row:
            raise HTTPException(404, "shipment not found")
        # 2. 前置条件（submission criteria）
        if row["status"] != "IN_TRANSIT":
            raise HTTPException(409, f"shipment status={row['status']}, only IN_TRANSIT can reroute")
        if p.reason_code not in {"CUSTOMER_CHANGE", "WEATHER", "CARRIER_DELAY"}:
            raise HTTPException(400, "invalid reason_code")
        # 3. 执行动作（事务内）
        cur.execute("""
            UPDATE shipment SET dest_city = %s, updated_at = %s WHERE id = %s
        """, (p.new_dest_city, datetime.datetime.utcnow(), p.shipment_id))
        # 4. 审计日志（不可篡改）
        cur.execute("""
            INSERT INTO audit_log (user_id, action_type, object_id, payload, ts)
            VALUES (%s, %s, %s, %s, %s)
        """, (user, "RerouteShipment", p.shipment_id, p.model_dump_json(), datetime.datetime.utcnow()))
        conn.commit()
    # 5. 事务外触发副作用（webhook / 通知）
    # notify_carrier_webhook(p.shipment_id, p.new_dest_city)
    return {"ok": True, "shipment_id": p.shipment_id, "new_dest": p.new_dest_city}

@app.post("/actions/ApproveClaim")
def approve_claim(claim_id: str, user: str = "demo-user", conn=Depends(get_db)):
    """审批理赔：金额 < 10k 自动通过"""
    with conn.cursor() as cur:
        cur.execute("SELECT * FROM claim WHERE id = %s FOR UPDATE", (claim_id,))
        row = cur.fetchone()
        if not row:
            raise HTTPException(404, "claim not found")
        if row["amount"] > 10000:
            raise HTTPException(403, "amount > 10000, requires human approval")
        cur.execute("UPDATE claim SET status='APPROVED', resolved_by=%s, resolved_at=%s WHERE id=%s",
                    (user, datetime.datetime.utcnow(), claim_id))
        cur.execute("""INSERT INTO audit_log (user_id, action_type, object_id, payload, ts)
                       VALUES (%s, %s, %s, %s, %s)""",
                    (user, "ApproveClaim", claim_id, '{"auto": true}', datetime.datetime.utcnow()))
        conn.commit()
    return {"ok": True, "claim_id": claim_id, "status": "APPROVED"}

if __name__ == "__main__":
    import uvicorn
    uvicorn.run(app, host="0.0.0.0", port=8080)

阶段 0：启动前的两个判断

3
  1. 客户是否真的需要 Action 层？ 如果只是「客服查手册」「员工查制度」，纯 RAG 够了，别上 Ontology。Ontology 的成本主要在 Action + 权限 + 写回审批。
  2. 有没有一条可端到端跑通的核心工作流？ 找一条高频、跨系统、有明确「现在人工在做」的流程（例如「客诉→派单→换货→退款」），作为第一个建模对象域。

工作坊议程（建议 2 天）：
1. 业务流程 mapping：让业务方画出「谁、对哪个对象、做了什么、改了什么字段、触发谁」。产出物：一张泳道图。
2. 列出名词清单：把流程图里反复出现的名词圈出来（Shipment、Order、Customer、Asset…）。这就是候选 Object Type。
3. 列出动词清单：把流程图里反复出现的动词圈出来（Approve、Reroute、Escalate、Assign…）。这就是候选 Action Type。
4. 确认关系：每两个对象之间，关系是 1:1 / 1:N / N:N？是强约束还是弱关联？
5. 定义 Action 的提交校验：ApproveClaim 要求金额 < 10k？要求保险单在有效期内？这些规则写进 action rules。
6. 权限矩阵：哪些角色能看哪些对象、能执行哪些动作。

阶段 2：在自建栈里实现（非 Palantir 平台）

3

我们常用的等价栈：
- 对象存储：PostgreSQL（对象表）+ 关系表（链接）+ 时序表（属性历史）
- 检索增强：对象字段同时向量化（bge-m3），挂在对象 UUID 上做 RAG
- Action 执行器：FastAPI 服务，每个 Action 一个 endpoint，强制走事务 + 审计日志
- AI Agent 接口：给 Agent 暴露 query_object(type, filters)、list_links(object)、apply_action(type, params) 三个工具（Ontology MCP 思路）

A. Palantir 官方：为什么说 Ontology 不是语义层，以及落地节奏

3

据[一手源]：Anthropic-FDE与Palantir-Ontology一手-20260930（palantir.com ontology-system，tier 1）· 全球FDE对标-Palantir与AI巨头方法论-20260930 §八
- 四重整合：Data（名词，把 ERP/CRM/工业库/传感器/文档统一成对象、属性、链接）+ Action（动词，"名词要配动词才能建模决策"，实时写回运营系统）+ Logic（规则、ML 模型、LLM 函数、多引擎编排）+ Security（织入前三者，AI agent 的安全范围继承其对应人类用户或项目权限）。官方原话"The Ontology is NOT a semantic layer"，因为这四件事做不进薄语义层或单体设计。
- Language / Engine / Toolchain 三件套：Language 管建模（对象/链接/属性、动作与自动化、逻辑字面量）；Engine 管读写（读：高并发 SQL、实时订阅、人+AI 混合物化；写：原子事务、批量变更、流、CDC 低延迟镜像）；Toolchain 管应用开发（OSDK + DevOps，把 Ontology 当后端）。自建栈对应物（自研对照，非源文）：Language≈对象/动作的 schema 文件，Engine≈上文 ontology_server.py 的读写服务，Toolchain≈给 Agent 的工具函数与 SDK。
- 对象建模维度还多一个 interfaces：Foundry 官方 overview 页列的是 object types + link types + action types + interfaces（OC 图谱对标调研引用）。与本篇三大原语是同一套东西的不同切面。
- 节奏锚点（AIP bootcamp 模式）：Day 0-1 建客户领域本体（Customer/Claim/Asset 等实体 + 属性 + 链接）→ Day 2 本体接入 AIP，暴露为 LLM 可推理的工具调用 → Day 3 交付一个分析员能端到端跑完的决策流应用 → Day 4-N 按用户反馈迭代本体与工具面。对照本篇「阶段 1 定义工作坊」（自研推论）：工作坊产出的第一版对象/动作清单应在 1-2 天内能跑出一条工作流，而不是画满整个企业。
- 选型口诀：LLM 应用没有客户专属本体就失败；通用模型给通用答案，企业价值要扎根客户的"名词+动词"，这是工程，不是 prompt。

B. 图谱结构质量：交付给客户的 Ontology/知识图谱怎么验收

3

据[一手源]：FDE知识图谱全球对标调研-20261029（Medium《KG Health Assessment Part 1: Structure》Fanghua Joshua Yu，2026-05；MDPI 本体质量指标；ScienceDirect RIDE KG 密度）· OC-FDE图谱对标调研-20261029（OpenClaw 直连官方一手源，下文标注【一手】或【自研·待验证】）

核心原则：图谱质量不只是语义的，更是结构的、证据的、运行的。 7 项结构健康指标可直接当验收清单：

# 指标 健康标准 警戒信号
1 度分布/枢纽性 少数有意义枢纽 + 多数低度节点（scale-free） 枢纽是 Thing/Document/RelatedTo 之类泛化词 → 检索被污染
2 小世界/路径长度 短而有意义的路径 + 局部簇 + 桥接概念 路径过长（噪声）或过短（全靠泛化 hub）
3 模块度/社区 有意义的领域社区 过度碎片化，或语义坍缩成一团
4 语义密度（强类型边占比） 以 Drug-TREATS-Disease 这类强类型边为主 大量 RELATED_TO/共现/提及弱边 → 看着连通，无法推理
5 语义枢纽质量 高度节点保留语义 噪声枢纽应排除遍历、降权或分层
6 证据接地覆盖率 实体/断言/关系/答案均可溯源到原始材料 无证据 → 难审计、难修复（可作 release gate）
7 聚类系数 中等聚类 = 连贯局部邻域 过高（冗余）或过低（离散）
  • "深度"的判据："短不一定好。一条 2 跳的 RELATED_TO 路径，可能不如一条 4 跳的带类型、带证据的关系路径。"所以验收多跳能力，要看强边子图上的链，不能只报全图跳数。
  • 分层拓扑（GenKM 多层结构）：文档图（Document→Section→Chunk→Sentence，树/序列）· 实体图（跨文档高频实体成枢纽，重尾）· 本体图（Thing→Organization→Company→Supplier，层级/DAG）· 社区图（模块化簇）· 跨层链接（异构、有类型、有向、含溯源）。
  • 顶级图谱的五条结构标准【一手归纳】：① 边全是语义关系，共现/提及类弱边不进主图，只做候选池；② 每实体语义关系数高（Google KG >5 亿 objects、>35 亿 facts，约 7 facts/object，后者为自算）；③ 受控词汇表（Wikidata 官方 API 2026-10-29 实测 123,805,330 items、14,010 properties；Palantir 对象/链接/动作/接口；schema.org），禁止用自然语言短语直接当边；④ 层级结构 + 摘要（Microsoft GraphRAG：实体图→Leiden 分层社区→社区摘要）；⑤ 语句级溯源（Wikidata 记录"不只是陈述，还有来源"，每条语句带 sources 和 qualifiers）。
  • FDE 领域落地做法【自研·待验证，OC 提出】：受控关系表 is_a / part_of / requires / leads_to / fixes / degrades / alternative_to / deployed_on / measured_by / owned_by；把"怎么修、怎么部署"这类程序性知识建成五段式流程边型 症状 →(diagnosed_by)→ 根因 →(fixed_by)→ 处置动作 →(requires)→ 工具/权限 →(validated_by)→ 验证凭据（借 Palantir action type 的精神）；一级实体铺六类：客户场景 / 产品组件 / 部署形态 / 故障模式 / 处置 playbook / 升级路径；每条边附 provenance {source_doc, source_span, confidence, extraction_date}；用 link prediction（随机留出 10% 语义边测命中）给完备性一个可失败的指标。
  • 和本篇"克制"纪律的关系（自研综合）：上面"边要多"指的是强类型语义边要多、弱边要退出主图，不是鼓励把所有表都建模成对象。客户的操作型 Ontology 仍遵守"只建模操作面"（常见坑 4）；这里的密度/溯源指标主要用于知识型图谱（FAQ、故障库、playbook）和对 Ontology 的质量体检。

本库基线快照（2026-10-29 实测，会过期，只用于理解差距）：FDE 图谱 538 实体 / 3263 关系；弱边 mentions(1804)+co_occurs(839)=2643 条，占 81%，真语义边（bfo:instance_of、skos 族、bfo 族）约 620 条，占 19%，平均 1.15 条/实体（顶级图谱锚点 5-7）；全图直径 6 跳、平均 2.86 跳，但强边子图直径 14 跳、平均 6.29 跳，强边稀疏（平均强边度 2.55，45 个小分量长尾断裂）。结论：骨架达标，短板是知识密度，现在更像"文档共现图"而非知识图谱；行动顺序是先补内容（真语义边占比目标 50%+、每实体语义关系 ≥5、补元数据）、再做 7 项体检、最后才重建向量库。

常见坑（来自 Palantir anti-pattern 文档 + 实施经验）

2
  1. Action Sprawl：为每个字段写一个 update 动作。→ 按业务操作捆绑，一个动作 = 一次完整业务事务。
  2. Time Machine：把历史版本建成独立对象类型。→ 一个实体一个对象，历史用 linked history 对象 / 时序属性。
  3. 把计算塞进 Action：CalculateRegionalSales。→ 让 pipeline 聚合出 Summary 对象。
  4. Ontology 当数据湖用：把所有表都建模成对象。→ 只建模操作面，其余留在数据层。
  5. 权限事后补：上线前没定角色矩阵，上线后 Agent 乱调。→ Workshop 阶段就出权限矩阵。
