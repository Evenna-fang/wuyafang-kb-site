3. Palantir 三大原语（官方定义）3 个重点▾ 点开看本节重点
本节重点
  • Action 要用业务动词命名（「TransferEmployee」、「EscalateSupportTicket」），不是 「UpdateInventoryStatus」 这种技术动作
  • Action 是带提交校验、带副作用的事务，不是"一个按钮改一个字段"
  • 克制（restraint）：每条 link 都是一条有人会走的路径，也是"过期关系→错误决策"的风险点
3
原语 含义 举例（物流）
Object Type 真实实体/事件的 schema Shipment、Asset、Order、Incident
Property 对象字段（主键/展示/时序） Shipment.dest_city、Shipment.eta
Link Type 有类型的对象间关系 Shipment→Asset（1..N）、Order→Shipment（1..1）
Action Type 受控事务（改属性+改链接+副作用） RerouteShipment、ApproveClaim

关键纪律：
- Action 要用业务动词命名（TransferEmployee、EscalateSupportTicket），不是 UpdateInventoryStatus 这种技术动作。
- Action 是带提交校验、带副作用的事务，不是"一个按钮改一个字段"。
- 克制（restraint）：每条 link 都是一条有人会走的路径，也是"过期关系→错误决策"的风险点。只建模操作真正会用的关系。
- 先做透一条工作流再扩第二条：不要一次性把全企业 E-R 图倒进来。
- Ontology 变更当生产库 migration 管：版本化、权限受控。

4. 中小微企业的 Ontology：流程再造是前置

3

中小微企业的典型现状——没有标准流程、数据散在微信/Excel/脑子里、预算有限、老板要快速见效。结论：AI 改造的第一步不是选模型，是先把最核心 1-2 个流程理清楚。

四步法（《流程！》+ FDE 实战结合）：
1. 识别核心流程：找每天重复最多、最耗人力、最容易出错的 1-2 个。奶茶店老板最痛的那个就是。
2. 流程可视化：谁、什么时间、用什么工具、做什么动作、产出什么——一步一步写清楚。你自己说不清流程，AI 怎么帮你跑？
3. 找 AI 可替代的环节："查信息→判断→回复"最适合 AI；"必须人到场"先别碰。
4. 最小化上线：80%/20% 只是素材中的教学配比，不是通用承诺；实际应按冻结 Eval、错误代价与人工容量决定自动处理和转人工范围，上线后持续看数据补知识库。

最大敌人是惯性——你推出去的工具员工不用等于白干。破法：把 AI 嵌到他们已经在用的地方（微信/钉钉/企业微信），不要让员工学新工具；找一个内部代言人（老板自己或愿意尝试的员工）先用起来做出效果。

阶段 1：Definitional Workshop（定义工作坊）——最关键3 个重点▾ 点开看本节重点
本节重点
  • Palantir 实施伙伴反复强调：Ontology 质量由 workshop 决定，不由平台决定
  • 1. 业务流程 mapping：让业务方画泳道图（谁、对哪个对象、做了什么、改了什么字段、触发谁）
  • 2. 列名词清单 → 候选 Object Type
3

Palantir 实施伙伴反复强调：Ontology 质量由 workshop 决定，不由平台决定。建议 2 天议程：
1. 业务流程 mapping：让业务方画泳道图（谁、对哪个对象、做了什么、改了什么字段、触发谁）。
2. 列名词清单 → 候选 Object Type。
3. 列动词清单 → 候选 Action Type。
4. 确认关系基数（1:1 / 1:N / N:N，强约束还是弱关联）。
5. 定义 Action 提交校验（ApproveClaim 要求金额 < 10k？保险单在有效期内？）。
6. 权限矩阵：哪些角色看哪些对象、能执行哪些动作。

产出物 YAML 示例：

object_types:
  - name: Shipment
    primary_key: shipment_id
    properties: [dest_city, eta, carrier, status, weight_kg]
    links:
      - to: Order
        cardinality: N:1
        relation: "fulfills"
action_types:
  - name: RerouteShipment
    input: [shipment_id, new_dest_city, reason_code]
    preconditions:
      - "shipment.status == 'IN_TRANSIT'"
      - "reason_code in {CUSTOMER_CHANGE, WEATHER, CARRIER_DELAY}"
    effects:
      - "shipment.dest_city = new_dest_city"
      - "shipment.log.append({action: 'REROUTE', by: current_user, ts: now()})"
    side_effects:
      - notify_carrier_webhook()
    roles_allowed: [DISPATCHER, PLANNER]

阶段 2：自建栈实现（非 Palantir 平台）

3
  • 对象存储：PostgreSQL（对象表 + 关系表 + 时序表）。
  • 检索增强：对象字段同时向量化（bge-m3），挂在对象 UUID 上做 RAG。
  • Action 执行器：FastAPI 每个 Action 一个 endpoint，强制走事务 + 审计日志。
  • AI Agent 接口：只暴露三个工具——query_object(type, filters)、list_links(object)、apply_action(type, params)。禁止直连业务库。

关键代码模式（RerouteShipment）：

@app.post("/actions/RerouteShipment")
def reroute(p: RerouteShipmentParams, user: str):
    with psycopg.connect("...") as conn, conn.transaction():
        cur = conn.cursor()
        cur.execute("SELECT status FROM shipment WHERE id=%s FOR UPDATE", (p.shipment_id,))
        row = cur.fetchone()
        if not row: raise HTTPException(404)
        if row[0] != "IN_TRANSIT": raise HTTPException(409, "not in transit")
        cur.execute("UPDATE shipment SET dest_city=%s WHERE id=%s",
                    (p.new_dest_city, p.shipment_id))
        cur.execute("INSERT INTO audit_log(user, action, payload) VALUES (%s,%s,%s)",
                    (user, "RerouteShipment", p.model_dump_json()))
    # 副作用 webhook 在事务外、提交成功后再触发
    notify_carrier_webhook(p)
    return {"ok": True}

阶段 4 补充：一手源口诀（技术边界见 Ontology、私有化与多模态专项）

3
  • 据[一手源]：Palantir 官方 ontology-system 文档：Ontology 不是薄语义层，是 Data（名词）+ Action（动词）+ Logic（规则/ML/LLM 函数）+ Security（权限织入前三者，agent 继承人类权限）四重整合；由 Language / Engine / Toolchain 三件套实现。AIP 节奏：Day 0-1 建本体 → Day 2 接 AIP 暴露为工具 → Day 3 交付可跑的决策流应用 → Day 4-N 迭代。
  • 据[一手源]：FDE知识图谱全球对标调研 / OC-FDE图谱对标调研（2026-10-29）：验收知识型图谱看 7 项结构指标，最关键三项是强类型语义边占比（共现/提及弱边不进主图）、证据接地覆盖率（每条边可溯源，可作 release gate）、枢纽质量（泛化词不当枢纽）；"短不一定好"，2 跳 RELATED_TO 不如 4 跳带类型带证据的路径。
  • 验收清单加两条：[ ] 每个 link type 都是强类型、有业务含义的谓词（不是 related_to） [ ] 每个对象/关系能回指数据来源与抽取时间

常见坑（Palantir anti-patterns）

3
  1. Action Sprawl：为每个字段写一个 update 动作 → 按业务操作捆绑，一个动作 = 一次完整业务事务。
  2. Time Machine：把历史版本建成独立对象 → 一个实体一个对象，历史用 linked history / 时序属性。
  3. 把计算塞进 Action：CalculateRegionalSales → 让 pipeline 聚合出 Summary 对象。
  4. Ontology 当数据湖用：把所有表都建模成对象 → 只建模操作面，其余留数据层。
  5. 权限事后补：Workshop 阶段就出权限矩阵。

def normalize_action(name, args):

本库真实落地（源码核对，2026-11-04）

  • Ontology 的最小可行形态：人工审校三元组表（ontology/ontology-triples.csv + rag/build_wiki_graph.py L130 load_triples()，grep 可验）：
    python def load_triples() -> tuple[dict, list]: """读取人工审校三元组，返回 (entities, relations)。""" with open(TRIPLES_CSV, encoding="utf-8") as f: for row in csv.DictReader(f): sub = (row.get("subject") or "").strip() pred = (row.get("predicate") or "").strip() obj = (row.get("object") or "").strip() src = (row.get("source") or "").strip() desc = (row.get("description") or "").strip() if not (sub and pred and obj): continue
    表头就是 subject,predicate,object,source,description,wiki_ref——source 与 description 是硬字段：一条边必须能说出"为什么连"和"依据在哪"，否则不算知识。
  • 谓词受控：未登记谓词不丢但标待复核（rag/build_wiki_graph.py L416 relabel_relations()）：fam is None 时 r["in_taxonomy"] = False; r["family"] = "unmapped"，既不静默丢弃，也不让它在多跳检索里冒充结构边。
  • 和课件讲法的差异：课件 Ontology 常从 TTL/OWL 起步（类、对象属性、基数约束）；本库从 CSV 三元组起步，因为客户现场往往只有术语表和 Excel，先求"能审校、能进检索"，再谈形式化。本库暂无 OWL/TTL 解析，也没有推理机。
