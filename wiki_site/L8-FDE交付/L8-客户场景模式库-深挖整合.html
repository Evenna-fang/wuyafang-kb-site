FDE 接到一个新客户时，最省力的上手方式不是从头背一遍方法论，而是先判断这个客户属于哪一类，再直接取对应的模式：切入点是什么，交付形态长什么样，必须盯住哪几个风险点，验收线定在哪里。本篇把素材里分散在几份文档中的三类高频场景合并成一张可对照的模式库。三类场景分别是智能客服坐席助手、企业知识库的文档问答 RAG、内部研发的代码助手。

三类场景的底层逻辑高度同构，这是本篇最想让读者记住的一点。第一，三者的起步形态全部是人在回路（Human-in-the-Loop，下文简称 HITL）的助手：客服是侧栏建议加坐席确认，知识库是带引用的回答加无证据拒答，代码助手是草稿加人工评审。全自动对外发送，在三类场景里都只是 Review 之后才评审的升级选项，不是第一期可以对客户承诺的内容。第二，权限都被放在 Day 0：知识库的文档权限要在检索层强制，代码库的权限要与 Git 读权限同步，客服数据要考虑出域约束。第三，评测集都必须含负例，也就是应拒答、应升级、跨权限诱饵、密钥泄漏这类题目，没有负例的黄金集等于没有门禁。第四，本地客服复盘中出现检索未召回或过期内容时，应优先检查检索；但代码助手的不存在 API、文档过期和模型推理错误不是同一机制，不能都归因于检索。对需要版本治理的知识，生效时间和版本号是一等元数据。

素材里有一条重要的诚实说明需要先交代：三个场景案例来自 VanGong1999/FDE，原文明确标注为合成教学案例，内容是脱敏后的行业共性，不是真实客户的细节。合成模式可用于设计参考，效果必须在目标项目实测，数字只是示意值。另有两条结论（幻觉根因多在检索层、省钱设计要第一天埋进架构）来自本地一个完整智能客服 RAG 项目的复盘，素材称之为本地真实实战经验。本文在引用数字时，会尽量标明出处属于哪一边。

本文结构如下：先给场景速查表，再分别展开三类场景，然后做横向对比和共性规则，接着整理面对客户常见说法时的应答，最后与实战方法论、交付模板库衔接，并单设案例章节把三个合成案例逐个讲完整。

复用什么，以及什么不能复用

2

模式库降低的是“从哪里开始、先防什么风险”的决策成本，不是把客户差异抹平。可复用的是流程切入点、权限位置、失败降级和评测设计；不可直接复用的是样本量、上线周数、阈值、采用率或成本收益。跳过这个区分，客服侧栏会被承诺成全自动，知识库会先全量接入再补权限，代码草稿会被误认为可直接合并，NL2SQL 则可能把可执行 SQL 当成正确经营结论。

适用条件是已有明确任务、权威数据源和业务 Owner，可以在有限范围对照验证。不属于本库模式的需求，不硬套四张卡；任务本身无判据、权限来源不清或无法接触真实使用者时，先回到 Discover。高风险业务动作没有确认责任与人工接管之前，任何模式都不构成自动化许可。

六、共性硬规则

3

素材总结了五条三场景共用的规则。前三条在案例库中已有详述，后两条是场景模式库额外强调的，这里放在一起按因果关系整理。

  1. 先助手后自动。三个场景的原文模式全部是 HITL 助手起步，全自动是 Review 之后的升级选项，不是对客户的第一期承诺。这是 FDE 交付中最容易被管理层施压违背的原则。
  2. 权限是 Day 0。知识库权限在检索层强制，代码库权限与 Git 同步，客服数据有出域约束；任何一个被放到项目后期处理，都会演变成安全事故或返工。
  3. 指标用业务语言。客服看首次解决率、平均处理时长、采纳率、满意度；知识库看自助解决率、专家升级次数、答后满意度；代码助手看首个有效 PR 时间、找代码耗时。素材明确反对使用“机器人回复条数”这类虚荣指标。
  4. 评测集必须含负例。应拒答、应升级、跨权限诱饵、密钥红队，这些构成真正的门禁。没有负例的黄金集，等于没有门禁。
  5. 生效时间与版本是一等元数据。客服活动窗口与制度版本需要显式治理；代码助手还要分别排查过时注释、未召回代码和模型虚构 API，不能把三种问题都归因于过期检索。

本文整理的因果链是：因为答错的后果不可控，所以先助手后自动；因为助手要从多个数据源取内容，所以权限必须前置；因为要证明助手可靠，所以要有含负例的评测集；因为评测集和线上都要避免旧内容，所以版本与时间是元数据；因为最终要让业务方买账，所以用业务语言报指标。五条规则互相支撑，缺一条则其余几条会失效。

实战方法论来自本地一个完整的智能客服 RAG 项目复盘，它为场景模式库提供了三个可迁移的原则，也解释了前文的许多数字背后的理由。

第一，幻觉的根因八成在检索。方法论里的故障复盘是这样的：系统错误地回答“掉色可以七天无理由退”，表面看是幻觉，根因是检索层根本没有召回“质量问题十五天”那条文档，那条文档的标题是“非人为损坏说明”，不含“掉色”二字，而纯语义检索对口语同义词不够敏感。定位顺序应当是先查召回，也就是前 k 个候选里有没有正确答案，再去怪模型。修复手段是混合检索加精排，把口语化提问真正相关的文档顶到第一位。性能类故障（比如超时）则优先查批处理凑批策略、定时任务抢占资源和上游限流，监控要盯队列长度而不只是响应时间。

第二，边界即安全。真正交付的不是“什么都能答”，而是“只答退货、物流、商品三类，其余转人工”。边界外的场景用代码硬编码转人工。SLA 也要可测量，比如响应时间小于三秒、准确率大于 85%，同时要配测量方式，比如首个字符出现时间从令牌计时、用 500 条人工标注评测集，否则无法验收也无法迭代。

第三，架构里埋省钱设计，即第二节的成本阶梯。方法论还解释了几个部署细节：流式输出让用户感知的等待时间等于首字出现时间而不是端到端时长；并发用有界信号量、队列上限、超时与背保护住上游，持续超载还要依据队列长度和 SLO 扩容，不能只用无界排队，超时则降级转人工；高频模板化问题（物流查询）走小模型，复杂判断（退货规则）走大模型，边界场景根本不调用大模型。

方法论里还有一个与场景模式库呼应的选型判断：RAG 主要解决外部知识与证据供给，微调主要解决经 Eval 证明的行为或任务适配；法律条文、医学指南即使更新慢，只要需要引用、权限和可追溯性，也不能默认把事实知识微调进参数。更新频率只是运营成本因素之一，不能单独决定选型。这与第六节“生效时间与版本是一等元数据”的结论一致：知识需要追溯时，要让变更在索引层生效，而不是默认写进模型参数。

十、第四张模式卡：NL2SQL 数据分析助手

3

原有素材只覆盖客服、文档问答和代码助手。新增的 B 站大会员 NL2SQL 深拆补上了第四类高频场景，但先把证据边界说清：业务排队取数、Schema 复杂、自然语言歧义和安全挑战有案例线索；“两天到分钟级、覆盖率 85%、重复需求减少 60%”在原件中无出处，且原件明确写 ROI 未公开，三个数字禁用。下述六阶段是业界参考架构，不是 B 站内部实现披露。

公开产品文档可帮助把“Schema 上下文工程”落到字段。阿里云百炼析言 GBI 指南包含表描述、主外键、枚举映射、名词解释、同义词、业务逻辑、优化案例与输出干预；这些属于另一家产品的公开参照，不是 B 站配置。其中输出干预不具泛化性，适合临时兜底，不应靠堆补丁凑准确率。

试点切法。先选一个主题域和十几张核心表，不开放全公司；上线前两周测取数时延中位数/P90、重复需求占比和口径冲突次数。评测按单表聚合、多表 join、时间范围、同比环比、嵌套查询、指标口径、歧义与越权分层。只有单 Agent 单场景稳定后，才考虑取数、归因、出图的多 Agent 协同。

二、智能客服：做坐席助手，不做全自动

3

2.1 链路与意图分级

素材给出的完整链路是：先取工单上下文并生成摘要和标签，然后做身份鉴权，接着对政策库、常见问答和历史优质工单做混合检索，随后生成建议并强制附引用，最后由坐席一键采纳，或编辑后发送。链路里有三处值得强调。鉴权放在检索之前，说明连客服场景也要从一开始考虑数据范围。混合检索指同时用语义向量和关键词稀疏检索，实战方法论里解释了原因：口语化的提问与文档标题用词不同，纯语义检索对口语同义词不够敏感。强制引用则让每一条建议都能被坐席核对，也为后续评测留下证据链。

意图要分级处理。素材把退款、销户、投诉升级列为高危意图，这类意图不让模型自由生成，而是路由到固定话术模板，再加一份人工确认清单。只有低危、高置信、模板化的意图，才在第二阶段开放半自动。本文整理：分级的依据其实是“答错的后果是否可逆”，退款承诺发出去就难以收回，而物流进度查询答错可以立刻更正。客户说我要个AI客服怎么拆解那篇素材给出了对应的业务侧拆法：把过去一周聊天记录按问题类型分三类，A 类有标准答案（物流查询、营业时间、退换货政策），B 类半结构化（产品参数、订单修改）需要 AI 辅助加人审核，C 类复杂（投诉、大额售后、情绪激动的客户）必须人工。两份素材从不同角度得出同一个结论：AI 客服的核心不是什么都答，而是把 A 类先吃掉。

2.2 三级自主度

自主度统一为三级：影子模式下系统记录建议但不影响坐席操作；建议模式下建议展示给坐席，由坐席采纳或编辑后发送；最后才仅对低危、高置信意图分级开放自动发送。实战方法论对此有一句旁证：边界之外的场景用代码硬编码为转人工，比让 Agent 自由发挥便宜得多，也安全得多，一次错误的退货承诺造成的损失，可能超过整个系统一个月的收益。

这里最容易被管理层挑战。素材的决策对照表专门写了应对方式：当管理层提出“三个月降人工”，要在 Discover 阶段书面否决第一期全自动对外，同时给出替代叙事，也就是先用助手模式跑通采纳率，再评审分级自动，用 12 周的节奏代替三个月的承诺。目的是把技术决策从情绪化的诉求拉回可验证的里程碑。

2.3 十二周节奏

素材给出的十二周节奏可以拆成六个两周的段落：

  1. 第 1 至 2 周是 Discover，核心产出是书面否决第一期全自动对外的诉求。
  2. 第 3 至 4 周做知识切片，加入生效窗口元数据，建立黄金集的第 0 版。
  3. 第 5 至 6 周做侧栏原型，接入权限，在内部做影子测试。
  4. 第 7 至 8 周在两个班组试点。
  5. 第 9 至 10 周硬化高危意图的路由，并演练“错误建议”场景，也就是故意构造系统给出错误建议的情形，检验坐席和流程能否兜住。
  6. 第 11 至 12 周做 Review，决定是否扩大品类。

这个节奏的特点是把“书面否决”放在最前面，把“错误演练”放在试点之后、扩展之前。本文整理：这两处正好对应管理层压力最大和系统风险最高的两个时间点，节奏设计是围着风险安排的，而不是围着功能。

2.4 评测与验收

素材给出的验收线是：冻结 150 题的黄金集；引用正确率不低于 85%；应拒答和应升级的命中率不低于 95%；试点期的建议采纳率不低于 30%。黄金集必须包含“应升级、应拒答”的题目。

需要提醒的是，素材里还有另一个评测集数字：本地智能客服实战复盘建议建一个 500 条真实提问的标注集，每次改动都回归跑一遍，强调“评测集比模型选型更重要”。两个数字并不矛盾，前者是合成案例中冻结的试点验收集，后者是实战项目的日常回归集，口径不同，不要混用。

2.5 成本阶梯

成本数字来自本地实战案例，两份素材（场景模式库和实战方法论）给出一致的数字：月活约一万用户，全量走大模型约 9360 元每月；加入模型路由，让约 75% 的请求走小模型，降到约 3700 元；再加语义缓存，再省约 35%，最终约 2400 元，合计节省约 74%。实战方法论还补充了两个设计细节：模型路由本身用轻量分类器，延迟控制在 200 毫秒以内；语义缓存在命中率达到 30% 至 40% 时，能省掉三分之一以上的大模型费用。素材强调这套省钱设计必须在写第一行服务代码时就埋进架构，上线后被财务质疑再回头重构，线上变更的风险远大于收益。

2.6 约束与坑

素材列出的常见约束有三条：管理层要三个月降人工，对策见 2.2；活动规则有时效且答错要补偿，对策是把生效时间过滤做成一等元数据；幻觉多在检索层，对策是先查召回再怪模型，详见第八节。反例也很具体：合成案例里曾因没有做活动生效时间过滤，两次引用了过期的活动页面，给出错误建议，补上过滤后问题解决。

三、文档问答 RAG：先权限，后智能3 个重点▾ 点开看本节重点
本节重点
  • 3.1 权限感知的数据流
  • 红线只有一句话：先向量化全库、再靠提示词“请不要泄露”，不可接受，这是安全事故
  • 素材给出的试点切法非常窄：一个区域，只覆盖“报销与差旅”这一个制度子集，周期八周，用 120 题分层评测，其中权限相关用例必须 100% 通过，才能开门禁
3

3.1 权限感知的数据流

素材要求画出的标准数据流是：用户通过单点登录（SSO）给出身份，身份映射到用户组或属性，连接器把文档的权限标签同步进索引，检索前先按权限过滤（用户看不到的文档永远不会进入前 k 个候选），生成阶段只基于可见片段并附引用，最后经过输出护栏，高危主题转人工。

红线只有一句话：先向量化全库、再靠提示词“请不要泄露”，不可接受，这是安全事故。本文整理：这句话的技术含义是，权限必须在“数据进入模型上下文之前”被强制，而不能依赖模型在输出时的自觉。提示词是模型层的软约束，检索层的过滤才是系统层的硬约束。

3.2 索引元数据与制度变更

索引中的元数据必须带四个字段：acl_tags（权限标签）、doc_version（文档版本）、updated_at（更新时间）、owner（负责人）。同时要配一个制度变更工作流：制度发布后自动触发重建或增量索引，并向相关订阅用户推送通知。这四个字段分别回答了四个问题：谁能看、是哪一版、什么时候更新的、出了问题找谁。其中版本和更新时间直接决定了能否治理过期内容，而过期内容正是这类场景幻觉的主要来源。

3.3 试点范围与黄金集分层

素材给出的试点切法非常窄：一个区域，只覆盖“报销与差旅”这一个制度子集，周期八周，用 120 题分层评测，其中权限相关用例必须 100% 通过，才能开门禁。

黄金集的分层比例为：可答且有证据的题占 50%，用来测正确率和引用；应拒答的无文档题占 20%，测拒答率；跨权限诱饵题占 20%，是门禁，必须 100% 通过；过期版本陷阱题占 10%，测版本选择与治理能力。这个比例意味着 50% 用于可答题，另外 50% 分别覆盖拒答、权限和版本治理；其中版本题不等同于“该不该答”，必须按各自判据计分。

3.4 常见坑的处理

素材列了四类典型情形和对应处理：

  • 客户提出“先把全库接上，再慢慢补权限”，直接拒绝，权限是 Day 0 而不是后期补丁。
  • 客户质疑“和现有企业搜索重复”，不要去争替换，明确两者并存，比较的是可溯源答案和自助解决率。
  • 扫描件和旧 PDF 质量差，单列一个解析质量专项，质量差的文档不进入生产索引。
  • 处分、裁员、股权等高风险主题，自动转人工专家队列，不允许 AI 直接作答。

四、代码助手：仓库级权限与密钥是底线

3

4.1 架构与权限

主模式是仓库索引的 RAG，加代码补全与问答，可选测试草稿生成。模型必须使用企业版或私有网关，关闭训练选项，日志做脱敏。权限方面，可检索的仓库集合按用户的 Git 读权限同步，用户权限被移除后，对应的索引必须同步删除，索引范围严格等于用户可读的仓库，绝不能索引全公司所有仓库。

4.2 引用与护栏

回答必须指向具体的文件路径和符号，查不到就明确说“仓库中未找到”。素材解释了原因：这类场景的幻觉最常出现在引用过时注释时，路径引用是降低幻觉的关键手段。提交前要做密钥正则扫描，禁止粘贴环境变量文件，密钥红队测试要进入持续集成流水线。

4.3 上线前六项安全检查表

素材给出的上线检查表有六项，全部通过才能上线：

  1. 企业版或私有网关与关闭训练的书面确认。
  2. 日志脱敏与保留期。
  3. 索引权限与 Git 读权限同步，包含权限移除后的删除。
  4. 环境变量文件与密钥模式的输入输出扫描。
  5. 客户定制分支的隔离策略书面化。
  6. “禁止粘贴生产密钥”写进界面提示与培训材料。

这六项中，前两项管数据去向，第三项管可见范围，第四项管泄漏出口，第五项管客户分支的边界，第六项管人的行为。本文整理：它覆盖了数据、权限、出口、边界、人五个层面，缺任何一层都会留下事故入口。

4.4 试点与文化口径

试点范围是 2 个中等复杂度的服务、20 名工程师、6 周；用 50 个“如何改某处”任务评测正确路径命中率；必须存在密钥泄漏红队用例，且成功泄漏数必须为 0。文化口径有三条：草稿不等于可合并；Copilot 不能替代架构评审；文档债仍要人工偿还。面对“用个人 ChatGPT 贴代码更快”的习惯，要强调企业入口可审计、合规风险更低；面对“自动开 PR 自动合并”的期待，明确这不是目标，草稿加人工评审才是安全边界。

4.5 验证与调试分诊的扩展

如果客户痛点是海量测试失败的分诊，素材以半导体验证场景为例，建议在上述安全底座之上分三级落地：第一级只读失败日志，写调查结论或工单；第二级提出补丁并开 PR，由人工合并；第三级在隔离环境里跑复现和单元测试，没有生产写权限。指标相应扩展为分诊平均时长、误导调查率、自动修复可合并率。其中“误导调查率”这个指标值得注意，它衡量的是助手给出的调查结论把人带偏的比例，是对“看起来很有道理的错误结论”的直接度量。

素材的决策对照表给出五种高频情形。下面按“说法、判断、做法”整理。

一、“三个月降人工”。 判断是管理层的诉求被情绪化的时间承诺主导。做法是书面否决第一期全自动对外，给出替代叙事：先助手模式跑通采纳率，再评审分级自动，用十二周的节奏代替三个月的承诺。

二、“先全库向量化，再补权限”。 判断是把权限当成后期补丁。做法是直接拒绝，并用安全事故的历史作类比说服：没有权限标签的全库向量库，等于把所有敏感文档做成可被任意问答的泄露通道，事后补权限的成本是一开始就做的十倍。需要说明，“十倍”是素材中的原话表述，素材没有给出推算依据。

三、“业务说坐席不信任 AI”。 判断是问题不在模型够不够好，而在默认开启自动发送，让坐席觉得失控。做法是切回建议模式，向坐席展示建议但由坐席采纳、编辑或拒绝，不替人做决定；影子模式只用于不影响坐席的离线观察。坐席信任要靠可核对的连续表现与反馈机制验证，而不是默认“自然会建立”。

四、“幻觉太多”。 在本地客服复盘同类问题中先检查检索，不要先怪模型；其他场景还要排查模型推理、工具返回与虚构 API。素材称该客服案例八成幻觉的根因是前 k 个候选里根本没有正确答案，或召回了过期版本，并建议加生效时间过滤、版本标签、强制引用。这里的“八成”和“一个数量级”均为素材原话，未附统计口径，不能外推成三场景普遍病因或收益承诺。

五、“成本太高”。 判断是成本设计滞后。做法是第一天就埋模型路由和语义缓存，把高频简单问题路由到小模型，把重复问答缓存下来，素材称真实案例证明能省掉七成以上的大模型调用成本，对应第二节的 74%。

案例一：电商类客服坐席助手（合成）

背景：客户属于坐席量大、工单系统成熟、活动政策高频变化的类型，管理层的诉求是“三个月把人工降一半”。

交付过程：第 1 至 2 周，FDE 在 Discover 阶段书面否决了第一期全自动对外，并给出“先助手后自动”的替代叙事。第 3 至 4 周完成知识切片，并为知识条目加入生效窗口元数据，建立黄金集第 0 版。第 5 至 6 周做出侧栏原型，接入权限，在内部做影子测试。第 7 至 8 周在两个班组试点。第 9 至 10 周硬化高危意图（退款、销户、投诉升级）的路由，演练错误建议场景。第 11 至 12 周 Review，决定是否扩品类。

验收口径：冻结 150 题黄金集，引用正确率不低于 85%，应拒答与应升级命中率不低于 95%，试点期建议采纳率不低于 30%。

结果与事故：合成结果为建议采纳率 41%，新人达标周期从 6 周缩短到 4 周。事故是，早期没有做活动生效时间过滤，系统两次引用了已过期的活动页面，给出了错误建议。对策是在检索层增加生效起止时间（素材字段名为 effective_from 和 effective_to）的元数据过滤，补上之后问题消失。

可复用点：其一，采纳率既是业务指标，也是坐席信任的代理指标，41% 超出验收线 30%，是建议模式下坐席采纳行为的合成示意，不能由影子模式产生，也不能单独证明信任；其二，过期活动页的事故说明，生效时间过滤必须在第一版就做，而不是等出了事故再补；其三，管理层的“三个月”被十二周的节奏转化成了可验证的里程碑。

案例二：制度知识库问答（合成）

背景：客户的制度和知识文档多，按事业部或职级分权，合规要求是零事故，诉求是“做个能问制度的机器人”。

交付设计：切入点是权限感知 RAG 加无证据拒答。试点范围刻意缩得很窄：一个区域，只做“报销与差旅”制度子集，周期八周。数据流按“SSO 身份、用户组、文档权限标签、检索前过滤、仅基于可见片段生成并附引用、输出护栏”来画。索引元数据带 acl_tags、doc_version、updated_at、owner 四字段，并建立制度变更工作流。评测集 120 题，按 50/20/20/10 分层，其中跨权限诱饵题全部通过才能开门禁。

客户可能提出的挑战：素材预设了几个客户反应并给出处理，例如先全库接入再补权限（拒绝）、与现有企业搜索重复（并存，比溯源和自助率）、扫描件质量差（单列解析专项，差质量文档不进生产索引）、高风险主题（转人工专家队列）。

结果：素材没有给出该案例的结果数字，这一点必须如实标注。本文不补写不存在的结果。能从中学到的是设计方法：试点范围的“窄”、评测集的“分层”，以及把权限用例设为 100% 通过的硬门禁。

可复用点：其一，这个案例最有价值的是用另外 50% 分别覆盖拒答、权限和版本治理，并为不同风险配专门判据；其二，试点选“报销与差旅”这种相对稳定、边界清晰的制度子集，是为了让第一次评测就有明确的判据；其三，高风险主题的拒答与转人工，是系统层的护栏，而不是模型层的自觉。

案例三：研发团队代码助手（合成）

背景：客户的研发团队大、遗留代码多、对密钥合规敏感，诉求是“让 AI 帮找代码、写测试”。

交付设计：仓库索引 RAG 加补全与问答，使用企业版模型或私有网关，关闭训练选项，日志脱敏。检索范围与用户的 Git 读权限同步，含权限移除后的索引删除。回答必须指向文件路径与符号，查不到就说“仓库中未找到”。试点为 2 个中等复杂度服务、20 名工程师、6 周，用 50 个“如何改某处”任务评测正确路径命中率，必须存在密钥泄漏红队用例，且成功泄漏数必须为 0。上线前过六项安全检查表。

结果：合成结果是新人首个 PR 的中位时间降低约 20%。素材特别指出，最大的价值在于“解释遗留模块”，而不是写新功能。

扩展场景：素材以半导体验证为例，说明如果客户的痛点是海量测试失败分诊，可以在同一安全底座上分三级落地。第一级是只读工具读取失败日志，写调查结论或工单；第二级是提出补丁并开 PR，由人工合并；第三级是在隔离环境里复现问题并跑单元测试，没有生产写权限。指标扩展为分诊平均时长、误导调查率、自动修复可合并率。素材没有给出这个扩展场景的结果数字，同样如实标注为未取得。

可复用点：其一，价值不在“替人写代码”，而在“帮人读懂已有代码”，这决定了宣传口径和指标选择；其二，权限与 Git 同步这一条把代码助手的安全问题转化为“已有权限体系的镜像”，不需要另造一套；其三，三级分诊是自主度分级思想的另一种具体形态，逐级放权，每一级都有人把关。

三个案例的共同轨迹（本文整理）

把三个案例并排看，它们遵循同一条轨迹：先书面确定非目标，再建立含负例的评测集，然后以窄范围试点，每一步都有权限或版本的硬门禁，最后用业务语言的指标判断是否扩大。区别在于每个案例暴露的主要风险不同：客服案例暴露的是版本过期，知识库案例设计上防范的是越权，代码助手案例防范的是密钥与幻觉引用。三类风险恰好对应第六节共性规则中的两条：权限是 Day 0，生效时间与版本是一等元数据。

  • NL2SQL 模式卡已有业界参考架构，但仍缺目标项目的实测结果与验收数据；多模态等其他常见形态仍需另行建立模式卡。

诚实边界

三个来自 VanGong1999/FDE 的案例均为合成教学案例，素材原文明确标注为脱敏后的行业共性，不是真实客户的细节。其中的采纳率 41%、新人达标 6 周缩短到 4 周、首个 PR 中位时间约降 20% 等数字都是示意值，用于说明模式，不构成可以对外引用的效果承诺。正式对客户承诺之前，必须用自己项目的实测数据替换这些示意数字。成本阶梯与幻觉复盘的数字来自本地一个实战项目，其口径也限于该项目。本文所有“本文整理”标注的内容，是对素材的归纳和重组，不是新增事实。

  • 图谱槽开关是"取舍留痕"的范式（同上 graph_slot_mode）：注释写明 含图谱槽 R@1=19.6% / 剔图谱槽 R@1=45.1%、after_top1 / multi_hop_only / always / never 四档，"一键回退用: 改回本行即可，无需回滚代码"——客户现场调参必须可回退、可解释。
  • 和课件讲法的差异：课件按"智能客服 / 文档问答 RAG / 代码助手 / NL2SQL"四张模式卡讲切入点与风险；本库只实现了文档问答 RAG 这一类的完整链路（含拒答与引用），智能客服的坐席侧栏、代码助手的 IDE 集成、NL2SQL 的 schema RAG 本库暂无实现。课件给"打法"，本库给"能跑的那一张卡"。
