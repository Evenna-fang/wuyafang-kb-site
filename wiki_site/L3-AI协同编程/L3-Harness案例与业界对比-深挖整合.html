1. 先列必须能力，不先打产品总分

3

用最近一次实际故障填写表格：故障触发、失败环节、已有机制、缺失能力、最小验证方法。例如“进程重启后从头开始”对应持久恢复，“模型修改工作区外文件”对应执行边界，“审批后产物被改”对应审批与版本绑定。每条都应能转成一个失败用例。

教学验收可以设为：正常任务完成；测试失败不能进入审查；拒绝审批不能完成；审批绑定旧产物时不能通过；进程重启后恢复正确阶段；超出重试上限转人工。阈值由任务风险决定，不能以某框架提供多少组件作为验收。

2. 用标准库先验证业务状态契约3 个重点▾ 点开看本节重点

  • raise ValueError("invalid transition or stale artifact")

下面的 workflow_demo.py 不依赖任何框架或模型，演示执行→测试→审批→完成的业务不变量。这些断言可以在迁移时复用；它不是生产工作流引擎，不实现数据库或副作用幂等。

from dataclasses import dataclass, replace

@dataclass(frozen=True)
class Job:
    stage: str = "planned"
    artifact: str = ""
    tested_artifact: str = ""
    approved_artifact: str = ""

def advance(job, event, artifact=""):
    if event == "generated" and job.stage == "planned" and artifact:
        return replace(job, stage="testing", artifact=artifact)
    if event == "tests_passed" and job.stage == "testing":
        return replace(job, stage="review", tested_artifact=job.artifact)
    if event == "approved" and job.stage == "review" and artifact == job.artifact:
        return replace(job, stage="ready", approved_artifact=artifact)
    if event == "finish" and job.stage == "ready":
        if job.artifact == job.tested_artifact == job.approved_artifact:
            return replace(job, stage="done")
    raise ValueError("invalid transition or stale artifact")

if __name__ == "__main__":
    initial = Job()
    testing = advance(initial, "generated", "sha256-demo-v1")
    review = advance(testing, "tests_passed")
    ready = advance(review, "approved", "sha256-demo-v1")
    assert advance(ready, "finish").stage == "done"
    invalid = [(initial, "finish", ""), (testing, "approved", "sha256-demo-v1"),
               (review, "approved", "sha256-demo-v2"),
               (replace(ready, artifact="sha256-demo-v2"), "finish", "")]
    for job, event, artifact in invalid:
        try:
            advance(job, event, artifact)
        except ValueError:
            pass
        else:
            raise AssertionError("invalid transition accepted")
    print("workflow: 5 checks passed")

python3 workflow_demo.py

sha256-demo-v1 是清楚标明的教学标识，不是真哈希。生产接入必须由可信侧计算实际产物摘要；调用者若能任意宣称 tests_passed，状态机再整齐也是假门禁。独立测试者、操作权限和不可任意改写的状态存储共同建立可信链。

3. 将同一契约映射到候选框架

3

LangGraph 路线：让节点分别负责生成、验证和审批，状态保存产物引用与实际检查结果；需要恢复时使用适合部署的持久检查点，并按线程标识恢复。课件的 MemorySaver 示例适合进程内练习，不能拿它冒充服务器重启后的恢复证据。[课1]

Deep Agents 路线：让 harness 处理复杂生成子任务，外层仍检查输出契约；根据任务需要选择文件后端、工具和子代理。官方文档将 planning、skills 等描述为可选能力，不能假设所有安装版本的默认工具和行为都相同。[业1]

CrewAI 路线：用 Flow 的状态和事件控制交接，Crew 承担具体工作；状态字段承载上述版本绑定。先核对当前 API，再选持久化方式。不能因为 role/goal 文字清楚就省略结构化输出校验，也不能因为引入 Flow 就断言所有审计需求已满足。[业2]

CLI 路线：已有 Codex/Claude Code 能完成单节点工作时，优先用明确输入输出包装它。必须同时处理任务退出、无结果、超时、取消和人工批准，不把 CLI 退出码直接映射成业务 done。对于一个独立小脚本，CLI 加现有测试就可能足够，不需要为展示架构再引入三个框架。

5. 迁移只动已证实的薄弱环节

3

如果外层状态图工作正常，而编码节点不可靠，只替换这个执行单元；保留流程标识、输入输出 schema 和回归用例。若失败来自状态恢复，就优先修持久化和幂等，不用换模型掩盖。两层同时换会丢失对照，也使回退困难。

从 AutoGen 迁出时，分别盘点：对话或协作顺序、工具协议、模型适配、消息状态、人工中断、终止条件、观测数据。先迁无副作用的支线，用相同脱敏样例双跑。涉及付款、写库或发消息的任务不能双跑两次真实副作用，可用模拟工具或影子记录对比。[业3；迁移步骤为本篇工程设计]

回退应回到已知可运行版本，而不是在新旧配置间反复猜测。回退也要兼容已产生的数据和状态：如果新栈已经写入新格式，旧栈可能读不了，必须事先设计转换或禁止在试验阶段写生产数据。

# 选型决策
故障：描述可复现问题，而不是“架构不够先进”。
候选：现有 CLI / LangGraph / Deep Agents / CrewAI / 其他。
必须能力：恢复、权限、审查、数据与接口约束。
实验：固定输入、版本、测试、故障注入方式。
结果：通过与失败项，端到端时间，包含失败的总成本。
选择：解释解决了哪项实际问题。
未解决：保留限制，不把计划写成已完成。
退出条件：出现哪种回归即停用，恢复哪一已验证版本。

七案例最终对应七个可操作问题：环境能否复现、失败是否变成验证、审查是否独立、增量是否可合并、实验是否控制变量、反馈是否足够短、规则是否定期修剪。它们共同指导试验，但没有任何一例能替代你自己的任务集与责任边界。

本库真实落地（源码核对，2026-11-04）

  • 本库的 Harness 就是 ~/.hermes/ 这几个件，各管一件事（本次实测调用）：
    | 件 | 职责 | 本次证据 |
    |---|---|---|
    | AGENTS.md | 行为规则（三档分流、审查链、停手规则） | 本次任务的执行说明即由此约束 |
    | scripts/dispatch-guard.py | 派单门禁：路由建议 + 通道检查 | 本次实跑输出「建议执行者: DSH」「写操作必须用真通道」 |
    | scripts/receipt.py | 完成凭据（declare → verify） | 本次任务判定为「不值得全流程」（纯文档改动） |
    | skills/ | 100+ SKILL.md 按需加载 | 本次加载 receipt-declare-verify、error-ledger |
    | shared-state.db | 六员任务总线（tasks + inbox） | 收口时回传用 |
  • 和业界 Harness（Claude Code / Codex / OpenHands）的对比点：本库多了一层「派单前机械门禁」——不是模型自己决定怎么干，而是脚本先判「这件事该谁干、用哪个通道、算哪一档」。好处是可审计，代价是规则变多后门禁自己成了维护成本。
  • 本库的真实教训（写进技能文档的）：receipt 全流程「实测烧 20 分钟 50 轮，改动本体 1 行」——门禁的成本要和改动的风险匹配，这是本库与业界 Harness 差异最大的一条设计判断。
  • 和课件讲法的差异：课件对比的是「用不用 Harness」；本库面对的是「自建 Harness 与官方 Harness 的边界」——壳层（规则/门禁/台账）自建，模型调用交给官方 CLI。
  • 本库暂无：没有统一的 Harness 性能/质量评测（如「同一任务用不用 Harness 的成功率差」），对比停留在定性。
