Harness 性能调优：统一测量 Token、延迟与成功交付成本

本主题合并 Token 优化、延迟优化、成本控制、三档预算、步级路由与省 Token 三件套。核验日：2026-11-03。

WHY：省输入不等于省成本，快返回不等于快交付3 个重点▾ 点开看本章重点
本章重点
  • 一个系统把提示词压短，却因为遗漏接口约束返工三次，总成本可能更高
  • 旧稿的“Token 预算差十倍、质量差不到两倍”“机器派单默认从八并发起步”“必须降成本 40% 才切换”均缺少可推广的证据
  • 另一个系统并行运行六个代理，单轮更快，但整合冲突花掉半小时，任务交付仍然更慢
2

一个系统把提示词压短，却因为遗漏接口约束返工三次，总成本可能更高。另一个系统并行运行六个代理，单轮更快，但整合冲突花掉半小时，任务交付仍然更慢。性能优化的对象应是“在既定质量门槛下完成一个任务”的总消耗，必须同时报告成功率、墙钟时间和成本。

课件明确提醒 before_model 中的同步代码会增加每次模型调用的耗时，避免繁重计算与阻塞；销售分析 Skill 要求优先消费脚本已有的结构化结果，禁止无意义重复计算。书籍主张最小高信号上下文、高配规划低配执行。当前官方缓存文档区分模型代际、缓存写入与读取、隐式与显式策略。三者合起来给出顺序：先量化调用链，再去掉重复工作，最后针对实际模型与宿主调参。[课1][课2][书1][书2][业1]

旧稿的“Token 预算差十倍、质量差不到两倍”“机器派单默认从八并发起步”“必须降成本 40% 才切换”均缺少可推广的证据。本篇不把这些数字作为行业规律或强制门槛。

WHAT / WHYT：先统一测量口径

2
指标 正确口径 不能拿来替代的量
输入 token 服务返回或匹配模型 tokenizer 的实测量 中文字数、字符数、文件字节
缓存读写 token 按供应商与模型的 usage 定义分别归类 一律从 input_tokens 再减同一个字段
墙钟时间 任务开始到最终验收的经过时间 子任务耗时相加、首 token 时间
总成本 所有尝试的输入、输出、缓存、工具费用 仅最后成功一次调用的费用
成功率 通过预先固定验收的任务数/总任务数 HTTP 成功比例、进程退出码比例
成功交付成本 整批总成本/验收成功任务数 只统计成功记录、排除失败消耗

并行性能下界受关键路径限制：理想时间不小于依赖链上各步骤耗时之和，还要加调度、排队与汇合开销。“六个文件并行约六倍加速”只有在完全独立、资源充足且协调代价可忽略时才可能接近，不是实现保证。

缓存也不是免费上下文。2026-11-03 获取的 OpenAI 官方页面已经区分不同模型代际的写入成本、读取成本和有效期，不能把旧稿的“所有缓存一律一折”“同内容只算一次钱”继续写进计费公式。本篇不硬编码当前某型号价格，读者应登记当次模型价目与币种。[业1]

2. 用四种 token 计费类别计算费用

3

下面是离线演算，保存为 cost_demo.py。数值为教学合成价格，单位是假定的“货币单位/百万 token”，不是任何厂商报价。归一化之前先读取供应商 usage 定义，保证普通输入、缓存写入、缓存读取互斥，防止双重计费。

from decimal import Decimal

def cost(row, prices):
    fields = ("uncached", "cache_write", "cache_read", "output")
    if any(row[name] < 0 for name in fields):
        raise ValueError("negative token count")
    token_cost = sum(
        Decimal(row[name]) * prices[name] / Decimal(1000000)
        for name in fields
    )
    return token_cost + Decimal(str(row.get("tools", 0)))

if __name__ == "__main__":
    prices = {"uncached": Decimal("2"), "cache_write": Decimal("2.5"),
              "cache_read": Decimal("0.2"), "output": Decimal("8")}
    row = {"uncached": 1000, "cache_write": 2000,
           "cache_read": 3000, "output": 500, "tools": 0}
    assert cost(row, prices) == Decimal("0.0116")
    assert cost({name: 0 for name in row}, prices) == 0
    try:
        cost({**row, "uncached": -1}, prices)
    except ValueError:
        pass
    else:
        raise AssertionError("negative usage accepted")
    print("cost: 3 checks passed; synthetic cost=0.0116")

python3 cost_demo.py

如果某模型有多种缓存写入时长，就增加独立类别，不能用一个固定 cache_write 单价覆盖。推理 token 是否已含在输出里也要按实际计费口径处理。没有 usage 时标“缺测”，不能拿字符粗估值填成实测成本。

4. 缓存优化先验证前缀稳定

3

在语义不变前提下，把固定规则、稳定工具定义放在稳定位置，把当前用户输入和会变化的资料放后面。不要每轮在最前面插入时间戳或随机任务 ID。具体缓存断点和有效期使用当前供应商接口，不复制另一个模型的字段。[业1]

做冷、热两组调用时控制模型、请求内容和时间间隔，记录 cache read/write usage 和实际成本。缓存命中不要求逐轮单调上升：过期、路由、内容变化和模型策略都会改变它。若总为零，再查长度条件、断点、内容变动与模型支持，不先假定缓存功能失效。

6. 路由使用任务证据，不使用固定品牌等级

3

Low/Mid/High 可以作为本地预算标签：Low 对应范围小且判据确定的任务，Mid 对应多步操作，High 对应复杂推理或独立审查。但预算应受任务复杂度、失败损失和剩余不确定性约束，不把某位成员永久锁成一个档位，也不自动更换成员底层模型。

书籍的高配规划、低配执行是一种假设，需要同任务对照。如果轻量模型多跑两次仍失败，它的成功交付成本可能更高。旧 AFP=0.5/1/5/9 不是行业价格标准，旧模型名、token 区间和无来源秒数不再作为当前选型表。[书2]

下面演示结果缓存键的必要维度，保存为 cache_key_demo.py。它只计算键，不缓存或执行任何任务。对会产生副作用的操作，还必须有幂等标识与外部状态校验。

import hashlib
import json

def cache_key(contract, input_hash, code_revision, permissions, model):
    payload = {"contract": contract, "input_hash": input_hash,
               "code_revision": code_revision,
               "permissions": sorted(permissions), "model": model}
    encoded = json.dumps(payload, sort_keys=True, ensure_ascii=False).encode()
    return hashlib.sha256(encoded).hexdigest()

if __name__ == "__main__":
    args = ("normalize", "input-a", "revision-1", ["read"], "fixture")
    original = cache_key(*args)
    assert original == cache_key(*args)
    assert original != cache_key("normalize", "input-b", "revision-1", ["read"], "fixture")
    assert original != cache_key("normalize", "input-a", "revision-2", ["read"], "fixture")
    assert original != cache_key("normalize", "input-a", "revision-1", ["write"], "fixture")
    print("cache-key: 4 checks passed")

动态外部数据、账号租户、模型参数、工具版本等若影响结果，也应进入实际键或使缓存失效。全文哈希只说明输入相同，不保证答案仍新鲜；涉及时间敏感信息还需要有效期。

本库真实落地（源码核对，2026-11-04）

  • 本库对 Harness 性能做过的最扎实一件事，是把「线程数 / batch 大小 / 文件系统」三个变量分别实测后写进注释（rag/ingest.py L41-62，本次读源码）：
    # [2026-10-14 性能修复] 索引/数据目录支持环境变量覆盖。 # 背景: 项目在 /mnt/c (WSL 9p 文件系统), 实测写速仅 24 MB/s, 而 WSL 原生盘 234 MB/s。 # [2026-10-14 性能修复] 编码线程数。……实测 4 线程 batch=4 相对 2 线程 batch=8 提速 4.4 倍 # (1.10 -> 2.00 条/秒, 全量 15156 chunk 从 3.8 小时降到 2.1 小时)。 # batch 越小越快, 因为 padding 浪费随"批内最长序列"放大, 而 CPU 早已饱和。
    结论反直觉但可复现：batch 越小越快（bs=4 → 1.05 条/秒，bs=8 → 0.73，bs=16 → 0.57，不传 → 0.34），原因是中文长文本的 padding 开销随批内最长序列放大。
  • Harness 层面的三条优化全部可回滚：RAG_TORCH_THREADS、RAG_EMBED_BATCH、RAG_INDEX_DIR 都是环境变量，默认值写在代码里，不改代码即可调参。
  • 本次实测的另一个 Harness 开销：模型冷加载 224.7 秒（bge-m3 首次加载到出第一个 dense 向量），单句编码只要 0.3 秒。这说明本库真正的「性能」瓶颈是进程启动，不是单次推理——所以 rag/query.py 被设计成「一次进程处理一个问题」，长驻服务才划算。
  • 和课件讲法的差异：课件讲 Harness 性能多从「LLM 调用延迟、上下文长度」切入；本库的性能账本里，最大的两项是 9p 文件系统写速（24 vs 234 MB/s）和模型冷启动（224.7s），都不是模型本身。
  • 本库暂无：没有把模型常驻成服务（每次 CLI 都重新加载），也没有 p50/p95 延迟统计。
