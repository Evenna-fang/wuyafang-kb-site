让模型生成一段能运行的程序，只完成了交付的一部分。真实任务还要求知道改哪个目录、哪些接口不能变、失败后从哪里继续，以及由什么证据证明结果满足需求。Harness 是承载这些动作的工程运行环境：模型提出行动，运行时检查权限、执行工具、收集观察，再把可验证的结果反馈给下一步。它影响可靠性，但“永远比模型重要”不是已经证明的普适定律。[课1][书1][业1]

课件从常见失败讲起：复杂任务容易路径错乱、上下文膨胀、目标丢失；DeepAgents 因而组合规划、文件操作、子代理和上下文管理。橙皮书把同类工程问题拆成指令、约束、反馈、记忆、编排五组件。当前 Deep Agents 官方文档直接称其为 agent harness，并说明它建立在 LangChain、LangGraph 之上。这三类材料应合成一个落地判断：先找出阻止交付的具体缺口，再补对应机制，不按组件数量评判先进程度。[课1][书1][业1]

例如，模型修改了接口却忘记更新调用方，优先补接口契约与回归；模型不知道测试命令，补薄入口；任务中断后重复执行付款，补幂等和持久状态。三种故障都不能靠“再认真一点”解决，也不必一律引入六个智能体。

编排 任务依赖、写入归属、交接契约 子任务失败时整体不能报完成 六个文件就应拆六个代理

五组件是书籍的教学分解，不是任何产品共享的配置协议。旧稿里的 harness/instruction.yaml、constraint.sandbox、feedback_strength 等字段没有对应加载器，不能复制进 Claude Code 或 Codex 就期待生效。本篇用真实指令文件、标准 Python 验证程序和显式任务契约代替这些“看似配置”的示意字段。[书1][书2]

三个层次也要分开：Prompt 工程处理单次表达；Context 工程处理输入资料的选择与组织；Harness 工程把这些输入连接到工具、权限、状态与验证。框架可以实现其中多个层次。DeepAgents 同时提供编排和执行能力，因此不应把“所有框架只管编排，所有 Harness 只管执行”写成绝对划分。[业1]

课件中的 MemorySaver 是内存检查点，不能据此宣称进程退出后仍可恢复；FilesystemBackend(..., virtual_mode=True)限定文件工具的路径视图，也不能替代任意 shell 命令的操作系统隔离。验证时必须分别测文件工具、命令执行、网络、持久化，不用一个参数推断四项能力。[课1，后两项为工程推导]

1. 先把需求写成契约

3

以下是教学项目，使用 Python 3 标准库，不连接模型、不读取凭据。任务是实现 normalize_tags：接收字符串列表，去除两侧空白、转小写、丢弃空项、去重并保持首次出现顺序；遇到非字符串抛 TypeError。它刻意包含顺序与错误分支，避免只验证正常输入。

在专用练习目录建立下面结构；不要把示例命令指向已有生产仓库。

harness-lab/
├── AGENTS.md
├── CLAUDE.md
├── tags.py
├── test_tags.py
└── handoff.md

AGENTS.md 的最小内容如下。Claude Code 使用的 CLAUDE.md 可放相同的短规则；这属于教学双工具适配，实际团队应明确哪个文件是维护正本。

# 项目约定

接口：normalize_tags(values: list[str]) -> list[str]。
保留首次出现顺序；非字符串元素抛 TypeError。
验收：python3 -m unittest -v test_tags.py。
先说明计划，再修改；完成时报告真实测试结果与剩余限制。

将下面内容保存成 test_tags.py。本例是行为契约，不限定实现算法。

import unittest
from tags import normalize_tags

class TagTests(unittest.TestCase):
    def test_normalize(self):
        self.assertEqual(normalize_tags([" AI ", "Python"]), ["ai", "python"])
    def test_order_and_dedup(self):
        self.assertEqual(normalize_tags(["B", "a", "b"]), ["b", "a"])
    def test_empty(self):
        self.assertEqual(normalize_tags(["", "  "]), [])
        self.assertEqual(normalize_tags([]), [])
    def test_non_string(self):
        for value in (None, 3, {}, True):
            with self.assertRaises(TypeError):
                normalize_tags(["ok", value])
    def test_input_unchanged(self):
        values = [" A ", "a"]
        original = values.copy()
        normalize_tags(values)
        self.assertEqual(values, original)

if __name__ == "__main__":
    unittest.main()

先只有空实现时测试应该失败。参考实现如下；可以交给 AI 独立实现后再比较行为，不能把“与参考代码长得一样”当作质量门槛。

def normalize_tags(values):
    result, seen = [], set()
    for value in values:
        if not isinstance(value, str):
            raise TypeError("tag must be a string")
        tag = value.strip().lower()
        if tag and tag not in seen:
            seen.add(tag)
            result.append(tag)
    return result

python3 -m unittest -v test_tags.py

预期 5 个测试通过。负例验证：临时把 result.append(tag) 改为 result.insert(0, tag)，顺序测试必须失败，然后恢复。这证明验收会识别一种真实缺陷，不能证明所有 Unicode、性能或业务需求都被覆盖。

3. 让反馈真正改变下一步

3

失败时交给执行者四项信息：失败测试名、输入、期望与实际、允许修改范围。不要只发“测试没过”。修复后复跑失败项与同模块回归；同一原因最多重试 2 次，再次失败应回到需求或环境诊断。两次是本任务采用的工作上限，不是行业默认值。

记忆只保存可复用内容：例如“标签顺序具有业务含义，禁止用排序替代去重”。一次性的运行日志只存引用，不变成常驻规则。课件的销售分析 Skill 同样要求先读 KPI 定义、调用现有脚本、消费结构化结果，只有脚本不覆盖需求时才补代码。这是减少重复推理与口径漂移的具体做法。[课2]

5. 何时升级系统

3

单任务可用时才考虑并行：先固定接口，拆成不相交写集；共享配置、数据库迁移、同一文件统一串行。需要跨进程恢复时引入持久检查点；需要业务审批时保存批准绑定的产物版本；需要长期运行时定期产出可验证增量。清单、哈希和测试各有作用：哈希能证明字节一致，不能证明内容正确；测试能证明覆盖行为，不能证明权限隔离。

  • 本库的「协同编程最佳答案」其实是三条能机械复现的约束（~/.hermes/AGENTS.md + 门禁脚本，本次实测）：
    1. 写操作必须派子智能体、且用真通道：dispatch-guard.py --task "..." 本次实跑给出「建议执行者: DSH」，并给后闸「写操作必须用真通道命令，不能用 delegate_task」。
    2. 完成必须有可执行证据：receipt.py 的技能文档写明「自述✅不被采信，逐项贴 -n 原始输出」；本次任务的验收就是「实跑 + 贴原始日志行」。
    3. 同错 3 次停手：错误指纹去时间戳/路径/ID 后 lookup_error.py 查台账，命中即套用。本次查询「替换后字数减少」「wiki 小节插入 位置」两条都是「新坑，台账无记录」——先查后动手。
  • 一个真实的失败成本对比：本库技能文档记录 receipt 全流程「实测烧 20 分钟 50 轮，改动本体 1 行」，因此判据被收窄为「能用一次真调/grep 复原验证的，不进 receipt 全流程」。这条判断是本库对「协同编程最佳答案」最有价值的贡献——门禁要按风险分级，不是越多越好。
  • 和课件讲法的差异：课件/文章讲多 Agent 协作多在「如何分工、如何通信」；本库补的是「如何防止多 Agent 互相帮倒忙」（并发写锁、trace 防篡改、收口人必填）。
  • 本库暂无：跨 Agent 的实时消息通道；六员交互靠任务表与文件落盘。
