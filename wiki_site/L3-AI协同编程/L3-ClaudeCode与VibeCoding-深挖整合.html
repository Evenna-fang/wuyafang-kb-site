Claude Code 与 Vibe Coding：从需求到可维护代码

本主题覆盖 Copilot、自然语言原型、Claude Code 的上下文、Skills、Hooks 与重构；团队分工与 Codex 操作见协作篇。核验日：2026-11-03。

自然语言很适合表达界面、数据处理和脚本需求，但一句“做个待办应用”没有回答数据损坏怎么办、删除是否可恢复、代码由谁维护。AI 加快实现之后，验收与理解成为必要的工作，而不是可以省略的尾声。旧稿宣称“效率提升 5—10 倍”，原材料没有实验设计、基线、任务集与耗时记录，本篇撤下这个结论。

书籍摘录强调 CLAUDE.md、Skills、SubAgents、Hooks 的协同；课件销售分析 Skill 则给出可观察的实例：先看表头和指标定义，再调用脚本，最后按结构化结果写报告。把两者融合到编程场景，就是先明确接口与验收，再调用工具实现，最后按运行结果解释行为。[书1][课1]

Vibe coding 的含义需要限定。Simon Willison 在 2025-03-19 的原文中将其解释为使用大模型构建软件而不审阅生成代码；审阅、充分测试并能解释实现的过程属于负责任的 AI 辅助开发。这个定义是历史概念来源，2026-11-03 复核可访问，并非“2026 年新发布”。工具名称也不决定工作方式：使用 Claude Code 可以做快速实验，也可以进行严格工程开发。[业2]

WHAT / WHYT：四种机制分别解决什么问题

2
机制 适合放什么 不应承诺什么
CLAUDE.md 常用验证命令、项目约束、需要读取的规范入口 自动执行所有规则、替代沙箱
Skills 专门流程、参考资料、可复用脚本与模板 自动抹除已经进入会话的上下文
Hooks 在具体事件运行确定性检查 任意脚本失败都会阻断、覆盖所有执行通道
Subagents 范围清晰、可独立完成的调查或实现 没有协调成本、天然没有文件冲突

“财务 Skill 在话题切换后退场”是书中说明按需加载的比喻；它不能证明宿主会即时删除已加载正文。实际收益取决于发现、加载和上下文整理机制。[书1]

原型、补全与工程协作的使用边界3 个重点▾ 点开看本节重点
本节重点
  • Copilot 可作为编辑器内补全和对话助手；产品具体能力随版本变化，本篇不再把它限定成“只能自动补全”
  • 对局部函数，先写输入、输出、边界再采纳建议；对跨模块重构，先建立调用关系与回归
  • 没有必要为了一个明确的局部修改引入复杂编排
3

Copilot 可作为编辑器内补全和对话助手；产品具体能力随版本变化，本篇不再把它限定成“只能自动补全”。对局部函数，先写输入、输出、边界再采纳建议；对跨模块重构，先建立调用关系与回归。没有必要为了一个明确的局部修改引入复杂编排。

Vibe 原型适合低风险、可丢弃的探索。转向长期维护时，必须补接口说明、测试、数据迁移和错误处理。原型做出来以后再读代码，也仍然要读；不能因为“AI 生成”就把理解责任转交给模型。

以基础篇的 normalize_tags 小项目为例，先在练习仓库执行：

pwd
git status --short
claude --version
claude --help

这些命令用于核对工作目录、未提交修改和本机 CLI 语法；本次编辑工作没有替读者启动模型会话。若本地帮助没有某个选项，就停止套用旧文章命令。旧稿中的 claude ultrareview --base main、--background 和 bug-locator 等名称没有在本次所读官方资料中完成核验，不再列为通用内置命令。自定义 agent 名称必须先在项目中定义。

在 CLAUDE.md 只保留项目真正需要的规则：保持公开接口、限定文件、运行 python3 -m unittest -v test_tags.py、完成时解释异常分支。复杂的迁移说明放 docs/，并写清何时读取。不是所有规则都要删到固定 100 行或 2000 字；先看内容对行为是否有价值，再做减法。[书1][书2]

2. 先探索再实现

3

直接给交互会话以下任务。这是可复制提示模板，不保证任何版本仅凭文字就拥有只读权限；应同时使用宿主提供的权限控制。

读取 tags.py、test_tags.py 和项目规则。
先说明现有行为、可能受影响的调用方和计划，暂不修改。
目标：normalize_tags 增加稳定去重；保留首次出现顺序。
非字符串继续抛 TypeError；不得吞掉异常或改写输入列表。
只允许修改 tags.py 和 test_tags.py。
验收至少覆盖空输入、重复值、顺序、非法类型、输入不变。
如果旧测试与目标冲突，先列出冲突，不通过删测试消除失败。

读计划时检查三点：是否识别稳定顺序、是否修改了公共签名、是否遗漏其他调用方。计划正确后进入实现，先跑现有测试建立基线，再做最小修改。若基线已经失败，保留失败项并单独归因，不能将所有失败都归咎于新修改。

Agent篇的 day16 Skill 包含 name、description、参考资料、脚本、输出结构，这种包结构可以迁移到代码任务。下面给出项目内示意内容，宿主的发现路径和字段支持需要以其版本文档确认；它不是已安装的插件。

---
name: stable-refactor
description: 公开接口保持不变的局部重构；适用于已有测试和明确写入范围的任务。
---
# 稳定重构
1. 读接口契约和调用方；记录现有失败。
2. 明确允许写入的文件及兼容性要求。
3. 完成最小变更，运行目标测试和受影响回归。
4. 对照 diff 检查异常路径、排序、编码与资源释放。
5. 输出改动、命令、结果、未覆盖事项和回退方法。
涉及数据库迁移或外部发布时使用相应专门流程。

从课件迁移的是“参考资料→现成脚本→结构化结果”的方法，不是销售指标本身。例如编程 Skill 的 references 可以放接口约定，scripts 放仓库已有检查器，assets 放评审模板。不要把每次任务输入都写成永久 Skill，也不要重复实现已经存在的测试工具。[课1]

4. 用可运行的检查证明约束逻辑

3

下面是通用路径归属检查器，不是 Claude Code Hook API。保存为练习目录的 check_scope.py，先离线验证算法，再按当前宿主文档接入事件。它只检查传入路径，不阻止另外一个未受控 shell，因此不能作为完整安全边界。

from pathlib import Path

def allowed(root, candidate):
    base = Path(root).resolve()
    target = (base / candidate).resolve()
    return target.is_relative_to(base)

if __name__ == "__main__":
    root = Path.cwd()
    assert allowed(root, "tags.py")
    assert allowed(root, "src/../tags.py")
    assert not allowed(root, "../outside.txt")
    assert not allowed(root, root.parent / "outside.txt")
    print("scope: 4 checks passed")

python3 check_scope.py

它要求 Python 3.9+。正例与 .. 负例应同时通过断言；生产检查还要考虑符号链接竞态、工具实际 cwd、路径大小写及不同操作系统行为。接 Hook 后再做事件级验证：允许行为通过、拒绝行为确实未执行、检查器崩溃时结果明确。不能只看到脚本输出“拒绝”就断言宿主阻断成功。

5. Vibe 待办应用从一句话变成验收矩阵3 个重点▾ 点开看本节重点
本节重点
  • 制作浏览器本地待办应用，持久化仅用 localStorage
  • 功能：新增、编辑、完成/取消完成、删除、刷新恢复
  • 边界：空标题禁止；纯空白 trim 后判断；同名任务各有独立 ID
3

旧稿的一句需求可以展开为如下任务卡，适合把原型做得可检验：

制作浏览器本地待办应用，持久化仅用 localStorage。
功能：新增、编辑、完成/取消完成、删除、刷新恢复。
边界：空标题禁止；纯空白 trim 后判断；同名任务各有独立 ID。
异常：localStorage 中存在损坏 JSON 时显示恢复提示，不静默覆盖原数据。
安全：用户文本按文本渲染；输入 <img src=x onerror=alert(1)> 不执行脚本。
交付：运行说明、数据结构、可复现的手动验收步骤、已知限制。
不接后端，不处理真实用户数据，不自动部署。

按顺序操作：空白输入应被拒绝；新增两个同名任务，删除其中一个后另一个仍在；刷新后完成状态保持；人为放入损坏 JSON，页面应进入明确恢复流程；输入 HTML 字符串，页面应显示文字而非执行。这里的“手动验收”是待执行清单，本次未创建该应用，也没有宣称浏览器端已通过。

6. 重构如何收口

3 
python3 -m unittest -v test_tags.py
git diff --check
git diff --stat
git diff -- tags.py test_tags.py

先看测试，再读 diff：有没有修改测试期望来掩盖退化，有没有把异常捕获成空结果，有没有顺手改无关模块。独立评审应拿到需求和补丁，不只拿执行者的解释。大重构按接口或垂直功能切增量，而不是“每个文件分一个 agent”。一个接口跨三个文件时，让单一负责人维护一致性往往更省协调成本。

如果会话停滞，区分仍在生成、等待权限、工具超时、进程已退出。未取得新证据前不要重复发同一任务造成双写。交接记录应含完成的子目标、测试状态与待处理问题；哈希只用于核对文件版本，不能替代独立执行和内容评审。

本库真实落地（源码核对，2026-11-04）

  • 本库 AI 协同编程的证据不是「用没用 AI」，而是「AI 改过的文件留没留痕」（本次实测）：~/.hermes/scripts/ 下同一个门禁脚本有 4 个带日期戳的备份——dispatch-guard.py.bak-20261104-jev2、dispatch-guard.py.bak-20261104-probe-rewrite、dispatch-guard.py.bak-20261104-proberegex、dispatch-guard.py.bak-jev-20261104-1357。
    一个人手工改 4 次只会有 1 个 ~ 备份，4 个带语义后缀的备份是「多次 AI 动手 + 每次可回滚」的指纹。
  • 自定义 skill 目录是 VibeCoding 的产物形态：projects/agent-service-toolkit/.claude/skills/ 下有 dependency-refresh/（含 references/live-e2e.md）、smoke-test/ 等 skill，把「刷新依赖」「冒烟测试」这类重复动作写成 Skill 而不是每次描述一遍。
    本库知识库侧也一样：~/.hermes/skills/software-development/ 下 100+ 个 SKILL.md，本次任务就用到了 receipt-declare-verify、error-ledger 两个。
  • AI 协同的纪律在 AGENTS.md 里被写成硬规则：写操作派子智能体、审查链 OC→DSH→Claude→Codex 轮次 ≤2、trace 带 sha256、同错 3 次停手。规则不是建议，是派单门禁的判据（dispatch-guard.py 遇到写操作会拒派非真通道）。
  • 和课件讲法的差异：课件/博客讲 VibeCoding 多强调「一句话生成整个应用」；本库的经验是 AI 改代码必须绑定可回滚的备份 + 可复跑的验收命令，速度来自「改完立刻验证」，不是来自「一次写对」。
  • 本库暂无：没有 Claude Code 的使用度量（每次会话改了哪些文件、耗时多少），协同质量靠复盘经验而非数据。
