六员协作与 Codex：按契约分工、按证据交接

本主题合并六员工具教程和渠道候选管理。Claude Code 的项目内用法见编程篇，token 分档与计费见性能篇。核验日：2026-11-03。

多开几个会话不会自动提高交付质量。每个执行者都需要目标、允许写入的路径、输入版本、验收标准和退出条件。如果两个会话改同一文件，或审查者只读执行者写的“已通过”，增加角色反而增加误判。协作首先是一套责任和证据协议，然后才是模型选择。

Agent课件将子代理用于复杂研究、独立上下文和专门工具，并明确不推荐用于单步极简任务、主代理必须查看所有中间数据的任务。书籍《Harness工程》讨论感知、规划、执行、反思；《Codex提效手册》强调先列计划、知识库规则和人工核验。Codex 当前官方接口提供非交互执行、沙箱选项和事件流，这些能力可承载上述协议，但不能替代协议本身。[课1][书1][书2][业1]

六员是本地团队约定，不是产品的能力上限。旧稿用“10 分钟内只能 Codex、超过 10 分钟只能 Claude”“Qwen 没有独立规划能力”描述角色，证据不足以推广；本篇保留岗位偏好，撤下固定时长推断能力的结论。[本1]

同一个产品可以换模型，但更换模型不意味着运行时、工具权限或角色责任也被替换。不同供应商提供“兼容接口”也不保证工具调用、事件流、错误协议全部兼容。渠道评估至少区分四层：是否可用、协议是否兼容、任务质量是否达标、成本是否可接受。

本地总网规定配置类操作串行、实现与审查分离；这些属于团队制度，引用时保留适用范围。书籍把“高配规划、低配执行”作为可用策略，并不要求把所有成员改成同一模型。任务路由选择承担者，运行时模型切换是另一个配置动作，不能偷偷合并。[本1][书2]

输入输出契约3 个重点▾ 点开看本节重点
本节重点
  • 有效输入至少包含目标、允许文件、基线版本、成功标准、预算或时限、失败返回方式
  • 有效输出包含状态、修改清单、检查结果、未完成事项和证据位置
  • “已完成”没有文件或命令支撑，不应推动状态机进入完成态
3

有效输入至少包含目标、允许文件、基线版本、成功标准、预算或时限、失败返回方式。有效输出包含状态、修改清单、检查结果、未完成事项和证据位置。“已完成”没有文件或命令支撑，不应推动状态机进入完成态。

状态可采用 planned → running → review → done，出现失败则进入 failed。这是本篇教学契约，不是某产品内置 schema。业务批准应绑定具体产物版本；审批后产物改了，需要重新判断批准是否仍适用。退出码 0、出现最后一条消息、收到一个文件，三者都不能单独证明任务通过验收。

2. 使用无凭据任务卡

3 
【免凭据】子智能体执行：normalize-tags
目标：实现标签规范化，稳定去重并保留首次顺序。
输入：已确认版本的 tags.py、test_tags.py、项目指令。
写白名单：tags.py、test_tags.py、handoff.md。
验收：python3 -m unittest -v test_tags.py；检查输入不变与非法类型。
交付：修改清单、运行命令与退出码、失败项、未验证事项。
停止：最多重试 2 次；范围外需求返回说明。
边界：不读凭据、不外传本地内容、不修改其他文件。

这里的免凭据指任务处理内容不需要秘密；若 CLI 自身需要已有登录，凭据仍由既有环境提供，不进入任务卡。工具调用若会把本地资料发送到远端，必须符合当前会话授权。本次知识库融合仅使用公开 GET，不执行任何模型 CLI 网络请求。

下面是已获得相应环境授权时的终端用法示意，task.txt 存上述卡片，位于专用练习仓库：

codex exec --sandbox read-only "读取项目规则并说明修改计划，暂不改文件。"
codex exec --sandbox workspace-write --json - < task.txt

read-only 是沙箱选择；workspace-write 不等于“只写卡片中的三个文件”，更细的边界仍需工具策略或外部验证。沙箱具体覆盖范围依赖宿主系统。非 Git 目录只有确实需要、且信任路径已核实才使用 --skip-git-repo-check；它跳过仓库检查，不能增加权限或解决所有路径错误。[业1]

3. 用离线检查验证交接格式3 个重点▾ 点开看本节重点
本节重点
  • 把下列程序保存为 「check_handoff.py」
  • 它验证的是已汇总的交接记录，字段不是直接照搬 Codex 原始事件；生产接入应从实际事件和独立检查填充，不能让模型随意写一个 「passed: true」
  • and isinstance(files, list)
3

把下列程序保存为 check_handoff.py。它验证的是已汇总的交接记录，字段不是直接照搬 Codex 原始事件；生产接入应从实际事件和独立检查填充，不能让模型随意写一个 passed: true。

def accepted(receipt, allowed_paths):
    checks = receipt.get("checks", [])
    files = receipt.get("files", [])
    return (
        receipt.get("status") == "review"
        and isinstance(files, list)
        and bool(files)
        and set(files) <= set(allowed_paths)
        and bool(checks)
        and all(check.get("exit_code") == 0 for check in checks)
        and receipt.get("remaining") == []
    )

if __name__ == "__main__":
    good = {"status": "review", "files": ["tags.py"],
            "checks": [{"name": "unit", "exit_code": 0}], "remaining": []}
    paths = ["tags.py", "test_tags.py"]
    assert accepted(good, paths)
    assert not accepted({**good, "checks": []}, paths)
    assert not accepted({**good, "files": ["outside.py"]}, paths)
    assert not accepted({**good, "status": "running"}, paths)
    assert not accepted({**good, "checks": [{"exit_code": 1}]}, paths)
    assert not accepted({**good, "remaining": ["未验"]}, paths)
    print("handoff: 6 checks passed")

python3 check_handoff.py

它用于防止空测试集、越界路径、仍在运行、失败检查、未完成事项被当完成，不提供安全认证。真实验收还要独立读取文件，验证实际路径归属，重跑测试，并对照基线 diff；如果交接人能改记录和产物，单独附一个 SHA-256 也不能证明过程没有被篡改。

4. 多任务如何划分

3

先把接口设计统一完成，再分配独立模块。例如解析器、展示层和文档可以在接口约定后独立处理；两个任务都需要修改同一个路由表时，由一个负责人串行整合。每个任务必须知道其依赖产物的版本，不能读到另一个任务尚未完成的一半文件。

课件自定义子代理包含 name、description、system_prompt、tools、model；这说明角色既有提示也有工具边界。迁移到六员时，任务描述不能替代工具限制，角色名称也不能替代实际能力探测。[课1]

如果并行结果冲突，停止合并，保留各自的差异，回到接口契约；不要让后来者覆盖前一人的未验收修改。重复运行含外部副作用的任务前先检查已有结果，避免“失败重试”造成重复付款、重复发消息或重复发布。

WHY：为什么聊天流之外还要进度看板

3

前文的责任与交接契约解决了“谁执行、拿什么证据交接”，却没有解决人如何看见协作过程。只有聊天流，难以回答任务处于 N1—N6 哪个节点、哪个子单阻塞、验收为何退回；只有看板，又看不到产生状态变化的消息与工具事件。前端因此需要同源的两种视图：对话/事件流解释过程，DAG 或 Kanban 展示进度，trace 与 receipt 提供下钻证据。

展示层不能直接成为第二套执行状态。若浏览器自行推断完成度、回写 checkpoint 或把“最后一条消息到了”当作完成，前端就会与 LangGraph 状态机耦合，甚至显示假完成。Cato 的单向数据流适合作为约束：执行层产生事实，投影层转换成视图，展示层只读；用户输入或审批若需要回写，应走独立、受权且幂等的命令接口，而不是让看板组件直接改任务状态。[业3]

HOW：接入 LangGraph 前端交付栈并展示 N1—N6

3

  1. 用同一场景做两候选 spike，再定唯一前端。 将 Flightdeck 与 OpenHands Agent Canvas 作为实现候选，准备同一份离线任务夹具：两个 Agent、一次 N5 验收失败退回 N4、一次断线重连。分别记录 ACP 实际接入方式、支持的事件字段、聊天与看板同步、扩展点、所需改动、资源占用和许可证复核结果。供料只证明候选方向，不证明六员已经提供 ACP 接口；若某成员没有对应适配器，应先补协议适配，不能在前端伪造事件。完成对照后只保留一套主前端，避免双看板成为新的状态分叉。

  2. 从权威状态生成只读投影。 LangGraph 总网改造已经规定 N1—N6 映射为显式 state graph，并以 durable execution、结构化 trace、任务状态契约作为地基。[本1] 前端不复刻这套状态机，建议采用以下单向链路：

text LangGraph state/checkpoint + tasks/inbox + trace/receipt → 只读投影接口 → 前端事件适配器（ACP 只承担多 Agent 接入适配） → 聊天流 + N1—N6 DAG/Kanban + 证据下钻

投影是本地集成设计，不是上述产品的现成字段。最小字段可定为 task_id、node、node_state、owner、last_event_seq、artifact_ref、receipt_ref、trace_ref、updated_at。node_state 必须由图事件或任务状态转换而来，禁止前端用计时器猜进度；receipt_ref 未通过时不得显示 done。聊天与看板使用同一 task_id + last_event_seq 排序和去重，trace/receipt 只保存引用，不把敏感正文复制进浏览器。

  1. 把六个节点映射成可验收的视图。 不只画六个静态方框，而要为每个节点绑定真实状态和证据：
看板节点 主要展示内容 完成/回流的依据
N1 分诊 任务、A/B/C 档、路由结果 档位已写入任务状态；越权或不可逆任务升 C
N2 规划 全景图、方案与待澄清项 信息不足回到澄清，不进入派单
N3 派单 子单、执行者、写集、门禁结果 guard 未通过不能显示已派出
N4 执行 Agent 对话/工具摘要、心跳、当前产物 子单失败或验收回流时保持非完成态
N5 验收 检查命令、退出码、receipt、失败项 未全绿不得显示 done；失败显示返回 N4 的边
N6 收口 最终产物、沉淀去向、清理结果 收口完成后归档，并保留证据链接

  1. 将展示与命令通道分开。 默认页面只读，通过投影接口取数，不直连数据库修改任务或 checkpoint。确需从聊天框发新任务、批准中断或重试时，另走带鉴权、任务版本和幂等键的命令 API；命令结果仍由 LangGraph 状态与事件回流到页面。这样既能保留 OpenHands/Agent Chat UI 的交互能力，也不破坏 Cato 式单向展示原则。

  2. 用正例和反例验收集成。 正例跑通 N1→N6，核对聊天、看板、trace 指向同一任务；反例至少覆盖 N5 失败回流 N4、重复事件不重复渲染、断线重连不漏事件、receipt 未绿不出现 done、静态 Lattice 图不被标成实时状态。最终交付栈保持为 LangGraph 权威状态 + 只读投影 + Flightdeck 或 OpenHands 主前端 + LangSmith/Langfuse 等 trace 下钻，而不是另建一个与总网竞争的前端状态库。

本库真实落地（源码核对，2026-11-04）

  • 本库六员协同靠的不是对话，而是一张带约束的任务表（scripts/sql/shared_task_bus_ddl.sql，本次读源码）：
    sql owner TEXT NOT NULL CHECK (length(trim(owner)) > 0), -- 执行人(被派单方, 六员之一) closer TEXT NOT NULL CHECK (length(trim(closer)) > 0), -- 收口人(必填: 无收口人不得建单) state TEXT NOT NULL DEFAULT 'pending' CHECK (state IN ('pending','claimed','done','failed')),
    「无收口人不得建单」是数据库层约束——协同中最常见的失败不是执行失败，是「没人收口」，本库把它写成了 schema 检查。
  • 防双抢用 fencing token：scripts/task_bus.py task_claim()（L133）抢单返回 claim_token，后续 task_heartbeat()/task_complete() 都要验 token；心跳超 TTL 由 sweep()（L434）回收。多 Agent 协作的并发问题，本质是分布式锁问题。
  • 结果回传是 append-only：inbox 表 state IN ('unread','read','acked')，执行人回写结果、收口人 inbox_take → inbox_ack 逐级确认——避免「结果被吞」和「谁看过了说不清」。
  • 工具选型在本库是「按岗职派」：执行/批量 → DSH，开发/写码 → Codex，验/审 → Claude，测试/审查 → OC，小运维 → Qwen，规划 → Hermes；dispatch-guard.py 会给路由建议，但要与岗职表双重核对。
  • 和课件讲法的差异：课件讲 A2A 协议（Agent Card / Task 生命周期）；本库用的是同一套语义的简化版（tasks 表 + inbox），没有标准协议栈，但字段名与 A2A 对齐（task_id/state/owner）。
  • 本库暂无：六员之间没有实时消息总线（靠库轮询），也没有标准 Agent Card 交换。
