L5 Agent 框架选型与平台生态（深挖整合）

← 返回 L5-Agent工程 相关：核心循环与业务落地 · 多Agent协作与编排 · 工具层与协议 · 记忆与自进化 · 生产化可靠性与评估 · OpenClaw模块协同

导读

这篇回答三个实际问题：一个 Agent 项目该从哪一层起步，哪一个代码框架适合哪类负载，以及对外的 IM 入口要不要接。

核心结论如下。

  1. 阶梯，不是并列。 Coze 用来验证想法（约 1 天），Dify 用来在企业内网落地（约 1 周），LangChain 或 LangGraph 用来做生产（约 1 个月以上）。反过来用，即 Coze 做生产或 LangChain 做 demo，都是错配。
  2. 没有单一赢家，按负载选。 LangGraph 适合显式状态机、断点续跑和人审。CrewAI 适合快速搭多角色原型。Claude Agent SDK 适合 Claude 为主的工具密集任务。OpenAI Agents SDK 适合 OpenAI 生态下的最短上手路径。
  3. 抽象层级越高，细粒度控制越贵。 选框架前要先确认，自己要调的那个参数，在该框架的那一层是否暴露。
  4. 2026 年的选型门槛已经从"上手快不快"转向"能不能上生产"。 断点续跑、结构化 trace 和显式状态图是三条硬指标。LangGraph 在三条上都排在前列。
  5. IM 入口是候选，暂不部署。 LangBot 可以做知识库的 IM 化入口，但它的内置 RAG 弱于本库现有的三路混合检索。触发条件满足前不接入。

一、选型总原则与阶梯

1.1 先找最简单的可行方案

Anthropic 在《Building Effective AI Agents》中给出的前置原则是：找最简单的可行方案，只有在需要时才增加复杂度。 能用工作流（固定路径）解决的问题，就不要上 agent（动态路径）。Agent 的本质是 LLM 在循环里根据环境反馈调用工具。

这条原则决定了后面所有选型的起点。低代码平台、代码框架和自研循环都是为不同复杂度准备的，选哪一层，先看任务是否真的需要 LLM 自己决定下一步。

1.2 Coze、Dify、LangChain 的阶梯

三者的本质区别是"控制粒度"与"落地速度"的权衡。

层级 时间节奏 用途 关键取舍
Coze（扣子） 约 1 天 验证想法 上手最快，但控制粒度最粗
Dify 约 1 周 企业落地，数据不出内网 开源可私有化，灵活性有限
LangChain / LangGraph 约 1 个月以上 生产交付 控制最细，学习和运维成本最高

判断口诀是：先用 Coze 验证想法（1 天），再用 Dify 落企业（1 周），最后用 LangChain/LangGraph 做生产（1 个月以上）。 选型按"验证、私有化、生产"三步走，不按"哪个新就用哪个"。

这条阶梯与"三者是并列关系"的说法不同。《Coze+Dify+LangChain》一书把三者并列介绍，读者容易产生"三者可以平替"的印象。从工程实践看，Coze 和 Dify 能做的事，LangChain 都能做，只是要写代码。反过来不成立。因此阶梯方向是单向的。

二、低代码平台的边界

2.1 所有平台都在卷同一套标准积木

《Coze+Dify+LangChain 零基础搭建》把智能体拆成五个标准模块，这是所有低代码平台的通用骨架。

  1. 提示词（指令说明书）：定义角色、输出格式和约束。
  2. 插件（工具箱）：独立功能的小模块，想用就装，不用就卸。
  3. 知识库（专业词典）：解决大模型在专业领域回答不准、信息滞后的问题。
  4. 记忆系统：感官记忆（第一印象、单次会话）加长期记忆（跨会话积累）。
  5. 工作流（行动路线图）：把多步操作串成固定路径。

低代码平台之间的差异，不在于有没有这五个组件，而在于组件的控制粒度，以及是否开源可私有化。这一点决定了平台的天花板。

2.2 Coze：快，但天花板低

Coze 的设计哲学是可视化拖拽、插件市场和卡片输出。它还提供"图像流"节点做多模态，把纯文本输出变成易读的卡片。书中列出七个适合场景：发票识别 Agent、标书阅读 Agent、知识问答 Agent、模拟面试官 Agent、小学生英语陪练、旅游助手，以及抖音和小红书的文案提取仿写。

它的硬边界有四条。

  • 数据必须在字节云上，不能私有化。 这是它对企业客户的最大门槛。
  • 工作流是固定路径 DAG，不是动态状态机。 遇到"LLM 自己决定下一步走哪"的场景就会卡住。
  • 复杂多 Agent 协作能力弱。 做不了"研究员、写作者、审查者"这种多角色循环。
  • 自定义 Python 工具链受限。 想接内部 API 或写复杂预处理逻辑时会碰壁。

2.3 Dify：开源可控，灵活性也有限

Dify 的核心优势是开源并且可以私有化部署。在金融、医疗、政府等行业，数据不出内网是硬要求，这是 Dify 能在企业客户中对抗 Coze 的主要原因。它提供五种应用形态：聊天助手、Agent、工作流、RAG 和文本生成，覆盖了大部分企业内场景。

它的边界有三条。

  • 工作流节点同样是 DAG 模型，复杂循环和动态路由不如 LangGraph。
  • 多 Agent 协作原生支持弱，往往要自己拼接。
  • 与现有代码库集成时，"回调处理器"这类细粒度钩子不如 LangChain 原生。

2.4 三类平台都解决不了的问题

《Coze+Dify+LangChain》第 3 章专门讲智能体的局限性。三类局限，低代码平台都绕不过去。

  • 数字识别不准。 大模型对金额、日期、编号等精确数字天生薄弱。低代码平台靠插件和知识库缓解，但不能根治。
  • 数学逻辑短板。 复杂计算必须外调代码，不能让模型心算。
  • 多模态和视觉陷阱。 图像识别有偏差。"图像流"节点只是封装，不改变模型本身的局限。

据此可以得出一个判断：低代码平台能覆盖约 80% 的常规场景，剩下约 20% 的高可靠性场景，例如金融计算、合规审查和精确数据处理，必须靠代码框架。

2.5 本库的对照

本库的六员体系与三类平台的对应关系如下。

  • Hermes：本质上是代码框架层的 Agent，对应 LangChain/LangGraph 一层。它通过 skill 系统提供了类似低代码"装模块"的体验，这是本库与纯低代码平台的最大差异。
  • DSH、Claude Code、Codex：已经在代码框架层，不需要再考虑 Coze 或 Dify。
  • OpenClaw：定位接近"Coze 的私有化版本"，即可视化加插件市场加多模态，适合给非工程师使用。

落地建议也随之明确。客户要快速给业务部门演示，可以用 Coze 做原型。要求数据不出内网，推荐 Dify。要求生产级和可观测，直接用 Hermes 或 LangGraph 一层的能力。

3.2 同一任务三框架跑：一手代码的启示

oxylabs 的横评把同一任务分别用 LangGraph、Claude Agent SDK 和 CrewAI 实现。它有两点值得记住。

  • 三个目录里的 schema.py 输出契约字节相同，所以横评的结果具有可比性。
  • 细节差异暴露了各家的设计哲学。LangGraph 的 max_tokens 就是 ChatAnthropic 的普通参数。Claude Agent SDK 没有 max_tokens 选项，要改用 CLAUDE_CODE_MAX_OUTPUT_TOKENS 环境变量。CrewAI 要改 thinking 或 output_config，得写 MatchParams httpx 拦截器去 patch 请求体。

由此得出的结论是：抽象层级越高，细粒度控制越贵。 选框架前先确认，你要调的那个参数在该框架的那一层是否暴露。

3.3 LangGraph：有状态编排的事实标准

LangGraph 的核心是状态机模型。每个节点是一个函数，边是控制流，State 是带 reducer 的 typed dict，并且支持环（cycles）。Agent 可以"重试、反思、再调用"，这是它与 DAG 框架的根本差异。

它有两个持久化原语，二者分工不同。

Checkpointer Store
持久化什么 图状态快照 应用自定义 KV
作用域 单线程（thread_id） 跨线程
记忆类型 短期、线程内 长期、跨线程
用途 对话连续性、HITL、time travel、容错 用户偏好、事实、共享知识
访问方式 config 里传 thread_id 节点或应用代码里读写

LangGraph 的差异点在人审（HITL）。下面的代码示意一个带人审中断的 agent，其中 execute_sql 只在写查询时需要人工批准。

agent = create_agent(model=..., tools=[...], middleware=[
  HumanInTheLoopMiddleware(interrupt_on={
    "execute_sql": {"allowed_decisions": ["approve","reject"], "when": is_write_query},
    "write_file": {"allowed_decisions": ["approve","edit","reject"]},
  }),
], checkpointer=InMemorySaver())   # 生产换 AsyncPostgresSaver / MongoDBSaver（官方原文注释）
config = {"configurable": {"thread_id": "some_id"}}
result = agent.invoke({...}, config=config)   # 撞到 interrupt 暂停，之后 Command(resume=...) 恢复

官方设计动机是：持久化为一等公民，每一步都读写状态检查点。这也是很多公司选择 LangGraph 的原因。LangGraph Platform 的 /threads/{thread_id}/runs 在 interrupt() 时返回 409 加 payload，前端收集用户输入后 POST Command(resume=...) 即可恢复（turion.ai 实战，二手，但与官方机制一致）。

checkpointer 的具体配置、断点续跑的生产要求，以及 Postgres 等后端的选择，归入 生产化可靠性与评估 详述，这里不重复。

LangGraph 不适合的情况也很明确。简单任务不需要图，违背 Anthropic 的复杂度原则。纯 TypeScript 的轻量聊天应用用 Vercel AI SDK 就够，它没有等价的状态管理与 HITL 检查点，但也就不必承担 LangGraph 的复杂度（BearPlex 评测，二手）。

3.4 CrewAI：角色扮演式快速协作

CrewAI 的核心模型由三部分构成（官方文档口径）。

  • Agent：role、goal、backstory，加上 tools、allow_delegation 和 llm。
  • Task：description 和 expected_output，加上负责的 agent 与工具。
  • Process：sequential（顺序）或 hierarchical（层级，manager 分派）。枚举类型锁死，只有这两档。

它的 MCP 集成有 Stdio、SSE 和 Streamable HTTPS 三种 transport，在三框架里最深（letssdatascience，二手）。MCP 与 A2A 的协议细节归入 工具层与协议。

CrewAI 的强项是快速原型。它的典型适用说法是"周五下午向利益相关者卖一个 demo 的最快路径"（pasqualepillitteri 横评的原话式总结）。它的生产短板有三条：共享状态需要手动调优，存在抽象泄漏（见 3.2 节的 httpx 拦截器），以及 Python-only，复杂技术栈的组织有摩擦（latenode 与 oxylabs）。

企业采用口径上，CrewAI 自称覆盖美国 Fortune 500 的 60%（appinventiv 转述）。这是厂商口径，未经独立验证，不宜直接引用为事实。

3.5 Claude Agent SDK：把 Claude Code 当库用

Claude Agent SDK 的 Python 包名为 claude-agent-sdk，TypeScript 包名为 @anthropic-ai/claude-agent-sdk。它暴露 Claude Code 的 agent 循环、内置工具、上下文管理和权限系统。该 SDK 原名 Claude Code SDK，2025 年末泛化后改名。

它的实现方式是：spawn Claude Code CLI 作为受管子进程，通过 stdio 通信，并返回异步的 typed message 流。认证使用 ANTHROPIC_API_KEY。Bedrock 和 Vertex 是否可直接替换，要查当期文档，因为 tech-insider 明确警告支持情况随版本变化。

hooks 是它的治理点。PreToolUse 可以在执行前拦截危险命令，PostToolUse 记录每次编辑，SessionStart 和 SessionEnd 做起止钩子。hook 是开发者自己的代码，在循环的固定点被调用（morphllm 汇总官方文档）。

有一个语言差异的坑需要留意（Shivansh Gupta 实测，二手）。SessionStart 和 SessionEnd 在 TypeScript 中是 callback，在 Python 中只支持经 settings 文件配置的 shell command hook。Python 主栈在设计架构前，要先查 hook 可用性表。

内存方面，官方经验口径约为每个 agent 1 GiB RAM（子进程模型）。50 个并发 session 就是 50 个进程，容器要按此预留，并设置 maxTurns（happycapy 引官方，二手，需要自测）。与 LangGraph 的进程内图相比，这正是它在 serverless 长任务中表现弱的根因（横评结论）。

模型锁定的代价也要算清楚。pasqualepillitteri 的成本观察指出（二手，价格随时间变化），绑定 Claude Agent SDK 的系统，无论任务是否需要 Claude，都要付 Claude 的溢价。LangGraph 和 CrewAI 的用户则可以按任务换模型，让贵的模型负责写代码，便宜的模型负责解析。选它之前，要先接受"模型自由度换工程效率"这笔交易。

与本库的关系是：Claude Agent SDK 与 Claude Code 同源。若要程序化驱动 Claude Code 干活，它就是对应路径，hooks 可以做审批门禁，对应本库的审批拦截实践。

3.6 OpenAI Agents SDK：四原语的极简路线

OpenAI Agents SDK 只有四个原语。

  • Agents：instructions、tools 和 typed output。
  • Handoffs：agent 之间移交控制权。
  • Guardrails：与 agent 并行运行，违规时可以短路。
  • Sessions：零样板的持久会话。

此外还内置 tracing（官方口径，经 cohorte 和 temporal 转述）。Hosted tools 包括 WebSearch、FileSearch、Computer 和 Code Interpreter。自写工具用 @function_tool 装饰器。

它与 LangGraph 的取舍在实测评测中有明确结论（二手）。抽象更高，所以上手快。但 Handoff"适合基础路由，规模化下缺鲁棒的状态管理与并发委派"。复杂编排要回到 LangGraph 的显式图。

3.7 其他框架与 SDK 一览

除上述四者外，选型还会遇到以下几类。

  • Vercel AI SDK：不是 agent 框架，但覆盖纯 TypeScript 的流式聊天和轻 agent 场景，约 80% 的应用场景够用。
  • Microsoft Agent Framework（MAF）：由 AutoGen 与 Semantic Kernel 合并而来，见第六节。
  • Google ADK、AWS Strands、Mastra：分别绑定 GCP、AWS 和 TypeScript 生态，见第四节的生产化横评。

四、生产化三维度横评：八个方案

前面的四框架是横向跑同一任务。本节换一个视角，看生产化三件套。三件套分别是：

  1. durable execution：崩溃后能从精确断点续跑，而不是整单重跑；
  2. structured trace：结构化的 span 与 trace 树，而不是纯文本日志；
  3. explicit state graph：机器可校验的显式状态图，而不是文字流程图。

这是"能不能上生产"的硬指标，与前文"上手快不快"的标准互补。

AWS Strands ◐ 会话快照级（S3 持久化），HITL 仍在设计中 ✅ 原生 OTel 全链路（模型、规划、工具、handoff） ✅ GraphBuilder 硬 DAG，可与 Swarm 嵌套 AWS 与 Bedrock 栈首选

OpenAI Agents SDK ◐ 会话级（RunState 序列化），无图级 checkpoint，崩溃后从头跑 ✅ 内建默认开启（自有 span 模型，非原生 OTel，需桥接） ✗ 无图引擎，仅 Handoff 建议式路由 单 agent、少工具、快速原型
Claude Agent SDK ◐ 会话级：continue、resume、fork 加 SessionStore ◐ OTel 三信号，但 traces 仍是 beta ✗ 无图：subagent 委派是模型决策而非硬控制流，dynamic workflow 要靠写 JS 复用 Claude Code 生态，脚本化扇出
Mastra ✅ suspend/resume，最成熟的 HITL，快照可跨进程 ✅ 原生 OTel，官方提供 Langfuse 与 Datadog 导出器 ✅ typed workflow（.then、.parallel）加最细的 delegation hooks TypeScript 项目，委派治理最细

三个维度的分项结论如下。

  • 断点续跑第一：LangGraph，因为它是 super-step 粒度，并且 time-travel 无争议。其余方案要么是会话级（OpenAI、Claude、Strands），要么是任务级（CrewAI、ADK）。
  • 结构化 trace 最合规：Microsoft、Google ADK 和 AWS Strands，三者都官方声明遵循 OTel GenAI 语义约定。LangGraph 胜在观测平台生态最厚，LangSmith 与 Langfuse 均可插拔。
  • 显式状态图第一：LangGraph，它的 API 被后来者对照，是事实标准。紧追者是 Google ADK 2.0。OpenAI 与 Claude 两个 SDK 在这一维度不合格，无法机械校验拓扑。

对本库的启示。本库是 Python 加六员协作加多模型混合的 WSL 单机环境。改造成本最低的是 LangGraph：它是 Python 原生，本体已安装，只差 langgraph-checkpoint-sqlite。六员分工天然对应 supervisor 模式，Send 可以做并行派单。get_state_history 还能直接支撑"同错 3 次停手后回放"的审查需求。

云绑定方案对本库是负担。MAF 绑 Azure，ADK 绑 GCP，Strands 绑 AWS。Mastra 受限于 TypeScript。具体的落地方式见 多智能体协作与编排。

五、实操选型：决策树与成本基线

5.1 决策树

选型按四个维度判断：状态复杂度、HITL 需求、模型自由度、部署形态。决策树如下。

需要 HITL / 断点续跑 / 长任务状态？ ──是──→ LangGraph（Postgres checkpointer）
        │否
        ├ 能接受 Anthropic 模型绑定吗？
        │     是 → 工具密集 / 开放任务 → Claude Agent SDK
        │     否 → OpenAI 生态？ → OpenAI Agents SDK（四原语，最快）
        │            多角色协作快速原型 → CrewAI
        │            纯 TS 流式聊天 / 轻 agent → Vercel AI SDK
        └ 模型要按任务轮换（省成本）？ → LangGraph / CrewAI（模型无关）

另一棵更简单的决策树来自生产化六大坑的选型文章，按技术栈与需求直接分流。

  • 已经在 Azure 或 .NET 生态中：选 MAF。
  • 角色分工清晰、门槛低的 PoC：选 CrewAI，搭配 Flows 与结构化输出。
  • 复杂状态、需要 HITL 断点或可回放：选 LangGraph，它是默认推荐。

5.2 补充纪律

appinventiv 的建议与 Anthropic 原则同向。两条纪律如下。

  • 把领域逻辑留在框架之外。 换框架时才不会连根拔起。
  • 多个框架并存时，按 workload 分派，而不是全公司统一。

5.3 成本基线

CrewAI 官方的三个真实项目给出了成本基线。

项目 架构 单次成本 耗时

客服分诊 Classifier → Doc Searcher → Responder → Escalation 约 $0.03/ticket 处理 80% 至 90% 的 tier-1 工单

七、IM 入口候选：LangBot

7.1 LangBot 是什么

LangBot 是一个开源的生产级 IM 机器人平台，GitHub 仓库为 langbot-app/LangBot，2022 年创建，发布 214 个 release。它用一套代码接入 10 多个聊天平台，把 LLM 变成聊天机器人或 Agent。

支持的聊天平台包括：QQ（个人号与官方）、微信（个人与公众号）、企业微信、飞书、钉钉、Discord、Telegram、Slack、LINE、KOOK、Matrix、Satori 和 Email。

模型后端通过 LiteLLM 统一请求层接入，覆盖 OpenAI、Anthropic、DeepSeek、Gemini、xAI、Moonshot、智谱、Ollama、LM Studio，以及硅基流动、百炼、火山方舟、魔搭和 302.AI 等网关。备忘写明，现有的 provider 全部可以接入。

7.2 核心能力与相关度

按对本项目的相关度排序，核心能力如下。

能力 说明 对本项目相关度
内置 RAG 默认 Chroma 向量库加 Rerank 精排，可插拔外部知识库（RAGFlow、Dify、FastGPT） ⭐⭐⭐ 与本地 RAG 栈同源（都是 Chroma），但能力弱于本地三路混合检索
MCP 协议 既做 MCP client（Stdio 与 HTTP），又暴露 /mcp 端点作为 MCP server，agent 可编程管理它 ⭐⭐⭐ 六员可直接管理 LangBot
Skills 与代码沙箱 按需加载指令包，用 Docker、nsjail 或 E2B 隔离执行 ⭐⭐ 与 Hermes 技能体系理念一致
多平台触达 一个机器人覆盖所有 IM ⭐⭐⭐ 手机端查任务、收通知的最强方案
Web 管理面板 浏览器配置，不必改 YAML ⭐⭐
插件生态 数百个社区插件，跨进程事件驱动，支持热插拔 ⭐⭐

7.3 部署方式

LangBot 有三种启动方式。

  • 一行启动：uvx langbot（需要 uv），启动后访问 http://localhost:5300。
  • Docker Compose：cd LangBot/docker && docker compose --profile all up -d。
  • 云部署：aaPanel、Kubernetes、Zeabur 和 Railway。

7.4 与现有体系的关系

LangBot 与六员体系的差异如下。

维度 LangBot 现有六员体系
架构 IM 机器人（消息驱动） CLI 与终端调度
RAG 内置 Chroma 加 Rerank 本地三路混合（dense、sparse、BM25）加图谱
模型接入 LiteLLM 统一层 各自配置 provider
适用场景 对外服务，例如群内问答、客服 内部开发与调度

结论是：LangBot 不替代、不冲突，是"对外服务层"的候选。

7.5 何时接入

备忘给出了明确的触发条件。

该接的情况：

  • 要给学员或同事提供"群里 @机器人 问知识库"的服务，即知识库 IM 化；
  • 需要在手机上多平台管理任务、收取通知，这比 telegram-send 更强。

不该接的情况（现状）：

  • 只想增强本地 RAG。LangBot 内置 RAG 不如现有三路混合检索。
  • 想替代六员体系。两者架构不同。
  • 内存紧张时。LangBot 是多一个常驻进程，而 WSL 总内存 7.8G，备忘写明可用约 3.5G，已经吃紧。

7.6 待办（挂账，不急）

  • 等触发条件满足（学员或同事有 IM 问答需求）再部署。
  • 部署前先评估内存预算。LangBot 加 Docker 至少需要 1G，而当前 WSL 可用约 3.5G。
  • 接入时优先用它的 MCP server 让六员管理它，而不是手动配置。

7.7 Cherry Studio 备注

Cherry Studio 是开源 AI 桌面客户端，支持多模型对话、本地知识库和多模态。它与现有体系的关系是：知识库能力冗余（不如本地三路混合检索），与 OpenWebUI 功能重叠。结论：不接，除非要在 Windows 桌面快速对比模型输出，而现有工具已覆盖这一需求。

Cherry Studio 与 LangBot 的区别在于定位。Cherry Studio 是个人桌面客户端，LangBot 是对外的 IM 服务。

小结

选框架先看任务复杂度，再按阶梯升级：Coze 验证，Dify 私有化，LangChain 或 LangGraph 做生产。代码框架各有负载。LangGraph 在断点续跑、trace 与状态图三件套上排在前列，适合长任务与需要人审的场景。CrewAI 适合快速原型。Claude Agent SDK 与 OpenAI Agents SDK 分别适合 Claude 与 OpenAI 生态下的工具型任务，代价是模型绑定或会话级的恢复能力。

本库走的是"不选框架"的路线，用进程级 agent 与派单协议替代图编排。若将来要把审批做成可执行编排，LangGraph 的 interrupt() 模式是最接近的参考。LangBot 是知识库 IM 化的候选入口，触发条件满足前暂不部署。
