1. 先回答"要不要拆"：两方一手立场

1.1 支持方：Anthropic 的数字

📄 Anthropic 工程博客《How we built our multi-agent research system》给出了少见的量化数据：

  • 架构是编排者—工作者：主 Agent 分析问题、制定策略，并行派生多个子 Agent 搜索，最后汇总；另有独立的 CitationAgent 给论断找来源。
  • 在其内部研究评测中，以 Opus 4 做主 Agent、Sonnet 4 做子 Agent 的多 Agent 系统，比单个 Opus 4 高 90.2%。
  • BrowseComp 评测中，三个因素解释了 95% 的性能差异，其中 token 用量单独解释 80%，另外两个是工具调用次数和模型选择。
  • 代价：Agent 约消耗聊天 4 倍 token，多 Agent 系统约 15 倍。因此只适合"高价值、可大量并行"的任务。
  • 博客明确说：编码类任务可并行的部分少，多 Agent 目前不太适用。

读这组数据要注意：80% 的差异来自 token 用量，意味着多 Agent 的收益很大一部分是"花了更多算力"，而不是协作本身神奇。算账时要问：同样的 token 预算给单 Agent 做并行工具调用，差距还有多大？这呼应 多Agent协作与编排-深挖整合 3.2 节"派单前先对单 Agent 基线算账"。

1.2 反对方：Cognition 的两条原则

📄 Cognition《Don't Build Multi-Agents》的论点是，2025 年的多 Agent 系统很脆弱，构建长时间运行的 Agent 应默认避开。两条原则（原文）：

  1. "Share context, and share full agent traces, not just individual messages"：要共享完整执行轨迹，不只是单条消息。
  2. "Actions carry implicit decisions, and conflicting decisions carry bad results"：每个动作都隐含决策，冲突的决策导致糟糕结果。

他们的例子：做 Flappy Bird 克隆，任务拆给两个子 Agent。一个把背景做成了超级马里奥风格，另一个做的小鸟既不像游戏素材、移动方式也不对，最后的 Agent 只能合并两个互相矛盾的理解。即使共享了上下文，两个子 Agent 仍基于没有事先约定的假设各自行动。推荐方案：单线程线性 Agent，需要时加一个专门的模型做上下文压缩。作者承认压缩很难做好，有时要微调小模型。

1.3 两个立场不矛盾

把两篇放在一起看，分歧在任务类型：

任务特征 倾向 原因
读多写少，子任务彼此独立（调研、检索、分析） 多 Agent 并行 子任务之间没有"隐含决策"需要对齐，汇总时只是合并信息
写多读少，产物需要整体一致（写代码、做设计） 单线程 子 Agent 之间的隐含决策会冲突，合并成本高

本文把它当作选型第一问：子任务的产物是"信息"还是"需要拼在一起的制品"？ 信息可以并行，制品要谨慎。

2. LangGraph 官方的五种多 Agent 模式

📄 LangChain 官方多 Agent 文档把模式归为五类，并强调多 Agent 的核心是上下文工程，即决定每个 Agent 能看到哪些信息。官方同时提醒：很多复杂任务用一个配了合适工具和提示的 Agent 就能完成。

模式 机制 强项 短板
Subagents 主 Agent 把子 Agent 当工具调用，路由全经主 Agent 并行、多跳、分布式开发 用户很难直接和子 Agent 对话
Handoffs 工具调用更新 state 变量，切换当前 Agent 或其提示/工具 多跳、可直接与用户交互 不支持并行
Skills 单 Agent 按需加载专门的提示和知识 实现简单、可直接交互 加载的上下文持续占 token
Router 路由步骤分类输入，分派给一个或多个专门 Agent 再综合 并行强 不支持多跳，每次都多一次路由调用
Custom workflow 用 LangGraph 混合确定性逻辑与 Agent，其他模式可作节点嵌入 灵活性最高 需要自己设计和维护

2.1 官方的量化对比

📄 官方用三个场景对比了模型调用次数和 token（官方明确说数字是示意，不是基准测试）：

模式 单次请求 重复请求（第二轮） 多领域对比
Subagents 4 次 4 次（累计 8） 5 次，约 9K token
Handoffs 3 次 2 次（累计 5） 7 次以上，约 14K+ token，串行
Skills 3 次 2 次（累计 5） 3 次，约 15K token，上下文累积
Router 3 次 3 次（累计 6） 5 次，约 9K token

从这张表能读出三条规律：

  • 有状态的 Handoffs 和 Skills 在重复请求时更省（第二轮只要 2 次调用），无状态的 Subagents 每轮都要走完整流程。
  • 多领域场景下，能并行的 Subagents 和 Router 最省 token；Handoffs 只能串行，最慢。
  • Skills 调用次数最少，但已加载的文档在之后每次调用都要重复处理，token 并不低。

2.2 选型决策

按官方建议整理成问答（📄 官方选择建议 + 本文补充）：

任务是确定性流程？            → Custom workflow（把其他模式当节点）
需要并行 / 上下文很大？       → Subagents 或 Router
需要子 Agent 直接和用户对话？  → Handoffs
单次请求、任务聚焦？          → Skills（最简单）
重复请求、对话有状态？        → Handoffs 或 Skills

📄 模式可以组合：子 Agent 可以内部是一个自定义工作流，也可以用 Skills 按需加载上下文。

3. Subagents：把子 Agent 做成工具

3.1 官方要点

📄 官方 Subagents 文档的核心：

  • 主 Agent 负责路由、传什么输入、如何合并结果。子 Agent 通过 tool 被调用，"By default, subagents are stateless"，记忆由主 Agent 维护。
  • 每次调用在干净的上下文窗口中进行，避免撑大主对话。
  • 同步（默认）：主 Agent 等子 Agent 返回，适合后续步骤依赖结果。异步：启动后台任务继续对话，通常需要"启动返回 job ID、查状态、取结果"三个工具，完成时由应用通知用户。
  • 工具组织：每个 Agent 一个工具（控制细，配置多）；或单个 task 分发工具（适合 Agent 多的场景，上下文灵活性低）。使用分发工具时，告知主 Agent 可选子 Agent 有三种方式：系统提示列举（少于 10 个且稳定）、枚举约束（类型安全）、工具发现如 list_agents（数量多或动态）。

3.2 最小可用写法

📄 官方示意，🧪 本文用确定性函数验证了异常回灌路径：

@tool("research", description="调研某个主题并返回结论")
def call_research(query: str) -> str:
    try:
        result = research_agent.invoke(
            {"messages": [{"role": "user", "content": query}]}
        )
        return result["messages"][-1].content      # 只返回最终消息文本
    except TimeoutError as e:
        return f"[research 失败: {e}] 请缩小范围重试或改用其他来源"

🧪 实测：工具内部把 TimeoutError 转成字符串返回，主 Agent 拿到的是一条普通工具结果，图不会崩溃，模型可以据此改写查询。

3.3 生产要点

  1. 输出契约。📄 官方说主 Agent 只能看到子 Agent 的最终消息，所以要在子 Agent 提示里要求把结论、依据、未解决的问题写进最终消息。需要结构化回传时，用 Command 把额外字段写回 state。
  2. 输入隔离。默认只传任务描述。📄 需要延续父 Agent 已做工作时才传消息历史，代价是提示变长、隔离性下降。
  3. 异常回灌（上面 3.2）：子 Agent 失败要变成文本，且工具返回要带 tool_call_id（@tool 机制自动处理）。
  4. 持久化范围。📄 默认的继承 checkpointer 模式下，每次调用从空状态开始，支持中断、可安全并行。想让子 Agent 跨调用保留自己的对话历史，编译时设 checkpointer=True。
  5. 可观测性有盲区。📄 子 Agent 在工具函数内部被调用，LangGraph 无法静态发现它们，get_state(..., subgraphs=True) 读不到其状态。需要排查子 Agent 内部时，应改成在自定义图的节点函数里调用子 Agent，或者另接 LangSmith 追踪。

3.4 🧪 实测：并行扇出与上下文隔离

用 Send 实现"主 Agent 同时派 3 个研究子 Agent"，结果靠 reducer 汇总：

class Orch(TypedDict):
    questions: list[str]
    answers: Annotated[list[str], operator.add]

g.add_conditional_edges(START, lambda s: [Send("worker", {"q": q}) for q in s["questions"]], ["worker"])
# 输入 3 个问题，answers 得到 3 条，顺序不保证

另一个实测是父子图状态映射：父图和子图 state 结构不同时，写一个包装节点，只把任务描述传进子图，只取回 result：

def call_sub(s):
    r = sub_app.invoke({"task": s["todo"][0], "result": ""})
    return {"results": [r["result"]]}      # 子图内部过程不进父图

结果父图只有 results，没有子图的中间消息。这是"上下文隔离"在代码上的落点：返回什么，父图就只能看到什么。

4. Handoffs：移交控制权

4.1 官方要点

📄 官方 Handoffs 文档：

  • 机制：工具返回 Command，更新 state 里的变量（如 current_step 或 active_agent），系统读取它来切换配置（system prompt、工具集）或把对话路由给另一个 Agent。
  • 适用：有先后顺序、需满足前置条件才能解锁能力的流程。例如先确认保修状态，再进入维修或退款。
  • 两种实现：单 Agent 加中间件（中间件按 current_step 覆盖提示和工具，多数场景更简单，应优先）；多 Agent 子图（每个 Agent 是图里一个节点，交接工具用 Command(goto=..., graph=Command.PARENT) 跳转，只在需要复杂专用实现时才值得）。
  • ToolMessage 配对：LLM 调用工具后，必须收到带相同 tool_call_id 的 ToolMessage，否则历史格式错误。
  • 子图交接的上下文控制：只传触发交接的 AIMessage 和一条确认用的 ToolMessage，不传子 Agent 的全部历史；接收方需要更多信息就把摘要写进 ToolMessage 内容。
  • 让用户接管前，最后一条消息应是 AIMessage。

4.2 🧪 实测：PARENT 跳转与消息配对

父图有两个子图节点 sales_agent、support_agent，销售子图内部节点返回：

def sales_node(state):
    ai = AIMessage(content="", tool_calls=[{"name": "transfer_to_support", "args": {}, "id": "c1"}])
    tm = ToolMessage(content="Transferred to support", tool_call_id="c1")
    return Command(goto="support_agent", graph=Command.PARENT,
                   update={"messages": [ai, tm]})

实测消息序列为 HumanMessage → AIMessage → ToolMessage → AIMessage，support 收到的历史是 3 条（用户消息加交接的两条），最终由 support 回复。交接成功，且 tool_call_id 配对完整。

4.3 容易出错的地方

  • 并行工具调用：📄 官方示例用 messages[-1] 取交接消息，前提是没有并行工具调用。同一轮模型同时发出多个工具调用时这样取会取错，生产里要按 tool_call_id 精确匹配，或者对交接工具禁用并行调用。
  • 未知步骤：中间件里按 current_step 查配置字典，未知步骤会 KeyError；prompt.format(**state) 遇到 state 缺字段也会抛错。这两处官方示例没处理，生产要加默认分支。
  • 移交死循环：A 交给 B，B 又交回 A。要在 state 里记录移交次数，超限转人工，结合 状态机设计篇 第 5 节的 RemainingSteps 兜底。

5. Supervisor 库的现状：别再新建依赖

本库旧文档和不少教程会提 langgraph-supervisor（create_supervisor）。📄 抓取其 GitHub README 的结果：

  • README 开头写明："We now recommend using the supervisor pattern directly via tools rather than this library for most use cases."（现在推荐直接用工具实现 supervisor 模式，而不是用这个库）。
  • 页面显示该仓库已于 2026 年 9 月 20 日被所有者归档，只读。仅当已有代码依赖它，或需要平滑升级到 LangChain 1.0 时才值得保留。
  • 该库本质是把 tool-calling 子 Agent 模式打包：自动生成 handoff 工具、管理消息历史。参数包括 output_mode（full_history 或 last_message）、add_handoff_messages、层级 supervisor 等。

结论：新项目按本文第 3 节自己写工具，对上下文工程的控制更直接；output_mode="last_message" 的思路（只保留子 Agent 最终回复）对应第 3.3 节的"输出契约"。库里 forward_message（把子 Agent 最后一条消息直接作为输出，省 token 且避免主 Agent 改写）的思路值得借鉴：当子 Agent 的回答不需要二次加工时，直接透传。

6. 生产级委派：Anthropic 的七条做法

📄 Anthropic 博客里的提示工程与评估做法，对任何多 Agent 系统都适用：

# 做法 细节
1 委派要写清楚 每个子 Agent 需要目标、输出格式、工具与来源指引、任务边界。模糊指令会导致重复搜索或遗漏
2 投入与复杂度匹配 简单事实查询 1 个 Agent、3–10 次工具调用；直接比较 2–4 个子 Agent、各 10–15 次；复杂研究 10 个以上
3 先宽后窄 先短而宽的查询了解全貌，再收窄
4 并行 主 Agent 同时启动 3–5 个子 Agent，子 Agent 同时用 3 个以上工具；复杂查询研究时间最多减少 90%
5 工具描述要清晰 让测试 Agent 反复调用有缺陷的工具并改写描述，后续任务完成时间下降 40%
6 评估从小样本开始 约 20 个真实查询即可起步；LLM 评委按事实准确性、引用准确性、完整性、来源质量、工具效率打分；人工测试必不可少，能发现来源选择偏差
7 有状态任务看终态 检查最终状态是否正确，不逐步检查过程

6.1 Anthropic 披露的生产难点

  • 错误累积：长时间运行的 Agent 出错后从头重启代价高。他们做了断点续跑，加重试和定期检查点。
  • 调试难：非确定性。他们加了完整生产追踪，并监控决策模式和交互结构，不读取单个对话内容以保护隐私。
  • 部署协调：用彩虹部署逐步切流量。
  • 同步瓶颈：主 Agent 要等一批子 Agent 全部结束才继续，一个慢子 Agent 拖住整体。异步能提高并行度，但带来结果协调、状态一致性和错误传播的新问题。

这四条在 LangGraph 里分别对应：checkpointer 与 invoke(None) 续跑（见持久化篇）、LangSmith/stream_mode="debug" 追踪、新旧版本并存、Send 扇出的 join 语义。同步瓶颈是 Send 加 join 的天然特性：add_edge 汇合要等所有分支完成。需要"先到先用"时，只能走异步 job 方式，复杂度高很多。

7. 工具调用：多 Agent 里最容易出事的环节

📄 LangChain 官方工具文档的生产相关要点，加本文补充：

  1. 类型和 docstring 就是 schema。@tool 的类型提示定义输入 schema，docstring 成为模型看到的描述。工具名用 snake_case。config、runtime 是保留参数名。
  2. 错误要回灌。用 @wrap_tool_call 中间件统一 catch，返回带 tool_call_id 的 ToolMessage，让模型看到错误后自行修正。别让工具异常直接冒泡成图崩溃。
  3. 并行工具调用。模型一次可调多个工具，全部执行后结果一起回传。📄 只有批次里每个工具都设 return_direct=True 才会直接结束；多个并行工具同时更新同一个 state 字段时，必须定义 reducer。
  4. 用 Command 从工具改 state。📄 Command(update=...) 指向当前图时，update 里必须包含 ToolMessage 且 tool_call_id 用 runtime.tool_call_id，否则 ToolNode 抛 ValueError；指向父图（graph=Command.PARENT）则不需要。
  5. 用 ToolRuntime 取上下文。📄 在工具签名加 runtime: ToolRuntime，由 ToolNode 自动注入，不会出现在发给模型的 schema 里。runtime.state 读会话状态，runtime.context 读每次调用的不可变配置，runtime.store 访问长期存储。旧的 InjectedState、InjectedStore 官方标记为旧写法。
  6. 动态工具选择。📄 两种：预注册后用 wrap_model_call 按权限或状态过滤；运行时才发现的工具（如 MCP）需要同时用 wrap_model_call 加入和 wrap_tool_call 执行。后者漏掉任何一个，Agent 都不知道怎么调用。

权限收敛是多 Agent 的安全底线：给每个子 Agent 只暴露它需要的工具。写操作工具（发信、转账、改库）单独放在一个子 Agent 里，并在其调用前用 interrupt() 做人工确认（见持久化篇第 3 节）。

8. CrewAI：Flows 才是生产形态

本库已有 CrewAI源码解析 与最小 Crew 示例。生产层面要补的是 Flows 和 Process。

8.1 Process：只有两种

📄 CrewAI 官方 Process 文档：

  • sequential：任务按列表顺序执行，前一个输出作为后一个的上下文，可用 Task 的 context 参数指定哪些输出供后续使用。
  • hierarchical：由管理者规划、分配、审核。必须指定 manager_llm 或 manager_agent 之一，否则无法运行。
  • 文档没有说明性能、成本、并发，也没有说明管理者出错时怎么办。这些是生产必须自己补的盲区。

8.2 Flows：事件驱动的编排层

📄 官方 Flows 文档的核心：Flow 负责编排，Crew 负责执行具体任务。

  • @start() 入口（可多个）；@listen(method) 在指定方法完成后执行，并把输出作为参数传入。
  • or_(a, b) 任一完成触发；and_(a, b) 全部完成才触发；@router(method) 返回字符串标签分支，下游用 @listen("label") 接收。
  • 状态：非结构化用 self.state 字典（自动生成 UUID id）；结构化则继承 Pydantic BaseModel 并写 Flow[MyState]。
  • 持久化：@persist，默认 SQLite，可自定义 FlowPersistence。kickoff(inputs={"id": uuid}) 恢复同一状态继续写；kickoff(restore_from_state_id=uuid) 从快照复制状态并分配新 id，原历史不变。
  • @human_feedback（CrewAI 1.8.0 起）暂停流程等人工反馈。
  • flow.usage_metrics 汇总一次 kickoff() 里所有 LLM 调用的 token，包括 Crew 内部；kickoff().token_usage 只反映最后一个 Crew。做成本核算要用前者。

8.3 与 LangGraph 的对应关系

能力 LangGraph CrewAI Flows
入口/串联 START、add_edge @start、@listen
条件分支 add_conditional_edges / Command @router + @listen("label")
汇合 add_edge([a, b], c) and_(a, b)
状态 TypedDict + reducer Pydantic BaseModel，无 reducer 概念
持久化 checkpointer（super-step 粒度，Postgres 等） @persist（SQLite 默认）
回放/分叉 get_state_history + update_state restore_from_state_id（复制快照）

差别集中在状态合并：LangGraph 的 reducer 明确规定并行写入怎么合并，CrewAI 文档里没有对应机制，并行写同一状态字段需要自己保证。这也是 框架实操选型 里把断点续跑和 time travel 判给 LangGraph 的依据之一。

9. AutoGen：现状与可借鉴的两个模式

9.1 现状（先于一切）

📰 二手资料（LangChain 对比页、迁移指南搜索结果，非 Microsoft 原文逐字）一致称：AutoGen 于 2025 年 10 月进入维护模式，只做社区维护、不再有新特性；微软推荐新项目用 Microsoft Agent Framework（合并了 AutoGen 的编排思想和 Semantic Kernel 的企业能力），据称 2026 年 4 月 1.0 GA。Microsoft Learn 上有官方的《AutoGen to Microsoft Agent Framework Migration Guide》。这一节的事实来自搜索摘要，上线决策前请读官方迁移指南核实。

本库旧文档的 AutoGen 最小示例（UserProxyAgent 加 AssistantAgent）可以保留作概念参考，不应作为新项目的技术选型。

9.2 GraphFlow：显式图（实验性）

📄 AutoGen AgentChat 的 GraphFlow 用有向图控制执行顺序，支持顺序、并行、条件分支、循环，文档标注为实验性。要点：

  • DiGraphBuilder 的 add_node、add_edge、set_entry_point、build。纯循环图没有源节点时必须用 set_entry_point。
  • 条件边：condition 可以是关键字或对 msg.to_model_text() 判断的 lambda。文档提醒条件字符串依赖 Agent 在系统提示里遵守输出约定，要自己验证。
  • 循环必须有退出条件，并用 termination_condition（如 MaxMessageTermination(10)）设上限。
  • activation_group 与 activation_condition（"all" 或 "any"）区分"必须全部到齐"和"先到先执行"，这是 LangGraph 里 add_edge([a,b], c) 与普通多边的差别的另一种表达。
  • 消息图与执行图分离：谁先执行是执行图的事，每个 Agent 看到哪些消息要用 MessageFilterAgent 和 PerSourceFilter 另外限制。默认所有消息发给所有 Agent，上下文会膨胀。

可借鉴点：把"谁执行"和"谁看到什么"拆成两件事设计。LangGraph 里对应的是图结构（边）与 state/传参（上下文）。

9.3 Swarm：去中心化移交

📄 AutoGen Swarm 与 LangGraph Handoffs 同构：Agent 通过特殊工具调用（HandoffMessage）移交，所有 Agent 共享同一份消息上下文，最近的 HandoffMessage 决定下一个发言者。几个值得带走的细节：

  • 移交依赖模型的工具调用能力。📄 模型若并行调用工具会同时产生多个移交，行为异常；OpenAI 客户端可设 parallel_tool_calls=False 避免。这与第 4.3 节的结论一致。
  • 移交给 "user" 时团队停止并等待输入，用户回复以 HandoffMessage 发回，这是 AutoGen 的人机协同方式，比 LangGraph interrupt() 粗糙：没有 checkpoint 级恢复。
  • 终止条件可组合：HandoffTermination(target="user") | TextMentionTermination("TERMINATE")。

10.2 上线检查清单

# 检查项
