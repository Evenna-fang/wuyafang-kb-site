Agentic RAG 六模式：控制权、反馈门控与可组合实现

返回知识库总入口

资产定位：总地图 N2 知识提炼，四之一知识层。本文把 Router、Agent-as-retriever、CRAG、Self-RAG、Adaptive RAG 与 Agentic-GraphRAG 放进同一套工程模型：它们不是六个互斥产品，而是“谁决定下一步、什么证据允许继续、失败后如何回退”的不同组合。相关代码背景可参见 L4 Agentic RAG 六模式代码模板，多 Agent 研究型检索见 Multi-Agent 协作。

WHY：为什么需要 Agentic RAG，又为什么不能一概而上

2

1. 固定管线的真正短板不是“没有循环”

3

Naive RAG 的基本路径是“问题—检索—拼接上下文—生成”。它便宜、可预测，适合语料覆盖良好、问题单一的问答。Advanced RAG 在此基础上加入查询改写、混合召回、重排和上下文压缩，解决“查得准不准”。Modular RAG 再把切分、索引、检索、评分、生成与评估拆成可替换模块，解决“系统能不能演进”。Agentic RAG 则进一步把运行时决策交给模型或策略器：是否检索、去哪个源、是否重查、何时停止、答案能否发布。

这三条轴线不能混为一谈。模块化是代码组织结构，Advanced 是检索与生成技巧，Agentic 是运行时控制权。一个完全硬编码的路由系统也可以采用 Modular RAG；一个写得极其混乱的 Agent loop 仍然是 Agentic，但不具备可维护性。工程上应以模块化承载六种模式，而不是把“Agentic”理解为推翻原检索管线。

固定管线在四类负载下会暴露结构性问题：闲聊与事实问答混合时，每次都检索浪费成本；多源知识并存时，单一向量库无法覆盖 SQL、Web 与图谱；检索结果噪声较大时，直接生成会把错误证据放大；多跳、全局总结或证据不足时，一次 top-k 不可能保证完整。Agentic 的价值就是为这些情况增加受约束的决策和反馈，而不是让模型无限制地自由行动。

2. 六模式是一条光谱，不是六选一

3

可以用两个正交维度理解六模式。第一维是控制权：工程规则固定路径，还是模型选择工具、路由和检索深度。第二维是反馈门控：只检查查询类别，还是继续检查文档相关性、证据充分性、答案忠实度与切题性。

模式 主要让渡的控制权 关键反馈门控 最典型的新增成本
Router 选择数据源、模型或处理路径 路由置信度与类别有效性 一次分类或轻量模型调用
Agent-as-retriever 是否检索、何时调用检索工具 工具结果相关性与停止条件 多轮模型决策与工具调用
CRAG 检索失败后采用何种纠正动作 检索评估器、文档过滤 评分、改写和备用搜索
Self-RAG 检索、批判、再生成等自适应决策 相关、支持、有用等反思信号 训练成本，或工程近似的多次评判
Adaptive RAG 按问题复杂度分配检索深度 复杂度分类与分支质量 分类器训练或路由调用
Agentic-GraphRAG 在局部、全局与关系检索间选择 图结果覆盖、社区证据与引用 图构建、社区摘要和维护成本

因此可以组合出很多合理形态：先用 Adaptive 判断难度，再把难题交给 Agent-as-retriever；检索后用 CRAG 过滤和补源，生成后用 Self-RAG 式双门禁；当问题被判定为全局关系型时，再路由到 GraphRAG 工具。反过来，只给 Agent-as-retriever 加一个 while 循环而不加评分器，只会让同一批差文档被反复消费。

3. 用失败成本而不是“先进程度”选型

3

简单 FAQ、稳定制度问答应从 Naive 或 Advanced RAG 起步；类别清晰的多库问答先上 Router；检索触发不确定再加检索工具；检索覆盖不稳定加 CRAG；答案错误代价高才增加生成后门禁；负载难度差异显著再引入 Adaptive；只有全局总结、跨文档关系与多跳遍历确实成为主要需求时，才评估 GraphRAG。

每次升级都要回答三个问题：当前基线的失败究竟发生在路由、召回、证据过滤还是生成；新增节点能否直接干预这个失败；提升是否覆盖新增延迟、token、索引和运维成本。没有基线评测集时，增加循环属于盲改。书籍章节笔记特别强调负例测试：除了“能答什么”，还必须测试“库里没有时是否拒答”。负例能识别一种常见假象——答案更流畅了，但系统更敢编造。

WHAT（WHYT）：六种模式的机制、论文差异与边界

2

1. Router：把一次选择变成可审计的分流

3

触发条件。 查询存在相对稳定、可枚举的类别，例如内部制度库与实时 Web、技术文档与产品手册、小模型与大模型。若类别边界模糊到人工也难标注，路由器只会增加一个错误源。

机制。 输入问题后，规则、传统分类器或 LLM 输出受 schema 约束的类别，条件边把请求送往对应查询引擎。课件 day05 的 RouterQueryEngine 用 QueryEngineTool 包装多个索引，再由 LLMSingleSelector 选择；ToolMetadata.description 实际上决定了模型对“哪个库有什么”的理解。路由并不天然等于 Agent，它完全可以是一条确定性的 workflow。

与原论文或官方范式的关系。 Router 主要对应 Anthropic 的 routing workflow，不是某一篇 RAG 论文的专有算法。LangGraph Adaptive RAG 教程也使用结构化路由，但教程中的“向量库或 Web”是数据源分流，不等于 Adaptive-RAG 论文的三档复杂度分类。

参数、适用与反例。 关键参数是类别集合、置信度阈值、默认分支、每类 top-k 和模型档位。适用于客服意图分流、多租户知识域选择、成本分级。反例包括类别高度重叠、路由描述长期不更新、一个问题天然需要多个来源却强制单选。后者应改成多选路由或并行检索。

观测与故障。 记录路由类别、置信度、描述版本、误路由率和各分支成功率。低置信度进入默认安全分支，而非强行选择； schema 解析失败时重试一次或直接走通用检索。若某分支 Recall@K 正常但最终答案差，应查生成而非继续调路由器。

2. Agent-as-retriever：把检索器变成工具，而不是把判断交给运气

3

触发条件。 同一入口既有无需检索的对话，又有需要私有知识的问题；或者检索次数、子查询和数据源无法预先写死。单一、稳定、每次都必须查库的 FAQ 没有必要付出工具决策成本。

机制。 将 retriever 封装成带名称、描述和参数 schema 的工具。模型在“直接回答”与“调用检索”之间选择，工具返回后由相关性评分节点判断是否可用；不足时改写问题或拆分子查询，达到证据充分或预算耗尽后停止。课件 day06 的 chat_mode="react" 已体现“检索作为工具”的思想，day03 的 FunctionAgent 则展示函数签名与 docstring 如何变成工具契约。

与官方实现的差异。 LangGraph 官方 Agentic RAG 教程提供 generate_query_or_respond、ToolNode、grade_documents、rewrite_question 和 generate 的闭环。生产实现不能只复制节点名，还要增加租户过滤、文档引用、每轮预算、空结果处理和最终忠实度门禁。

参数、适用与反例。 建议把 max_iterations 初始设为 3 到 5，另设总 token、工具次数和墙钟时间上限；具体值必须按任务分布压测。适合研究助理、混合对话、多跳问答。反例是强监管场景下让模型自行决定是否查强制依据，或所有问题都有固定检索步骤。此类场景应把必要检索写成硬约束。

观测与故障。 除答案指标外，必须记录“该检索未检索”和“不该检索却检索”两类决策错误，以及每轮查询、工具参数、文档 ID、评分和停止原因。连续两轮查询语义等价、文档集合不变时应提前停止；工具超时返回结构化错误，不允许异常直接冒泡成无限重试。

3. CRAG：先判断检索是否可信，再决定纠正动作

3

触发条件。 知识库覆盖不全、文档时效性差异大，或者 top-k 经常混入表面相关但无法回答问题的片段。若基线召回已经稳定，额外评分和 Web 搜索可能只增加噪声。

机制。 CRAG 在检索后引入评估器，对结果给出正确、模糊或错误的判断。Correct 路径保留并精炼证据；Ambiguous 可结合内部与外部知识；Incorrect 触发查询改写和备用搜索。其关键不是“搜不到就上网”，而是纠正动作由证据质量驱动。

与原论文的差异。 原论文《Corrective Retrieval Augmented Generation》使用轻量检索评估器，并包含 decompose-then-recompose 知识精炼：把文档拆成知识条带，过滤后再组合。常见 LangGraph 工程教程用 LLM 二值评分代替评估器，并简化为“过滤—改写—Web 搜索”，是工程近似而非完整复现。

参数、适用与反例。 需要标定高、低阈值和灰区，设定最少有效文档数、备用源数量、改写次数与外部搜索预算。适合动态知识、开放域补充和内部覆盖不完整的助手。反例包括禁止外网的私有数据场景、Web 来源不可信、查询涉及严格权限控制。此时备用动作应是拒答、转人工或查受控数据源，而不是自动联网。

观测与故障。 监控评估器判准率、过滤后保留率、纠正触发率、改写后 Recall@K 增量、外部来源引用正确率。若改写后结果没有改善，停止重试并明确证据不足；若评估器频繁把正确证据判错，应先用人工标注集校准评分器，而非继续增加循环。

4. Self-RAG：原版是训练范式，托管 API 只能做工程近似

3

触发条件。 答案错误代价高，单纯“文档相关”仍不足以保证每个论断受证据支持，例如合规、医疗、法律和财务问答。若只是低风险闲聊或创意写作，生成后多次评判通常得不偿失。

机制。 原论文通过训练让模型按需生成四类反思标记：是否检索、文档是否相关、生成是否受支持、答案是否有用，并用这些信号控制检索和生成。其核心是把反思能力学习进模型及生成过程，而不是在提示词末尾写一句“请检查自己”。

与原论文的差异。 托管聊天 API 通常不能训练这些控制 token，也不能复现原模型的控制权重、采样和评分机制。工程上只能用独立结构化评分器近似：检索后做相关性过滤，草稿后做证据支持检查，再做切题检查；不支持则重生成，忠实但跑题则改写或重检索。应明确称为“Self-RAG 式门禁”或“Self-RAG 工程近似”，不能宣称复现了原版收益。

参数、适用与反例。 分别限制检索轮数、重写轮数和重生成轮数，避免三个循环叠加爆炸。评分器最好独立于生成模型，关键判断用人工标注校准。适合高失败成本、证据可显式引用的任务。反例是无法提供可核查证据的开放创作，或延迟预算极低的实时交互。

观测与故障。 至少观测 faithfulness、answer relevancy、无依据论断数、门禁误杀率、重生成后改善率和负例拒答率。模型连续生成不受支持的内容时，不应无限“再想一次”，而应回退到证据抽取式答案或拒答。忠实与切题必须分开，否则“复述了一段真实但无关的文档”也会被误判为成功。

5. Adaptive RAG：把计算预算分配给真正困难的问题

3

触发条件。 流量中同时存在无需检索的简单问题、一次检索可解的事实题和需要多轮检索的复杂题，而且三者比例足以影响总成本。若任务分布单一，固定管线更简单。

机制。 原论文训练复杂度分类器，将问题分到 no-retrieval、single-step 和 iterative 三类策略，以效率与效果的平衡为目标。路由的依据是解题所需步骤，而不只是主题或时效性。

与原论文的差异。 常见工程教程不训练分类器，改用 LLM 结构化输出；有些示例还把类别简化为“向量库或 Web”。这种做法只能算受 Adaptive 思想启发的工程路由。要对齐论文，应保留三档复杂度、构建银标准或人工标签，并比较分类器成本与节省的检索成本。

参数、适用与反例。 每档分别配置 top-k、最大轮数、模型和预算；简单分支也应有升级机制，防止分类过低导致无证据作答。适合混合负载和高流量系统。反例包括所有请求都必须引用企业知识、分类标签无法稳定获得、 router 调用本身比节省的检索更贵。

观测与故障。 按复杂度分层统计准确率、平均工具次数、p95 延迟和单成功任务成本，特别记录“难题被分到简单档”的漏升级率。低置信度可升到中间档；分类器漂移时回退到固定单步检索。不能只看总平均分，否则简单题的收益会掩盖难题退化。

6. Agentic-GraphRAG：只为全局与关系问题支付图成本

3

触发条件。 主要问题是“整个语料有哪些主题”“多个实体如何关联”“跨文档证据链是什么”，而普通 top-k 无法代表全库。单一事实、精确条款和局部语义问答通常不应默认走图。

机制。 Microsoft GraphRAG 在索引期抽取实体与关系，构建图和社区，并预生成社区摘要；查询期 local search 聚焦实体邻域，global search 通过社区摘要的 map-reduce 回答 query-focused summarization。Agentic 化是把 local、global 以及其他检索器作为工具，由路由或 Agent 选择并组合。

与原论文和官方框架的差异。 原论文重点是 GraphRAG 的索引与全局摘要方法，不等于必须有多 Agent。把 local/global 包成工具是后续工程集成方式。图也不会自动带来正确推理：实体消歧、关系抽取和社区摘要任何一环出错，都可能生成结构漂亮但证据错误的答案。

参数、适用与反例。 需要估算抽取模型、块大小、实体去重、社区层级、更新频率、local/global 调用预算和引用回溯方式。适合情报分析、跨文档主题研究、关系密集语料。反例是小库、更新极频繁但无法增量维护、问题以精确事实为主、无法承担索引期大量 LLM 调用。图索引成本必须在上线前做全量与增量两笔账。

观测与故障。 单独建立全局、关系、多跳评测集，观察答案覆盖、关系正确率、引用可追溯性、图与向量索引可见时间差。实体误合并应能回滚到原文证据；图结果为空时回退普通检索并声明降级，禁止把“没有关系边”解释为“现实中不存在关系”。

HOW：用统一状态、模块和预算实现可组合系统

2

1. 先把离线知识底座做稳：day03—06 的落点

3

Agentic 层不能弥补糟糕的数据底座。课件 day03 的 VectorStoreIndex.from_documents 提供最小索引路径；day04 按文档性质选择 SentenceSplitter、CodeSplitter 或 HierarchicalNodeParser；day05 用 IngestionPipeline 把切分、嵌入和元数据抽取串成可复用管道，并用 RouterQueryEngine 实现多索引分流；day06 通过 storage_context.persist 与 load_index_from_storage 避免每次重启重建索引。

落地时应把权限元数据、文档版本、来源位置和内容哈希在摄取期写入节点，而不是等检索后再补。层次切分可用叶节点召回、父节点补上下文；代码按结构切分；普通中文制度文本从句子切分起步。IngestionPipeline 中的 LLM 标题抽取和并发要计入索引成本，且抽取结果不能覆盖原始来源。持久化目录必须和嵌入模型、切分参数、schema 版本绑定，否则“成功加载旧索引”可能只是静默使用了不兼容向量。

2. 统一模块化状态 schema

3

六模式共享状态，才能组合和做消融实验。下面是框架无关的 Python 骨架；Document 保留证据身份，Budget 把循环安全变成数据而非口头约定。

from dataclasses import dataclass, field
from typing import Literal, TypedDict

@dataclass
class Document:
    doc_id: str                 # 稳定证据编号
    text: str                   # 原文片段
    source_uri: str             # 可回溯来源
    version: str                # 文档或索引版本
    tenant_id: str              # 权限过滤维度
    retrieval_score: float = 0.0
    relevance: Literal["unknown", "yes", "no"] = "unknown"

@dataclass
class Budget:
    max_iterations: int = 5     # 总检索反馈轮数
    max_rewrites: int = 2       # 查询改写上限
    max_regenerations: int = 1  # 生成重试上限
    max_tool_calls: int = 12    # 工具调用总上限
    max_tokens: int = 30000     # 全链路 token 上限
    deadline_seconds: int = 60  # 墙钟时间上限

class RagState(TypedDict, total=False):
    trace_id: str
    original_question: str
    question: str
    route: Literal["direct", "single", "iterative", "graph_local", "graph_global"]
    documents: list[Document]
    generation: str
    citations: list[str]
    iteration: int
    rewrite_count: int
    regeneration_count: int
    tool_calls: int
    tokens_used: int
    stop_reason: str
    errors: list[dict]
    budget: Budget

状态只保存必要证据与计数，大型原文可按引用存放。每次节点返回部分更新，不在路由函数里偷偷修改状态。并行分支必须定义 reducer，避免后完成者覆盖先完成者。original_question 永远保留，改写不能逐步漂移用户意图。

3. 五个可操作模块：检索、评分、改写、生成与门禁

def retrieve(state: RagState, retriever) -> dict:
    # 权限过滤必须先于评分与生成，不能把越权文本交给后续模型
    docs = retriever.search(
        state["question"],
        top_k=20,
        tenant_id=current_tenant(),
    )
    return {
        "documents": docs,
        "iteration": state.get("iteration", 0) + 1,
        "tool_calls": state.get("tool_calls", 0) + 1,
    }

def grade_documents(state: RagState, grader) -> dict:
    kept = []
    for doc in state["documents"]:
        verdict = grader.relevance(state["original_question"], doc.text)
        doc.relevance = verdict
        if verdict == "yes":
            kept.append(doc)
    return {"documents": kept}

def rewrite_question(state: RagState, rewriter) -> dict:
    # 显式告知上一轮失败，保留原问题约束，禁止扩大主题
    rewritten = rewriter.invoke({
        "original": state["original_question"],
        "previous": state["question"],
        "failure": "现有证据不足以回答，不得改变用户意图",
    })
    return {
        "question": rewritten,
        "rewrite_count": state.get("rewrite_count", 0) + 1,
    }

def generate(state: RagState, generator) -> dict:
    answer = generator.invoke({
        "question": state["original_question"],
        "documents": state["documents"],
        "instruction": "仅依据证据回答；证据不足就明确拒答，并保留引用编号",
    })
    return {"generation": answer.text, "citations": answer.citations}

def generation_gate(state: RagState, judge) -> str:
    # 忠实与切题是两个独立判断，不能合并成一个“看起来不错”
    if not judge.is_grounded(state["generation"], state["documents"]):
        return "regenerate" if can_regenerate(state) else "insufficient"
    if not judge.answers_question(state["original_question"], state["generation"]):
        return "rewrite" if can_rewrite(state) else "insufficient"
    return "publish"

grader 可先用重排分数做廉价分层，再让 LLM 只处理灰区，但阈值必须在标注集上标定。judge 不应复用生成器的“我觉得正确”，而应接收结构化 claim—evidence 对，输出可审计理由。任何模型评分都可能误判，因此门禁还需人工抽检和负例回归。

4. 用统一路由函数组合六模式

3 
def next_step(state: RagState) -> str:
    # 先检查硬预算，再考虑模型希望做什么
    if exhausted(state):
        return "degrade"
    if not state.get("documents"):
        return "rewrite" if can_rewrite(state) else "degrade"
    if state["route"] == "iterative" and needs_correction(state):
        return "correct"
    return "generate"

5. 六模式的落地参数表与降级策略

3
模式 首批需要压测的预算 正常停止 预算耗尽或异常时
Router 路由调用 1 次、默认分支、类别置信度 命中有效类别并进入分支 通用受控检索或澄清

CRAG 改写 1—2 次、备用源数量、评分灰区 证据达到发布门槛 受控拒答，不强制外搜
Self-RAG 式门禁 重生成 1 次、双门禁、独立 judge 忠实且切题 证据抽取式回答或转人工
Adaptive 三档各自预算、低置信升级 当前档完成且通过门禁 升级一档或回退固定单步
GraphRAG 索引成本、社区层级、查询调用上限 全局或局部证据充分 回退向量检索并标记降级

这些数值只是工程起点，不是论文保证或通用最优值。应以真实流量确定。若增加一轮检索后 Recall@K 与 faithfulness 都无改善，继续循环通常没有价值。

6. 评估必须覆盖检索、生成、决策和成本

3

检索层。 Recall@K 衡量标准相关文档是否出现在前 K 个候选中，至少要区分首次召回和最终保留证据；MRR 可看首个相关结果位置，nDCG 可处理多级相关性。门控过滤后也要重算召回，防止“过滤噪声”变成“删掉答案”。

生成层。 faithfulness 检查答案中的原子论断能否由所给证据推出，answer relevancy 检查是否真正回应问题。二者都不能被单一流畅度评分替代。引用准确率还要核对引用文档是否真的支持对应句子，而非只存在一个链接。

决策层。 建立路由混淆矩阵、检索必要性判断、升级与降级正确率、每轮改写增益和停止原因分布。最终答案错误时，沿 trace 找最早错误节点：选错库、未召回、误过滤、证据不足仍生成，分别对应不同修复。

负例与对抗。 至少包括库中无答案、相似但错误实体、过期版本、无权限文档、矛盾证据、全局问题误入 local 工具。期望行为是拒答、澄清、降级或列出冲突，而不是补全一个貌似合理的答案。

成本层。 记录每问模型调用、检索次数、输入输出 token、p50/p95 延迟、索引摊销和每个成功任务成本。消融实验按“基线—加路由—加评分—加改写—加生成门禁”逐项推进，同一评测集比较质量与成本。GraphRAG 还要单独计算离线建图和更新成本，不能只统计查询期 token。

7. 本批论文怎么用：先修证据标注，再解释检索分数

3

arXiv:2610.31606 研究的是一个仅含 18 篇文档、18 个查询的乳腺病灶管理 RAG 开发集。论文在不改变检索排序的情况下，把人工接受的证据 span 从 25 扩到 37、对应可接受 chunk 从 36 扩到 51，说明 Recall@K、MRR 等分数会直接受 ground truth 覆盖方式影响；它不是“补标让检索器突然变准”。文中 0.94 等结果只属于这个小开发集，且作者明确要求独立验证，不能外推为本库收益。

我们把论文转成四条落地动作：第一，每个评测问题标注所有足以支持答案的证据 span，不要只指定一个碰巧命中的 chunk；第二，含同一证据的重叠 chunk 都计为相关，避免把合理召回误判为假阳性；第三，检索标注版与生成答案版分开评测，不能用 LLM judge 的高分反推召回完整；第四，每次修改切分或重叠率后，冻结同一查询与标注版本重跑 Recall@K、MRR、nDCG，并另留未参与标注调整的查询做独立检查。若补标前后排序完全没变，应解释为“评价口径更完整”，而不是宣称检索算法已优化。

8. 推荐的渐进实施顺序

3

第一步，用持久化索引和统一 Document schema 建立 Naive/Advanced 基线，完成 Recall@K、faithfulness 和负例集。第二步，若多源误路由明确，引入 Router；若检索必要性不稳定，引入 Agent-as-retriever。第三步，加入相关性评分和一次受限改写，形成 CRAG 的最小闭环。第四步，只在高价值分支增加 Self-RAG 式生成双门禁。第五步，流量足够大时用历史 trace 标注复杂度，训练或校准 Adaptive 分类器。最后才用全局/关系问题集验证 GraphRAG 是否有增量收益。

这条顺序的核心是：先获得可解释基线，再逐项购买自主性；先确保每个反馈信号可信，再允许它驱动循环。六模式的最优形态通常不是一个“大而全 Agent”，而是一组可插拔、可预算、可降级、可评测的小决策。
