Agent 记忆与自进化：深挖整合

导读

本篇把 Agent 记忆方面的素材按主题重新排列，涵盖记忆分类、双进程读写范式、多智能体共享记忆、记忆保鲜、冲突治理与信念修订，以及自进化。代码实操放在最后一节。核心结论如下。

  1. 记忆先按两个维度区分。第一个维度是保存时长：checkpointer 管短期记忆，Store 管长期记忆。第二个维度是读写路径：System-1 快路径处理大多数查询，System-2 慢路径处理复杂查询，中间的门控决定这一次要不要慢下来。
  2. 多智能体共享记忆用三层图组织。Insight Graph 存泛化经验，Query Graph 存任务指纹与派单结果，Interaction Graph 存原始轨迹。查询越深，成本越高，所以不同角色查询的层数不同。
  3. 存得住不等于还是真的。记忆的寿命应按内容变化速度设定，过期记忆必须可见地标出。冲突时由代码取最新时间戳决定哪条生效，LLM 只负责判断两条记忆是不是同一件事。
  4. 信念修订保留演化链。新事实通过双向 supersedes 指针接到旧事实上，旧版本不做物理删除，争议发生时可以顺着链回溯。
  5. 自进化需要闸门。快慢双速固化经验，失败当场蒸馏，技能更新后跑回归，记忆带来源标签，外部技能先扫描，自动起草的技能经人审后再发布。

一、记忆分类：短期与长期

Agent 的记忆按保存时长分为短期和长期两类。短期记忆保存单次会话内的状态，长期记忆保存跨会话的信息。LangGraph 为两类记忆各提供一个持久化原语。

原语 保存什么 索引键 对应记忆
Checkpointer 每一步执行完后，把图状态序列化到后端（内存、SQLite、Postgres、Redis 均可） thread_id 短期记忆，当前会话的 state
Store 应用自定义的 KV 数据，可以挂向量索引做语义搜索 namespace，如 (user_id, 命名空间) 长期记忆，跨会话的用户画像

两者的作用范围不同。Checkpointer 的范围是单个线程（thread_id），Store 的范围是跨线程的 namespace。

Checkpointer 的存储后端与写法在第七节展开。Checkpointer 带来的断点恢复语义属于 durable execution（断点续传）的范畴，本篇不展开理论，相关内容见 L5-Agent生产化可靠性与评估-深挖整合.md。

二、双进程范式：System-1 与 System-2

2.1 范式定义

这一范式借鉴人类快思考与慢思考的双系统模型，把记忆与推理中的高频决策拆成两层。System-1 负责轻量的快速检索和快速路由。System-2 负责重读原始历史和慢速推理。两层之间有一个低开销的门控器，它决定这一次查询要不要升级到 System-2。

2.2 三篇论文的同一结构

三篇论文对同一结构的实现各有不同。

论文 System-1 System-2 门控位置
Jev-Mem（写入与查询，arXiv:2609.23986） 小分类器或规则做类型判定、图视图路由、候选打分、自适应停止 LLM 做最后的答案合成 System-One 控制面输出带类型的概率，不生成自然语言
D-Mem（查询期，arXiv:2603.18631） 向量近邻检索（embedding top-k）得到摘要事实 从原始会话或事件历史中重读片段（reraw） Quality Gating：置信度、证据稀疏度、查询复杂度共同决定升级概率
PRIME（推理期，arXiv:2509.22315，源文标注为待精读） 快推理 Agent 日常运行 慢思考 Agent 由自省触发 自省信号：推理步数、矛盾数、假设空间

Jev-Mem 与 D-Mem 的分工按阶段划分。Jev-Mem 管写入期：把写入时的高频决策（类型判定、冗余过滤、图视图路由、候选打分、自适应停止）从自回归 LLM 中抽出，交给轻量控制面，LLM 只做最后的合成。D-Mem 管查询期。两者分别覆盖写入端和查询端，合起来形成闭环。Jev-Mem 的 canonical node 挂四种 typed edge：semantic、temporal、causal、entity。

2.3 为什么要分成两个进程

成本方面，大多数查询不需要翻原始历史或走重推理，硬塞进去只会烧 token。D-Mem 的实测结果是：只付 35.8% 的 token，就能拿到全量重读 96.7% 的效果，LoCoMo F1 为 53.5。

质量方面，少量查询必须慢下来。时序、因果、矛盾和多跳类问题如果只靠向量召回，结果会"像但不是"。

两份素材对快路径承担的比例写法不同。双进程范式称 90% 的查询和决策不需要慢路径；D-Mem 条目称 85% 的查询由向量快检索直接出结果。本文保留两个数字并注明来源，不做取舍。

门控是整个范式的关键。门控本身必须极轻，不能调用 LLM 做自然语言判定，否则省下的 token 会被门控吃掉。

2.4 门控的实现要点

Quality Gating 的输入是置信度、证据稀疏度和查询复杂度，输出是升级概率。素材中的起步阈值为 τ=0.5，对应 G-DMem1 质量门控脚本。Jev-Mem 另有自适应停止机制：每轮评估证据是否充分，充分即停止检索。

门控决定"这次要不要慢下来"。一条记忆是否还值得保存，由衰减机制决定，见第四节。两者相互独立。

2.5 PRIME：慢思考的触发条件

PRIME 借鉴《思考，快与慢》：System-1 负责快速回答兜底，System-2 负责规划并集成检索做深度推理，按需唤起。慢思考的产出落盘为结构化记忆，包括规划步骤、检索证据和结论。同类问题再次出现时，直接复用这些记忆。

素材把 PRIME 的思路映射到本库的三阶评审流程，下表为升级建议。全部条目的状态都是"调研待评估"，尚未落地。

触发条件 当前做法 PRIME 升级建议
DSH 或 Codex 一次通过 直接交付 保持（System-1）
两个 Agent 投票一致且置信度 >0.7 直接交付 保持
两个 Agent 分歧，但置信度都 >0.7 直接升用户 先唤起 OC 慢思考归并一轮，仍分歧才升用户
任一 Agent 自报"我不确定" 升用户 自动唤起 System-2，不等用户指令
同一问题第 3 次出现 升用户 直接复用历史慢思考结论

慢思考有硬终止条件：OC 审查最多 2 轮，每轮必须有独立证据，禁止引用前一轮的结论。

2.6 六员落地映射

双进程范式对六员现状的映射如下。

层 对应六员现状 升级方向
System-1 快 fact_store.search、holographic 三层检索、shared-skills grep 已具备，不需重建
System-2 慢 翻 state.db 会话历史、OpenClaw 深度审查、Claude 多跳 debug 缺少自动触发，目前靠人判断
门控 无 G-DMem1（质量门控脚本，τ=0.5 起步）与 G-PRIME1（自省触发信号）

2.7 双进程的反例

  • 每轮都把全量会话历史塞进上下文。这相当于没有 System-1，只剩 System-2，token 开销爆炸。
  • 只用向量召回，从不重读原文。这相当于只有 System-1，复杂问题答不准。
  • 门控用 LLM 做自然语言判定。门控本身比省下的 token 还贵。

三、多智能体共享记忆：G-Memory 三层图

3.1 三层结构

G-Memory（arXiv:2506.07398，代码见 github.com/bingreeky/GMemory）把多智能体协作中的记忆按抽象程度分为三层，每层是一张图。

层 保存什么 谁用 成本
Insight Graph（泛化经验层） 多次任务中抽象出的教训、模式和踩坑经验，例如"flaky 测试不要盲目重跑" 编排层（Hermes）及其他 Agent 复用经验 最低，短摘要
Query Graph（任务指纹层） 任务指纹、派给哪个 Agent、结果如何，可复用"这类任务该派谁" 编排层派单时查询 中
Interaction Graph（原始轨迹层） 完整的 Agent 交互记录、对话、代码 diff 工程层（Claude、Codex）debug 时多跳追溯 最高，长上下文

三层相互引用。Interaction 沉淀为 Query，Query 抽象为 Insight。反向也成立，从 Insight 可以下钻到具体的 Query 和原始 Interaction。

3.2 四视图并行检索

同一张图上，检索时并行走四种边。

  • semantic：语义相似的记忆。
  • temporal：时间邻近的记忆，例如上周或昨天发生了什么。
  • causal：因果链，例如 A 导致 B。
  • entity：共享实体，例如同一个项目或同一个错误码。

召回顺序是有方向的。Insight 排在前面，先给经验；evidence 排在后面，再给原始证据支撑。

3.3 按角色决定检索深度

不同角色的查询深度不同。Hermes 做编排，只查 Insight 层，成本最低。Claude 和 Codex 做工程，查全部三层并多跳追溯。

这种差异对应 BudgetMem 的查询预算分级（arXiv:2602.06025，ICML 2026）。Low、Mid、High 三档按查询复杂度自动选择检索预算，RL 路由器用 λ 参数化。六员角色天然对应这三档：编排为 Low（千级），执行为 Mid，工程为 High（十万级）。AGENTS.md 的预算档四元组已经体现了这一对应。素材建议先用规则路由器替代 RL，按关键词复杂度分档，该项同样是"调研待评估"。

3.4 对 error-ledger 的改造

error-ledger 现在只记录"错误到修复"的单层关系。按照 G-Memory 的模型，可以拆成三层。

  • Insight 层：泛化经验，对应 ~/shared-skills/insight-log.md，六员共享。
  • Query 层：任务指纹到派单对象，再到结果。
  • Interaction 层：原始 trace 归档，来源为 state.db 与 cron 输出。

拆分后有两个收益。其一，各角色可以差异化检索深度。其二，一个 Agent 踩过的坑沉淀到 Insight 层后，其他 Agent 可以直接召回，不用重新踩。这与 error-ledger 台账"同一坑不踩第二次"的要求一致。

素材中，这一改造标注为"调研待评估"。最佳答案的缺口清单还记录了一项相关缺口：error-ledger 目前只能记录错误，尚不能自动应用已验证的修复方案。

3.5 共享记忆的反例与来源门

  • 所有记忆都放进一层长上下文。没有分层，Insight 和原始轨迹混在一起，编排层也要承担高成本。
  • 只有 Insight，没有原始轨迹。抽象过头，工程 debug 时找不到具体证据。
  • 只有原始轨迹，没有 Insight。每次都从零推理，多智能体无法复用经验。

最佳答案总结的四条落地教训中，有一条是共享记忆需要来源 gating。素材称，RAG 无差别收录会让假信念被下游采信 97% 至 99%，因此进库要过来源门。第六节的 authority 标签沿用了同一原则。

四、记忆保鲜：persistence 不等于 truth

4.1 问题的来源

存得住不等于还是真的，这是行业通病。Mem0、Letta 和 Zep 都只优化"存加检索"，都没有机制发现记忆已经过期。素材引用的数据如下：TimeQA 上最好模型准确率为 46%，人类为 87%；LongMemEval 上，商业助手在跨会话场景下准确率下降 30%。数据来源为 Kymata Labs 2026 白皮书，https://kymatalabs.com/research/memory-staleness。

4.2 半衰期五档

记忆的寿命应按"内容多久变一次"来定，而不是按"内容多重要"来定。

档位 例子 半衰期
永久 生日、老家 几十年
慢 住址、雇主 几年
中 当前项目、偏好 几个月
快 今天在干什么 几小时
易变 价格、额度、可用性 几分钟

这套分档与知识库保鲜的三分档同源。两者都按内容的变化频率定寿命。

4.3 写入时打标与五个控制项

Kymata 提出五个控制项，按性价比排序如下。

  1. 写入时打 last_verified 时间戳和 fact_class 档位标签。这是最便宜的一项，并且解锁其余所有控制项。
  2. 过期记忆可见地标红，不能静默当作新事实输出。这样可以防止模型"自信地撒谎"。
  3. 后台主动重验证"高频被查但久未验证"的记忆。
  4. 保留 contradiction-on-write（写入时的矛盾检测）作为地板，而不是天花板。
  5. 每条记忆保存 provenance（来源）。没有来源的记忆，信任度最低。

本库的落地现状（2026-10-10 核账）如下。

项 状态
Hindsight 记忆打 fact_class 标签 8176 条：permanent 1638，medium 4449，volatile 2049
volatile 类标 is_stale 1086 条
记忆保鲜每日扫描 cron 每天 09:00
备份位置 ~/.hermes/backups/memory-curation/

4.4 Ebbinghaus 衰减模型

每条记忆带一个连续的衰减率。记忆被成功召回时，衰减曲线后移，即得到强化。长期不被召回的记忆，按衰减曲线被驱逐。

素材给出的 TTL_TIERS 示例如下：immutable（衰减率 0）、long（衰减率 0.001，寿命 1 年）、short（衰减率 0.01，寿命 30 天）、session（衰减率 0.1，寿命 1 天）。

衰减与门控相互正交。门控决定这次查询要不要慢下来，衰减决定这条记忆还值不值得保存。

五、冲突治理与信念修订

5.1 冲突判定：LLM 不当裁判

这是保鲜主题中最反直觉、也最有价值的一条实证。arXiv:2606.01435 的测试显示，让 LLM 判断"哪条记忆更新"时，Mem0 的准确率只有 18%，Zep 只有 7%。改用代码 max(timestamp / serial) 取最新的一条，准确率达到 78%，提高了 60 个百分点。

据此定下铁律：LLM 只负责识别"这两条是不是同一件事"，"哪个更新"交给代码，取最新的 timestamp。

5.2 成品实测对比

素材列出三家产品的 2026 benchmark 数据。

产品 架构 冲突解决率 备注
Zep 时序图谱 95.8%（Recall@5 为 93.6%） 双时间轴：写入时间加事实为真的时段
Letta / MemGPT 类操作系统的分层记忆（core / recall / archival） 89% 分层清晰，可解释
Mem0 向量加实体图 76.5% 起步快，冲突处理最弱

数据来源为 https://agentic-pulse.dev/blog/2026-10-02-mem0-vs-letta-vs-zep-ai-agent-long-term-memory-benchmark-2026。

选型启示：历史事实会被改写的场景（人事、价格、政策）优先用时序图谱。只沉淀偏好的场景，用向量加实体图即可。

5.3 信念修订追踪：DCPM

DCPM（Dual-Process Cognitive Memory，arXiv:2606.09483）批判现有长期记忆的做法。这些系统把用户说过的话、偏好和行为模式压平成一个检索面，于是丢失了三样东西。

丢失的信息 后果
信念的中间状态 只见最终结论，不知道它从哪个旧结论改过来
偏好漂移的原因 知道偏好变了，但不知道为什么变
跨域行为的潜在链接 发现不了"A 场景与 B 场景行为矛盾"这类漂移点

这三样丢失，正是多 Agent 讨论中观点漂移不可追溯的根源。

DCPM 的解法分为两个进程。

进程 时机 做什么
System-1 同步写入 每次新对话到来 与向量库已有条目协调。旧信念被新事实取代时，写入双向 supersedes 指针，不做物理删除，保留演化链
System-2 异步引擎 夜间批量 把新鲜事实聚类成域内 schema、潜在意图和跨域核心模式，扫描跨域矛盾

双向指针（old ⇄ new）是核心机制。新事实取代旧事实时，旧版本保留，两者互相指向。修订过程因此是一条双链，而不是一次覆盖。多 Agent 的观点漂移可以按时间轴展开：同一问题下，不同 Agent 的回答依次排列，共识的形成与破裂都能看到。

落地时只取双链思想，不引入完整的 DCPM。评审历史按如下模板记录。

## 条目: <问题指纹>
- 当前结论: <最新结论>
- 修订链: [v1 2026-09-22 DSH提出=X] ⇄ [v2 2026-09-23 OC审改=Y, 原因=证据Z] ⇄ [v3 2026-09-28 最终=Y+补R]
- 漂移原因: <为什么改>
- 下次命中直接跳到 v3, 不重新推理

下次争议出现时，直接读历史链跳到最新版，不用重新吵一遍。

DCPM 与其他机制的关系如下。

  • 与 G-Memory：DCPM 是 G-Memory temporal edge 的 schema 细节指南，两者天然兼容。G-Memory 管记忆怎么分层存放，DCPM 管时间边上挂什么。
  • 与周复盘 cron：System-2 的夜间异步聚类，对应每周一的 update 钩子。一周内零散的评审结论被聚成 schema，例如"哪类问题总要 OC 审"，并扫描跨域矛盾，例如"配置类操作在 A 场景串行、在 B 场景并发通过"。
  • 与保鲜：保鲜回答"这条还值不值得信"，DCPM 回答"这个结论是怎么一步步变成现在这样的"。两者互补。

DCPM 的反例如下。

  • 覆盖式写入，只留最新结论。观点漂移不可追溯，下次争议要重新吵一遍。
  • 只存最终立场。OpenClaw 的 Devil's Advocate 角色需要观点演化链才能有效质疑，只存最终立场等于没有质疑材料。
  • 跨周、跨月的长程任务不带时间指针，会被过时事实误导。

5.4 保鲜与冲突治理的反例

  • 只做存加检索，不做过期发现。越用越错。
  • 让 LLM 判断哪条记忆更新。实测准确率只有 7% 至 18%。
  • 过期记忆静默返回。模型会自信地撒谎，这比回答"不知道"的危害更大。
  • 冲突时物理删除旧版本。丢失演化链，无法回溯共识是怎么形成的。

六、自进化

6.1 快慢双速：Experience Funnel

Experience Funnel（arXiv 2609.08919，2026-09-08）把交互轨迹分两步处理。快速层是显式的文本状态，即技能或 harness，可修改、可验证。慢速层通过 transition-aware 蒸馏，把跨状态修订后仍然有效的行为固化进模型策略。两层交替循环。

这样设计的理由是：纯文本技能改起来快，但不可携带；纯参数微调更新太慢。快慢双速是工程上可落地的折中。

对六员而言，快速层就是现有的技能库和 AGENTS.md。需要补的是慢速层的定期固化，即把反复验证有效的技能沉淀为更强的流程规则。素材说明这一步不需要微调，并且与 task_state 状态机天然衔接。

6.2 实时纠偏：PILOT supervisor-worker

PILOT（arXiv 2608.26530，2026-08-27）让独立的 supervisor 在执行中实时重定向或中止 worker，即 live steering。同时，执行中暴露的失败模式被当场蒸馏成可复用的技能与记忆，即 live self-evolution，而不是等任务结束再复盘。

素材给出的实测数据如下。

  • Terminal-Bench 2.0 上最高提升 9.8 个百分点。
  • 自改进设定下，GLM-5.1 提升 14.6 个百分点，Kimi-K2.6 提升 12.4 个百分点。
  • 输出 token 分别下降 42.9% 和 47.4%；每百万 token 的成功评测数分别提升 110% 和 134%。

对六员的落地方式如下。六员分工中，流程硬执行的角色天然就是 supervisor。审查员在第一轮发现问题时，不必打回等下一轮，而是当场给执行者发 steering，改方向或中止，同时把这次失败写入错误台账或技能草案。这是纯 prompt 与流程的改动，不需要新依赖。

6.3 过程级评测与技能回归门禁：EvoPathBench

EvoPathBench（arXiv 2609.24663，2026-09-21）固定基座模型和工具，在演化检查点冻结记忆或技能工件，再用留出任务评测三项能力：泛化、保持（retention）、规则适应。

结论有两条。其一，被选中落地的演化更新，普遍低于候选更新的潜力。其二，候选评估与选择是关键瓶颈。

对六员的落地方式是：每次 Workshop 技能 update 后，用固定样例集跑一次 verify，防止技能演化悄悄退化。这是 receipt 门禁的自然延伸，也是落地三步中的第一步。

6.4 其他三个方向

方向 来源 落地方式

6.5 安全护栏：自进化的前置阀门

自进化能力越强，越需要先过安全阀门。素材列出两项风险。

第一项是 Authority 坍缩（AuthMem-Bench，arXiv 2608.01679）。固化记忆时，如果丢掉"这条信息允许被怎么用"的来源约束，记忆就会获得超过其来源的权威。素材称 49 个配置中有 48 个存在此问题。自动标注并持久化 authority 标签后，未授权行动率从 16.9% 降到 0.0%。

落地方式是：每条记忆或技能都带来源标签，标签取值示例为人下令、已验证 receipt、仅观察。低权威条目禁止被当作指令执行。这一约定只需在 frontmatter 中加一行。

第二项是自投毒（EvoMal，arXiv 2608.25776）。自己写工具的 coding agent，会把检索到的恶意技能当模板模仿，生成携带载荷的新技能并回写技能库，形成自传播的蠕虫。在 153 个 SWE-bench 任务上，自投毒率为 20.3% 至 41.8%。

落地方式是：保持"自动起草、人审发布"，不放松。从外部引入的技能，例如 shared-skills 拉取的技能，要加静态扫描步骤。

6.6 落地三步

  1. 第一步（本周）：技能变更回归门禁。workshop 发布技能前，跑固定 5 条样例集的 verify，防止退化。
  2. 第二步（下月）：supervisor 当场 steering。审查员发现问题后当场发出方向修正，同时写错误台账。
  3. 第三步（长期）：记忆晋升机制与技能来源标签。草稿区的记忆被第二次独立任务复用后晋升主记忆；技能带上来源标签。

七、代码实操

7.1 超长历史自动摘要：SummarizationMiddleware

示例来自课件 day08。

import os
from dotenv import load_dotenv
from langchain_openai import ChatOpenAI
from langchain.agents import create_agent
from langchain.agents.middleware import SummarizationMiddleware
from langchain_tavily import TavilySearch
from langgraph.checkpoint.memory import InMemorySaver

load_dotenv()
llm = ChatOpenAI(model="qwen3.5-flash-2026-02-23",
                 api_key=os.getenv("DASHSCOPE_API_KEY"),
                 base_url=os.getenv("DASHSCOPE_BASE_URL"),
                 temperature=0.1)

SHORT_SUMMARY_PROMPT = """你是一个记忆压缩专家。请将下方的对话历史压缩成一段简洁的背景摘要，
保留：1) 用户最终目标  2) 已执行的关键步骤  3) 待办事项。
待压缩的对话：{messages}"""

agent = create_agent(
    model=llm,
    tools=[TavilySearch(max_results=1)],
    checkpointer=InMemorySaver(),           # 短期记忆：按 thread_id 存历史
    middleware=[SummarizationMiddleware(    # 中间件：超长自动摘要
        model=llm,
        trigger=[("tokens", 4000), ("messages", 10)],  # 或关系
        keep=("messages", 5),               # 保留最近 5 条，其余做摘要
    )],
)

config = {"configurable": {"thread_id": "user-001"}}
agent.invoke({"messages": [{"role": "user",
                             "content": "2026年3月最新的AI大模型技术趋势？"}]}, config)

关键参数如下。

  • trigger 有三种触发方式：("tokens", 4000)、("fraction", 0.5)、("messages", 10)。多个条件之间是 OR 关系，任一满足即触发。
  • keep=("messages", 5) 表示保留最近 5 条原文，更早的全部交给 LLM 做摘要。
  • 示例中定义的摘要提示词要求保留三项内容：用户最终目标、已执行的关键步骤、待办事项。
  • checkpointer=InMemorySaver() 是内存版。生产环境换成 SqliteSaver 或 PostgresSaver。
  • thread_id 是会话隔离的键。不同用户必须传不同的值，否则会串台。

7.2 短期记忆：Checkpointer 与 trim_messages

示例来自课件 day13 与 day15。

import os
from dotenv import load_dotenv
from langchain.chat_models import init_chat_model
from langchain_core.messages.utils import trim_messages, count_tokens_approximately
from langgraph.graph import StateGraph, MessagesState, START, END
from langgraph.checkpoint.memory import InMemorySaver

load_dotenv()
llm = init_chat_model(api_key=os.getenv("DASHSCOPE_API_KEY"),
                      base_url=os.getenv("DASHSCOPE_BASE_URL"),
                      model_provider="openai",
                      model="MiniMax-M2.1")

def call_llm(state: MessagesState):
    # 调 LLM 前先修剪消息，防止 token 爆掉
    messages = trim_messages(
        state["messages"],
        strategy="last",
        token_counter=count_tokens_approximately,
        max_tokens=500,
        start_on="human",
        end_on=("ai", "tools", "human"),
    )
    return {"messages": [llm.invoke(messages)]}

builder = StateGraph(MessagesState)
builder.add_node(call_llm)
builder.add_edge(START, "call_llm")

# 关键：compile 时传入 checkpointer，自动按 thread_id 持久化
graph = builder.compile(checkpointer=InMemorySaver())

config = {"configurable": {"thread_id": "user-001"}}
graph.invoke({"messages": "我叫初见"}, config)
graph.invoke({"messages": "帮我家猫写首诗"}, config)
final = graph.invoke({"messages": "我叫什么名字？"}, config)
print(final["messages"][-1].content)   # 能答出"初见"

关键概念如下。

  • checkpointer 在每一步执行完后，自动把 state 序列化到后端，后端可以是内存、SQLite、Postgres 或 Redis。
  • thread_id 是会话主键。同一个 thread_id 的多次 invoke 会自动加载上次的 state。
  • trim_messages 在调用 LLM 前按 token 数截断历史。start_on="human" 保证截断后第一条永远是用户消息，不会从 AI 的半截回复开始。
  • 生产环境换成 langgraph-checkpoint-sqlite 或 PostgreSQL，重启后会话不丢失。

trim_messages 只按长度截断，不做压缩。最佳答案的缺口清单中还有一项多轮对话 query rewriting，即当前把全部历史塞进去会导致 token 爆炸，该项尚未实现。

7.3 长期记忆：Store 与语义检索

示例来自课件 day13。

import uuid
from langgraph.store.memory import InMemoryStore
from langchain_huggingface import HuggingFaceEmbeddings

# 带向量索引的 store：可以语义搜索记忆
store = InMemoryStore(
    index={
        "embed": HuggingFaceEmbeddings(model_name="BAAI/bge-large-zh-v1.5"),
        "dims": 1024,
        "fields": ["hobby", "food_preference"],   # 对哪些字段建向量索引
    }
)

namespace = ("user-001", "memories")   # (user_id, 命名空间)

# 存
store.put(namespace, str(uuid.uuid4()),
          {"hobby": "篮球、音乐、美食、编程"})
store.put(namespace, str(uuid.uuid4()),
          {"food_preference": "臭豆腐、小龙虾、红烧肉"})

# 语义搜：query 是自然语言，自动 embedding 匹配
results = store.search(namespace, query="用户喜欢吃什么？", limit=3)
for r in results:
    print(r.dict())

代码中 fields 指定对哪些字段建向量索引。search 接收自然语言的 query，并自动做 embedding 匹配。

Checkpointer 与 Store 的分工如下。

  • checkpointer 是短期记忆，按 thread_id 保存当前会话的 state。
  • Store 是长期记忆，按 namespace（如 user_id）保存跨会话的用户画像。
  • 真实产品中，checkpointer 用 PG，Store 用 PG 或向量库（如 Qdrant）。

八、小结

  • 记忆分为短期和长期。短期用 checkpointer，按 thread_id 隔离；长期用 Store，按 namespace 隔离。
  • 双进程范式用门控区分快慢两条路径。多智能体用三层图分层存放经验，检索深度按角色决定。
  • 记忆的寿命按内容变化速度设定，过期记忆必须可见。冲突更新交给代码取最新时间戳，LLM 只负责识别是不是同一件事。
  • 信念修订用双向 supersedes 指针保留演化链，不做物理删除。
  • 自进化靠快慢双速、当场 steering 和技能回归门禁推进，同时用 authority 标签与"自动起草、人审发布"来控制风险。
