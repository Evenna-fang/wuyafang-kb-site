LangGraph 状态机：从状态设计到可恢复执行

← 返回知识库总入口

本篇把课件的图编排语法、两本书的章节重点、官方文档和旧稿中的本机实验记录合并为一条完整主线。下一篇从业务上线角度讨论部署、验证、观测、评估与回滚：Agent 生产级部署。

证据口径：文中“旧稿记录的本机实测”均指旧稿在 langgraph 1.2.11、确定性节点和内存检查点上的历史实验，本次整理没有重跑。生产 PostgreSQL 路径未实连，代码是可继续验证的骨架，不代表已经在当前环境跑通。

WHY

2

为什么 Agent 需要状态机，而不是更长的提示词

3

单轮问答的核心是“输入一个问题，返回一个答案”；业务 Agent 的核心却是“在多次模型判断和外部动作之间，持续推进一个可检查的任务”。后者天然包含循环、等待、失败、恢复和人工接管。若把所有逻辑塞进一个 ReAct 循环，短期看代码很少，长期会出现四类失控：模型反复调用同一工具却没有统一停止条件；进程退出后只剩一段聊天文本，无法知道哪些步骤真正完成；工具已经扣款或发信，重试又执行一次；人工审批期间一直占用进程，重启后无法接着审批。

LangGraph 的价值不是让图看起来复杂，而是把这些隐式行为变成显式工程对象。状态回答“现在知道什么”，节点回答“这一步做什么”，边回答“接下来去哪”，检查点回答“失败以后从哪里恢复”，中断回答“何时把决定权交还给人”。这正好对应书籍章节笔记反复强调的图式思维：先确定状态变化，再确定控制流，最后才选择模型和工具。

这也解释了为什么不能把状态机理解成固定 DAG。Agent 的“生成—检查—修订”“调用—失败—重试”“计划—执行—再规划”都需要回流边。但支持循环不等于鼓励自主漫游。生产图必须同时具备有限出口、步数预算、错误分类和人工兜底；否则图只是把一个不可控循环画得更漂亮。

为什么恢复能力会反过来决定代码结构

3

很多团队先写一个大节点，里面依次检索、调用模型、写数据库、发通知，最后再考虑接检查点。这种顺序会失败，因为检查点不是“给任意代码自动增加断点续传”的魔法。LangGraph 的恢复单位主要是节点：失败节点会从头重跑，而不是从抛异常的那一行继续。节点里越早发生的副作用，在重试和恢复时越可能重复。

因此，节点边界必须按恢复语义设计，而不是按代码文件长短设计。昂贵或不确定的模型调用应独立；有外部副作用的调用应独立；便宜、确定、可重复的格式转换可以合并。拆分以后，检查点才能保存“草稿已经完成，只剩发送”这一事实，避免恢复时重新生成草稿并再次扣费。

人机协同也遵循同一原则。interrupt() 恢复时，所在节点会从头执行，所以中断前的非幂等操作会重做。持久化不是最后接上的一个存储器，而是迫使我们把业务流程改写成可重放、可审计、可补偿的结构。

本篇解决什么问题

3

下文用一条“状态—路由—错误—持久化—中断—回放—观察”的链路回答六个问题：State 应该保存什么；并行结果怎样不丢失；静态路由和动态路由怎样选择；不同错误为什么不能一概重试；崩溃和审批后怎样安全恢复；怎样把执行过程暴露给测试、前端和事故复盘。阅读目标不是背 API，而是能为一个真实业务流程画出可恢复的最小图，并写出对应验收用例。

WHAT（WHYT）

2

一、StateGraph：共享状态、部分更新与受控流转

3

一张 StateGraph 由 State、Node 和 Edge 构成。节点接收当前状态，返回需要更新的字段，而不是直接修改整份状态；编译后的图负责把部分更新合并进状态并选择后继节点。普通边表达固定依赖，条件边表达有限路由，结束边把流程交给 END。

TypedDict 是图内部状态的常用轻量表达。它的价值首先是字段契约：哪些字段由入口提供，哪些由节点生成，哪些用于审计，都能被代码评审和测试看见。图的输入、输出 schema 可以与内部状态不同，因此对外只暴露必要字段，内部草稿和错误信息无需成为 API 承诺。入口边界若需要严格类型和范围校验，可以再用 Pydantic；不能把“内部 TypedDict 很轻”误解为“外部输入也不需要验证”。

State 的第一条设计红线是：只存原始数据，不存格式化后的 prompt。例如保存邮件正文、分类字典、检索片段、工具结果和审批决定，不要保存“你现在是客服，请根据以下材料……”这类拼接字符串。原始数据可以被不同节点按不同方式消费，提示词改版也不会迫使历史 checkpoint 改变结构。调试时，开发者看到的也是事实和决策，而不是难以 diff 的大段文本。

第二条原则是“跨步骤需要才保存，能推导则使用时再算”。把所有中间文本都放入 State，会让 checkpoint 膨胀、流式输出变大，也增加敏感数据长期留存的面。数据库连接、客户端对象等不可序列化资源不应作为业务状态保存；它们应由运行时依赖注入或节点内部获取。反过来，恢复后仍需要的业务事实不能因为“体积有点大”就藏进全局变量，否则换进程恢复时会丢失。

二、Reducer 与 add_messages：定义合并，而不是碰运气

3

普通字段的默认合并语义是新值覆盖旧值。对单一写入者的 status、draft 等字段，这通常合理；对并行分支共同写入的日志、结果列表，就会发生冲突。Reducer 用 Annotated[类型, 合并函数] 显式声明某个 key 如何合并已有值和节点更新，例如 operator.add 可以把各分支返回的列表拼接起来。

对话字段应优先使用框架提供的 add_messages，或直接继承 MessagesState。它不仅处理追加，还按消息 ID 支持更新语义；简单使用列表相加并不等价。工具消息还要维持与工具调用的配对关系，错误回灌时不能随意丢掉 tool_call_id。消息裁剪、人工修改和恢复都依赖这些结构，而不是依赖消息在列表中的偶然位置。

判断是否需要 reducer，不能只看“字段是不是列表”，而要看“同一执行步是否可能有多个写入者”。串行列表字段是否覆盖，由业务决定；并行列表字段若要汇总，就必须有合并规则。对于计数、集合、字典或只允许一个分支胜出的结果，也应选择符合业务的合并函数，而不是机械套 operator.add。Reducer 还要考虑空值和清空语义：追加型合并里返回空列表通常意味着“没有新增”，不是“清空历史”。

三、super-step、并行写冲突与节点边界

3

LangGraph 以 super-step 推进执行：同一步可运行的节点形成一批，节点更新按规则写回，随后进入下一步。一个节点有多条普通出边时，可以形成并行分叉；多个上游汇入后继时，可以形成等待汇合。并行能减少关键路径上的等待，但也引入共享状态竞争、外部限流和成本放大。

并行设计有三条检查线。第一，同一 key 的并发写入必须有明确 reducer，或者让每个分支只写自己的 key。第二，扇出数量必须有上限，尤其当分支数来自用户上传的文档数或模型生成的子任务数时。第三，外部工具要按下游容量限流，不能把“图支持并行”理解为“所有 API 都能承受同时调用”。

super-step 也是理解恢复和流式的关键。前端看到某个节点事件，不等于整个业务事务已经提交；某个并行分支成功，也不等于整步成功。涉及多个外部系统的写入，不能假设它们自动组成一个原子事务。需要原子性的场景应把事务放到同一业务系统内部，跨系统则采用幂等、读回和补偿。

四、普通边、条件边、Command 与 Send

3

四种路由手段应按“谁决定下一步”选择，而不是混着用。

手段 决策位置 适用场景 主要约束
普通边 图结构预先决定 固定先后、并行分叉与汇合 多条出边可能并行，不是按书写顺序逐个选择
条件边 独立路由函数 根据分类、错误码或审批状态选分支 路由函数只读状态，返回有限且已声明的出口
Command 节点执行后决定 同一节点要同时更新状态并跳转 声明可能去向，避免和该节点静态路由重复
Send 运行时生成任务列表 每项数据派一个 worker 的 map-reduce 控制扇出，worker 输入是显式子状态，汇总需 reducer

条件路由最适合把模型判断约束在枚举内。模型可以输出 question、refund、human 等类别，但不应自由生成任意节点名。路由函数遇到未知值要有安全出口，通常是澄清、人工审查或拒绝，而不是 KeyError 后让图崩溃。

Command(update=..., goto=...) 适合“执行结果本身决定下一步”。例如工具节点成功后去生成节点，参数可修正时把错误作为数据返回模型节点，超出修正次数则去人工节点。这里的关键是把状态更新和路由作为一个决策返回，而不是先修改一份隐藏全局状态再跳转。节点返回类型用 Command[Literal[...]] 标明可能去向，也有助于类型检查和图可视化。

Send(node, state) 用于运行时动态扇出。与固定并行不同，它允许为每个 worker 构造不同输入，例如每个文档片段只收到自己的 document_id 和正文。worker 不应假设能看到完整主状态；所需数据必须显式传入。所有 worker 的结果通过 reducer 汇总后，再进入 reduce 节点。若输入为空、重复或极大，路由层应先定义行为，避免静默返回空答案或制造调用风暴。

五、循环预算：recursion_limit 与 RemainingSteps

3

带环图必须有停止条件。recursion_limit 是运行时安全网，限制一次运行可推进的 super-step 数，超过后抛出递归错误。它应放在顶层 config，而不是塞进 configurable。它的作用是最后一道防爆阀，不能代替业务停止条件：订单已终态、审批已拒绝、证据已足够、错误不可恢复，都应在图内明确结束。

RemainingSteps 是由框架维护的剩余步数信息，可用于在接近上限前进入降级分支。与直接让递归错误冒出相比，图内降级能返回“暂时无法完成，已保留任务并转人工”这类可处理结果。但要给降级和收尾节点预留步数，不能在剩余一步时才试图执行一段多节点补偿流程。

合理的上限来自业务 trace：先估算最大模型轮数、工具调用数、修订次数和并行汇合开销，再加少量余量。固定流程的防御上限与开放式 Agent 的循环预算不会相同。任何具体数值都只是业务配置起点，不是 LangGraph 官方保证；必须通过故障注入证明超限后确实停止、状态可查、费用不继续增长。

六、错误分类、RetryPolicy 与 fallback

3

生产错误至少分四类，处理者和动作都不同。

  1. 瞬时基础设施错误：连接中断、明确可重试的限流或下游临时不可用。适合节点级 RetryPolicy，配合超时、指数退避和抖动。
  2. 模型可修正错误：工具参数不符合 schema、输出解析失败、缺少可推导字段。适合把结构化错误写回 State，让模型在有限次数内修正。
  3. 需要外部决定：缺账号、越权、高风险审批、证据冲突。适合 interrupt() 等待用户或人工，而不是让模型猜测。
  4. 程序缺陷或永久业务错误：字段不存在、依赖版本错误、余额不足、订单状态不允许退款。应快速失败或走确定 fallback，不能用重试掩盖。

RetryPolicy 的重试单位是节点。配置时应显式限定 retry_on，并设置最大尝试次数和时间参数；不要因为默认策略“可能认识某类异常”就把所有业务异常交给它。重试只能解决“再次执行可能成功”的问题，不能修复逻辑错误，更不能保证副作用只发生一次。

fallback 也不是“换个模型再来一遍”这么简单。可靠顺序通常是：同类健康实例、能力较弱但可用的模型、缓存或简化结果、明确拒绝并保留任务。每次降级都要记录原因和质量损失，防止系统长期静默运行在低质量路径。重试耗尽后的恢复分支可以更新错误状态并路由到 fallback；具体声明式错误处理参数依赖框架版本，使用前要核对当前 API，不能把较新文档中的参数直接移植到旧版本。

七、Checkpointer、Store 与 thread_id

3

Checkpointer 保存图执行过程中的状态快照，是会话续接、失败恢复、人审和 Time Travel 的基础。Store 保存应用自定义的跨线程数据，适合用户偏好、长期事实和共享知识。前者回答“这个任务执行到哪”，后者回答“不同任务之间哪些信息可以复用”，两者不能互相替代。

thread_id 是线程恢复的主键。同一任务的多次调用、崩溃后的 invoke(None, config)、审批后的 Command(resume=...) 都要使用同一个线程标识。不同用户或不同业务任务必须隔离，不能图省事共用固定值；业务授权还必须在数据层检查“当前调用者能否访问该 thread”，只知道标识不应等于拥有读取和恢复权限。

内存 Saver 适合单测和原型，进程退出即丢。SQLite 适合本地或轻量单机场景。PostgresSaver／AsyncPostgresSaver 是生产候选，但要处理建表、连接池、迁移、并发、备份、保留和清理。旧稿只验证了内存检查点，没有实连 Postgres，因此本篇不宣称生产持久化已验证。

checkpoint 会随步骤增长，保留策略必须区分运行中、等待审批、已完成和审计冻结的线程。不能简单按时间删除所有旧记录，否则一笔等待数天的审批会失去恢复依据。State 的 schema 演进也要考虑旧 checkpoint：新增字段应有默认或兼容读取逻辑，重命名节点和改变字段类型都可能让挂起线程无法在新代码上恢复。

八、节点级恢复与 durable execution

3

StateGraph 的恢复不是行级续跑。已完成节点从检查点读取结果，失败或中断节点从节点开头重跑；节点内子图还有相应父图和子图恢复边界。由此得到一条硬规则：恢复会重跑的节点必须幂等，至少不能造成不可接受的重复副作用。

所谓幂等，不是“代码看起来一样”，而是同一业务动作用同一幂等键重复请求时，外部世界仍只有一个有效结果。下游若支持幂等键，应稳定传递订单号、任务号加动作名等标识；下游不支持时，需要本地去重记录、写后读回或补偿流程。仅在节点里打印“已经执行”不能防重。

Functional API 的 @task 可以把已完成任务的结果记入检查点，恢复时复用，从而减少函数重放中的重复调用。但它仍不能解决“外部动作已经生效，本地在收到响应前崩溃”的半完成窗口。无论 Graph API 还是 Functional API，副作用本身的幂等和结果读回都不可省略。

持久化写入时机也存在可靠性与延迟取舍：同步持久化更强调下一步前落盘，异步模式折中吞吐，退出时持久化则不适合要求中途崩溃可恢复的流程。选择应依据动作风险、任务长度和可重做成本，并用杀进程测试验证，而不是只凭模式名称判断。

九、interrupt、Command(resume) 与副作用位置

3

interrupt(payload) 把可序列化的审批问题暴露给调用方并保存暂停状态；调用方之后用同一线程和 Command(resume=value) 恢复。恢复值会成为本次 interrupt() 的返回结果，节点再据此更新审批状态，后续条件边决定继续、修改或拒绝。

最重要的规则是：恢复时节点从头执行，所以 interrupt 前不得有非幂等副作用。推荐把中断放在审批节点最前面，把扣款、发送、发布等动作放到审批后的独立节点。即使中断前只是写日志，也应考虑重放后是否会产生重复审计事件。不要用宽泛的 try/except Exception 包住 interrupt()，以免把框架用于暂停的控制流异常吞掉。

同一节点多个中断按顺序匹配恢复值，条件性跳过或不确定循环会让恢复错位。需要反复校验输入时，应每轮保存提示和错误，再通过条件边重新进入审批节点，而不是在一个节点里写无限 while True。多个并行中断则需要按各自 ID 提交恢复值，不能假设一个布尔值能代表所有审批。

十、Time Travel：replay 是重走，fork 是新增历史

3

get_state_history(config) 可查看线程历史。选择某个 checkpoint 后以空输入继续，是从该位置重放后续节点；update_state(...) 则可以在历史状态上写入修正并形成分叉。分叉不是把旧历史抹掉，原记录仍可用于审计，这一点对事故追责和人工纠错都很重要。

重放并不保证得到原结果。模型输出可能变化，外部数据可能更新，副作用节点也可能再次执行。因此 replay 更像“在指定状态重新运行后续图”，不是无副作用的只读影片。用于生产纠错前，要识别后续路径上的写操作，必要时在隔离环境重放，或改走带补偿的分叉流程。最终已经无后继的检查点也不能提供“重新执行整个任务”的捷径。

旧稿记录过一个值得复核的细节：从历史 checkpoint 重放到新的中断后，继续携带旧 checkpoint_id 恢复曾复用旧恢复值，改用只含 thread_id 的 config 后得到新决定。该现象本次未重跑、原因也未定位，不能上升为所有版本的普遍规则；但它提醒我们在恢复测试中明确区分历史 config 和线程最新 config。

十一、Streaming 与 Functional API 的定位

3

Streaming 解决的是执行过程如何被观察。values 提供每步完整状态，适合调试但数据量大；updates 提供节点增量，适合进度展示；messages 暴露模型 token，适合打字机效果；custom 让节点发送业务进度；检查点、任务和调试模式服务于更细的排障。多种模式可以同时订阅。若需要子图内部事件，要核对并启用子图流式选项，否则可能最终答案正确，却看不到子图 token 和节点进度。

Functional API 用 @entrypoint 与 @task 表达普通 Python 控制流，同时复用持久化、恢复和中断能力。它适合线性或简单分支、已有函数渐进接入、希望用任务缓存减少重复工作的场景。Graph API 更适合复杂回流、显式路由、动态扇出和需要图评审的场景。两者是同一运行模型下的不同表达，不是“高级版”和“低级版”的关系。

一、完整最小图：原始状态、条件路由与安全出口

3

下面的确定性骨架不调用真实模型，用来展示最小图的完整结构。实际接入时，只需把 classify 和 draft 内的占位逻辑替换为受控服务调用；测试仍应保留假实现，避免流程测试依赖模型随机性。

import operator
from typing import Annotated, Literal, TypedDict
from langgraph.graph import END, START, StateGraph


class TicketState(TypedDict):
    ticket_id: str
    raw_text: str
    category: str
    draft: str
    status: str
    trail: Annotated[list[str], operator.add]


def classify(state: TicketState) -> dict:
    # 真实项目让模型只返回有限枚举，不返回节点名
    text = state["raw_text"]
    category = "billing" if "退款" in text else "question"
    return {
        "category": category,
        "trail": [f"classify:{category}"],
    }


def route_category(state: TicketState) -> Literal["billing", "answer", "human"]:
    # 路由只读状态，未知类别进入人工安全出口
    return {
        "billing": "billing",
        "question": "answer",
    }.get(state["category"], "human")


def billing_node(state: TicketState) -> dict:
    # 此处只做资格判断；真实退款应放到独立幂等动作节点
    return {"status": "needs_refund_check", "trail": ["billing"]}


def answer_node(state: TicketState) -> dict:
    return {
        "draft": f"已受理问题：{state['raw_text']}",
        "status": "answered",
        "trail": ["answer"],
    }


def human_node(state: TicketState) -> dict:
    return {"status": "needs_human", "trail": ["human"]}


builder = StateGraph(TicketState)
builder.add_node("classify", classify)
builder.add_node("billing", billing_node)
builder.add_node("answer", answer_node)
builder.add_node("human", human_node)
builder.add_edge(START, "classify")
builder.add_conditional_edges(
    "classify",
    route_category,
    {"billing": "billing", "answer": "answer", "human": "human"},
)
builder.add_edge("billing", END)
builder.add_edge("answer", END)
builder.add_edge("human", END)
graph = builder.compile()

result = graph.invoke({
    "ticket_id": "ticket-001",
    "raw_text": "我想申请退款",
    "category": "",
    "draft": "",
    "status": "new",
    "trail": [],
})
assert result["status"] == "needs_refund_check"

验收重点不是输出文本是否漂亮，而是路径是否符合预期。至少准备 question、billing、未知类别三类输入，检查 trail、终态和没有访问的分支。若把分类节点改为 Command 路由，应在同一返回值中写入分类和 goto，并删除重复的静态条件边，避免两套路由同时生效。

二、动态扇出：Send、局部输入与 reducer 汇总

3 
import operator
from typing import Annotated, TypedDict
from langgraph.graph import END, START, StateGraph
from langgraph.types import Send


class ResearchState(TypedDict):
    documents: list[str]
    summaries: Annotated[list[str], operator.add]
    report: str


def fan_out(state: ResearchState) -> list[Send]:
    # 扇出上限是业务预算的一部分，示例值不是通用推荐
    documents = state["documents"]
    if not documents:
        raise ValueError("空文档集必须显式拒绝或走空结果分支")
    if len(documents) > 20:
        raise ValueError("超过单批上限；调用方必须分批，禁止静默截断")
    return [
        Send("summarize_one", {"document": document})
        for document in documents
    ]


def summarize_one(state: dict) -> dict:
    # worker 只依赖显式传入的局部状态
    return {"summaries": [f"摘要:{state['document']}"]}


def reduce_results(state: ResearchState) -> dict:
    return {"report": "\n".join(state["summaries"])}


builder = StateGraph(ResearchState)
builder.add_node("summarize_one", summarize_one)
builder.add_node("reduce_results", reduce_results)
builder.add_conditional_edges(START, fan_out, ["summarize_one"])
builder.add_edge("summarize_one", "reduce_results")
builder.add_edge("reduce_results", END)
map_reduce_graph = builder.compile()

当前骨架对空文档和超过 20 个文档都显式拒绝，由调用方选择空结果分支或分批；不会生成遗漏输入的“完整报告”。这里还要用三个负例验收：空文档列表是否按业务返回明确空结果或拒绝；超过上限是否按预期拒绝、截断或分批且行为可解释；两个 worker 同时写 summaries 时结果是否全部保留。还应记录扇出数和实际外部调用数，避免代码截断了输入，却在别的重试路径继续放大成本。

def route_remaining(state: LoopState) -> Literal["repair", "fallback"]:

    return "fallback" if state["remaining_steps"] <= 2 else "repair"

五、人审：中断先行，副作用后置

3 
from typing import Literal
from langgraph.types import Command, interrupt


def approve_refund(state: TicketState) -> dict:
    # 节点最前面中断，之前不扣款、不发通知、不写外部系统
    decision = interrupt({
        "kind": "refund_approval",
        "ticket_id": state["ticket_id"],
        "summary": state["raw_text"],
    })
    if decision not in {"approve", "reject"}:
        return {"status": "invalid_approval"}
    return {"status": decision}


def route_approval(state: TicketState) -> Literal["execute", "close", "human"]:
    return {
        "approve": "execute",
        "reject": "close",
    }.get(state["status"], "human")


# 首次调用后检查 __interrupt__，恢复仍使用同一 thread_id
# first = graph.invoke(initial_state, config)
# resumed = graph.invoke(Command(resume="approve"), config)

execute 应是独立幂等节点，且执行后再做结果读回。验收用例至少覆盖：批准只执行一次；拒绝不执行；非法恢复值不执行；审批等待期间重启进程可恢复；同一中断重复提交不会产生第二笔动作；中断前的日志或通知是否因重放重复。若涉及钱、权限或对外发布，还要把审批人、理由、时间和动作版本写入不可变审计记录。

from langgraph.checkpoint.memory import InMemorySaver
from langgraph.func import entrypoint, task


@task
def load_document(document_id: str) -> str:
    # 外部读取结果会作为 task 结果参与恢复
    return f"原始文档:{document_id}"


@task
def summarize_document(document: str) -> str:
    return f"摘要:{document}"


@entrypoint(checkpointer=InMemorySaver())
def document_workflow(document_id: str) -> str:
    document = load_document(document_id).result()
    return summarize_document(document).result()

Functional API 的验收与图相同：在第二个 task 前制造失败，恢复后第一个 task 不应因已完成而无意义地重复；若第一个外部动作只执行到一半，则仍需要幂等和读回。流式验收则分别检查 token、节点事件、子图事件和中断载荷，不能只看最终文本。

八、本批论文怎么用：按可避免的任务损失验收状态与记忆

3

arXiv:2610.31303 把记忆价值拆成保存、操作使用、 costly recovery 与修订：保留多少 token 不是目标，真正要比较的是某种持久状态能否降低后续任务损失。论文的反例还指出，一个与答案零互信息的指针仍可能降低精确恢复成本；在固定检索证据时，保存 ledger 会改变后续回答，在固定 Agent 输出时，评估器修订又会改变分数。因此不能只用“上下文更短”或一次回答分来证明 Checkpointer/Store 设计有效。

我们怎么用：为 LangGraph 增加三组确定性对照。保存测试比较完整正文、受控引用和丢弃三种状态，在相同任务上测恢复成功率与读取成本；使用测试固定检索证据，只切换 ledger/checkpoint 是否可读，检查后续决策是否真正利用它；修订测试在需求变化后更新来源与版本，验证旧事实不再静默覆盖新事实，同时仍可从历史 checkpoint 审计。大对象优先存受控引用加哈希，但引用必须可解析、可授权、可恢复；不能因论文肯定某些指针的恢复价值，就把任意 URL 或不可序列化连接塞入 State。
