Multi-Agent 协作：从单 Agent 基线到可控编排

返回知识库总入口

资产定位：总地图 N2 知识提炼，四之一知识层。本文先建立 ReAct、Plan-and-Execute、Reflection 的单 Agent 基线，再讨论 orchestrator-worker、sequential pipeline、parallel fan-out、handoff、debate 与 supervisor/subagents。检索侧的反馈门控见 Agentic RAG 六模式。

WHY：先证明单 Agent 不够，再支付协作成本

2

1. 单 Agent 基线：ReAct、Plan-and-Execute 与 Reflection

3

多 Agent 选型不能从“我要几个角色”开始，而要先知道一个 Agent 在何处失败。课件 day07—09 用 create_agent、Function Calling 和中间件形成最小执行闭环：模型根据消息选择工具，工具结果回到消息历史，模型继续决策；before_agent、wrap_tool_call 等钩子负责权限、审计、参数清洗和重试。这个阶段最重要的不是框架名称，而是把输入、工具、状态、反馈和停止条件做实。

ReAct 在每轮观察后决定下一动作，适合路径不确定、需要边走边看的短任务。它的优势是适应性，短板是局部视野和绕圈风险。必须设置 max_iterations、工具次数与总时延上限；不能因为框架自动处理 tool-call loop，就误以为循环天然会结束。

Plan-and-Execute 先由 Planner 产出有序步骤，再由 Executor 逐步执行，必要时 Replanner 根据真实工具结果调整剩余计划。课件 day10 的旅行规划示例体现了“先计划、每步用 ReAct 执行”的组合。它适合可分解、依赖明确的任务，不适合需求本身仍模糊或环境快速变化的场景。计划是待验证假设，不是完成凭据；每一步都要写回状态、检查失败，而不是把生成计划当成任务完成。

Reflection 在草稿之后加入批评与修订，适合代码、方案、法律文书等质量敏感产物。反馈应尽量来自测试、规则校验、检索证据或独立评审，而非同一个模型反复宣布“我已改进”。反思只放在关键产物上，并限制修订轮数；每个工具调用后都反思，通常只会放大成本和自我偏好。

三者可以组成强单 Agent：Planner 管全局，Executor 内部用 ReAct 适应环境，最终由 Reflection 或确定性测试把关。如果这个组合在质量、延迟和成本上已满足需求，就没有理由拆成多 Agent。

2. 拆分信号要落在可测量瓶颈上

3

真正值得评估拆分的信号包括：单一上下文无法容纳任务所需信息；工具与指令过多导致选择错误；子任务可独立并行且总时延受关键路径限制；不同子任务需要不同权限、工具或模型；执行者与审查者必须分离；团队需要独立维护不同能力。相对的，“流程看起来复杂”“框架支持多角色”“想让系统显得更智能”都不是拆分理由。

拆分前先跑三组基线：单 Agent 顺序执行、单 Agent 加并行工具调用、单 Agent 加 Planner/Reflection。只有多 Agent 相对这些基线在同一评测集上有稳定增量，才继续。评估要同时记录任务成功率、最终产物质量、token、墙钟时间、工具调用、人工接管和失败定位时间。新增一个角色就新增一份提示、一条上下文边界和一类故障，不能只比较最终答案。

3. 第一问：产物是“信息”，还是“需一致的制品”

3

这是 Anthropic 与 Cognition 两种看似相反观点可以统一的边界。

产物是信息。 例如分别调研三个技术方案、搜索不同语料、独立核对若干事实。子任务读多写少，结果是可以去重、引用和排序的信息，不要求所有执行者共享同一设计决策。此类任务适合 parallel fan-out 或 orchestrator-worker，主 Agent 最后综合。

产物是需一致的制品。 例如同一个代码仓库、统一视觉设计、共享数据库 schema 或一份逻辑严密的长文。写多读少时，每个动作都带有隐含决策：命名、接口、结构、风格、数据约束。多个 Agent 即便拿到相同需求，也可能作出互相冲突的局部选择，最终合并成本高于并行收益。此类任务优先单线程；可以并行只读分析，但由一个写入者串行落地。

Cognition 因此主张共享完整 agent trace 而非零散消息，并指出动作携带隐含决策。这里的“共享 trace”不等于把所有内容无差别塞给每个 Agent，而是关键决策及其理由必须可见；大体积中间数据仍应按引用传递。Anthropic 的研究系统则展示了另一面：在可广度并行、结果是研究信息的工作中，lead 与独立上下文子 Agent 能发挥作用。其 +90.2%、约 4 倍与 15 倍 token 等数字均来自原文内部研究评测和其成本口径，只说明该系统的权衡，不能外推为任意任务都提升或都消耗相同倍数。

WHAT（WHYT）：六种协作模式的控制流、上下文与终止

2

1. Orchestrator-worker：中心规划，工作者执行

3

控制流。 Orchestrator 接收目标、拆解任务、选择 worker、收集结果并决定是否补派。Worker 只完成明确子任务，不直接改变全局计划。书籍《Building Agentic AI Systems》的 Coordinator—Delegator—Worker 可视为职责细分：Coordinator 管目标与整合，Delegator 管能力、负载和权限匹配，Worker 管执行。三者可以部署为三个组件，也可以由一个编排进程承担。

上下文与状态。 编排器保存全局目标、任务 DAG、预算、各任务状态和最终整合所需摘要；worker 默认只拿最小任务包及必要证据引用，不继承整段对话。全局状态应包含任务版本、依赖、幂等键、产物位置、错误和重试次数。需要 worker 延续上游决策时，传“已决定事项及理由”，而不是只传最后一句答案。

终止条件。 所有必需任务成功且整合通过验收；或预算耗尽、关键路径失败、无法消除的阻塞出现。可失败的可选任务不应拖死全局，但必须显式标记缺失。

适用与反例。 适合复杂研究、多源分析、异构工具与明确分工。反例是强一致制品并行写入、任务无法清晰拆解、编排器本身成为单点且没有持久化。同步等待全部 worker 还会让最慢分支决定总延迟，必要时应改异步任务与结果轮询，而不是不断增加空等重试。

2. Sequential pipeline：依赖明确的质量流水线

3

控制流。 任务按 A→B→C 顺序执行，每步消费上游产物并产生新产物，例如检索→分析→写作→审查。CrewAI 的 Process.sequential 与 Task context 是课件 day10 的直观示例；生产上更重要的是上游产物要结构化传递，不能只写“等上一步完成”。

上下文与状态。 每一步只需要本步指令、上游契约产物和全局不可变约束，无需复制全部历史。状态机记录当前阶段、输入版本、产物哈希、门禁结果和补偿动作。并行分支若汇入同一阶段，必须先定义合并规则。

终止条件。 最后阶段通过验收；任一强制质量门失败时可回到指定前序阶段修订，但回退次数有限。永久性输入错误应立即终止，不做无意义重试。

适用与反例。 适合数据加工、文档生产、发布审核等依赖清晰的流程。反例是步骤之间没有真实依赖，串行只会增加延迟；或每一步都需要全局反复协商，硬串行会制造大量返工。流水线的单点慢会拖住全链路，应监控各阶段耗时，而不是只测总耗时。

3. Parallel fan-out：动态分发，受控汇合

3

控制流。 Map 阶段把相互独立的子任务同时发给多个 worker，Join/Reduce 阶段等待所需结果并归并。LangGraph Send 支持运行时决定分支数，课件 day11 的 map-reduce 示例说明局部状态只发给对应 worker，reducer 负责结果合并。

上下文与状态。 每个分支有独立输入和局部状态，全局只共享只读约束与任务标识。并行写必须写唯一 key，或通过 reducer 合并；不能让多个节点直接覆盖同一字段。大结果写产物存储，状态中只留引用、哈希和摘要。

终止条件。 必需分支全部完成，或达到“允许部分成功”的法定数量；总 deadline 到期后取消剩余分支并汇总部分结果。扇出数量、单分支重试和总 token 必须有硬上限。

适用与反例。 适合多文档摘要、独立检索、批量只读分析。反例是分支共同修改一个仓库或数据库、任务拆分后高度重复、Join 必须等待一个可能永久挂起的分支。并行不是免费加速，模型配额、下游限流和汇合成本都可能使吞吐反而下降。

4. Handoff：移交控制权，而非一次普通委派

3

控制流。 当前 Agent 通过 transfer_to_x 工具或 Command(goto=...) 把后续对话控制权交给另一个 Agent。接收方成为新的主动方，可直接与用户交互；这与“主 Agent 调子 Agent 工具并继续掌握最终回答权”不同。课件 day16 的主管与专家交接体现了这一模式。

上下文与状态。 状态需包含 active_agent、移交原因、最小任务摘要、已完成工作、未决问题和移交历史。工具调用必须有配对的 ToolMessage 与 tool_call_id，否则消息历史不完整。全量历史默认不复制，接收方需要更多上下文时按引用拉取。

终止条件。 当前专家完成并返回结果、明确交给用户、进入终态，或移交次数超限转人工。状态中的路径记录用于检测 A→B→A 循环。

适用与反例。 适合售前转技术支持、保修确认后转退款、需要不同角色直接接管的对话。反例是需要并行探索、主 Agent 必须持续统一口径、多个专家频繁互相退回。Handoff 不适合隐藏责任边界：每次移交都要能解释为什么、交给谁、带走了什么。

5. Debate：独立意见与仲裁，不是多人聊天

3

控制流。 两个或多个 Agent 在不知道彼此答案的情况下独立作答，随后展示证据和分歧，由 arbiter 依据共同 rubric 裁决；必要时只针对分歧追加一轮。它适合高风险方案比较，不适合用角色数量替代证据。

上下文与状态。 独立阶段共享相同问题、约束和证据包，但不共享彼此结论，避免过早锚定。仲裁阶段保存各结论、证据来源、分歧点、少数意见和裁决理由。若议题可客观验证，测试和工具结果优先于“谁辩得更有说服力”。

终止条件。 仲裁作出决定、达到预设轮数，或证据不足升级人工。禁止以“大家终于同意”作为唯一质量标准，同源模型可能共同犯错。

适用与反例。 适合架构选型、复杂排障假设、独立风险评估。反例是简单事实题、存在确定测试可直接裁决、参与者没有独立信息或不同能力。辩论会增加 token 和延迟，也可能把原本正确的独立答案带偏，因此必须保留初始答案供审计。

6. Supervisor/subagents：主管保持控制，子 Agent 工具化

3

控制流。 Supervisor 接收用户目标，通过 task 或专用工具调用 subagent，拿到结构化回传后继续路由、整合或回答。Subagent 可以有独立提示、工具和内部循环，但对主管表现为受控能力。该模式与 orchestrator-worker 很接近，差别在强调点：前者常描述整体组织架构，后者强调“子 Agent 作为工具、主管保留控制权”的实现。

上下文与状态。 默认 subagent 无状态，每次在干净上下文中执行，主管保存会话和全局状态。只传任务契约，回传最终契约产物；需要排查内部过程时另接 trace 或将子 Agent 作为显式图节点。父图与子图 schema 不同则做显式映射，不能把内部消息无意泄漏到父状态。

终止条件。 子 Agent 成功、返回可回灌错误、超时或被取消；主管在所有必需子调用完成并通过验收后结束。每个子 Agent 也有独立迭代和工具上限，主管另有全局上限，形成双层预算。

适用与反例。 适合主管需要统一回答、子任务要求专用上下文、并行与多跳结合的场景。反例是用户必须直接与专家连续对话，此时 handoff 更自然；或所谓 subagent 只包装一次普通函数调用，直接给主管一个工具更简单。

7. 本批论文怎么用：共享记忆不能只按“稀有”或“相关”压缩

3

arXiv:2610.37624 的 CrossProfile 在 60 个模板、480 个 hidden-profile 任务上交叉安排支持证据、诱饵和无关事实。论文发现：按决策相关性挑选会把“也在话题内”的诱饵重新放进记忆；按稀有度挑选平均并不优于随机；给事实附上“很多 Agent 都这样说”的归属标签，还会诱发类似社会证明的额外权重。完整讨论 transcript 也可能比无笔记更差，因为证据在进入最终决策前就已经被噪声淹没。这些数值和结论属于该基准及所测模型，不是所有多 Agent 系统的固定损耗。

我们怎么用：orchestrator 汇总时不再只保存“最稀有/最相关”的几句话，而是保存 claim—evidence—source—counter_evidence 结构，确保支持项、反证和未决项按原任务配比可见；归属人数只能作为来源元数据，不能直接乘成置信度；Join 验收增加三组对照——打乱 Agent 归属标签、固定内容改变行序、比较完整 transcript 与结构化证据包——看最终答案是否被与证据无关的因素改变。对高风险决策，最终 arbiter 必须能回读原始证据引用；若结构化摘要反而遗漏关键反证，应判摘要门失败，而不是让下游继续“达成共识”。

HOW：契约、图骨架与生产故障治理

2

1. 用结构化契约替代散文式派单

3

委派契约必须让执行者知道目标、边界、可用工具、输入、完成定义和预算；回传契约必须让上游知道交付物、证据、未决项和真实状态。以下 Pydantic 模型可独立做校验，状态枚举避免“成功了但什么也没交”。

from enum import Enum
from typing import Literal
from pydantic import BaseModel, Field

class TaskStatus(str, Enum):
    SUCCEEDED = "succeeded"
    FAILED = "failed"
    BLOCKED = "blocked"
    PARTIAL = "partial"

class Budget(BaseModel):
    max_iterations: int = Field(default=5, ge=1, le=20)
    max_tool_calls: int = Field(default=10, ge=0, le=100)
    timeout_seconds: int = Field(default=120, gt=0)

class TaskContract(BaseModel):
    task_id: str                 # 全局追踪标识
    idempotency_key: str         # 重试去重键
    objective: str               # 单一可验证目标
    inputs: dict[str, str]       # 大对象只传引用
    expected_output: str         # 完成态与格式
    acceptance: list[str]        # 可机检或可审查的验收条件
    allowed_tools: list[str]     # 最小权限工具集
    read_scope: list[str]        # 允许读取的工作域
    write_scope: list[str]       # 允许写入的工作域，只读任务为空
    context_refs: list[str] = [] # 必要决策与上游产物引用
    budget: Budget = Budget()

class ResultContract(BaseModel):
    task_id: str
    status: TaskStatus
    summary: str
    artifact_refs: list[str] = []
    evidence_refs: list[str] = []
    decisions: list[str] = []    # 关键取舍及理由
    unresolved: list[str] = []   # 不确定性与未完成项
    rejected_actions: list[str] = []
    error: dict[str, str] | None = None
    metrics: dict[str, float] = {}

上游先校验 task_id、schema 版本和产物哈希，再接受结果。PARTIAL 不得被归并逻辑当成 SUCCEEDED；BLOCKED 必须说明缺什么输入或权限；错误文本不能含凭据、私有配置或无关原文。自然语言自由讨论可以存在，但跨边界状态和产物必须遵守契约。

2. LangGraph Send：有界扇出、异常回灌与显式归并

3 
import operator
from typing import Annotated, TypedDict
from langgraph.graph import StateGraph, START, END
from langgraph.types import Command, Send

class CollabState(TypedDict):
    tasks: list[TaskContract]
    results: Annotated[list[dict], operator.add]
    final_status: str

def dispatch(state: CollabState):
    task_ids = [task.task_id for task in state["tasks"]]
    if not task_ids:
        raise ValueError("空任务集直接拒绝，不允许被 all([]) 误判为成功")
    if len(task_ids) != len(set(task_ids)):
        raise ValueError("task_id 必须唯一，否则无法判定 Join 是否完整")
    return {}

def fan_out(state: CollabState):
    # 已返回 ID 不再派发；每轮最多四个，剩余任务由 reduce 转回 dispatch
    returned = {item["task_id"] for item in state["results"]}
    pending = [task for task in state["tasks"] if task.task_id not in returned]
    return [Send("worker", {"task": task}) for task in pending[:4]]

def worker(state: dict):
    task = state["task"]
    try:
        raw = execute_subagent(task)  # 注入具体执行器，内部也有迭代上限
        result = ResultContract.model_validate(raw)
        if result.task_id != task.task_id:
            result = ResultContract(
                task_id=task.task_id,
                status=TaskStatus.FAILED,
                summary="子 Agent 返回了其他任务的 ID，结果不予接受",
                error={"type": "task_id_mismatch", "retryable": "false"},
            )
    except TimeoutError:
        result = ResultContract(
            task_id=task.task_id,
            status=TaskStatus.FAILED,
            summary="子任务超时，未确认产生外部副作用",
            error={"type": "timeout", "retryable": "true"},
        )
    except Exception as exc:
        # 异常变成可观察结果，不让整个 Join 因一个分支静默消失
        result = ResultContract(
            task_id=task.task_id,
            status=TaskStatus.FAILED,
            summary="子任务执行失败",
            error={"type": type(exc).__name__, "retryable": "unknown"},
        )
    return {"results": [result.model_dump(mode="json")]}

def reduce_results(state: CollabState) -> Command:
    # 必须按全部必需 task_id 验收，不能把“当前已返回”误当全集
    required_ids = {task.task_id for task in state["tasks"]}
    returned_ids = {item["task_id"] for item in state["results"]}
    if unknown_ids := returned_ids - required_ids:
        raise ValueError(f"收到未知任务结果: {sorted(unknown_ids)}")
    if len(returned_ids) != len(state["results"]):
        raise ValueError("同一 task_id 返回了重复结果，必须先做幂等归并")
    if returned_ids != required_ids:
        return Command(goto="dispatch")  # 下一批最多四个，直到必需任务全部有结果

    required_ok = all(
        item["status"] == TaskStatus.SUCCEEDED.value
        for item in state["results"]
    )
    status = "ready_for_review" if required_ok else "degraded"
    return Command(update={"final_status": status}, goto=END)

builder = StateGraph(CollabState)
builder.add_node("dispatch", dispatch)
builder.add_node("worker", worker)
builder.add_node("reduce", reduce_results)
builder.add_edge(START, "dispatch")
builder.add_conditional_edges("dispatch", fan_out, ["worker"])
builder.add_edge("worker", "reduce")
graph = builder.compile()

骨架中的 execute_subagent 是注入点，不代表本文已连接真实模型。空任务和重复 ID 在入口拒绝；worker 拒绝把其他任务的结果冒充当前结果，Join 拒绝未知或重复结果 ID；超过四个任务会分批回到 dispatch，不会静默截断；Join 只有收齐全部必需 ID 才判断成功或降级。若业务允许部分成功，应另设法定数量和显式缺失清单，不能利用 all([])。Join 默认等待当前批次全部分支，慢分支会阻塞汇总；需要“先到先用”时应采用持久化异步 job、状态查询和取消机制。重试前必须先查幂等记录，尤其是写操作，不能仅凭超时就认定副作用未发生。

3. 工具化 subagent：主管保留最终回答权

3 
from langchain_core.tools import tool

@tool("research_specialist", description="只读调研一个明确子问题，返回结构化结论")
def call_research_specialist(task_json: str) -> str:
    task = TaskContract.model_validate_json(task_json)
    if task.write_scope:
        # 工具边界再次强制权限，不能只相信主管提示词
        return ResultContract(
            task_id=task.task_id,
            status=TaskStatus.BLOCKED,
            summary="只读子 Agent 收到越界写权限",
        ).model_dump_json()
    try:
        result = run_research(task)
        return ResultContract.model_validate(result).model_dump_json()
    except Exception as exc:
        # 将失败回灌给主管，由主管决定缩小范围、换源或终止
        return ResultContract(
            task_id=task.task_id,
            status=TaskStatus.FAILED,
            summary="调研工具未完成",
            error={"type": type(exc).__name__, "retryable": "unknown"},
        ).model_dump_json()

工具描述只声明能力，不构成安全保证。权限必须由执行层、沙箱和资源层再次检查。主 Agent 只依赖最终契约，不依赖子 Agent 中间自言自语；需要完整排障时，通过 trace_id 查看受控 trace，而不是把所有中间消息重新注入上下文。

4. Handoff 防死循环与消息一致性

3

移交状态至少记录 handoff_path、handoff_count、last_reason 和 active_agent。若下一目标已在最近路径中重复出现，或计数达到上限，就不再移交，转入主管汇总或人工。移交工具禁止与普通写工具并行调用，防止同一轮发生多个相互矛盾的控制权变更。

def guard_handoff(state: dict, target: str, reason: str) -> dict:
    path = state.get("handoff_path", [])
    count = state.get("handoff_count", 0)
    if count >= 4 or (len(path) >= 2 and path[-2] == target):
        return {"active_agent": "human_review", "stop_reason": "handoff_loop"}
    return {
        "active_agent": target,
        "handoff_path": path + [target],
        "handoff_count": count + 1,
        "last_reason": reason,
    }

若通过工具返回 Command，还要按所用框架版本保证 ToolMessage 与 tool_call_id 配对。接收方只获得最小交接包：用户当前目标、已完成工作、关键决定、移交原因和待办。让人接管前，最后一条消息应符合目标框架的消息约束。

5. 幂等、权限、检查点和补偿必须一起设计

3

幂等。 每个任务与副作用使用稳定幂等键，执行前后记录状态。读操作可缓存结果，写操作需要“准备—执行—确认”记录。超时只代表调用方未收到确认，不代表下游没有执行；恢复时先对账，再决定重试或补偿。付款、发信、发帖等不可逆动作不能只靠 LLM 判断。

权限。 每个 subagent 只获得完成契约所需的最小工具和数据范围，不继承主管的全部凭据。审查者默认只读，执行者不能自审自批。外部写入、跨域传输与高风险配置改动按影响与可逆性分级审批，审批失败默认关闭而非放行。

检查点。 课件 day13 的 checkpointer 与 thread_id 说明会话状态可以恢复；生产应将内存实现换成持久后端，并把任务、工具结果、产物和审批状态放在一致的状态模型里。恢复时跳过已确认步骤，不能从起点重放所有副作用。书籍关于决策版本化、反馈、反思和检查点的观点，在这里转化为可执行的状态治理。

补偿。 对已发生但后续流程失败的动作，定义补偿或人工处理路径。不能补偿的动作应在执行前确认。安全资源不足时不得通过关闭沙箱、放宽网络或越权读取来“降级”；正确降级是排队、缩小任务或失败关闭。

6. 独立审查与 decisive error 归因

3

执行者提交 ResultContract 后，独立审查者读取任务契约、最终产物、证据引用和必要 trace，按同一验收清单检查。审查者不应只看执行者的总结，也不应因输出更长、更自信而给高分。确定性检查优先，LLM 评审用于难以编码的质量维度；关键判断保留人工抽检。

失败复盘先找 decisive error：沿时间线和数据血缘定位最早产生并向下游传播错误的节点。例如 router 先派错任务，后续 worker 即使忠实执行也不是根因；子 Agent 生成错误 schema，主管未校验便接受，则“产出错误”和“门禁缺失”分别记录，但最早可阻断点要清楚。只让决定性错误所在环节做针对性反思，其他 Agent 不陪跑修改。修复后用同一失败样本回归，防止全员改 prompt 掩盖根因。

可解释性不等于展示冗长思维过程，而是能回答：接收了什么输入、依据哪些来源、调用了什么工具、作出什么关键决定、产物在哪里、谁批准、为何停止。trace 应跨主管与子 Agent 关联，同时对敏感信息脱敏。

7. 六员与 OpenClaw 模块协同的抽象案例

3

在不涉及任何本机敏感配置的前提下，可把现有协作思想抽象为：规划者生成任务 DAG，路由层按能力与工作域选择执行者，只读研究可并行，工程实现保持工作域互斥或单线程，独立审查者只读验收，最终由确定性门禁检查状态与产物。角色名称不是关键，关键是能力注册、权限边界和契约一致。

OpenClaw 模块笔记提供了另一视角：Routing 将 Task 拆为 Job 并选择 Target；Subagent Manager 管理 Pending、Running、Succeeded、Failed、Timeout 等生命周期；执行结果和资源用量写回历史，供路由复用、重试或升级；协同流程图把控制面、数据面与执行面分开。可复用的不是具体命令或配置，而是“任务路由—隔离执行—状态回流—审计复用”的闭环。

同时也要对笔记中的工程建议做安全筛选：资源超限不能成为取消隔离的理由，检索为空不能在高风险场景直接纯生成，幂等 ID 也不能替代真实业务去重。多 Agent 架构图越漂亮，越需要用失败注入验证降级路径是否真实存在。

9. 观测指标、负例与上线顺序

3

每种模式都应观测任务成功率、部分成功率、p50/p95 延迟、token 与单成功任务成本、扇出数、移交次数、重试与重复副作用、人工接管率、契约校验失败率、各阶段等待时间和审查驳回率。Orchestrator 还要看关键路径与单点排队，pipeline 看阶段返工，fan-out 看汇合等待，handoff 看往返循环，debate 看独立答案被改错的比例，supervisor 看子调用错误是否正确回灌。

负例至少覆盖：子 Agent 超时但写入已成功、同一任务重复投递、永久错误被反复重试、空产物却报告成功、部分结果被当成全量成功、A/B 互相移交、并行写覆盖、审查者越权修改、错误来源在跨 Agent 转述后变成“可信事实”。这些用例比一次 happy-path 演示更能证明系统可运行。

上线顺序建议为：先实现单 Agent 基线与结构化工具结果；再把一个明确的只读子任务工具化；然后加入有界 Send 并行和 reducer；需要直接角色接管时再加 handoff；最后才考虑自由辩论或更复杂拓扑。每增加一层都重跑基线、负例和恢复测试。最终目标不是让最多 Agent 同时工作，而是用最少的控制权转移，得到可验证、可恢复、可归责的结果。
