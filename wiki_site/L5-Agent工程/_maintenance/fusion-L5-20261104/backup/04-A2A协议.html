A2A 协议：Agent Card、任务生命周期与可靠协作实战

← 返回总入口
相关新篇：MCP 协议实战：从能力连接到 FastMCP 与 FastAPI 落地

A2A（Agent2Agent）面向的是另一个问题：当一个 Agent 把一项可能耗时、需要补充输入、产生多个结果的任务交给另一个独立 Agent 时，双方怎样发现能力、交换消息、追踪状态、取消任务并验收产物。它不把对端的规划器、记忆、工具或提示词暴露出来，而是用协议对象定义协作边界。

版本口径。 2026-11-03 的业内完整扫描记录 A2A 官方仓库 release 为 v1.0.1，发布于 2026-05-28。该发布说明包含 HTTP binding 优先使用 application/a2a+json 等修订；当前规范目录包含 Agent Card 签名、缓存、authenticated extended card 和任务级授权作用域。2025 年 Google 发布背景和旧资料中的 /.well-known/agent.json 仅用于理解历史，不应当作当前唯一发现路径。本文以官方 v1.0.1 与目标规范为主要协议依据，但本次没有实现客户端或服务端，具体字段仍须用目标版本 Schema 和 SDK 校验。

WHY

2

1. 多 Agent 真正难的是任务边界，不是多发几条消息

3

在同一个进程里调用函数，调用方通常知道函数是否返回、异常是否抛出、结果是什么类型。跨 Agent 委派则不同：执行者可能运行很久，中途需要用户补资料或重新授权；网络断开后，调用方不知道任务是没收到、仍在执行，还是已经完成但响应丢失；结果也可能不是一段文本，而是报告、表格、文件和引用的组合。如果只把任务塞进自然语言 prompt，再用“最后回复成功”判断完成，系统很快会出现重复执行、状态丢失、越权读取和无法审计。

A2A 的价值是把这些问题拆成标准对象和抽象操作。Agent Card 回答“对方是谁、宣称能做什么、通过什么接口交互”；Message 与 Part 回答“这一轮交流传递了什么”；Task 回答“工作处于什么状态”；Artifact 回答“产出了哪些可独立验收的结果”；streaming 与 push 回答“长任务如何报告进展”；取消、错误和授权状态回答“不能继续时如何安全停下”。

这套协议不要求双方使用同一种模型或框架。一个 LangGraph Agent 可以把审查任务交给用其他框架实现的 Agent，只要双方对同一 Canonical Data Model 和抽象操作达成一致。协议绑定可以不同，但任务语义不应随 JSON、HTTP 或其他绑定随意改变。

2. A2A 不是多 Agent 框架的替代品

3

LangGraph、CrewAI、AutoGen 或其他框架解决的是内部编排：如何分解任务、维护图状态、选择下一个节点、保存检查点、组织模型循环。A2A 解决的是独立 Agent 之间的互操作边界。它不会替你做任务规划，不规定 supervisor 必须存在，不提供共识算法，也不会自动解决死锁、重复工具调用、模型幻觉或结果质量评估。

因此可以有两种合理架构：单进程内部继续用框架的状态图和 handoff，只有跨团队、跨机器或跨信任域的边界使用 A2A；或者内部框架本身把一个 Agent 包装成 A2A Server，对外仍只暴露标准任务接口。反之，给本机每个函数都架一个 A2A 服务，通常只会增加部署与排障成本。业内工程资料的共同建议是先证明单 Agent 与工具不足，再增加 Agent 和协议复杂度。

3. 发现、认证、授权、可信是四道不同门

3

Agent Card 是能力声明，不是能力证明，更不是访问授权。任何站点都可以发布一张写着“我能退款、我能审查生产配置”的卡片。即使卡片带有可验证签名，也只能帮助验证卡片来源与完整性，不能证明该 Agent 的业务结果正确，更不能证明当前调用者有权发起任意任务。

完整判断应依次回答：卡片是否来自预期发行方，接口地址是否属于预期服务，调用者身份是否认证，任务所需 scope 是否被授予，租户与资源是否匹配，具体动作是否需要人审。authenticated extended card 可以给已认证调用者展示更多能力，但公开卡与扩展卡的分层本身也不能替代服务端授权。

这一区分对产物同样重要。远端 Agent 返回的文本、结构化数据、文件链接和状态说明都是外部输入。completed 只表示对端声称任务进入完成状态，不表示业务验收通过；仍需检查 Artifact 类型、来源、内容、引用和实际副作用。

WHAT（WHYT）

2

1. 协议三层与当前 HTTP 绑定口径

3

A2A 规范可理解为三层：Canonical Data Model 定义 Task、Message、Part、Artifact 等核心语义；Abstract Operations 定义发送消息、查询任务、取消、订阅等操作；Protocol Bindings 把这些语义映射到具体传输。三层分离的意义是避免某个 SDK 的函数名或某种传输细节反过来改变任务语义。

v1.0.1 的 HTTP binding 修订优先使用 application/a2a+json。实现不能把所有响应都笼统当成 application/json，也不能把旧 JSON-RPC 教程、REST 教程和新 HTTP 绑定混成一个请求。Client 与 Server 应明确协商协议版本、绑定和媒体类型，检查 Content-Type 与 Accept，对不支持媒体类型和版本给出可诊断错误。

官方 release、规范版本、语言 SDK 包版本是三个相关但不同的坐标。部署清单要分别记录，不能只写“使用 A2A 1.0”就假设所有语言实现行为完全一致。本次未做跨 SDK 互通，字段示例均以目标规范复核为前提。

2. Agent Card：机器可读的能力入口

3

一张 Agent Card 通常描述以下信息：

  • 身份与维护信息：名称、说明、提供方、实现版本、文档入口。
  • 接口信息：服务地址、协议版本或绑定偏好，以及可能的其他接口。
  • 交互能力：是否支持 streaming、push notification、状态历史等。
  • 默认输入输出模态：文本、结构化 JSON、文件或其他媒体类型。
  • Skills：稳定标识、用途说明、典型输入输出与示例，帮助路由方判断是否匹配。
  • 安全要求：认证方案和安全引用；需要时声明是否支持认证后的扩展卡。
  • 完整性信息：需要时对卡片签名，供接收方验证来源与篡改情况。

当前发现方式不应只背一个旧路径。官方资料列出 well-known URI、企业或策展注册表、直接配置交换等策略；当前常见 well-known 路径为 /.well-known/agent-card.json。旧资料中的 /.well-known/agent.json 可作为历史兼容线索，但新实现必须以目标版本为准。企业内部往往优先使用受控注册表和显式地址，避免模型根据不可信输入任意发现并发网请求。

Card 缓存要服从目标规范和 HTTP 缓存策略，记录获取时间、来源、版本和内容哈希。卡片更新可能意味着工具或权限面扩大，不能永久沿用首次审批。签名验证应检查受信密钥或证书链、算法、签名覆盖内容和有效期，并防止把卡片里的任意密钥地址当成自动信任根。签名有效后仍需做网络出口、身份和业务授权检查。

3. Message、Part、Artifact：三种对象各管一层

3

Message 是一次协作消息，通常具有角色、消息标识以及可选的 task、context 关联。它可以表示用户补充要求，也可以表示 Agent 的解释或状态相关消息。Message 不等于整个任务，也不必然是最终交付物。

Part 是 Message 或 Artifact 的内容组成。文本 Part 适合说明，Data Part 适合结构化数据，File Part 适合文件内容或受控引用。多 Part 允许同一个结果同时带人读摘要与机读数据，但每个 Part 都应带正确媒体类型，不能把 JSON 字符串伪装成已校验对象。

Artifact 是任务产生的可交付结果，具有独立标识和若干 Part。例如“审查报告”Artifact 可以包含 Markdown 摘要、结构化问题清单和签名后的证据文件。Artifact 与 Task 状态分离：任务处于 working 时可能已经产生中间产物，任务 completed 时也可能有多个最终产物。客户端不能仅取最后一段文本就丢掉其余产物。

contextId 类关联用于把同一协作上下文中的多次交互联系起来，taskId 则定位具体工作单元。两者不能混用为全局会话，也不能跨租户猜测。Message、Task、Artifact 的 ID 都要进入去重、审计和访问控制设计。

4. Task 生命周期与状态边界

3

常见核心状态包括 submitted、working、input-required、auth-required、completed、failed、canceled、rejected；某些模型还提供 unknown 等用于无法确定状态的场景。实现时应以目标版本的 TaskState 枚举为准，不自定义同义字符串分散在代码中。

  • submitted：任务已被接收或登记，尚未进入实质执行。它不表示副作用已发生。
  • working：执行方正在处理，可伴随进度消息或中间 Artifact。
  • input-required：缺少继续所需的信息，任务暂停在等待输入的边界。补充输入必须关联原任务并重新鉴权，不能把等待状态当失败重试。
  • auth-required：需要额外认证或授权才能继续。它不是普通参数缺失，客户端不能通过反复提交同一请求绕过，也不能自行把低 scope 令牌换成高 scope。
  • completed：执行方声明完成，客户端继续验收 Artifact 与业务结果。
  • failed：执行无法完成，应保留稳定错误类别、可重试性和安全诊断。
  • canceled：取消语义已经生效；它与“客户端停止等待”不同。
  • rejected：任务在接受阶段因契约、策略或能力不匹配被拒绝，不应假装进入 working。
  • unknown：若目标绑定用于表达未知状态，客户端应进入对账流程，而不是猜测成功。

input-required 与 auth-required 是可恢复的中断边界，不是终态。completed、failed、canceled、rejected 通常按终态处理，不应为了让 UI “重新转起来”直接改回 working。业务重试可新建 attempt 或新 Task，并通过父任务、幂等键和原因关联。

5. 异步、streaming 与 push：三种等待方式

3

轮询最容易实现和排障：提交任务后按 deadline 查询，看到终态或中断状态就处理。缺点是请求多、进度不及时，必须指数退避、抖动和服务端限流，不能 tight loop。

streaming适合持续状态、消息和 Artifact 增量。客户端要处理重复事件、乱序、断流、游标恢复和最终对账。收到流不等于任务一定完成，连接正常关闭也不必然等于 completed；仍要读取最终 Task 状态。每个事件最好结合任务状态版本或事件标识去重，避免重连后重复追加 Artifact。

push notification适合调用方无法保持长连接的场景。回调配置必须绑定任务与租户，回调端点要防止 SSRF、伪造、重放和凭据泄漏。通知最好只作为“有变化”的信号，接收方再通过已认证通道拉取任务，而不是信任回调正文中的全部结果。轮换回调地址或认证配置时也要防止旧配置继续接收敏感事件。

选择可以组合：普通任务轮询，交互任务流式，超长任务 push 加查询对账。无论选哪种，都需要统一的状态持久化和幂等处理，不能让三种入口各自维护一套真相。

6. A2A 与 MCP 的分工

3
维度 A2A MCP
对端 另一个具有任务执行能力的 Agent 工具、资源或提示模板提供方
主要对象 Agent Card、Task、Message、Part、Artifact Tools、Resources、Prompts 及能力描述
时间模型 长任务、异步、中断恢复、取消 常为一次能力调用，也有自身生命周期与传输规则
发现 Agent Card 与注册、直接配置等机制 协议能力与工具、资源、Prompt 清单
内部实现 不暴露对端记忆、规划和工具细节 Server 封装业务系统，Host 控制模型可见范围

典型组合是：Agent 对外通过 A2A 接任务，对内通过 MCP 调工具。 例如审查 Agent 收到 A2A Task 后，内部用 MCP 读取代码、查询规范和生成报告，再把报告作为 A2A Artifact 返回。A2A 调用方不需要知道这些 MCP Server 的存在，也不应自动继承它们的凭据。

《一本书讲透MCP》的章节笔记把这一关系概括为工具层与 Agent 层互补。书籍能帮助建立分层心智模型，但不能替代 A2A 官方规范中的字段、状态、授权与绑定细节。

7. 取消、失败、重试与幂等必须一起设计

3

远程调用超时时，请求可能根本没到，也可能已经执行完成。直接重试有副作用的任务会造成重复付款、重复发帖或重复写入。客户端应给提交操作稳定幂等键，服务端保存“租户＋幂等键＋任务”的映射；相同键与相同载荷返回原任务，相同键但载荷不同则拒绝。

取消也应是幂等操作：重复取消同一任务返回一致的当前状态，终态任务不能被取消回退。取消被接受不等于副作用已经回滚，必要时需要补偿任务和人工核查。失败后是否重试取决于错误类别：网络暂时中断可在退避后查询或重试，契约错误与权限拒绝不应自动重试，input/auth 中断要补齐对应条件后恢复。

恢复不能仅保存最后状态字符串。至少要持久化任务 ID、上下文 ID、幂等键、状态版本、截止时间、attempt、已处理事件游标、Artifact 校验结果和外部副作用关联 ID。这样才能在进程重启后继续对账，而不是从头再跑一次。

HOW

2

1. 普通 Agent Card JSON 示例

3

下面展示常用字段子集，用于解释结构，不是声称可未经校验直接投入所有 v1.0.1 SDK。实际字段名、安全方案表达、接口声明和必填项必须用目标版本 JSON Schema 验证。

{
  "name": "policy-research-agent",
  "description": "检索经授权的制度材料并生成带引用的研究报告",
  "version": "1.0.0",
  "protocolVersion": "1.0",
  "url": "https://agents.example.com/research/a2a",
  "preferredTransport": "HTTP+JSON",
  "provider": {
    "organization": "Example Research Group",
    "url": "https://example.com"
  },
  "capabilities": {
    "streaming": true,
    "pushNotifications": true,
    "stateTransitionHistory": true
  },
  "defaultInputModes": ["text/plain", "application/json"],
  "defaultOutputModes": ["text/markdown", "application/json"],
  "securitySchemes": {
    "bearerAuth": {
      "type": "http",
      "scheme": "bearer",
      "bearerFormat": "JWT"
    }
  },
  "security": [{"bearerAuth": []}],
  "supportsAuthenticatedExtendedCard": true,
  "skills": [
    {
      "id": "policy-review",
      "name": "制度审查",
      "description": "只对调用者有权访问的制度进行差异审查",
      "tags": ["policy", "review"],
      "examples": ["比较两版报销制度并列出冲突"],
      "inputModes": ["application/json"],
      "outputModes": ["application/json", "text/markdown"]
    }
  ]
}

security 表达进入服务所需要求，不应把具体令牌、密钥或客户凭据放进卡片。Skill 的 examples 也不能包含私有数据。公开卡只放可公开信息，敏感 Skill 和内部端点通过认证扩展卡或企业注册表按权限提供。

2. Signed Agent Card 示意：不伪造真实签名

3

下列签名值是明确的占位符，不是有效 JWS，也不能通过验证。真实系统应由受控密钥和合规 JOSE 库在发布时生成，验证方按目标规范处理受保护头、签名覆盖内容与密钥链。

{
  "name": "policy-research-agent",
  "description": "签名卡片结构示意，其余业务字段应按目标 Schema 补齐",
  "version": "1.0.0",
  "protocolVersion": "1.0",
  "url": "https://agents.example.com/research/a2a",
  "signatures": [
    {
      "protected": "<base64url-jose-protected-header>",
      "signature": "<generated-by-real-signing-process>"
    }
  ]
}

禁止把随机 base64 字符串当成“测试签名”再宣称验签通过。负例测试应覆盖签名被篡改、算法不被允许、密钥来源不可信、卡片 URL 被替换和签名有效但 scope 不足。卡片签名解决的是完整性与来源问题，不解决任务授权、结果质量和业务许可。

3. 六员渐进任务 envelope：本地契约不等于官方 Task

3

在尚未跨机器部署完整 A2A 前，可以先让六员使用结构化任务信封。以下 Pydantic 模型是本地渐进契约，借用 Task、Part、Artifact 思想，不冒充官方 A2A Schema。它强调禁止未声明字段、状态版本、租户、截止时间和幂等键。

from datetime import datetime, timezone
from enum import StrEnum
from typing import Any, Literal
from uuid import UUID

from pydantic import BaseModel, ConfigDict, Field, field_validator


class TaskState(StrEnum):
    SUBMITTED = "submitted"
    WORKING = "working"
    INPUT_REQUIRED = "input-required"
    AUTH_REQUIRED = "auth-required"
    COMPLETED = "completed"
    FAILED = "failed"
    CANCELED = "canceled"
    REJECTED = "rejected"


class TaskPart(BaseModel):
    model_config = ConfigDict(extra="forbid")

    kind: Literal["text", "data", "file_ref"]
    media_type: str
    text: str | None = None
    data: dict[str, Any] | None = None
    file_ref: str | None = None


class Artifact(BaseModel):
    model_config = ConfigDict(extra="forbid")

    artifact_id: UUID
    name: str
    parts: list[TaskPart]
    sha256: str | None = Field(default=None, pattern=r"^[0-9a-f]{64}$")


class TaskEnvelope(BaseModel):
    model_config = ConfigDict(extra="forbid")

    schema_version: Literal["local-task-envelope/1"]
    task_id: UUID
    context_id: UUID
    tenant_id: str
    idempotency_key: str = Field(min_length=8, max_length=128)
    state: TaskState
    state_version: int = Field(ge=0)
    objective: str
    input_parts: list[TaskPart]
    expected_output: str
    artifacts: list[Artifact] = []
    deadline_at: datetime
    attempt: int = Field(default=0, ge=0)
    trace_id: str

    @field_validator("deadline_at")
    @classmethod
    def require_utc(cls, value: datetime) -> datetime:
        # 禁止朴素时间，避免跨机器时区歧义
        if value.tzinfo is None or value.utcoffset() is None:
            raise ValueError("deadline_at 必须带时区")
        return value.astimezone(timezone.utc)

生产代码还应给 TaskPart 增加“恰好一种内容字段非空”的校验，为 data 指定各 Skill 的 JSON Schema，并把 file_ref 限制为受控存储句柄而非任意 URL。默认列表在 Pydantic v2 会安全复制，但若追求更清晰可写成 Field(default_factory=list)。

4. 保守状态机合法迁移表

3

下表是应用侧建议的保守子集，用来阻止明显倒退；若目标规范对某个事件有更严格条件，应以规范为准。迁移由服务端验证，客户端不能只改本地字符串。

当前状态 允许的目标状态 触发与约束
submitted working 契约、能力和初始授权检查通过，开始执行
submitted rejected 请求不合法、能力不匹配或策略拒绝
submitted canceled 尚未执行或执行方可安全取消
submitted failed 接收后发生不可恢复的内部失败
working working 仅进度更新，state_version 单调增加
working input-required 缺少必要业务输入，保存等待原因
working auth-required 需要额外授权，不执行越权降级
working completed 所需 Artifact 与状态说明已持久化
working failed 不可恢复失败，记录可重试性
working canceled 取消生效并记录未完成副作用
input-required working 收到关联原任务的合法补充输入并重新授权
input-required canceled / failed 等待期间取消或发生不可恢复失败
auth-required working 完成所需授权流程，服务端重新检查 scope
auth-required canceled / failed 放弃授权、授权失败或任务终止
completed / failed / canceled / rejected 无 终态不可倒退；新工作创建新 attempt 或 Task

所有迁移都应比较并递增 state_version，使用数据库条件更新防止两个 Worker 同时把同一任务写成不同终态。状态、事件与 Artifact 写入要尽量处于同一事务或可恢复日志中，避免“状态已完成但产物丢失”。

5. 客户端轮询与流式伪代码

import asyncio
import random

TERMINAL = {"completed", "failed", "canceled", "rejected"}


async def wait_task(client, task_id: str, deadline_s: float = 60.0):
    delay = 0.5
    async with asyncio.timeout(deadline_s):
        while True:
            task = await client.get_task(task_id)  # 每次携带调用者与租户上下文

            if task.state in TERMINAL:
                return task
            if task.state == "input-required":
                # 交给上层收集输入；不要盲目重复提交
                return task
            if task.state == "auth-required":
                # 交给授权流程；不在循环中自动扩权
                return task

            await asyncio.sleep(delay + random.uniform(0, delay * 0.2))
            delay = min(delay * 2, 8.0)


async def consume_stream(client, task_id: str, cursor: str | None):
    seen_events = set()
    async for event in client.stream_task(task_id, cursor=cursor):
        if event.event_id in seen_events:
            continue  # 重连后的重复事件不重复应用
        seen_events.add(event.event_id)
        await apply_event_atomically(event)       # 同事务保存事件与游标
        cursor = event.event_id
        if event.is_final:
            break

    # 流结束后再对账，连接关闭不等于任务完成
    return await client.get_task(task_id)

真实客户端需要持久化 seen_events 或使用事件游标，而不是只用内存集合；服务端也可以只保证有限重放窗口，所以游标失效时要全量拉取 Task 与 Artifact。asyncio.timeout 只停止本地等待，接下来是否取消远端任务要按业务语义显式决定。

6. 超时、取消与恢复流程

3

一个安全流程是：提交前生成幂等键并设置总 deadline；超时后先查询一次任务，不立刻重试提交；若业务要求停止，则发送取消；随后持续查询直到 canceled 或确认已进入其他终态；若外部写入结果不明，进入人工或自动对账，不宣称“已回滚”。

恢复时先读取持久任务，不重新生成任务 ID。working 任务从最近检查点继续，input-required 等合法输入，auth-required 等重新授权，流式任务从持久游标重连，completed 任务只补做 Artifact 验收。恢复逻辑必须识别已经执行的副作用，不能因进程重启重复发送邮件或创建工单。

重试使用指数退避与抖动，区分连接超时、限流、服务暂不可用、永久契约错误和授权拒绝。对不幂等操作，优先“查询原任务”而不是“再次提交”。熔断与并发隔舱用于防止一个远端 Agent 失效拖垮全部调用者。

7. Artifact 校验：完成状态之后还有一道验收

3 
import hashlib
from pathlib import PurePath

ALLOWED_MEDIA = {"application/json", "text/markdown", "text/plain"}


def validate_file_artifact(
    *, filename: str, media_type: str, content: bytes,
    expected_sha256: str, max_bytes: int = 2_000_000,
) -> None:
    if media_type not in ALLOWED_MEDIA:
        raise ValueError("不允许的产物媒体类型")
    if len(content) > max_bytes:
        raise ValueError("产物超过大小限制")

    path = PurePath(filename)
    if path.is_absolute() or ".." in path.parts or path.name != filename:
        raise ValueError("非法产物文件名")

    actual = hashlib.sha256(content).hexdigest()
    if actual != expected_sha256:
        raise ValueError("产物摘要不匹配")


def validate_artifact(
    artifact, *, task, skill_id: str, tenant_id: str, schema_registry,
) -> None:
    # Skill 与租户来自已认证任务上下文，不伪造为 Artifact 的标准字段
    if tenant_id != task.tenant_id:
        raise ValueError("租户上下文不匹配")
    if artifact.artifact_id not in {item.artifact_id for item in task.artifacts}:
        raise ValueError("Artifact 不属于当前 Task")

    # Artifact 内每个 Part 独立校验，不能因一个是文本就跳过其余数据
    for part in artifact.parts:
        if part.kind == "data":
            schema = schema_registry.for_skill(skill_id, part.media_type)
            schema.validate(part.data)
        elif part.kind == "file_ref":
            # 不自动抓取任意 URL，只允许受控存储引用并检查租户归属
            validate_controlled_reference(part.file_ref, tenant_id)

还应验证 Artifact 是否属于当前 Task、是否满足 expected output、引用是否真实支持结论、生成者与时间是否可追踪。Markdown 中的链接、图片和 HTML 按不可信内容渲染，防止脚本与跟踪外链。结构化结果 Schema 合法也只表示形状正确，关键结论仍需业务规则、第二数据源或独立审查。

8. 本批论文怎么用：把删除与撤回扩展到派生产物

3

arXiv:2610.31366 的 AfterDeleteBench 说明：删除原始记忆记录，并不必然删除由它派生的摘要和状态；即使完整秘密字符串已不存在，分散保存的组件在公开组合规则下仍可能被重建。论文还区分了重建、重新写回和新会话召回，并用带 provenance 的闭包消除了其测试正基线中的恢复现象。该实验针对固定权重 Agent 与合成秘密，不是 A2A 协议测试，但直接暴露跨 Agent Artifact 的治理盲点。

我们怎么用：在本地 envelope 与 Artifact 元数据中保存 derived_from、来源任务、租户和保留策略，形成“原始输入→摘要/记忆→A2A Artifact→下游副本”的派生闭包；删除或撤回时沿闭包传播 tombstone，并阻止下游继续把已撤回内容写回。验收不能只查源表记录消失，还要在全新会话中询问、要求组合碎片、检查已有 Artifact 和重新写回路径，期望行为均为不可恢复或明确拒绝。completed 不代表删除完成，canceled 也不等于 Artifact 已擦除；这些属于应用层数据治理，不能冒充 A2A 标准自动提供的能力。

9. 版本、媒体类型、多租户与鉴权检查清单

3

版本与互通

  • 分别锁定 A2A 规范、官方 release、语言 SDK 和模型 Schema 版本，保存兼容矩阵。
  • v1.0.1 HTTP binding 优先核对 application/a2a+json，同时验证 Content-Type、Accept、错误媒体类型和不支持版本响应。
  • 不把旧 /.well-known/agent.json 当当前唯一入口；按目标规范使用 agent-card.json、注册表或直接配置。
  • 用至少两个独立实现做发现、提交、查询、流式、取消、授权中断和 Artifact 互通，不能只测同源 SDK。

多租户与授权

  • 每次 submit、get、cancel、stream、push 配置和 Artifact 下载都检查调用者、租户和任务归属，不能只校验 task ID 是否存在。
  • 使用任务级授权作用域，按 Skill 和动作授予最小 scope；校验发行方、受众、过期、签名和授权上下文，禁止跨服务透传令牌。
  • authenticated extended card 在认证与授权后生成，响应不缓存到公开层；公开卡与扩展卡不得泄露其他租户能力。
  • Agent Card 声明和签名不等于业务授权；高风险任务仍需策略检查、人审与审计。
  • push 回调验证来源、任务关联、时间窗与重放标识，限制回调目标网络范围；通知正文尽量不携带敏感全量产物。

缓存与供应链

  • 缓存 Card 时记录来源、版本、哈希和重新验证时间，遵循目标缓存规则；签名或接口变化触发重新信任评估。
  • 注册表条目与真实部署状态同步，Skill 下线后不能继续路由；能力描述变化要可审计。
  • 对端实现升级前跑契约、负例、取消和恢复测试；发现服务地址不可信时禁止自动跟随重定向到内网或其他租户。

10. 六员体系的渐进落地顺序

3

第一阶段不急着让所有角色变成远程 A2A Server。先为 Hermes、DSH、Claude Code、Codex、OpenClaw、QwenCode 编写各自的 agent_card.md，说明能力边界、输入契约、输出契约、典型任务、权限限制和不能承担的工作。路由按能力选择，而不是只记角色名。

第二阶段统一 task envelope，把任务 ID、上下文、状态、状态版本、输入 Parts、期望输出、Artifacts、截止时间、租户和幂等键结构化。Hermes 的派单、OpenClaw 的审查结果、Claude Code 的工程产物都走同一状态语义；本机 CLI 和文件仍可作为传输，避免为了协议增加无收益网络跳数。

第三阶段补持久化状态机、事件日志、超时取消和 Artifact 校验，让本机协作先具备可恢复与可验收能力。第四阶段只有出现真实跨机器、跨团队或跨信任域需求时，再选择官方 SDK 实现完整 A2A，并做双实现互通和安全测试。这样既保留协议思维，也避免把六员协作一次性重写为难以运维的分布式系统。
