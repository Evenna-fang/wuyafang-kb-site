L5 Agent 工程 · 最佳答案

← 返回总入口

WHY：这个能力域为什么重要

2

Agent 是 FDE 交付的进阶能力——从"问答系统"到"自主工作流"。Anthropic 的前置原则：「找最简单的可行方案，只有在需要时才增加复杂度」——能用工作流（固定路径）就别上 agent（动态路径）。Agent 的本质就是「LLM 在循环里根据环境反馈调工具」。7 本书交叉验证：Agent 不是"通用智能助手"，而是"某个具体痛点的数字员工"——一个明确的重复劳动 + 一个可验证的输出 + 一个能被工具化的数据源。

WHAT：这个节点到底是什么

2

Agent 定义与四大关键能力

3

规划（Planning）/ 记忆（Memory）/ 工具调用（Tool Use）/ 多智能体协作（Multi-Agent）。三本书共同警告：追求"通用 Agent" = 什么都干不好；所有成功案例都是单痛点。

三种 Agent 循环（按任务复杂度分层）

3
循环 节奏 适合 不适合
ReAct 观察→思考→行动→再观察 步骤 ≤ 5、路径不明确 长任务（必须设 max_iterations，一般 10–20 步）
Plan-and-Execute 先拆 N 步计划再逐步执行 任务清晰、步骤 ≥ 5（库存调度/标书阅读） 路径高度不确定（计划做了也白做）
Reflection 产出→自我批判→修订 高质量要求（代码/文案/法律） 低成本高并发（反思贵，token 翻倍）

判断口诀：默认先上 ReAct，跑偏了加 Planner，产出不满意加 Reflection。三层可叠加——Plan-and-Execute 每步内部是 ReAct，最终产出再过 Reflection。

框架选型（2026）

3

没有单一赢家，按负载选。

场景 选
显式状态机、断点续跑、HITL 人审、长任务 LangGraph（checkpointer + interrupt() 一等公民）
快速搭多角色协作原型、周五演示 CrewAI（role/backstory + sequential/hierarchical process）
Claude 为主、工具密集、开箱工具/权限/子代理 Claude Agent SDK（spawn Claude Code CLI 子进程，约 1 GiB RAM/agent）
OpenAI 生态、最短上手 OpenAI Agents SDK（四原语：Agents/Handoffs/Guardrails/Sessions）
纯 TypeScript 聊天/流式/轻 agent Vercel AI SDK

Anthropic 工具设计原则（不论选哪个框架都适用）：
1. 简单优先——工具文档和测试花的功夫应超过花在 prompt 上的
2. token 预算——58 个工具约 55K token 起步；优化前工具定义能吃掉 134K token。对策：defer_loading / Tool Search，按需加载，延迟加载的工具不进初始 prompt，不破坏 prompt caching
3. 响应截断——Claude Code 默认把工具响应限制在 25,000 token
4. 抽象层级越高，细粒度控制越贵——选框架前先确认"你要调的那个参数在它那层暴露了吗"

LangGraph 两个持久化原语：Checkpointer（图状态快照，单线程，短期记忆）+ Store（应用自定义 KV，跨线程，长期记忆）。

Coze / Dify / LangChain 边界（阶梯不是并列）

3
  • Coze（零代码，字节云）：周五给老板演示 Bot、发票识别、文案仿写。不能做：私有化、深度定制、长任务状态机
  • Dify（开源可私有化）：企业内网 RAG、知识问答、数据不出内网。不能做：复杂多 Agent、精细状态图控制
  • LangChain/LangGraph（代码框架）：生产级、断点续跑、多 Agent、和业务系统深度耦合。不能做：非工程师快速搭原型

判断口诀：Coze 验证想法（1 天）→ Dify 落企业（1 周）→ LangGraph 生产（1 个月+）。错配是最大浪费。

工具层：Function Calling vs MCP vs 自定义工具

3

三者不在同一层，是叠加关系，不是三选一。

层 解决 典型
Function Calling 模型怎么决定调哪个函数 prompt 塞 JSON schema，模型输出 {"name","arguments"}
MCP 工具怎么被标准化发现/授权/复用 工具 server 暴露 tools/list、tools/call，客户端即插即用
自定义工具 业务函数怎么写 Python 函数 + docstring + 装饰器

MCP 解决 N×M 集成爆炸：5 个应用接 5 个工具 = 25 份定制代码 → MCP 降到 N+M。三类原语：Resources（只读）/ Tools（有副作用）/ Prompts（模板）。安全红线：OAuth 内建、高风险操作人审弹窗、工具描述必须标注"只读 vs 会改状态"、pin 版本不用 latest、每 agent 活跃 MCP ≤ 6 个。

MCP vs A2A：MCP 解决"Agent ↔ 工具"（手），A2A 解决"Agent ↔ Agent"（嘴）。互补不竞争。A2A 核心是 Agent Card + Task Lifecycle（submitted→working→input-required→completed）。

记忆双进程范式（System-1 / System-2）

3

模仿人类快思考/慢思考：System-1 轻量快检索/快路由（90% 查询直接出），System-2 重读原始历史/慢推理（10% 复杂查询），中间用低开销门控决定"这次要不要慢下来"。 D-Mem 实测 35.8% token 拿 96.7% 上限效果。

反例：每轮全量历史塞上下文（纯 System-2，token 爆炸）；只用向量召回从不重读原文（纯 System-1，复杂问题答不准）；门控用 LLM 做自然语言判定（门控本身比省的还贵）。

G-Memory 三层图记忆（多 Agent 共享）

3
层 存什么 谁用 成本
Insight Graph 泛化经验/教训/模式（"flaky 测试不要盲目重跑"） 编排层复用 最低
Query Graph 任务指纹→派谁→结果 编排层派单时查 中
Interaction Graph 完整交互原始记录/diff 工程层 debug 多跳追溯 最高

多视图并行检索：semantic / temporal / causal / entity 四种边同时召回。

单 Agent vs 多 Agent

3

多 Agent 不是更高级，是更贵（2–5 倍 token）、更慢（3–10 倍延迟）、更难调试。 只有 4 个信号才拆：
1. prompt 已经装不下（30 个工具描述 + 5 套业务规则 + 2 个人格）
2. 工具选错率高（同一个 Agent 既查 DB 又发邮件又写代码）
3. 需要"对抗"或"批判"（写代码的 Agent 不该自己审自己——Reflection 必须独立 Critic）
4. 任务天然分阶段（调研→设计→执行→验收）

默认结论：先上单 Agent（ReAct 或 Plan-and-Execute），跑一周遇到真实瓶颈再拆。简单任务拆多 Agent 是 N 倍 API 成本换不来收益。

HOW：怎么落地

2

落地 5 步通用流程（跨 7 本书提炼）

3
  1. 找痛点：挑"每周重复 ≥ 3 次、单次 ≥ 30 分钟、出错代价高"的活
  2. 定输入输出：输入格式（PDF/Excel/聊天记录）、输出格式（结构化 JSON / 卡片 / 邮件）
  3. 选工具：哪些 RAG（查知识库）、哪些 FC（调 API）、哪些代码执行（Python 算）
  4. 搭循环：简单用 ReAct，复杂用 Plan-and-Execute，要质量加 Reflection
  5. 接日志和回调：每次用户提问、链的运行状态、模型输出都记录到日志——这一步是从 demo 到生产的分水岭

生产化必备 4 件事

3
  1. 错误处理 & 重试：每个工具调用包 try/except；设 max_iterations 硬上限；高风险操作（写库/发邮件/删文件）必须人工确认（MCP 原生支持弹窗）
  2. 观测 & 日志：最少记——完整 prompt、每步工具调用（名/参/返回/耗时）、最终输出 + 用户反馈、异常堆栈
  3. 安全 & 权限：OAuth 授权、令牌传递、高风险操作确认弹窗、工具描述标注影响等级、API key 用环境变量不写进 prompt
  4. 状态检查点：每完成一步落盘当前状态（已完成步骤/中间结果/下一步计划），崩溃后从最近检查点恢复。长任务（>30 步）必须有这个

常见生产化坑：不设超时（LLM 挂死整个 Agent 跟着挂）、不设速率限制（API 限流被封）、把 API key 写进 prompt、多 Agent 之间没有共享状态、不做评估（只看"能不能跑"不看"跑对了多少"）。

多智能体协作编排模式（六员实测）

3

默认骨架：orchestrator-worker + 步骤间自动校验 + 独立 LLM 评审层（OpenClaw）+ 确定性终门。

模式 流程 适用
Pipeline Hermes→DSH执行→OC审 线性流水线、需要逐步校验
Fan-out（并行） 同一题派多个 worker 并行 可并行拆解、上下文装不下
Debate（辩论） Claude+Codex 独立作答→OC 对比归并 选型/架构/排障方向等高风险决策

四条落地教训（arXiv 12 篇核心论文对照）：
1. 通信结构化：派单 context 用 JSON 契约（需求/输入/输出格式/验收），不写散文——消息体曾占 token 预算 40–60%，结构化后 3.2× 压缩不掉点
2. 先试单 Agent 再拆：派单前先问"单 Agent 能不能干"
3. 失败先归因再反思：先定位 decisive error 是哪一步向下游传的错，只让那个反思（pre-hoc 上游筛查比事后救火便宜 65×）
4. 共享记忆来源 gating：RAG 无差别照收会让假信念被下游 97–99% 采信，进库要过来源门

我们库当前的落地点

2

六员协作体系（Hermes/DSH/Claude Code/Codex/OpenClaw/QwenCode）本质是「不选框架的路线」：用进程级 agent + 派单协议替代图编排——与 Anthropic「最简单方案优先」原则一致。已有 MCP 落地：codebase-memory（158 语言代码图）、GitHub MCP、Docker MCP。记忆双进程范式已建 wiki + Quality Gating τ=0.5 起步。error-ledger 技能已具备错误记录，但自动应用已验证修复方案的闭环还没做。

循环形态：Hermes 主对话 = ReAct + 软 Reflection（self-verification-blindspots 技能）；Claude Code = Plan + ReAct 执行 + Reflection（跑测试自验）；OpenClaw = ReAct 为主。

待落地：Playwright/Tavily/Context7 三个 MCP（P0）；A2A 思维借用（agent_card.md + task envelope JSON）；G-Memory 三层图升级 error-ledger；PRIME 慢思考升级触发器；六员统一"高风险操作确认"机制。

本库真实落地（源码核对，2026-11-04）

  • 单 Agent 主链路 + 业务级循环上限（rag/agentic_query.py，grep 可验）：
    python DEFAULT_MAX_REWRITES = 3 ROUTE = "complex_reasoning" def route_after_grade(state: AgenticState) -> str: if state.get("relevant_docs"): return "generate" if state.get("rewrite_count", 0) < state.get("max_rewrites", DEFAULT_MAX_REWRITES): return "rewrite" _log(f"已改写 {state.get('rewrite_count', 0)} 次仍无相关片段, 拒答") return "refuse"
    循环上限写在业务状态里（max_rewrites 可被 CLI --max-rewrites 覆盖），不靠框架保护。这正是"先上单 Agent、跑一周遇真瓶颈再拆"的可执行形态。
  • 工具失败不炸链（rag/query.py::rerank L890）+ 配额耗尽进程内切换（rag/agentic_query.py::chat）：rerank 超时/异常返回 None（熔断）而非抛异常，由 rerank_node 决定降级；生成端点 429 时 chat() 切到 FALLBACK_GENERATION 重试一次。工具层统一"返回可解释的空值/降级结果"，上层据此决策。
  • 状态检查点（/home/wuyafang/.hermes/scripts/handoff_state.py）：HANDOFF.md 六段式含 Still unverified 段，把不确定性显式化，长任务靠它恢复，而不是靠"再问一遍模型记得啥"。
  • 和课件讲法的差异：课件 L5-Agent工程-最佳答案 里的 ReAct / Plan-and-Execute 都是单次任务内的推理循环；本库把"计划"外置到 raw/_task_orders/总地图.md + 派单卡，Agent 只负责单步执行。原因是这些 Agent 多为短命 CLI 调用，推理循环越长越容易中途丢上下文——外置计划 = 可审计、可换执行者重跑。
