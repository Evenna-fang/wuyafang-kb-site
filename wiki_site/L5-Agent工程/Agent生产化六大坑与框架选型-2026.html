Agent 生产化六大坑与框架选型（2026）

WHY

2026 年多 Agent 框架已经从"demo 能跑"进入"生产可审计"阶段。LangChain 官方报告指出 >60% 生产 agent 事故源于状态管理。本页从 LangGraph / CrewAI / AutoGen 三大框架的一手文档 + 生产案例中，提炼出选型决策树 + 生产红线 + 真实成本基线。

WHAT

一、2026 年框架格局

框架 定位 生产用户
LangGraph 状态机式编排，支持循环、断点、回放 Anthropic、Replit、LinkedIn、Uber
CrewAI 角色/任务式编排，门槛最低、社区增速最快 GitHub stars 2026.02 的 44k → 2026.08 的 57k
AutoGen → Microsoft Agent Framework (MAF) 2025.10 宣布与 Semantic Kernel 合并，1.0 GA 2026-04-02 微软生态

二、生产级 Agent 六大坑（getting-started 文档不会告诉你）

坑 1：工具选择不可靠

  • 症状：工具调用随机失败、超时、返回脏数据。
  • 解法：工具调用必须有 retry / timeout / fallback 节点，try/except 路由到 fallback，而非让 graph 崩溃。

坑 2：记忆爆炸 / 状态丢失

  • 症状：长任务跑着跑着忘了前面说过什么，或 agent 崩溃后状态全丢。
  • 解法：必须配 checkpointer（Postgres / SQLite / LangGraph Platform 托管 PG），agent 崩溃、resume、rewind 都基于 checkpoint。这是头号事故源。

坑 3：上下文窗口溢出

  • 症状：多轮对话后 context 爆了，模型开始"失忆"或行为漂移。
  • 解法：结构化输出强制 schema（Pydantic 模型），把不需要的上下文从对话历史里裁掉，只留摘要 + 关键状态。

坑 4：幻觉与输出不可信

  • 症状：agent 编一个不存在的工具返回值，下游 pipeline 直接炸。
  • 解法：不打 schema 就把 agent 输出给下游 = 生产事故。必须强制结构化输出 + 校验。

坑 5：eval 缺失

  • 症状：改了 prompt 不知道变好还是变坏，靠人肉试。
  • 解法：必须配 observability（LangSmith 或 OpenTelemetry）+ 离线 golden set + 在线 rollout + LLM-as-judge 三步 eval。

坑 6：成本失控

  • 症状：跑一天烧几十刀，不知道钱花在哪。
  • 解法：每个任务路径埋 cost 日志，按 run 统计 token 消耗；参考真实成本基线（见下）。

三、选型决策树

已经在 Azure / .NET 生态？
  → 是：MAF（Microsoft Agent Framework）
角色分工清晰、低门槛 PoC？
  → 是：CrewAI（Flows + 结构化输出）
复杂状态 / 需要 HITL 断点 / 可回放？
  → 是：LangGraph（默认推荐）

HOW（生产红线清单）

必须做的

  • ✅ 配 checkpointer（否则 state 丢失是头号事故）
  • ✅ 工具调用有 retry / timeout / fallback
  • ✅ 接 observability（LangSmith 或 OpenTelemetry）
  • ✅ 强制结构化输出（Pydantic schema）

绝对不能做的

  • ❌ 用裸 ReAct loop（无 state 持久化）
  • ❌ 让 agent 无限制循环（必须设 max_iterations）
  • ❌ 不打 schema 就把 agent 输出给下游

LangGraph 核心生产要素

  1. 状态机模型：每个节点是函数，边是控制流；State 是带 reducer 的 typed dict；支持环（cycles）—— agent 可以"重试、反思、再调用"，这是它与 DAG 框架的根本差异。
  2. 可观测调试：LangGraph Studio（2026 GA），可视化渲染 graph、逐步调试节点、任意 checkpoint 回放——被比作"agent 界的 Chrome DevTools"。
  3. 生产部署：通过 LangGraph Platform（自托管/云托管）暴露 REST API。
