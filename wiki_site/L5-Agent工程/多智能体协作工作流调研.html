核心结论

多智能体不是默认更优解，而是"用 token 换能力"的权衡：Anthropic 官方口径下多 agent 约烧 15× chat token（单 agent 约 4×），且 token 用量单独解释 BrowseComp 80% 的方差——"多 agent 的魔法很大程度是花更多算力"。协作成立有硬前提：任务真可并行、无共享上下文强依赖、无写冲突；Cognition《Don't Build Multi-Agents》更进一步主张共享完整 agent trace、写操作单线程。生产主流骨架是 orchestrator-worker（Anthropic：lead agent 拆解 → 并行 spawn 3–5 个子 agent，内部评测比单 Opus 4 高 90.2%），另有顺序流水线、并行 fan-out、handoff、辩论等形态，各有边界。失败模式高度集中在少数几类（MAST 论文 arXiv:2503.13657，1642 条 trace：系统设计缺陷 44.2%、agent 间错位 32.3%、任务验证 23.5%），所以最值钱的不是换架构，而是拆卡前先判可并行性、通信结构化、失败先归因再反思。

关键细节

协作范式与适用边界

范式 代表 成立条件 代价
orchestrator-worker（星型/中心编排） Anthropic Research：lead=Opus 4 → 3–5 个 Sonnet 4 子 agent（独立 context）+ CitationAgent 二遍引用 任务可 breadth-first 并行、子任务独立 15× token；同步 fan-out 是信息流瓶颈（lead 不能中途纠偏）
sequential pipeline 质量门之间串行 + 分工明确 clear sequential dependencies 单点慢即全线慢
parallel fan-out 同题多 worker 并行 上下文装不下、无写冲突 易重复劳动（Anthropic 曾对简单 query spawn 50 个子 agent）
handoff 分歧升用户 需要人接手的边界 交接信息易丢失
debate（辩论） Claude+Codex 独立作答 → 归并 高风险决策 过度协商反模式：辩论实验里 correct→incorrect 翻转数在所有配置下压过反向

反方权威：Cognition 主张默认排除多 agent——① 要共享完整 agent trace 而非零散消息；② 动作携带隐式决策，冲突决策产生坏结果（两个子 agent 各自定视觉风格，产物互相打架）。RefactorPlatform（arXiv:2609.04898）实测佐证：仓库级重构"瘦检索单 agent"达 86%，"子 agent 委派"只有 66%——多派一层子 agent 反而把任务做坏。

常见坑与规避（实证）

问题 实证 规避
通信开销 / 上下文损耗 自然语言消息占 40–60% token 预算（Routed Graph Handoff, 2608.25277）；强制英文中转掉点（西语 13pp、印地语 30.6pp） typed JSON / schema 传状态；155-token 轻量 router 做图/NL 自适应切换（3.2× 压缩不掉点）；消息带来源指针
死循环 / 重复劳动 / 平台期 AgentWorld(2609.31590) 50+ 轮、3–20 角色最好仅 52% 成功率；Agensh(2609.26781) 中心编排者即容量瓶颈 任务先试单 agent 再拆；贡献度归因（DAG-Shapley 把 LLM 调用降 80%）；隔离 lazy agent；异步共享工作区
单点 / 级联故障 Proxifield(2609.20889)：星型只保 38.8% 奖励，语义路由去中心化保 73.6% 去中心拓扑；pre-hoc 风险推断（HalluProp AUROC 84.6%，比事后快 65×）；故障隔离 + 局部回滚（BRA-Audit）
责任边界模糊 / 踢皮球 DoCtOR(2608.28264)：全员反思是反模式，先归因 decisive error agent 再只让它反思，提升 22–27% 角色契约显式化；先归因再反思；责任血缘图落盘
评估困难 SCHEMA(2608.00711)：最终答案准确率与轨迹诚实度脱钩，蒙对≠推理对 加过程级指标（CCE 因果贡献度、轨迹诚实度）；长程+异步+黑盒评测
幻觉传递 CPB(2609.30813)：一条假信念进共享记忆后，下游在 0.97–0.99 的探测里当它为真 不确定性随消息传递（logprob/语义熵）；共享记忆按来源 gating；对抗性 critic
成本失控 BRA-Audit 预算感知调度后端到端 token 降 17.2–40.6%；Cost-Aware HMAS 平均分析成本降 43.97% 自适应分层；审计按预算贪心投放；中间输出复用；先算委派的账

链式可靠性是底层数学：95% 单步 × 10 步 = 59.9%，× 20 步 ≈ 36%——长链必腐，每加一个 agent 就多一次上下文掉落的交接。

A2A 协议（Agent2Agent）

Google 2025-04 发布，基于 HTTP(S) + JSON-RPC 2.0 + SSE。三件核心：

  • Agent Card：每个 agent 在 /.well-known/agent.json 声明身份、能力（skills）、支持的模态、认证要求，供其他 agent 发现。
  • Task Lifecycle：标准任务状态机 submitted → working → input-required → completed/failed/canceled，支持长时任务与异步推送。
  • Rich Artifacts：结果可为文本、文件、结构化 JSON，甚至中途动态协商模态；client/server 对称，只暴露能力边界、不暴露内部 memory/tools。

MCP vs A2A：MCP 解决 agent ↔ 工具（结构化同步调用、list_tools 发现），A2A 解决 agent ↔ agent（对话式可异步、Agent Card 发现、完整任务生命周期）。两者互补不互斥。

落地口径：六员都在本机，短期不上 JSON-RPC server（CLI 开销更小），只借它的两个产物——① 每个 agent 写 agent_card.md（能力边界/输入契约/输出契约/典型任务）；② 派单走 task envelope（{task_id, status, input, artifacts} 落盘，而非散在 prompt 里）。长期要跨机器协作（如云端 OpenClaw）再上真协议。

Agent 知识链路七层（输入 → 采集 → 提炼 → 分流 → 检索 → 应用 → 回流）

层 职责
1 输入 Intake 用户 query / arXiv 订阅 / GitHub watch / 会话轨迹 / 手工笔记
2 采集 Collection 从输入源抓全文，raw/ 冻结快照
3 提炼 Distillation raw 长文 → 3–5 行核心 + 对我们的价值，写进 wiki/
4 分流 Routing/Tagging 按 source_tier / 主题 / Owner 归档
5 检索 Retrieval ChromaDB + bge-m3 dense+sparse，top-k 召回
6 应用 Application 召回 chunk 拼进 prompt 当上下文
7 回流 Feedback Loop 记录哪些 chunk 被采纳/忽略，反馈回提炼层

落地清单（可直接抄）

  1. 拆卡前三问：子任务真独立？只读/无写冲突？价值配得上 fan-out 放大？任一不满足就走单 agent 串行。
  2. 委派契约四字段：objective / 输出格式 / 工具与来源指引 / 任务边界——只分任务不"教"委派，子 agent 会重复劳动、留空隙、误读任务。
  3. 并行卡声明工作域（负责的文件/目录/检索关键词），互斥才并行，重叠即串行或合并卡。
  4. 派单前先对单 agent 基线算账（RefactorPlatform 教训：委派可能同时更贵更差）。
  5. 回传契约 schema 化：交付了什么 / 证据路径 / 关键取舍 / 未解决不确定性 / 被拒动作，防多级转述信息衰减。
