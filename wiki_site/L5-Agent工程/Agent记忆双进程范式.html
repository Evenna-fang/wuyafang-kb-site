Agent 记忆双进程范式 (System-1 / System-2)

← 返回总入口 相关：Agent框架选型 · Agent框架进展 · 多智能体协作 · G-Memory共享记忆 · 记忆保鲜与冲突治理

来源: 从 raw/Agent记忆论文-JevMem-GMem-BudgetMem-DMem-20260928.md 提炼 关联论文: Jev-Mem(arXiv:2609.23986) / D-Mem(arXiv:2603.18631) / PRIME(arXiv:2509.22315, 待精读) 入库: 2026-09-28

范式一句话

模仿人类快思考/慢思考双系统, 把记忆和推理里的高频决策拆成两层: System-1 轻量快检索/快路由, System-2 重读原始历史/慢推理, 中间用一个低开销的门控器决定"这次要不要慢下来"。

三个论文都在讲同一件事

论文 System-1 是什么 System-2 是什么 门控在哪
Jev-Mem (写入+查询) 小分类器/规则做类型判定、图视图路由、候选打分、自适应停止 LLM 做最后答案合成 System-One 控制面输出 typed 概率, 不生成自然语言
D-Mem (查询期) 向量近邻检索 (embedding top-k) 出摘要事实 从原始会话/事件历史 reraw 片段重读 Quality Gating: 置信度+证据稀疏度+查询复杂度 → 升级概率
PRIME (推理期, 待精读) 快推理 Agent 日常走 慢思考 Agent 自省触发 自省信号(推理步数/矛盾数/假设空间)

为什么这个范式对 Agent 重要

  • 成本: 90% 的查询/决策不需要翻原始历史或走重推理, 硬塞进去只是烧 token。D-Mem 实测 35.8% token 拿 96.7% 上限效果。
  • 质量: 但有 10% 的复杂查询(时序/因果/矛盾/多跳)必须慢下来, 否则向量召回会"像但不是"。
  • 门控是关键: 不是简单分档, 而是动态判定"这次该不该升级"。门控本身必须极轻(不调 LLM), 否则省下来的 token 又被门控吃掉。

六员落地映射

层 对应六员现状 升级方向
System-1 快 fact_store.search / holographic 三层检索 / shared-skills grep 已经是, 不用重建
System-2 慢 翻 state.db 会话历史 / OpenClaw 深度审查 / Claude 多跳 debug 缺自动触发, 现在靠人拍脑袋
门控 无 G-DMem1 (质量门控脚本, τ=0.5 起步) + G-PRIME1 (自省触发信号)

反例 (不要这么做)

  • ❌ 每轮都把全量会话历史塞进上下文 = 没有 System-1, 纯 System-2, token 爆炸
  • ❌ 只用向量召回, 从不重读原文 = 纯 System-1, 复杂问题答不准
  • ❌ 门控用 LLM 做自然语言判定 = 门控本身比省下来的还贵
