LangBot：IM 入口候选备忘（2026-10-22 · 暂不部署）

← 返回总入口 相关：MCP到底解决什么问题 · Coze-Dify-LangChain边界在哪 · Dify 部署与 RAG 集成

用户定位（原话）："可以调换下用法放进 RAG 有需要再启动"——作为知识库 IM 化的候选入口，暂不部署，触发条件满足再启动。

是什么

开源生产级 IM 机器人平台（GitHub: langbot-app/LangBot，2022 年创建，214 个 release）。一套代码接 10+ 聊天平台，把 LLM 变成聊天机器人/Agent。

  • 支持平台：QQ（个人号+官方）、微信（个人+公众号）、企业微信、飞书、钉钉、Discord、Telegram、Slack、LINE、KOOK、Matrix、Satori、Email。
  • 支持模型后端：LiteLLM 统一请求层 → OpenAI/Anthropic/DeepSeek/Gemini/xAI/Moonshot/智谱/Ollama/LM Studio + 硅基流动/百炼/火山方舟/魔搭/302.AI 等网关。现有 provider 全部可接。

核心能力（按对本项目的相关度排）

能力 说明 对本项目相关度
内置 RAG 默认 Chroma 向量库 + Rerank 精排，可插拔外部知识库（RAGFlow/Dify/FastGPT） ⭐⭐⭐ 与本地 RAG 栈同源（Chroma），但能力弱于本地三路混合检索
MCP 协议 既做 MCP client（Stdio/HTTP），又暴露 /mcp 端点当 MCP server（agent 可编程管理它） ⭐⭐⭐ 六员可直接管理 LangBot
Skills + 代码沙箱 按需加载指令包 + Docker/nsjail/E2B 隔离执行 ⭐⭐ 与 Hermes 技能体系理念一致
多平台触达 一个机器人覆盖所有 IM ⭐⭐⭐ 手机端查任务/收通知的最强方案
Web 管理面板 浏览器配置，不改 YAML ⭐⭐
插件生态 数百个社区插件，跨进程事件驱动，热插拔 ⭐⭐

部署方式

  • 一行启动：uvx langbot（需 uv）→ http://localhost:5300。
  • Docker Compose：cd LangBot/docker && docker compose --profile all up -d。
  • 也有 aaPanel / Kubernetes / Zeabur / Railway 云部署。

与现有体系的关系

维度 LangBot 现有六员体系
架构 IM 机器人（消息驱动） CLI/终端调度
RAG 内置 Chroma + Rerank 本地三路混合（dense+sparse+BM25）+ 图谱
模型接入 LiteLLM 统一层 各自配置 provider
适用场景 对外服务（群内问答、客服） 内部开发/调度

结论：不替代、不冲突，是"对外服务层"的候选。

何时值得接入（触发条件）

✅ 该接： - 要给学员/同事提供"群里 @机器人 问知识库"的服务（知识库 IM 化）。 - 需要在手机上多平台管理任务/收通知（比 telegram-send 强）。

❌ 不该接（现状）： - 只是想增强本地 RAG（它内置 RAG 不如现有三路混合检索）。 - 想替代六员体系（架构不同）。 - 内存紧张时（多一个常驻进程，WSL 7.8G 已吃紧）。

待办（挂账，不急）

  • [ ] 等触发条件满足（学员/同事有 IM 问答需求）再部署。
  • [ ] 部署前先评估内存预算（当前 WSL 可用 ~3.5G，LangBot + Docker 至少要 1G）。
  • [ ] 接入时优先用它的 MCP server 让六员管理，而不是手动配。

附：Cherry Studio 一句话备忘（2026-10-22）

Cherry Studio：开源 AI 桌面客户端（多模型对话 + 本地知识库 + 多模态）。与现有体系关系：知识库能力冗余（不如本地三路混合检索）、与 OpenWebUI 功能重叠。结论：不接，除非想在 Windows 桌面快速对比模型输出（现有工具已覆盖）。与 LangBot 不同：Cherry Studio 是个人桌面客户端，LangBot 是对外 IM 服务。
