核心结论

协作工作流调研 已收录编排范式与失败模式；本篇补上那份调研中没展开的生产化三道防线，每条都有硬数字：①断点续传——checkpoint 的语义是"每次 LLM 调用恰好付一次 token"，无 checkpoint 的 naive retry 在 3 小时 50 分任务第 29 分钟崩溃时要损失 3.9 小时，有 checkpoint 则分钟级续跑；②上下文治理——上下文失效四型里 clash（互相矛盾）是多 agent 高发，防线 = 隔离 + 状态字段化，且子 agent 产物必须落文件、只回传轻引用（防传话游戏）；③工具层验证——最反直觉的一条：模型不能当验证层，工具返回 success:true 只代表"系统接受了命令"，{"status":"queued"} 比 success:true 诚实，验证必须是位于模型之下的 harness 层确定性读回。配套给出 MAST 十类失败模式对照表与 10 条优化点清单。

关键细节

一、断点续传（durable execution / checkpoint-resume）

机制 做法 关键依据
checkpoint 语义 持久化"已完成的执行边界"，恢复时跳过已完成步骤、只重跑失败的那个 Temporal 不可变 event history / Restate journal / Inngest step.run
exactly-once LLM 工具调用不天然幂等（订两张机票/发两封邮件）；重试必须挂在幂等键 + 已验证失败上，不能挂在未验证的成功信号上 5 步×99%=95%、10 步=90%，真实 agent 几十步
HITL 挂起原语 人审等待可长达小时/天，工作流在检查点挂起、持久化全部状态、审批信号到达后从原点恢复（waitForEvent / awakeable），不空转轮询 Inngest/Restate
派单卡状态机 每卡机器可读状态 pending / running / awaiting-review / blocked / done + 产物路径 + 已完成步骤清单 + 幂等键；崩溃后按状态文件续跑而非靠回忆 5方向调研方向 3
预算硬上限 派单模板加 budget_tokens 字段，默认 2k/8k/30k 三档；超预算自动 kill + 写 error-ledger 5方向调研方向 4

状态文件级状态机即可起步，不必引入 Temporal 重基建。LangGraph 路线见 生产级Agent与Evals实操（必须配 checkpointer 是红线，>60% 生产事故源于状态管理）。

二、上下文治理（context engineering）

  • LangChain 四策略：write（scratchpad/Memory 落窗口外）/ select（按需取回）/ compress（只留必要 token）/ isolate（切分给子 agent/沙箱/state 字段隔离）。LangGraph 可把工具回包隔离在非暴露字段，需要时才给模型。
  • 上下文失效四型（Breunig，经 LangChain 引用）：poisoning（幻觉进上下文）、distraction（上下文淹没训练知识）、confusion（冗余干扰作答）、clash（互相矛盾——多 agent 高发型）。
  • 防传话游戏（Anthropic 附录）：结构化产物（代码/报告/图表）让子 agent 直接写外部系统，回 lead 只给轻量 reference；plan 必须先写入 Memory 再开干（防 200k 截断丢计划）；上下文逼近上限时开 fresh subagent + 精心交接，而非硬撑。
  • 反方（Cognition）：隔离的代价是信息衰减——只传单条消息而非完整 trace，子 agent 各自隐式决策 → 产物互相冲突。折中形态：隔离执行过程，共享决策与产物。
  • 回传契约五字段（机械防线）：交付了什么 / 证据路径 / 做了哪些关键取舍 / 未解决的不确定性 / 被卡外拒绝的动作。
  • Code-as-MCP（5方向调研方向 5）：子 Agent 用 search_file / read_file / run_test / apply_patch 工具四件套操作代码，而非把文件内容贴进上下文——比"整个 repo 塞 prompt"省 95% token。

三、工具层验证（post-condition，防 success:true 假成功）

核心论断（TianPan）：工具返回 {"success": true} 只代表"系统接受了命令"，不代表"世界按要求变了"（200=请求被接收、邮件=进了队列、DB=写到未同步副本）。让模型"更怀疑地核对"是错误层级——prompt 里的怀疑论只产生表演式怀疑。验证必须是确定性的、位于模型之下的 harness 层，以证据形式喂给模型。

post-condition 四件套：

  1. 调用点幂等键（Stripe 式，重试安全的前提）
  2. 写后确定性读回（按 key 读回校验存在与字段）
  3. 契约区分 accepted vs completed（{status:"queued", message_id} 比较诚实）
  4. 按后果分级验证预算（营销邮件不验、退款三重验）；对应派单卡"验证档"：V0=读类自查 / V1=预埋 check 复跑 / V2=写后读回+独立审查 / V3=读回+人工确认（钱、配置、对外发布）

分层验证（Anthropic）：约 20 条真实 query 小样本立即开测 → LLM-as-judge 按 rubric 打分（单一 judge 单 prompt 输出 0-1 分最稳定，多 judge 反而一致性差）→ 人工评测抓自动化漏的边缘案例 → 改状态的长程 agent 用 end-state evaluation（看终态 + 切成离散检查点）。审查者需 gold set 校准，业界 kappa≈0.797 算 substantial——未经 kappa 验证的"judge 说不行"只是 vibe。

四、MAST 失败模式对照表（业界实证 vs 现有防线）

# 业界失败模式（实证占比） 现有防线 缺口
1 step repetition / 死循环（MAST 最高频 15.7%） 同错 3 次停手 只防"同错"，不防同步骤换皮重复；无动作相似度检测
2 不知何时停（premature 6.2%） 绿即停、验收四门 依赖验收方认真
3 验证缺失/错误（合计 23.5%） 自报不采信、G0-G9 工具层假成功无读回验证；judge 无一致性校准
4 规格空泛（specification 41.8% 最大类） 白名单、六要素 委派契约缺"输出格式/工具指引"显式字段
5 agent 间错位（32.3%） 配置全局串行、审查只读 审查者上下文过窄易误判；回传消息无 schema
6 重复劳动 / fan-out 撞车 batch≤3 拆卡无工作域声明，事前发现不了撞车
7 过度协商 / 多数暴政（correct→incorrect 翻转压过反向） 审查轮≤2、分歧升用户不投票 已基本覆盖
8 错误传播（0.95^10=59.9%） 停手三线、fallback 多卡串联无"链长×成功率"提示
9 任务漂移（semantic/coordination/behavioral 三型） 白名单、回边 A 重计划 复计划无"新任务清单 vs 原目标"显式 diff
10 说做不符（13.2%，MAST 第二高频） 凭据标注 + receipt 对账 免凭据卡无外部对账，是残留敞口

五、全局优化点清单（按动作分类）

  • 【新增】：拆卡前三问（真独立？只读无写冲突？价值配得上 fan-out 放大？）；工具层 post-condition 读回；派单卡状态机 + 断点续传；验证档 V0–V3；并行卡工作域声明。
  • 【补充】：委派契约补"输出格式/工具指引"两字段；token 台账加"vs 单 agent 放大倍数"列（对照单 agent ≈4×、多 agent ≈15× chat 基准）；judge 抽样 10–20 条人工 gold set 校准。
  • 【冲突需裁决】：C1 审查者上下文——"只给产物路径"与 Cognition "share full traces" 正面冲突，折中 = 产物路径 + 执行侧决策摘要（不含过程日志）；C2 并行写串行边界是否从"配置类"扩展到"同仓并行写"；C3 三阶评审+三级审的累计轮次是否计入"审查轮≤2"。
