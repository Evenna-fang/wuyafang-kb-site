MCP 到底解决了什么问题：为什么不能直接调 API

📄 一手源：MCP原理与实战：高效AI Agent智能体开发

← 返回总入口

这个问题的答案是什么

MCP 不是「又一个 API 协议」，它解决的是「N 个 AI 应用 × M 个工具/数据源」的 N×M 集成爆炸问题。 在没有 MCP 之前，每接一个新的数据源或工具，都要为每一个 AI 客户端（Claude、Cursor、Cherry Studio、自研 Agent）单独写一份胶水代码——5 个应用接 5 个工具就是 25 份定制代码。MCP 把这 25 份变成「每工具一份 server + 每客户端一份协议适配」，降到 N+M。

它和直接调 API 的本质区别有三层：

  1. API 是给人/前端看的，MCP 是给 LLM 看的——工具描述里要写清副作用（只读还是会改状态）、参数 schema、权限等级，LLM 才能安全地选工具。
  2. API 只解决"调得通"，MCP 解决"调得安全、调得可发现、调得可授权"——OAuth 流程、用户高风险操作确认弹窗、资源发现（Resources/Tools/Prompts 三类原语）都是内建的。
  3. API 是点对点的，MCP 是"USB-C 式"的——一次实现，所有兼容客户端都能用，这是它被称为"AI 应用的 USB-C"的原因。

详细内容

一、N×M 爆炸：为什么手写胶水代码走不通

《MCP原理与实战》开篇举的典型场景：5 种 AI 应用都要接 5 种数据源，就是 25 套定制方案。这个数字再乘上"每个工具都要重新做鉴权、错误处理、参数解析"，工程成本是指数级的。

《一本书讲透 MCP》从产业视角补了一刀：传统 Agent 的瓶颈不是"模型不够聪明"，而是"Agent 之间、Agent 与工具之间连不起来"——Agent 要自己爬 API、自己拼 prompt、自己维护工具描述库，等于每个 Agent 都把同样的活重干一遍。MCP 把这一层抽成了"连接层"。

二、三类原语：MCP server 到底对外暴露什么

《MCP原理与实战》第 2 章把抽象压到三个原语，这个分类在两本 MCP 书里是一致的：

原语 形态 典型例子 副作用
Resources（资源） 只读、"万物皆资源"——文档全文、DB 记录、一次 API 返回、截图、日志 读取一份 PDF、查询一条订单 无状态，LLM 读了不改变世界
Tools（工具） 可执行、动态、有副作用 create_repo、pods_exec、send_email 会改变外部系统状态
Prompts（提示模板） 可复用的指令片段 "简历筛选模板"、"代码评审 prompt" 团队统一输出风格

关键工程细节：工具描述里必须标注"只读 vs 会修改数据"——这是让 LLM 安全选工具的基础，也是主机弹出"大模型想执行删除操作，是否允许"确认框的依据。

三、MCP vs 直接 Function Calling：不是替代，是分层

《一本书讲透 MCP》第 2 章明确把 Function Call 和 MCP 放在一起讲：

  • Function Calling 是模型能力——模型输出结构化 JSON，告诉应用"我要调这个函数"。
  • MCP 是传输和发现协议——规定 server 怎么暴露工具、客户端怎么发现、怎么鉴权、怎么传参。

简单说：Function Calling 是"模型会点菜"，MCP 是"整个餐厅的菜单系统+传菜口+结账流程"。MCP 可以建立在 Function Calling 之上，而不是取代它。

四、安全机制：为什么 MCP 比直接写 API 安全

两本书在安全这点上口径一致，也是 MCP 最容易被忽略的价值：

  1. OAuth 内建：访问第三方服务走标准 OAuth，不暴露用户名密码，用令牌通信。
  2. 高风险操作人审：主机端可以弹确认框，"大模型想执行删除，是否允许"——用户同意才放行。
  3. 权限分级：工具在描述里声明自己是只读还是会改状态，主机据此决定要不要人审。
  4. 沙箱/权限裁剪：比如 MCP Run Python 用 -N -R 参数显式打开网络和 node_modules 读写，默认是收紧的。

《MCP原理与实战》的例子：Gitea MCP 内置近 30 个工具，全部一一映射到 Gitea REST API（POST /repos/{owner}/{repo}/issues 之类），调用完返回 JSON 给大模型判断——这就是"把已有 REST API 包成 MCP server"的标准姿势，1 个 server 喂所有客户端。

五、MCP vs A2A：别把这俩混了

《一本书讲透 MCP》第 11 章专门讲两者关系：

  • MCP 解决"Agent 怎么连工具"——人机/人-系统连接层。
  • A2A 解决"Agent 怎么连 Agent"——Agent 之间的协作协议（Google 主推）。

两者不是竞争关系，是互补：MCP 是"手"（工具调用），A2A 是"嘴"（Agent 间通信）。未来的形态大概率是 MCP + A2A 同时存在。

来自哪些书的哪些观点

  • 《MCP原理与实战》：N×M 集成爆炸的起源故事；三类原语（Resources/Tools/Prompts）的定义；安全机制（OAuth、人审弹窗、工具副作用标注）；Gitea/Cloudflare/K8s MCP server 的实操细节。
  • 《一本书讲透MCP》：MCP 是"AI Agent 互联网最优解"的产业叙事；MCP vs Function Call、vs A2A 的分层关系；对经典 Agent 框架（Agently/BISHENG）的重构效应。

⚠️ 观点差异：两本书对 MCP 定位略有差异——《实战》把它当作"工具接入标准"，偏工程师视角；《讲透》把它上升到"AI 互联网的 TCP/IP"，偏产业视角。工程上按《实战》落地，产业判断按《讲透》参考即可。

我们库当前的落地点（对照六员体系）

  • Hermes：已经在做 MCP 客户端（browser_*、xurl、notion 等工具本质上就是 MCP 风格的工具封装），但 server 端对外暴露还没标准化。
  • DSH/Claude Code/Codex：Claude Code 是 MCP 客户端的标杆（官方支持），这也是我们为什么把"工具描述要写清副作用"当作硬性规范——Anthropic 自己就是这么要求的。
  • OpenClaw：它的"工具"生态（图像生成、视频生成、MCP server）就是典型的 MCP 化方向。
  • 待落地：未来把 Hermes 的自定义工具按 MCP 三类原语（Resources/Tools/Prompts）重新梳理一遍，让所有六员能通过同一套 server 互相调用工具。

一句话总结：MCP 不是新 API，是"N 个客户端 × M 个工具"的集成降维——每工具一份 server，客户端即插即用，还内建 OAuth 和人审。
