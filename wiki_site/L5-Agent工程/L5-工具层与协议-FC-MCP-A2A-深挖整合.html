L5 工具层与协议：Function Calling、MCP、自定义工具与 A2A

← 返回总入口 相关：Agent 核心循环与业务落地 · 多 Agent 协作与编排 · Agent 框架选型与平台生态 · Agent 记忆与自进化 · Agent 生产化可靠性与评估 · OpenClaw 模块协同

导读

Agent 要靠工具才能动手，工具层因此是 Agent 工程的基础设施。这一层通常被问成"用 Function Calling 还是用 MCP"，但两者不在同一层。下面几条是本篇的核心结论：

  1. 三者是叠加关系，不是三选一。 Function Calling（FC）决定模型"调哪个函数、传什么参数"；MCP 决定工具"怎么被标准化发现、授权、复用"；自定义工具是业务里那段真正做事的函数。
  2. 选择看复用范围和副作用。 单人单次的 demo 直接写 FC；工具要被多个 Agent 或客户端复用，就包成 MCP server；工具会改外部状态，就必须有授权和确认环节。
  3. MCP 的价值是把 N×M 的集成降到 N+M，并内建 OAuth、人工确认和副作用标注。 这些能力裸 FC 不带，要自己实现。
  4. FastMCP 能把工具写成 server 或挂进 FastAPI。 手工设计的 MCP 工具效果明显优于从 REST 接口自动转换的工具。MCP 与 A2A 分工明确：MCP 管 Agent 与工具之间的连接，A2A 管 Agent 与 Agent 之间的协作。

一、工具层分层：FC、MCP、自定义工具不是三选一

1.1 三层各自解决的问题

工具层可以拆成三层，每层由不同的角色定义，解决的问题也不同：

层 解决的问题 谁定义 典型形态
Function Calling（FC） 模型怎么决定"现在该调哪个函数、传什么参数" 模型厂商（OpenAI、Anthropic、GLM 等） 在 prompt 里塞 JSON schema，模型输出 {"name":"...","arguments":{...}}
MCP（Model Context Protocol） 工具怎么被标准化发现、授权、复用 Anthropic 主导的开放协议 工具服务器暴露 tools/list、tools/call，客户端（Claude Desktop、Cursor）统一接入
自定义工具 业务里"查库存、开发票"这类函数怎么写 使用方自己 Python 函数加 docstring 加装饰器，被 FC 或 MCP 注册

三层分别回答三个问题：模型会不会选，工具怎么接入，业务函数怎么实现。因为回答的问题不同，三者没有替代关系。

1.2 FC 与 MCP 的分工

FC 与 MCP 经常被放在一起比较，两本 MCP 书的口径一致：Function Calling 是模型能力，模型输出结构化 JSON，告诉应用"我要调这个函数"。MCP 是传输和发现协议，规定 server 怎么暴露工具、客户端怎么发现工具、怎么鉴权、怎么传参。

可以用餐厅来类比。Function Calling 是"模型会点菜"。MCP 是"整个餐厅的菜单系统、传菜口和结账流程"。MCP 建立在 Function Calling 之上，并不取代它。 模型仍然靠 FC 能力决定调用哪个工具，MCP 负责把这些工具按统一方式提供出来。

FC 的价值在于执行权留在应用代码手里。模型只负责选函数和填参数，真正的调用由应用层完成。这是目前把 LLM 接到外部 API 最可靠的做法，比让模型自己拼 curl 更可控。

1.3 判断口诀

按三个条件选层：

  • 单次 demo，且只有自己一个人用：直接写 FC，一个 @tool 装饰器就够用。
  • 工具要给多个 Agent 或多个客户端复用：包成 MCP server。
  • 工具会改变外部状态，例如删库、发邮件、转账：必须走 MCP 的授权与确认弹窗，不能裸跑 FC。

1.4 本库六员的工具层现状

二、选工具的原则

2.1 实操共识：三条基本规则

几本书对工具设计的建议高度一致，可以归纳成三条：

  1. 工具粒度要小。 一个工具只做一件事，模型选错的概率才低。
  2. 工具描述里写清"什么时候用、什么时候不用"。 这比函数实现本身更影响调用准确率。FC 的价值很大程度取决于 schema 的描述质量，docstring 写得越清楚，模型选错的概率越低。
  3. 只读工具和写工具要分开。 写工具必须有人审、有日志、有回滚。

工具是可插拔的，Agent 主脑是稳定的。《零基础搭建 Coze+Dify+LangChain》把插件比作智能体的工具箱，并强调模块化解耦："想用就装，不用就卸，不影响核心系统"。自定义工具的设计哲学正是如此。

2.2 Anthropic 工具设计原则

Anthropic 的工具设计原则适用于任何框架，不论选哪种 SDK：

  1. 简单优先。 工具文档和测试花的功夫，应当超过花在 prompt 上的功夫。
  2. 控制 token 预算。 58 个工具的定义约 55K token 起步。优化前，工具定义可能吃掉 134K token。对策是 defer_loading 或 Tool Search：按需加载，延迟加载的工具不进入初始 prompt，也不破坏 prompt caching。
  3. 限制响应长度。 Claude Code 默认把单次工具响应限制在 25,000 token。
  4. 抽象层级越高，细粒度控制越贵。 选框架或封装工具前，先确认要调的那个参数，在该层是否暴露。

第一条和第二条都在提醒同一件事：工具越多，模型负担越重。这也是后面 MCP 安全章节"每个 Agent 活跃 MCP 数不超过 6"的依据。

2.3 从 demo 到生产：工具层的位置

工具层是 Agent 落地的一个环节。《最佳答案》给出的落地 5 步中，第 3 步是"选工具"：判断哪些需求用 RAG 查知识库，哪些用 FC 调 API，哪些用代码执行做计算。第 5 步是"接日志和回调"，每次用户提问、链的运行状态、模型输出都要记录，这一步是从 demo 到生产的分水岭。工具调用本身属于 Agent 循环的一部分，循环怎么设计见核心循环与业务落地。

三、MCP 解决什么问题

3.1 N×M 集成爆炸与 N+M 降维

《MCP原理与实战》开篇给出典型场景：5 种 AI 应用要接 5 种数据源，传统做法要写 25 套定制接入。这个数字还要乘以"每个工具都要重新做鉴权、错误处理、参数解析"，工程成本接近指数增长。

MCP 把这一层抽成统一协议。每个工具写一份 server，每个客户端实现一份协议适配，总量从 N×M 降到 N+M。

《一本书讲透 MCP》从产业视角补充了一点：传统 Agent 的瓶颈不是"模型不够聪明"，而是 Agent 之间、Agent 与工具之间连不起来。Agent 要自己爬 API、自己拼 prompt、自己维护工具描述库，等于每个 Agent 都把同样的活重干一遍。MCP 把这一层抽成独立的连接层。

3.2 API 与 MCP 的三点区别

MCP 不是"又一个 API 协议"。它与直接调用 API 的区别有三层：

  1. API 面向人和前端，MCP 面向 LLM。 工具描述里要写清副作用（只读还是会改状态）、参数 schema、权限等级，LLM 才能安全地选工具。
  2. API 只解决"调得通"，MCP 还解决"调得安全、调得可发现、调得可授权"。 OAuth 流程、高风险操作的确认弹窗、资源发现（Resources、Tools、Prompts 三类原语）都是协议内建的。
  3. API 是点对点的，MCP 是通用接口式的。 实现一次，所有兼容客户端都能用。这是 MCP 被称为"AI 应用的 USB-C"的原因。

3.3 三类原语

MCP server 对外暴露三类原语。两本 MCP 书的分类一致：

原语 形态 典型例子 副作用
Resources（资源） 只读，"万物皆资源"，包括文档全文、数据库记录、一次 API 返回、截图、日志 读取一份 PDF，查询一条订单 无状态，LLM 读取后不改变外部世界
Tools（工具） 可执行、动态，有副作用 create_repo、pods_exec、send_email 会改变外部系统状态
Prompts（提示模板） 可复用的指令片段 "简历筛选模板"、"代码评审 prompt" 团队统一输出风格

工程上的关键细节是：工具描述里必须标注"只读"还是"会修改数据"。 这一标注既是 LLM 安全选工具的基础，也是主机端弹出确认框的依据。

3.4 MCP 与 FC 的分层关系

FC 与 MCP 的关系已在 1.2 节说明：FC 是模型能力，MCP 是传输和发现协议，两者叠加使用。实际接入时，LangChain 这类框架会把 MCP server 暴露的工具转换成框架自身的 Tool 对象，交给 Agent 使用。见第五节的集成示例。

3.5 两本书的定位差异

《MCP原理与实战》把 MCP 当作"工具接入标准"，偏工程视角。《一本书讲透 MCP》把它上升到"AI 互联网的 TCP/IP"，偏产业视角。工程上按前者落地，产业判断可以参考后者。

四、MCP 的安全与治理

4.1 协议内建的安全机制

MCP 相对直接写 FC 的最大增量在安全。以下四项是协议或主机端提供的能力：

  1. OAuth 内建。 访问第三方服务走标准 OAuth 授权，不暴露用户名和密码，用令牌通信。
  2. 高风险操作人审。 主机端可以弹出确认框，"大模型想执行删除操作，是否允许"。用户同意后才放行。
  3. 权限分级。 工具在描述里声明自己只读还是会改状态，主机据此决定是否需要人审。
  4. 沙箱与权限裁剪。 以 MCP Run Python 为例，网络访问和 node_modules 读写需要用 -N -R 参数显式打开，默认收紧。

这些能力都是 FC 原生不带的，需要自己写。这也是把"工具描述要写清副作用"当作硬性规范的原因。Claude Code 是 MCP 客户端的标杆实现，Anthropic 自己也这样要求。

4.2 把已有 REST API 包成 MCP server

《MCP原理与实战》给出的例子是 Gitea MCP。它内置近 30 个工具，每个工具映射到一个 Gitea REST 接口，例如 POST /repos/{owner}/{repo}/issues。调用后返回 JSON，由大模型判断下一步。这就是"把已有 REST API 包成 MCP server"的标准做法：一个 server 供所有客户端使用。

后面第六节会说明，这种自动转换适合做原型，不适合直接作为面向 LLM 的最终工具集。

4.3 生态层面的硬约束

2026 年的 MCP 生态已经很大。外部调研显示，公开 MCP server 已超过 10,000 个，头部集中度高：前 17 个覆盖约 80% 的搜索量。头部包括 Playwright、Figma、GitHub、Jira、Context7 等。这些数字来自榜单式的二手综合，只能作为生态规模的参考，不能当作精确统计。

数量多也带来风险。2026 年 4 月披露过一件事：下载量达 1.5 亿的某个 MCP server 存在 RCE 漏洞。因此，调研结论给出了五条硬约束：

  1. 只用官方 vendor server，并固定版本号，不用 latest。
  2. API token 按最小权限配置。 数据库账号只读，GitHub token 只勾选必要的 scope。
  3. 文件访问范围限定在单一项目目录，不开放整个 home 目录。
  4. Web fetch 类工具开启 SSRF 防护。
  5. 每个 Agent 活跃的 MCP 数不超过 6 个。 超过后，模型工具选择会陷入困惑。

这五条与前面的安全机制互为补充。协议保证鉴权和确认流程能走通，这五条决定工具面的范围和来源。

五、动手：FastMCP 实操

FastMCP 是 Python 的高层 MCP 框架。它把装饰器与 JSON Schema 生成封装在一起，写一个 server 的成本很低。以下三段代码对应课件第六节的三个步骤。

5.1 MCP Server 最小示例

from fastmcp import FastMCP
from typing import Annotated
from pydantic import Field

mcp = FastMCP(name="health_server")

# 1) Tool：给 LLM 当"手"
@mcp.tool()
async def add(a: int, b: int) -> int:
    """计算两数之和"""
    return a + b

@mcp.tool()
async def calculate_bmi(weight_kg: float, height_m: float) -> str:
    """计算 BMI 指数并返回健康建议"""
    if height_m <= 0:
        return "错误：身高必须大于 0"
    bmi = weight_kg / (height_m ** 2)
    tip = "偏瘦" if bmi < 18.5 else "正常" if bmi < 24.9 else "偏胖"
    return f"BMI: {bmi:.2f} ({tip})"

# 2) Resource：给 LLM 当"眼睛"（静态/动态数据）
@mcp.resource("resource://health-guidelines", mime_type="text/plain")
async def get_health_guidelines() -> str:
    """通用健康指南"""
    return "1. 每天 8 小时睡眠  2. 多吃蔬菜水果  3. 每周运动 150 分钟"

# 3) Prompt：给 LLM 当"模板"
@mcp.prompt()
async def analyze_my_health(
    name: Annotated[str, Field(description="用户姓名")],
    weight: Annotated[float, Field(description="体重 kg")],
    height: Annotated[float, Field(description="身高 m")],
) -> str:
    """生成健康分析提示词"""
    return f"用户 {name}，体重 {weight}kg，身高 {height}m。请计算 BMI 并给出建议。"

if __name__ == "__main__":
    mcp.run()   # 默认 stdio 传输；也可以 mcp.run(transport="http")

代码要点如下：

  • @mcp.tool()、@mcp.resource(uri)、@mcp.prompt() 三个装饰器分别对应 MCP 的三类原语。
  • FastMCP 是高层封装，会自动生成 JSON Schema。需要动态生成工具时，可以退到底层写法：用 mcp.server.Server 手动编写 @server.list_tools()。课件也讲了这种写法，但只在动态场景下使用。
  • 传输方式默认是 stdio，即通过子进程通信，适合本地工具。HTTP 或 SSE 适合远程 server。

5.2 MCP Client 调用 Server

import asyncio
from fastmcp import Client

async def main():
    # Client 直接传 server 脚本路径，自动拉起子进程
    async with Client("01-first_mcp_server.py") as client:
        await client.ping()

        # 1) 列出并调用工具
        tools = await client.list_tools()
        print("可用工具:", [t.name for t in tools])
        r = await client.call_tool("add", {"a": 10, "b": 5})
        print("add 结果:", r.content[0].text)

        # 2) 读资源
        resources = await client.list_resources()
        r = await client.read_resource("resource://health-guidelines")
        print("健康指南:", r[0].text)

        # 3) 取提示词模板
        prompt = await client.get_prompt("analyze_my_health",
                                         {"name": "Alice", "weight": "60", "height": "1.65"})
        print(prompt.messages[0].content.text)

asyncio.run(main())

Client 的三步对应 server 的三类原语。先用 list_tools 发现工具，再用 call_tool 调用；用 read_resource 读取资源；用 get_prompt 取模板。

5.3 LangChain Agent 集成 MCP

import asyncio, os
from dotenv import load_dotenv
from langchain_openai import ChatOpenAI
from langchain.agents import create_agent
from langchain_mcp_adapters.client import MultiServerMCPClient

load_dotenv()
llm = ChatOpenAI(model="kimi-k2.5",
                 api_key=os.getenv("DASHSCOPE_API_KEY"),
                 base_url=os.getenv("DASHSCOPE_BASE_URL"))

async def main():
    # 一个 client 可以连多个 MCP server
    client = MultiServerMCPClient({
        "health_server": {
            "transport": "stdio",
            "command": "python",
            "args": ["./01-first_mcp_server.py"],
        },
    })
    tools = await client.get_tools()    # 自动把所有 server 的 tool 拉成 LangChain Tool

    agent = create_agent(model=llm, tools=tools)
    r = await agent.ainvoke({"messages": [
        {"role": "user", "content": "我体重 75kg，身高 1.80m，算一下 BMI"}]})
    print(r["messages"][-1].content)

asyncio.run(main())

5.4 三段代码的意义

这组示例体现了 MCP 的几个工程效果：

  • 工具定义从业务代码中抽离，变成独立的 server 进程。
  • 同一个 MCP server 可以被 Claude Desktop、Cursor、LangChain Agent 和自研 Agent 同时复用。
  • MultiServerMCPClient 允许一个 Agent 同时挂载 N 个工具 server。课件把这种做法视为生产架构的标准做法。

六、FastMCP 与 FastAPI 的两条集成路径

如果要把 RAG 检索或知识库查询做成 MCP server 供六员调用，FastMCP 是官方首选框架。FastMCP 与 FastAPI 的集成有两条路径，适用场景完全不同。用错会导致 LLM 调用工具的效果变差，也会出现 session 不初始化、CORS 冲突等问题。

6.1 路径 A：从 FastAPI 生成 MCP server

路径 A 的作用是把现有 API 转成 MCP 工具：

from fastmcp import FastMCP
mcp = FastMCP.from_fastapi(app=app)  # 一行转换
mcp.run()

要点如下：

  • 底层基于 OpenAPIProvider（v3.0.0 及以上），从 FastAPI 的 OpenAPI spec 抽取工具。
  • 工具名取自 FastAPI 的 operation_id。必须显式指定，否则会生成类似 list_products_products_get 的难看名字。
  • 转换后得到的仍是完整的 FastMCP 实例，可以继续用 @mcp.tool 添加新工具或资源。
  • 支持 RouteMap，可以自定义端点到 MCP 组件的映射，例如 GET 映射为 Resource，POST、PUT、DELETE 映射为 Tool。
  • 支持通过 httpx_client_kwargs 传入认证头。

官方明确警告：LLM 对手工设计的 MCP server 效果显著优于自动转换的 server，对复杂 API（多端点、多参数）尤其明显。因此路径 A 只建议用于 bootstrap 或原型阶段，不建议把 REST API 原样搬到 LLM 客户端。

6.2 路径 B：把 MCP server 挂进 FastAPI

路径 B 的作用是给已有的 Web 应用增加 MCP 能力：

from fastmcp import FastMCP
from fastapi import FastAPI

mcp = FastMCP("Analytics Tools")
mcp_app = mcp.http_app(path='/mcp')

# 必须传 lifespan（否则 session manager 不初始化）
app = FastAPI(title="E-commerce API", lifespan=mcp_app.lifespan)
app.mount("/analytics", mcp_app)
# 现在：REST API 在 /products/*，MCP 在 /analytics/mcp/

要点如下：

  • 如果两个 app 各自有 lifespan，用 combine_lifespans 合并。合并后按顺序进入、逆序退出。
  • 这条路径可以组成"REST 加 MCP 双入口"：同一个代码库同时提供传统 API 和 MCP 端点。

6.3 四个关键坑

坑 说明 解法
operation_id 决定 MCP 工具名 不显式指定，会生成 list_products_products_get 写成 operation_id="get_user_by_id"
lifespan 必须传 不传，MCP session manager 不初始化 FastAPI(lifespan=mcp_app.lifespan)
不要全局加 CORSMiddleware 与 OAuth 保护的 MCP server 冲突，表现为 .well-known 路由 404、OPTIONS 请求失败 采用 sub-app 模式挂载，不做全局 CORS
FastAPI 需单独安装 FastMCP 不包含 FastAPI pip install fastmcp fastapi uvicorn

6.4 本项目的落地方案

对本库的 RAG 检索而言，路径 B 更合适。理由是：

  • REST 加 MCP 双入口可以同时服务两类调用方。DSH、Codex 等 Agent 用 REST，Claude、OpenClaw 等 LLM 用 MCP。
  • 现有的 rag-kb-mcp 已经用 FastMCP 构建，运行在 8770 端口。如果要增加 REST 入口，可以按路径 B 重构。
  • RAG 检索工具要做成 purpose-built，即手工设计 MCP 工具，而不是从 REST 接口自动转换。这与官方"手工设计效果更好"的结论一致。

仍有两个问题待验证：

  • [ ] 本地 rag-kb-mcp 改造成 FastAPI 加 MCP 双入口，收益是否大于重构成本。
  • [ ] 路径 A 的"自动转换效果差"，在 RAG 检索场景下是否同样成立。RAG 工具通常参数较少，影响可能较小，但尚未验证。

七、A2A 与 MCP 的分工

7.1 A2A 协议的三件核心

A2A（Agent2Agent）是 Google 在 2025 年 4 月提出的 Agent 间互操作协议，基于 HTTP(S)、JSON-RPC 2.0 和 SSE。它有三件核心：

  • Agent Card。 每个 Agent 在 /.well-known/agent.json 声明身份、能力（skills）、支持的模态和认证要求，供其他 Agent 发现。
  • Task Lifecycle。 标准任务状态机：submitted、working、input-required、completed、failed、canceled。支持长时任务和异步推送。
  • Rich Artifacts。 结果可以是文本、文件或结构化 JSON，中途还能动态协商模态。Client 与 Server 对称，只暴露能力边界，不暴露内部 memory 和 tools。

7.2 MCP 与 A2A 的分工

维度 MCP A2A
解决的问题 Agent 与工具之间的连接 Agent 与 Agent 之间的协作
交互模式 结构化同步调用 对话式，可异步，基于 SSE
能力发现 tool list（list_tools） Agent Card
任务生命周期 无，单次调用 完整状态机，支持长时任务

《一本书讲透 MCP》第 11 章专门讨论了两者的关系。MCP 解决 Agent 怎么连工具，是人与系统之间的连接层，好比"手"。A2A 解决 Agent 怎么连 Agent，是 Agent 之间的协作协议，好比"嘴"。两者是互补关系，不是竞争关系。未来的形态大概率是 MCP 和 A2A 并存。

7.3 本库的落地口径

六员都在本机运行。当前的协作本质上是 Hermes 硬编码派单（delegate_task，或 shell 调 CLI），可以说是"伪 A2A"。短期内不上 JSON-RPC server，因为本机 CLI 的开销更小。本库只借用 A2A 的两个产物：

  1. 每个 Agent 写一份 agent_card.md，写明能力边界、输入契约、输出契约、典型任务。
  2. 派单走 task envelope。 用 {task_id, status, input, artifacts} 结构落盘到 ~/.hermes/tasks/，而不是散在 prompt 里。

长期规划是跨机器协作，例如把审查任务发到云端 OpenClaw 时，再上真正的 A2A 协议。这一点在调研里仍是"待评估"，并未进入实施。

小结

工具层由 FC、MCP、自定义工具三层叠加而成。FC 让模型会选工具，MCP 让工具可以标准化地被发现、授权和复用，自定义工具承载业务逻辑。选择时按复用范围和副作用判断：单人 demo 用 FC，多方复用用 MCP，改写外部状态的工具必须有确认环节。

MCP 的价值在于把 N×M 集成降到 N+M，并内建 OAuth、人审弹窗与副作用标注。它的安全效果依赖工具描述的准确性，以及固定版本、最小权限、限定目录范围、SSRF 防护和活跃 server 数不超过 6 这些治理措施。

动手层面，FastMCP 提供 tool、resource、prompt 三个装饰器，Client 与 LangChain 的 MultiServerMCPClient 负责调用。把 FastAPI 与 MCP 结合时，路径 B 适合双入口服务，路径 A 只适合原型。A2A 负责 Agent 之间的协作，MCP 负责 Agent 与工具之间的连接，两者分工明确。
