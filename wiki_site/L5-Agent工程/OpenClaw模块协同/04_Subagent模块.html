OpenClaw 核心模块 —— Subagent（子代理调度）

什么是 Subagent

在 OpenClaw 中，Subagent 是指 由主 Agent（Gateway）派生的、具备独立运行环境的子任务执行体。它们可以是： - 语言模型实例（如 Claude、DeepSeek、OpenAI） - 脚本执行器（Python、Node、Shell） - 外部服务代理（调用内部微服务、数据库、HTTP API）

Subagent 的目标是 实现业务细化：把一个大任务拆解成若干细粒度子任务，每个子任务交给最适合的执行单元，从而提升整体吞吐与可靠性。

Subagent 的生命周期

+-------------------+      +----------------------+      +-------------------+
|   Routing 层      | ---> | Subagent Manager     | ---> |  Subagent 实例   |
+-------------------+      +----------------------+      +-------------------+
          |                         |                         |
          v                         v                         v
    调度决策                资源分配                执行/返回
  1. 调度决策（Routing）为每个子任务决定 runtime、sandbox、priority 等属性；
  2. 资源分配（Subagent Manager）为每个 Subagent 分配 cgroup、namespace、网络配额，并记录 subagent_id；
  3. 执行：Subagent 在 Sandbox 中启动，完成任务后将 结果、状态、日志 写回 Memory RAG；
  4. 回收：Manager 根据 ttl 以及 exit_code 自动回收容器或进程。

图：Subagent 生命周期状态机

stateDiagram-v2
    [*] --> Pending
    Pending: 排队中 等待资源
    Pending --> Spawning: 分配 cgroup 与 namespace
    Spawning: 创建中
    Spawning --> Running: 启动成功
    Spawning --> Failed: SUB001 启动失败
    Running: 执行中
    Running --> Succeeded: exit_code 为 0
    Running --> Failed: 非零退出
    Running --> Timeout: 超过 timeoutSeconds
    Timeout --> Pending: retryCount 小于 maxRetries
    Failed --> Pending: retryCount 小于 maxRetries
    Timeout --> Recycled: 重试耗尽 SUB004
    Failed --> Recycled: 重试耗尽
    Succeeded --> Recycled: 结果写回 Memory RAG
    Recycled --> [*]

配置模型（openclaw.json 示例）

{
  "subagents": {
    "defaults": {
      "runtime": "codex",          // 可选：codex、openclaw、custom
      "sandbox": true,
      "timeoutSeconds": 180,
      "maxRetries": 2,
      "priority": "normal"
    },
    "overrides": {
      "rag": {
        "runtime": "openclaw",
        "sandbox": false,
        "timeoutSeconds": 300
      },
      "highPriority": {
        "priority": "high",
        "cpuQuota": "400%"
      }
    }
  }
}
  • defaults 为全局默认值；
  • overrides 按 标签（如 rag、highPriority）自定义；
  • runtime 决定使用哪种 Agent Harness（Codex、OpenClaw、Claude Code）。

Subagent 运行方式

1. Codex Runtime

openclaw agent exec '生成 Python 代码' \
    --model xiaomimimo/mimo-v2.6-pro \
    --runtime codex \
    --sandbox true
  • Codex 通过内部插件 codex 与 OpenClaw 交互，返回 代码片段 并自动写入 ~/openclaw/tmp/；
  • 结果会被 Sandbox 包装，防止恶意代码直接访问系统。

2. OpenClaw Runtime（内置 LLM）

openclaw subagent run \
    --task-id 0x1a2b3c \
    --payload '{"action":"summarize","text":"..."}'
  • OpenClaw 自带的 轻量 LLM（默认 deepseek-v4-pro）用于低延迟的短文本处理；
  • subagent_id 自动生成，日志中可追踪 subagent_id 与 task_id 的对应关系。

3. 自定义 Runtime（插件）

openclaw plugins enable my_custom_agent --accept-capabilities
openclaw subagent run --runtime my_custom_agent --payload ...
  • 插件提供 自定义入口（如调用内部微服务、运行 Rust 二进制），需要在 plugins.load.extraDirs 中声明路径。

结果回流至 Memory RAG

子代理完成后，Subagent Manager 会调用 MemoryRAG.append_history，写入如下结构（SQLite 表 subagent_history）： | col | type | |-----|------| | subagent_id | TEXT | | task_id | TEXT | | status | TEXT (success/error/timeout) | | output | TEXT | | stderr | TEXT | | timestamp | INTEGER | | resource_usage | JSON |

示例记录：

{"subagent_id":"sub-20261030-001","task_id":"0x1a2b","status":"success","output":"生成的 Python 代码...","stderr":"","timestamp":1730304001,"resource_usage":{"cpu_ms":124,"mem_kb":3124}}

后续的 Routing 或 Memory RAG 在需要时可以直接查询此表，完成 状态闭环 与 结果复用（如缓存同类任务的输出）。

监控指标（Prometheus）

  • openclaw_subagent_active_total – 当前活跃的 Subagent 数量；
  • openclaw_subagent_spawn_latency_seconds – 创建 Subagent 所耗时；
  • openclaw_subagent_execution_seconds{runtime="codex"} – 单个 Subagent 的执行时长；
  • openclaw_subagent_failure_total{reason="timeout"} – 超时失败计数。

常见故障及排查

错误码 含义 可能原因 解决办法
SUB001 子代理启动失败 unshare 权限缺失、cgroup 配置错误 确认用户在 unprivileged_userns_clone=1（WSL）或 docker 组；检查 /etc/cgconfig.conf 是否启用 cpu,memory 控制器
SUB002 沙箱内网络不可达 域名未加入白名单 更新 sandbox.networkWhitelist 并 openclaw sandbox reload
SUB003 结果写入 Memory RAG 失败 SQLite 锁冲突或磁盘满 查看 openclaw memory status；若锁冲突，执行 openclaw memory reset --mode sqlite；
SUB004 超时 timeoutSeconds 设得过低 根据任务复杂度调高，例如 --timeout 300

资源池与调度策略

OpenClaw 支持 两类资源池： 1. 本地进程池（默认） – 直接在本机创建 cgroup，适用于低延迟的轻任务； 2. 容器池 – 基于 Docker（或 Podman）启动轻量容器 openclaw/agent:<runtime>，适用于需要特定运行时（如 Node、Java）。

动态伸缩示例（Python）

from openclaw.subagent import SubagentPool
pool = SubagentPool()
# 根据当前负载自动扩容至 16 实例
pool.scale(target=16)
# 运行任务
result = pool.run(task_id="0xdeadbeef", payload={"action":"scrape","url":"https://example.com"})
print(result.output)

与其他模块的闭环

  • Routing 决定 sandbox=true 或 runtime=codex，将任务属性写入 Subagent；
  • Sandbox 为 Subagent 提供安全执行环境；
  • Memory RAG 持久化 Subagent 的输出与状态，实现 记忆 与 后续检索；
  • Routing 再次读取 Memory RAG，依据历史结果决定是否 复用、重试 或 升级（如转向更强大的模型）。

实践建议

  1. 标签化：在任务 payload 中加入 tags（如 {"tags":["highPriority","ioBound"]}），让 Subagent Manager 根据标签选取合适的资源池；
  2. 幂等设计：子任务必须使用唯一 task_id，子代理在异常重试时应 检查历史，避免重复写入导致业务重复；
  3. 日志统一：所有 Subagent 的 stdout 与 stderr 必须统一写入 sandbox_audit.log，并在 Memory RAG 中保存 log_snapshot，便于事后审计。
  4. 监控阈值：生产环境建议 cpuQuota 不超过 300%、memoryLimit 不超过 1Gi，以免单个子代理耗尽节点资源。

小结

Subagent 通过 细粒度调度、安全沙箱 与 统一记忆，实现了 OpenClaw 多智能体平台的 可扩展、可观测、可安全 的核心能力。结合 Routing、Memory RAG、Sandbox，形成闭环的任务流转，使得平台能够在高并发、异构任务场景下保持高可用与高效能。后续章节将展示 模块间协同流程图，帮助快速定位端到端的执行路径。
