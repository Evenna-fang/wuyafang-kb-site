生产级 Agent 与 Evals 实操

📄 一手源：生产级Agent开发实战-外部调研-20261012 · Evals实操-调研-20261012

核心结论

  1. 2026 年多 Agent 框架已从"demo 能跑"进入"生产可审计"：LangGraph 走状态机式编排（支持循环、断点、回放），CrewAI 走角色/任务式低门槛路线，AutoGen 已并入 Microsoft Agent Framework（MAF）进入 maintenance mode。选型本质是"你要多少状态控制力"。
  2. 生产事故的头号来源是状态管理：LangChain 2026 State of Agent Engineering 报告指出 >60% 生产 agent 事故源于状态管理——所以"必须配 checkpointer"不是可选项，是红线。
  3. Evals 从"锦上添花"变成"刚需"，且直接决定迭代速度：没有 eval 的团队在模型升级时要花数周手动测试，有 eval 的几天内就能完成模型切换。
  4. RAG/Agent 评估有明确范式：Anthropic 的 Task→Trial→Grader→Transcript→Outcome 结构 + RAGAS 三大指标（Faithfulness / Answer Relevancy / Answer Correctness）是当前最成熟的落地组合。
  5. 一个高价值诊断信号：高 faithfulness 但低 answer_correctness，几乎总是指向"检索质量问题"而非"生成问题"——这个信号直接告诉你该优化哪一环。

生产级 Agent 开发实战

2026 框架格局：

框架 定位 关键事实
LangGraph 状态机式编排，支持循环/断点/回放 Anthropic、Replit、LinkedIn、Uber 已生产使用；默认推荐
CrewAI 角色/任务式，门槛最低、社区增速最快 GitHub stars 从 2026-02 的 44k 涨到 8 月的 57k
AutoGen (Microsoft) 已并入 MAF，AutoGen repo 进 maintenance mode MAF 1.0 GA 2026-04-02
  • LangGraph 核心生产要素：State 是带 reducer 的 typed dict（如 add_messages 决定部分更新如何合并）；支持环（cycles），这是它与 DAG 框架的根本差异——agent 可以"重试、反思、再调用"；Checkpointer 支持 Postgres/SQLite/托管 PG，崩溃、resume、rewind 全基于 checkpoint；LangGraph Studio（2026 GA）被比作"agent 界的 Chrome DevTools"，可可视化渲染 graph、逐步调试、任意 checkpoint 回放；错误恢复靠 try/except 路由到 fallback 节点，而非让 graph 崩溃。
  • CrewAI 生产要点：Flows 负责状态/路由/编排；结构化输出在 v1.10.0（2026-02-27）强化，Pydantic 强制 schema；生产四坑是工具可靠性、成本控制、observability、部署模式。
  • CrewAI 真实项目成本：自动化销售前调研（Scraper→News→Tech Stack→Report）约 $0.08/run、5min；PR 自动 code review（Security→Performance→Report Writer）约 $0.15/run、2min；客服分诊（Classifier→Doc Searcher→Responder→Escalation）约 $0.03/ticket，处理 80–90% 的 tier-1。
  • AutoGen → MAF 迁移：MAF 统一了 AutoGen 的对话式多 Agent 抽象 + Semantic Kernel 的企业能力（会话状态/中间件/telemetry/类型安全），支持 A2A 协议与 MCP 工具集成、跨 Python/.NET runtime；BUILD 2026 新增 Agent Harness、Hosted Agents、CodeAct。
  • 选型决策：Azure/.NET 生态 → MAF；角色分工清晰、低门槛 PoC → CrewAI；复杂状态/需 HITL 断点/可回放 → LangGraph。
  • 生产红线：必须配 checkpointer；工具调用必须有 retry/timeout/fallback；必须接 observability（LangSmith 或 OpenTelemetry）。不要做：用裸 ReAct loop（无状态持久化）、让 agent 无限制循环、不打 schema 就把输出给下游。

Evals 落地实操

  • 搭建基础数据集：从生产日志抽 100–200 条真实 query，人工标注 reference answer；按 Anthropic 范式定义 task（input prompt + expected output + grader logic）；初期可用脚本而非框架，关键先有 test cases。
  • RAGAS 三大指标：Faithfulness（回答是否忠实于检索上下文，无监督）、Answer Relevancy（与问题相关性，无监督）、Answer Correctness（对标准答案，需 reference）。RAGAS 0.3+ 的 collections API 支持 Faithfulness/AnswerRelevancy/AnswerCorrectness，judge 用 llm_factory。
  • LLM-as-Judge 配置：judge 用比被评模型小一档的模型（如 gpt-4o-mini 评 gpt-4o）控成本；每个指标定义明确 rubric 防漂移；定期人工抽检校准（Anthropic 建议每周）。
  • CI eval 门禁：每次代码/prompt/embedding 变更后自动跑；阈值如 faithfulness ≥ 0.85、answer_relevancy ≥ 0.80；退步超 5% 自动阻断合并。
  • 线上线下分层：线上实时跑 faithfulness + answer_relevancy（无需 reference、可批量）；离线 CI 跑全部含 answer_correctness + context_precision/recall；每月从 bad case 抽新 query 入集，保持数据集新鲜。
  • Anthropic 结构范式：单次运行叫 trial，多 trial 取平均消除随机性；grader 可以是代码规则、LLM-as-judge 或单元测试。
  • 关键教训：Claude Code 初期靠 dogfooding 迭代，后加 evals 才发现"concision"和"over-engineering"两个隐藏问题——evals 不替代人工，而是让人工抽检更有针对性。OpenAI 强调重点覆盖 edge case（多意图 query、typo、短 query、长对话），happy path 往往不是瓶颈。
  • 低成本幻觉检测：RAGAS 的 HHEM-2.1-Open（Vectara 开源 T5 小模型）可替代 LLM-judge 做 faithfulness 的第二步验证，适合批量生产、成本极低。
