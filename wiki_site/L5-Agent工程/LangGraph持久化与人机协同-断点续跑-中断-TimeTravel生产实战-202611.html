LangGraph 持久化与人机协同：断点续跑、中断恢复、Time Travel 生产实战

← 返回总入口 相关：状态机设计篇 · 多Agent协作生产级实战 · 多智能体生产化缺口与断点续传 · 框架实操选型（含 HITL 对比）

0. 本篇补什么缺口

现有文档回答了"LangGraph 的 checkpointer 比别家强"（框架实操选型 第 3 节横评），也给过一段 HumanInTheLoopMiddleware 示例。缺的是出事故时怎么办的细节：

  • 进程崩了，从哪一步续？已经成功的副作用会不会重复执行？
  • interrupt() 恢复后，暂停前的代码为什么又跑了一遍？
  • 线上某个 thread 跑歪了，怎么回到中间某一步重来，或者改一个值后分叉？
  • 三种 durability 模式怎么选？checkpoint 越积越多怎么办？

本篇所有"🧪"标记的结论都是在本机 ~/ai-stack（langgraph 1.2.11，InMemorySaver，确定性节点）上跑出来的。📄 表示官方文档原文。官方 durable-execution 页面本次无法从 docs.langchain.com 直接抓到，该页内容取自 GitHub 上的文档镜像仓库（miraland-labs/langchain-ai-docs，二手镜像），已在来源中标明；同一结论凡能在本机复现的，以实测为准。

1. 两套存储：Checkpointer 与 Store

📄 官方 persistence 文档把持久化分成两类，职责不同：

Checkpointer Store
存什么 图在每一步的状态快照 应用自定义的键值数据
作用域 单个 thread（线程内） 跨 thread 共享
对应记忆 短期记忆 长期记忆
典型用途 会话连续、HITL、time travel、容错 用户偏好、事实、共享知识

多数生产应用两个都要：checkpointer 管"这次任务进行到哪"，store 管"这个用户长期是什么样"。

1.1 Checkpointer 选型

📄 官方列出的实现：

  • InMemorySaver（即 MemorySaver）：存在内存里，进程重启全部丢失，只用于开发和测试。
  • SqliteSaver：本地文件，适合开发和单机小规模。
  • PostgresSaver / AsyncPostgresSaver：官方建议的生产选择，后者用于异步服务。

📄 Postgres 初始化：

from langgraph.checkpoint.postgres import PostgresSaver

checkpointer = PostgresSaver.from_conn_string("postgresql://...")
checkpointer.setup()   # 首次部署时建表和索引

本机 ~/ai-stack 已装 langgraph_checkpoint_postgres 3.2.0，但本篇没有连库实测 Postgres 路径（本机 5432 上的实例是 Hindsight 记忆库，不能拿来做试验），下面的行为结论都基于内存版 saver。内存版与 Postgres 版遵循同一套接口，语义相同；差别只在持久性和并发，上线前必须在 Postgres 上把本篇的恢复用例再跑一遍。

1.2 生产配置的四条硬性要求

  1. setup() 放进部署流程，不要放在每个请求里。
  2. thread_id 限制在 255 字符以内。📄 官方说明 Postgres 里该列长度有限，超长报数据库错误。建议用 UUID 生成，业务含义放到别的字段。
  3. checkpoint 会无限增长。📄 官方原话建议：长对话会累积 checkpoint，拖慢响应并增加存储成本，要定期清理或设置保留策略（比如定时任务删除 N 天前的 checkpoint）。官方页面没有提供清理 API，所以这个清理任务要自己写 SQL，并且只删已完成（next 为空）的 thread，别删还在等待人工审批的。
  4. 使用 LangGraph Agent Server 时，📄 官方说明持久化由服务端自动处理，不用自己配。自托管才需要上面三条。

2. Durable Execution：恢复不是"从停下的那一行继续"

2.1 官方要求的三件事

📄（镜像）durable execution 的前提：

  1. 指定 checkpointer。
  2. 运行时指定 thread_id。
  3. 把非确定性操作（随机数、时间）和有副作用的操作（写文件、调 API）包进 task，或放在独立节点里。

2.2 关键认知：恢复是重放

📄 官方明确写了一句容易被忽略的话：恢复时代码不会从停止的那一行继续，框架会从"恢复起点"重放，直到走到中断处。恢复起点是：

场景 恢复起点
StateGraph 被中断/失败的节点开头
节点里调用了子图 父节点开头；子图内部从它停止的节点继续
Functional API entrypoint 函数开头（已完成的 task 从缓存读）

这意味着每个节点必须能被安全地重复执行。下面是实测证据。

2.3 🧪 实测一：崩溃后用 invoke(None) 续跑

场景：step1 → step2，step2 第一次抛错。

app = g.compile(checkpointer=InMemorySaver())
cfg = {"configurable": {"thread_id": "crash"}}
try:
    app.invoke({"out": []}, cfg, durability="sync")
except RuntimeError:
    pass                       # step2 失败，进程"崩溃"
# 修复问题后
r = app.invoke(None, cfg, durability="sync")   # 输入给 None = 从 checkpoint 续跑

实测执行轨迹为 ["step1", "step2", "step2"]，最终输出 ["s1", "s2"]。三点结论：

  • step1 没有重跑，已完成节点的结果直接从 checkpoint 读。
  • step2 从头重跑，不是从它失败的那一行继续。
  • 续跑的写法就是同一个 thread_id 加 None 输入。📄 官方也是这样说的。

2.4 🧪 实测二：@task 缓存副作用

节点里如果有两个外部调用 A、B，B 失败后节点重跑，A 会被再调一次。用 Functional API 的 @task 包起来可以避免：

from langgraph.func import entrypoint, task

@task
def call_api_a(x): ...      # 有副作用的调用
@task
def call_api_b(x): ...

@entrypoint(checkpointer=InMemorySaver())
def wf(x: int):
    ra = call_api_a(x).result()
    rb = call_api_b(x).result()    # 这里第一次失败
    return [ra, rb]

B 失败后用同一 thread_id 以 None 续跑，实测 A 的调用次数仍是 1，最终结果 ['a1', 'b1']。📄 官方对应说法：每个 task 的结果会保存进 checkpoint，同一 thread 恢复时已完成的 task 不会重跑。

📄 官方同时提醒：task 启动了但没完成（比如进程在 API 调用中途死掉），恢复时会重新执行。所以 task 本身仍要幂等：用幂等键（订单号、请求 ID）调下游，或者写入前先查是否已有结果。task 缓存只解决"已完成的不重做"，不解决"做到一半死了"。

2.5 durability 三种模式

📄（镜像，与 reference.langchain.com 的类型定义 Durability = Literal['sync','async','exit'] 一致）：

模式 何时写 checkpoint 优点 风险
exit 图退出时（成功、报错、人工中断） 性能最好 进程中途被 kill 时，没有中间 checkpoint 可恢复
async 下一步执行的同时异步写 性能与持久性折中 进程在写入完成前崩溃，最新一个 checkpoint 可能丢
sync 下一步开始前同步写 每步都已落盘，最稳 每步多一次写延迟

选型建议（本文判断，非官方）：

  • 涉及付款、发信、改外部系统的流程用 sync，多出的毫秒级写延迟相对一次 LLM 调用可以忽略。
  • 纯问答、只读检索类用 async。
  • exit 只在批处理、可整体重跑的离线任务里考虑。

调用时通过参数指定：app.invoke(inputs, cfg, durability="sync")。🧪 本机 1.2.11 实测该参数可用。

2.6 优雅停机

📄（镜像，标注 langgraph>=1.2）：创建 RunControl 传给 invoke/stream，在其他线程调用 request_drain()，图在当前 super-step 结束后停下并留下可恢复 checkpoint，抛 GraphDrained，之后用同一 thread_id invoke(None, config) 继续。注意它不会取消正在跑的 asyncio 任务。这是滚动发布时的收尾手段。🧪 本机未实测，上线前自己验证。

3. interrupt：人机协同的五条铁律

3.1 基本流程（🧪 已实测）

from langgraph.types import interrupt, Command

def approve(state):
    ok = interrupt({"question": "批准吗", "amount": state["amount"]})
    return {"status": "approved" if ok else "rejected"}

cfg = {"configurable": {"thread_id": "t-1"}}
r = app.invoke({"amount": 500, "status": "", "log": []}, cfg)
# r["__interrupt__"][0].value == {"question": "批准吗", "amount": 500}
app.get_state(cfg).next            # ("approve",)  线程停在 approve 节点
r = app.invoke(Command(resume=True), cfg)   # 同一个 thread_id 恢复

实测：首次 invoke 返回里带 __interrupt__，载荷就是传给 interrupt() 的值；get_state(cfg).next 为 ('approve',)；用 Command(resume=True) 恢复后 status 为 approved，后续的扣款节点正常执行一次。

📄 官方补充：用 stream_events(..., version="v3") 时，通过 stream.interrupted 判断是否暂停、stream.interrupts 读取载荷；Command(resume=...) 是唯一能作为输入传给 invoke/stream 的 Command 形式，update、goto、graph 只用于节点返回值。

3.2 铁律一：暂停前的代码恢复时会重跑

🧪 实测在 interrupt() 之前放一个计数器，整个流程（暂停加恢复）结束后计数为 2。证实 📄 官方的规则：恢复时节点从头执行，interrupt() 之前的代码每次恢复都会重新执行。

推论：interrupt() 之前不能有非幂等副作用。写成这样是错的：

def bad(state):
    send_email(state["to"])          # 恢复时会再发一次
    ok = interrupt("确认发送结果?")

正确做法有两种：interrupt() 放在节点第一行（官方《Thinking in LangGraph》："interrupt() must come first"），或者把副作用拆到 interrupt() 之后的另一个节点。

3.3 铁律二：不要用裸 try/except 包 interrupt

📄 interrupt() 内部靠抛一个特殊异常暂停执行。裸 except Exception 会把它吞掉，图就不会暂停。要么只捕获具体异常类型，要么把 interrupt() 放在 try 外面。

3.4 铁律三：同节点内多个 interrupt 按顺序匹配

📄 同一个节点里有多个 interrupt() 时，恢复值按调用顺序一一对应。因此不能条件性地跳过某个 interrupt()，也不能放进次数不定的循环里，否则恢复值会错位。

3.5 铁律四：输入校验不要写 while True

📄 官方明确反对在节点里用 while True 循环反复 interrupt() 校验输入，因为每次恢复都会重放之前的循环。正确做法：把提示语存进 state，节点只 interrupt() 一次；输入无效时把错误写回 state，再用条件边回到该节点。这样每一轮校验都是一个独立 super-step，有自己的 checkpoint。

3.6 铁律五：载荷用简单类型

📄 interrupt() 的值必须能 JSON 序列化，只传简单类型或由简单值组成的字典，不传函数和类实例。

3.7 多个并行 interrupt

📄 并行分支同时触发多个 interrupt 时，把每个 interrupt 的 id 映射到各自的恢复值，一次性传入：Command(resume={i.id: value for i in stream.interrupts})。

📄 另外，interrupt_before / interrupt_after 是静态断点，官方只推荐用于逐节点调试，人机协同请用 interrupt()。

3.8 带校验的恢复值

📄 官方标注 langgraph>=1.2.12 起 interrupt() 支持 response_schema（Pydantic、TypedDict 或 dataclass），用来校验恢复值并让客户端渲染表单；校验失败抛 pydantic.ValidationError，可用同一 thread_id 重新提交。🧪 本机 1.2.11 低于该版本，未实测。

4. Time Travel：重放与分叉

线上 thread 跑歪了（比如第 3 步 LLM 选错了工具），不用从头重来。📄 官方提供三个 API：

API 作用
get_state_history(config) 返回该 thread 的 checkpoint 列表，按时间倒序
invoke(None, checkpoint.config) 从指定 checkpoint 重放
update_state(config, values=...) 在指定 checkpoint 上分叉，返回新 config

4.1 🧪 实测：重放

找到停在 approve 之前的 checkpoint（h.next == ("approve",)），用它的 config 调 invoke(None, ...)：

  • 该 checkpoint 之前的节点不重跑。
  • 该 checkpoint 之后的节点重新执行，包括 LLM 调用、API 调用和 interrupt。实测重放后 approve 再次触发 interrupt，返回 __interrupt__。
  • 📄 官方提醒：重放的结果可能和原来不同，因为 LLM 输出和外部状态会变；从最终 checkpoint（next 为空）重放没有任何效果。

4.2 🧪 实测发现的坑：重放后用哪个 config 恢复

这是实测中遇到的、官方页面没写的行为。重放后图停在新的 interrupt，我做了两种恢复：

  • 用旧 checkpoint 的 config（带原来的 checkpoint_id）传 Command(resume=False)：最终 status 是 approved，不是我传的 rejected，旧的恢复值被复用了。
  • 用线程 config（只有 thread_id，不带 checkpoint_id）传 Command(resume=False)：status 为 rejected，log 为 ['approve:False']，符合预期。

结论：重放之后，恢复要用只含 thread_id 的 config，让框架取最新 checkpoint。不要再拿着旧 checkpoint_id 去 resume。我没有深入定位底层原因，推测与旧 checkpoint 上已存的 pending writes 有关，属推测，需要时读源码确认。

4.3 🧪 实测：分叉

fork_cfg = app.update_state(before_approve.config, {"amount": 1})
app.get_state(fork_cfg).values["amount"]     # 1

实测分叉成功，原 thread 的历史条数没有减少。📄 官方要点：

  • update_state 不回滚 thread，它新建一条分支，原历史保留。这对审计很重要：你永远能回答"当时的状态是什么、谁改了什么"。
  • as_node 参数指定"这次更新算哪个节点产生的"，执行从该节点的后继开始。三种情况必须显式给：同一步有多个并行节点更新状态（否则报 InvalidUpdateError）、新 thread 没有执行历史、想跳过某些节点。

4.4 子图与 time travel

📄 默认情况下子图继承父图的 checkpointer，整个子图算父图的一个 super-step，只能从父图层级回溯，不能停在子图内部节点之间。想在子图内部分叉，要给子图设 checkpointer=True 获得独立历史，再用 get_state(config, subgraphs=True) 取子图 config。

📄 persistence 文档也提醒：每个子图管理自己的 checkpoint namespace，子图更新后父图不一定立刻看到。跨图边界共享的数据放进 Store，或让子图写入父 checkpoint。

4.5 生产用途

场景 做法
客服答错，复现问题 get_state_history 找到出错步，replay，观察是否复现
人工纠正中间结果后继续 update_state 分叉，修正字段，invoke(None, fork_cfg)
回归测试 对线上 thread 的某个 checkpoint 重放，换新 prompt 比对输出
事故审计 历史不可变，分叉不改原记录

5. 流式输出：把图的进展暴露给前端

📄 官方 streaming 文档的 stream_mode：

模式 内容 用途
values 每步后的完整 state 调试，数据量大
updates 每步各节点返回的增量，附节点名 前端进度条、日志
messages LLM token，(chunk, metadata) 打字机效果，可用 metadata["langgraph_node"] 过滤
custom 节点内 get_stream_writer() 发的任意数据 长任务的业务进度
checkpoints / tasks 检查点事件 / 任务起止和错误 需要 checkpointer，监控和排障
debug 前两者合并加元数据 完整追踪

可同时订阅多个：stream_mode=["updates", "custom"]。

5.1 🧪 子图流式必须加 subgraphs=True

实测把子图直接当节点加入父图，stream(..., stream_mode="updates", subgraphs=True) 得到的命名空间集合里既有根图 ()，也有 ('sub:<task_id>',) 这种子图命名空间。📄 官方强调 messages 模式同样要加 subgraphs=True，否则父图拿不到子图内 LLM 的 token。create_agent 生成的编译图作为节点时就属于这种情况，不加的症状是前端没有打字机效果，但最终结果是对的，很容易误判成前端 bug。

5.2 Interrupt 与流式的配合

把审批做成产品时，前端流程是：流式展示进度 → 收到 interrupt 载荷 → 渲染审批卡片 → 用户点击 → 后端 Command(resume=...)。📄 框架实操选型 里已记录 Agent Server 在 interrupt 时返回 409 加载荷的约定，自建服务可参考同样的状态语义。

6. Functional API：什么时候不用画图

📄 官方 Functional API 用 @entrypoint 和 @task 把普通 Python 函数变成可持久化的工作流。它与 Graph API 共用同一套运行时，可以在同一应用里混用。

核心能力（📄）：

  • task 结果进 checkpoint，同 thread_id 恢复时不重跑（上面 2.4 节已实测）。
  • 并行：先批量调用 task 拿到一组 future，再统一 .result()。适合并发调 LLM 或 API。
  • RetryPolicy、CachePolicy(ttl=...) 可挂在 task 上；timeout 仅支持 async 的 task 和 entrypoint，超时抛 NodeTimeoutError。
  • 可在 task 内 interrupt()，恢复后前面 task 结果复用。
  • entrypoint.final(value=..., save=...) 可把"返回给调用方的值"和"存进 checkpoint 的值"分开。

选择建议（本文判断）：流程是线性或简单分支、团队更习惯写普通函数、主要诉求是"给现有脚本加断点续跑"时用 Functional API；流程有多个并行分支、复杂回流、需要可视化评审时用 Graph API。官方页面本身没有给出对比结论，只提到"minimal changes to your existing code"是 Functional API 的卖点。

7. 生产事故预案

事故 症状 处置
进程崩溃 thread 停在某节点，无响应 同 thread_id、invoke(None) 续跑，副作用靠 task 缓存和幂等键兜底
审批超时 thread 长期停在 interrupt 业务侧维护超时表，到期后 Command(resume=<默认拒绝>) 并通知，不要靠 checkpoint 自己过期
发版后旧 thread 恢复失败 反序列化或节点名找不到 见下方"发版兼容"，用新旧版本并存
checkpoint 表膨胀 查询变慢、磁盘涨 定时清理已完成 thread，保留审计需要的天数
重复副作用 同一封邮件发了两次 查该节点是否在 interrupt() 之前做了副作用，或没用幂等键

发版兼容

Anthropic 工程博客（📄 一手）描述了多 Agent 研究系统的做法：Agent 可能处在流程任意阶段，不能同时更新所有实例，所以用彩虹部署（逐步切流量，新旧版本并存运行）；另外他们实现了断点续跑，出错时从出错处恢复而不是从头重启，并结合重试逻辑和定期检查点。

对 LangGraph 的启示是（以下为本文推断）：checkpoint 保存的是旧版本 state 和"下一个节点名"。挂起中的 thread 恢复时用的是新代码，所以：

  1. 不要重命名或删除可能有挂起 thread 的节点。
  2. state 只加字段不改类型，新字段给默认值。
  3. 确需破坏性改动时，让旧 thread 在旧版本上跑完，新 thread 走新版本。

8. 对本库的落地启示

  • 本库 shared-tasks.db 以 task_id 为 thread_id 的设计与 LangGraph 的 thread 概念对齐，是对的。若迁移到 PostgresSaver，thread_id 沿用 task_id 并保持在 255 字符内。
  • OC 审查、人工验收这类环节是天然的 interrupt() 点。注意第 3.2 节：审查节点里不要在 interrupt() 之前写回台账或发通知。
  • receipt verify 只能跑一次、重跑会误判的血坑（见 CLAUDE.md 附注），本质上就是"副作用节点不幂等"。按本篇做法，把"写基线"拆成独立节点加幂等键，可以从结构上消除。
  • 以上是对照分析，未改造任何现有脚本。
