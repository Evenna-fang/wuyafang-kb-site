多智能体协作流程（编排模式实测 + 落地清单）

← 返回总入口 相关：Agent框架选型 · Agent框架进展 · Agent记忆双进程 · G-Memory共享记忆

同主题去重导航（4 篇分工）：本篇=最权威（编排模式实测 + 落地教训）；多智能体（六员）高阶玩法与并行调度=编排原语与并行调度引擎；六员配置终局=角色/模型/预算配置；六员通道与派单监督-一手=通道实测与派单监督。

核心结论

六员协作的默认骨架是 orchestrator-worker + 步骤间自动校验 + 独立 LLM 评审层（OpenClaw）+ 确定性终门。实测三种编排模式都能跑通；最重要的反模式纪律是"先试单 Agent 再拆"——简单任务拆多 Agent 是 N 倍 API 成本换不来收益。

关键细节

三种编排模式实测（同一任务：查 RAG 索引状态）

编排原语（Kanban Swarm / Goals / Loops / MoA）与并行调度引擎全量细节详见 多智能体（六员）高阶玩法与并行调度篇（本节只讲三模式实测对比与落地教训）。

模式 流程 适用
Pipeline Hermes→DSH执行→OC审 线性流水线、需要逐步校验
Fan-out（并行） 同一题派多个 worker 并行 可并行拆解、上下文装不下
Debate（辩论） Claude+Codex 独立作答→OC 对比归并 选型/架构/排障方向这类高风险决策

四条落地教训（来自 arXiv 12 篇核心论文对照）

  1. 通信结构化：派单 context 用 JSON 契约（需求/输入/输出格式/验收），不写散文——消息体曾占 token 预算 40–60%，结构化后 3.2× 压缩不掉点。
  2. 先试单 Agent 再拆：派单前先问"单 Agent 能不能干"，能就不拆。
  3. 失败先归因再反思：先定位 decisive error 是哪一步向下游传的错，只让那个反思（pre-hoc 上游筛查比事后救火便宜 65×）。
  4. 共享记忆来源 gating：RAG 无差别照收会让假信念被下游 97–99% 采信，进库要过来源门。

全局体检结论

15 个协作技能曾过量未收敛（职责重叠 3 组、硬矛盾 4 组、触发词撞车 3 处），最大缺口不是内容缺失而是分发链断裂（规则只写在 Hermes 真源，六员读不到）。
