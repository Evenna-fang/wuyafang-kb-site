OpenClaw 模块协同（深挖整合）

导读

本文把 OpenClaw 的四个核心模块（Routing 路由、Memory RAG 记忆检索、Sandbox 沙箱、Subagent 子代理）和一份端到端协同流程图合并为一篇。模块章节讲各自的机制，横切章节把配置项、Prometheus 指标和错误码放到同一张表里对照。

核心结论：

  1. Routing 是任务进入平台后的第一道决策点。它把 Task 拆成 Job，为每个 Job 选择 Target，并标记 rag.enabled 与 sandbox 等属性，决定后续走哪条路径。
  2. Sandbox 是子代理执行的必经环境。命名空间、cgroup 配额、chroot 文件系统根限定、seccomp 系统调用过滤、iptables 域名白名单共同限制子代理的资源、文件和网络。
  3. Subagent 的生命周期可以用 7 个状态描述：Pending、Spawning、Running、Succeeded、Failed、Timeout、Recycled。失败或超时的任务按 maxRetries 重试，重试耗尽后回收。
  4. Memory RAG 用 Chroma 存文档向量，用 SQLite 存时序记忆，两者在生成前融合成 Prompt。子代理的输出写回 subagent_history 表，Routing 再读取它做复用、重试或升级，从而形成闭环。
  5. 错误码（SBOX001 至 SBOX004、SUB001 至 SUB004）和 Prometheus 指标分别对应不同的排查入口。源材料中有若干处数值和命名前后不一致，已在第八节列出，使用前需要核对。

一、整体架构与模块职责

1.1 三层视角

OpenClaw 的 Routing、Memory RAG、Sandbox、Subagent 四个模块位于用户请求入口与底层执行环境之间。用户通过 OpenClaw CLI、API 或 UI 提交 Task，Gateway 接收后交给 Routing。Routing 决定任务怎样拆分、去哪里执行、是否需要检索上下文。执行结果经过 Subagent Manager 与 Sandbox 回到 Memory RAG，最后由 Gateway 返回给用户。

1.3 模块间的标记传递

模块之间主要通过属性标记传递决策。Routing 为子任务写入 rag.enabled=true，Memory RAG 据此参与生成。Routing 为需要隔离执行的任务写入 sandbox=true，Sandbox 据此启用隔离。Routing 或 Subagent 的配置决定 runtime（Codex、OpenClaw、Custom）与 priority。下一章起各模块的细节展开说明这些标记。

二、Routing：任务路由

2.1 背景与设计目标

OpenClaw 作为多智能体协同平台的核心组件之一，承担任务分发与路由调度的职责。它位于用户请求入口与具体执行子代理之间，负责把高层业务需求划分为可由各子代理执行的子任务。它还要根据策略把这些子任务路由到合适的执行环境，包括本地进程、容器、远程服务等。

Routing 有三个设计目标：

  1. 高可用：路由层必须在 Gateway 异常、子代理崩溃时仍能提供降级路径；
  2. 可扩展：支持插件化的路由策略，能够随时接入新型调度器，例如 K8s 调度、云函数等；
  3. 可观测：提供完整的路由日志与监控指标，便于运维排障。

2.2 关键概念

  • Task（任务）：用户通过 OpenClaw CLI 或 API 发送的原始请求。
  • Job（作业）：Task 在内部拆解后的最小执行单元，包含 job_id、payload、deadline、priority 等字段。
  • Router（路由器）：实现 route(job) -> target 接口的组件。默认实现为 RoundRobinRouter，可通过 router.custom 配置自定义实现。
  • Target（目标）：具体的执行环境描述，例如 {type:"local", runtime:"codex"}、{type:"container", image:"openclaw/agent:2026.9"}。

2.3 路由流程

Dispatch 函数的伪代码分三步：拆分 Task，为每个 Job 选择 Target，把 Job 写入调度队列。

func Dispatch(task Task) []Job {
    // 1️⃣ 将原始任务拆分
    jobs := splitTask(task)
    // 2️⃣ 为每个 Job 选择目标
    for i, job := range jobs {
        target := router.Route(job)
        jobs[i].Target = target
    }
    // 3️⃣ 将 Job 写入调度队列
    queue.Enqueue(jobs)
    return jobs
}

2.4 拆分策略

Routing 支持三种拆分策略，按任务的输入形态选择：

  • 命令式拆分：基于正则或关键词匹配，将复合指令拆成多个子指令；
  • 结构化拆分：如果 Task 中提供了 JSON 或 YAML 结构，则直接映射为多个 Job；
  • AI 辅助拆分：当任务含有自然语言描述时，OpenClaw 会调用内部 Agent（如 Claude）进行意图解析，并返回拆分方案。

三种策略对应三类输入：命令式拆分处理复合指令，结构化拆分处理带 JSON 或 YAML 结构的 Task，AI 辅助拆分处理自然语言描述的 Task。

2.5 路由配置

路由配置位于 openclaw.json 的 routing 节点下：

{
  "routing": {
    "defaultRouter": "roundRobin",
    "routers": {
      "roundRobin": {
        "type": "builtin",
        "maxConcurrency": 32
      },
      "priority": {
        "type": "builtin",
        "policy": "priorityQueue",
        "preemptive": true
      },
      "k8s": {
        "type": "plugin",
        "pluginPath": "~/openclaw/plugins/k8s-router.so",
        "namespace": "openclaw",
        "maxPods": 64
      }
    }
  }
}
  • defaultRouter 决定默认使用的路由器；
  • maxConcurrency 控制同一目标的并发上限，防止资源争用。

三个路由器的差异体现在 type 与 policy 上。roundRobin 与 priority 是内置实现，k8s 是插件实现，需要 pluginPath 指向可执行的共享库。priority 路由器启用了 priorityQueue 策略和抢占（preemptive: true）。

2.6 故障恢复

Routing 层有三种故障恢复机制：

  1. 目标不可用：路由器在发现 target.health==false 时，会自动降级至 fallbackTarget（默认本地 Runtime）；
  2. 作业超时：若 job.deadline 超过 target.timeout，调度器会重新分配至 backupTarget 并记录 retryCount；
  3. 幂等保证：所有 Job 必须实现幂等 ID（job_id），路由层在重复投递时会检测已有记录并直接返回成功响应，避免业务层面重复执行。

图：Routing 故障恢复流程（幂等，降级，改派）

flowchart TD
    J["Job 到达路由层"] --> DUP{"job_id 已存在"}
    DUP -->|"是"| RET["直接返回已有结果 幂等"]
    DUP -->|"否"| H{"target.health"}
    H -->|"异常"| FB["降级到 fallbackTarget 默认本地 Runtime"]
    H -->|"正常"| EXE["投递执行"]
    FB --> EXE
    EXE --> TO{"deadline 超过 target.timeout"}
    TO -->|"是"| BK["改派 backupTarget 并记录 retryCount"]
    TO -->|"否"| OK["完成"]
    BK --> EXE

2.7 路由监控与坑点

路由相关的 Prometheus 指标有三个：openclaw_router_jobs_total{router="roundRobin"} 统计已调度的作业总数，openclaw_router_job_latency_seconds{router="priority"} 统计作业路由延迟，openclaw_router_target_active{target="local"} 统计当前活跃目标数量。

日志为 JSON 格式，示例如下：

{"time":"2026-10-30T12:34:56Z","level":"INFO","msg":"job routed","job_id":"c7f9a1","router":"priority","target":"container","latency_ms":12}

常见坑点有三个：

  • 插件路径错误：router.k8s.pluginPath 必须是绝对路径且文件可执行，否则路由器启动失败，Gateway 会报 Plugin load error；
  • 并发阈值过低：默认 maxConcurrency=32 在高负载场景会成为瓶颈，需要根据业务峰值调高；
  • 日志噪声：开启 debug 模式会产生大量 job routed 日志，建议在生产环境关闭 debug。

三、Sandbox：沙箱隔离

3.1 沙箱的定位

在开放式 AI 平台中，安全与可控是最关键的运营指标。OpenClaw 通过 Sandbox 为每一次子代理（Sub-agent）的执行提供进程级别的资源隔离与 IO 沙箱，防止恶意代码、无限循环或资源泄露影响主系统。

Sandbox 同时兼顾两个目标。一是低延迟，对即时任务快速响应；二是高可配置，支持容器、虚拟机、用户命名空间等多种后端。

3.2 核心特性

特性 说明
进程隔离 每个子任务在独立的 Linux 命名空间（pid、net、mnt）中运行，使用 unshare 与 cgroups 限制 CPU、内存、IO。
文件系统根限定 通过 chroot 将可见文件系统限制在 /home/wuyafang/.openclaw/sandbox_root，防止子代理读取系统敏感文件。
网络白名单 支持 iptables 规则，仅允许访问白名单域名（如 api.openai.com、*.bailian.aliyun.com），默认阻断所有外网。
资源配额 cpu_quota=200%、memory_limit=512Mi、pids_limit=64，可在配置中自行调整。
审计日志 每一次执行产生 sandbox_audit.log，记录 pid、uid、resource usage、exit_code、stderr 与 stdout。
快速回滚 运行结束后自动 umount、delete 临时挂载点，确保无残留文件。

3.3 多层隔离架构

Sandbox 的隔离由内到外逐层限制。子代理进程先受命名空间隔离，再受 cgroup 配额约束，然后被 chroot 限定文件系统，之后经过 seccomp 与 AppArmor 过滤系统调用，网络层由 iptables 白名单控制，最外层由 auditd 与审计日志记录全部行为。

图：Sandbox 多层隔离架构（由内到外逐层限制）

flowchart TB
    SUB["Sub-agent 进程"] --> NS["命名空间隔离 pid net mnt"]
    NS --> CG["cgroup 配额 cpu 200 percent 内存 512Mi pids 64"]
    CG --> FS["chroot 限定 sandbox_root"]
    FS --> SEC["seccomp 与 AppArmor 系统调用过滤"]
    SEC --> NET["iptables 域名白名单"]
    NET --> AUD["auditd 与 sandbox_audit.log 审计"]
    AUD --> OUT["stdout stderr 写入 Memory RAG"]

3.4 工作流程

Sandbox 的工作流程由下面的时序图表示。

flowchart LR
    A[Routing] --> B[Sandbox Manager]
    B --> C[Create Namespace]
    C --> D[Copy Exec Binary]
    D --> E[Run Sub‑agent]
    E --> F[Collect Output]
    F --> G[Write to Memory RAG]
    G --> H[Return Result]

按步骤说明：

  1. Routing 把子任务交给 Sandbox Manager；
  2. Sandbox Manager 根据配置创建 cgroup 与 namespace；
  3. 将可执行文件（openclaw-agent、python、node）拷贝至沙箱根目录；
  4. 通过 unshare --mount --uts --ipc --net --pid 启动子进程；
  5. 子进程完成后，Sandbox Manager 收集 stdout 与 stderr，写入 Memory RAG 供后续子代理使用。

3.5 配置

Sandbox 配置位于 openclaw.json 的 sandbox 节点：

{
  "sandbox": {
    "enabled": true,
    "rootPath": "~/openclaw/sandbox_root",
    "cpuQuota": "200%",
    "memoryLimit": "512Mi",
    "pidsLimit": 64,
    "networkWhitelist": [
      "api.openai.com",
      "*.bailian.aliyun.com"
    ],
    "auditLog": "~/openclaw/logs/sandbox_audit.log"
  }
}
  • rootPath 必须在用户可写的目录下；首次运行时会自动 mkdir -p 并 chmod 700；
  • networkWhitelist 支持通配符，内部使用 iptables -d 实现。

3.6 安全加固

Sandbox 在默认隔离之上有四项加固措施：

  1. Seccomp 过滤：默认禁用 fork、execveat、ptrace 等危险系统调用；需要额外二进制时可在 sandbox.seccompProfile 中白名单；
  2. AppArmor（如系统支持）可在 /etc/apparmor.d/openclaw-sandbox 中添加 profile；
  3. 透明日志：auditd 记录所有 execve、open 系统调用；
  4. 资源泄漏检测：监控 cgroup.memory.max_usage_in_bytes 与 cpu.stat，若超过阈值则自动 kill 子进程。

3.7 沙箱错误码

Sandbox 的错误码为 SBOX001 至 SBOX004：

错误码 含义 可能原因 解决方案
SBOX001 创建 Namespace 失败 unshare 权限不足（需要 CAP_SYS_ADMIN） 检查用户是否在 docker 或 unprivileged 组；若在 WSL，确认 kernel.unprivileged_userns_clone=1 已启用。
SBOX002 文件系统访问受限 chroot 路径缺失或权限不足 确认 sandbox.rootPath 已存在且 chmod 700。
SBOX003 网络被阻断 目标域名未在白名单 将域名加入 sandbox.networkWhitelist 并执行 openclaw sandbox reload。
SBOX004 资源超限 CPU 或 Memory 超出配额 调整 sandbox.cpuQuota、sandbox.memoryLimit，或优化子任务代码。

图：Sandbox 错误码判定路径

    S["启动沙箱"] --> A{"创建 Namespace"}
    A -->|"失败"| E1["SBOX001 检查 CAP_SYS_ADMIN 与 userns 开关"]
    A -->|"成功"| B{"挂载 chroot 根目录"}
    B -->|"失败"| E2["SBOX002 检查 rootPath 与权限 700"]
    B -->|"成功"| C{"运行中访问网络"}

3.8 实战案例：安全调用第三方 API

下面的命令在隔离环境中调用第三方 API：

openclaw agent exec '调用 https://api.openai.com/v1/chat/completions' \
    --model deepseek/deepseek-v4-pro \
    --sandbox true \
    --timeout 120
  • 通过 --sandbox true 强制在隔离环境中执行；
  • 请求仅能访问 api.openai.com（已在白名单），若代码尝试访问其他域名会返回 SBOX003 错误。

四、Subagent：子代理调度

4.1 什么是 Subagent

在 OpenClaw 中，Subagent 是指由主 Agent（Gateway）派生的、具备独立运行环境的子任务执行体。它们可以是以下三类：

  • 语言模型实例，如 Claude、DeepSeek、OpenAI；
  • 脚本执行器，如 Python、Node、Shell；
  • 外部服务代理，如调用内部微服务、数据库、HTTP API。

Subagent 的目标是实现业务细化。它把一个大任务拆解成若干细粒度子任务，每个子任务交给最适合的执行单元，从而提升整体吞吐与可靠性。

4.2 生命周期

Subagent 的生命周期分四步。

+-------------------+      +----------------------+      +-------------------+
|   Routing 层      | ---> | Subagent Manager     | ---> |  Subagent 实例   |
+-------------------+      +----------------------+      +-------------------+
          |                         |                         |
          v                         v                         v
    调度决策                资源分配                执行/返回
  1. 调度决策（Routing）为每个子任务决定 runtime、sandbox、priority 等属性；
  2. 资源分配（Subagent Manager）为每个 Subagent 分配 cgroup、namespace、网络配额，并记录 subagent_id；
  3. 执行：Subagent 在 Sandbox 中启动，完成任务后将结果、状态、日志写回 Memory RAG；
  4. 回收：Manager 根据 ttl 以及 exit_code 自动回收容器或进程。

图：Subagent 生命周期状态机

stateDiagram-v2
    [*] --> Pending
    Pending: 排队中 等待资源
    Pending --> Spawning: 分配 cgroup 与 namespace
    Spawning: 创建中
    Spawning --> Running: 启动成功
    Spawning --> Failed: SUB001 启动失败
    Running: 执行中
    Running --> Succeeded: exit_code 为 0
    Running --> Failed: 非零退出
    Running --> Timeout: 超过 timeoutSeconds
    Timeout --> Pending: retryCount 小于 maxRetries
    Failed --> Pending: retryCount 小于 maxRetries
    Timeout --> Recycled: 重试耗尽 SUB004
    Failed --> Recycled: 重试耗尽
    Succeeded --> Recycled: 结果写回 Memory RAG
    Recycled --> [*]

状态机的 7 个状态及其含义如下：

状态 含义 进入条件 离开条件
Pending 排队中，等待资源 任务进入调度 分配 cgroup 与 namespace
Spawning 创建中 资源已分配 启动成功进入 Running，启动失败进入 Failed（SUB001）
Running 执行中 启动成功 exit_code 为 0 进入 Succeeded，非零进入 Failed，超过 timeoutSeconds 进入 Timeout
Succeeded 执行成功 exit_code 为 0 结果写回 Memory RAG 后进入 Recycled
Failed 执行失败 启动失败或非零退出 retryCount 小于 maxRetries 时回到 Pending，否则进入 Recycled
Timeout 执行超时 超过 timeoutSeconds retryCount 小于 maxRetries 时回到 Pending，否则进入 Recycled（SUB004）
Recycled 已回收 重试耗尽或执行成功后 终态

4.3 配置模型

Subagent 的配置位于 openclaw.json 的 subagents 节点：

{
  "subagents": {
    "defaults": {
      "runtime": "codex",          // 可选：codex、openclaw、custom
      "sandbox": true,
      "timeoutSeconds": 180,
      "maxRetries": 2,
      "priority": "normal"
    },
    "overrides": {
      "rag": {
        "runtime": "openclaw",
        "sandbox": false,
        "timeoutSeconds": 300
      },
      "highPriority": {
        "priority": "high",
        "cpuQuota": "400%"
      }
    }
  }
}
  • defaults 为全局默认值；
  • overrides 按标签（如 rag、highPriority）自定义；
  • runtime 决定使用哪种 Agent Harness（Codex、OpenClaw、Claude Code）。

配置中有几个字段需要区分。timeoutSeconds 与 maxRetries 决定状态机中 Timeout 与 Failed 状态的重试次数。sandbox 决定子代理是否进入 Sandbox。overrides 中 rag 标签的子代理设置了 sandbox=false，与 defaults 的 sandbox=true 相反，这一点在第八节列为待核对项。

4.4 三种运行方式

Subagent 有三种运行方式，对应三类 runtime。

1. Codex Runtime

openclaw agent exec '生成 Python 代码' \
    --model xiaomimimo/mimo-v2.6-pro \
    --runtime codex \
    --sandbox true
  • Codex 通过内部插件 codex 与 OpenClaw 交互，返回代码片段并自动写入 ~/openclaw/tmp/；
  • 结果会被 Sandbox 包装，防止恶意代码直接访问系统。

2. OpenClaw Runtime（内置 LLM）

openclaw subagent run \
    --task-id 0x1a2b3c \
    --payload '{"action":"summarize","text":"..."}'
  • OpenClaw 自带的轻量 LLM（默认 deepseek-v4-pro）用于低延迟的短文本处理；
  • subagent_id 自动生成，日志中可追踪 subagent_id 与 task_id 的对应关系。

3. 自定义 Runtime（插件）

openclaw plugins enable my_custom_agent --accept-capabilities
openclaw subagent run --runtime my_custom_agent --payload ...
  • 插件提供自定义入口，例如调用内部微服务或运行 Rust 二进制，需要在 plugins.load.extraDirs 中声明路径。

按源材料的描述，Codex 的结果由 Sandbox 包装，OpenClaw Runtime 的业务代码在 Sandbox 中执行。Custom Runtime 是否经过 Sandbox，源材料未明确说明，实际是否隔离由 sandbox 配置决定。

4.5 结果回流至 Memory RAG

子代理完成后，Subagent Manager 会调用 MemoryRAG.append_history，把结果写入 SQLite 表 subagent_history，结构如下：

字段 类型 说明

task_id TEXT 任务标识，用于幂等检查
status TEXT success、error 或 timeout
output TEXT 子代理输出
stderr TEXT 标准错误输出
timestamp INTEGER 时间戳
resource_usage JSON 资源用量

示例记录：

{"subagent_id":"sub-20261030-001","task_id":"0x1a2b","status":"success","output":"生成的 Python 代码...","stderr":"","timestamp":1730304001,"resource_usage":{"cpu_ms":124,"mem_kb":3124}}

后续的 Routing 或 Memory RAG 在需要时可以直接查询此表，完成状态闭环与结果复用，例如缓存同类任务的输出。

4.6 资源池与调度

OpenClaw 支持两类资源池：

  1. 本地进程池（默认）：直接在本机创建 cgroup，适用于低延迟的轻任务；
  2. 容器池：基于 Docker（或 Podman）启动轻量容器 openclaw/agent:<runtime>，适用于需要特定运行时（如 Node、Java）的任务。

动态伸缩通过 SubagentPool 实现：

from openclaw.subagent import SubagentPool
pool = SubagentPool()
# 根据当前负载自动扩容至 16 实例
pool.scale(target=16)
# 运行任务
result = pool.run(task_id="0xdeadbeef", payload={"action":"scrape","url":"https://example.com"})
print(result.output)

资源池选择的依据是任务的标签。实践建议中提到，任务 payload 可以带 tags，例如 {"tags":["highPriority","ioBound"]}，由 Subagent Manager 据此选取资源池。

4.7 Subagent 故障码

Subagent 的错误码为 SUB001 至 SUB004：

错误码 含义 可能原因 解决办法
SUB001 子代理启动失败 unshare 权限缺失、cgroup 配置错误 确认用户在 unprivileged_userns_clone=1（WSL）或 docker 组；检查 /etc/cgconfig.conf 是否启用 cpu,memory 控制器。
SUB002 沙箱内网络不可达 域名未加入白名单 更新 sandbox.networkWhitelist 并执行 openclaw sandbox reload。
SUB003 结果写入 Memory RAG 失败 SQLite 锁冲突或磁盘满 查看 openclaw memory status；若锁冲突，执行 openclaw memory reset --mode sqlite。
SUB004 超时 timeoutSeconds 设得过低 根据任务复杂度调高，例如 --timeout 300。

4.8 实践建议

  1. 标签化：在任务 payload 中加入 tags，让 Subagent Manager 根据标签选取合适的资源池；
  2. 幂等设计：子任务必须使用唯一 task_id，子代理在异常重试时应检查历史，避免重复写入导致业务重复；
  3. 日志统一：所有 Subagent 的 stdout 与 stderr 必须统一写入 sandbox_audit.log，并在 Memory RAG 中保存 log_snapshot，便于事后审计；
  4. 监控阈值：生产环境建议 cpuQuota 不超过 300%、memoryLimit 不超过 1Gi，以免单个子代理耗尽节点资源。

五、Memory RAG：Chroma 与 SQLite 的融合

5.1 为什么需要 Memory RAG

在多智能体系统中，记忆（Memory）用于保存上下文、历史对话与业务状态，检索（Retrieval）负责快速定位相关信息。单独的记忆或检索往往不足以满足复杂业务需求：

  • 记忆的线性增长导致查询效率下降；
  • 检索只能返回文档片段，缺少业务状态的时序关联。

Memory RAG（Retrieval-Augmented Generation）将两者融合。它先通过向量检索定位相关文档，再在记忆库中补充时序状态，实现上下文感知的生成，从而提升回答的准确性与一致性。

5.2 两个存储的分工

维度 Chroma 向量检索引擎 SQLite 时序记忆数据库
存储内容 文档向量 每次 Agent 调用的输入、输出、状态与时间戳，使用 JSON 列
检索方式 Hybrid（dense 加 sparse），返回 Top-k 片段 按 session_id、task_type 等条件查询
可替代实现 Zilliz 无
配置键 memory.rag.vectorStore memory.rag.temporalStore
嵌入模型 bge-m3（embeddingModel） 不涉及
数据保留 未说明 purgeAfterDays: 180

向量库回答“哪些文档和问题相关”，时序库回答“这个会话之前发生过什么”。两者合在一起，生成阶段既有语义依据，也有状态连续性。

5.3 RAG 流程

RAG 流程分五步：

  1. Chunk 化：用户请求先进行语义 Chunk；
  2. 向量检索：返回候选文档片段；
  3. 记忆筛选：在 SQLite 中检索符合 session_id、task_type 的历史记录；
  4. 融合：把检索到的文档与时序记忆拼接为 Prompt；
  5. 生成：交给模型（Claude、OpenAI、DeepSeek）生成答案。

图：Memory RAG 查询数据流

sequenceDiagram
    participant R as Routing
    participant M as MemoryRAG
    participant V as Chroma 向量库
    participant T as SQLite 时序记忆
    participant L as 模型
    R->>M: 子任务 rag.enabled 为 true
    M->>M: 语义 Chunk 化
    M->>V: 向量检索 topK
    V-->>M: 候选文档片段
    M->>T: 按 session_id 与 task_type 查询
    T-->>M: 历史状态记录
    M->>M: 融合 concat 或 weighted 或 rerank
    M->>L: 富上下文 Prompt
    L-->>M: 生成答案
    M->>T: 写回本次输入输出与时间戳
    M-->>R: 返回答案

5.4 关键配置与融合策略

配置位于 openclaw.json 的 memory.rag 节点：

{
  "memory": {
    "rag": {
      "enabled": true,
      "vectorStore": {
        "type": "chroma",
        "path": "~/openclaw/data/chroma",
        "embeddingModel": "bge-m3",
        "topK": 8
      },
      "temporalStore": {
        "type": "sqlite",
        "path": "~/openclaw/data/memory.sqlite",
        "purgeAfterDays": 180
      },
      "fusionStrategy": "concat",   // concat | weighted | rerank
      "weights": {
        "vector": 0.6,
        "temporal": 0.4
      }
    }
  }
}
  • topK 控制检索返回数量；
  • fusionStrategy 支持三种取值：concat 直接拼接，weighted 加权融合（在生成前对每段打分），rerank 调用二次检索模型进行排序。

三种融合策略对比如下：

策略 做法 配置依赖 适用场景（源材料描述）
concat 直接拼接向量片段与时序记录 无 配置默认值，源材料未给出适用场景
weighted 生成前对每段打分，按 weights 中 vector（0.6）与 temporal（0.4）加权 weights 融合 Prompt 超长时的降级选择
rerank 调用二次检索模型排序 bge-reranker 检索片段噪声大导致幻觉时启用

5.5 动态查询示例

Python 示例展示 MemoryRAG.build_prompt 的调用方式：

from openclaw.rag import MemoryRAG

rag = MemoryRAG()
prompt = rag.build_prompt(
    user_query="本月的用户活跃度下降原因是什么？",
    session_id="sess-20261001",
    task_type="analysis"
)
# prompt 已经包含向量检索结果 + 时序记忆
print(prompt)

输出示例（截取）：

[向量检索] 文档片段1: “… 2026 年 9 月用户活跃度下降 12% …”
[时序记忆] 2026‑09‑01 10:12:34 - 生成日报 – 活跃度 78% → 70%
[时序记忆] 2026‑09‑02 09:45:12 - 部署新功能 – “社交分享”导致活跃度波动
---
请基于以上信息回答用户问题。

输出中向量检索的结果和时序记忆分属两个前缀，说明融合后两类信息在 Prompt 中是并列出现的。

5.6 失效检测与恢复

Memory RAG 有三类失效场景，每类有对应的恢复命令：

  1. 向量库损坏：chroma check --path … 若返回错误，执行 chroma rebuild 并从备份恢复；
  2. 时序记忆库锁死：SQLite 锁超时时，openclaw memory reset --mode sqlite 会自动切换到 WAL 模式并进行 VACUUM；
  3. 检索准确率下降：监控 openclaw rag eval --metric recall，当 Recall 低于 0.7 时自动提示重新 embeddings（openclaw rag reembed）。

    Q -->|"向量库 check 报错"| A2["chroma rebuild 并从备份恢复"]
    Q -->|"SQLite 锁超时"| A3["openclaw memory reset 切换 WAL 并 VACUUM"]

5.7 Memory RAG 监控指标

Memory RAG 的 Prometheus 指标有四个：

  • openclaw_rag_vector_hits_total：向量检索命中次数；
  • openclaw_rag_temporal_hits_total：时序记忆命中次数；
  • openclaw_rag_fusion_latency_seconds：融合构建 Prompt 所用时间；
  • openclaw_rag_query_total{status="error"}：异常查询计数，包括库文件损坏、超时等。

5.8 常见坑点与推荐方案

症状 可能原因 解决方案
检索返回空 向量库未同步，或文档未嵌入 执行 openclaw rag index --path <doc_dir>，并确认 embeddingModel 正常。
时序记忆查询慢 SQLite 未开启 WAL，磁盘 IO 瓶颈 执行 openclaw memory config --sqlite-wal true，或设置 PRAGMA journal_mode=WAL。
融合 Prompt 超长 topK 设得过大，或 fusionStrategy=concat 将 topK 调低至 6，并改为 weighted 融合。
RAG 生成出现幻觉 检索片段噪声大 启用 rerank，并使用 bge-reranker 进行二次过滤。

主链路的 8 个步骤如下：

  1. 用户请求通过 OpenClaw CLI、API 或 UI 进入系统；
  2. Routing 根据任务属性（标签、优先级、是否需要 RAG）决定后续路径；
  3. Memory RAG（若需要）进行向量检索与时序记忆融合，生成富上下文 Prompt；
  4. Subagent 调度根据 Prompt 的 runtime（如 Codex、OpenClaw、Custom）创建对应 Subagent 实例；
  5. Sandbox 为 Subagent 提供进程或容器级别的安全隔离，并限制资源使用与网络访问；
  6. 子代理执行完成业务逻辑（代码生成、API 调用、文档摘要等），输出 stdout 与状态；
  7. 结果写回 Memory RAG，将执行产物、日志、资源使用写入时序记忆，供后续任务或审计使用；
  8. 生成最终答案（可能再次走 RAG 进行二次检索），并通过 OpenClaw Gateway 返回给用户。

6.4 控制面与数据流的对应

控制面（Routing、Subagent Manager）决定做什么，数据面（Chroma、SQLite）保存与检索信息，执行面（Sandbox、子代理）真正运行代码。第一章的分层图给出了三者之间的连接关系：Routing 对向量库与时序库发起查询，对 Subagent Manager 下发属性，Subagent Manager 驱动 Sandbox，子代理把输出与日志写入 SQLite，SQLite 的历史结果再回到 Routing。

6.5 故障回退路径

协同流程图给出了四类故障的回退规则：

  • Routing 失效：使用默认本地 Runtime（OpenClaw）直接执行；
  • RAG 检索为空：直接跳过 RAG，进入 Subagent（纯生成）；
  • Sandbox 资源超限：降级为本地进程（不启用网络隔离），并记录 SBOX004 错误；
  • Subagent 超时：触发重试（最多 maxRetries），若仍失败则返回错误给用户并记录 SUB004。

八、源材料待核对点

以下是源材料内部的不一致或未说明的地方。本文按原文转述，没有擅自改值。使用前需要对照原始配置确认。

  1. 沙箱根路径不一致：第三章特性表写 /home/wuyafang/.openclaw/sandbox_root，配置示例写 ~/openclaw/sandbox_root，两处路径前缀不同。
  2. 资源上限不一致：Sandbox 默认 cpuQuota 为 200%、memoryLimit 为 512Mi。Subagent 生产建议写 cpuQuota 不超过 300%、memoryLimit 不超过 1Gi，但 overrides.highPriority 配置了 cpuQuota 为 400%。
  3. 隔离降级语义冲突：第三章说 Sandbox 默认阻断外网，第六章的回退规则在 Sandbox 超限时降级为“本地进程（不启用网络隔离）”。降级是否允许跳过网络白名单，源材料没有给出判断依据。
  4. Subagent 覆盖配置关闭了 Sandbox：overrides.rag 设置 sandbox=false，而 Subagent 默认值为 sandbox=true。源材料对关闭隔离的条件没有说明。
  5. memory reset 的语义未说明：第五章写 openclaw memory reset --mode sqlite 会切换 WAL 并 VACUUM，第四章的 SUB003 同样使用它处理锁冲突。命令名中含 reset，源材料没有说明它是否清空记录。执行前需要确认。
  6. 指标名不一致：Routing 模块的延迟指标为 openclaw_router_job_latency_seconds，协同流程图使用 openclaw_routing_latency_seconds。openclaw_sandbox_execution_seconds 与 openclaw_response_total 只在协同流程图中出现。
  7. runtime 决策归属：第四章写 runtime 由 Routing 决定，第六章的主链路写 Subagent 调度根据 Prompt 的 runtime 创建实例。两处对 runtime 的决策方归属写法不同。
  8. 示例模型与白名单不匹配：Sandbox 实战案例使用 deepseek/deepseek-v4-pro 模型，但请求的目标是 api.openai.com，白名单中也只有这一个 OpenAI 域名。源材料没有说明 DeepSeek 调用的目标域名是否需要加入白名单。
  9. 数据保留未说明机制：purgeAfterDays: 180 出现在配置中，文中没有说明清理的触发方式与执行者。
  10. 图文件名：协同流程图备注中提到 05_Flowchart.mmd，实际文件名为 05_协同流程图.md。

小结

OpenClaw 的五个模块文件分别讲了四个核心模块和一张端到端流程图。Routing 决定任务的拆分与去向。Sandbox 为每次子代理执行提供命名空间、cgroup、chroot、seccomp 与 iptables 白名单等隔离层。Subagent 通过 7 个状态的生命周期和 maxRetries 管理执行与重试。Memory RAG 用 Chroma 做语义检索，用 SQLite 做时序记忆，并以 concat、weighted、rerank 三种策略融合。四个模块通过 rag.enabled、sandbox、runtime 等标记和 subagent_history 表串成闭环。

排查时可以从症状出发，先定位模块，再对应错误码与 Prometheus 指标。使用配置前，应先核对第八节列出的不一致点。
