L5 Agent 核心循环与业务落地：ReAct、Plan-and-Execute、Reflection 与动手实现

← 返回总入口

导读

这篇文章回答三个问题：Agent 的循环怎么选，一个业务场景怎么变成可落地的 Agent，以及这些循环在代码里长什么样。全文按"原理、方法、代码"的顺序展开，同一个概念只在一处讲透，其余地方用链接指回。

核心结论有四条：

  1. 循环按任务复杂度分层，不分先进与落后。 ReAct 适合短任务和路径不明的任务，Plan-and-Execute 适合步骤多且可分解的任务，Reflection 用来补产出质量。三者可以叠加使用。
  2. 默认先上 ReAct，遇到跑偏再加 Planner，产出不满意再加 Reflection。 这个顺序的成本最低，也最容易排查问题。
  3. 能落地的 Agent 是某个具体痛点的数字员工。 它需要一个重复劳动、一个可验证的输出，以及一个能被工具化的数据源。7 本书里所有成功案例都是单一痛点，没有一个是"通用助手"。
  4. 动手时按课件顺序推进：先搭 HTTP 外壳，再接检索和工具，最后加推理模式。 课件代码按 FastAPI、LlamaIndex、LangChain 的顺序组织。

框架选型、低代码平台的边界、工具协议、记忆设计、多 Agent 编排和生产化要求分属其他文章。本文只在需要时用一句话指向它们，相关链接见文末。

一、循环模式与选型

1.1 三种循环的节奏与适用边界

Agent 的核心是"LLM 在循环里根据环境反馈调用工具"。循环的形态决定了 Agent 每一步怎么想、怎么做、什么时候停。下表列出三种最常见的循环，以及它们各自适合和不适合的任务。

循环 核心节奏 适合的任务 不适合的任务
ReAct 观察、思考、行动、再观察，循环到结束 步骤不超过 5 步、路径不明确、需要边走边看 步骤多、要全局最优、容易跑偏的长任务
Plan-and-Execute 先一次性拆解成 N 步计划，再逐步执行 任务清晰、步骤不少于 5 步、可分解（库存调度、标书阅读） 路径高度不确定，计划做了也白做
Reflection / Introspection 产出、自我批判、修订 对质量要求高的任务（代码、文案、法律文书） 低成本、高并发的任务，因为反思本身很贵

三种循环的差别在于"什么时候做决定"。ReAct 每一步都重新决定下一步动作，决定是在看到结果之后做出的。Plan-and-Execute 在开始时就把整条路径定下来，之后按计划执行。Reflection 不关心路径，只关心产出过不过关。因此，三者解决的是不同层面的问题，不构成互相替代的关系。

1.2 判断口诀与叠加方式

选循环时可以记一句口诀：默认先上 ReAct，跑偏了加 Planner，产出不满意加 Reflection。

三层可以叠加使用。Plan-and-Execute 的每一步内部本身就是一个 ReAct 循环，最终产出还可以再过一遍 Reflection。

1.3 ReAct：边想边干

ReAct 是最经典的 Agent 循环。它的设计哲学来自《动手做 AI Agent》（黄佳）引述的原话："在动态和不确定的环境中，有效的决策需要持续的学习和适应，以及快速将推理转化为行动的能力，即形成有效的观察—思考—行动—再观察的循环。"

《动手做 AI Agent》第 6 章直接用 LangChain 的 create_react_agent 跑了鲜花定价的案例。《大模型项目实战》（高强文）基于 AgentScope 的 ReAct Agent 也是同一套结构：UserAgent 接收任务，ReActAgent 做 Reason-Acting 迭代。两本书用的框架不同，循环结构相同，说明 ReAct 已经是教材级的标准件。

ReAct 有两个主要的坑。

  • 步数不可控。 模型可能在第 10 步还在原地打转。因此必须设置 max_iterations。最佳答案给出的经验值是长任务一般设为 10 到 20 步。
  • 计划视野短。 ReAct 不看全局，容易走偏。所以它只适合"边走边看"的活，不适合需要全局规划的长任务。

1.4 Plan-and-Execute：先想清楚再动手

Plan-and-Execute 的标准样例见《动手做 AI Agent》第 7 章，案例是物流管理和库存调度。它由三个角色组成。

  1. Planner 一次性把任务拆成 N 步，输出结构化的计划。
  2. Executor 逐步执行计划，每一步本身是一个小的 ReAct 循环。
  3. Replanner 可选。执行完几步后回头看剩余计划是否需要调整。

《大模型项目实战》里的 BabyAGI 是这个范式的极简原型。它"根据先前任务的结果和预定义的目标创建任务"，并用向量库存放任务上下文。原书评价它"代码量虽小，但方法论起了意想不到的效果"。

这种循环适合任务可以分解、步骤多、路径可预期的场景。发票识别、标书阅读、库存调度都属于这一类。

它不适合任务本身就模糊的场景。比如"帮我调研一下竞品"这种需求，Planner 第一次拆出来的步骤很可能就是错的，计划做了也白做。这时应该先用 ReAct 把问题澄清，再考虑规划。

1.5 Reflection：给自己挑毛病

《Building Agentic AI Systems》第 4 章专门讲了 Reflection and Introspection。它的核心做法是：Agent 产出结果后，让另一个 LLM 调用对产出做批判，例如"这个定价合理吗？数据来源可靠吗？"。批评意见再交还给原 Agent，让它修订。

Reflection 的几个典型场景如下。

  • 代码生成。 写完代码后跑一下测试，测试不过就进入反思。
  • 文案生成。 写完后让 Critic 打分，分数不够就修改。
  • 个性化推荐。 《Building Agentic AI Systems》提到"反思型代理"可以用于营销推荐，通过识别"某些类型的推荐总是低分"来调整策略。

Reflection 的代价是贵。如果每一步都反思，token 消耗几乎翻倍。因此，它应该只用在最终产出或关键节点上，不要每一步都做。

1.6 组合：现实中的 Agent 长什么样

现实中的 Agent 很少只用一种循环。《Building Agentic AI Systems》第 6 章提出了 Coordinator-Worker-Delegator 三层编排。

  • Coordinator 接收任务并做规划，相当于 Planner。
  • Delegator 把子任务分派给 Worker。
  • Worker 具体执行，内部是 ReAct 循环。

在关键节点再叠加 Reflection，就得到一个可以投入生产的 Agent 骨架。同一本书还提出，高风险任务应该"投入更多计算资源做更深入推理"，也就是按风险自适应地分配算力。

《零基础搭建 Coze+Dify+LangChain》（徐洋）则从另一个角度给出了类似的结论。低代码平台里的"工作流节点"，其实就是 Plan-and-Execute 的可视化版本。每个节点是一步，连线就是执行顺序。

1.7 Agentic RAG 的六种模式

当 Agent 的工具是检索时，循环结构会变成 Agentic RAG。L5 最佳答案列出了六种模式：Router、Agent-as-retriever、CRAG、Self-RAG、Adaptive 和 Agentic-GraphRAG。源文目前只对 CRAG 给出了思路：加一个轻量的检索质量评估组件，自动判断检索质量，并在质量不够时触发 web 搜索兜底。其余五种在源文中只有名称，库里还没有对应的代码模板。

二、循环设计细则

循环设计的核心是给每个循环定义边界，包括何时停止、步数上限、反思次数和失败处理。下面按源文的说法逐条整理。

2.1 终止与步数上限

终止条件分为两类。一类是任务完成，另一类是达到上限。ReAct 循环最需要显式的上限，因为它没有全局计划可以判断是否已经走完。源文给出的经验是长任务设置 max_iterations，一般为 10 到 20 步。

Plan-and-Execute 在执行中途失败时需要处理。课件的说法是每步失败还能 replan，即重新规划剩余步骤，而不是整条计划作废。

2.2 反思的频率与位置

反思是循环里最贵的环节，所以它的位置比它的存在更重要。源文的原则是：只在最终产出或关键节点做反思。每一步都反思，等于每一步的 token 消耗翻倍。

这个原则也适用于代码任务。例如代码写完后跑一次测试，失败时进入一轮反思，而不是在每个函数写完后都做一轮反思。

2.3 Plan-and-Execute 中的重规划

重规划的触发点通常是执行中出现与计划不符的结果。源文没有给出具体的触发阈值，只说明 Replanner 是可选的，执行完几步后回头看剩余计划是否需要调整。因此，重规划的频率需要根据任务本身确定，源文没有给出通用的数字。

2.4 中间件作为循环的守门员

课件把中间件作为在 Agent 循环外围做拦截、审计和注入的机制。LangChain create_agent 支持的钩子有五种，每种对应循环中的一个位置。

  • @before_agent：Agent 启动前，适合做权限、敏感词和上下文注入。
  • @before_model：每次调用 LLM 前，适合做动态系统提示词和上下文压缩。
  • @after_model：LLM 输出后，适合做日志和审计。
  • @wrap_model_call：包住一次 LLM 调用，适合做重试和降级（fallback）。
  • @wrap_tool_call：包住一次工具调用，适合做权限校验和参数清洗。

中间件的好处是不需要改动循环本身。权限和审计逻辑放在钩子里，循环的主流程保持不变。具体代码见第四章。

2.5 循环的状态与恢复

循环中的状态分为两种。一种是会话内的短期状态，按会话 ID 保存。另一种是跨会话的长期状态。课件中 LangChain 的 InMemorySaver 对应短期状态，thread_id 是会话隔离的主键。源文特别提醒，不同用户必须传入不同的 thread_id，否则会话内容会串台。

长期状态的存储和检索属于记忆设计，不在本文展开，见 L5-Agent记忆与自进化-深挖整合.md。

三、业务落地方法

3.1 能落地的与不能落地的

源文用一张表区分了"数字员工"和"玩具"。判断一个场景能不能落地，只需要对照这四条。

能落地（数字员工） 不落地（玩具）
输入是结构化的，例如发票、标书、聊天记录 输入是开放的"帮我想想"
输出可验证，有对错或过不过的判断 输出只能靠主观评价
有现成工具能查到真相，例如 OCR、数据库、API 只能靠模型脑补
人工原本要花 1 小时以上 人工 5 分钟就能完成，Agent 反而更慢

这张表的第四行经常被忽略。如果人工只要几分钟，Agent 调用模型、等待工具和校验结果的时间加起来，往往比人工还慢。落地前应该先算清楚这笔账。

3.2 落地的五步流程

源文跨 7 本书提炼出五步通用流程。

  1. 找痛点。 挑一个"每周重复 3 次以上、单次 30 分钟以上、出错代价高"的工作。《动手做 AI Agent》引用的创业建议是："初期专注特定、小规模业务场景，深入解决具体问题，而不是追求建立大型平台。"
  2. 定输入输出。 明确输入的格式，例如 PDF、Excel 或聊天记录。再明确输出的格式，例如结构化 JSON、卡片或邮件。
  3. 选工具。 区分哪些步骤是 RAG（查知识库），哪些是 FC（调 API），哪些是代码执行（用 Python 算）。
  4. 搭循环。 简单任务用 ReAct，复杂任务用 Plan-and-Execute，需要质量时加 Reflection。
  5. 接日志和回调。 《零基础搭建 Coze+Dify+LangChain》特别强调 LangChain 的回调处理器。它要求把每次用户提问、链的运行状态和模型输出都记录到日志文件，出问题时才能快速定位。源文认为这一步是从 demo 到生产的分水岭。

3.3 常见的失败模式

源文从书里反推出四种常见失败模式。

  • 追求"通用 Agent"。 一个 Bot 什么都能干，结果就是什么都干不好。7 本书所有成功案例都是单一痛点。
  • 跳过 RAG，直接让模型回答。 《零基础搭建》划线统计中，这一条排在第 1 位，有 2379 人同意。书中的观点是，大模型在医疗、法律和企业内部知识等专业领域回答不准，且信息滞后。
  • 不做日志。 用户反馈"回复异常"时，无法定位是哪一步出的问题。这一条和落地第 5 步是同一件事的两面。
  • 忽视数字短板。 《零基础搭建》第 3 章专门讲了 AI 为什么无法准确识别数字、为什么有数学逻辑短板。因此，涉及金额和数量的计算必须交给计算器或代码执行，不能让模型心算。

这四种模式的共同点是把 Agent 当成万能工具使用。业务落地的方法，本质上就是把它拉回到单一痛点、可验证输出和可靠工具上。

3.4 业务案例的分类

源文收集了 7 本书中 20 多个落地案例，并按业务域分成五类。下面的列表保留了每个案例的来源章节，方便回查。

A. 文档与票据处理类（最成熟）

  • 发票识别 Agent（《零基础搭建》第 7 章）：OCR 加字段抽取，再输出结构化结果，即"告别手动录入"。
  • 标书阅读 Agent（第 8 章）：做合规性检查，即"减少标书违规"。
  • 知识问答 Agent（第 9 章）：企业知识库 RAG，即"让知识库活起来"。
  • 财报检索 Agent（《动手做 AI Agent》第 8 章）：LlamaIndex 加 ReAct 的 RAG。

B. 人机交互与陪练类

  • 模拟面试官 Agent（《零基础搭建》第 10 章）：按结构化的面试流程进行。
  • 小学生英语陪练 Agent（第 11 章）：多模态对话加引导逻辑。

C. 信息收集与内容生产类

  • 旅游助手 Agent（第 12 章）：查询航班、酒店和攻略。
  • 抖音、小红书文案提取仿写 Agent（第 13 章）：短链抓取加风格仿写。
  • 新闻播报智能体（第 4 章提到）：通过插件取新闻，再做卡片化输出。

D. 工程与自动化类

  • 创作 PPT Agent（《动手做 AI Agent》第 4 章）：Assistants API 加 DALL·E 3。
  • 鲜花定价 Agent（《动手做 AI Agent》第 6 章）：ReAct 加外部 API 查价格。
  • 库存调度 Agent（《动手做 AI Agent》第 7 章）：Plan-and-Execute。
  • 辅助编程 Agent（《大模型项目实战》第 12 章）：AutoGen 多 Agent。
  • 多智体图像应用（《大模型项目实战》第 15 章）：Qwen-Agent 加 CogVLM2。

E. 企业监控类

  • 运营与财务异常监控（《零基础搭建》划线中提到）：实时监控、发现异常、提醒排查，适用于"财务造假、设备故障、合规风险"。

源文的"最成熟"标注出现在 A 类，理由是这类任务的输入结构化、输出可核对。

3.5 低代码与代码的选型

低代码平台与代码框架的取舍，源文给出了阶段性的判断，具体的阶梯和对比在 Coze-Dify-LangChain边界在哪 中展开。这里只保留落地视角的一条判断：演示和一周内要结果的场景偏向低代码，内网数据不能出域的场景偏向私有化平台，要断点续跑、多 Agent 或深度耦合业务系统的场景偏向代码框架。

class ModelName(str, Enum):
    English = "英语"
    Chinese = "中文"
    French  = "法语"

app = FastAPI()

# 1) 路径参数 + 枚举校验：?model_name=xxx 不在枚举里直接 422
@app.get("/models/{model_name}")
async def get_model(model_name: ModelName):
    if model_name is ModelName.English:
        return {"model_name": model_name, "message": "这是英文"}
    if model_name.value == "中文":
        return {"model_name": model_name, "message": "这是中文"}
    return {"model_name": model_name, "message": "这是法语"}

# 2) 路径参数 + 元数据（Swagger 里会显示 description）
@app.get("/users/{id}")
async def get_user(id: Annotated[int, Path(description="用户id")]):
    return {"id": id, "message": f"这是用户id为{id}的人"}

# 3) 查询参数：有默认值 = Query 参数（?skip=0&limit=5）
fake_items = [{"item_name": n} for n in
              ["苹果","香蕉","橙子","笔记本电脑","无线鼠标"]]

@app.get("/items/")
async def read_item(skip: int = 0,
                    limit: Annotated[int, Query(description="条数")] = 5):
    return fake_items[skip: skip + limit]

if __name__ == "__main__":
    uvicorn.run(app)

这段代码有三个关键点，源文都列为常见坑。

  • 接口匹配是按从上到下的顺序进行的。/root/{id} 必须写在 /root/test 后面，否则 test 会被当作 id 匹配掉。
  • Annotated[int, Path()] 的第一个位置参数必须是类型，元数据跟在后面，不能省略类型。
  • 启动后访问 http://127.0.0.1:8000/docs 即可得到 Swagger UI，这是 FastAPI 免费提供的功能。

4.1.2 Pydantic 请求体校验

下面的代码来自 day01。

from typing import Annotated
import uvicorn
from fastapi import FastAPI, Body
from pydantic import BaseModel, Field

class Item(BaseModel):
    name: str = Field(description="商品名称")
    # 字符串长度约束用 max_length；数值约束用 ge / le / lt / gt
    description: str | None = Field(default=None, description="商品描述", max_length=100)
    price: float = Field(description="商品价格", ge=0, le=5000)
    tax: float | None = None

app = FastAPI()

@app.post("/items/")
async def create_item(item: Annotated[list[Item], Body(embed=True)]):
    item_dict = item[0].model_dump()
    if item[0].tax is not None:
        item_dict["price_with_tax"] = item[0].price + item[0].tax
    return item_dict

if __name__ == "__main__":
    uvicorn.run(app, host="127.0.0.1", port=8000)

参数的使用规则如下。

  • ge=0, le=5000 用于数值范围。字符串应使用 max_length=100、min_length=2 之类的约束，不要混用。
  • Body(embed=True) 表示请求体的形状是 {"item": {...}}。不加 embed 时，请求体直接就是对象本身。批量接收列表时经常踩到这个坑。
  • model_dump() 把 Pydantic 对象转成字典，这是新版本的写法，dict() 已经被标记为弃用。

4.1.3 文件上传接口

下面的代码来自 day01，给出了两种读取方式。

import uvicorn
from fastapi import FastAPI, File, UploadFile

app = FastAPI()

# 方式 A：bytes 一次性读进内存（小文件用）
@app.post("/uploadfile/")
def create_upload_file(file: bytes = File(description="以字节形式读取")):
    return {"file_size": len(file)}

# 方式 B：UploadFile 流式（大文件、要拿元数据用这个）
@app.post("/uploadfile1/")
async def create_upload_file(file: UploadFile = File(description="流式读取")):
    return {"filename": file.filename,
            "content_type": file.content_type,
            "size": file.size}

if __name__ == "__main__":
    uvicorn.run(app, host="127.0.0.1", port=8000)

两种方式的选择取决于文件大小。bytes 会把整个文件读进内存，适合小文件。UploadFile 是 SpooledTemporaryFile，超过阈值会自动落盘，适合大文件，而且能拿到文件名、类型和大小等元数据。

RAG 场景上传 PDF 或文档时，建议使用 UploadFile，这样几百 MB 的文件不会被整个读进内存。另外，只有 async def 配合 UploadFile 才能享受异步 IO。普通的 def 函数会被放到线程池中执行。

4.2 LlamaIndex 检索与 FunctionAgent

LlamaIndex 是 RAG 的主要工具之一，和 LangChain 相比，它更偏向数据管道和索引引擎。课件 day03 讲入门，day04 讲文本切分，day05 讲摄取管道和路由，day06 讲自定义查询、检索和合成。

4.2.1 索引构建与默认 LLM、Embedding 配置

下面的代码来自 day03。

from dotenv import load_dotenv
from llama_index.core import VectorStoreIndex, SimpleDirectoryReader, Settings
from llama_index.embeddings.huggingface import HuggingFaceEmbedding
from llama_index.llms.dashscope import DashScope
import os

load_dotenv()

model = "qwen3-max"
api_key = os.getenv("DASHSCOPE_API_KEY")
api_base = os.getenv("DASHSCOPE_BASE_URL")

# LlamaIndex 全局默认配置：以后所有节点/查询引擎都用它
Settings.llm = DashScope(model_name=model,
                        api_key=api_key,
                        api_base_url=api_base)
Settings.embed_model = HuggingFaceEmbedding(
    model_name=r"D:\llm\Local_model\BAAI\bge-small-zh-v1___5"
)

# 1) 加载文档（自动按后缀选择 reader）

# 2) 构建向量索引（内存版；生产上换 Qdrant/Chroma）
index = VectorStoreIndex.from_documents(documents)
# 3) 查询引擎 + 提问
query_engine = index.as_query_engine()
print(query_engine.query("公司的上下班时间？"))

这段代码里有几个参数需要注意。

  • Settings.llm 和 Settings.embed_model 是全局单例，修改一次整个工程都会生效。不要在每个文件里各自新建一个 LLM，否则会重复加载 embedding 模型。
  • bge-small-zh-v1.5 适合中文，本地加载快。生产环境建议换成 bge-large-zh-v1.5 或 bge-m3。
  • VectorStoreIndex.from_documents 内部默认的 chunk_size 是 1024，中文文档建议通过 Settings.chunk_size=512 调小。

4.2.2 FunctionAgent 最小示例

下面的代码来自 day03。

import asyncio
from dotenv import load_dotenv
from llama_index.core.agent.workflow import FunctionAgent
from llama_index.llms.dashscope import DashScope
import os

load_dotenv()
llm = DashScope(model_name="qwen3-max",
                api_key=os.getenv("DASHSCOPE_API_KEY"),
                api_base_url=os.getenv("DASHSCOPE_BASE_URL"))

def multiply(a: float, b: float) -> float:
    """两个数相乘并返回乘积"""
    return a * b

def add(a: float, b: float) -> float:
    """两个数相加并返回和"""
    return a + b

# FunctionAgent = 函数自动被识别为工具，docstring 就是工具描述
workflow = FunctionAgent(
    tools=[multiply, add],
    llm=llm,
    system_prompt="你是一个可以使用工具执行基本数学运算的代理。请用中文回答",
)

async def main():
    response = await workflow.run(user_msg="请计算 20+(2*4)?")
    print(response)

if __name__ == "__main__":
    asyncio.run(main())

FunctionAgent 的要点有三个。

  • LlamaIndex 会读取函数签名和 docstring，自动生成工具的 schema。因此 docstring 写得越清楚，模型调用工具就越准确。
  • 课件备注称，千问模型在 LlamaIndex agent 中对某些工具调用的兼容性不好，建议换成 DeepSeek。这是课件作者实际遇到的问题。
  • 需要流式输出时，使用 workflow.stream_events() 加 AgentStream 事件，不要用 print(response) 阻塞等待结果。

4.2.3 文本切分器

下面的代码来自 day04。

from llama_index.core.node_parser import CodeSplitter, HierarchicalNodeParser
from llama_index.core import SimpleDirectoryReader

# 1) 代码切分器：按语言 AST 切，比字符串切分更准
documents = SimpleDirectoryReader(input_files=["./03-MarkdownElement解析器.py"]).load_data()
splitter = CodeSplitter(
    language="python",
    chunk_lines=50,          # 每块目标行数
    chunk_lines_overlap=10,  # 块之间重叠行数
    max_chars=300,          # 单块最大字符
)
nodes = splitter.get_nodes_from_documents(documents)

# 2) 层次节点解析器：生成"粗块-细块"两级，配合 AutoMergingRetriever
node_parser = HierarchicalNodeParser.from_defaults(
    chunk_sizes=[512, 300],  # 从粗到细的 token 数
    chunk_overlap=70,
)
hier_nodes = node_parser.get_nodes_from_documents(documents)

三种切分器的选用场景如下。

  • 普通中文文档使用 SentenceSplitter(chunk_size=512, chunk_overlap=50)，day05 用的就是这个配置。
  • 代码仓库使用 CodeSplitter。
  • 长文档和制度手册使用 HierarchicalNodeParser 配合 AutoMergingRetriever。检索到叶节点后，系统会自动合并回父节点，再一起交给 LLM，避免切得太碎导致上下文丢失。

4.2.4 摄取管道 IngestionPipeline

下面的代码来自 day05。

from llama_index.core import SimpleDirectoryReader
from llama_index.core.ingestion import IngestionPipeline
from llama_index.core.text_splitter import SentenceSplitter
from llama_index.core.extractors import TitleExtractor

documents = SimpleDirectoryReader(input_files=["../data/小说.txt"]).load_data()

# 1) 切分器
text_splitter = SentenceSplitter(chunk_size=256, chunk_overlap=30)
# 2) 自动标题抽取器（用 LLM 给每个 chunk 起标题，存进 metadata）
title_extractor = TitleExtractor(
    nodes=5,
    node_template="请为以下文档生成一个简洁的标题: {context_str}",
    num_workers=5,
)

# 3) 管道 = 切分 → 向量化 → 抽取标题，一次跑完
pipeline = IngestionPipeline(
    transformations=[text_splitter, embed_model, title_extractor]
)
nodes = pipeline.run(documents=documents)
for node in nodes:
    print(node.metadata)

使用管道的理由有两点。第一，普通的 VectorStoreIndex.from_documents 背后就是一条默认管道。第二，一旦需要加入自定义抽取器、embedding、去重或缓存，就得自己编写 IngestionPipeline。

num_workers=5 表示并行调用 LLM 抽取标题的并发数。文档多时能明显加速，但并发数不能超过 API 的 QPS 上限。

4.2.5 路由索引 RouterQueryEngine

下面的代码来自 day05。

from llama_index.core import VectorStoreIndex, SimpleDirectoryReader
from llama_index.core.query_engine import RouterQueryEngine
from llama_index.core.selectors import LLMSingleSelector
from llama_index.core.tools import QueryEngineTool, ToolMetadata

# 1) 多个独立文档各自建索引
tech_docs = SimpleDirectoryReader(input_files=["../data/java_basics_manual.md"]).load_data()
product_docs = SimpleDirectoryReader(input_files=["../data/DeepSeek15天指导手册.pdf"]).load_data()
tech_index = VectorStoreIndex.from_documents(tech_docs)
product_index = VectorStoreIndex.from_documents(product_docs)

# 2) 每个索引配一个 query engine，参数不同
tech_engine = tech_index.as_query_engine(similarity_top_k=3, response_mode="compact")
product_engine = product_index.as_query_engine(similarity_top_k=5, response_mode="tree_summarize")

# 3) 包装成"工具"，用 ToolMetadata 描述适用场景
query_tools = [
    QueryEngineTool(query_engine=tech_engine,
                    metadata=ToolMetadata(name="technical_docs",
                                          description="java 基础技术文档库...")),
    QueryEngineTool(query_engine=product_engine,
                    metadata=ToolMetadata(name="product_manual",
                                          description="deepseek 使用手册...")),
]

# 4) RouterQueryEngine 用 LLM 自动选引擎
router = RouterQueryEngine(
    selector=LLMSingleSelector.from_defaults(),
    query_engine_tools=query_tools,
)
print(router.query("怎么在 Java 里写一个单例？"))

这里有两个需要注意的点。

  • response_mode 的选择影响答案的形式。compact 适合快问快答，tree_summarize 适合长文综述，refine 会逐个 chunk 迭代修改答案，速度慢但更准确。
  • ToolMetadata.description 写得好不好，直接决定路由能不能选对引擎。这和 Agent 工具描述的原理相同。

4.2.6 聊天引擎与存储持久化

下面的代码来自 day06。

from llama_index.core import (
    VectorStoreIndex, SimpleDirectoryReader, StorageContext, load_index_from_storage
)

# 1) 首次：建索引并持久化到磁盘
documents = SimpleDirectoryReader(input_files=["../data/公司规章制度.txt"]).load_data()
index = VectorStoreIndex.from_documents(documents)
index.storage_context.persist(persist_dir="./storage")

print(chat_engine.chat("那年假呢？"))  # 自动带上下文

课件指出，不持久化就意味着每次启动都要重新计算 embedding，已经花掉的 API 费用就白白浪费了。生产环境必须做持久化。

chat_mode 有两个常用选项。context 把检索结果作为系统上下文，适合单个知识库。react 把检索结果当作工具使用，适合多个知识库。

4.3 LangChain create_agent：Function Calling 与中间件

4.3.1 自定义中间件：@before_agent 做权限与敏感词拦截

下面的代码来自 day08。

from langchain.agents import create_agent, AgentState
from langchain.agents.middleware import before_agent
from langchain.messages import HumanMessage, AIMessage
from langchain_openai import ChatOpenAI
from langgraph.runtime import Runtime
from dataclasses import dataclass

@dataclass(frozen=True)
class Context:           # 通过 runtime 注入的运行时上下文
    user_id: str
    user_permissions: str

@before_agent(can_jump_to="end")
def guard_middleware(state: AgentState, runtime: Runtime[Context]):
    # 1) 找到最新用户问题
    user_msg = ""
    for m in reversed(state["messages"]):
        if isinstance(m, HumanMessage):
            user_msg = m.content
            break
    # 2) 敏感词拦截
    sensitive = ["TM", "TMD", "CNM", "垃圾"]
    if any(w in user_msg.upper() for w in sensitive):
        return {"messages": [AIMessage(content="检测到不当言论，请文明交流")],
                "jump_to": "end"}     # 直接结束 agent
    # 3) 权限控制
    if runtime.context.user_permissions != "Vip":
        print("非 VIP，限制可用工具")
    return None

agent = create_agent(model=llm, tools=[...], middleware=[guard_middleware])

这段代码的结构可以拆成三部分。第一部分从消息列表中取出最新的用户问题。第二部分做敏感词拦截，命中时直接返回提示语，并通过 jump_to 结束 Agent。第三部分根据运行时上下文中的权限字段做控制。

运行时上下文 Context 是冻结的数据类，通过 runtime 注入，中间件从 runtime.context 读取用户身份和权限。

4.3.2 Function Calling 的真实代码

下面的代码来自 day09。

import os
from dotenv import load_dotenv
from langchain_openai import ChatOpenAI
from langchain_core.tools import tool
from langchain.agents import create_agent

load_dotenv()
llm = ChatOpenAI(model="qwen3.5-flash",
                 api_key=os.getenv("DASHSCOPE_API_KEY"),
                 base_url=os.getenv("DASHSCOPE_BASE_URL"))

@tool
def calculator(expression: str) -> str:
    """支持多个表达式的数学计算器（使用 numexpr），用分号分隔多个表达式"""
    import numexpr, math
    local = {"pi": math.pi, "e": math.e}
    exprs = [e.strip() for e in expression.split(";") if e.strip()]
    return "\n".join(f"{e} = {numexpr.evaluate(e, local_dict=local)}"
                      for e in exprs)

@tool
def get_weather(city: str) -> str:
    """获取指定城市的实时天气"""
    return f"{city} 今天晴朗，24-28°C"

agent = create_agent(model=llm, tools=[calculator, get_weather])
resp = agent.invoke({"messages": [{"role": "user",
        "content": "北京天气怎么样？另外帮我算一下 (52+18)*2/pi"}]})
print(resp["messages"][-1].content)

这段代码的关键点如下。

  • @tool 装饰器会把函数签名和 docstring 转换成 OpenAI function schema。docstring 的第一行就是工具描述，必须写得让模型能看懂"什么时候该用这个工具"。
  • create_agent 内部会自动处理工具调用循环。模型返回 tool_calls 后，系统执行函数，把结果放回消息列表，再调用 LLM。开发者不需要手写 while 循环。
  • 千问和 DashScope 兼容 OpenAI 协议，直接设置 ChatOpenAI(base_url=...) 即可使用。

calculator 支持用分号分隔多个表达式，每个表达式各输出一行结果。

4.4 三种推理模式的代码

课件 day10 把 Plan-and-Execute、Self-ASK 和 Reflection 放在同一天讲。下面三节分别给出每种模式的代码或结构。

4.4.1 Plan-and-Execute

下面的代码来自 day10。

import os, math, numexpr
from dotenv import load_dotenv
from langchain_openai import ChatOpenAI
from langchain_experimental.plan_and_execute import (
    PlanAndExecute, load_agent_executor, load_chat_planner
)
from langchain_tavily import TavilySearch
from langchain_core.tools import tool

load_dotenv()
llm = ChatOpenAI(model="MiniMax-M2.1",
                 api_key=os.getenv("DASHSCOPE_API_KEY"),
                 base_url=os.getenv("DASHSCOPE_BASE_URL"))

@tool
def calculator(expression: str) -> str:
    """数学计算器，支持分号分隔多个表达式"""
    local = {"pi": math.pi, "e": math.e}
    return "\n".join(f"{e} = {numexpr.evaluate(e.strip(), local_dict=local)}"
                     for e in expression.split(";") if e.strip())

tools = [TavilySearch(), calculator]

# Planner = 先写计划（一串步骤）
planner  = load_chat_planner(llm)
# Executor = 每一步用 ReAct 执行
executor = load_agent_executor(llm, tools, verbose=True)

agent = PlanAndExecute(planner=planner, executor=executor, verbose=True)
result = agent.invoke(
    "我有5000人民币预算，想去日本旅行5天。按当前汇率在东京能住几晚中等价位酒店？"
)
print(result)

这段代码把循环拆成了 Planner 和 Executor 两部分。Planner 先生成计划，Executor 中每一步都是 ReAct。

Plan-Execute 和 ReAct 的区别在于两点。ReAct 走一步看一步，容易走偏或绕圈。Plan-Execute 则先一次性生成 N 步计划，然后逐步执行，每步失败还可以重新规划。它适合任务可以分解、步骤明确的场景，例如旅行规划和数据处理流水线。它不适合开放式对话。

4.4.2 Self-ASK

Self-ASK 的核心是一个暂停和续接的过程。模型输出 Follow up: xxx 后暂停，外部搜索工具填入 Intermediate answer: xxx，然后模型再继续提出下一个问题。课件通过自定义 stop words 加中间件实现这个过程。

from langchain_openai import ChatOpenAI

llm = ChatOpenAI(model="deepseek-chat", ...)
# 关键：让模型在"Intermediate answer:" 处停下来，把控制权交给外部搜索
llm_with_stop = llm.bind(stop=[
    "\nIntermediate answer:", "Intermediate answer:",
    "\nIntermediate answer：", "Intermediate answer：",
])

SELF_ASK_SYSTEM_PROMPT = """你是搜索链推理专家。
规则：
1. 每次只输出一个 "Follow up:" 问题，输出后立即停止。
2. 禁止自己生成 "Intermediate answer:"，那是外部工具填的。
3. 格式：
   Question: [用户输入]
   Are follow up questions needed here: [Yes/No]
   Follow up: [具体搜索问题]
   Intermediate answer: (等待工具)
   So the final answer is: [结论]
"""

llm.bind(stop=...) 的 stop 列表同时包含半角冒号和全角冒号两种写法。系统提示词的三条规则分别约束了问题的数量、中间答案的来源和输出格式。

Self-ASK 适合多跳问题。例如"马斯克第二家公司的现任 CEO 是谁"，需要先搜"第二家公司是什么"，再搜"现任 CEO"。与纯 ReAct 相比，它每一步只问一个问题，因此更省 token。

4.4.3 Reflection

课件的 thinking_and_self-Refection 用两个 LLM 节点串联完成反思，结构如下。

draft_node:    LLM 生成答案
review_node:   LLM 读草稿 → 指出问题
revise_node:   LLM 读草稿+批评 → 改一版

在 LangGraph 中，可以用三个节点加一条条件边实现这个结构。如果 review 认为没有问题，流程直接结束；否则回到 revise 节点。课件认为这是 day16 "自定义主管架构" 的雏形。LangGraph 的节点和条件边的详细用法，见 L5-Agent框架选型与平台生态-深挖整合.md，这里不再重复。

Reflection 的结构与 Plan-and-Execute 不同，它是一个固定的三节点闭环，没有 Planner。由于反思本身很贵，它应该限制在关键节点上，与 2.2 节的原则一致。

小结

Agent 的循环分为 ReAct、Plan-and-Execute 和 Reflection 三种，它们按任务复杂度分层，可以叠加使用。默认先用 ReAct，跑偏了加 Planner，产出不满意再加 Reflection。循环需要明确的步数上限，Reflection 应该放在关键节点上。

业务落地要求场景具备重复劳动、可验证输出和可靠工具三个条件。落地按找痛点、定输入输出、选工具、搭循环和接日志五步进行。常见的失败包括追求通用、跳过 RAG、不做日志和忽视数字短板。

动手实现时，先用 FastAPI 搭 HTTP 外壳，再用 LlamaIndex 完成检索，然后用 LangChain 的 create_agent 加中间件和 Function Calling 实现工具调用，最后用代码实现三种推理模式。依赖和学习路径按课件的 day 顺序组织。
