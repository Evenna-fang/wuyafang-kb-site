LangGraph 生产级状态机设计：State、Reducer、路由与错误处理

← 返回总入口 相关：课件实操（语法入门） · Agent框架实操选型 · 持久化与人机协同实战 · 多Agent协作生产级实战

0. 本篇补什么缺口

L5 现有文档对 LangGraph 的覆盖集中在两处：课件实操 第 5 章讲了 StateGraph、条件边、Send、父子图的语法；框架实操选型 讲了为什么选 LangGraph。两者之间缺一块：怎么把一个业务流程设计成一张在生产上不出事故的图。具体缺口有四项。

  1. State 里该放什么、不该放什么，没有判断标准。
  2. Reducer 只讲了 add_messages，没讲并行写同一个 key 时会发生什么。
  3. 错误处理没有分类，所有异常都靠"外面包 try/except"。
  4. 递归上限、死循环兜底、节点粒度这些上线前必查项没有清单。

本篇的代码全部在本机 ~/ai-stack（langgraph 1.2.11）上用确定性节点（不调真实 LLM）跑通过，文中标 🧪 的结论即来自这次实测。官方文档对应的结论标 📄。

版本说明：GitHub Releases 显示 langgraph 最新版为 1.2.19（2026-10-30 发布，📄 api.github.com 实查），本机是 1.2.11。文中个别 API（error_handler、set_node_defaults）官方标注需要 langgraph>=1.2，本机未逐一验证，已在对应位置标注"未实测"。

1. 官方心智模型：节点干活，边决定下一步

📄 官方 Graph API 文档的原话是："nodes do the work, edges tell what to do next"。一张图由三部分组成：

部分 是什么 生产含义
State 整张图共享的状态快照 它就是 checkpoint 的内容，也是你排查事故时唯一能看到的"现场"
Node 接收 state、返回部分更新的函数 节点边界就是 checkpoint 边界，决定失败后重做多少活
Edge 决定下一个执行哪个节点 普通边是确定性路径，条件边把"LLM 判断"限制在你声明的出口里

执行模型是 super-step：同一步里能并行的节点一起跑，全部写完状态后进入下一步。这一点决定了后面讲的 reducer 为什么必须设计。

📄 compile() 之前图只是一个定义，编译时会检查结构（比如有没有悬空节点），并接收 checkpointer、断点等运行选项。生产代码里应该把"建图"和"调用"分开：建图在模块加载时做一次，调用时只传 thread_id 和输入。

2. State 设计：只存原始数据，不存格式化文本

2.1 官方的两条判断标准

📄 官方《Thinking in LangGraph》给出的标准很简单：

  • 需要跨步骤保留的数据，放进 state。
  • 能从已有数据推导出来的，需要时再算，不存。

并且明确要求 state 存原始数据（邮件原文、分类结果字典、检索到的片段列表），不存格式化后的字符串或拼好的 prompt。各节点在用的时候自己格式化。

这条规则的实际收益有三个：

  1. 不同节点可以用不同格式消费同一份数据。分类节点要结构化字典，起草节点要一段自然语言，同一份 state 都能支持。
  2. 改 prompt 模板不用改 state 结构，也就不会让历史 checkpoint 失效。这点在生产上很重要：线上有大量挂起中的 thread，它们的 checkpoint 是按旧 state 结构存的。
  3. 调试时直接能看到节点拿到的原始输入，而不是一坨拼好的字符串。

2.2 用 TypedDict 还是 Pydantic

📄 官方说法：默认用 TypedDict；需要默认值用 dataclass；需要递归校验用 Pydantic BaseModel，但更慢。我们的建议：

  • 图内部 state 用 TypedDict，轻、快、和 reducer 的 Annotated 写法天然配合。
  • 图的入口和出口（外部输入、返回给调用方的结果）才用 Pydantic 做校验。官方支持输入、输出 schema 与内部 state 不同。
  • 不想暴露给调用方的中间字段（草稿、重试计数），放进私有 channel，invoke 的返回里不会带出来。注意 📄 官方说明私有 channel 对 streaming 仍可见，别把密钥放进去。

2.3 一个生产级 State 的样子

下面是工单处理流程的 state（结构参考官方邮件客服示例，字段为本库改写）：

import operator
from typing import Annotated, Literal, TypedDict

class Classification(TypedDict):
    intent: Literal["question", "bug", "billing", "complex"]
    urgency: Literal["low", "medium", "high", "critical"]
    summary: str

class TicketState(TypedDict):
    # 输入：只读，不被任何节点覆盖
    ticket_id: str
    raw_text: str
    # 中间产物：原始数据，不是 prompt
    classification: Classification | None
    evidence: list[str] | None
    draft: str | None
    # 审计轨迹：并行节点都能追加，用 reducer 合并
    trail: Annotated[list[str], operator.add]
    # 失败信息：给 LLM 节点读，让它自己修正
    last_error: str | None

三个设计细节：

  • ticket_id 和 raw_text 只在入口写一次。节点返回部分更新时不会碰它们，天然只读。
  • trail 用 operator.add 做 reducer。每个节点只返回 {"trail": ["节点名:结果"]}，不需要先读后写。事后复盘，这个字段就是执行路径的明文记录。
  • last_error 是后面错误处理一节的"LLM 可恢复错误"通道。

3. Reducer：并行节点写同一个 key 的规则

3.1 默认行为是覆盖

📄 每个 state key 有自己的 reducer，调用形式是 reducer(left, right)，left 是已有值，right 是节点这次的更新。不声明 reducer 就是覆盖。

单线程图里覆盖没问题。一旦出现并行分支（一个节点连出多条边，或者用了 Send），多个节点在同一个 super-step 里写同一个 key，没有 reducer 就会冲突。

3.2 实测：并行写 + reducer

🧪 本机实测（节点 a 同时连到 b、c，b、c 汇入 END，logs 用 operator.add）：

class S1(TypedDict):
    logs: Annotated[list[str], operator.add]
    score: int

g = StateGraph(S1)
g.add_node("a", lambda s: {"logs": ["a"], "score": 1})
g.add_node("b", lambda s: {"logs": ["b"]})
g.add_node("c", lambda s: {"logs": ["c"]})
g.add_edge(START, "a")
g.add_edge("a", "b")
g.add_edge("a", "c")
g.add_edge(["b", "c"], END)      # 数组形式 = 等 b、c 都完成才继续
out = g.compile().invoke({"logs": [], "score": 0})
# out["logs"] 包含 a、b、c 三项；score == 1

结果三个日志都保留，没有丢更新。注意 add_edge(["b", "c"], END) 的数组写法表示"等两者都完成"，这是汇合（join）的标准写法。

3.3 几个容易踩的点

  • 📄 reducer 是合并语义，所以返回空列表清不掉旧内容。官方提供 Overwrite 包装值来强制清空。
  • 📄 消息列表直接用内置 add_messages：新消息追加，同 ID 的消息原地更新。自己写 operator.add 处理消息会丢掉"按 ID 更新"的能力，在做消息裁剪、撤回时会出问题。
  • 📄 UntrackedValue 标注的字段不进 checkpoint，恢复时会被重置。适合放数据库连接这类不可序列化对象，但不要放任何恢复后还需要的业务数据。
  • 并行工具调用同理：📄 官方工具文档明确提醒，多个并行工具可能同时更新同一个 state 字段，要为该字段定义 reducer。

判断口诀：画图时只要看到"一个节点后面出了两条以上的边"，或者用了 Send，立刻检查它们写的 key 是否都有 reducer。

4. 路由：普通边、条件边、Command、Send 怎么选

📄 官方 Graph API 文档给了四种路由手段，我们按"谁来做决定"整理：

手段 决策者 适合 注意
add_edge 图结构（固定） 流程固定的步骤 一个节点多条出边会并行执行
add_conditional_edges(node, router) 独立的路由函数 路由逻辑和业务逻辑想分开，便于单测 路由函数只读 state，不改 state
Command(update=..., goto=...) 节点自己 节点处理完才知道下一步去哪，更新和跳转要原子完成 官方提醒：静态边仍会和 goto 一起执行，一个节点只用一种路由方式
Send(node, state) 条件边返回 分支数运行时才知道（map-reduce） 每个 Send 可带不同的子 state

4.1 Command：更新和路由原子完成

🧪 实测：

def router(s) -> Command[Literal["big", "small"]]:
    return Command(
        update={"path": ["router"]},
        goto="big" if s["n"] > 5 else "small",
    )

输入 n=9 路径为 router→big，n=1 为 router→small，均符合预期。返回类型标注 Command[Literal[...]] 不只是给类型检查看的：📄 官方说明它会把节点的可能去向声明出来，画图（get_graph()）时才能画出这些边。生产代码里不标注，图可视化就缺边，评审时没人看得出流程。

📄 Command 还有两个字段在多 Agent 里很关键：graph=Command.PARENT（从子图跳到父图的节点）和 resume（恢复被 interrupt() 暂停的执行）。这两个在后面两篇展开。

4.2 Send：运行时扇出

🧪 实测 map-reduce：

def fan(s):
    return [Send("work", {"x": i}) for i in s["items"]]

g.add_node("work", lambda s: {"results": [s["x"] * 2]})
g.add_conditional_edges(START, fan, ["work"])
# items=[1,2,3] -> results 排序后 [2,4,6]

两条生产经验：

  1. Send 的子 state 是独立的，不是主 state 的副本。worker 只能看到你塞进去的字段，天然实现"上下文隔离"，这是多 Agent 并行研究的基础。
  2. 汇总靠 reducer。results 必须有 operator.add，否则只剩最后一个 worker 的结果。扇出数量要有上限（比如最多 N 个），否则一个脏输入能触发几百个并行 LLM 调用，直接烧钱。

4.3 路由函数的写法规范

  • 返回值要么是节点名字符串，要么配一个映射字典，不要返回动态拼接的节点名。
  • LLM 做分类时，用结构化输出把结果限制在枚举里（上面的 Literal），路由函数再根据枚举值走分支。LLM 只负责"判断"，不负责"写出节点名"。
  • 路由函数里要有兜底分支。LLM 返回了意料之外的值时走 human_review 或 END，别抛 KeyError。

5. 递归上限与死循环兜底

Agent 图里最典型的循环是"LLM→工具→LLM"。模型偶尔会反复调同一个工具，循环不收敛。

📄 官方机制：recursion_limit 限制一次运行的 super-step 总数，超出抛 GraphRecursionError。官方说明默认值在 1.1.4 及以后是 10,007。这个默认值对生产来说太大：一个死循环要跑上万步才会被拦住，成本早就爆了。

⚠️ 官方特别说明：recursion_limit 要放在顶层 config，不是 configurable 里面。

5.1 实测：两种兜底

🧪 方案一，让它抛错，调用方捕获：

try:
    app.invoke(inputs, config={"recursion_limit": 5})
except GraphRecursionError:
    ...   # 记告警、降级回复

实测一个自环节点在 limit=5 时确实抛出 GraphRecursionError。

🧪 方案二（推荐），图内自己降级，让用户拿到一个可用结果而不是报错。用官方的 RemainingSteps 托管值：

from langgraph.managed import RemainingSteps

class S5(TypedDict):
    i: int
    note: str
    remaining_steps: RemainingSteps     # 由框架维护，节点不用写

def route(s):
    return "fallback" if s["remaining_steps"] <= 2 else "loop"

g.add_conditional_edges("loop", route, ["loop", "fallback"])
out = app.invoke({"i": 0, "note": ""}, config={"recursion_limit": 6})
# out["note"] == "degraded"，没有抛错

实测 limit=6 时循环 4 次后进入 fallback，返回 degraded。预留 2 步是给 fallback 本身和收尾用的，预留量要按你降级分支的实际长度定。

5.2 生产建议

图类型 建议 recursion_limit 理由
固定流程（无循环） 步数 ×2 只是防御性上限
ReAct 型 Agent 循环 25–50 按"最多几次工具调用"×2 估
带人工审批的长流程 单次运行的步数，不含挂起时间 挂起不消耗 super-step

上面的数字是本文给的经验起点，不是官方数据，要按自己业务的 trace 调整。

6. 错误处理：先分类，再选手段

这是本篇最重要的一节。📄 官方《Thinking in LangGraph》把错误分成四类，每类有不同的修复者：

错误类型 谁来修 处理手段
瞬时错误（网络抖动、429 限流） 系统自动 RetryPolicy 自动重试
LLM 可恢复错误（工具参数错、解析失败） LLM 自己 把错误写进 state，回到 LLM 节点再来一轮
需要用户补信息（缺账号 ID） 用户 interrupt() 暂停等待
未预期错误 开发者 直接抛出，别吞掉

另外官方文档提到（标注需 langgraph>=1.2）：重试耗尽后的可恢复失败，可以用 error_handler 声明式地跳进补偿分支。🧪 本机 1.2.11 未实测该参数，使用前先查你的版本。

6.1 瞬时错误：RetryPolicy

🧪 实测节点前两次抛 ConnectionError，第三次成功：

g.add_node(
    "flaky", flaky,
    retry_policy=RetryPolicy(max_attempts=3, initial_interval=0.01, retry_on=ConnectionError),
)

实测节点共执行 3 次后成功。要点：

  • retry_on 建议显式写，只对确定是瞬时的异常类型重试。🧪 读本机 1.2.11 源码 default_retry_on 得知：不写时，ConnectionError 和 HTTP 5xx 会重试，ValueError、TypeError、RuntimeError、OSError 等常见内置异常不重试，但其他所有异常（包括你自定义的业务异常类、SDK 抛的专有异常）默认都会重试。依赖默认值时，一个"余额不足"之类的自定义异常会被白白重试 3 次，放大成本。
  • 重试单位是节点。节点里如果有多个副作用（发邮件 + 写库），重试会让前面成功的副作用重复执行。所以官方强调节点粒度要小，外部调用单独成节点。这点和下一篇的幂等规则直接相关。
  • 📄 官方提供 timeout= 限制单次尝试时长，以及 StateGraph.set_node_defaults(...) 给全图设默认策略，单节点配置优先。默认值接口标注较新，🧪 未实测。

6.2 LLM 可恢复错误：把错误当数据

工具调用失败不要让异常冒泡成图崩溃。📄 官方示例的做法是 catch 后把错误文本作为工具结果回给模型：

def execute_tool(state) -> Command[Literal["agent", "execute_tool"]]:
    try:
        result = run_tool(state["tool_call"])
        return Command(update={"tool_result": result}, goto="agent")
    except ToolError as e:
        return Command(update={"tool_result": f"Tool error: {e}"}, goto="agent")

在 create_agent 体系里，📄 官方工具文档用 @wrap_tool_call 中间件统一做这件事，catch 异常后返回带 tool_call_id 的 ToolMessage。必须带 tool_call_id，否则模型的消息历史会缺配对，下一次调用 API 直接报格式错误。

要给这条回路加次数上限。LLM 可能反复用同一个错误参数重试。state 里放一个计数器（或直接用 RemainingSteps），超限后转人工。

6.3 需要用户补充：interrupt

缺少用户才能提供的信息时，用 interrupt() 暂停，而不是让 LLM 猜。📄 官方还给出一条硬规矩："interrupt() must come first"，即 interrupt 要放在节点最前面，因为恢复时节点会从头重跑。细节在 持久化与人机协同实战。

6.4 未预期错误：让它抛

不要写 except Exception: pass。未预期错误吞掉后 checkpoint 会继续往下写，坏数据被固化进 thread 历史。让它抛出，调用方记录后，用同一个 thread_id 以 invoke(None, config) 从失败节点续跑（下一篇实测）。

7. 节点粒度：以 checkpoint 为尺子

📄 官方原话（概括）：节点边界就是 checkpoint 位置，节点越小，失败后重复的工作越少。外部服务调用（检索、建单、发送）适合各自成节点，这样可以单独配重试。

用一个具体例子对比：

写法 失败在"发送"这一步时
一个大节点：检索 → LLM 起草 → 发送 重试要重新检索、重新调 LLM（再花一次钱），LLM 输出还可能变
三个节点：retrieve → draft → send 只重试 send，draft 的结果已在 checkpoint 里

拆分原则：

  1. 每个 LLM 调用单独成节点：贵，且结果不确定，不应重复。
  2. 每个有外部副作用的操作单独成节点：便于配幂等和重试策略。
  3. 纯计算、纯格式转换可以合并，它们便宜且确定。
  4. 单个节点超过一屏代码，通常就该拆。

8. 上线前检查清单

# 检查项 通过标准
1 所有并行写入的 key 都有 reducer 画图时逐个核对
2 State 里无格式化 prompt、无不可序列化对象 打印一份 checkpoint 看内容
3 路由函数有兜底分支 单测喂入非法枚举值，不抛 KeyError
4 Send 扇出数有上限 代码里有 [:N] 或前置校验
5 recursion_limit 已显式设置，且在顶层 config 用 limit=5 的单测确认会降级
6 每个外部调用有 RetryPolicy 且写了 retry_on 代码审查
7 工具失败回灌为 ToolMessage 且带 tool_call_id 构造失败工具的集成测试
8 LLM 自修复回路有次数上限 超限转人工的测试
9 节点返回类型标注了 Command[Literal[...]] 图可视化能看到所有边
10 图的构建与调用分离，thread_id 由调用方传入 代码审查

测试策略

  • 节点单测：节点就是 state -> 部分更新 的纯函数，LLM 客户端通过参数注入，测试时换假实现。上面所有 🧪 实测脚本都是这个思路：没有任何真实 LLM 调用，几秒内跑完。
  • 图级测试：用 InMemorySaver 编译，覆盖正常路径、重试路径、降级路径、超限路径四条。
  • 评估：LLM 输出质量另走 eval，不要和流程正确性混在一个测试里。参见 生产级Agent与Evals实操。

9. 对本库的落地启示

本库六员协作的 N1–N6 节点流（总地图第一节）本身就是一张带条件边和回流边的状态机，已有 ~/.hermes/shared-tasks.db（task_id=thread_id）作为状态表。结合本篇可以直接对照三点：

  1. 回流边 = 条件边。"验收不通过→回 N4"、"卡点≥2 次→回 N2"，在 LangGraph 里都是 add_conditional_edges 加一个计数字段，计数超限时转人工，这与第 5、6 节的兜底思路一致。
  2. 子单结果 = 带 reducer 的 key。多个子单并行回传结果时，用 operator.add 汇总，避免后到的覆盖先到的。
  3. 派单卡的必填字段 = 入口 Pydantic 校验。dispatch-guard 的"4 核必填"对应入口 schema 校验，内部 state 保持轻量 TypedDict。

这三点是设计对照，不代表已改造。真正落地走总地图 N2 规划、N3 派单流程。
