Agent 框架实操选型（2026）：LangGraph vs CrewAI vs Claude/OpenAI SDK

核心结论

2026 年的选型共识（📰 多篇横评口径一致，二手）：没有单一赢家，按负载选，且大厂越来越同时跑多个。一句话版——

场景 选
需要显式状态机、断点续跑、人审（HITL）、长任务 LangGraph
快速搭多角色协作原型、给利益相关者周五演示 CrewAI
Claude 为主的工具密集型任务、想要开箱的工具/权限/子代理 Claude Agent SDK
OpenAI 生态、要最短上手路径 OpenAI Agents SDK
纯 TypeScript 的聊天/流式/轻 agent 应用 Vercel AI SDK（不是 agent 框架，但覆盖 80% 场景）

Anthropic 的前置原则（📄 一手《Building Effective AI Agents》原文）：「找最简单的可行方案，只有在需要时才增加复杂度」——能用工作流（固定路径）就别上 agent（动态路径）；agent 的本质就是「LLM 在循环里根据环境反馈调工具」。

一手横评最有价值的部分：同一任务同三框架跑（oxylabs GitHub）

  • schema.py 输出契约在三个目录里字节相同，可比性成立
  • 细节差异暴露设计哲学：
  • LangGraph：max_tokens 等就是 ChatAnthropic 的普通参数
  • Claude Agent SDK：没有 max_tokens 选项，走 CLAUDE_CODE_MAX_OUTPUT_TOKENS 环境变量
  • CrewAI：要改 thinking/output_config 得写 MatchParams httpx 拦截器 patch 请求体
  • 结论：抽象层级越高，细粒度控制越贵——选框架前先确认「你要调的那个参数在它那层暴露了吗」

二、LangGraph：有状态编排的事实标准（官方文档口径）

2.1 两个持久化原语（📄 docs.langchain.com Persistence 官方表）

Checkpointer Store
持久化什么 图状态快照 应用自定义 KV
作用域 单线程（thread_id） 跨线程
记忆类型 短期、线程内 长期、跨线程
用途 对话连续性、HITL、time travel、容错 用户偏好、事实、共享知识
访问方式 config 里传 thread_id 节点/应用代码里读写

2.2 HITL 是它的差异点（📄 LangChain 官方 HITL 文档 + 官方博客）

agent = create_agent(model=..., tools=[...], middleware=[
  HumanInTheLoopMiddleware(interrupt_on={
    "execute_sql": {"allowed_decisions": ["approve","reject"], "when": is_write_query},
    "write_file": {"allowed_decisions": ["approve","edit","reject"]},
  }),
], checkpointer=InMemorySaver())   # 生产换 AsyncPostgresSaver / MongoDBSaver（官方原文注释）
config = {"configurable": {"thread_id": "some_id"}}
result = agent.invoke({...}, config=config)   # 撞到 interrupt 暂停，之后 Command(resume=...) 恢复
  • 官方设计动机（📄 langchain.com 博客《Making it easier to build HITL agents with interrupt`》）：持久化是一等公民，每一步都读写状态检查点——这是很多公司选 LangGraph 的原因。
  • LangGraph Platform 的 /threads/{thread_id}/runs 在 interrupt() 时返回 409 + payload，前端收集用户输入后 POST Command(resume=...) 恢复（📰 turion.ai 实战，⚠️二手但与官方机制一致）。

2.3 什么时候不该用

复杂度不匹配的简单任务（Anthropic 原则）；纯 TypeScript 轻量聊天应用用 Vercel AI SDK 就够（📰 BearPlex：AI SDK 没有等价的状态管理与 HITL 检查点——反过来说 LangGraph 也没有 AI SDK 的 UI 流式顺手）。

三、CrewAI：角色扮演式快速协作

3.1 核心模型（📄 docs.crewai.com 官方文档口径）

  • Agent：role / goal / backstory + tools + allow_delegation + llm
  • Task：description + expected_output + 负责 agent + 工具
  • Process：sequential（顺序）或 hierarchical（层级，manager 分派）——枚举类型锁死，只有这两档
  • MCP 集成三种 transport（Stdio / SSE / Streamable HTTPS），是三框架里最深的（📰 letssdatascience，⚠️二手）

3.2 真实边界

  • 快速原型强：「周五下午向利益相关者卖一个 demo 的最快路径」（📰 pasqualepillitteri 横评的原话式总结）
  • 生产短板：共享状态需手动调优、抽象泄漏（见 §1 oxylabs 的 httpx 拦截器细节）、Python-only（复杂栈组织有摩擦）（📰 latenode / oxylabs）
  • 企业采用口径：CrewAI 自称覆盖美国 Fortune 500 的 60%（📰 appinventiv 转述，⚠️厂商口径未经独立验证）

四、Claude Agent SDK：把 Claude Code 当库用

4.1 它是什么（Anthropic 官方定位，经 📰 tech-insider/happycapy 转述）

  • Python (claude-agent-sdk) / TypeScript (@anthropic-ai/claude-agent-sdk) 包，暴露 Claude Code 的 agent 循环、内置工具、上下文管理、权限系统——原名 Claude Code SDK，2025 末泛化后改名。
  • 实现方式：spawn Claude Code CLI 作为受管子进程，stdio 通信，返回异步 typed message 流。
  • 认证：ANTHROPIC_API_KEY（Bedrock/Vertex 是否可直接替换要查当期文档——📰 tech-insider 明确警告支持情况随版本变）。

4.2 hooks 是它的治理点

PreToolUse（跑之前拦危险命令）/ PostToolUse（记录每次编辑）/ SessionStart / SessionEnd（起止钩子）——hook 是你自己的代码，在循环的固定点被调用（📰 morphllm 汇总官方文档）。

⚠️ 语言差异坑（📰 Shivansh Gupta 实测，⚠️二手）：SessionStart/SessionEnd 在 TypeScript 是 callback，在 Python 只支持经 settings 文件的 shell command hook——Python 主栈要先查 hook 可用性表再设计架构。

4.3 内存口径

官方经验口径约 1 GiB RAM/agent（子进程模型），50 个并发 session = 50 个进程——容器按此预留并设 maxTurns（📰 happycapy 引官方，⚠️二手需自测）。对比 LangGraph 的进程内图，这是它 serverless 长任务表现弱的根因（📰 横评）。

4.4 模型锁定的真实代价

📰 pasqualepillitteri 的成本观察（⚠️二手、价格随时间变）：绑定 Claude Agent SDK 的系统无论任务是否需要 Claude 都付 Claude 溢价；LangGraph/CrewAI 用户可以按任务换模型（贵模型只给写代码、便宜模型给解析）。选它之前先接受「模型自由度换工程效率」这笔交易。

五、OpenAI Agents SDK：四原语极简路线

  • 原语：Agents（instructions + tools + typed output）、Handoffs（agent 间移交控制）、Guardrails（与 agent 并行跑，违规可短路）、Sessions（零样板持久会话），外加内置 tracing（📄 官方口径，经 📰 cohorte/temporal 转述）。
  • Hosted tools：WebSearch / FileSearch / Computer / Code Interpreter；自写工具用 @function_tool。
  • 与 LangGraph 的取舍（📰 实测评测，⚠️二手）：抽象更高 → 上手快；但 handoff「适合基础路由，规模化下缺鲁棒状态管理与并发委派」，复杂编排要回到 LangGraph 的显式图。

六、生产化三维度横评：8 方案对照（2026-10 一手调研）

前面四框架是"同任务横向跑"，本节换一个视角：生产化三件套——① durable execution（崩溃后从精确断点续跑，不是整单重跑）；② structured trace（结构化 span/trace 树，不是纯文本日志）；③ explicit state graph（机器可校验的显式状态图，不是文字流程图）。这是"能不能上生产"的硬指标，与选型篇前文的"上手快不快"互补。

方案 ① 断点续跑 ② 结构化 trace ③ 显式状态图 一句话定位
LangGraph ✅ 最强：super-step 粒度 checkpointer + 5 种存储后端 + pending writes 不重跑成功节点 + durability 三档 ✅ 生态最厚：LangSmith + OTLP，可接 Langfuse/Datadog ✅ 标杆：StateGraph + reducer + Send + Command，独有 time-travel replay/fork 三维度唯一全进前二，Python 生态事实标准
Microsoft Agent Framework ✅ 任务级：CheckpointManager + Cosmos DB ✅ 官方明确原生 OTel GenAI 三信号 ✅ 双轨：Graph API（WorkflowBuilder）+ Functional API .NET/Azure 企业栈首选
Google ADK 2.0 ✅ 事件日志回放（at-least-once，需幂等） ✅ 原生 OTel 三信号，--otel_to_cloud 一键接 GCP ✅ 2.0 起一等图对象（Workflow + 条件路由 + join），紧追 LangGraph GCP/Vertex 栈首选；2.0 是 breaking change
AWS Strands ◐ 会话快照级（S3 持久化），HITL 仍在设计 ✅ 原生 OTel 全链路（模型/规划/工具/handoff） ✅ GraphBuilder 硬 DAG，可与 Swarm 嵌套 AWS/Bedrock 栈首选
CrewAI 1.x ✅ 任务粒度：CheckpointConfig + fork() ◐ 有但默认绑自家 AMP 云，数据出域敏感者慎选 ◐ 半个：Flow 装饰器事件图，无 nodes/edges 数据结构、无图引擎 角色分工式快速协作，图不图无所谓
OpenAI Agents SDK ◐ 会话级（RunState 序列化），无图级 checkpoint，崩溃从头跑 ✅ 内建默认开（自有 span 模型，非原生 OTel，需桥接） ✗ 无图引擎，仅 Handoff 建议式路由 单 agent 少工具、快速原型
Claude Agent SDK ◐ 会话级：continue/resume/fork + SessionStore ◐ OTel 三信号但 traces 仍 beta ✗ 无图：subagent 委派是模型决策非硬控制流，dynamic workflow 靠写 JS 复用 Claude Code 生态、脚本化扇出
Mastra ✅ suspend/resume 最成熟 HITL，快照跨进程 ✅ 原生 OTel，官方 Langfuse/Datadog 导出器 ✅ typed workflow（.then/.parallel）+ 最细 delegation hooks TypeScript 项目、委派治理最细

分维度结论： - 断点续跑第一 → LangGraph（super-step 粒度 + time-travel 无争议）；其余要么会话级（OpenAI/Claude/Strands）要么任务级（CrewAI/ADK）。 - 结构化 trace 最合规 → Microsoft / Google ADK / AWS Strands（都官方声明遵循 OTel GenAI 语义约定）；LangGraph 胜在观测平台生态最厚（LangSmith/Langfuse 可插拔）。 - 显式状态图第一 → LangGraph（API 被后来者对照，是事实标准），紧追者 Google ADK 2.0；OpenAI/Claude SDK 在这一维不合格，无法机械校验拓扑。

对本库（Python + 六员协作 + 多模型混合的 WSL 单机）：改造成本最低是 LangGraph——Python 原生、本体已装（只差 langgraph-checkpoint-sqlite），六员分工天然对应 supervisor 模式（Send 做并行派单），get_state_history 还能直接支撑"同错 3 次停手后回放"的审查痛点。云绑定方案（MAF 绑 Azure、ADK 绑 GCP、Strands 绑 AWS）对多模型混合单机是负担；Mastra 受限于 TS。详见 多智能体生产化缺口与断点续传（讲本库怎么落地）与 任务执行流程行业对标-2026（讲流程侧缺口）。完整矩阵与一手源见 raw/multi-agent/多智能体编排方案横评-20261013.md。

七、Anthropic 的工具设计原则（不论选哪个框架都适用，📄 一手）

  1. 简单优先：维护简单设计、显式展示规划步骤、精心打磨 ACI（agent-computer interface）——工具文档和测试花的功夫应超过花在 prompt 上的（原文，SWE-bench 工作 reportedly 先优化工具再优化 prompt）。
  2. token 预算：工具定义会吃掉大量上下文——Anthropic 自己见过优化前工具定义吃掉 134K token；58 个工具约 55K token 起步、Jira 一家 ~17K。对策：defer_loading / Tool Search——按需加载工具，且延迟加载的工具不进初始 prompt，不破坏 prompt caching（📄 advanced-tool-use 原文）。
  3. 响应截断：对可能吃爆上下文的工具做 pagination/range/filter/truncation；Claude Code 默认把工具响应限制在 25,000 token（📄 writing-tools-for-agents 原文）；截断时给模型引导性错误信息（鼓励多次小搜索而非一次大搜索）。
  4. 评测方式：用直接 LLM API 调用 + 简单 while 循环跑 agent loop，每个评测任务一个循环（📄 writing-tools-for-agents 原文）——与 wiki/LLM评估体系-Evals-2026.md 的 Level 1 衔接。

八、选型决策树

需要 HITL/断点续跑/长任务状态? ──是──→ LangGraph（Postgres checkpointer）
        │否
        ┥ 要不要 Anthropic 模型绑定也能接受？
        │     是 → 工具密集/开放任务 → Claude Agent SDK
        │     否 → OpenAI 生态？ → OpenAI Agents SDK（4 原语最快）
        │            多角色协作快速原型 → CrewAI
        │            纯 TS 流式聊天/轻 agent → Vercel AI SDK
        └ 模型要按任务轮换（省成本）？ → LangGraph / CrewAI（模型无关）

补充纪律（📰 appinventiv 的建议，与 Anthropic 原则同向）：把领域逻辑留在框架之外——换框架时才不会连根拔起；多个框架并存时按 workload 分派而不是全公司统一。
