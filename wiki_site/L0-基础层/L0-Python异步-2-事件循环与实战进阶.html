1. 是什么：事件循环是协程的调度引擎

2

事件循环可以理解成一位持续接收通知、安排下一步工作的调度员。协程运行到真正需要等待的异步操作时暂停，循环便执行其他就绪工作；当网络可读、定时器到期或等待的结果准备好时，再安排相关协程恢复。它不会替普通 Python 代码自动插入切换点，也不会让同一线程同时执行两段 Python 函数体。

概念 在程序中承担的职责 初学者要记住的边界
协程对象 描述可以暂停和恢复的执行过程 调用异步函数不等于已经执行它
Task / Future Task 驱动协程，Future 表示未来结果；Task 是 Future 的子类 业务代码通常创建 Task，不直接操作 Future
就绪队列 保存准备运行的回调以及任务恢复动作 回调执行太久会影响排在后面的工作
定时回调 到指定时间后进入可执行状态 到期意味着可以调度，不保证精确按时执行
I/O 通知 告诉循环某个异步等待可以继续 底层实现随平台而异，不必手工轮询
asyncio.run 为一次顶层调用创建、运行并关闭事件循环 返回前处理剩余任务取消、异步生成器和执行器收尾

从 CPython 的常见实现看，循环会结合就绪回调、定时器和底层 I/O 等待推进工作；这是一种理解模型，不应把内部私有队列当成公共接口。asyncio.run(main()) 是脚本推荐入口，业务协程里用 get_running_loop() 取得正在运行的循环。不要把某次运行创建的客户端、锁或任务随意带到另一个已经重建的循环中复用。

2.1 单线程协作式调度不会抢救阻塞代码

3

协作式调度依赖正在执行的任务主动让出控制权。await 是等待语法，但不是“这一行必定让出线程”的保证：如果等待对象已经完成，或者被调用的协程没有真正挂起，它可能立即继续。连续执行大量这种操作，仍可能长时间占用循环。理解这一点后，就不会把所有延迟都归因于网络慢。

常说“阻塞一个 await 拖垮整个 loop”，准确含义是：被 await 的协程如果执行了同步阻塞操作，它占住的仍是事件循环线程。await bad_fetch() 无法把 bad_fetch 内部的 requests.get 变成异步请求。反过来，一个正常挂起、等待异步网络响应的任务不会拖住整个循环，其他任务仍可推进。诊断时必须区分“当前请求在等待”和“所有请求都无法被调度”。

素材 C 的咖啡店比喻说明等待可以重叠；落实到服务端，收益来自多个请求的 I/O 等待互相交错，而不是协程提高了单个 CPU 核心的计算能力。如果响应前还要做大段压缩、解析或模型计算，循环仍会被计算占用。同步 I/O 可用线程桥接；纯 Python CPU 密集工作一般应考虑进程或独立服务，不能指望加一个 await 就获得并行计算。

2.2 并发能力越强，越需要限制下游压力3 个重点▾ 点开看本节重点
本节重点
  • 假设每个入口请求并发访问三个下游，入口同时有一百个请求，就可能产生三百个正在等待的下游调用
  • 若每次都新建连接、无限创建任务，数据库连接池、文件描述符和对端限额会先耗尽
  • 此时总吞吐未必增加，排队、超时和重试反而会放大压力
3

假设每个入口请求并发访问三个下游，入口同时有一百个请求，就可能产生三百个正在等待的下游调用。若每次都新建连接、无限创建任务，数据库连接池、文件描述符和对端限额会先耗尽。此时总吞吐未必增加，排队、超时和重试反而会放大压力。

信号量限制“正在执行的调用数”，连接池限制“可用连接数”，有界队列限制“积压工作数”，三者解决不同问题。只给一百万个 Task 外面套信号量，虽然限制了网络并发，却仍要为一百万个任务对象分配内存。素材 A 的小批量抓取适合演示信号量；素材 B 的生产者消费者更适合解释大量输入时的背压。

2.3 失败与退出也是并发程序的一部分

3

并发调用的难点往往在正常返回之外：一个下游失败后，其他调用是否继续？请求超时以后，后台任务是否还在占资源？服务退出时，连接和生成器由谁关闭？这些问题都与任务的所有者有关。结构化并发把任务放进明确作用域，取消语义让停止请求有机会执行清理，超时则为等待设定边界。

因此，最常见的性能事故“async 里塞同步代码”需要从调用链定位；最常见的资源事故“创建后没人等待”需要从生命周期定位。下面按入口、任务、资源、接口、排错的顺序建立可直接使用的做法。

3.1 用回调排队观察循环行为

3

call_soon 登记下一轮可执行的普通回调，同一线程按登记顺序调用；call_later 接收相对延迟，call_at 接收循环单调时钟的绝对时间。不要把 time.time() 的日历时间传给 call_at。回调必须是短小的同步函数，不能直接传异步函数并期待循环自动 await。

import asyncio

async def worker():
    # 只有进入正在执行的 Task 后，current_task 才有业务意义。
    print("当前任务：", asyncio.current_task().get_name())
    await asyncio.sleep(0.01)
    return "完成"

async def main():
    loop = asyncio.get_running_loop()
    loop.call_soon(print, "回调一")
    loop.call_soon(print, "回调二")  # 与回调一保持登记顺序
    removed = loop.call_later(1, print, "这条已取消")
    removed.cancel()
    loop.call_later(0.02, print, "相对定时回调")
    loop.call_at(loop.time() + 0.03, print, "绝对定时回调")
    task = loop.create_task(worker(), name="查询任务")
    print("主协程先执行到这里")
    print(await task)  # 等待时允许已登记的回调与任务运行
    await asyncio.sleep(0.05)  # 给本例定时回调留出执行时间

asyncio.run(main())

默认任务工厂下，创建任务意味着将其安排执行，不意味着创建语句返回时它已经完成；如果应用显式启用了立即执行任务的工厂，启动时机可能不同。上例依赖的关键保证是回调登记顺序和显式等待，不应扩展推断所有定时回调的精确输出顺序。

在普通协程里，asyncio.create_task() 通常比先取 loop 更简洁。只有需要定时回调或底层接口时才取循环。创建任务后保存引用，并决定在哪里等待、在哪里取消；不能把“程序马上退出时 run 会帮忙取消”当成正常业务收尾策略。

3.2 用 TaskGroup 管理同一批数据源查询3 个重点▾ 点开看本节重点
本节重点
  • 以下改写素材 A 的数据库、API、缓存查询示例
  • 「TaskGroup」 退出时等待组内任务结束；正常退出后可读取结果
  • 如果某个任务出现非取消异常，组会取消其余任务、等待清理，再抛出异常组
3

以下改写素材 A 的数据库、API、缓存查询示例。TaskGroup 退出时等待组内任务结束；正常退出后可读取结果。如果某个任务出现非取消异常，组会取消其余任务、等待清理，再抛出异常组。只有在成功路径才能直接对每个任务调用 result()。

import asyncio

async def fetch_data(source, delay):
    await asyncio.sleep(delay)  # 模拟课件中的数据源 I/O
    return {"source": source, "data": [1, 2, 3]}

async def main():
    async with asyncio.TaskGroup() as group:
        tasks = [
            group.create_task(fetch_data(name, delay), name=name)
            for name, delay in [("数据库", 0.05), ("API", 0.1), ("缓存", 0.02)]
        ]
    print([task.result() for task in tasks])  # 列表保留创建顺序

asyncio.run(main())
选择 一个子任务失败时的默认行为 适用判断
TaskGroup 取消同组剩余任务，等待退出，汇总非取消异常 一组调用必须共同成功，失败后应尽快收尾
gather 首个异常向调用者传播，其他任务通常继续 需要按输入顺序聚合，并已设计失败收尾
gather(return_exceptions=True) 等待全部结束，把异常作为结果项返回 每个任务独立，允许部分成功

TaskGroup 不会回滚已经提交的数据库写入或已经完成的外部操作；它管理的是任务生命周期。取消信号也不是瞬间强制杀死代码。若业务需要事务或补偿，必须另行设计，不能把“其他任务被取消”理解成“前面什么也没发生”。

3.3 取消请求、处理清理，再传播取消

3

task.cancel() 发出取消请求，通常在任务下一次可以恢复的挂起点注入 CancelledError。它不等于任务已经结束。调用者还应 await 该任务，确认退出和清理都发生了。CancelledError 继承自 BaseException，普通 except Exception 捕获不到它；不要为了方便改成吞掉所有异常。

import asyncio

async def fetch_data():
    try:
        print("开始查询")
        await asyncio.sleep(10)
    except asyncio.CancelledError:
        print("收到取消，记录查询已停止")
        raise  # 保留取消语义，让所有者知道任务没有成功
    finally:
        print("释放模拟连接")  # 实际资源应配合 async with 管理

async def main():
    task = asyncio.create_task(fetch_data(), name="可取消查询")
    await asyncio.sleep(0.01)
    task.cancel()
    try:
        await task  # 请求取消以后，等待它真正结束
    except asyncio.CancelledError:
        print("调用者确认取消：", task.cancelled())

asyncio.run(main())

清理应尽量短小、明确。若清理本身还需要异步 I/O，要考虑再次取消和关闭超时，不应无边界等待。压住取消不再抛出，可能破坏 TaskGroup 和 timeout 的内部协作；入门阶段应坚持“清理后重新抛出”。

3.4 shield 保护被等待任务，但不保护外层调用者3 个重点▾ 点开看本节重点
本节重点
  • 「shield」 让外层等待被取消时，不把这次取消继续传播给内部任务
  • 下面只是数据源查询的取消机制演示，不是在推荐所有请求断开以后仍继续工作
  • 它不会阻止内部任务被其他代码直接取消，也不会让任务跨越事件循环关闭继续生存
3

shield 让外层等待被取消时，不把这次取消继续传播给内部任务。它不会阻止内部任务被其他代码直接取消，也不会让任务跨越事件循环关闭继续生存。下面只是数据源查询的取消机制演示，不是在推荐所有请求断开以后仍继续工作。

import asyncio

async def fetch_data():
    await asyncio.sleep(0.05)
    return "查询完成"

async def main():
    task = asyncio.create_task(fetch_data())  # 保持强引用
    try:
        async with asyncio.timeout(0.01):
            await asyncio.shield(task)
    except TimeoutError:
        print("外层等待超时，内部取消状态：", task.cancelled())
    print(await task)  # 所有者仍负责等待并处理内部结果

asyncio.run(main())

这里超时上下文取消了当前等待者，shield 隔离了向内部查询的取消传播；退出上下文后由所有者继续等待查询。若内部任务最终抛异常，也必须读取并处理。盲目 shield 所有下游请求会让已经失去业务意义的请求继续消耗资源，所以必须先明确保护理由和最终回收位置。

4.1 异步上下文管理器负责进入和退出3 个重点▾ 点开看本节重点
本节重点
  • 「async with」 会等待 「__aenter__」 获取资源，并在离开时等待 「__aexit__」 释放资源
  • 以下保留素材 B 模拟连接池的教学方式，列表只是资源状态标志，不能当作真正数据库连接池使用
  • 返回 「False」 表示不吞掉业务异常；省略返回值的效果也一样
3

async with 会等待 __aenter__ 获取资源，并在离开时等待 __aexit__ 释放资源。以下保留素材 B 模拟连接池的教学方式，列表只是资源状态标志，不能当作真正数据库连接池使用。返回 False 表示不吞掉业务异常；省略返回值的效果也一样。

import asyncio

class AsyncDatabasePool:
    async def __aenter__(self):
        await asyncio.sleep(0.01)  # 模拟建立连接
        self.pool = []
        print("连接池已创建")
        return self

    async def execute(self, query):
        await asyncio.sleep(0.01)
        return f"Result of: {query}"

    async def __aexit__(self, exc_type, exc_value, traceback):
        await asyncio.sleep(0.01)  # 模拟关闭连接
        self.pool = None
        print("连接池已关闭")
        return False  # 业务异常继续向外传播

async def main():
    async with AsyncDatabasePool() as pool:
        print(await pool.execute("SELECT * FROM users"))

asyncio.run(main())

如果 __aenter__ 获取到一半就失败，Python 不会再为这次进入调用 __aexit__，因此进入方法内部也要负责释放已获取的部分资源。真实项目优先使用库已经提供的异步上下文接口，避免手写一套容易遗漏异常分支的开关逻辑。

4.2 异步生成器逐项产出，async for 逐项等待

3

素材 A 的 AsyncTimer 与 async_range 可以组合观察逐项消费。异步生成器同时包含 async def 和 yield；调用它得到异步迭代对象，不能直接 await async_range(...)。每次迭代等待下一项，不意味着所有数据预先并发获取。

import asyncio
import time
from contextlib import aclosing

class AsyncTimer:
    async def __aenter__(self):
        self.start = time.perf_counter()
        return self

    async def __aexit__(self, exc_type, exc_value, traceback):
        print(f"耗时：{time.perf_counter() - self.start:.3f} 秒")
        return False

async def async_range(n):
    try:
        for i in range(n):
            await asyncio.sleep(0.01)  # 模拟等待下一项
            yield i
    finally:
        print("生成器已关闭")

async def main():
    async with AsyncTimer():
        # 提前 break 时，aclosing 也会及时关闭生成器。
        async with aclosing(async_range(5)) as numbers:
            async for number in numbers:
                print(number)
                if number == 2:
                    break

asyncio.run(main())

异步生成器适合课件中的逐块响应，但前提是读取下一块时也使用非阻塞接口。素材 D 在异步生成器内部写了普通 for chunk in stream，如果底层同步迭代会等待网络，仍会阻塞循环。应优先选择 SDK 的异步流并使用 async for；不能只把外层函数改成 async 就认定改造完成。

下面把素材 A 的多数据源查询和素材 D 的 SSE 封装方式组合成一个最小服务。为便于本机复现，下游也定义在同一应用内，通过 HTTPX 访问本机接口；这是教学安排，生产中应改为受控的真实下游地址。URL 固定，示例不会把客户端任意传入的地址当作请求目标。

先执行 pip install fastapi uvicorn httpx，将代码保存为 app.py，然后执行 uvicorn app:app --host 127.0.0.1 --port 8000。浏览器访问 http://127.0.0.1:8000/aggregate 可查看并发汇总，运行 curl -N http://127.0.0.1:8000/stream 可观察 SSE。若更换端口，代码内下游端口也需要一起修改。

# 依赖：pip install fastapi uvicorn httpx
import asyncio
import json
from contextlib import asynccontextmanager

import httpx
from fastapi import FastAPI, HTTPException, Request
from fastapi.responses import StreamingResponse

@asynccontextmanager
async def lifespan(app: FastAPI):
    # 按应用生命周期复用连接池，而不是每个请求重新创建客户端。
    app.state.limit = asyncio.Semaphore(8)
    async with httpx.AsyncClient(
        timeout=httpx.Timeout(2.0),
        limits=httpx.Limits(max_connections=8, max_keepalive_connections=8),
    ) as client:
        app.state.client = client
        yield

app = FastAPI(lifespan=lifespan)

@app.get("/downstream/{source}")
async def downstream(source: str):
    await asyncio.sleep(0.05)  # 本机模拟下游 I/O
    return {"source": source, "data": [1, 2, 3]}

async def fetch_source(request: Request, source: str):
    async with request.app.state.limit:
        response = await request.app.state.client.get(
            f"http://127.0.0.1:8000/downstream/{source}"
        )
        response.raise_for_status()
        return response.json()

@app.get("/aggregate")
async def aggregate(request: Request):
    try:
        async with asyncio.timeout(3):  # 包括排队等待的整体预算
            async with asyncio.TaskGroup() as group:
                tasks = [
                    group.create_task(fetch_source(request, name))
                    for name in ("database", "api", "cache")
                ]
        return {"results": [task.result() for task in tasks]}
    except TimeoutError:
        raise HTTPException(status_code=504, detail="汇总等待超时") from None
    except ExceptionGroup:
        # 本例任务体仅做下游调用；实际项目应细分异常并记录内部原因。
        raise HTTPException(status_code=502, detail="下游调用失败") from None

@app.get("/stream")
async def stream(request: Request):
    async def events():
        # 流已经发送响应头后，错误应按流协议表达。
        try:
            async with asyncio.timeout(3):
                async with asyncio.TaskGroup() as group:
                    tasks = [
                        group.create_task(fetch_source(request, name))
                        for name in ("database", "api", "cache")
                    ]
                    for completed in asyncio.as_completed(tasks):
                        data = await completed
                        yield "data: " + json.dumps(
                            {"content": data, "done": False}, ensure_ascii=False
                        ) + "\n\n"
            yield 'data: {"done": true}\n\n'
        except (TimeoutError, ExceptionGroup):
            yield 'data: {"error": "下游响应失败", "done": true}\n\n'
        # 不捕获 CancelledError，让断开连接引发的取消继续向任务组传播。

    return StreamingResponse(events(), media_type="text/event-stream")

这个示例的 /aggregate 会在同一请求内并发查询三个数据源，再按创建顺序汇总；/stream 则按完成顺序输出每个下游的完整 JSON。它演示的是“多个结果逐个返回”，不是把某个下游 HTTP 响应体逐字节透传。若需要透传，使用 HTTPX 的流式上下文与 aiter_bytes() 或 aiter_lines()，并让上下文覆盖生成器消费的整个阶段。

信号量放在应用生命周期内，因此同一进程里的多个入口请求共享并发预算；如果放在接口函数内部，它只约束单个请求。启动多个 worker 后，每个进程有独立预算，八个名额不会自动变成全局八个。对外服务还需要入口限流，因为信号量只控制执行，不限制有多少入口请求正在排队。

HTTPX 的超时覆盖连接、读取、写入和池等待等阶段，整体 timeout 再约束这次业务的总等待。连接池复用减少重复握手，但并不代替业务限流。不要在 FastAPI 已经运行的循环里再次调用 asyncio.run，也不要自己关闭框架提供的循环。断开连接后的取消行为依赖服务端及框架版本，部署时应验证流消费者退出后子任务是否清理。

6.2 requests 等同步库塞进 async

3

❌ requests.get 即便写在 async 函数里，网络等待仍是同步的；✅ 首选原生异步客户端，已经采用 HTTPX 的程序可直接参照上一节。无法替换同步库时，用 to_thread 桥接。以下通过同步标准库 HTTP 客户端访问本机临时服务，展示同类阻塞边界，不依赖 requests，也不访问外网。

import asyncio
import threading
from http.server import BaseHTTPRequestHandler, ThreadingHTTPServer
from urllib.request import urlopen

class Handler(BaseHTTPRequestHandler):
    def do_GET(self):
        self.send_response(200)
        self.end_headers()
        self.wfile.write(b"ok")

    def log_message(self, *args):
        pass  # 保持教学输出简洁

def sync_get(url):
    with urlopen(url, timeout=1) as response:
        return response.read().decode()

async def wrong(url):
    return sync_get(url)  # ❌ 等价风险：在这里直接调用 requests.get

async def correct(url):
    return await asyncio.to_thread(sync_get, url)  # ✅ 在线程里等待同步 I/O

async def main(url):
    print(await asyncio.gather(correct(url), correct(url)))

if __name__ == "__main__":
    server = ThreadingHTTPServer(("127.0.0.1", 0), Handler)
    thread = threading.Thread(target=server.serve_forever, daemon=True)
    thread.start()
    try:
        asyncio.run(main(f"http://127.0.0.1:{server.server_port}/"))
    finally:
        server.shutdown()
        server.server_close()
        thread.join()  # 关闭本例创建的服务线程

取消 to_thread 的等待者通常不会终止已经运行的线程，所以同步函数自身仍要设置网络超时。线程池也有容量；如果输入无界，必须在提交线程工作之前施加背压。桥接适合迁移同步 I/O，不应成为无限堆积阻塞调用的借口。

6.4 gather 一个任务抛异常，不能假定其余任务已停止

3

❌ 捕获 gather 的异常以后立刻关闭共享客户端，可能使仍在运行的兄弟任务访问已关闭资源。✅ 可以选择 TaskGroup 的整体失败策略，或像下面一样显式取消剩余任务并等待。默认 gather 传播异常后可能已经完成，再调用它的 cancel() 未必能取消尚在运行的子任务，因此要保留子任务引用。

import asyncio

async def fetch_data(name, fail=False):
    await asyncio.sleep(0.01 if fail else 0.05)
    if fail:
        raise ValueError(f"{name} 查询失败")
    return name

async def wrong():
    try:
        await asyncio.gather(fetch_data("API", True), fetch_data("缓存"))
    except ValueError:
        print("❌ 假定所有调用已经停止，立即关闭资源")

async def main():
    tasks = [asyncio.create_task(fetch_data("API", True)),
             asyncio.create_task(fetch_data("缓存"))]
    try:
        print(await asyncio.gather(*tasks))
    except ValueError as error:
        print(error)
    finally:
        for task in tasks:
            if not task.done():
                task.cancel()  # ✅ 取消仍在进行的兄弟任务
        await asyncio.gather(*tasks, return_exceptions=True)  # 等待清理
    print("现在可以关闭共享资源")

asyncio.run(main())

使用 return_exceptions=True 汇总独立任务时，应逐项判断结果是否为异常，不能直接把异常对象当成成功数据继续处理。单个子任务被取消不会自动让 gather 取消其他子任务；反过来，gather 自身被取消时会向未完成子任务传播取消。区分这两种方向，才能写对超时与主动停止逻辑。

6.5 asyncio.Lock 与跨任务死锁3 个重点▾ 点开看本节重点
本节重点
  • 单线程不代表没有竞争：只要读取与写入之间存在挂起点，别的任务就可能修改共享状态
  • 另一个容易漏掉的坑是在同一个任务中重复进入同一把 asyncio 锁，同样会等待自己释放锁
  • 「asyncio.Lock」 可以保护同一循环内的协程临界区，但它不是可重入锁，也不是线程锁
3

单线程不代表没有竞争：只要读取与写入之间存在挂起点，别的任务就可能修改共享状态。asyncio.Lock 可以保护同一循环内的协程临界区，但它不是可重入锁，也不是线程锁。持锁等待一个必须获取同一把锁才能结束的子任务，会形成跨任务等待环。

❌ 下面的 parent 持锁等待 child，而 child 等锁；✅ 在等待子任务前退出锁作用域。对多个锁，也应约定一致的获取顺序，并缩小持锁范围；不要把长时间网络等待随意放进临界区。

import asyncio

async def child(lock):
    async with lock:
        print("子任务完成共享状态操作")

async def wrong(lock):
    async with lock:
        task = asyncio.create_task(child(lock))
        await task  # ❌ parent 等 child，child 等 parent 释放锁

async def correct(lock):
    async with lock:
        print("父任务完成共享状态操作")
    await child(lock)  # ✅ 等待时已经释放锁

async def main():
    # 用超时有界演示错误路径，避免示例永久挂起。
    try:
        async with asyncio.timeout(0.03):
            await wrong(asyncio.Lock())
    except TimeoutError:
        print("检测到等待环，超时后取消并释放锁")
    await correct(asyncio.Lock())

asyncio.run(main())

超时只是把卡住的程序拉回来，不是死锁的根治方案。修复仍需画出谁持有什么、谁在等谁，并打破等待环。另一个容易漏掉的坑是在同一个任务中重复进入同一把 asyncio 锁，同样会等待自己释放锁。

6.6 无限创建 Task，不回收也不背压

3

❌ 无限循环里 create_task，既不限制数量也不读取结果，会使待处理工作持续增长；如果又把完成任务永久存进列表，还会保留结果和异常引用。✅ 使用固定数量消费者和有界队列，让生产者在队列满时暂停。下面是素材 B 生产者消费者模式的缩小版，终止标记也必须对应 task_done()。

import asyncio

async def fetch_data(item):
    await asyncio.sleep(0.01)
    return item

async def wrong():
    item = 0
    while True:
        asyncio.create_task(fetch_data(item))  # ❌ 创建无上限且无人收结果
        item += 1
        await asyncio.sleep(0)  # 即使让出循环，也没有背压

async def main():
    queue = asyncio.Queue(maxsize=4)  # ✅ 输入积压有上限

    async def consume():
        while True:
            item = await queue.get()
            try:
                if item is None:
                    return
                print(await fetch_data(item))  # 及时消费结果，不无限缓存
            finally:
                queue.task_done()

    async with asyncio.TaskGroup() as group:
        for _ in range(2):
            group.create_task(consume())  # 固定两个消费者
        for item in range(10):
            await queue.put(item)  # 满时挂起生产者，形成背压
        for _ in range(2):
            await queue.put(None)
        await queue.join()

asyncio.run(main())

这里同时存在的任务数量基本固定，而不是与输入规模一起增长。若消费者异常，TaskGroup 会取消生产者所在的主体，避免无限等待 join()。后台任务并非天然泄漏：真正的问题是没有所有者、没有并发上限、没有结果与异常回收，以及没有停机策略。小批量数据可以 gather，大批量或持续输入应优先用队列。

7.1 开启调试并观察未完成任务3 个重点▾ 点开看本节重点
本节重点

  • 调试会增加开销，输出没有告警也不等于程序不存在死锁或资源泄漏
  • 「asyncio.all_tasks()」 返回当前循环中尚未完成的 Task，包含正在检查的当前任务
3

脚本可以用 PYTHONASYNCIODEBUG=1 python demo.py 启动调试；跨平台也可传 asyncio.run(main(), debug=True)。配合日志后，可发现慢回调、部分线程使用错误以及未读取的异常。调试会增加开销，输出没有告警也不等于程序不存在死锁或资源泄漏。

asyncio.all_tasks() 返回当前循环中尚未完成的 Task，包含正在检查的当前任务。任务命名能让排障更直接；print_stack() 可查看挂起位置。不要因此遍历打印业务参数、请求正文或凭据，尤其不要把生产栈信息直接返回给接口调用者。

import asyncio
import logging

async def fetch_data():
    await asyncio.sleep(0.05)
    return "完成"

async def main():
    loop = asyncio.get_running_loop()
    loop.slow_callback_duration = 0.05  # 超过阈值的执行片段值得检查
    task = asyncio.create_task(fetch_data(), name="待排查查询")
    await asyncio.sleep(0)  # 让查询进入挂起状态
    for pending in asyncio.all_tasks():
        print(pending.get_name(), "是否当前任务：", pending is asyncio.current_task())
        if pending is task:
            pending.print_stack(limit=1)
    print(await task)

logging.basicConfig(level=logging.DEBUG)
asyncio.run(main(), debug=True)

all_tasks() 是诊断快照，不是资源管理器；任务完成后便不会继续列在其中。要排查“Task exception was never retrieved”，仍需找到任务创建者并建立 await 或结果处理。排查卡顿时先看全局心跳是否也暂停，再检查同步网络库、同步磁盘操作和长 CPU 段，最后分析锁与依赖关系。

7.2 timeout 与 wait_for 的取消对象不同

3

asyncio.timeout 在 Python 3.11+ 提供异步上下文，可覆盖多步等待，超时会取消当前任务，并在上下文外把它转换成 TimeoutError；应在上下文外捕获。wait_for 直接等待一个 awaitable，超时通常取消被等待任务，并等待其取消完成，因此实际耗时可能超过所写秒数。

import asyncio

async def fetch_data():
    try:
        await asyncio.sleep(1)
        return "结果"
    finally:
        print("查询清理完成")

async def main():
    try:
        async with asyncio.timeout(0.02):
            await fetch_data()  # 也可以在此放入多次相关 await
    except TimeoutError:
        print("timeout：整个操作预算用尽")

    task = asyncio.create_task(fetch_data())
    try:
        await asyncio.wait_for(task, timeout=0.02)
    except TimeoutError:
        print("wait_for：被等待任务已取消：", task.cancelled())

asyncio.run(main())

两者都依赖协作式取消，不能及时打断当前线程中的 time.sleep 或无限 CPU 循环。等待已完成后再检查超时不等于拥有实时抢占能力。将超时与 shield 组合会改变取消传播，只有确认需要让内部任务继续并能够回收它时才这样做。

自查时沿一次请求的路径逐项核对：入口是否复用框架循环；每个同步调用是否已替换或转移到线程；每个 Task 是否有所有者；并发数与队列长度是否分别有上限；异常路径是否等待兄弟任务退出；取消是否清理后重抛；客户端与生成器是否按作用域关闭；超时是否覆盖排队和处理全过程。检查这些边界，通常比增加更多 create_task 更能改善稳定性。

事件循环管理可执行工作，协程负责在等待时合作让出控制权；TaskGroup、异步上下文和有界队列分别明确任务、资源和输入的边界。选择 gather 还是 TaskGroup 前先定义失败策略，使用 shield 前先定义继续执行的所有者，设置超时前先确认调用链没有同步阻塞。课件中的模拟等待适合验证控制流；真实网络性能还要结合连接池、限流和下游承载能力测量。

  1. 观察调度与取消：改写数据源查询，让一个源失败、一个源较慢，分别用 gather 和 TaskGroup 运行。记录每个任务的开始、异常、finally 与结束，解释为什么外层收到异常时兄弟任务未必已经停止。验收要求是所有创建的任务都有结果或明确取消状态，不留下未读取异常。
  2. 实现有界批量处理：沿用素材 A 的模拟 URL 抓取，把输入扩大为一千项，使用素材 B 的队列模式，设置队列容量十、消费者五。统计当前执行数及峰值，确认峰值不超过五，并在某项失败时验证能退出，不永远等待 join。不要用一千个任务外套信号量来替代固定消费者。
  3. 验证接口失败边界：运行 FastAPI 示例，将模拟下游延迟提高到超过总预算，观察 /aggregate 的状态码和 /stream 的结束事件，再恢复正常。随后让一个下游返回错误，检查其他任务是否收尾，说明为什么流发送响应头后不能再靠普通 HTTP 状态码表达后续失败。测试只访问本机模拟下游。
