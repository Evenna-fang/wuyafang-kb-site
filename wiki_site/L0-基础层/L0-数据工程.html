WHY

2

数据工程先解决「为什么必须持久化、为什么要控制质量」，再谈工具。没有这一层，AI 应用重启即失忆、重复数据挤占检索名额、业务统计失去一致口径；装好数据库也不等于数据已经可用。

1. 这篇文档解决什么问题

3

AI 应用不是「会调模型」就够了，真正决定能不能落地的是数据从哪来、存哪里、怎么查、怎么被模型用。这篇文档面向刚接触数据工程的学习者，把以下问题一次讲清楚：

  1. MySQL 装在哪、怎么装、装完怎么验证（Windows 下最常见的一条路径）。
  2. SQL 的四类语句各干什么：DDL 定义结构、DML 改数据、DQL 查数据、DCL 管权限。
  3. Python 怎么连 MySQL（pymysql）和 SQLite（sqlite3），把增删改查写成可复用函数。
  4. AI 应用里数据库到底存什么——对话历史、文档元数据、评测日志。

适用场景：要做一个「能记住用户之前说过什么」的 AI 应用；要把爬虫/业务数据入库再给 RAG 当知识源；要接手别人的数据库但不知道表怎么设计。

前置条件：装好 Python 3.10+（见 L0-环境与工具链）；有 Windows 管理员权限或 Linux/macOS 终端；知道 pip install 怎么用。

2. 让数据库服务 AI 应用

3

数据库在 AI 应用里不是主角，但缺了它，「AI 有记忆」就是空话。实战讲义的判断很直接：「所谓『AI 有记忆』，真相是：你的程序保存信息 → 下次请求时取出来 → 重新塞进 Context」。所以数据库的职责是持久化 + 可查，真正的记忆拼装发生在应用层。

三条落地建议：

  1. 会话历史入库，重启不丢：用下面的 messages 表，save_message 写、load_history 读，历史超过窗口就裁剪（保留 system + 最近 N 条）。
  2. 文档元数据与正文分离：documents 表存文件名、页码、来源路径；正文切块后进向量库。这样 RAG 回答时能标注「出自第几页」，可追溯。
  3. 调用日志单独一张表：每次模型调用记时间、模型名、token 用量、耗时、是否成功。出问题时按 logs 查，比翻聊天记录快。

数据库管数据，向量库管语义——RAG 项目里两者分工见 L4-RAG工程 与课件《RAG基础》「向量数据库」小节。

3. 数据质量与去重：为什么先去重再入库

3

数据库只是容器，容器里的数据质量决定 AI 应用的上限。课件《数据存储》把「数据去重」列为独立一节（第七个学习目标），说明它在数据管道里和存储同等重要。

RAG 项目里重复数据的代价被放大：同一段文本入库多次，检索时它会霸占 Top-K 的多个坑位，把真正多样的上下文挤出去，答案质量直接下降。业务库里的重复则导致统计口径错乱（订单算两次）。所以数据工程的标准流水线是：采集 → 清洗 → 去重 → 入库 → 校验，去重在入库之前。

WHAT / WHYT

2

这一部分建立存储选型与关系模型的概念边界：文件、关系库、文档库、缓存和向量库不是互相替代的「同级工具」，SQL 也不只是查询语句。先按数据形态、访问方式、一致性和并发需求选容器，再进入 HOW 照命令实操。

1. 数据存储的全景：文件、关系库、向量库各管什么

3

课件《数据存储》开篇把存储分成两大类：文本文件存储（TXT、JSON、CSV）和数据库存储（MySQL、MongoDB、Redis）。三类各有边界：

  • 文件（TXT/JSON/CSV）：零配置、好调试，适合小批量中间结果、配置、日志。缺点是不利检索、并发写会互相覆盖。
  • 关系型数据库（MySQL / PostgreSQL / SQLite）：表结构 + 主外键 + 事务，适合「有明确字段、要多表关联、要精确查询」的业务数据。RAG 项目里存用户、会话、文档元数据、调用日志，基本都用它。
  • 向量数据库（Chroma / Milvus / pgvector）：存 Embedding 向量、支持相似度检索。RAG 检索层靠它，但它不适合当业务库——课件原话：「我们这个向量的数据存在哪里，存 mysql MongoDB？这种数据库我们可以做查询语句，但是我们没有办法做空间的计算」。所以真实项目里常见「关系库存业务数据 + 向量库存语义检索」双库并存。

什么时候选什么：数据是表格化的、字段固定、要 JOIN → MySQL；数据是半结构化文档、字段可变 → MongoDB；要按语义相似找片段 → 向量库；只是缓存或去重集合 → Redis。AI 应用里这四样常常同时出现，别指望一个库通吃。

2. SQL 语句四大家族

3

SQL（Structured Query Language）按用途分四类，面试和实战都围绕这四类转。

家族 全称 干什么 代表语句
DDL Data Definition Language 定义/修改表结构 CREATE TABLE / ALTER TABLE / DROP TABLE
DML Data Manipulation Language 增删改数据行 INSERT / UPDATE / DELETE
DQL Data Query Language 查询数据 SELECT（含 WHERE / JOIN / GROUP BY）
DCL Data Control Language 权限控制 GRANT / REVOKE

官方语法索引：https://dev.mysql.com/doc/refman/8.4/en/sql-data-definition-statements.html（DDL）、https://dev.mysql.com/doc/refman/8.4/en/select.html（SELECT）。

3. 关系型数据库的原理底座：为什么是「二维表」

3

课件《数据存储》在进入 MySQL 之前先讲清了关系模型的本质，这段判断标准值得记住：

关系型数据库是基于关系模型的数据库，而关系模型是通过二维表来保存的，所以它的存储方式就是行列组成的表，每一列是一个字段，每一行是一条记录。表可以看作某个实体的集合，而实体之间存在联系，这就需要表与表之间的关联关系来体现，如主键外键的关联关系。多个表组成一个数据库，也就是关系型数据库。

这句话拆开是三层含义：

  1. 表 = 实体的集合。一张 students 表装所有学生，一行一个学生，一列一个属性。
  2. 行 = 记录，列 = 字段。字段有类型约束（INT / VARCHAR / TEXT），这是「数据完整性」的来源——数据库替你挡住「年龄写成字符串」这种低级错误。
  3. 表间联系靠主外键。enrollments 表用 student_id 指向 students.id，把「谁选了什么课」这个事实单独建模，而不是把课程名冗余地塞进学生表。

关系型数据库有多种，课件列了 SQLite、MySQL、Oracle、SQL Server、DB2。对初学者的建议路径是：SQLite 入门（零配置）→ MySQL 上生产（多用户、要权限）→ PostgreSQL 要高级特性（pgvector、JSONB）。

3.1 索引：让查询从全表扫描变点查

课件没展开索引，但它是 SQL 性能的第一杠杆。索引就像书的目录：没索引时 WHERE name='柏汌' 要逐行比对（全表扫描），有索引时直接定位。代价是写入变慢（每次 INSERT/UPDATE 都要维护索引）且占空间。给 WHERE、JOIN、ORDER BY 常用的字段加索引，给高频写的表少加索引。主键自带索引，所以 WHERE id='00001' 永远最快。

3.2 事务与 ACID

事务（Transaction）保证一组操作「要么全成功、要么全失败」，ACID 是四个特性：原子性（Atomicity，全做或全不做）、一致性（Consistency，状态合法）、隔离性（Isolation，并发互不干扰）、持久性（Durability，提交后不丢）。AI 应用里典型场景：扣用户额度 + 写调用日志，两件事必须同生共死，否则会出现「扣了钱没记录」。Python 侧 db.commit() / db.rollback() 就是事务边界。

4. 非关系型存储对照：MongoDB 与 Redis 在数据管道里的位置

3

MySQL 只是数据工程的一块拼图。课件《数据存储》在讲完 MySQL 之后紧接着讲 MongoDB 与 Redis，这两个在 AI 数据管道里也有固定位置，提前知道边界能少走弯路。

4.1 MongoDB：字段不固定的半结构化文档

MongoDB 是 C++ 编写的非关系型数据库，存储形式类似 JSON 对象，字段值可以包含其他文档、数组及文档数组，非常灵活。

什么时候选 MongoDB：爬虫抓回来的原始 JSON、字段每页都不一样的网页数据、原型期还没想清楚 schema 的日志。什么时候别用：需要跨表 JOIN、强事务、唯一约束的业务数据——那是 MySQL 的地盘。翻车形态：把 MongoDB 当主业务库，上线后要加唯一索引才发现同一批数据已重复入库，得先写脚本去重再补索引。

4.2 Redis：去重与缓存的持久化容器

课件把去重分成两个概念，判断逻辑很清楚：

根据给定的判断依据和给定的去重容器，将原始数据逐一进行判断，判断去重容器中是否有该数据，如果没有那就把该数据对应的判断依据添加去重容器中，同时标记该数据是不重复数据，如果有就不添加，同时标记该数据是重复数据。

去重容器分两种：临时容器（list、set 等内存结构，程序一关就没了，优点是简单，缺点是无法共享、无法持久化）和持久化容器（redis、mysql 等数据库，优点是持久化、共享，缺点是实现复杂些）。爬虫场景下推荐持久化容器，否则重启后重复抓一遍全站。

特征值计算的三种常见做法（课件原文）：信息摘要 hash 算法（指纹）、SimHash 算法（模糊文本）、布隆过滤器（上亿级别数据去重）。

什么时候用 Redis：去重、限流计数、会话缓存、排行榜这类「快、可丢、要共享」的数据。什么时候别用：把它当主存储——Redis 是内存数据库，配置不当重启就丢数据，业务主数据必须落 MySQL/PostgreSQL。

5. 文件层存储：TXT / JSON / CSV 什么时候够用

3

在把数据塞进数据库之前，先想清楚是不是真的需要数据库。课件《数据存储》前三节讲的就是文件层三种格式，它们在 AI 项目里出镜率不低。

5.1 TXT：最简单，最不利检索

TXT 几乎兼容任何平台，操作最简单，课件的评价是「它有个缺点，那就是不利于检索」。适合存爬虫的原始抓取结果、临时日志。打开模式课件列了 11 种（r / rb / r+ / w / a 等），最常用的是 r（只读）、w（覆盖写）、a（追加）。写中文记得 encoding='utf-8'，否则 Windows 默认 GBK 会出乱码。

5.2 JSON：结构化交换的主力

JSON（JavaScript Object Notation）用对象（{} 键值对）和数组（[]）自由组合表示数据，可无限嵌套。Python 的 json 模块四个方法要分清：

方法 作用
json.dumps() 把 Python 对象转换成 JSON 字符串
json.dump() 把 dict 转成字符串并写入 json 文件
json.loads() 把 JSON 字符串解码成 Python 对象
json.load() 从 json 文件读取数据

AI 应用里 JSON 是 Prompt 与结构化输出的通用载体——模型返回的 JSON 用 json.loads() 解析，解析失败要有兜底（实战讲义第 18 章专门讲 Structured Output 的三种方案）。

5.3 CSV：表格数据的纯文本形态

CSV（Comma-Separated Values）以纯文本存表格数据，比 Excel 简洁（不含公式、格式），适合导出给人看、给 pandas 读。

6. 三类特征值计算的适用边界

3
  • 信息摘要 hash（MD5/SHA1 指纹）：把整条数据压成一个定长字符串，比对快。适合「完全相同的重复」。翻车点：字段顺序或空白差异会导致指纹不同，同一内容判成两条不同数据。
  • SimHash（模糊文本）：给相似文本算相近的指纹，适合「几乎相同的重复」（如转载文章改了标点）。翻车点：阈值不好调，太松会误杀、太严漏判。
  • 布隆过滤器：用极小内存判断「一定不存在 / 可能存在」，适合上亿级别去重。翻车点：有误判率（把不存在判成存在），且不支持删除。

选型一句话：完全重复用 hash，近似重复用 SimHash，海量粗筛用布隆过滤器。

7. 常见误区：新手最容易搞混的几对概念

3
  1. 「存进数据库」≠「数据安全」：数据库只保证不丢、可查，不保证数据正确。校验要在入库前做。
  2. 「MySQL 里建了表」≠「设计好了 schema」：字段类型乱用（全 VARCHAR）、没有主键、没有索引，都是隐形债。表结构要按业务实体建模，不是按爬虫返回的 JSON 原样倒进去。
  3. 「SQL 能查」≠「适合给模型用」：模型吃的是文本片段，数据库存的是结构化行。中间要有「行 → 文本」的序列化层，这是 RAG 元数据到正文的桥。
  4. 「用了 ORM 就不用懂 SQL」：ORM 只是翻译层，慢查询、N+1、事务边界还是得靠 SQL 知识排查。实战讲义的原话：换库时「用 SQLAlchemy 做 ORM，SQL 基本不用改」——前提是你的 SQL 本身写得规范。
  5. 「向量库能替代关系库」：向量库擅长语义检索，不擅长精确条件查询、聚合统计、事务。两者是互补关系。

HOW

2

下面按可执行顺序组织：先装 MySQL，再用 SQL 和 Python 完成增删改查，随后扩展到 MongoDB、Redis 与文件存储，最后串起数据管道、安全、连接管理、表设计、RAG 元数据、排错和交付自检。示例中的账号密码仅用于本地学习，真实环境应改为最小权限账号与外部密钥配置。

1. MySQL 安装：Windows 主路径

3

素材里有两份安装教程（基础篇/day11__资料__mysql安装__msyql安装.md 与 _converted/教程_MySQL安装流程.md），步骤几乎一致，合并成一条主路径。

1.1 下载与解压

  1. 官方下载：https://dev.mysql.com/downloads/mysql/（课件提示：可跳过 Oracle 账号注册直接下载）。
  2. 国内镜像（课件提供，下载慢时用）：http://mirrors.sohu.com/mysql/MySQL-8.0/。注意镜像只覆盖 8.0 系列，要装 8.4 LTS 请走官方（MySQL 版本分为 Innovation 与 LTS 两类，见官方 https://dev.mysql.com/doc/refman/8.4/en/mysql-releases.html）。
  3. 解压到全英文、无空格的路径，例如 D:\MySQL\mysql-8.4.x-winx64。教程_MySQL安装流程.md 特别强调：路径里出现中文或空格，后面命令容易翻车。

1.2 配置环境变量

把解压目录下的 bin（例如 D:\MySQL\mysql-8.4.x-winx64\bin）加进系统变量 Path。这样任意目录下都能敲 mysql、mysqld。

1.3 初始化 + 注册服务 + 启动（管理员 cmd）

:: 在 bin 目录下，管理员身份运行 cmd
mysqld --initialize-insecure --user=mysql
:: 备注：-insecure 表示 root 初始密码为空；若用 mysqld --initialize 则生成随机初始密码
mysqld -install
net start mysql

顺序不要颠倒。课件《教程_MySQL安装流程.md》的经验：mysqld -install 回车后出现 Service successfully installed 才算成功；出现 Install of the Service Denied 就是没用管理员身份开 cmd。两份素材对 initialize 与 install 的先后顺序略有出入，只要两者都做、且都在 net start 之前即可。

1.4 登录并改密码

mysql -u root -p
:: 初始密码为空（--initialize-insecure），直接回车

进入 mysql> 后立刻改密码：

ALTER USER 'root'@'localhost' IDENTIFIED BY '你的新密码';

课件里还留了一条老写法 ALTER USER 'root'@'localhost' IDENTIFIED WITH mysql_native_password BY '...'。MySQL 8.x 默认认证插件是 caching_sha2_password，除非客户端不支持新插件才需要显式指定 mysql_native_password（该插件在 8.4 里已是遗留选项）。新项目直接 IDENTIFIED BY '...' 即可。

1.5 卸载（留作备份知识）

net stop mysql
mysqld -remove mysql

2. SQL 实操：DDL、DML、DQL 与 DCL

3

2.1 DDL：建库建表

课件《数据存储》里的原汁原味建表语句（spiders 库 students 表）：

CREATE DATABASE spiders DEFAULT CHARACTER SET utf8;

CREATE TABLE IF NOT EXISTS students (
    id   VARCHAR(255) NOT NULL,
    name VARCHAR(255) NOT NULL,
    age  INT NOT NULL,
    PRIMARY KEY (id)
);

官方 CREATE TABLE 语法：https://dev.mysql.com/doc/refman/8.4/en/create-table.html。常用字段类型速查：

  • INT：整数。自增主键写 INT AUTO_INCREMENT PRIMARY KEY（课件里爬虫入库的 ali 表就是 id int primary key auto_increment not null）。
  • VARCHAR(n)：变长字符串，最多 n 个字符。n 不是越大越好，索引和内存都受影响。
  • TEXT：长文本（职位描述 requirement TEXT 就是这个）。
  • DATETIME / TIMESTAMP：时间。AI 应用存消息时间戳用 TIMESTAMP DEFAULT CURRENT_TIMESTAMP。

字符集一栏：DEFAULT CHARACTER SET utf8 在 MySQL 8.x 里等价于 utf8mb3（最多 3 字节，存不下 emoji）。要存 emoji、特殊符号，写 utf8mb4。官方字符集文档：https://dev.mysql.com/doc/refman/8.4/en/charset.html。这是新手最常见的中文乱码根因。

2.2 DML：增删改

INSERT INTO students(id, name, age) VALUES ('00001', '柏汌', 19);

UPDATE students SET age = 20 WHERE id = '00001';

DELETE FROM students WHERE id = '00001';

UPDATE / DELETE 不带 WHERE 就是全表操作，生产第一条铁律：先写 WHERE，确认影响行数再提交。事务（BEGIN / COMMIT / ROLLBACK）能在写错时反悔，Python 侧对应 db.commit() / db.rollback()。

2.3 DQL：查询

SELECT id, name, age
FROM students
WHERE age >= 18
ORDER BY age DESC
LIMIT 10;

-- 多表关联（官方 JOIN 语法：https://dev.mysql.com/doc/refman/8.4/en/join.html）
SELECT s.name, c.course
FROM students s
JOIN enrollments e ON s.id = e.student_id
JOIN courses c     ON e.course_id = c.id;

SELECT 的执行顺序是 FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY → LIMIT，理解这个顺序，写聚合查询就不会把别名用错地方。

2.4 DCL：权限

CREATE USER 'app'@'%' IDENTIFIED BY 'strong_password';
GRANT SELECT, INSERT ON spiders.* TO 'app'@'%';
FLUSH PRIVILEGES;

AI 应用连库时不要用 root，建一个只有必要权限的账号，泄漏时损失可控。

建表 + 插入的完整函数（课件「3.创建数据表」「4.插入数据」）：

import pymysql

def create_table():
    db = pymysql.connect(host="localhost", user="root", password="root", db="spiders")
    cursor = db.cursor()
    sql = '''
    CREATE TABLE IF NOT EXISTS students (
        id VARCHAR(255) NOT NULL,
        name VARCHAR(255) NOT NULL,
        age INT NOT NULL,
        PRIMARY KEY (id))
    '''
    try:
        cursor.execute(sql)
        print("CREATE TABLE SUCCESS.")
    except Exception as ex:
        print(f"CREATE TABLE FAILED,CASE:{ex}")
    finally:
        db.close()

def insert_record(id_, user, age):
    db = pymysql.connect(host='localhost', user='root', password='root', db='spiders')
    cursor = db.cursor()
    sql = 'INSERT INTO students(id, name, age) values(%s, %s, %s)'
    try:
        cursor.execute(sql, (id_, user, age))
        db.commit()
        print('数据插入成功...')
    except Exception as e:
        print(f'数据插入失败: {e}')
        db.rollback()
    finally:
        db.close()

if __name__ == '__main__':
    create_table()
    insert_record('00001', '柏汌', 18)

关键点：cursor.execute(sql, (参数...)) 用 %s 占位符，绝不要用 f-string 拼 SQL——那是 SQL 注入的经典入口。db.commit() 不写，插入不会真正落库。

3.2 用 sqlite3 做零配置存储

AI 应用早期最省事的选择是 SQLite（Python 自带，无服务进程）。实战讲义第 37 章给出的会话表设计：

import sqlite3

conn = sqlite3.connect("app.db")
conn.execute("""
CREATE TABLE IF NOT EXISTS messages (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    conversation_id TEXT NOT NULL,
    role TEXT NOT NULL,
    content TEXT NOT NULL,
    tokens INTEGER DEFAULT 0,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
)""")
conn.commit()

def save_message(conv_id, role, content, tokens=0):
    conn.execute(
        "INSERT INTO messages (conversation_id, role, content, tokens) VALUES (?,?,?,?)",
        (conv_id, role, content, tokens))     # ← 必须用参数占位符，防 SQL 注入
    conn.commit()

def load_history(conv_id, limit=20):
    rows = conn.execute(
        "SELECT role, content FROM messages WHERE conversation_id=? "
        "ORDER BY id DESC LIMIT ?", (conv_id, limit)).fetchall()
    return [{"role": r, "content": c} for r, c in reversed(rows)]

AI 应用典型表清单（实战讲义原表）：users（用户）、conversations（会话）、messages（每条消息，含 token 数、模型名）、documents（上传文档）、knowledge_bases（知识库）、logs（调用日志）。tokens 字段存每次调用的用量，是后续做成本核算和限流的原始数据。

SQLite → PostgreSQL 的换库时机（实战讲义原话）：多用户并发、数据量大、需要 pgvector 把向量和业务数据放一起时。换的时候用 SQLAlchemy 做 ORM，SQL 基本不用改。

import hashlib

def get_md5(val):
    """把目标数据进行哈希，用哈希值去重更快"""
    md5 = hashlib.md5()
    md5.update(str(val).encode('utf-8'))
    return md5.hexdigest()

def save_data(item):
    value = get_md5(item)
    res = self.red.sadd('mg:filter', value)
    if res:
        self.collection.insert_one(item)
        print('插入成功!!!!')
    else:
        print('数据重复!!!!')

5.1 TXT 读写要点

5.3 CSV 三种写法

课件的三种写法：

import csv
# 1. 逐行写
with open('data.csv', 'w', encoding='utf-8', newline='') as csvfile:
    writer = csv.writer(csvfile)
    writer.writerow(['id', 'name', 'age'])
    writer.writerow(['10001', 'Mike', 20])

# 2. 多行一次写（二维列表）
    writer.writerows([['10002', 'Bob', 22], ['10003', 'Jordan', 21]])

# 3. 字典写入（字段名对齐更安全）

6. 数据入库的完整流程：从爬虫到 RAG 元数据

3

把前面所有零件串起来，看一个数据从「网页」到「能被 AI 用」的完整旅程。这条流水线在课件《数据存储》里是分节讲的，实际项目里它是一条连续管道。

6.1 标准流水线

采集(请求/解析) → 清洗(去噪/规范化) → 去重(hash/指纹) → 入库(文件或数据库) → 校验(抽样对账) → 服务(AI/RAG消费)

每一步的产物都是下一步的输入：

  1. 采集：requests 拿原始 HTML/JSON，BeautifulSoup / lxml / 正则提取字段。产物是 Python 的 dict/list。
  2. 清洗：去 HTML 标签、统一编码为 UTF-8、字段类型规范化（字符串转数字、时间格式统一）、空值兜底。产物是「干净的 dict」。
  3. 去重：用 MD5/SimHash 算指纹，Redis 集合或数据库唯一索引判重（见 WHAT 的「三类特征值计算的适用边界」）。产物是「不重复的 dict」。
  4. 入库：小批量、临时结果用文件（JSON/CSV）；要查询、要并发、要持久用数据库（MySQL/SQLite/MongoDB）。
  5. 校验：抽样几条和原网页对账，确认字段没串位、编码没乱、条数对得上。这一步跳过，后面 RAG 检索出错会极难排查。
  6. 服务：业务数据供应用查询；文档正文切块、向量化后进向量库供 RAG 检索，元数据（source、page）留在关系库/向量库 metadata 里做引用。

6.2 向量库一条记录长什么样

实战讲义第 24 章给出的向量库记录结构非常清楚：

向量 + 原文 + source + page + 其他 metadata

metadata 的用处是过滤——比如只在「2024 年的财务文档」里搜。这解释了为什么 WHY 的「让数据库服务 AI 应用」说「文档元数据与正文分离」：source 和 page 既存进关系库的 documents 表，也冗余进向量库的 metadata，两边都能按它过滤和引用。

6.3 三问对这条流水线的追问

  • 什么情况下用：任何「外部数据 → AI 消费」的场景都走这条流水线，尤其 RAG 知识库建设、爬虫数据中台、用户上传文档入库。
  • 什么情况下别用：数据只有几条、一次性用完、不需要追溯——直接写死在 Prompt 里更省事，别为 3 条数据建库。
  • 翻车长什么样：跳过校验直接入库，RAG 检索出来说「文档里写了 X」但翻原文根本没有；或者去重用了内容 hash 但网页有时间戳参数，每次刷新指纹都不一样，去重形同虚设。排查信号：向量库里同内容 chunk 出现多条、检索 Top-K 被同一段话霸占。改：清洗时剥掉时间戳等易变字段再算指纹；入库后抽样比对。

7. 安全与合规：数据库层面的三条底线

3

数据工程不只管「存得下」，还要管「不泄漏、不被篡改、能追责」。三条底线在 AI 应用里尤其敏感，因为数据库里往往有用户隐私和企业文档。

  1. 最小权限 + 密钥不进代码：应用连库用受限账号（见「DCL：权限」），密码放 .env 或密钥管理服务，绝不写进代码提交到 Git。实战讲义的提醒很直白：把 .env 提交到 GitHub 导致 Key 泄漏被盗刷，发生了要立刻吊销重新生成。
  2. SQL 注入防线：所有动态条件走参数占位符。cursor.execute(sql, (参数,)) 是底线，字符串拼接是禁区。输入侧再做长度/类型校验，双保险。
  3. 审计与备份：logs 表记录谁在什么时候改了什么；数据库定期备份，备份要能恢复（没验证过恢复的备份等于没有）。AI 应用里「删库跑路」的常见变体是「误操作全表 UPDATE」，事务 + 备份是最后防线。

课件里 skip-grant-tables 那种救急后门用完必须关掉，同理：任何「临时放开权限」的操作都要有回收动作，否则临时变永久。

8. 连接数据库的工程化写法：别把连接代码散落各处

3

课件里的 pymysql.connect(...) 是教学写法——每次调用都新建连接、用完关掉。真实项目里这样写会在高并发下耗尽连接数（MySQL 默认 max_connections 151，超过就报 Too many connections）。工程化改法是连接池：启动时建一批连接，用的时候借、用完还。Python 常用 SQLAlchemy 的 create_engine 或 DBUtils 的连接池。下面给一个不引第三方库的最小连接管理写法（思路借鉴实战讲义的封装风格）：

import pymysql
from contextlib import contextmanager

DB_CONFIG = {
    "host": "localhost",
    "user": "app",              # 不要用 root，见「DCL：权限」
    "password": "strong_password",
    "db": "spiders",
    "charset": "utf8mb4",       # 防中文乱码，见「DDL：建库建表」
    "cursorclass": pymysql.cursors.DictCursor,  # 查询结果返回字典，比元组好用
}

@contextmanager
def get_conn():
    """借连接：with get_conn() as conn: ... 用完自动 close"""
    conn = pymysql.connect(**DB_CONFIG)
    try:
        yield conn
        conn.commit()           # 正常退出提交事务
    except Exception:
        conn.rollback()         # 异常退出回滚
        raise
    finally:
        conn.close()

def query_users(min_age: int) -> list[dict]:
    with get_conn() as conn:
        with conn.cursor() as cursor:
            cursor.execute(
                "SELECT id, name, age FROM students WHERE age >= %s", (min_age,))
            return cursor.fetchall()

这个写法的价值：参数化 SQL（防注入）+ 自动 commit/rollback（防忘写）+ 自动 close（防连接泄漏）+ 结果是字典（row["name"] 而不是 row[1]）。三件事一次解决，是「教学代码」到「能上线代码」的最小跨越。

9. 查询进阶：聚合、分页与批量写

3

SQL 真正的威力在查询层。三个高频场景的写法：

聚合统计（每天调用多少次、平均 token 用量）：

SELECT DATE(created_at) AS day,
       COUNT(*)         AS calls,
       AVG(tokens)      AS avg_tokens
FROM messages
WHERE created_at >= '2026-10-01'
GROUP BY DATE(created_at)
ORDER BY day DESC;

分页查询（列表页展示）：

SELECT id, name, age FROM students
ORDER BY id
LIMIT 20 OFFSET 40;   -- 第 3 页，每页 20 条

LIMIT n OFFSET m 的翻车点：数据频繁增删时会漏行或重复。要稳定分页用「游标分页」（WHERE id > 上一页最后一条的 id ORDER BY id LIMIT 20）。

批量写（爬虫抓 1000 条一次性入库）：

def batch_insert(rows: list[tuple]):
    sql = 'INSERT INTO students(id, name, age) values(%s, %s, %s)'
    with get_conn() as conn:
        with conn.cursor() as cursor:
            cursor.executemany(sql, rows)   # executemany 比循环 execute 快一个量级

executemany 在 pymysql 里会自动拼成多值 INSERT 或用批量协议，1000 条数据比循环 1000 次 execute 快 10 倍以上。翻车点：批量里有一条数据类型错，整批回滚——所以入库前的清洗校验（见「数据入库的完整流程」）更重要。

10. 表设计：从爬虫字段到规范化 schema

3

课件里的 students 表（id/name/age）是教学最小例子，真实项目里表设计要考虑「以后会怎么查」。三个实用原则：

原则一：先问查询，再定字段。不要照抄爬虫返回的 JSON 原样建表（字段全是 VARCHAR、没有主键、没有索引）。先列出最常见的 3~5 个查询（按时间查、按分类查、按关键词查），再反推字段和索引。

原则二：把「会变的」和「不变的」分开。文档的原文（正文）不变，但它的解析状态、向量 ID、更新时间会变。分开建表能减少锁竞争和误更新。RAG 项目常见三张表：

-- 文档元数据（相对稳定）
CREATE TABLE documents (
    doc_id      BIGINT PRIMARY KEY AUTOINCREMENT,
    file_name   VARCHAR(255) NOT NULL,
    source_path VARCHAR(500) NOT NULL,
    file_hash   CHAR(32) NOT NULL,          -- MD5，用于去重和变更检测
    page_count  INT DEFAULT 0,
    created_at  TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    UNIQUE KEY uk_file_hash (file_hash)     -- 同一文件不重复入库
);

-- 文档切块（正文进向量库，这里只存映射）
CREATE TABLE chunks (
    chunk_id   VARCHAR(64) PRIMARY KEY,     -- 如 "doc12-p3-2"
    doc_id     BIGINT NOT NULL,
    page_no    INT NOT NULL,
    chunk_text TEXT NOT NULL,
    token_count INT DEFAULT 0,
    FOREIGN KEY (doc_id) REFERENCES documents(doc_id) ON DELETE CASCADE
);

-- 调用日志（只增不改）
CREATE TABLE call_logs (
    log_id      BIGINT PRIMARY KEY AUTOINCREMENT,
    model_name  VARCHAR(100),
    prompt_tokens INT DEFAULT 0,
    completion_tokens INT DEFAULT 0,
    latency_ms  INT DEFAULT 0,
    success     TINYINT(1) DEFAULT 1,
    created_at  TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

原则三：主键用什么。自增整数（BIGINT AUTO_INCREMENT）简单高效，适合内部表；分布式或多来源合并时用 UUID/雪花 ID，避免冲突。别用业务字段（如邮箱、文件名）当主键——业务字段会变，主键不能变。课件里 students 表用 VARCHAR(255) 的 id 当主键是教学妥协，真实项目优先用自增整数 + 业务字段建唯一索引。

11. RAG 元数据层：数据工程怎么支撑检索

3

前面 WHY 的「让数据库服务 AI 应用」说了「数据库管数据，向量库管语义」，这里把接缝讲清楚。RAG 的离线建库流程（实战讲义第 20 章的总结）：

文档 → 解析 → 切分 → Embedding → 存入向量库

数据工程在其中负责「解析后的落地」和「元数据的可查」：

  1. 解析阶段：用 pypdf / python-docx / pdfminer 抽文本，从第一步就带上 source 和 page，否则后面做不出引用（实战讲义的原话）。抽出来的文本常有乱码/多余空行，要清洗。
  2. 切分阶段：按长度切块带重叠（中文 300~600 字/块、重叠 50~100 字），优先在句号处断开。每个 chunk 生成唯一 chunk_id（如 source-p页码-序号），去重、引用、调试都要用它。
  3. 入库阶段：正文和向量进向量库（Chroma/Milvus），元数据（doc_id、page_no、source）同时写进关系库和向量库的 metadata。两边用 chunk_id 关联。
  4. 查询阶段：问题向量化后检索 Top-K chunk，同时能按 metadata 过滤（如「只在 2024 年的财务文档里搜」），命中后把 chunk 文本 + 来源信息组装进 Prompt，让模型带引用回答。

关键认知：RAG 的检索质量很大程度上取决于「入库时数据工程做得好不好」——chunk 切得好不好、元数据全不全、去重做得对不对。检索算法（余弦相似度、混合检索、精排）是锦上添花，数据质量是雪中送炭。翻车现场：花了两周调检索算法，结果发现入库时 source 全是 undefined，引用功能根本没法做，得回头重灌一遍库。

12. 三问：什么情况用 / 什么情况别用 / 翻车长什么样

3

12.1 什么情况下用（适用场景 + 前置条件）

  • 业务数据要多表关联、精确查询：订单、用户、权限、库存——MySQL 是标准答案。前置：有运维能维护实例；数据量预计百万级以上。
  • 单机小项目 / 快速原型 / 本地 AI 应用：SQLite 起步，零配置、一个文件就是库。前置：并发写需求低（SQLite 写锁是库级）。
  • AI 应用的会话、文档、日志：任何要「重启后还在」的数据都该入库，SQLite / MySQL 都行。
  • RAG 的元数据层：文档路径、页码、更新时间放关系库，和向量库一一对应，方便做引用与保鲜。

12.2 什么情况下别用（反例 + 替代方案）

  • 别用 MySQL 存 Embedding 向量做相似度检索（除非上 pgvector 扩展）：关系库没有空间索引，算余弦相似度要全表扫描。替代：Chroma / Milvus / pgvector，见 L4-RAG工程。
  • 别把大段原始文档塞进 MySQL TEXT 当知识库：检索不精准、更新痛苦。替代：正文进向量库，关系库只存元数据。
  • 别用 root 账号从应用连库：泄漏即全库失守。替代：建最小权限账号（见「DCL：权限」）。
  • 别用 f-string 拼 SQL：SQL 注入高危。替代：参数占位符 %s（pymysql）或 ?（sqlite3）。
  • 别在 SQLite 上跑高并发写：库级写锁会让请求排队。替代：换 MySQL / PostgreSQL。

12.3 翻车长什么样（真实失败形态 → 排查信号 → 怎么改）

  1. 中文写入变乱码/问号：建库用了 utf8（mb3）存不下 emoji，或连接没指定编码。排查：SHOW CREATE TABLE 看字符集、SHOW VARIABLES LIKE 'character_set%';。改：建库用 utf8mb4，连接加 charset='utf8mb4'。
  2. Access denied for user 'root'@'localhost'：密码不对或没改初始密码。排查：mysql -u root -p 手工登录试。改：走「登录并改密码」的 ALTER USER 改密码；课件里 skip-grant-tables 是救急后门，用完必须从 my.ini 删掉再重启服务。
  3. Install of the Service Denied：cmd 没用管理员身份。改：管理员重开 cmd 再 mysqld -install。
  4. Python 报 ModuleNotFoundError: No module named 'pymysql'：装到了别的解释器。排查：which python && python -m pip list | grep -i mysql。改：python -m pip install pymysql（见 L0-环境与工具链）。
  5. 插入成功但查不到：忘了 db.commit()。排查：SELECT COUNT(*) FROM ...。改：DML 后 commit；异常分支 rollback。
  6. UPDATE 把全表改了：没写 WHERE。排查：SELECT * FROM 表 LIMIT 20 对账。改：永远先写 WHERE，事务里先 SELECT 确认再 UPDATE。
  7. AI 应用重启后「失忆」：对话只存内存 list。排查：查 messages 表有没有数据。改：用 save_message 落库，启动时 load_history 恢复。
  8. 中文路径下初始化 MySQL 失败：解压路径含中文/空格。排查：mysqld --initialize 报错看路径。改：挪到全英文路径重来（课件《教程_MySQL安装流程.md》第 1 条）。

13. 数据工程的自检清单：交库之前逐条核对

3

在把数据库交给下游（应用、RAG、报表）之前，用这张清单自查。每条都能用一条 SQL 或脚本验证，不要凭感觉说「应该没问题」。

□ 表结构    主键存在且唯一；字段类型不是清一色 VARCHAR；常用查询字段有索引
□ 字符集    全库 utf8mb4；中文/emoji 写入读出无乱码
□ 权限      应用账号非 root；只有 SELECT/INSERT/UPDATE 必要权限
□ SQL 安全  全部参数化；无字符串拼接 SQL；有 SQL 注入测试用例
□ 事务      写操作有 commit/rollback；异常路径不吞异常
□ 数据质量  入库前去重；抽样 10 条和源数据对账一致；条数和源数据对得上
□ 元数据    RAG 场景下 source/page 齐全；chunk_id 唯一可追溯
□ 备份      有备份策略；至少验证过一次恢复流程
□ 日志      关键操作有审计记录；错误日志能定位到具体行
□ 性能      慢查询日志开启；Top 3 查询有执行计划（EXPLAIN）验证

这十项里最容易被跳过的是「抽样对账」和「恢复验证」——前者决定数据对不对，后者决定出事能不能救。其他项工具能查，这两项必须人工做。

数据工程的长期价值在于可复现和可维护：别人拿到你的库，能看懂表结构、能重建环境、能查出问题。如果只有你自己能维护，那不算交付，算黑箱。这也是为什么本库把数据工程放在 L0 基础层——它是所有上层应用（RAG、Agent、全栈）共用的地基，地基歪了上面全歪。

学完本篇你应该能做到三件事：独立装好 MySQL/SQLite 并建出规范的表；用 Python 把增删改查写成可复用、防注入的函数；为一个 RAG 项目设计出带元数据、可追溯的数据层。做不到的回到对应小节补，做得到就进 L0-学习路径导航 看下一步。

动手练习建议：把课件里的 students 表扩展成一个「AI 对话记录」库（users / conversations / messages 三张表），用 pymysql 写出增删改查四个函数，再用 SQLite 重写一遍对比两者的差异。这个练习能一次覆盖建表、事务、参数化 SQL、Python 封装四个核心点。

14. 速查清单

3
  1. Windows 装 MySQL：解压到全英文路径 → bin 进 Path → 管理员 cmd 跑 mysqld --initialize-insecure + mysqld -install + net start mysql → 登录改密码。
  2. 建库建表用 utf8mb4，别用 utf8。
  3. pymysql 连库：pymysql.connect(host, user, password, db) → cursor.execute(sql, 参数) → commit/rollback。
  4. SQLite 存 AI 会话：messages(conversation_id, role, content, tokens, created_at)。
  5. 永远参数化 SQL，永远写 WHERE，DML 后 commit。
  6. 向量别塞 MySQL，业务数据别塞向量库——双库并存是常态。
