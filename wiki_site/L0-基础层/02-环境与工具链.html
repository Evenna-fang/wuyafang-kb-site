环境与工具链：解释器、依赖隔离、网络探测与可复现重建

本文合并原「环境与工具链」和「国内镜像与可达性速查」。主线是：先确认正在运行哪个解释器，再隔离项目依赖，随后锁定与验证，最后才处理网络可达性。镜像是条件性工具，不是环境搭建的第一步，更不是永久事实。

验证边界：标准库环境检查脚本已在本机以隔离模式实跑；Windows/macOS 安装、虚拟环境重建和第三方包安装命令未实跑。旧稿 2026-09-28 的镜像结果仅保留为历史记录，本文只把 2026-11-04 明确复核的 GET 结果写成当前证据。

WHY

2

1. 环境问题为什么常被误诊为代码问题

3

同一段 import pandas 在一台机器成功、另一台失败，可能不是代码不同，而是 python、pip 和编辑器分别指向三个环境。直接执行 pip install 后运行 python app.py，若二者不对应，就会出现「刚装完仍 ModuleNotFoundError」。全局安装还会让项目 A 的升级破坏项目 B，最终只能靠删除重装碰运气。

可复现环境解决四个痛点：

  • 入口不清：不知道脚本由哪个解释器执行。
  • 依赖漂移：只写包名不写版本，今天与下月安装结果不同。
  • 路径串台：Windows、WSL、macOS/Linux 的命令名和文件系统不同，把 Windows 的 python.exe 当作 WSL 包管理目标。
  • 网络误判：DNS、TLS、代理、镜像失效和包不存在被统一描述成「网不好」，随后盲目更换更多镜像。

不做这些基础约束，后续 Python、数据分析、RAG 的报错都无法稳定复现；别人拿到代码也无法回答「该在什么环境跑」。

2. 为什么不能把镜像清单当永久配置

3

旧速查的价值在于保存了 2026-09-28 的一次探测，并提醒 ghproxy.com 等老域名已经变化；其局限是把当时可达扩展成「必须配置」「国内优先」的一般结论。可达不等于内容可信，更不等于供应链安全。第三方 GitHub 代理会经手代码下载，镜像也可能改变证书、重定向、文件完整性或可用版本。

正确顺序是：官方源先试 → 记录完整错误 → 分层探测 → 确有需要再选镜像 → 校验版本和哈希 → 定期复测。不全局固化来历不明的代理，不把凭据放进镜像 URL，不用 http 明文下载包。

WHAT / WHYT

2

3. 五个对象必须分清

3
对象 负责什么 不负责什么 常见误判
Python 解释器 执行代码、决定标准库与语言版本 不自动隔离第三方依赖 看见 python --version 就以为项目环境正确
虚拟环境 .venv 为项目提供独立解释器入口与 site-packages 不锁定依赖、不打包系统动态库 把 .venv 提交仓库或复制到另一台机器
pip 从索引下载并安装 Python 包 不保证所有包与当前解释器兼容 pip 与 python 分属不同环境
requirements*.txt / lock 记录直接依赖或完整解析结果 不替代虚拟环境，也不保证系统依赖存在 只有 requests 一行就声称完全可复现
包索引/镜像 提供包与元数据下载 不解决本地 PATH、编译器和系统库问题 所有安装失败都换镜像

虚拟环境回答「包安装到哪里」，锁定文件回答「这次具体安装哪些版本」，容器/系统镜像回答「操作系统与系统库是什么」。三者可以组合，但互不替代。.venv 通常由命令重建，不作为源码分发。

4. 版本选择：兼容性与支持状态优先

3

课件建议 Python 3.12/3.13 的教学意图是选稳定版本，但其「3.13 活跃开发、3.14 实验性」具有时间性，不能永久照抄。版本状态应以 Python 官方版本页为准；项目还要检查 NumPy、数据库驱动、部署平台等依赖是否提供对应 wheel。

实用策略：

  1. 新项目选择仍在支持期、核心依赖已支持的版本，而非机械追求最大号。
  2. 复现旧项目先读其 lock、容器文件和 CI 版本，不擅自升级解释器。
  3. 同时装多个版本时，用明确命令创建环境，例如 python3.12 -m venv .venv，创建后统一使用 .venv 内入口。
  4. 记录 sys.version 与平台；不要用「Python 3」作为可复现版本描述。

5. Windows、WSL 与 macOS/Linux 的边界

3

Windows PowerShell、CMD 与 WSL 是不同运行环境。WSL 中通常用 python3，Windows 常见 python 或 py；PowerShell 的激活脚本与 POSIX shell 不同。WSL 可以访问 /mnt/c，但把环境直接建在 Windows 项目树中可能遇到权限、文件监听与性能差异；不要假设一个 .venv 可以跨 OS 共用。

排错先看 sys.executable，再看 pip 实际位置，不凭终端标题猜。当前用户全局规则中另有本机 shim 等环境事实，那些属于特定机器配置，不能写成所有学习者的标准安装步骤。

6. 论文怎么说，我们怎么用

3

SquashFS 数据集研究（arXiv:2610.20578）关注大量小文件给 HPC 并行文件系统元数据服务器带来的压力，比较 11 种把只读数据集制成 SquashFS 镜像的工作流，并按下载形态、构建位置和压缩线程给出建议。它不是 Python 虚拟环境教程，也不证明「所有 AI 数据都应压缩成镜像」。

我们的落点是「环境包含数据布局与系统依赖，且优化必须测量」：当项目从几十个文本扩展到数百万小文件时，仅靠 requirements 无法描述读取瓶颈；应记录文件数量、存储位置、是否只读与基准结果，再决定是否采用镜像或打包。入门项目不为追求论文方案增加复杂度。

HOW

2

7. 建立隔离环境：同一解释器贯穿创建、安装与运行

3

以下 POSIX/WSL 命令是标准做法，本次未实跑；在新建练习目录中执行：

# 按项目兼容性选择明确版本；没有 python3.12 时先安装，不要跳过检查
python3.12 --version
python3.12 -m venv .venv
source .venv/bin/activate

# 之后不再单独使用含义不明的 pip
python -m pip --version
python -m pip install --upgrade pip
python -m pip install requests==2.32.5
python -c "import sys, requests; print(sys.executable); print(requests.__version__)"

Windows PowerShell 对应入口（未实跑）：

py -3.12 -m venv .venv
.venv\Scripts\Activate.ps1
python -m pip --version
python -m pip install requests==2.32.5

如果 PowerShell 阻止激活脚本，不要第一步就放宽整台机器的执行策略；可直接调用 .venv\Scripts\python.exe，或只针对当前进程按组织安全策略处理。Linux 若缺少 venv，应安装发行版对应的 python3.xx-venv 系统包，而不是用 pip install venv。

8. 环境验收脚本：先证明入口与依赖目录一致

3

保存为 verify_env.py，在项目环境中执行 python -I verify_env.py。脚本只读版本、路径和包元数据，已实跑：

from importlib import metadata
from pathlib import Path
import platform
import site
import sys
import sysconfig

print("version:", sys.version.replace("\n", " "))
print("executable:", sys.executable)
print("platform:", platform.platform())
print("prefix:", sys.prefix)
print("base_prefix:", sys.base_prefix)
print("purelib:", sysconfig.get_paths()["purelib"])
print("in_venv:", sys.prefix != sys.base_prefix)

if sys.prefix == sys.base_prefix:
    print("WARN: 当前不在虚拟环境；临时全局工具可接受，项目开发应重建 .venv")

for dist in ["requests"]:
    try:
        print(dist, metadata.version(dist))
    except metadata.PackageNotFoundError:
        print(dist, "NOT_INSTALLED（按需安装，不作为基础环境失败）")

print("cwd:", Path.cwd())
print("sitepackages:", getattr(site, "getsitepackages", lambda: [])())

验收不是要求所有输出相同，而是能回答：解释器路径是否属于本项目、purelib 是否属于同一环境、包版本是否与记录一致、当前目录是否放错。-I 是隔离模式，可避免当前目录偶然提供同名模块；日常项目测试是否使用它要看项目导入需求。

9. 记录依赖：直接依赖与完整冻结分开

3

最小练习可执行（未实跑）：

python -m pip install requests==2.32.5
python -m pip freeze > requirements-lock.txt
python -m pip check

requirements-lock.txt 是当时环境解析出的完整 Python 包集合，但不一定跨 OS、跨 Python 小版本通用。团队协作可再维护只写直接依赖的 requirements.in 或 pyproject.toml，用选定工具生成锁文件；工具未统一前，不要同时维护多份互相漂移的「唯一 lock」。

重建验证（会创建新环境，未实跑）：

python3.12 -m venv .venv-rebuild
.venv-rebuild/bin/python -m pip install -r requirements-lock.txt
.venv-rebuild/bin/python -m pip check
.venv-rebuild/bin/python -I verify_env.py

真正的重建测试应在不含旧 .venv 的目录或干净容器中进行；只运行 pip freeze 不算完成复现。

10. 网络排错：一次只改变一个变量

3

按层记录错误：

  1. 包名/版本问题：索引明确返回「No matching distribution」，先查包名、Python 版本和平台，不换镜像。
  2. DNS/TLS/超时：保留完整错误与时间，区分名称解析、证书和连接超时。
  3. HTTP 层：用无凭据 GET 检查官方文档或索引页；状态 200 只证明该次请求可达，不证明所有文件可下载。
  4. 代理/镜像层：确需替代源时只在当前命令或当前项目配置，核对包名、版本与哈希，不复制旧清单。
  5. 编译/系统库层：错误涉及 compiler、header、shared library 时，换 Python 包镜像通常无效。

可达性 GET 示例（会访问公开站点，未实跑）：

curl -L --max-time 30 -sS -o /dev/null -w 'python_docs=%{http_code}\n' \
  https://docs.python.org/3/tutorial/venv.html
curl -L --max-time 30 -sS -o /dev/null -w 'pypi_simple=%{http_code}\n' \
  https://pypi.org/simple/requests/

临时指定 Hugging Face 镜像的写法是 HF_ENDPOINT=https://hf-mirror.com，但这只是一项可选环境变量，不应写成「必须配置」。第三方下载仍需核对模型仓库、文件 SHA-256、许可证与组织安全要求。旧稿中的 GitHub 代理地址不再作为推荐命令保留。

11. 最小交付清单与翻车排查

3
症状 第一检查 修复方向
安装后仍找不到包 python -m pip --version 与 sys.executable 用目标解释器的 python -m pip 重装
激活后仍是旧版本 sys.prefix / base_prefix 与 shell 命令路径 重建或正确激活 .venv
换机器后包冲突 lock、Python 小版本、OS 平台 按兼容环境重建，不复制 .venv
Windows 正常、WSL 失败 是否误用 Windows python.exe 在 WSL 内单独建 POSIX 环境
只有某镜像能下 官方源错误、镜像版本与哈希 限制镜像作用域，保留证据，定期复测
构建包时报编译错误 编译器、头文件、系统库 补系统构建依赖或选兼容 wheel

环境交付至少包含：支持的 OS 与 Python 版本、创建命令、直接依赖、锁定产物、验证脚本、网络与系统依赖说明。不要包含真实凭据、全局代理配置或来历不明的安装脚本。

    |---|---|---|
    | 3.14.4 | /home/wuyafang/.venv-hermes/bin/python | 跑 ~/.hermes 体系脚本（receipt.py/lookup_error.py 本次用它） |
    | 3.12.14 | rag/.venv/bin/python | 跑 rag/query.py、rag/agentic_query.py（本次实跑用） |
    | 系统 3.x | /usr/bin/python3 | 跑 rag/check_ttl.py（纯标准库，本次实跑 PASS） |
  • 环境隔离链的第一环是 PYTHONPATH，不是 venv（本次实测两次失败后才定位）：本库没有用 Docker 包住 rag/，shell 里只要挂着 Hermes 内核的 site-packages，项目 venv 就会被污染。
    正确姿势不是「再建一个 venv」，而是启动命令里显式剥离：
    bash env -u PYTHONPATH rag/.venv/bin/python query.py "问题"
    同一份代码，加不加 env -u PYTHONPATH 是「ImportError」和「exit 0 出答案」的区别。
  • 工具链版本要 pin 在仓库里，不靠机器状态（rag/pyproject.toml L4-31，本次读取）：requires-python = ">=3.12" + 全部依赖带 ==（如 chromadb==1.5.9、langgraph==1.2.11、mcp==2.3.0），配 .python-version（3.12）。
    再加上 rag/.prek.toml 的 pre-commit 钩子（ruff check / ruff format / ty check / pytest），工具链才算可复现。
  • 和课件讲法的差异：课件讲「装个 Python + pip install 就能跑」；本库的真实约束是多解释器共存 + 宿主注入的 PYTHONPATH，pip install 之前要先回答「我这条命令会用哪个 python」。IDE/编辑器选的解释器也可能与命令行不同。
  • 本库暂无：没有 uv.lock-级的锁文件进 git（rag/ 不在 git 仓库内，git status 本次报 fatal: not a git repository），依赖一致性靠 pyproject.toml 的 == 约束保证。
