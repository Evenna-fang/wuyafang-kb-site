Python 异步编程：协程、取消、超时与有界并发

本文合并两篇 asyncio 原稿，只保留一条主线：先理解事件循环协作式切换，再写可取消、可限时、有并发上限的 I/O 任务。咖啡店类比只用于建立直觉，工程验收以任务状态和异常行为为准。

验证边界：离线 asyncio.sleep 示例已在 Python 3.14.4 实跑，包括失败传播与取消；真实 HTTP、数据库和 FastAPI 部署未实跑。示例使用 TaskGroup，要求 Python 3.11+。

WHY

2

1. 为什么 I/O 等待值得异步

3

一个请求花 100 ms 等待远端 API，如果大部分时间是网络等待，同步串行处理 20 个请求会累积等待；协程能在一个线程中，于任务等待时切换到其他任务。常见 AI 应用中，模型调用、检索请求和数据库访问都有 I/O 等待，异步可提高单进程在途请求容量。

但 async def 只是定义协程函数，不会自动并发；直接 await slow() 仍等待它结束。若在事件循环里调用 time.sleep、同步 requests、重 CPU 数值计算，其他协程仍无法运行。误用异步的后果包括延迟尾部长、任务泄漏、连接池耗尽、未消费异常和进程退出时后台任务被 abruptly 取消。

2. 为什么「全部 create_task」不是完整方案

3

创建一万个 Task 只需很少代码，却会同时持有一万个输入、响应和连接状态。信号量可以限制临界区内正在请求的数量，却不能限制已创建 Task 的总内存；没有上限的队列同样可能把延迟和内存推向失控。因此，生产主线必须包括：并发上限、排队边界、超时、取消传播、结果消费和关闭顺序。

WHAT / WHYT

2

3. 核心对象与相似概念

3
概念 含义 与相邻概念的区别
协程 可在 await 处让出执行权的计算 调用协程函数只得到协程对象，尚未执行
Task 事件循环上调度的协程执行单元 多个 Task 可交错推进，不代表多核并行
事件循环 调度就绪任务、处理 I/O 回调 不会抢先在普通同步代码中间切走任务
gather 并发等待多个 awaitable，并可分别收集异常 return_exceptions=True 会把异常作为结果返回，调用方必须检查
TaskGroup 结构化管理子任务，失败时取消同组任务并汇总异常 不是无异常包装器，需处理 ExceptionGroup
wait_for 等待操作并在超时后取消它 超时不是远程操作一定停止，仍需服务端幂等/取消支持
信号量 限制同时进入临界区的任务数 不限制任务总数、队列长度和总内存

并发 vs 并行：并发是多个任务在时间上重叠推进；并行是多个计算真正同时执行。asyncio 主要解决 I/O 并发，一个事件循环中的普通 Python 字节码不会因协程自动使用多核。CPU 密集任务应评估进程池、本地优化或专用计算服务；阻塞型第三方 I/O 可谨慎用 asyncio.to_thread，但线程数和下游容量仍要有界。

4. 生命周期与失败语义

3

推荐「创建—等待—处理异常—关闭」在同一作用域完成，优先 asyncio.run 和 asyncio.TaskGroup，不要把未引用的 Task 随意丢到后台。Python 官方文档特别提示要保存 Task 引用，避免任务在执行中被垃圾回收；更根本的是调用方需要知道任务是否完成和失败。

取消是协作式的：任务收到 CancelledError 后应清理资源并通常继续传播，不要把它当普通失败吞掉。使用 async with 管理异步资源，保证退出时释放；在 FastAPI 等框架中把客户端、连接池等放到 lifespan 启停，而不是每个请求重复建池。

5. 论文怎么说，我们怎么用

3

EnvSched（arXiv:2610.37609）研究的是 Agent 强化学习中的环境交互调度：固定时间步会让慢样本造成 bubble，且采样覆盖与任务配比影响训练。它不是 asyncio 调度算法的实验证据。

跨领域可借鉴的只有问题意识：调度不能只看平均吞吐，还要看等待气泡、慢任务、配额与覆盖；落到 asyncio，就是记录队列等待、执行时长、超时与取消，并用背压避免快生产端淹没慢消费端。不能把论文训练收益写成 FastAPI 或 asyncio 的性能结论。

HOW

6. 可离线实跑：并发、上限、失败传播和取消

3

保存为 async_demo.py（已实跑）：

import asyncio
import time


async def job(name: str, delay: float, semaphore: asyncio.Semaphore) -> str:
    async with semaphore:
        print(f"start {name}")
        await asyncio.sleep(delay)  # 模拟非阻塞 I/O，真实项目替换为异步客户端
        if name == "bad":
            raise RuntimeError("注入失败")
        print(f"done {name}")
        return name.upper()


async def gather_demo() -> None:
    semaphore = asyncio.Semaphore(2)
    started = time.perf_counter()
    results = await asyncio.gather(
        *(job(name, delay, semaphore) for name, delay in
          [("a", 0.04), ("b", 0.04), ("c", 0.04), ("d", 0.04)]),
        return_exceptions=True,
    )
    elapsed = time.perf_counter() - started
    assert all(isinstance(item, str) for item in results), results
    assert elapsed < 0.12, f"并发未按预期重叠：{elapsed:.3f}s"
    print("gather:", results, f"elapsed={elapsed:.3f}s")


async def task_group_failure_demo() -> None:
    semaphore = asyncio.Semaphore(2)
    try:
        async with asyncio.TaskGroup() as group:
            group.create_task(job("ok", 0.02, semaphore))
            group.create_task(job("bad", 0.01, semaphore))
    except* RuntimeError as errors:
        print("TaskGroup 捕获注入失败:", len(errors.exceptions))
    else:
        raise AssertionError("注入失败没有传播")


async def timeout_demo() -> None:
    semaphore = asyncio.Semaphore(1)
    cancelled = asyncio.Event()

    async def slow() -> None:
        try:
            await asyncio.sleep(10)
        except asyncio.CancelledError:
            cancelled.set()
            raise

    try:
        async with asyncio.timeout(0.02):
            await slow()
    except TimeoutError:
        pass
    assert cancelled.is_set(), "超时没有传播取消"
    print("timeout: 已观察取消传播")


async def main() -> None:
    await gather_demo()
    await task_group_failure_demo()
    await timeout_demo()


if __name__ == "__main__":
    asyncio.run(main())

运行（已实跑）：

python -I async_demo.py

验收点不是打印顺序固定，而是：四个 40 ms 任务在信号量 2 下约两批完成；bad 的 RuntimeError 被 except* 明确处理；超时任务观察到 CancelledError 并重新抛出。墙上时间断言只适用于本地教学示例，CI 高负载下应放宽或改成调度行为断言，不能当作性能基准。

7. 从固定任务列表升级为有界生产—消费

3

真实批量任务不要先创建全部 Task。按下面步骤改造：

  1. 用固定数量 worker，例如 8 个，从 asyncio.Queue(maxsize=32) 取任务。
  2. 生产端 await queue.put(item)；队列满时自然等待，这就是背压。
  3. 为每个 I/O 调用设置总超时、连接超时与重试上限；写操作先定义幂等键。
  4. worker 用 try/finally 调用 queue.task_done()，异常是否继续必须有策略。
  5. 停止时先停止生产，再 await queue.join()，随后取消并等待 worker；或在 TaskGroup 中用明确关闭协议。
  6. 监控 queue.qsize()、在途数、各阶段耗时、取消/异常数，不只看 RPS。

信号量适合限制共享资源临界区，worker 池适合限制整个处理管线；两者可组合，但数字应从下游配额、响应大小与内存测量得出。

8. 真实 I/O 替换原则

3

未实跑的替换清单：

  • HTTP：选支持异步的客户端，复用 AsyncClient/session，设置连接池和超时；不要在协程里直接调用同步 requests.get。
  • 数据库：使用匹配的异步驱动与连接池；连接池上限通常应小于或等于数据库可承受配额。
  • 阻塞文件或遗留客户端：小范围使用 await asyncio.to_thread(blocking_call, ...)，同时限制线程池；这不是把 CPU 密集任务变异步。
  • 子进程：用 asyncio 子进程 API，消费 stdout/stderr，设置超时并等待退出，避免管道缓冲堵塞。
  • Web 服务：应用启动创建共享客户端，关闭时先停止接收，再完成或取消在途任务，最后关闭连接池。

真实压测至少比较同步基线与异步版本，记录并发、P50/P95/P99、错误率、内存和下游限流。不能只凭总耗时一次下降就推广。

9. 翻车清单

3
现象 根因候选 处理
coroutine was never awaited 只调用协程函数，未 await/调度 明确 await 或交给 TaskGroup
并发后仍与串行一样慢 逐个 await、同步阻塞调用 同时调度任务，替换阻塞客户端
内存随批量线性暴涨 预先创建全部 Task/结果 有界队列 + 固定 worker
超时后仍产生重复写入 远端未取消，重试不幂等 幂等键、状态查询、限制重试
程序退出才看到异常 后台 Task 未等待、异常未消费 结构化并发，保存并等待任务
CPU 批处理没有提速 单事件循环仍执行同一 CPU 工作 进程池/原生向量化/独立服务

  • 本库两条链路对异步的态度完全相反，这是学 async 最好的对照样本（本次读源码）：
    | 链路 | 写法 | 证据 |
    |---|---|---|
    | rag/serve.py（知识库服务） | 同步 def，靠 uvicorn 线程池 | L323 def chat_completions(req: ChatCompletionRequest):、L366 def completions(req: CompletionRequest): |
    | projects/agent-service-toolkit（Agent 服务模板） | async def + AsyncGenerator 流式 | src/service/service.py 顶部 from collections.abc import AsyncGenerator、from fastapi.responses import StreamingResponse |
  • 为什么 rag/serve.py 敢用同步：它的瓶颈是「一次 embedding + 一次 rerank + 一次云端生成」（本次实跑单问题约 3 分钟；另据 rag/config.yaml 注释，主生成端实测约 2.2 秒/次），单机单用户场景下线程池（uvicorn 默认 worker 线程）足够；写成 async def 但内部全是阻塞调用，反而会卡住事件循环。
    对照课件「把 I/O 写成 async」的一般建议：async 的价值在「大量并发等待」，不在「单次调用更快」，请求量上不去时同步 + 线程池是更简单的正确解。
  • 真实并发等待点在哪：rag/agentic_query.py 的一轮检索里要先 query.retrieve_hybrid（dense 走云端 embedding HTTP）再 query.rerank_node（本地重排模型），两段都是阻塞的；这正是「想提速就必须串行改并行」的地方，也是本库目前没做的优化。
  • 和课件讲法的差异：课件用 asyncio.gather 并发请求做示例；本库没有 async 代码进入主检索链，异步只出现在 fork 的服务模板里（StreamingResponse 推送 token）。
  • 本库暂无：rag/ 侧没有异步化改造，也没有并发请求压测数据；「并发会不会把内存打满」在本库未实测（内存护栏 RAG_MEM_LIMIT_GB 是可选环境变量，见 rag/query.py 文末）。
