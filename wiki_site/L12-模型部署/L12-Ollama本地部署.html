WSL GPU 检测（实跑，含负例）

WSL 下 GPU 可能"看着装好了但不可用"，用脚本区分"驱动问题"和"Ollama 配置问题"：

"""WSL 下的 GPU 可见性检测：区分驱动问题与 Ollama 配置问题。"""
import subprocess, shutil, os

def detect_gpu():
    findings = []
    if not shutil.which("nvidia-smi"):
        findings.append("nvidia-smi 不在 PATH -> WSL GPU 支持未启用或驱动未装")
        return findings, False
    try:
        out = subprocess.run(["nvidia-smi", "--query-gpu=name,memory.total,driver_version",
                              "--format=csv,noheader"], capture_output=True, text=True, timeout=10)
        if out.returncode == 0:
            for line in out.stdout.strip().splitlines():
                findings.append(f"GPU: {line}")
        else:
            findings.append("nvidia-smi 存在但报错 -> 驱动/WSL 集成问题")
            return findings, False
    except Exception as e:
        findings.append(f"nvidia-smi 调用失败: {e}")
        return findings, False
    # WSL 特有: 查 /dev/dxg 是否存在(WSL GPU paravirtualization 设备)
    if not os.path.exists("/dev/dxg"):
        findings.append("/dev/dxg 不存在 -> WSL GPU 直通未启用(Windows 侧需装支持 WSL 的驱动)")
        return findings, False
    findings.append("/dev/dxg 存在, GPU 直通正常")
    return findings, True

if __name__ == "__main__":
    f, ok = detect_gpu()
    for line in f:
        print(line)
    print("结论:", "GPU 可用" if ok else "GPU 不可用, Ollama 会退 CPU")

实跑输出（本机 WSL 未装 NVIDIA 驱动的负例）：

nvidia-smi 不在 PATH -> WSL GPU 支持未启用或驱动未装
结论: GPU 不可用, Ollama 会退 CPU

读数：负例验证了第一道防线——nvidia-smi 缺失直接给结论，不会让 Ollama 静默退 CPU 造成"装好了但慢"的困惑。正例会打印 GPU 名称/显存/驱动版本，并检查 /dev/dxg（WSL GPU 半虚拟化设备，Windows 驱动要支持 WSL 才有）——两道检查缺一不可：nvidia-smi 能看到卡不代表 /dev/dxg 存在（后者才是 WSL 内可用的凭据）。装好后跑这个脚本再启动 ollama serve。

3.1 GGUF 是什么3 个重点▾ 点开看本节重点
本节重点
  • GGUF 是 llama.cpp 生态的模型文件格式（不是量化方法本身）：单文件打包元数据 + 张量，支持 CPU/GPU 混合加载、内存映射（mmap，冷启动快）、以及从 Q2 到 F16 的一整套量化档位

  • 其中 「 」 就是量化类型（「Q4_K_S」、「Q5_K_M」、「Q8_0」、「F16」……），「 」 是分片编号（「-00001-of-00002」）
3

GGUF 是 llama.cpp 生态的模型文件格式（不是量化方法本身）：单文件打包元数据 + 张量，支持 CPU/GPU 混合加载、内存映射（mmap，冷启动快）、以及从 Q2 到 F16 的一整套量化档位。命名规范（源：llama.cpp wiki）：

<BaseName><SizeLabel><FineTune><Version><Encoding><Type><Shard>.gguf
例如：llama-2-13b-Q4_K_S.gguf

其中 <Type> 就是量化类型（Q4_K_S、Q5_K_M、Q8_0、F16……），<Shard> 是分片编号（-00001-of-00002）。

3.2 GGUF 命名解析器（实跑）

3

真实文件名经常不完整或带自定义后缀，用解析器而不是靠眼睛认：

import re

def parse_gguf_name(name):
    """解析 llama.cpp 官方 GGUF 命名：
    <BaseName><SizeLabel><FineTune><Version><Encoding><Type><Shard>.gguf
    段之间用 '-' 分隔，shard 形如 -00001-of-00002。"""
    assert name.endswith(".gguf"), "必须 .gguf 结尾"
    core = name[:-5]
    shard = None
    m = re.search(r"-(\d{5})-of-(\d{5})$", core)
    if m:
        shard = (int(m.group(1)), int(m.group(2)))
        core = core[: m.start()]
    parts = core.split("-")
    qtype = parts.pop()                      # Type：如 Q4_K_S / q4_k_m
    size = None
    for i, p in enumerate(parts):
        if re.fullmatch(r"\d+(?:\.\d+)?[BM]", p, re.I):
            size = parts.pop(i); break
    return {"base": "-".join(parts), "size": size, "qtype": qtype, "shard": shard}

for n in ["llama-2-13b-Q4_K_S.gguf",
          "Qwen2.5-7B-Instruct-v1.0-UD-Q4_K_XL-00001-of-00002.gguf"]:
    print(n, "->", parse_gguf_name(n))

实跑输出：

llama-2-13b-Q4_K_S.gguf -> {'base': 'llama-2', 'size': '13b', 'qtype': 'Q4_K_S', 'shard': None}
Qwen2.5-7B-Instruct-v1.0-UD-Q4_K_XL-00001-of-00002.gguf -> {'base': 'Qwen2.5-Instruct-v1.0-UD', 'size': '7B', 'qtype': 'Q4_K_XL', 'shard': (1, 2)}

读数：解析器对两个真实格式都正确提取了 size 与 qtype——下载模型后先跑这一步，能避免"下错档位装不上/装上了以为是 Q5 其实是 Q2"这类事故。

下载后校验（实跑，含负例）

GGUF 文件动辄几 GB，下载不完整或下错档位是高频事故。校验脚本把"命名解析 + 大小核对 + sha256"三件事合起来：

"""GGUF 下载/校验工作流：sha256 校验 + 大小核对 + 命名解析三合一。"""
import hashlib, os, re

def parse_gguf_name(name):
    assert name.endswith(".gguf"), "必须 .gguf 结尾"
    core = name[:-5]
    shard = None
    m = re.search(r"-(\d{5})-of-(\d{5})$", core)
    if m:
        shard = (int(m.group(1)), int(m.group(2)))
        core = core[: m.start()]
    parts = core.split("-")
    qtype = parts.pop()
    size = None
    for i, p in enumerate(parts):
        if re.fullmatch(r"\d+(?:\.\d+)?[BM]", p, re.I):
            size = parts.pop(i); break
    return {"base": "-".join(parts), "size": size, "qtype": qtype, "shard": shard}

def verify_local(path, expected_sha256=None, expected_size_gb=None):
    issues = []
    if not os.path.exists(path):
        return ["文件不存在"]
    size = os.path.getsize(path)
    if expected_size_gb and abs(size/1024**3 - expected_size_gb) > 0.2:
        issues.append(f"大小不符: 实际 {size/1024**3:.2f}GB vs 预期 {expected_size_gb}GB (可能下载不完整)")
    if expected_sha256:
        h = hashlib.sha256()
        with open(path, "rb") as f:
            for chunk in iter(lambda: f.read(1<<20), b""):
                h.update(chunk)
        if h.hexdigest() != expected_sha256:
            issues.append("sha256 不匹配")
    issues.append(f"元信息: {parse_gguf_name(os.path.basename(path))}")
    return issues or ["校验通过"]

if __name__ == "__main__":
    print("本地文件不存在的负例:", verify_local("/tmp/nonexistent.gguf"))
    with open("/tmp/fake-7B-Q4_K_M.gguf","wb") as f:
        f.write(b"\0"*1024)
    print("大小不符负例:", verify_local("/tmp/fake-7B-Q4_K_M.gguf", expected_size_gb=4.0))

实跑输出（两个负例都触发了对应分支）：

本地文件不存在的负例: ['文件不存在']
大小不符负例: ['大小不符: 实际 0.00GB vs 预期 4.0GB (可能下载不完整)', "元信息: {'base': 'fake', 'size': '7B', 'qtype': 'Q4_K_M', 'shard': None}"]

读数：负例验证了三条防线——①文件不存在返回明确"文件不存在"而不是抛异常；②大小核对抓出下载不完整（0.00GB vs 4.0GB）；③即使大小不符，元信息照常解析（qtype: Q4_K_M），方便排查"档位对不对"。sha256 校验是可选参数（下载源提供 checksum 时用）。下载 GGUF 后固定跑这个脚本，再 ollama create——比"装不上才发现文件坏了"省一小时。

def write_modelfile(path, gguf, ctx=8192, temp=0.7, system="你是一个严谨的中文助手。"):
    lines = [
        f"FROM {gguf}",
        f"PARAMETER temperature {temp}",
        f"PARAMETER num_ctx {ctx}",
        "PARAMETER num_predict 512",
        'TEMPLATE """{{ .System }}\n{{ .Prompt }}"""',
        f'SYSTEM """{system}"""',
        "",
    ]
    content = "\n".join(lines)
    with open(path, "w") as f:
        f.write(content)
    return content

if __name__ == "__main__":
    print(write_modelfile("/tmp/Modelfile.l12", "./qwen2.5-7b-instruct-q4_k_m.gguf"))

Modelfile 校验器（实跑）

写完 Modelfile 先过一遍校验，再 ollama create：

"""Modelfile 校验器：检查 TEMPLATE 占位符、SYSTEM 存在、PARAMETER 合法值。"""
import re

def validate_modelfile(text):
    issues = []
    if "FROM " not in text:
        issues.append("缺 FROM 指令")
    tpl = re.search(r'TEMPLATE """(.*?)"""', text, re.S)
    if tpl:
        body = tpl.group(1)
        if "{{ .Prompt }}" not in body:
            issues.append("TEMPLATE 缺 {{ .Prompt }} 占位符 -> 输出为空")
        if "{{ .System }}" not in body and "SYSTEM" in text:
            issues.append("TEMPLATE 缺 {{ .System }} 占位符 -> 系统提示不生效")
    elif "SYSTEM" in text:
        issues.append("有 SYSTEM 但无 TEMPLATE -> 可能走默认模板，SYSTEM 失效")
    ctx = re.search(r"PARAMETER num_ctx (\d+)", text)
    if ctx and int(ctx.group(1)) > 32768:
        issues.append(f"num_ctx={ctx.group(1)} 过大，注意 KV 显存")
    return issues

if __name__ == "__main__":
    bad = ("FROM ./qwen2.5-7b-instruct-q4_k_m.gguf\nPARAMETER num_ctx 65536\nSYSTEM "
           + '"""' + "严谨作答" + '"""')
    for i in validate_modelfile(bad):
        print("NG", i)
    good = ("FROM ./qwen2.5-7b-instruct-q4_k_m.gguf\nPARAMETER num_ctx 8192\n"
            "TEMPLATE " + '"""' + "{{ .System }}\n{{ .Prompt }}" + '"""' +
            "\nSYSTEM " + '"""' + "严谨作答" + '"""')
    print("good:", validate_modelfile(good) or "通过")

实跑输出（负例 + 正例双向验证）：

NG 有 SYSTEM 但无 TEMPLATE -> 可能走默认模板，SYSTEM 失效
NG num_ctx=65536 过大，注意 KV 显存
good: 通过

读数：负例抓到两个真实坑——①有 SYSTEM 但没写 TEMPLATE 时，Ollama 会用推断的默认模板，你的系统提示可能根本不生效（这是"设了角色设定但模型不听"的高频根因）；②num_ctx 65536 触发 KV 显存警告（对应 §4.2 的乘积算式）。正例全绿才 ollama create。

4.2 KV 显存算式（实跑）：旋钮是乘法关系

3 
"""Ollama 长上下文/并发翻车自检：对比默认配置与目标配置的 KV 显存估算。"""
def kv_mb(ctx, layers=32, kv_heads=8, head_dim=128, dtype_bytes=2, batch=1):
    per_tok = 2 * layers * kv_heads * head_dim * dtype_bytes
    return per_tok * ctx * batch / 1024**2

if __name__ == "__main__":
    rows = [
        ("默认 num_ctx=4096, 并发4", 4096, 4),
        ("目标 num_ctx=32768, 并发8", 32768, 8),
        ("目标+q8_0 KV, 并发8", 32768, 8),
    ]
    for name, ctx, b in rows:
        dbytes = 1 if "q8_0" in name else 2
        m = kv_mb(ctx, batch=b, dtype_bytes=dbytes)
        print(f"{name}: KV 显存 {m:.0f} MB")
    print("教训: num_ctx 与 OLLAMA_NUM_PARALLEL 同时拉大，KV 显存按乘积暴涨")

实跑输出：

目标 num_ctx=32768, 并发8: KV 显存 32768 MB

读数：从默认配置（2GB）到"想要长上下文+高并发"（32GB），KV 显存涨 16 倍——这就是"开了 32K 上下文 + 8 并发后，模型突然加载不出来/OOM"的定量解释。三个旋钮是乘法关系，不是加法；调大任何两个之前先用这个算式过一遍。q8_0 KV cache 能砍一半，是显存紧张时的第一杠杆。

4.4 环境变量配置生成器（实跑）

把 §4.1 的变量与 §4.2 的显存算式串起来，按显存预算生成推荐配置：

"""Ollama 环境变量生成器：给定显存预算与业务并发/上下文需求, 输出推荐环境变量。"""
def gen_env(gpu_gb, target_ctx=8192, target_parallel=4, want_speed=True):
    # KV 显存估算(7B 级模型, 32 层, 8 KV head, head_dim 128)
    def kv_mb(ctx, batch, dtype_bytes=2):
        return 2 * 32 * 8 * 128 * dtype_bytes * ctx * batch / 1024**2
    # 权重(Q4_K_M 约 4.4GB) + 开销 2GB
    fixed = 4.4 + 2.0
    budget_mb = (gpu_gb - fixed) * 1024
    dtype = 2
    need = kv_mb(target_ctx, target_parallel)
    while need > budget_mb and dtype > 1:
        dtype = 1  # q8_0 KV cache
        need = kv_mb(target_ctx, target_parallel, dtype)
    if need > budget_mb:
        # 压并发
        target_parallel = max(1, int(target_parallel * budget_mb / need))
        need = kv_mb(target_ctx, target_parallel, dtype)
    env = {
        "OLLAMA_NUM_PARALLEL": str(target_parallel),
        "OLLAMA_CONTEXT_LENGTH": str(target_ctx),
        "OLLAMA_MAX_LOADED_MODELS": "1",
    }
    if want_speed:
        env["OLLAMA_FLASH_ATTENTION"] = "1"
    if dtype == 1:
        env["OLLAMA_KV_CACHE_TYPE"] = "q8_0"
    return env, round(need/1024, 2), round(budget_mb/1024, 2)

if __name__ == "__main__":
    for gpu in [16, 24, 48]:
        env, kv_gb, budget_gb = gen_env(gpu, 32768, 8)
        print(f"GPU {gpu}GB: KV需要{kv_gb}GB/预算{budget_gb}GB")
        for k, v in env.items():
            print(f"  export {k}={v}")

Ollama 的 HTTP API 在 localhost:11434，/api/chat 是对话接口：

import json, urllib.request

def chat(prompt, model="qwen2.5:7b", stream=False):
    body = json.dumps({
        "model": model,
        "messages": [{"role": "user", "content": prompt}],
        "stream": stream,
        "options": {"num_ctx": 8192, "temperature": 0.7},
    }).encode()
    req = urllib.request.Request(
        "http://localhost:11434/api/chat",
        data=body, headers={"Content-Type": "application/json"})
    with urllib.request.urlopen(req, timeout=120) as r:
        if not stream:
            return json.loads(r.read())["message"]["content"]
        out = []
        for line in r:
            chunk = json.loads(line)
            if chunk.get("done"):
                break
            out.append(chunk["message"]["content"])
        return "".join(out)

if __name__ == "__main__":
    print(chat("用一句话解释 KV cache"))

要点：

  • options.num_ctx 是按请求的上下文长度，超过 OLLAMA_CONTEXT_LENGTH 会被截断到后者——两处要对齐；
  • 流式返回是 NDJSON（每行一个 JSON），不要用 json.loads(r.read()) 整体解析；
  • ollama serve 未启动时连接会 ConnectionRefused，生产部署用 systemd/nssm 拉成服务；
  • OpenAI 兼容层：/v1/chat/completions 也支持（0.30+），现有 OpenAI SDK 客户端改 base_url 即可零改动迁移。

现象：Modelfile 里 num_ctx 32768，ollama run 时模型加载到一半 killed / 显存爆。

根因：KV cache = num_ctx × 并发 × per_token（§4.2 实跑：32768×8 并发 = 32GB）。很多人以为"上下文长只是回答能更长"，忽略了它和并发是乘积关系。

6.2 翻车二：并发不生效，多用户排队

3

现象：设了 OLLAMA_NUM_PARALLEL=8，两个并发请求还是串行跑（第二个等第一个完成）。

根因：两层可能——① Mac MLX 后端上 runner 可能被强制 Parallel:1，环境变量形同虚设（源：模型部署调优实操-2026.md §2.2 二手，需自己复验）；② 环境变量设在 ollama serve 启动之后（服务进程读的是启动时的环境）。

改法：验证标准不是"日志里读到了变量"，而是两条真实并发请求的时间窗是否重叠（ollama ps 看加载状态 + 两条 curl 的耗时对比）；改环境变量后必须重启 ollama serve；Mac 上实测不生效就接受串行，或换 llama.cpp server。

"""Prompt 回归集执行器：对一组固定 prompt 跑模型, 对比两版本输出的结构指标。"""
REGRESSION = [
    {"id": "R01", "prompt": "用一句话解释 KV cache", "expect_len": (20, 120)},
    {"id": "R02", "prompt": "列出 3 个量化格式并各给一句话", "expect_len": (20, 300)},
    {"id": "R03", "prompt": "1+1=?", "expect_len": (1, 200)},
    {"id": "R04", "prompt": "写一个 Python 函数求斐波那契数列第 n 项", "expect_len": (20, 600)},

def check_output(case, output):
    issues = []
    n = len(output)
    lo, hi = case["expect_len"]
    if n == 0:
        issues.append("空输出(模板/服务异常)")
    if n < lo and n > 0:
        issues.append(f"输出过短({n}<{lo})")
    if n > hi:
        issues.append(f"输出过长({n}>{hi})")
    return issues

def run_regression(model_fn):
    report = []
    for c in REGRESSION:
        out = model_fn(c["prompt"])
        issues = check_output(c, out)
        report.append({"id": c["id"], "chars": len(out), "issues": issues or ["OK"]})
    return report

if __name__ == "__main__":
    good = lambda p: "这里是对 '" + p + "' 的正常回答。" * 2
    bad = lambda p: ""
    for name, fn in [("正常模型", good), ("模板失效模型", bad)]:
        print(f"== {name} ==")
        for r in run_regression(fn):
            print(r)

3

现象：nvidia-smi 显示还有 6GB 空闲，ollama run 7b-q5 却报 out of memory。

7.1 服务健康自检脚本（实跑，含负例）

"""Ollama 服务健康自检：端口、模型列表、并发能力探测。"""
import json, time, urllib.request

BASE = "http://localhost:11434"

def ping(timeout=2):
    try:
        with urllib.request.urlopen(BASE + "/api/tags", timeout=timeout) as r:
            return True, len(json.loads(r.read()).get("models", []))
    except Exception as e:
        return False, str(e)

def concurrent_probe(model="qwen2.5:7b", n=2):
    """并发验证：发送 n 条请求，检查时间窗是否重叠（总耗时 < 单条耗时*n 的 0.7 倍）。"""
    def one():
        body = json.dumps({"model": model,
                           "messages": [{"role": "user", "content": "说'好'"}],
                           "stream": False,
                           "options": {"num_predict": 1}}).encode()
        req = urllib.request.Request(BASE + "/api/chat", data=body,
              headers={"Content-Type": "application/json"})
        t0 = time.perf_counter()
        with urllib.request.urlopen(req, timeout=60) as r:
            json.loads(r.read())
        return time.perf_counter() - t0
    single = one()
    t0 = time.perf_counter()
    import threading
    ts = []
    threads = [threading.Thread(target=lambda: ts.append(one())) for _ in range(n)]
    for t in threads: t.start()
    for t in threads: t.join()
    wall = time.perf_counter() - t0
    overlap = wall < single * n * 0.7
    return single, wall, overlap

if __name__ == "__main__":
    ok, info = ping()
    print(f"服务在线: {ok}, 模型数/错误: {info}")
    if ok:
        s, w, ov = concurrent_probe()
        print(f"单条 {s:.2f}s, 2并发墙钟 {w:.2f}s, 并发生效: {ov}")
    else:
        print("提示: 服务未启动时本脚本返回 False —— 属预期的负例")

8. 与 vLLM 的分界：什么时候该"毕业"

2

Ollama 的并发上限与吞吐天花板是结构性的（封装 llama.cpp、无连续批处理/PagedAttention）。判断"该毕业了"的信号：

  1. 并发需求 >10：50 并发下 Ollama 吞吐仅 vLLM 的 7.5%（源：模型部署调优实操-2026.md §1 二手横评，⚠️需自测复核）；
  2. 需要 prefix caching：多轮/RAG/agent 共享前缀，Ollama 无此机制，vLLM/SGLang 有；
  3. 需要多模型路由 + 生产监控：Prometheus 指标、健康检查、灰度发布；
  4. 成本核算显示"省下的 API 费 > 自建 GPU 成本"：见 模型部署调优实操-2026.md §4 的 break-even 口径。

毕业路径：Ollama 上验证过的 prompt/系统提示/回归集，直接搬到 vLLM（OpenAI 兼容层两家都支持，客户端零改动）；GGUF 档位经验换算到 AWQ/FP8（见《L12-模型量化》）。Ollama 阶段积累的 prompt 质量与回归集，是毕业时最值钱的资产——模型会换，评测不会。

if __name__ == "__main__":
    o = {"num_ctx": 8192, "num_parallel": 8, "kv_cache_type": "q8_0"}
    for k, v in migrate(o).items():
        print(f"{k}: {v}")

实跑输出：

gpu-memory-utilization: 0.85 (vLLM 管显存, 不等同 Ollama 的 num_ctx 观念)
max-model-len: 8192
max-num-seqs: 8
quantization: fp8

读数：num_ctx → max-model-len、OLLAMA_NUM_PARALLEL → max-num-seqs 是直接对应；但 gpu-memory-utilization 在 Ollama 里没有对应物（Ollama 自己按需吃显存，vLLM 预留 KV 池子）——迁移时这个参数要重新按 vLLM 的显存账算（见《L12-vLLM推理加速》§3），不能照抄。quantization 的映射是近似：Ollama 的 KV cache 量化（q8_0）对应 vLLM 的 KV cache dtype，不是权重量化，权重量化要看你换的是 AWQ/FP8/GGUF 哪种权重文件。

8.2 迁移回归：搬完必须重跑的三件事

3
  1. 输出质量：固定 prompt 回归集（10–20 条覆盖你的业务）对比 Ollama 与 vLLM 的输出——同一 GGUF 档位在两个引擎上的采样路径、template 渲染可能有差异，系统提示要在 vLLM 侧重新确认生效；
  2. 延迟特征：Ollama 单用户低延迟 vs vLLM 高并发吞吐优先，同样的 num_predict 在 vLLM 上 TTFT/TPOT 口径不同，SLO 要重新定；
  3. 并发行为：Ollama 的 OLLAMA_NUM_PARALLEL 是每模型并发上限，vLLM 的 max-num-seqs 是单实例所有序列上限——负载均衡多实例时别重复计数。

9.1 本地部署的经济账：什么时候比调 API 便宜

3

本地部署的成本不体现在账单上，但一样是钱。算式为本文自建模型，单价为示例占位，以你的实际硬件与电价为准：

月本地成本 = 硬件购置价 / 折旧月数 + 功耗(kW) × 运行小时 × 电价
每百万token成本 = 月本地成本 / (月生成token / 1e6)
盈亏平衡条件 = 月API成本(同token量) > 月本地成本

代入示例占位：一张 8,000 元的消费级显卡按 36 个月折旧（约 222 元/月），整机推理功耗 0.35 kW、每天跑 12 小时、电价 0.6 元/度，则月成本 ≈ 222 + 0.35 × 360 × 0.6 ≈ 298 元/月。若 7B Q4 模型实测输出 40 tok/s、利用率 25%，月生成 ≈ 40 × 3600 × 12 × 30 × 0.25 ≈ 3.9 亿 token，每百万 token 成本 ≈ 298 / 390 ≈ 0.76 元。

三个结论：

  1. 量小不划算：每月只用几百万 token 时，API 按量付费远低于折旧+电费，本地部署的合理动机是隐私/离线/学习，不是省钱。
  2. 利用率决定一切：同一台机器，利用率从 25% 提到 75%，每 token 成本直接除以 3——团队共享一个 Ollama 实例比每人各跑各的省。
  3. 别忽略隐性成本：维护升级、翻车排查的人力时间没算进上式；把它折进去，盈亏平衡点还要后移。与 vLLM 高吞吐场景的对比见 L12 vLLM 推理加速 第 9 节。
9.2 OpenAI 兼容流式调用（对话产品标配）1 个重点▾ 点开看本节重点
本节重点
  • stream.close() 用户中断时必须关闭：否则服务端继续生成、白烧 GPU
3

Ollama 的 /v1 端点与 OpenAI SDK 兼容，流式只需 stream=True（本文编写，pip install openai）：

from openai import OpenAI
client = OpenAI(base_url="http://127.0.0.1:11434/v1", api_key="ollama")

stream = client.chat.completions.create(
    model="qwen2.5:7b",
    messages=[{"role": "user", "content": "用三句话解释 KV cache"}],
    stream=True,
)
try:
    for chunk in stream:
        if chunk.choices and chunk.choices[0].delta.content:
            print(chunk.choices[0].delta.content, end="", flush=True)
finally:
    stream.close()   # 用户中断时必须关闭：否则服务端继续生成、白烧 GPU

两个 Ollama 特有注意点：① 单实例默认并发有限（第 4 节 OLLAMA_NUM_PARALLEL），流式长连接会占住并发槽，前端要做超时与取消；② 流式下想拿 token 用量，用原生 /api/generate 响应末帧的 eval_count/prompt_eval_count，OpenAI 兼容层的 usage 字段支持以你所用版本实测为准。

2
术语 一句话定义
GGUF llama.cpp 生态的单文件模型格式，打包元数据+张量，支持 CPU/GPU 混载与 mmap
Modelfile Ollama 的声明式模型描述文件：FROM/参数/模板/系统提示

  • 本库确实在用 Ollama，但只用于 embedding 与生成，不用来跑量化大模型（rag/config.yaml L16 / L132-136，grep 可验）：
    yaml ollama_url: "http://localhost:11434"
    yaml generation: # [2026-10-21] 切回火山豆包(实测200/2.2s通)。回退小米: 改回下面注释三行 model: "doubao-seed-2.1-lite" api_url: "https://ark.cn-beijing.volces.com/api/plan/v3/chat/completions" api_key_env: "VOLCENGINE_ARK_PLAN_KEY"

  • 稀疏向量走 Ollama 的坑（rag/config.yaml L18-20 注释，grep 可验）：
    yaml # [2026-10-14 澄清] eval_mode=true 仅让 *dense* 编码走 Ollama(省内存), # 不再影响 sparse —— query_sparse() 已改为独立加载本地模型(_get_sparse_model)。 # Ollama 的 bge-m3 只输出 dense 1024 维, 没有 lexical_weights, 无法提供 sparse。
