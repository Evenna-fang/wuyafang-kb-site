L12 GPTQ 量化实操：从论文算法到 2026 年的工具链

TL;DR：GPTQ 是一次性（one-shot）权重量化：用校准数据算出每层的 Hessian，逐列量化并把误差补偿给还没量化的列。论文报告 OPT-175B 在单张 A100 上约 4.2 小时量化完，4bit 的 WikiText2 困惑度只比 FP16 高 0.03。2026 年做 GPTQ 量化不再用 AutoGPTQ，要用 GPTQModel 或 llm-compressor。本篇给出：算法五个设计点的拆解、本机实跑的玩具实现（验证"通道相关性越强，GPTQ 收益越大"）、三条工具链的操作步骤与参数、vLLM 加载与评测方法、翻车排查。

WHYT：逐层量化目标与五个算法设计点

1. GPTQ 在做什么：一个逐层的最小二乘问题

2

GPTQ 把"量化整个模型"拆成"逐层量化"。对第 ℓ 层，设原始权重为 W，校准数据经过前面各层后到达该层的输入为 X，要找一个落在量化网格上的 Ŵ，使该层输出的变化最小：

argmin_Ŵ  ‖ W·X − Ŵ·X ‖²₂

这是论文的层级目标（源：arXiv:2210.17323）。注意它优化的是输出的误差，不是权重本身的误差。两者的差别在《L12-模型量化》§4.2 已经实测过：4bit 权重重构误差约 0.5%，输出相对误差却有 15.6%。GPTQ 的出发点就是直接压输出误差。

这个目标有两个关键推论：

  1. 目标对 X 敏感，所以必须有校准数据，且校准数据的分布会影响结果（§3.4、§10.1 有实测）。
  2. 目标的二阶项是 Hessian H = 2XXᵀ。如果两个输入通道高度相关，量化其中一个权重造成的误差可以由另一个通道的权重"吃掉"。GPTQ 的全部收益就来自这种补偿，通道之间互不相关时收益很小（§3.2 有实测）。

GPTQ 的前身是 OBQ（Optimal Brain Quantization），每量化一个权重，就按 OBS（Optimal Brain Surgeon）公式更新其余未量化权重：

选下一个权重：w_q = argmin (quant(w_q) − w_q)² / [H_F⁻¹]_qq
补偿其余权重：δ_F = −(w_q − quant(w_q)) / [H_F⁻¹]_qq · (H_F⁻¹)_{:,q}

其中 F 是尚未量化的权重集合（源：论文 §3，经 ar5iv 页面核对）。OBQ 精确但慢，量化 175B 模型不可行。GPTQ 做了四处改动，加上一个工程细节，共五点：

① 任意顺序（arbitrary order）。 OBQ 每一行各自贪心选下一个权重，所以每行的 H⁻¹ 都不同。GPTQ 发现：按同一个固定列顺序量化所有行，效果几乎不差。这样所有行共享同一个 H⁻¹，只依赖层输入。论文给出的复杂度从 O(d_row·d_col³) 降到 O(max{d_row·d_col², d_col³})，加速比为 min{d_row, d_col}。

② 懒批量更新（lazy batch updates）。 逐列更新时，每次都要整块读写权重和 H⁻¹，GPU 算力吃不满。GPTQ 把列分成 B = 128 一块：块内的更新局部做，块结束后再一次性更新块外的列。数学结果不变，访存次数大幅下降。

③ Cholesky 重构。 反复更新 H⁻¹ 会累积数值误差，大模型上会让 H⁻¹ 变得不正定。GPTQ 改成一开始对 H⁻¹ 做一次 Cholesky 分解，之后只用分解出来的因子。论文原话的意思是：小模型只靠阻尼就够，大模型必须用 Cholesky。

④ 阻尼（dampening）。 给 H 的对角线加 λI，λ 取对角线平均值的 1%。目的是防止 H 奇异或接近奇异。

⑤ 校准数据与网格。 论文用 C4 的 128 条随机片段，每条 2048 token；量化网格是逐行（每个输出通道）的 min-max 非对称均匀网格，口径类似 LLM.int8()；基线 RTN 用同一套网格直接取最近值。

工程细节：论文把 6 个 Transformer 层作为一个块依次搬进 GPU，每块的输入来自已部分量化的模型。这意味着后面的层看到的是前面量化后的激活，误差不会"看不见"。

HOW：玩具验证、量化操作、部署与质量验收

3. 本机实跑：玩具 GPTQ

2

下面这份脚本按上述五点实现了一个 numpy 版 GPTQ（仅为说明机理，不是生产实现），在合成数据上对比 RTN。合成数据的限制：权重是高斯随机数，输入的协方差谱按幂律 i^(−decay) 衰减，decay 越大通道相关性越强；度量的是层输出误差，不是整模型困惑度。数字用来验证"机理方向"，不能换算成真实模型的掉点。

import numpy as np

def make_layer(seed=0, d_out=256, d_in=512, n=2048, decay=0.5):
    rng = np.random.default_rng(seed)
    Q, _ = np.linalg.qr(rng.normal(size=(d_in, d_in)))
    sv = np.arange(1, d_in + 1) ** (-decay)       # decay=0 -> 各向同性（通道不相关）
    X = (rng.normal(size=(n, d_in)) * sv) @ Q.T
    W = rng.normal(0, 0.02, size=(d_out, d_in))
    return W, X.T                                   # X: (d_in, n)

def grid_params(blk, bits):                         # 逐行 min-max 非对称网格
    qmax = 2 ** bits - 1
    mn, mx = np.minimum(blk.min(1), 0), np.maximum(blk.max(1), 0)
    scale = (mx - mn) / qmax
    scale[scale == 0] = 1.0
    return scale, np.round(-mn / scale), qmax

def quant_col(w, scale, zp, qmax):
    return (np.clip(np.round(w / scale) + zp, 0, qmax) - zp) * scale

def rtn(W, bits, group=128):
    out = np.empty_like(W)
    for g in range(0, W.shape[1], group):
        b = W[:, g:g + group]
        s, z, qm = grid_params(b, bits)
        out[:, g:g + group] = quant_col(b, s[:, None], z[:, None], qm)
    return out

def gptq(W, X, bits, group=128, block=128, damp=0.01):
    W = W.copy(); d_in = W.shape[1]
    H = 2 * X @ X.T
    H[np.diag_indices(d_in)] += damp * np.mean(np.diag(H))        # ④ 阻尼
    Hinv = np.linalg.cholesky(np.linalg.inv(H)).T                  # ③ Cholesky
    Q = np.zeros_like(W)
    for i1 in range(0, d_in, block):                               # ② 懒批量
        i2 = min(i1 + block, d_in)
        W1 = W[:, i1:i2].copy(); Err1 = np.zeros_like(W1); Hinv1 = Hinv[i1:i2, i1:i2]
        for i in range(i2 - i1):
            col = i1 + i
            if col % group == 0:                                   # 新 group：用已补偿的权重定网格
                scale, zp, qmax = grid_params(W1[:, i:i + group], bits)
            q = quant_col(W1[:, i], scale, zp, qmax)
            Q[:, col] = q
            err = (W1[:, i] - q) / Hinv1[i, i]
            W1[:, i:] -= np.outer(err, Hinv1[i, i:])               # ① 固定列序下块内补偿
            Err1[:, i] = err
        W[:, i2:] -= Err1 @ Hinv[i1:i2, i2:]                       # 块结束后更新块外
    return Q

def layer_loss(W, Wq, X):
    return float(np.linalg.norm((W - Wq) @ X) ** 2 / X.shape[1])

说明：此处 block 与 group 都取 128 且对齐，所以一个 group 不会跨块。完整脚本含四组实验，下面逐组给出输出。

本节重点

读数：decay=0 时输入各通道不相关，没有可补偿的方向，GPTQ 只比 RTN 好 12%（0.878）。随着 decay 增大，输入越集中在少数主方向，GPTQ 把误差推向"几乎不影响输出"的方向，层误差降到 RTN 的 2.3%（decay=1.0）和 0.9%（decay=1.5）。这就是 GPTQ 的机理：它不是把每个权重量化得更准，而是把误差放到输出看不见的地方。 真实 LLM 的激活相关性很强，这解释了论文里 4bit 下 GPTQ 稳定优于 RTN。

我第一次跑这个实验时，用的是"一个共享因子占 0.9"的输入，GPTQ/RTN 在 4/3/2bit 下都恰好是 0.019，相同得不正常。原因是这样构造的 X 近似秩 1，补偿几乎完美。这是合成数据的假象，所以换成幂律谱并加了 decay=0 的负对照。用玩具实验验证机理时，必须同时给一个"机理不应起作用"的对照组，否则看不出是机理在起作用还是数据构造在起作用。

推理加速： 3bit 自定义 kernel，batch size 1、生成 128 token：A100 80GB 上 230 ms→71 ms（3.24×，GPU 数 5→1）；A6000 48GB 上 589 ms→130 ms（4.53×，GPU 数 8→2）。论文明确说明：加速来自减少矩阵向量乘的访存，不减少计算量，也不量化激活。这条结论对判断"GPTQ 什么时候有用"很重要：权重量化只在访存受限（小 batch、decode 阶段）时提速；大 batch 或 prefill 阶段计算受限，收益变小。Marlin 专门解决这个问题（§8）。

llm-compressor（vLLM 项目） 活跃；输出 compressed-tensors 格式，与 vLLM 原生衔接；支持 GPTQ、AWQ、SmoothQuant、AutoRound 等 面向 vLLM 部署的量化 llm-compressor README、vLLM 文档
Marlin 推理 kernel，不支持量化 加速 4bit 推理 transformers 文档、Marlin README

选择建议（我的判断，非官方结论）：目标引擎是 vLLM、且希望一套工具覆盖 GPTQ/AWQ/FP8 → llm-compressor；需要 GPTQModel 特有能力（非对称、多后端 kernel、Apple/AMD/CPU 等平台、per-module dynamic）→ GPTQModel；只想最快产出一个 HF 格式的 4bit 模型 → transformers 的 GPTQConfig（底层调用 GPTQModel）。

两个历史包袱要认识：①网上大量 2023–2024 教程用 AutoGPTQ，其 API 与产出的权重格式与 GPTQModel 不完全兼容（transformers 文档：GPTQModel "is not backward compatible with legacy AutoGPTQ checkpoints"）。②Hugging Face Hub 上大量现成 GPTQ 权重（vLLM 文档称 5000 个以上）是旧工具产出的，加载（推理）通常没问题，GPTQModel README 的迁移说明也提到现有 GPTQ/AWQ 推理集成一般不用改；但用新工具重新量化时，参数名和默认值会变，见 §7。

6.3 路径 C：llm-compressor 的 GPTQModifier（vLLM 官方 INT4 配方）

3

环境隔离：vLLM 文档明确建议用两个独立虚拟环境，一个装 llmcompressor（量化），一个装 vllm 与 lm-eval[api]>=0.4.12（服务与评测），因为两者的依赖可能冲突。GPTQModel README 对 vLLM / SGLang 也有同样的建议。

from transformers import AutoTokenizer, AutoModelForCausalLM
from datasets import load_dataset
from llmcompressor import oneshot
from llmcompressor.modifiers.quantization import GPTQModifier

MODEL_ID = "meta-llama/Meta-Llama-3-8B-Instruct"
model = AutoModelForCausalLM.from_pretrained(MODEL_ID, device_map="auto", dtype="auto")
tokenizer = AutoTokenizer.from_pretrained(MODEL_ID)

NUM_CALIBRATION_SAMPLES, MAX_SEQUENCE_LENGTH = 512, 2048
ds = load_dataset("HuggingFaceH4/ultrachat_200k", split="train_sft")
ds = ds.shuffle(seed=42).select(range(NUM_CALIBRATION_SAMPLES))
ds = ds.map(lambda ex: {"text": tokenizer.apply_chat_template(ex["messages"], tokenize=False)})
ds = ds.map(lambda s: tokenizer(s["text"], padding=False, max_length=MAX_SEQUENCE_LENGTH,
                                truncation=True, add_special_tokens=False),
            remove_columns=ds.column_names)

recipe = GPTQModifier(targets="Linear", scheme="W4A16", ignore=["lm_head"])
oneshot(model=model, dataset=ds, recipe=recipe,
        max_seq_length=MAX_SEQUENCE_LENGTH, num_calibration_samples=NUM_CALIBRATION_SAMPLES)

SAVE_DIR = MODEL_ID.split("/")[1] + "-W4A16-G128"
model.save_pretrained(SAVE_DIR, save_compressed=True)   # 必须 save_compressed=True，才会存成 compressed-tensors 打包格式
tokenizer.save_pretrained(SAVE_DIR)

两个细节：①预处理里用 apply_chat_template 再 add_special_tokens=False，因为模板已经带了 BOS。文档提示量化模型对 BOS 敏感，评测时要加 add_bos_token=true（§9）。②ignore=["lm_head"] 表示输出层不量化，输出层对精度敏感且参数占比小，这是通用做法。

文档还给出展开写法，可精细控制：QuantizationArgs(num_bits=4, type=INT, strategy=GROUP, group_size=128, symmetric=True, dynamic=False, actorder="weight")，另有 update_size=NUM_CALIBRATION_SAMPLES 与 dampening_frac=0.01。

2
参数 含义 常见取值 影响与取舍 依据
bits 权重位宽 4（默认）；3、2 更激进 4bit 是质量/体积的拐点；3bit 以下模型越小越容易掉点（§4 表中 125M–6.7B 的 3bit GPTQ 退化明显） 论文、GPTQModel README（GSQ 支持 2–8bit）
group_size 多少个权重共享一组 scale/zp 128（事实默认）；64、32 更细；-1 表示整行 越小越准、元数据越多。4bit 对称+FP16 scale：g128 是 4.125 bit/权重，g32 是 4.5 bit/权重（我算的） 论文、各工具默认值
desc_act（activation reordering，act-order） 按激活大小降序量化列 True / False 通常提升精度；GPTQModel README 里 GAR 要求 desc_act=False；对 kernel 速度的影响因后端而异，以所用版本文档为准 官方 gptq 仓库 --act-order、GPTQModel README
sym 对称/非对称 True / False GPTQModel 支持非对称，可能降低误差，但 transformers 文档指出"并非所有 kernel（如 Marlin）支持非对称" transformers 文档
阻尼 damp_percent / dampening_frac H 对角线加的比例 0.01 过小数值不稳定，过大补偿弱（§3.3） 论文、llm-compressor 文档
校准样本数 估计 H 的数据量 128×2048（论文）、512×2048（llm-compressor）、1024 条（GPTQModel 示例） 少则 H 估计不准（§3.4） 同上
序列长度 每条校准样本 token 数 2048 文档建议从 2048 起步 llm-compressor 文档
ignore 不量化的层 ["lm_head"] MoE 的 router/gate 等小而敏感的层也常排除 llm-compressor README 示例
true-sequential（原仓库） 块内子层按先后顺序量化 开 后面的子层看到前面已量化的结果 官方 gptq 仓库

group_size 的存储账（实算）。 4bit 对称、每组一个 FP16 scale：每权重实际占 4 + 16/g 位。g=32→4.5，g=64→4.25，g=128→4.125，g=256→4.0625。若再存一个 FP16 零点（非对称），g=128 变成 4.25。所以 8B 模型（8.03B 参数）权重约 4.1 GB，对 FP16 的 16.1 GB 节省 74.2%；70.6B 的 70B 模型从 141.2 GB 降到 36.4 GB。这是"理论权重体积"，不含 embedding/lm_head 保持 FP16 的部分，实际文件会略大。 Marlin README 提到的理论加速上限 3.87× 正是 16 ÷ 4.125 = 3.879，两处数字能对上。

8.2 Marlin 与硬件

3
  • Marlin 是什么：IST-DASLab 的 FP16×INT4 矩阵乘 kernel。README 称在 batch size 16–32 以内能接近理想的 4× 加速（理论上限 3.87×，g128），而此前的 kernel 只在 1–2 个 token 时有效。要求 CUDA 11.8+，GPU 算力 ≥ 8.0（Ampere、Ada）；README 写"尚未针对 Hopper 优化"。
  • vLLM 侧：vLLM 的 GPTQModel 页面称，兼容的模型可用 vLLM 的 Marlin 与 Machete 自定义 kernel，面向 Ampere（A100+）与 Hopper（H100+）。（Marlin README 与此处对 Hopper 的说法不同，前者是较早的仓库说明，后者是 vLLM 当前文档；Hopper 卡请以 vLLM 当前版本的启动日志为准。）
  • transformers 侧：GPTQConfig(bits=4, backend="marlin") 可启用，文档注明 Marlin 只做推理、不支持量化。
  • GPTQModel 侧：Marlin 对应 BACKEND.GPTQ_MARLIN 与 FORMAT.MARLIN，另有 GPTQ_MACHETE、GPTQ_EXLLAMA_V2、GPTQ_TRITON、GPTQ_TORCH 等十余个后端。
  • 精度（Marlin README，4bit g128，WikiText2 困惑度）：Llama2-7B 5.12→5.27，13B 4.57→4.67，70B 3.12→3.21，MMLU 41.80→40.07、52.10→51.13、65.43→64.81。这些是 Marlin 仓库自带 GPTQ 脚本的结果，且 Llama2-7B 的 FP16 困惑度 5.12 与 AWQ 论文表里的 5.47 不同，说明两处评测口径（如上下文长度）不一致，不同来源的困惑度不能直接比较，只能比较同一来源内部的"量化前后"。

kernel 路径检查（对应《L12-模型量化》§5.3）：启动 vLLM 后在日志里确认量化层走的是 Marlin/Machete 一类的优化 kernel，而不是 fallback。二手基准称走不走 Marlin 吞吐可差 4–10 倍（《L12-模型量化》§4.3 已标注二手），所以量化上线必须压测对照 FP16 基线。

9. 质量验证：不看 perplexity 一个指标3 个重点▾ 点开看本章重点
本章重点

2

做完量化，按下面三步验证（沿用《L12-模型量化》§5.1 的"双指标"纪律）：

第一步：能加载、能出字。 用 §8.1 的代码跑 10–20 条真实业务 prompt，肉眼看有没有乱码、重复、截断。

第二步：任务级评测。 vLLM 文档给的命令（在装了 vllm 与 lm-eval 的环境里）：

lm_eval --model vllm \
  --model_args pretrained="./Meta-Llama-3-8B-Instruct-W4A16-G128",add_bos_token=true \
  --tasks gsm8k --num_fewshot 5 --limit 250 --batch_size 'auto'

关键是 add_bos_token=true（文档提示量化模型对 BOS 敏感）。--limit 250 只跑 250 条，样本少，波动在几个百分点，只用于冒烟。正式对比要跑全量并用同一份脚本评测 FP16 基线，记录"量化后/基线"的恢复率。

第三步：业务回归集。 从你的真实流量取 100–500 条，带标准答案，跑 FP16 与 GPTQ 两套，逐条对比。这一步抓的是通用 benchmark 抓不到的问题，§10.1 解释了原因。

判定标准由业务定，不照抄别人的阈值。《L12-模型量化》§5.1 里的对比器脚本可直接复用。

10.1 校准域与评测域不一致3 个重点▾ 点开看本节重点

3

现象：通用 benchmark 正常，业务数据上明显变差。

机理（实跑，玩具）：GPTQ 的补偿是针对校准数据的协方差定制的。我在合成数据上用 A 域校准、B 域评估（离群通道位置相同、通道相关结构不同），三个随机种子下：

seed=0  同域: GPTQ=1.642e+00 | 换域(B): GPTQ=6.279e+00 RTN=5.924e+00 | GPTQ换域/同域=3.82x
seed=1  同域: GPTQ=1.842e+00 | 换域(B): GPTQ=5.724e+00 RTN=5.725e+00 | GPTQ换域/同域=3.11x
seed=2  同域: GPTQ=1.544e+00 | 换域(B): GPTQ=6.131e+00 RTN=6.165e+00 | GPTQ换域/同域=3.97x

读数：换域后 GPTQ 的层误差涨到同域的 3.11–3.97 倍，几乎退化到和 RTN 一样（5.72–6.28 vs 5.72–6.17）。这是极端构造，真实模型不会退化得这么彻底，但方向可信：GPTQ 的优势有一部分是"对校准分布的拟合"。AWQ 论文给的对应数字是：校准集与评测集不同时，AWQ 的困惑度上升 0.5–0.6，GPTQ 上升 2.3–4.9（AWQ 作者的实验，见《L12-AWQ量化实操》§5）。改法：校准数据取业务代表性样本，条数用到 512 条以上；若模型做过微调，用一部分训练数据校准（llm-compressor 文档的建议）；对话模型要套模板。

10.2 数值不稳定

3

现象：量化中途报 Cholesky 失败、出现 NaN，或某些层权重异常。

机理：H 奇异或接近奇异（常见于校准数据太少、重复多、有死通道）。改法：先把校准数据加大并去重，再考虑提高阻尼（把 dampening_frac 从 0.01 往上调一档）。不要往下调。我实测 float64 下阻尼从 0.01 降到 1e-4 只带来 3% 的误差改善（§3.3），不值得冒稳定性风险。

3

10.6 不要拿 3bit 当省显存的默认答案

3

论文表里 OPT-125M 的 3bit GPTQ 困惑度是 53.85（FP16 为 27.65），OPT-66B 的 3bit 是 14.16（FP16 为 9.34），6.7B 是 14.86（FP16 为 10.86），说明 3bit 对不同规模模型的损伤并不单调。改法：默认 4bit g128，3bit 只在 4bit 也放不下时考虑，且要完整回归。

  7. 质量：任务级评测对照 FP16 基线（含 add_bos_token=true）+ 业务回归集。
  8. 性能：压测 TTFT 与吞吐，对照 FP16 基线，不只看显存。
  9. 回滚：保留 FP16 原始权重与量化脚本、校准数据的版本号。

12. 术语表

2
术语 一句话定义
one-shot 只用少量校准数据、不做训练就完成量化
Hessian（H=2XXᵀ） 层输出误差对权重的二阶导，反映输入通道的相关性
OBS / OBQ 最优脑外科 / 最优脑量化，GPTQ 的算法祖先，量化一个权重后补偿其余权重
懒批量更新 块内局部更新、块结束统一更新块外，减少访存
Cholesky 分解 把正定矩阵分解为三角因子，GPTQ 用它避免反复求逆的数值误差
阻尼 给 H 对角线加 λI，防奇异，λ=对角线均值的 1%
act-order / desc_act 按激活幅值降序量化列
W4A16 权重 4bit、激活保持 16bit
compressed-tensors llm-compressor 的保存格式，vLLM 可直接读取
Marlin / Machete vLLM 中的 4bit 权重矩阵乘优化 kernel

13.1 成本侧：量化本身不是零成本

3 
一次性成本 = 校准量化GPU时 × 时价 + 质量回归评测GPU时 × 时价 + 人工排查工时

GPTQ 是逐层二阶校准，7B 模型通常以"小时"计、70B 以"数十小时"计（量级随硬件与实现差异大，以你的实测为准，此处不给确定数字）；第 9 节的质量回归（多任务而非只看 perplexity）同样占 GPU 时。校准域不匹配返工一次（10.1 节），一次性成本直接翻倍——前期在校准数据上花的时间是省钱不是花钱。

13.2 收益侧与回本点3 个重点▾ 点开看本节重点
本节重点
  • 其中每百万 token 成本用 vLLM 篇第 9 节算式（GPU 时价 / 有效吞吐）分别代入原精度与量化后的实测吞吐
  • 3. 少开卡：原需 2 卡的模型量化后 1 卡可跑，GPU 时成本减半——这是回本最快的情形
  • 判读口径：回本月数 ≤ 3 个月且质量回归通过，值得做；模型迭代快（每月换底座）的团队，一次性成本会反复发生，优先选"少开卡"这种当月见效的收益，而不是赌长期摊薄
3 
月收益 = (原精度每百万token成本 - 量化后每百万token成本) × 月token量 / 1e6
回本月数 = 一次性成本 / 月收益

其中每百万 token 成本用 vLLM 篇第 9 节算式（GPU 时价 / 有效吞吐）分别代入原精度与量化后的实测吞吐。量化带来的收益有三个来源，别只算显存：

  1. 同卡可跑更大模型或更长上下文：KV cache 预算变大（显存收益核算见《L12-模型量化-GPTQ-AWQ-GGUF》5.4 节）；
  2. 吞吐提升：Marlin kernel（8.2 节）在兼容硬件上提升解码吞吐，直接降单价；
  3. 少开卡：原需 2 卡的模型量化后 1 卡可跑，GPU 时成本减半——这是回本最快的情形。

判读口径：回本月数 ≤ 3 个月且质量回归通过，值得做；模型迭代快（每月换底座）的团队，一次性成本会反复发生，优先选"少开卡"这种当月见效的收益，而不是赌长期摊薄。

13.3 与"直接换小模型"的对照

3

量化的替代方案不是只有"跑原精度"，还有"直接换同家族小一号模型"。决策顺序建议：先比小模型原精度 vs 大模型 4bit 的任务指标（用同一套回归集），任务指标相当时选总成本低的；量化保住的是"大模型的能力上限"，如果任务用不到这个上限，量化就是在为不需要的能力付校准成本。
