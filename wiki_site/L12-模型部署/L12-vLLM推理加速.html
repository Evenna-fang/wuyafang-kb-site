Transformer 推理的显存大头不是权重而是 KV cache：每生成一个 token，就要为它缓存所有历史 token 的 Key/Value 向量。朴素实现按 max_model_len 一次性给每条序列预留连续大块显存，序列没用满也占着——碎片化严重。

PagedAttention 借鉴操作系统的虚拟内存分页：把 KV cache 切成固定大小的块（block），序列按需申请块、块之间不必连续。效果是同样的显存能塞下更多并发序列，且序列结束立刻释放块给新请求。它不改变计算结果，只改变显存的分配方式——所以 PagedAttention 是"显存效率"优化，不是"计算加速"优化。

1.2 Continuous batching：请求随完成随进随出

3

传统静态批处理把一批请求凑齐、算完、再进下一批——一条短请求要等同批最长的那条。Continuous batching 让每个迭代步都重新组批：完成的序列退出、排队的序列补进来。这就是 vLLM 并发吞吐的来源，也是为什么不要在应用层自己攒批——引擎已经做了，应用层攒批只会把延迟堆高。

prefill 与 decode 的矛盾是本质性的：prefill 是计算密集（把整段 prompt 一次算完），decode 是内存带宽密集（每 token 只做一次小计算）。一个长 prompt 的 prefill 会阻塞同批所有 decode，表现为延迟毛刺。--enable-chunked-prefill 把长 prompt 切块、和 decode 混批执行，是在线服务压毛刺的首选开关。

下面的实跑量化了"阻塞"到底多严重：

"""Batched prefill 时间估算：对比 chunked-prefill on/off 下，一条长 prompt
对同批其他 decode 请求的阻塞时间。"""
def prefill_block(prompt_tokens, prefill_tok_s=4000, chunk_size=None):
    total = prompt_tokens / prefill_tok_s
    if chunk_size is None:
        return round(total, 3), "整块 prefill，阻塞全批 decode"
    chunks = (prompt_tokens + chunk_size - 1) // chunk_size
    per_chunk = chunk_size / prefill_tok_s
    return round(per_chunk, 3), f"切成 {chunks} 块，每块 decode 最多等 {per_chunk:.3f}s"

if __name__ == "__main__":
    for pt in [1024, 4096, 16384]:
        t1, d1 = prefill_block(pt)
        t2, d2 = prefill_block(pt, chunk_size=512)
        print(f"prompt={pt}: 关chunked -> {t1}s ({d1})")
        print(f"           开chunked(512) -> {d2}")

3.1 KV cache 算式

3

每 token 的 KV cache 字节数：

per_token = 2 × num_layers × num_kv_heads × head_dim × dtype_bytes
  • 2 是 K 和 V 两份；
  • GQA/MQA 模型的 num_kv_heads 远小于 num_attention_heads（Llama-3-8B 是 8 个 KV head），这是省 KV cache 的结构性红利；
  • dtype_bytes：FP16/BF16 是 2，INT8 KV cache 是 1。

def kv_cache_bytes(num_layers, num_kv_heads, head_dim, max_model_len,
                   dtype_bytes=2, batch=1):
    per_token = 2 * num_layers * num_kv_heads * head_dim * dtype_bytes
    return per_token * max_model_len * batch, per_token

def total_vram_gb(params_b, weight_bytes, kv_bytes, overhead_gb=2.0):
    return params_b * weight_bytes + kv_bytes / 1024**3 + overhead_gb

# Llama-3-8B 近似结构：32 层, 8 个 KV head(GQA), head_dim 128
b, per = kv_cache_bytes(32, 8, 128, 8192, 2, 1)

import math

def ttft_tpot_model(prompt_len, output_len, prefill_tok_s, decode_tok_s):
    """离线估算 TTFT / TPOT / 总时延 —— 用于容量规划 sanity check。"""
    ttft = prompt_len / prefill_tok_s
    tpot = 1.0 / decode_tok_s
    total = ttft + output_len * tpot
    return round(ttft, 3), round(tpot * 1000, 2), round(total, 2)

def concurrency_vs_latency(base_tpot_ms, n_seq, contention=0.06):
    """连续批处理下 TPOT 随并发粗估：每翻倍并发 + contention 的比例惩罚。"""
    factor = 1 + contention * math.log2(max(n_seq, 1))
    return round(base_tpot_ms * factor, 2)

if __name__ == "__main__":
    for plen, olen in [(256, 256), (4096, 256), (8192, 512)]:
        ttft, tpot, total = ttft_tpot_model(plen, olen, 4000, 60)
        print(f"prompt={plen} out={olen} -> TTFT={ttft}s TPOT={tpot}ms total={total}s")
    for n in [1, 8, 16, 32, 64]:
        print(f"并发{n}: 估算TPOT={concurrency_vs_latency(25, n)}ms")

"""vLLM 启动参数模板生成器：按场景输出命令行/JSON config。"""
def gen_config(scenario="online", model="meta-llama/Llama-3-8B-Instruct",
               gpu_gb=24, max_len=8192, tp=1):
    cfg = {
        "model": model,
        "gpu_memory_utilization": 0.85,
        "max_model_len": max_len,
        "tensor_parallel_size": tp,
        "port": 8000,
    }
    if scenario == "online":
        cfg.update({"max_num_seqs": 16, "enable_chunked_prefill": True,
                    "enable_prefix_caching": True})
        cfg["gpu_memory_utilization"] = 0.80
    elif scenario == "batch":
        cfg.update({"max_num_seqs": 256, "enable_chunked_prefill": True,
                    "enable_prefix_caching": False})
        cfg["gpu_memory_utilization"] = 0.90
    elif scenario == "low_vram":
        cfg.update({"max_num_seqs": 8, "enable_prefix_caching": True})
        cfg["gpu_memory_utilization"] = 0.70
        cfg["max_model_len"] = min(max_len, 4096)
    cfg["enable_metrics"] = True
    cfg["metrics_port"] = 9090
    return cfg

def to_cli(cfg):
    flags = {
        "model": "--model", "gpu_memory_utilization": "--gpu-memory-utilization",
        "max_model_len": "--max-model-len", "tensor_parallel_size": "--tensor-parallel-size",
        "max_num_seqs": "--max-num-seqs", "port": "--port",
    }
    parts = ["vllm serve"]
    for k, v in cfg.items():
        if k in flags:
            parts.append(f"{flags[k]} {v}")
    for k in ["enable_chunked_prefill", "enable_prefix_caching", "enable_metrics"]:
        if cfg.get(k):
            parts.append("--" + k.replace("_", "-"))
    if cfg.get("metrics_port"):
        parts.append(f"--metrics-port {cfg['metrics_port']}")
    return " \\\n  ".join(parts)

if __name__ == "__main__":
    for s in ["online", "batch", "low_vram"]:
        print(f"# === {s} ===")
        print(to_cli(gen_config(s)))
        print()

5.1 Prefix caching 的坑

3

--enable-prefix-caching 对 agent/多轮/RAG 提速明显（共享 system prompt 跳过重复 prefill），但：

  • 收益要用 benchmarks/benchmark_prefix_caching.py 或自建负载 A/B 验证，别假设一定赚。

        "prefill计算": round(expect_prefill, 3),
        "调度/网络开销": round(max(overhead, 0), 3),

现象：内网压测（固定 256 token prompt、32 并发）稳如老狗；接真实流量（用户贴 10K 文档问问题）两小时后 OOM 重启。

翻车现象的共同根源是"批处理模型选错后，怎么调参数都别扭"。下面的模拟用同一组 8 条异构请求（到达时间、prompt 长度、输出长度都不同）对比两种策略，直观看到 continuous batching 为什么是 vLLM 的默认：

"""连续批处理队列模拟：对比 static batching vs continuous batching 的完成时间。
可离线跑，直观展示两种批处理策略的差异。"""

def static_batching(reqs, batch_size=4, per_tok=0.01):
    """reqs: [(arrival, prompt_len, output_len)] 固定凑批。"""
    t = 0.0; done = []
    pending = sorted(reqs)
    i = 0
    while i < len(pending):
        batch = pending[i:i+batch_size]; i += batch_size
        start = max(t, max(a for a, _, _ in batch))
        batch_time = max(p + o for _, p, o in batch) * per_tok
        t = start + batch_time
        for a, p, o in batch:
            done.append(round(t - a, 2))
    return done

def continuous_batching(reqs, max_seqs=4, per_tok=0.01):
    """近似：逐 token 调度，完成即补位。"""
    t = 0.0
    events = sorted(reqs)
    active = []
    waiting = list(events)
    done = []
    while waiting or active:
        while waiting and len(active) < max_seqs and waiting[0][0] <= t:
            a, p, o = waiting.pop(0)
            active.append([a, p, o])
        if not active:
            t = max(t, waiting[0][0]); continue
        t += per_tok * (1 + 0.05 * len(active))
        still = []
        for seq in active:
            seq[2] -= 1
            if seq[2] <= 0:
                done.append(round(t - seq[0], 2))
            else:
                still.append(seq)
        active = still
    return done

    c = continuous_batching(reqs, max_seqs=4)

def hit(seq_prefix, cache_prefix):

9.1 每百万 token 成本：一个算式串起压测与账单

3 
每GPU小时成本 C = 实例时价（或购置价/折旧小时 + 电费）
每小时可服务token T = 输出吞吐(tok/s) × 3600 × 卡数 × 目标利用率
每百万输出token成本 = C × 卡数 / (T / 1e6)
                = C / (输出吞吐 × 3600 × 目标利用率 / 1e6)

代入示例占位：单卡 A100 时价 8 元、压测输出吞吐 1,500 tok/s（用第 7 节 vllm bench serve 实测值代入，不要抄这个数）、生产目标利用率 50%（留峰值余量）：

T = 1500 × 3600 × 0.5 = 2,700,000 tok/小时
每百万输出token成本 = 8 / 2.7 ≈ 2.96 元

三个推论：

  1. 吞吐翻倍 = 单价减半：第 2 节的吞吐调优（continuous batching、chunked prefill、并发档位）不是性能洁癖，是直接降单价。任何"优化开关"的效果都能用这个算式验收。
  2. 利用率是最大的隐形成本：低谷期空跑的 GPU 照样计费。按 50% 而非 100% 利用率算成本才接近真实账单；利用率长期低于 30% 就该缩容或合批（离线任务攒批跑）。
  3. 与 API 的盈亏平衡点：若同档模型 API 输出价为 P_api（元/百万 token），则自部署划算的条件是 C / (吞吐 × 3600 × 利用率 / 1e6) < P_api，外加数据合规与延迟的约束。量级小时（日 token 量低于盈亏平衡点）直接用 API 更便宜，别为"有自己的推理服务"而部署。

9.2 每日巡检脚本框架（实跑骨架）

"""vLLM 每日巡检：抓 /metrics 关键指标, 与阈值比对, 输出告警项。"""
import urllib.request

def fetch_metrics(base="http://localhost:9090/metrics"):
    with urllib.request.urlopen(base, timeout=10) as r:
        text = r.read().decode()
    return dict(
        line.split(" ", 1) for line in text.splitlines()
        if line and not line.startswith("#") and " " in line
    )

def audit(metrics, thresholds=None):
    th = thresholds or {
        "vllm:num_requests_waiting": ("gt", 0),
        "vllm:gpu_cache_usage_perc": ("gt", 0.9),
    }
    alerts = []
    for key, (op, val) in th.items():
        cur = metrics.get(key)
        if cur is None:
            continue
        cur = float(cur)
        if op == "gt" and cur > val:
            alerts.append(f"{key}={cur} 超过 {val}")
        if op == "lt" and cur < val:
            alerts.append(f"{key}={cur} 低于 {val}")
    return alerts or ["全部正常"]

if __name__ == "__main__":
    # 离线演示: 用模拟指标跑通比对逻辑
    fake = {"vllm:num_requests_waiting": "5",
            "vllm:gpu_cache_usage_perc": "0.95"}
    for a in audit(fake):
        print("告警:", a)

实跑输出（模拟指标触发两条告警）：

告警: vllm:num_requests_waiting=5 超过 0
告警: vllm:gpu_cache_usage_perc=0.95 超过 0.9

读数：fetch_metrics 抓真实 Prometheus 文本格式（--enable-metrics 开启后 /metrics 可达），audit 用阈值表比对。本演示用假指标验证比对逻辑，真实部署时替换 fake 为 fetch_metrics() 的返回。注意指标名前缀 vllm: 随版本可能变，首次接入先看 /metrics 原文确认键名。

  • GPU 侧：nvidia-smi dmon 看显存峰值与 SM 利用率；gpu_cache_usage 长期贴 1.0 说明 KV 池子不够（要么降 max_model_len、要么升 utilization 换显存、要么上 INT8 KV cache）。
  • 队列侧：num_requests_waiting 持续 > 0 说明排队，先看是不是长 prompt 挤占（开 chunked-prefill），再考虑加并发或加实例。
  • 延迟侧：TTFT p99 对照 SLO；TPOT p99 突刺多半是 KV 池子触顶触发 swap，或某条超长序列独占 prefill。
  • 成本侧：把压测拿到的 tok/s × 实际利用率代进自建成本算式（见 模型部署调优实操-2026.md §4.3）——低利用率的自建一定亏（arXiv:2606.11690 实测：同一张 H100 上 Mixtral 8x7B FP16，1 req/s 时 $15.25/百万 token，25 req/s 时 $0.87，17.5 倍差）。上线后每月复核一次利用率，低于盈亏平衡点就该考虑回退 API。
  • 变更侧：升级 vLLM 版本后重跑一次 vllm bench serve 基线——参数默认值和 kernel 路径随版本变（如 gpu-memory-utilization 默认值 0.9 → 0.85），旧结论不要默认沿用。
