1. 为什么要量化

2

量化让模型变小（显存/磁盘↓）、推理和微调都变快（访存带宽需求↓）。显存需求的算式（源：day03微调之量化 课件，已复算）：

基座模型显存 = 参数数量 × 单个参数大小

Llama3 8B FP16：8B 参数 × 2 Byte = 16 GB。换成 INT4：8B × 0.5 Byte = 4 GB——四分之三的显存省下来给 KV cache，直接换并发（见《L12-vLLM推理加速》§3.2 的显存账）。

总显存需求不止权重（课件口径）：

总显存需求 = 基座模型显存 + 微调权重显存 + 中间值显存 + 框架占用显存
（后两项受 上下文大小 与 batch size 影响）

课件示例：Llama3 8B FP16 + LoRA + batch size=4 + context 8K + unsloth = 16G + 0.1G + 2G + 1G = 19.1G。量化砍的是第一项，后三项的乘积关系见《L12-Ollama本地部署》§4.2。

2.1 对称量化（课件数值复现）

3

对称量化的 scale 由最大绝对值决定：scale = |max| / 127（int8），量化 q = round(val / scale)，反量化 val' = q × scale。课件给的算例：max=10.8, min=-7.59, val=5.47，scale = 10.8/127 = 0.085，int8 = round(5.47/0.085) = 64，反量化 = 64 × 0.085 = 5.44。

课件里 0.085 是四舍五入值，精确 scale 是 0.085039——下面的实跑把这点误差也算出来了：

"""课件数值复算：对称 int8 量化 round(5.47/0.085)=64, 反量化=5.44 的完整推导，
含 scale 精度对误差的影响（0.085 是四舍五入值，真实 scale=10.8/127）。"""

def symmetric_int8(val, mx, scale_rounded=None):
    true_scale = abs(mx)/127
    s = scale_rounded if scale_rounded else true_scale
    q = round(val/s)
    deq = q*s
    return q, deq, true_scale, s

if __name__ == "__main__":
    q, deq, ts, s = symmetric_int8(5.47, 10.8, scale_rounded=0.085)
    print(f"round(5.47/0.085)={q}  反量化={round(deq,3)}  (课件数字)")
    q2, deq2, ts2, s2 = symmetric_int8(5.47, 10.8)
    print(f"用精确scale={ts2:.6f}: q={q2}  反量化={deq2:.6f}")
    print(f"四舍五入 scale 引入的额外误差: {abs(deq-deq2):.6f}")

    # 非对称量化对照（课件第 66 页）
    mx, mn, val = 10.8, -7.59, 5.47
    s_a = (mx - mn)/255
    zp = round(-mn/s_a)
    q_a = round(val/s_a) + zp
    deq_a = (q_a - zp)*s_a
    print(f"非对称: scale={s_a:.6f} zero_point={zp} q={q_a} 反量化={deq_a:.4f}")

实跑输出：

round(5.47/0.085)=64  反量化=5.44  (课件数字)
用精确scale=0.085039: q=64  反量化=5.442520
四舍五入 scale 引入的额外误差: 0.002520
非对称: scale=0.072118 zero_point=105 q=181 反量化=5.4809

读数：课件数字复现无误。量化本身引入 5.47 → 5.4425 的误差（0.5%），而课件用的四舍五入 scale 又叠加了 0.0025 的额外误差——手算示例里的误差有两层来源：量化损失 + scale 记录精度。生产上 scale 要以足够精度存进模型文件（GGUF/AWQ 的 block 元数据就是干这个的），别用打印出来的短位数。非对称量化（min=-7.59, max=10.8 分布不对称时）用 zero_point 平移，scale 变小（0.072 vs 0.085），同样 5.47 的反量化误差更小（5.4809 vs 5.4425）——分布偏斜时非对称量化更准。

BF16 只有 8 位尾数（FP32 是 23 位），却几乎不掉点——因为大模型权重的动态范围比尾数精度重要：

def f32_to_bf16_round(x):
    import numpy as np
    b = np.frombuffer(np.float32(x).tobytes(), dtype=np.uint32)[0]
    rounding_bias = (b >> 16) & 1
    b16 = (b + 0x7FFF + rounding_bias) >> 16
    return np.frombuffer(np.uint32(b16 << 16).tobytes(), dtype=np.float32)[0]

if __name__ == "__main__":
    vals = [0.1, 0.3333333333, 5.47, 123.456, 1e-3, -7.59, 10.8, 0.085]
    errs = []
    for v in vals:
        r = f32_to_bf16_round(v)
        e = abs(v - r)/abs(v)
        errs.append(e)
        print(f"FP32 {v} -> BF16 {r}  相对误差 {e:.2e}")
    print("平均相对误差:", sum(errs)/len(errs))

2.3 权重分布与 scale 粒度：AWQ/GPTQ 的共同直觉（实跑）

3

量化误差不是均匀分布的——一个离群权重撑大全局 scale，让所有普通权重的量化变粗：

import numpy as np

def quant_rmse(W, mode, group=128):
    if mode == "per_tensor":
        s = np.abs(W).max()/127
    elif mode == "per_channel":
        s = np.abs(W).max(axis=1, keepdims=True)/127
    elif mode == "per_group":
        g = W.reshape(W.shape[0], W.shape[1]//group, group)
        s = np.abs(g).max(axis=2, keepdims=True)/127
        q = np.clip(np.round(g/s), -127, 127)
        err = g - q*s
        return float(np.sqrt((err**2).mean()))
    q = np.clip(np.round(W/s), -127, 127)
    err = W - q*s
    return float(np.sqrt((err**2).mean()))

if __name__ == "__main__":
    rng = np.random.default_rng(11)
    W = rng.normal(0, 0.02, size=(256, 512)).astype(np.float32)
    W[:, 0] = 0.3  # 植入激活离群列
    for m in ["per_tensor", "per_channel", "per_group"]:
        print(m, "RMSE:", round(quant_rmse(W, m), 6))

实跑输出：

per_tensor RMSE: 0.000681
per_channel RMSE: 0.000681
per_group RMSE: 0.000357

读数：把 scale 的粒度从"整个张量"细化到"每 128 个权重一组"，RMSE 从 0.000681 降到 0.000357（约 1.9 倍）——这就是 GGUF 的 K-quant（每块 16 权重共享 scale）、GPTQ 的分组、AWQ 的激活感知共同的数学动机：scale 粒度越细，离群值的破坏半径越小。per_channel 在这个构造里没帮助，因为离群是"某一列所有行都大"（列向），per_channel 是按行分组——scale 粒度要和离群结构对齐，这也是 AWQ 用激活统计来找"哪些权重重要"的原因。

3.3 AWQ：激活感知保护关键权重

3

AWQ（Activation-aware Weight Quantization）不看权重本身的大小，而看激活值的分布：少数权重通道对输出影响极大（激活离群），量化时给这些通道更高精度/更细 scale，其余照常 4bit。课件与素材的口碑（模型部署调优实操-2026.md §3.1，二手）：同 INT4 下 AWQ 在 MMLU/HumanEval 上比 GPTQ 高 1–3%，且 vLLM/SGLang 都内置 AWQ 优化 kernel，吞吐更优。

import numpy as np

def quant_err(bits, seed=2026, n=4096):
    rng = np.random.default_rng(seed)
    w = rng.normal(0, 0.02, size=n).astype(np.float32)
    qmax = 2**(bits-1) - 1
    s = np.abs(w).max()/qmax
    q = np.clip(np.round(w/s), -qmax, qmax)
    err = np.abs(w - q*s)
    return float(err.max()), float(err.mean())

if __name__ == "__main__":
    for b in [16, 8, 4, 3, 2]:
        if b >= 16:
            print(f"{b}bit: 近似无损(FP16/BF16 原生存储)")
            continue
        mx, mn = quant_err(b)
        print(f"{b}bit: max_err={mx:.6f} mean_err={mn:.6f}")

4.2 输出层误差：量化掉点的直接证据（实跑）

3

权重误差不等于输出误差——矩阵乘法会累积误差。直接测一次 W @ x 的输出偏差：

import numpy as np

rng = np.random.default_rng(2026)
W = rng.normal(0, 0.02, size=(256, 512)).astype(np.float32)
x = rng.normal(0, 1.0, size=512).astype(np.float32)
ref = W @ x

def quant_matrix(W, qmax):
    s = np.abs(W).max()/qmax
    q = np.clip(np.round(W/s), -qmax, qmax)
    return q*s

for bits, qmax in [(8,127),(4,7),(2,1)]:
    y = quant_matrix(W, qmax) @ x
    rel = np.linalg.norm(y-ref)/np.linalg.norm(ref)
    cos = float(y@ref/(np.linalg.norm(y)*np.linalg.norm(ref)))
    print(f"{bits}bit  输出相对误差={rel:.4f}  余弦相似度={cos:.6f}")

实跑输出：

8bit  输出相对误差=0.0087  余弦相似度=0.999963
4bit  输出相对误差=0.1560  余弦相似度=0.988185
2bit  输出相对误差=0.9203  余弦相似度=0.462643

读数：4bit 权重重构误差 0.5%（§4.1），但输出相对误差 15.6%——矩阵乘把权重误差放大了约 30 倍；2bit 时余弦相似度塌到 0.46，输出方向已经不对。这解释了为什么"权重看起来没掉多少点，任务却崩了"：评测必须在输出/任务层做，不能只看权重重构误差。8bit 输出余弦 0.99996，质量几乎无损——INT8 是"安全默认"。

现象：量化后测 perplexity 6.56 → 6.84（几乎没变），但业务任务 pass@1 从 62% 掉到 48%。

根因：perplexity 是平均意义的下一段 token 概率，对个别推理链的错误不敏感；任务指标（代码能不能跑、推理链对不对）对单点错误敏感。§4.2 的输出误差实测（4bit 输出余弦 0.988）说明：输出"平均方向对"不代表"关键推理步对"。

改法：质量回归必须双指标——perplexity 看整体，任务级 pass@1 看关键路径；掉点先看是不是集中在某一类任务（数学/代码最敏感，闲聊最不敏感）；敏感任务升一档量化（Q4→Q5/Q6，AWQ→FP8）。

质量回归对比器（实跑）

把上面的排查做成脚本，量化前后各跑一遍指标，自动出掉点判断：

"""量化前后质量回归的对比报告器：输入两份指标，输出掉点判断。"""
def compare(base, quant):
    """base/quant: {metric_name: value}。higher_better 集合之外视为越低越好。"""
    higher_better = {"pass@1", "accuracy", "f1", "rouge", "mmlu"}
    report = []
    for k in base:
        if k not in quant:
            continue
        b, q = base[k], quant[k]
        delta = q - b
        pct = (q - b)/abs(b) * 100 if b else 0
        if k in higher_better:
            verdict = "掉点" if delta < -1.0 else ("提升" if delta > 1.0 else "持平")
        else:
            verdict = "变差" if delta > 0.5 else ("变好" if delta < -0.5 else "持平")
        report.append(f"{k}: {b} -> {q} ({pct:+.1f}%) {verdict}")
    return report

if __name__ == "__main__":
    base = {"ppl": 6.56, "pass@1": 62.0, "mmlu": 65.1}
    quant = {"ppl": 6.84, "pass@1": 48.0, "mmlu": 63.8}
    for line in compare(base, quant):
        print(line)

pass@1: 62.0 -> 48.0 (-22.6%) 掉点
mmlu: 65.1 -> 63.8 (-2.0%) 掉点

读数：这正是 §5.1 描述的病灶——perplexity 判"持平"（+4.3% 在阈值内），但 pass@1 掉 22.6%。单一指标会骗你：阈值 1.0/0.5 是示例口径，换成你的业务容忍线（通常 pass@1 容忍 1–2%，ppl 容忍 5%）。注意 mmlu -2.0% 被判"掉点"而 ppl 变化被忽略，方向判定（higher_better 集合）要按指标语义配好，别搞反。

5.2 翻车二：校准数据不对，量化质量系统性偏差

3

现象：AWQ/GPTQ 量化后，模型在你的业务域表现差，但通用 benchmark 正常。

根因：PTQ 的 scale/zero_point 由校准数据集的激活分布算出（§3.1 三步）。校准用通用语料、生产跑专业领域（法律/医疗/代码），激活分布不匹配，离群通道识别错，关键权重没被保护。

改法：校准数据用业务代表性样本（几百到几千条真实输入分布）；量化后先在业务回归集上测，别信通用 benchmark；有条件对比两套校准数据的量化结果。

5.4 翻车四：以为量化能救显存，KV cache 没算

3

现象：权重从 16GB 降到 4GB，以为能开 32 并发，结果 KV cache OOM。

根因：量化砍的是权重显存；KV cache 占用不变（见《L12-vLLM推理加速》§3.2：8K×32 并发 KV = 32GB）。INT4 权重省下的 12GB 被 KV 吃掉，若 max_model_len × 并发 没减，照样 OOM。

改法：量化收益要按"权重省下的显存 → 一部分还给 KV cache 换并发，一部分留 buffer"分配；INT8 KV cache（OLLAMA_KV_CACHE_TYPE=q8_0 / vLLM 的 kv_cache_dtype）是 KV 侧的独立杠杆；两个杠杆可以叠加。

显存收益核算器（实跑）

"""量化显存收益计算器：给定参数量与量化档，输出权重显存、KV 预算变化。"""
def vram_tradeoff(params_b, qtype, kv_gb_needed, gpu_gb):
    bytes_per = {"F16":2.0,"BF16":2.0,"FP8":1.0,"INT8":1.0,"INT4":0.5,
                 "Q4_K_M":0.55,"Q5_K_M":0.65,"Q6_K":0.75,"Q8_0":1.0}
    w = params_b * bytes_per[qtype]
    overhead = 2.0
    kv_budget = gpu_gb - w - overhead
    fit = kv_budget >= kv_gb_needed
    return {
        "weights_gb": round(w,1),
        "kv_budget_gb": round(kv_budget,1),
        "kv_needed_gb": kv_gb_needed,
        "fit": fit,
        "verdict": "能装下" if fit else f"KV 缺 {round(kv_gb_needed-kv_budget,1)}GB",
    }

if __name__ == "__main__":
    for q in ["F16","INT4","Q4_K_M","Q8_0"]:
        r = vram_tradeoff(8, q, 16, 24)
        print(f"{q}: 权重{r['weights_gb']}GB, KV预算{r['kv_budget_gb']}GB, 需{r['kv_needed_gb']}GB -> {r['verdict']}")

实跑输出（8B 模型、24GB 卡、需要 16GB KV 即 8K×16 并发）：

F16: 权重16.0GB, KV预算6.0GB, 需16.0GB -> KV 缺 10.0GB
INT4: 权重4.0GB, KV预算18.0GB, 需16.0GB -> 能装下
Q4_K_M: 权重4.4GB, KV预算17.6GB, 需16.0GB -> 能装下
Q8_0: 权重8.0GB, KV预算14.0GB, 需16.0GB -> KV 缺 2.0GB

读数：同一张 24GB 卡，FP16 权重下 KV 预算只剩 6GB（放不下 16GB 需求），INT4 直接放得下——量化收益必须从"KV 预算"角度验算，不是看权重从 16GB 降到 4GB 就宣布成功。Q8_0（8bit 权重）差 2GB，再叠加 INT8 KV cache 或压 max_model_len/并发才够——这正是"两个杠杆叠加"的具体算法。bytes_per 是经验值（K-quant 含块元数据），精确值以转换工具输出为准。

"""量化收益成本建模：显存/吞吐/质量三维权衡的量化收益表。"""
def quant_roi(params_b, qtype, gpu_cost_per_gb_month=30,
              throughput_gain=1.0, quality_loss_pct=0.0):
    """输出: 每月省的显存成本 vs 质量损失百分比。"""
    bytes_per = {"F16":2.0,"INT8":1.0,"INT4":0.5}
    base_gb = params_b*2.0
    new_gb = params_b*bytes_per[qtype]
    saved_gb = base_gb - new_gb
    saved_cost = saved_gb * gpu_cost_per_gb_month
    return {
        "显存节省GB": round(saved_gb,1),
        "月成本节省": round(saved_cost,0),
        "吞吐倍数": throughput_gain,
        "质量损失%": quality_loss_pct,
        "建议": "值得" if saved_cost > 100 and quality_loss_pct < 3 else "需权衡",
    }

if __name__ == "__main__":
    for q, tg, ql in [("INT4", 1.5, 1.2), ("INT8", 1.15, 0.3), ("F16", 1.0, 0.0)]:
        r = quant_roi(70, q, throughput_gain=tg, quality_loss_pct=ql)
        print(q, r)

读数：70B 模型 INT4 量化每月省 $3150（105GB 显存），质量损失 1.2%（示例值，必须自己测）——经济账通常支持量化。但"建议: 值得"的阈值（saved_cost > 100 且 quality_loss_pct < 3）是业务口径：质量容忍度因场景而异（客服闲聊 3% 可忍，医疗诊断 0.3% 都嫌多）。gpu_cost_per_gb_month 换成你的云商单价；throughput_gain 用压测实测（§4.2 的输出吞吐对照：AWQ/GPTQ 各家差 4–10 倍，别抄二手）。别把二手 benchmark 的质量损失直接填进来——那只是筛选候选的起点，上线前必须本地回归（§5.1）。
