2.1 两阶段流水线为什么是公认最优

单路 dense 只能抓"意思相近"，抓不住"关键词精确命中"（用户搜 RRF 这种缩写，dense 经常被中文长句带偏）；sparse 路抓词面，抓不住同义改写。两路并行召回再融合，覆盖面才是 1+1>2；融合后名次仍粗糙，所以必须再用 cross-encoder 精排。

2.3 为什么"先调分块和 metadata，最后才换 embedding"

🏢 StackAI 的 fix-order playbook：① 分块 + metadata → ② 混合检索权重/RRF → ③ candidate size → ④ 才换 embedding。理由是检索质量的天花板是你嵌进去的内容本身。本库验证了这个方向：_sweep_boost.py 扫 8 组 wiki boost 网格，全部 ≤ baseline（差距文档 §3.3）——调权重是死路，真正的结构性问题是 raw 层占 89.7%、wiki 只占 10%，候选池被 raw 课件淹没。

2.4 为什么必须有门禁和评测这两层（缺了会怎样）

没有门禁：用户问一个知识库里根本没有的问题（例如"Snowflake Time Travel 能保留多少天"），系统照样从最近邻里挑几段看似相关的文字让大模型编一段答案。本库实测这类域外题的最佳 dense 距离只有 0.43，任何"距离小于 0.60 就算相关"的粗规则都会放行——这正是 2026-10-15 修复的主路径：让 simple_fact 路由也走 rerank，用 0.45 阈值把 0.0021 分的域外结果挡在生成之前。门禁的工程意义是把"我不知道"变成一个可配置、可回归测试的输出，而不是指望生成模型自觉。

没有评测：所有优化都会退化成"感觉变好了"。本库连续踩过三次尺子失真（10-09 目录扁平化 55/76 条标签失效、10-14 合并文档 10 条死标签、域外负样本混进召回分母），每次失真都让 Recall 凭空掉几十个百分点，看上去像检索坏了，实际是尺子烂了。所以差距文档把"修度量"排在执行顺序第 1 位——先让尺子可信，再谈调参。

代价：门禁收紧会误拦边界正样本（阈值挪到 0.34 时安全间隙只有 0.03），端到端评测每轮要跑 31 分钟。这笔成本必须付，因为一次错误上线的代价是用户对整个知识库失去信任，而信任丢掉之后，改对了也没人敢信。

2.5 哪些是标配、哪些是前沿（对标判定，防止过度工程）

据[一手源]：RAG业内最高标准-20261009.md §④：判定法是标配看多家官方 docs 是否列为推荐/默认路径，前沿看论文 + cookbook 存在但未成为默认。
- 标配（本架构五段已覆盖）：混合检索 + RRF、cross-encoder rerank、metadata filter、parent-child 分块、自动评测（含生成层）、Tracing、增量 reindex，以及 Contextual（LLM 前缀）作为成熟标配基线（AWS Bedrock 已产品化）。
- 前沿，不要当硬性要求：GraphRAG（前沿→商业化中，场景限定全局多跳）、HyDE/multi-query/step-back、Self-RAG / CRAG / Adaptive RAG、Agentic RAG、Late Chunking、训练型 contextual embeddings；OTel GenAI semantic conventions 仍是 Development 状态；语义缓存 Qdrant 官方自称"optimization layer, not default"。
- 已过时：单 dense-only、无 rerank 的一阶段、一刀切固定分块。上面 2.1 的 +39% 就是淘汰它们的数字依据。
- Contextual 的成本与官方口径：LLM 前缀一次性约 $1.02/M document tokens；prompt caching 是成本机制（缓存写 1.25×、读 0.1×，cookbook 实测 61.83% 输入 token 命中缓存），不是独立准确率变体；官方否定"通用文档摘要"（very limited gains）。Anthropic 的 35%/49%/67% 是 top-20 检索失败率（基线 5.7%）的相对降幅，不是 Recall 目标。

据[一手源]：RAG业内对标与工程化改造-20261013.md §6：业内双管线的标准画法是离线索引管线（摄入 → 解析清洗/OCR → 分块 → dense+sparse embedding → 向量库 + BM25 索引）与在线查询管线（改写 → 混合检索 → rerank → 上下文组装 + 引用 → 生成）彼此分离，外加一个独立可观测层（RAGAS 评测、Langfuse/LangSmith 追踪、延迟/召回/rerank 分数/token 监控、黄金集离线 A/B）。本文 1.1 的五段管线是这个画法的压缩版，评测侧 + 门禁侧对应独立可观测层；配置化（参数集中到 rag/config.yaml，业内用 YAML + pydantic-settings）是投入最小、收益最大的第一步，本库已做到。

0.4 小白最容易搞错的三件事

  1. "灌进库 = 查得到"是错的。upsert 打印 N chunks 只说明向量写进去了，能不能浮上来是检索层的事——新文档必须跑一次真检索，确认它出现在 top-k，否则"入库完成"是假完成。
  2. "有结果返回 = 检索正常"是错的。单路 dense 甚至纯 sparse 都能返回结果，只有日志里 dense top-N 与 sparse top-M 同时非 0，混合检索才算真的在工作。
  3. "换更强的 embedding 模型就能变好"是错的。本库 8 组权重网格全部打不过 baseline，说明当前瓶颈在语料结构（raw 占 89.7%）和评测可信度，不在模型。换模型是 Fix-Order 的最后一步，前面三步没做完就换，等于把噪声调参固化进索引。

1.1 定义

生产级 RAG 架构 = 一条带指标的五段管线，每段都有出口判据：

索引侧  ingest.py   分块 → contextual 前缀 → bge-m3 dense+sparse → Chroma upsert（registry 增量）
检索侧  query.py    路由 → dense top-1000 ∥ sparse top-100 → RRF(k=60) → 去重/tier 加权
精排侧  rerank      bge-reranker-v2-m3 给 top-10 打分，阈值 0.45
门禁侧  gate        rerank 分 < 0.45 → 拒答；rerank 不在线 → 退回 dense_threshold 0.50
评测侧  eval/       golden-q 召回率 + RAGAS 四指标 + 端到端保真脚本

五段缺一段就不是生产级：缺评测=不知道有没有变差，缺门禁=域外问题照样编答案，缺去重=同一份课件霸榜 top-k。

# rag/query.py::rrf_fuse —— 两路名次 → 统一分值（真实代码节选）
def rrf_fuse(rank_lists, k=None, weights=None):
    k = k or CONFIG["retrieval"]["rrf_k"]      # 本库 k=60
    scores, sources = {}, {}
    if weights is None:
        weights = [1.0] * len(rank_lists)
    for li, rank_list in enumerate(rank_lists):
        w = weights[li] if li < len(weights) else 1.0
        for rank_idx, h in enumerate(rank_list, start=1):
            hid = h.get("_id") or (h["source"], h["chunk"])
            scores[hid] = scores.get(hid, 0.0) + w / (k + rank_idx)  # 名次越靠前贡献越大
            sources.setdefault(hid, h)
    ranked = sorted(scores.items(), key=lambda x: x[1], reverse=True)
    merged = []
    for hid, sc in ranked:
        h = dict(sources[hid]); h["rrf_score"] = sc; merged.append(h)
    return merged
  • 参数解释：k=60 时第 1 名贡献 1/61≈0.0164、第 100 名 1/160≈0.00625，名次差距被压平，所以两路都进 top 才稳；weights 可给两路配权，本库等权。
  • 常见错误：单路为空时 retrieve_hybrid 会退化成"按顺序伪造 rrf_score"（if not sparse_hits: ... 1.0/(k+i)），日志会显示 sparse top-0——分数看起来正常但混合已失效，别被分数骗了。
