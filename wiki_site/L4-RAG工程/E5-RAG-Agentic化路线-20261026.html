RAGFlow v1.0.0-rc2（2026-10-16）核心变更3 个重点▾ 点开看本节重点

  • 不再用"思考深度"开关控制，改成 agent 化的检索/推理流程
  • 含义：RAG 从"一次检索 + 一次生成"的静态 pipeline，变成 agent 自己决定"要不要再检索 / 要不要换 query / 要不要 rerank"的动态流程

  1. chat 模式弃 Low/High 思考档，改 Agentic mode
    - 不再用"思考深度"开关控制，改成 agent 化的检索/推理流程。
    - 含义：RAG 从"一次检索 + 一次生成"的静态 pipeline，变成 agent 自己决定"要不要再检索 / 要不要换 query / 要不要 rerank"的动态流程。

  2. parser 统一为 Pipeline
    - 多格式解析器（PDF / Word / 图片 OCR / 表格）统一挂到 pipeline 上。
    - 便于多模态接入，与我们已有的 MinerU OCR 路线呼应。

  3. 新增 MinerU 4 解析器
    - 与本项目"图片多模态入库"的 MinerU OCR 路线直接对齐。

启用 Agentic mode 前的四道护栏（一手源融合）1 个重点▾ 点开看本节重点
本节重点
  • RAGFlow 的 Agentic mode 是"路由 + rerank + rewrite 交给 agent"，等于直接跳到第 3–4 步，接入时按这四步对照，别整体切换
3
  • 据[一手源]：Agentic-RAG检索循环-外部调研-20261012（FDE 落地建议）：①别一上来就 agentic——简单 FAQ 用 naive RAG，多跳/跨文档/长文档分析才上 agentic（agentic 分支难题稳定胜出、易题反输）；②预算硬约束：max_iterations ≤ 5，faithfulness judge 必配；③trace 是刚需：任何 agentic RAG 必须接 LangSmith/OpenTelemetry，没有 trace 等于盲开；④渐进迁移：Naive RAG + query 改写 → 加 retriever tool → 加 critique judge → 加 subagent decomposition。RAGFlow 的 Agentic mode 是"路由 + rerank + rewrite 交给 agent"，等于直接跳到第 3–4 步，接入时按这四步对照，别整体切换。
  • 据[一手源]：Agentic-RAG检索循环-外部调研-20261012（最常见失败模式）：没有 critique 步，agent 只是把同一个检索无限循环刷一遍；Reflection 循环是 Retrieve → Read → Critique → Refine → Loop，直到置信度高或步数预算触顶。本库 CRAG 已有 grade + rewrite，缺的是"草稿后的独立 faithfulness judge"（futureagi 事故：法律 QA agent 用了 6/8 个 chunk，凭空捏造第 7 个事实，因没有 span 做 faithfulness 评分）。
  • 据[一手源]：Agentic-RAG-调研-20261012（Anthropic，Building effective agents）：agent 系统一步失败会让执行轨迹完全不同，prototype 到 production 的 gap 比传统软件大，所以 Agentic mode 的 A/B 不能只看最终答案——还要看"该检索时没检索 / 不该检索时检索了"的决策正确性，与上面的 golden-q A/B 铁律叠加使用。

本库真实落地

2

2026-11-04 源码核对：路径全部 os.path.exists 通过，代码块逐字摘自源文件。

  • 本篇说「agent 决定要不要再检索」，本库已经有一份按这个思路写的实现：rag/agentic_query.py（295 行，LangGraph 图），节点序列 decide → retrieve → grade → (rewrite→retrieve 环) → generate / refuse。
  • 「要不要检索」这一步是显式决策节点，不是硬编码（rag/agentic_query.py L96）：
    python def decide_node(state: AgenticState) -> dict: try: out = _parse_json(chat(DECIDE_PROMPT.format(question=state["question"]), DECIDE_SYSTEM, timeout=30)) or {} except Exception as e: _log(f"decide 失败({e}), 默认检索") out = {}
    except 分支的行为是 out = {}，下面按「不命中 respond 即 retrieve」处理——决定失败的默认动作是检索（代码注释：「decide 失败(...), 默认检索」），这与上面的 prompt 取向一致：拿不准就检索。
  • 翻页式多轮检索是它和主链路最大的区别（L109）：
    python def retrieve_round(col, search_query: str, question: str, excluded: set) -> dict: """单轮检索: hybrid(dense+sparse RRF) → 去重 → 排除已判无关 → rerank top-k。"""
    excluded_ids 让第二轮不会再捞到第一轮已经判死的片段，这是 RAGFlow「Agentic mode」里最实际的那条机制。
  • 评分是二元判定且有明确失败语义（L147）："官方二元相关性判定, 批量对 top-k 逐条打分。LLM 两次失败则抛出(不静默放行)。"
  • 预算硬编码：DEFAULT_MAX_REWRITES = 3（L31）。官方 Agentic 路线的风险正是「循环无界」，本库用固定轮数收口，且没有做成配置项——想调只能改代码，这是当前实现的一个粗糙点。
  • 和本库主链路的关系：rag/query.py 的 build_rag_graph() 是生产链路（router→retrieve→grade→rerank→gate→generate），agentic_query.py 是并行的 Agentic 实验链路；两者共用 query.retrieve_hybrid / query.rerank_node，没有各写一套检索。

  • RAGFlow 本身本库没有部署：全仓无 RAGFlow 容器/配置；本篇的 RAGFlow 结论是情报，不是本库运行事实。

  • 本库暂无：agentic 链路没有接进 rag/serve.py 的对外端点，也没有进 golden 回归（56 条基准测的是生产图）；Parser Pipeline 统一化未落地，MinerU OCR 只有批处理脚本 scripts/mineru_ocr_batch.py，未接入 ingest 主流程。
