业务价值、反事实与启用边界

2

本篇解决的业务问题不是“追上三个热点”，而是把三种失败分开：证据需要多轮寻找，用 Agentic；答案藏在表格或版式里，用多模态；已有证据因索引参数进不了候选池，才查向量库。若把三种问题都当成“换更强模型”，会同时增加调用费、部署依赖和排障变量，却仍不知道哪一步修好了问题。

来源：Agentic 调研明确要求从简单方案开始、补文档评价和决策评测；多模态调研把页面图像标注列为前置。因此适用边界是：真实问题需要动态取证或视觉证据，且已有文本基线；纯 Markdown FAQ、单点事实、没有标注与预算的试点不应同时打开所有增强。

上线前先约定质量合同：简单事实不因增强而退化，多跳证据链能回溯来源，视觉答案中的表格数值能对照原页，达到循环预算时停止而不是继续猜。下文旧文的调用次数、GPU 门槛、pgvector 规模与召回比例均保留为原调研观察，不构成所有模型、硬件和数据集的通用保证。

核心论点

2

检索范式的真正分水岭不是"用不用 Agent"，而是把质量决策权交给谁：Agentic RAG 把"要不要检索、够不够好"的判断交回 LLM，靠 grade_documents 评估节点和独立 faithfulness judge 兜底，缺了这两道门禁的循环只是把差检索反复刷。它在难题上稳定胜出、在易题上反输，且每次回答涨到 3–8 次 LLM 调用 + 2–6 次检索，因此边界是按负载切片而非一律 agent 化。多模态方向的核心主张是跳过 OCR——ColPali/VisRAG 直接编码页面图像比"OCR→文本→embedding"更保真，但 ColPali 推理要 A100 级 GPU，这是本地部署的实际门槛。工程侧的默认解已经收敛：pgvector 在 200 万向量内零调优，但默认 ef_search=40 只召回约一半，这类隐形坑比选型争论更值得先修。

  • 动机（WHY）：Agentic RAG、多模态 RAG、向量库调优是 2026 年 RAG 工程的三个热点方向，但每个方向都有"宣传与实测的落差"：Agentic RAG 在难题上胜出但易题反输、成本涨到 3-8 次 LLM 调用；多模态跳 OCR 更保真但要 A100 级 GPU；向量库 pgvector 默认参数只召回一半。不调研直接上，会在成本/硬件/召回上踩隐形坑——调研的动机是先搞清各方向的适用边界与真实代价，再决定上不上、按什么顺序上。

核心结论

2
  1. 检索正从"固定前置步骤"变成"Agent 的工具调用"：传统 RAG 是 query→检索→生成的一步到位管线，而 Agentic RAG 让模型在回答前自主判断要不要检索、检索几次、结果够不够，检索被封装成 tool。这一跃迁的本质是决策权从工程硬编码交回给 LLM，代价是延迟和 token 成本上升。
  2. 真正拉开质量差距的是"评估节点"而非"循环本身"：LangGraph 模板里的 grade_documents（判断检索结果是否相关，不相关则改写 query 重检）才是核心；digitalapplied 明确点出——缺了 critique/self-check 步的 agent 只是把同一次检索反复刷，属于最常见的失败模式。
  3. Agentic RAG 不是万能药，要按工作负载切片：2026 年检索层分裂为两支，agentic 分支在难题上稳定胜出、在易题上反输。落地顺序应是"先判断负载，再决定上不上"，而非一律 agent 化。据[一手源]：Agentic-RAG-调研-20261012：Anthropic 的核心建议是"从最简单的方案开始，只在灵活性收益大于延迟和成本时才增加复杂度"，先用单 agent + tool use，不要一上来 multi-agent；Anthropic 5 种 workflow pattern（prompt chaining / routing / evaluator-optimizer / tool use / orchestrator-workers）里，Agentic RAG 本质是 tool use 的特例。
  4. 多模态 RAG 的核心转变是"跳过 OCR"：ColPali 与 VisRAG 两条 ICLR 2025 路线都证明直接编码页面图像做检索，比"OCR→文本→embedding"管线更保真，尤其对表格、图表、复杂版式文档。
  5. 向量库选型在 2026 已收敛：pgvector 是大多数 RAG 系统的默认最优解，200 万向量以内零特殊调优；但默认 ef_search=40 只召回约一半，是"答案质量受损却无人知晓"的隐形坑。

  • 迭代检索反思 pattern 五步：Retrieve → Read → Critique → Refine → Loop，循环到置信度高或步数预算耗尽。
  • 与 Classic RAG 的量级差：每轮检索次数由 1 次变为 1–6 次动态；延迟由 1 次 LLM+1 次检索，涨到 3–8 次 LLM 调用 + 2–6 次检索。
  • 真实事故：某生产法律 QA agent 检索 8 chunks、草稿直接发货，两天后客户发现其中一条是编造的——trace 显示它用了 6/8，凭空捏造第 7 个事实，全因没有任何 span 做 faithfulness 评分。2026 行业共识：草稿生成后必须由独立 judge 过门禁才允许输出。
  • arXiv 一手：arXiv:2501.09136v4 综述给出四大 pattern（Reflection / Tool Use / Planning / Multi-Agent Collaboration）；企业知识库场景见 arXiv:2605.05538；RL 自适应检索深度见 arXiv:2604.17337（AutoSearch）；arXiv:2505.04588（ZeroSearch，阿里通义，用 LLM 模拟检索、训练成本约降 88%）；arXiv:2511.19399（DR Tulu，Allen AI）；arXiv:2605.10899（RubricEM）。
  • 三种范式：Tool-use RAG（LangGraph，通用）、Multi-agent RAG（Anthropic，主 agent 规划 + 子 agent 并行检索）、Just-in-time retrieval（Anthropic 2025-09 上下文工程，不预建索引、运行时按文件路径/URL 按需加载）。
  • 2026 框架：LangGraph（有状态、可调试、可 instrument）、OpenAI Agents SDK（轻量单厂商）、LlamaIndex AgentWorkflow（retrieval-first）、LangChain Deep Agents（skills-guided retrieval + rubric grading + subagent）。
  • 转折信号：RL 正在替代"手写 agent loop"——OpenAI Deep Research（2025-02-02，端到端 RL，HLE 26.6%）；vLLM 2026-06 起支持 Session-Aware Agentic Routing。
  • FDE 落地：max_iterations ≤ 5、faithfulness judge 必配、必须接 LangSmith/OpenTelemetry（无 trace = 盲开），渐进迁移路径为"Naive RAG + query 改写 → 加 retriever tool → 加 critique judge → 加 subagent decomposition"。
  • 据[一手源]：Agentic-RAG-调研-20261012（现状差距 7 维）：从传统 RAG 升级要补的是——①检索触发（每次都检索 → LLM 自主决定，缺决策节点）②检索质量（直接用 top-k → 要 grade_documents 门控）③Query 处理（原 query 直检 → rewrite 迭代）④数据源（单向量库 → 向量 + Web + SQL 多源 router）⑤执行框架（线性管线 → LangGraph 状态图）⑥可观测性（基础日志 → 每步决策 trace）⑦Eval（端到端质量 → 决策质量 + 答案质量）。
  • 据[一手源]：Agentic-RAG-调研-20261012（Eval 口径）：Agentic RAG 比传统 RAG 多出"决策路径"维度，评测要问"不该检索时检索了吗 / 该检索时没检索吗"，并用 LangSmith/Langfuse 记录每轮 tool call、grade 结果、rewrite 历史；Anthropic 指出 agent 一步失败会让执行轨迹完全不同、错误级联放大，缺 eval suite 就分不清"决策错误"还是"生成错误"。成本是双刃剑：省掉不必要的检索，但增加 LLM 决策调用的 token，所以"简单 query 直接回答"的能力至关重要。
  • 据[一手源]：Agentic-RAG检索循环-外部调研-20261012（来源分层）：该源 12 个 URL 里 tier1 一手 8 个（arXiv 2501.09136v4 / 2605.05538 / 2604.17337 / 2505.04588 / 2511.19399、LangGraph 与 Deep Agents 官方文档、vLLM 官方博客），tier2 二手 4 个（digitalapplied、futureagi、buzzgrewal、rahulkolekar）。上文的"1–6 次检索 / 3–8 次 LLM 调用"对比表、法律 QA 事故案例、RL 转折判断都出自二手博客，引用时标"二手观察"，不能当官方基准数字；Reflection 四大 pattern 的定义才是 arXiv 一手。

m / ef_construction 16 / 64（默认即可） 仅当 ef_search=200 仍召回不足 95% 才重建
halfvec >2000 维必用 vector 类型 3072 维撞 HNSW 2000 维上限
DiskANN(SBQ) pgvectorscale 索引可由 193MB 压到 21MB
  • 分片决策树：<100 万向量什么都不做；100 万–1000 万先调 ef_search + halfvec + DiskANN；>1000 万考虑 Citus 分布式表/PgDog 分片/迁 Qdrant；>5000 万是 pgvector 单节点上限，必须专用库（Qdrant/Milvus）。
  • HNSW 构建时间随 m 线性增长（100 万条 1536 维约 60 分钟），是运维瓶颈信号。
  • 选型结论：pgvector（含 pgvectorscale）是 2026 大多数系统默认最优（跑在 Postgres 内、零额外运维、200 万以内免调优）；Chroma 仅适合原型；Qdrant 在自托管吞吐与量化压缩上更强，适合 500 万以上且需高级过滤。
  • 据[一手源]：RAG优化-外部调研-20260929（方向 3，本地 vs 云端选型）：Chroma 适合本地开发/原型，"几百万向量内 + 简单过滤"都够用，162 chunks 远在舒适区；团队需要"自有基础设施上的过滤 + 持久化"时再升 Qdrant（Rust，p95 < 10ms @ 1000 万向量，过滤模型强，量化成熟）；Milvus/Weaviate 星数高（44k+）但分布式运维复杂，不适合个人/小团队；已有 Postgres 的团队 pgvector 比 Chroma 更优（单 VM 约 $50/月起步）。统一天花板："All of them share one ceiling: the quality of the content you embed"，换库不是当前瓶颈，应把精力放在 chunking + metadata + eval；该源给的迁移触发线是 chunk 数 > 1 万再迁 Qdrant。
