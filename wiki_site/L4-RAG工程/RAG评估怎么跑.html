WHY：把找到、排好、答对拆开验，避免修错层

业务价值与评测合同

2

评测的价值是回答“这次改动修好了谁，又伤害了谁”。不分层就会把错误标注算成召回故障，把生成误用旧值算成 embedding 弱；没有无答案题还会把放宽门禁后的幻觉误记成召回进步。本篇 sources 的10-14 基线中 B010 是标签错、不是分数低，正是先校尺子的具体证据。

适用于能保留问题、源证据和答案参照的离线回归及生产抽样；不把公开榜单替代自己的任务集，不用 5 条样本承诺整个业务可靠，也不因没有人工预算就让同一生成模型自评通过。原文“30 条下限”“不用人工也能跑”是成本启发，不是统计定理：关键事实和引用仍要人工核验，裁判只能辅助扩展覆盖。

质量合同先写有效分母、正负例分开、题型覆盖、版本与阈值依据；同题同配置下比较前后变化。下文 0.787、70%、51/56 题和 RAGAS 历史分数均保留原采样范围，不能混为一组新基线。只看到进程退出 0 也不够，还要检查每题是否真的有结果、是否回退和缺项。

核心论点

2

RAG 评估必须分层拆开：检索质量和生成质量是两个独立变量，混在一起测必然误诊。 7 本书共识是检索层看 Recall@K/MRR/NDCG、生成层看 faithfulness/answer relevance，且"没有评测集就没有优化方向"——本库实测也证明了这一点（检索 Recall@5=100% 时端到端 answer_correctness 只有 0.787，同题差 20 个百分点）。评测集必须来自真实 query、覆盖事实/对比/开放三类、每季度回补 badcase，30 条是能出统计信号的下限；LLM-as-judge 可以替代标注预算，但关键指标（Recall@K）不能让 LLM 评 LLM。

为什么要分层评估（动机与代价）3 个重点▾ 点开看本章重点
本章重点

  • 关键指标（Recall@K）不能让 LLM 评 LLM（judge 偏差），必须人工标注，这是不可省的成本

  • 动机（WHY）：RAG 是"检索 + 生成"两步串联系统，端到端答案差有两种完全不同的病因——检索没召回到正确文档（检索层问题），或召回到了但生成时被旧值/幻觉带偏（生成层问题）。混在一起测必然误诊：本库实测"检索 Recall@5=100% 时端到端 answer_correctness 只有 0.787"，若只看端到端分数会把生成层 bug 算到检索头上，修错方向。分层评估的动机就是把两个独立变量拆开测，定位病因再修。

是什么（定义与边界）

2

定义：RAG 评估 = 用量化指标分层度量"检索质量"（Recall@K / MRR / NDCG / Context Precision，衡量找得全不准、排得好不好）与"生成质量"（faithfulness / answer relevance / answer correctness，衡量答得忠不忠、切不切题）；配套评测集（真实 query + 标注 ground truth chunk/答案）与 LLM-as-judge 自动化跑分。

边界：
- ✅ 管：检索层与生成层的量化质量度量、评测集建设方法、评估时机（上线前/每次改 pipeline/生产监控）。
- ❌ 不管：检索不准时的排查步骤（RAG检索不准怎么排查）、阈值标定（RAG管线现状与阈值标定）、具体指标的深度机制（RAG评测三层方法论）。
- ⚠️ 检索层 Recall@K 必须人工标注 ground truth，LLM-as-judge 只用于生成层——这是"不能让 LLM 评 LLM"的边界所在。

一、评估体系总览

3
层级 指标 衡量什么 怎么算
检索层 Recall@K 正确 chunk 有没有进 top-K 人工标注 ground truth
检索层 MRR (Mean Reciprocal Rank) 正确 chunk 排第几 1 / rank_of_first_correct
检索层 NDCG@K 排序质量（考虑相关度分级） 标准公式
检索层 Context Precision@K 检索到的 chunk 里有多少是真相关 相关 chunk 数 / K
生成层 Faithfulness 答案是不是只基于检索到的内容（不幻觉） LLM-as-judge 或 NLI 模型
生成层 Answer Relevance 答案有没有回答用户的问题 LLM-as-judge
生成层 Answer Correctness 答案和 ground truth 一致度 人工 + LLM 对比
二、怎么建评测集（最关键的一步）3 个重点▾ 点开看本节重点
本节重点
  • 不要用公开 benchmark，要建自己的领域评测集
  • 1. 从真实用户日志里采样 100-300 条 query（不要自己编）
  • 2. 每条 query 人工标注：正确答案 + 哪些 chunk 是相关的
3

不要用公开 benchmark，要建自己的领域评测集。 黄佳《RAG实战课》和李多多《企业级RAG系统》都强调：

  1. 从真实用户日志里采样 100-300 条 query（不要自己编）
  2. 每条 query 人工标注：正确答案 + 哪些 chunk 是相关的
  3. 覆盖三类：事实型（"X 是什么"）、对比型（"A 和 B 区别"）、开放型（"总结一下X"）
  4. 更新频率：每季度补充新 bad case 进评测集

最低成本版本：30 条 query 就能看出问题——够你判断"是不是要加 rerank"。

据[一手源]：raw/rag-arch/RAG业内对标与工程化改造-20261013.md（改造路线 Step 3）：业内工程化改造把评测落地排在 Step 3，ragas 依赖列 P1，先建 50-100 条黄金测试集再接 RAGAS（faithfulness / answer relevance / context precision）。本库对标表里"RAGAS 评测"一栏当时是 ❌ 无，现在已落地（见"怎么用"节）。

据[一手源]：raw/rag-arch/RAG基线评测-20261013.md：黄金集的标注本身会错，建完要先过一遍。10 条 golden 基线里 B010（FastAPI 依赖注入）top1 score 最高（0.7572）却判 miss，因为 golden 指定的术语表根本没有 FastAPI 章节，是标注错误造成的假阴性，应修 golden 而不是改检索。口诀：top1 分数最高却 miss，先怀疑尺子。

三、LLM-as-Judge：不用人工也能跑评估

3

没有标注预算怎么办？用 GPT-4 / Claude 当评判员：

Prompt 模板（faithfulness 评估）：
给定上下文和答案，判断答案中的每个陈述是否能从上下文中推出。
- 能推出：得分 1
- 不能推出：得分 0
输出 JSON: {"faithfulness": 0.8}

注意：
- LLM-as-judge 有偏差，GPT-4 评 GPT-4 会偏高评
- 关键指标（Recall@K）必须人工标注，不能让 LLM 评 LLM
- 用 RAGAS / TruLens / DeepEval 等开源框架可以一键跑这些指标

五、常见误区

3
  1. 只评生成不评检索：答案烂是因为检索烂，不是因为 LLM 烂
  2. 评测集太小（< 30 条）：统计上看不出显著差异
  3. 只看 top-1 准确率：漏掉了"正确答案排第 3"这种可优化的信号
  4. 不记录 bad case：每次优化都从头试，不积累
  5. 不跑回归测试：改了 chunking 提升了法律文档的召回，却降了技术文档的召回——没回归就不知道
  6. 把 Anthropic 官方的 35/49/67% 当 Recall 目标：据[一手源]：raw/rag-arch/RAG标准落位方案-20261009.md（修订1）与 raw/rag-arch/RAG业内最高标准-20261009.md：这组数字是 top-20 检索失败率的相对降幅（基线 5.7% → Contextual Embeddings 3.7% 降 35% → +Hybrid 2.9% 降 49% → +Cohere rerank 1.9% 降 67%），不是 Recall 达标线；验收要写成本库同一 golden set 前后对比。同一方案把"评测补三层"立为标准-0b 硬前置，先有标尺再动库。
  7. 自报通过、只测正例：据[一手源]：raw/rag-arch/反面教材-踩坑Top10-20260928.md（Top3）：Agent 自称"我测过了"没有外部凭据，或只测正例没测负例，都属无效验收；验收三件套是正例 + 负例误报 + 文档与实测一致。本库 golden-q 的 5 条域外负样本（拒答题）就是负例。
  8. CI 回归和线上漂移用同一套工具、没有参照线：据[一手源]：raw/sources/RAG优化-外部调研-20260929.md（方向 4）：DeepEval 在 PR 阶段拦回归，RAGAS 做长期漂移监控（"DeepEval catches regressions at PR time, RAGAS monitors drift over time"），faithfulness < 0.80 触发告警；检索侧 arXiv 2604.01733 实测 hybrid+rerank Recall@5=0.816、dense-only 0.587，可当 Recall 参照线。
