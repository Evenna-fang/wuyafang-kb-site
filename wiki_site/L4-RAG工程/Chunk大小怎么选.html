WHY：分块先保护证据完整性，再谈召回与成本

为什么这不是一个“填 512”的参数题

2

业务需要的是完整证据：一条定义的条件与结论、表格的表头与数据、函数的签名与实现不能被分开后失去关联。块太碎会让答案缺前提，块太大又会把无关主题一起编码。下游换 embedding 或扩 top_k 不能恢复已经切丢的事实，所以不做分块验收的后果是“索引成功、问答却持续漏条件”。

来源：《RAG实战课》第 2/6/9 章提炼把分块、分层索引与评测串成闭环；整本书调研 Q1/Q4提供参数对照。适用于源文已经解析正确、失败可归因到证据边界的场景；扫描件缺字、库里根本无资料、越权访问不属于尺寸调参问题。验收先看结构完整，再看同一题集的召回与生成，不能拿块数更少当质量更好。

核心论点

2

检索质量的天花板由 chunk 边界决定，不由模型决定——分块是 RAG 里"最便宜的高杠杆优化"。 没有普适最优 chunk 大小，只有"分层检索"这一结构性解法：小 chunk（256–384 tok）管召回精度、父 chunk（≤1024 tok）管生成完整性，7 本书里被划线最多的就是这条。默认起点是递归分块 512/overlap 50，特殊载体（合同按条款、代码按函数、表格整张）必须放弃统一切法；所有分块策略的收益都要用同一把评测尺子（Recall@5）验证，否则"今天 256 好、明天 512 好"的摇摆永无止境。

WHYT：结构边界、父子块与尺寸单位如何共同决策

数据契约与尺寸选择依据

2 
原文标题/段落/表格 → child（定位证据）→ dense+sparse 检索
                         │ 命中位置
                         └→ parent_text（恢复条件）→ 生成与引用
source + heading_path + file_hash 将两种粒度关联到同一源版本

原文书籍/调研里的 token 经验值与本库实现必须区分。2026-11-03 核对 rag/ingest.py：RecursiveCharacterTextSplitter 未指定 token 长度函数，384/80 与父块 800/100 按字符计；Markdown legacy 路径先按标题切，再由 _md_fine_splitter 800/100 细切，不能把 RAG_CHUNK_SIZE=512 当成所有 Markdown 块都变成 512 token。下面 10-14“表格未处理”是历史快照；后文 10-26 表格保护是后续状态，不能把两张表当同一时点。

选型按任务对标：固定/递归是低成本基线，结构切分保护文档语义，父子分层分离检索与生成粒度，RAPTOR 更适合长文跨章；语义切分、Late Chunking 要证明边际收益。上游材料的 benchmark 来自不同语料，不推出“父子分块永远最优”。本篇保留所有原始推荐区间，但将其作为候选，不作为生产硬阈值。

这个问题的答案是什么

2

没有一个"正确"的 chunk 大小，只有"场景化的默认值 + 分层检索"。 7 本书交叉对比下来，共识是：

  1. 不要用单一 chunk 大小——小了丢上下文，大了稀释相似度。
  2. 生产环境的最优解是 hierarchical（父子分块）：用小 chunk（256–384 token）做检索找位置，用父 chunk（≤1024 token）喂给 LLM 做生成。这是黄佳《RAG实战课》1460 人划线的最高频观点。
  3. 默认起点：纯文本递归分块 512 token / overlap 50；法律 / 合同用文档逻辑分块（按条款）；Markdown 按标题层级切。

据[一手源]：整本书入库最佳实践-20261014.md —— "最智能"不等于"最准"，2026 年的两份实测都不支持语义分块：Vecta/FloTorch benchmark（50 篇学术论文、90 万 token）里 recursive 512-token 端到端准确率 69% 排第一，semantic chunking 平均只切出 43 token 的碎片，准确率 54%（LLM 拿不到完整上下文）；Vectara NAACL 2025 同行评审（25 种配置 × 48 个模型）里 fixed-size 在三个评估任务上都赢了 semantic chunking。NVIDIA 2024 七策略对比中 page-level 切分以 0.648 的准确率排第一。选型口诀：默认递归 256–512，语义分块要自己的评测集证明更好才换，别因为"贵"就以为"好"。

二、为什么"小 chunk 检索 + 大 chunk 生成"是生产最优3 个重点▾ 点开看本节重点
本节重点
  • 小 chunk（200–300 tok）：dense 向量相似度准（因为语义集中），但 chunk 本身信息不完整，LLM 读了答不出
  • 大 chunk（800–1200 tok）：上下文完整，但一个 chunk 里塞了多个主题，向量被"平均"掉，召回不准
  • small chunk (256 tok) 向量检索 → 找到命中位置
3

矛盾：
- 小 chunk（200–300 tok）：dense 向量相似度准（因为语义集中），但 chunk 本身信息不完整，LLM 读了答不出。
- 大 chunk（800–1200 tok）：上下文完整，但一个 chunk 里塞了多个主题，向量被"平均"掉，召回不准。

解法（small-to-big / hierarchical）：

用户 query
   ↓
small chunk (256 tok) 向量检索 → 找到命中位置
   ↓
回查父 chunk (1024 tok) → 喂给 LLM 生成答案
  • 黄佳 §6.1（1460 人划线）："先使用较小的文本块进行检索（以提高检索精度），然后在生成阶段引用更大、更完整的文本块"。
  • 郑天民 / 凌峰 也在 LlamaIndex 里用 NodeRelationships 实现类似机制。

四、容易踩的坑3 个重点▾ 点开看本节重点
本节重点
  • 1. overlap 设太大（≥200）：chunk 之间高度重叠，向量库膨胀，检索结果冗余
  • 经验值 overlap ≤ chunk 的 15–20%
  • 2. 把 Markdown 表格当纯文本切：表格被切成无意义碎片
3
  1. overlap 设太大（≥200）：chunk 之间高度重叠，向量库膨胀，检索结果冗余。经验值 overlap ≤ chunk 的 15–20%。
  2. 把 Markdown 表格当纯文本切：表格被切成无意义碎片。要么按整表存，要么用 TableSummarizer 生成摘要后入库。
  3. PDF 页眉页脚没去掉：每个 chunk 都带"第 X 页"噪声，稀释 embedding。黄佳 §1.8 专门讲 PDF 版面识别。
  4. chunk 太碎（<128 tok）：单 chunk 语义不足，embedding 质量差；且召回 top-k 时一片碎片，LLM 上下文混乱。
  5. metadata 忘了带 heading_path：chunk 知道自己是哪个章节的，rerank 和过滤才能用。
  6. 把构建产物当知识切（据[一手源]：各类格式进RAG处理方案-20261021.md）：LlamaIndex 的 docstore.json / vector_store.json、rerank_cache/*.json、registry.json 是构建产物不是知识，绝不进库；该源在本库实测 725 个 json 几乎全部不进，14 个 csv 全部不进（机器学习数据集、评测报告、ontology 三元组派生物）。切分之前先判"该不该进"，切得再好也救不了垃圾 chunk 对 faithfulness 的拉低。
  7. 编码没修就切（同源）：实测 requirements.txt 是 UTF-16/GBK 乱码，课程笔记是 UTF-8；混编码文件先用 chardet/ftfy 修好，否则切出的 chunk 全是乱码向量。

五、进阶索引构建（黄佳 §2.6 / §6）

3
  • 滑动窗口（sentence window）：以句子为单位，前后各扩展 N 句作为上下文入库
  • 父子节点（Parent-Child）：small-to-big 的标准实现
  • RAPTOR（Recursive Abstractive Tree）：对 chunks 递归聚类 + LLM 生成摘要，建一棵摘要树——支持从"粗摘要"到"细节"多级检索
  • 前后向扩展（prev/next node）：回答"在某事件之前 / 之后"类问题时，自动把相邻节点也带回来（黄佳 §6.4，1440 人划线）

据[一手源]：整本书入库最佳实践-20261014.md —— 这几项进阶索引的适用边界（RAPTOR、Late Chunking 别盲目上）：

  • Parent-Child：child 128–256 精确检索、命中后返回 512–1024 的 parent，业内实战参数 parent 800–1200 字符 / child 150–250 字符；本库 384/800 在推荐区间内，不是主要矛盾。
  • RAPTOR（Stanford ICLR 2024）：适合"单本长文档的多步推理 QA"（如 QASPER、复杂法律文书）；几百篇横向对比的库不适合，最多给最厚的单本书单独建一棵树。
  • Late Chunking（Jina 2024.08）：要 8K 上下文 embedding 模型先通读再 token 级 pooling；bge-m3 虽支持 8K，但 FlagEmbedding 没暴露 token-level pooling API，要换模型，改造成本高，Contextual Retrieval 和去重做完、baseline 仍不够时再考虑。

与课件教法的差异（实测）

3

统计 raw/courseware/ 全部 md 的方法提及次数：

方法 提及次数
RecursiveCharacterTextSplitter 809
chunk_size 804
chunk_overlap 599
父文档 / ParentDocumentRetriever 253 / 84
CharacterTextSplitter 42
TokenTextSplitter 23
MarkdownHeaderTextSplitter 4（仅提及）

课件主力是按长度递归切（RecursiveCharacterTextSplitter(chunk_size=1000, chunk_overlap=200) 是出现最多的参数组合），本库 .md 主路径却是按标题切。实测同一课件文件：

  • MarkdownHeaderTextSplitter + 800 细切 → 109 块，中位 706 字符，p90 788
  • RecursiveCharacterTextSplitter(384/80) → 234 块，中位约 338 字符

代价：MarkdownHeaderTextSplitter 不识别代码围栏，课件代码块里的 # 注释 会被当成标题切一刀（实测在 # 推荐写法 处产生 chunk 边界），代码密集的课件会切出以代码片段开头的块。

收益：章节标题进 heading_path metadata，chunk 语义边界更贴合文档结构；同等文件 chunk 数约为纯递归切法的 45%，索引更省。

若要完全对齐课件：把 split_file() 的 .md 分支换成 RecursiveCharacterTextSplitter(chunk_size=1000, chunk_overlap=200)，split_parent_chunks() 保持不动即可。
