WHY：把外部标准变成有先后顺序的本地质量合同

为什么要对标，为什么不能照抄排行榜

2

业务需要的是“每次动库知道收益与风险”，不是把外部产品能力全部打勾。没有标准会漏掉生成层、负例和数据新鲜度；照搬标准又可能把小规模单用户库升级成昂贵的多服务平台。价值在于把差距按风险、依赖与可测收益排队，让评测先于重切、模型升级与图谱扩张。

依据是本篇 sources 的标准落位方案：先修尺子，再补三层评测；Tracing 对当时单用户库是可选增强，不应抢掉质量主线。适用于制定本地改造顺序和上线合同；不把某一厂商博客当跨行业认证，不把早期盘点当今天的生产状态，也不把医疗、权限等业务风险缩成统一 Recall 阈值。

本次保留所有早期“未达标”与后续“已落地”的记录，并补充阅读顺序：先看日期和测量范围，再看结论。当前只能用源码证明入口存在，用配置证明声明值；要证明有效仍须在相同题集与索引上实测，本文结构升级本身不是能力升级。

核心论点

2

2026 年生产 RAG 的"五件套"（混合检索 dense+sparse+RRF、cross-encoder 精排、结构化分块、metadata filter、自动评测）已是多家向量库官方文档的推荐路径，属于标配而非前沿——本库 4/5 达标，评测层是唯一的系统性缺口。"找到≠答对"不是口号而是实测：检索 Recall=100% 时 answer_correctness 只有 0.787，只拿 Recall 当动库门禁会放走生成层 bug，因此评测必须升为动库任务的硬前置，门禁从"Recall 不降"升级为三层指标联合不降。引用 Anthropic 数字时的边界要守住：35%/49%/67% 是检索失败率的相对降幅而非 Recall 目标值，官方否定启发式摘要，数字只出自 LLM 生成版 Contextual。优先级有定论：先补三层评测（1–2 天/项）再动 metadata 预过滤、Contextual LLM 版（$1.02/M doc tokens）、Tracing，semantic chunking 因需重建索引放最后。

  • 动机（WHY）：RAG 技术栈选项多（检索/分块/评测/观测每层都有多种方案），没有行业标准对照就不知道"自己做到哪了、缺的是不是关键件"。2026 年生产 RAG 的"五件套"（混合检索、cross-encoder 精排、结构化分块、metadata filter、自动评测）已是多家向量库官方文档的推荐路径——对照标准的价值是把"感觉还行"变成"4/5 达标、评测层是唯一系统性缺口"这种可执行的差距清单，避免在不重要的方向投入（如 semantic chunking 因要重建索引应放最后）。

数据、检索、生成的度量不能互相替代。Contextual 的官方 35/49/67% 是 top-20 失败率相对下降；本库的 Recall@5、生成 faithfulness、答案 correctness 是另一套指标，不能做直接百分比比较。标题/路径规则前缀不等于 LLM 逐 chunk 生成上下文；BGE-M3 sparse 也不应被改叫独立第三路 BM25。

选型依据按依赖链理解：字段和标注先于切分实验，候选覆盖先于换 embedding，稳定的检索/生成基线先于 GraphRAG/Agentic。来源中“标配/前沿/维护期”沿用 2026-10 调研语境，不新增未经核验的当日行业判断。原表 RAGAS、元数据过滤与 Tracing 的叉号是特定时点缺口，不能仅凭本文保留旧表就宣称当前仍完全没有。

质量合同至少记录题库版本、索引版本、配置、模型实际路由、有效样本数、分层分数与失败题。rag/eval/_e2e_eval.py 的当前调用只到 retrieve→rerank，虽名为 e2e，仍不包含完整生成/答案正确性；“跑了 e2e”不能自动打勾生成层。

  • 本库只落地了检索层 Recall 一项，且是关键词判定版，等于"三层缺两层、检索层还缺一半"

2
  1. 2026 生产 RAG 的"五件套"是标配而非可选：混合检索 dense+sparse+RRF、cross-encoder 二阶段精排、结构化分块、metadata filter、自动评测——在 Elastic/Weaviate/Qdrant/Milvus/LangChain/LlamaIndex 官方文档中均被列为推荐路径。本库 4/5 已达标（metadata filter 半达标），评测层是唯一的系统性缺口。
  2. "三层评测"不是二创，而是 RAGAS 论文 Table 1（arXiv:2309.15217）的表格组织方式：检索层（Context Recall/Precision/Relevance）+ 生成层（Faithfulness/Answer Relevancy）+ 端到端（Answer Correctness/Similarity）。本库只落地了检索层 Recall 一项，且是关键词判定版，等于"三层缺两层、检索层还缺一半"。
  3. "找到≠答对"有实测证据：本库 Recall@5 基线 87.5%（56 条 golden-q），但 5 条样本试跑中检索 Recall=100% 时 answer_correctness 仅 0.787——只拿 Recall 当动库门禁，会放走生成层 bug。
  4. 因此 评测必须升为动库任务的硬前置（标准-0b，排在"全库 Contextual"等改库动作之前），门禁从"Recall 不降"升级为"三层指标不降"。
  5. 本库知识库分层严重倒挂：raw 占 93.8%、wiki 5.0%、ontology 1.2%，且 raw 内逾七成是过程性文档——补 wiki 层正是纠偏方向。

2

定义：本文回答"2026 年生产 RAG 的标配是什么、本库差在哪"——含 RAGAS 三层评测的官方口径、五件套达标打勾表、未达标项的改动量与优先级、引用红线。核心结论：标配看"多家官方 docs 是否列为推荐路径"，前沿看"论文/cookbook 存在但未成为默认"。

边界：
- ✅ 管：行业标准盘点、本库现状对照、缺口优先级排序、引用口径红线。
- ❌ 不管：具体每项缺口怎么补（各专项文档：RAG评估怎么跑、Contextual-Retrieval官方方法）、图谱选型（RAG知识图谱标准与验证）、阈值标定（RAG管线现状与阈值标定）。

RAGAS 三层评测：官方依据 + 本库状态

3
层 官方指标（论文 Table 1） 判定机制 本库
检索层 Context Recall 参考答案拆句，判每句有无检索上下文支持 🟡 有 Recall@k，但用关键词而非 LLM 逐句判定
检索层 Context Precision 相关 chunk 的加权 precision@k，测排序质量 🔴 无
检索层 Context Relevance LLM 直判 chunk 与 query 相关性（免标注） 🔴 无
生成层 Faithfulness answer 拆 claims → 逐条判 context 是否支持 🔴 无
生成层 Answer Relevancy 由答案反推问题 → 与原问 embedding 余弦相似度 🔴 无
端到端 Answer Correctness / Similarity 与 ground truth 对比 🔴 无

几乎全部指标为 LLM-as-judge（内置 NLI 式 prompt），embedding 相似度仅用于 answer_relevancy 的最终匹配。最小充分指标集 = 6 个（检索层 3 + 生成层 2 + 端到端 1）；若系统只检索不生成，检索层 3 个即可。

据[一手源]：RAG业内最高标准-20261009.md §①，表里没展开的官方机制与口径：
- 算法一句话：Faithfulness = 被 context 支持的 claims / 总 claims（两阶段：先拆 claims，再逐条判支持）；Context Recall = 被检索上下文覆盖的参考句数 / 参考句总数；Context Precision 需 ground truth，按 Σ(precision@k × relevance_flag) / 相关 chunk 总数算，测的是排序质量而非召回；Answer Relevancy 是反转式生成（从答案反推 N 个问题，算与原问的 embedding 余弦均值）。
- 论文 Table 1 里还有三个本库没列的指标：Noise Sensitivity（打乱/删除 chunk 后重新生成，看正确性掉多少）、Topic Adherence（答案是否留在预设主题内）、Hallucination（无 ground truth 版忠实度，= 1 − 不受支持 claims / 总 claims）。它们不在 6 指标最小集里，属进阶项。
- 版本口径：现行 docs.ragas.io 已改按 metricset 分组、不再分三层，"三层"以论文 Table 1 为准，引用时要写明出处；context_entities_precision 在 v0.2 移除，被 LLM 版 context_precision/recall 取代。
- 官方流程：已有 golden set 直接 evaluate()；没有就先用 TestsetGenerator 从文档合成带 reference 的测试集再评，合成样本要人工抽检滤幻觉（估 2–3 天）。

3
  • 检索层补 Context Precision + Context Relevance：复用 56 条 golden-q，1–2 天（小）。
  • 生成层补 Faithfulness + Answer Relevancy：golden-q 加 reference_answer 字段，2–3 天（小-中）。

  • Contextual 规则版升级 LLM 版：按官方 prompt，一次性成本 $1.02/M doc tokens，先小批 A/B 再全量，3–5 天。
  • Tracing（Langfuse/LangSmith）：2–3 天；semantic chunking 需重建索引：3–5 天。
  • 优先级：先补三层评测（#1–#3）→ metadata 预过滤 → Contextual LLM 版（先 A/B）→ Tracing → 测试集合成 → semantic chunking。

据[一手源]：RAG业内最高标准-20261009.md §②，Contextual 两变体与缓存口径：
- 变体一是 contextual embeddings + contextual BM25，入库时给每个 chunk 加 LLM 生成前缀后分别建索引。变体二"with prompt caching"把整篇文档写一次缓存（写 1.25× 输入费率），后续每个 chunk 读缓存前缀（0.1×，即 90% 折扣）。变体二是成本机制，不是独立的准确率变体，别当成第二档准确率数字引用。
- 官方 cookbook 实测 61.83% 输入 token 命中缓存；$1.02/M 的假设前提是 800-token chunk、8k-token 文档、50-token 指令、每 chunk 约 100 token 前缀。
- 官方否定两条替代路径："generic document summaries... very limited gains"，"summary-based indexing... low performance"。后继方法可对照：Late Chunking（arXiv:2409.04701，与 contextual 直接竞品，2504.19754 做了头对头独立评测）、训练型 contextual embeddings（2505.24782）。两者均属前沿，非默认。

RAG进阶调研 从半年前"133 chunk / bge-m3 dense 单模式 / 阈值 0.465"的基线出发，给出按投入产出排序的三条路径，现多已落地为本库现行管线：

业内对标：Agentic / GraphRAG / Ontology / 工程化（10-13 对标源）

3

据[一手源]：RAG业内对标与工程化改造-20261013.md。该文对标的"我们现状"（纯 dense、无 rerank 之外的一切、raw 9311 / wiki 329 / ontology 0）是 10-13 时点的旧判断，本库此后已上线 dense+sparse+RRF 混检，数字以上文"本库现状底账"的实测为准（真值层级：实测命令输出 > 官方一手文档 > 二手总结）。下面只取对标源里仍成立的机制与选型口诀。
- Agentic RAG 六模式：Router Agent（数据源干净分区时用）、Agent-as-retriever（复杂查询分解）、CRAG（检索质量不稳时用，grader 判不相关就重写查询，相关文档 <2 篇触发重写，最多 2 次）、Self-RAG（精细控制）、Adaptive RAG（查询异质性高时按复杂度选策略）、Agentic GraphRAG（跨文档多跳）。2026 生产实现不再训练 reflection tokens，而是用 LLM grader 的 prompt 实现，三个判断是 ISREL（文档相关？）、ISSUP（答案被上下文支持？）、ISUSE（答案有用？）。框架口诀：状态机 + 分支 + 重试 + 人审选 LangGraph（LangChain 约 125k stars），数据密集的文档/检索选 LlamaIndex Workflows，二者常搭配（LlamaIndex 管检索、LangGraph 管编排），简单线性 handoff 才用 OpenAI Agents SDK。
- 投入产出最高的第一步是 Adaptive 路由层：用便宜模型做路由，简单问题跳过检索（源文预期省约 30%，是预估非实测）。Modular RAG 三层 = 可插拔检索层 → 可插拔生成层 → 稳定 state schema 的编排层，价值是换模型不改图结构、A/B 成本为零。
- GraphRAG 四型选型：Type 1 图增强向量搜索（低成本，第一步）、Type 2 图引导检索（中，中期）、Type 3 图摘要即 MS GraphRAG（$50–200/500 页、约 45 min、约 14k stars，全局查询最佳，暂不需要）、Type 4 时序知识图谱（Graphiti，Agent 记忆用，需 Neo4j，非文档 RAG 不适用）。LightRAG：$0.50/500 页、约 3 min、40.1k stars（EMNLP 2025），质量为 MS 的 70–90%，成本约 1/100，是起点。LightRAG 四种查询模式：naive（纯向量）、local（实体级局部事实）、global（社区级"总结所有 X"）、hybrid（局部 + 全局，质量最佳、成本略高）。对标源估算本库全量实体抽取约 4600 chunk × 1 次 LLM，DeepSeek 价格约 $2–5、30–60 min，仍须过上面的双闸门。
- Ontology 构建四法：纯人工（精度最高、人力极高）；LLM 实体抽取（LightRAG 模式，全自动，$0.5/500 页）；LLM + 规则约束（LangChain LLMGraphTransformer，半自动，精度高）；从关系库反推（结构化领域精度最高）。口诀：先用 entity_types.yaml 定好领域词汇表约束抽取范围，再让 LightRAG 填充，最后人工审核：degree >5 的高频实体优先、同名模糊实体合并、与现有 wiki 条目映射对齐。抽取输出含 entity_name / entity_type / description 与 source / target / relationship_description / relationship_strength（1–10）。
- 工程化双管线：离线索引管线（摄入 → 解析清洗/OCR → 分块 → dense+sparse embedding → 向量库 + BM25 索引）与在线查询管线（查询改写 HyDE → 混合检索 → cross-encoder rerank → 上下文组装 + 引用 → LLM 生成）分离，加一个独立的可观测层（RAGAS 评测、Langfuse/LangSmith 追踪、延迟/召回/rerank 分数/token 用量监控、黄金集离线 A/B）。配置化第一步投入最小收益最大：参数抽到 config/rag.yaml，用 pydantic-settings 做类型安全，再按 ingestion/ retrieval/ generation/ 模块化，组件走可插拔接口。
- 路线图四阶段：Phase 1（第 1–2 周）配置化 + 模块化 + 混合检索 + 50–100 条黄金集，不引入新框架；Phase 2（第 3–4 周）LangGraph 路由 + CRAG 纠错环 + Self-RAG grounding 校验 + Langfuse trace；Phase 3（第 5–6 周）实体类型表 + LightRAG 批量索引（预期 ~500–2000 术语、~1000–5000 条关系）；Phase 4（第 7–8 周）LightRAG local 模式接入在线查询并与向量检索做 RRF，用 RAGAS 对比改造前后。注意它与本文 9 步标准顺序不同：9 步要求先过评测与去重闸门再碰图谱，冲突时以 9 步（含止损线）为准。
