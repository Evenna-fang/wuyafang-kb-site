核心论点

3

RAG 和微调不是竞争关系而是分层关系：RAG 管"知识外置、可随时更新"，微调管"行为/风格/领域术语内化"，两者解决的是不同问题。 7 本书（Denis 第 1 章直接对比）的共识是：知识频繁变动、需要引用溯源、要控制幻觉 → RAG；要改输出格式/语气/领域能力、且知识相对稳定 → 微调；而"RAG + 微调"的组合（先 RAG 补知识、再微调对齐行为）才是生产常见终态。判断顺序永远是"先试 RAG，不够再叠加微调"，因为 RAG 可回退可审计，微调改动不可逆。

  • 判断顺序永远是"先试 RAG（可回退可审计），不够再叠加微调"——因为微调错了没法撤，RAG 错了改文档就行
3
  • 动机（WHY）：LLM 的知识固化在权重里，截止训练日期后的新知识、企业私有文档它天然不知道。解决"模型缺知识"有两条路：把知识外挂成知识库运行时检索（RAG），或把知识训进权重（微调）——两条路的成本结构、更新方式、可审计性完全不同，所以"先做哪个、要不要做另一个"必须先想清，否则会出现"花几天微调了 LLM，其实改两份文档就能解决"的错配。
  • 代价与权衡：RAG 的代价是每次回答多一轮检索延迟 + 需要维护知识库（入库/去重/保鲜），收益是知识分钟级可更新、答案带来源可追溯；微调的代价是训练小时-天级、改动不可逆（回滚=重新训练）、需要 1k-10k 条高质量标注，收益是行为/格式/风格稳定内化、推理无检索延迟。判断顺序永远是"先试 RAG（可回退可审计），不够再叠加微调"——因为微调错了没法撤，RAG 错了改文档就行。

不是二选一，而是分层用。 7 本书（尤其 Denis Rothman 第 1 章直接对比 RAG vs fine-tuning）的共识是：

需求 选 RAG 选微调
知识频繁更新（新闻、政策、产品文档） ✅ 改文档即可 ❌ 每次更新都要重训
需要引用来源、可追溯 ✅ 天然带来源 ❌ 模型不知道从哪来
领域术语密集、语义理解差 ❌ 通用 embedding 召回差 ✅ 微调 embedding 或 LLM
固定输出格式 / 风格（如 JSON、法律文书腔） ❌ prompt 难以稳定控制 ✅ 微调后格式稳定
数据量 < 1000 条 ❌ 微调数据不够 ✅ few-shot 微调有效
需要降低推理成本（小模型跑大活） ❌ 检索延迟高 ✅ 微调小模型替代大模型
幻觉问题严重 ✅ 有 ground truth 约束 ❌ 微调反而加剧幻觉

一句话版本：知识用 RAG，风格用微调，语义用微调 embedding。生产环境 80% 场景应该是 RAG 为主 + 微调为辅（微调 embedding 而非 LLM）。

是什么（定义与边界）

3

定义：RAG = 运行时从外部知识库检索相关片段拼进 prompt 再生成（知识外置）；微调（Fine-tuning）= 用标注数据继续训练模型权重，把知识/行为固化进参数（知识内化）。两者不是同一层的替代品：RAG 管"知识从哪来"，微调管"行为/风格/格式长什么样"。

边界：
- ✅ RAG 管：知识时效性（新闻/政策/产品文档）、引用溯源、幻觉约束（有 ground truth）。
- ✅ 微调管：输出格式稳定（JSON/法律文书腔）、领域对话风格、小模型替代大模型降本。
- ⚠️ "微调 embedding"是第三条路（只调编码器提升召回，不动生成模型），归在 Embedding模型选型对比，不算"微调 LLM"。
- ⚠️ 两者可组合（"黄金组合"= RAG 补知识 + 微调对齐行为），不是二选一的终局。

一、本质区别

维度 RAG 微调（Fine-tuning）
知识来源 外部知识库，运行时检索 权重中，训练时固化
更新成本 改文档/重建索引（分钟级） 重新训练（小时-天级）
可解释性 天然带来源引用 黑盒
数据需求 文档量越大越好 高质量标注数据（1k-10k 条）
推理成本 检索 + 长上下文 LLM，延迟高 一次推理，无检索延迟
擅长 "什么是X"（事实型） "像X一样说话"（风格型）
幻觉 低（有 ground truth） 高（模型可能"编造"）

二、什么时候必须微调 LLM（不是微调 embedding）

只有以下 3 种场景值得直接微调 LLM：
1. 输出格式高度稳定：如医疗报告、法律判决书格式，prompt 怎么调都不稳定
2. 领域对话风格：如客服需要像真人一样寒暄、委婉拒绝，prompt 控制不了语气
3. 小模型替代大模型降本：用 7B 微调后达到 GPT-4 80% 的效果，API 成本降 10 倍

其他所有场景，先优化 RAG（chunking、embedding、rerank、prompt），不够再微调 embedding 模型。

优化顺序口诀（前移微调之前的每一步都有一手数据）：
- 据[一手源]：RAG优化-外部调研-20260929（StackAI fix-order playbook）：召回差先调 chunking + metadata → 再 hybrid → 再 candidate size → 最后才换 embedding 模型；换 embedding（含微调）排在最末，说明前几步没做满就微调是错配。同源 arXiv 2604.01733 实测 hybrid+rerank Recall@5 = 0.816，比 dense-only（0.587）高 39%，这笔收益不需要动任何模型权重。
- 据[一手源]：RAG优化-外部调研-20260929（方向 2，MIT 数据）：95% 的企业 AI pilot 没有可测回报，差异不在模型，在于"工作流逻辑、guardrails、retrieval architecture、monitoring & audit layer"有没有固化进系统——"训模型"通常不是瓶颈。
- 据[一手源]：RAG进阶调研-6方向-Top3落地方案-20260928：连换 embedding 都建议"先用自建 query eval set 对比，不急着换"（Qwen3-Embedding 对 bge-m3）；bge-m3 自带 sparse + ColBERT 能力本库还没吃满，属免费升级空间，先吃满再谈微调。
- 据[一手源]：Agentic-RAG-调研-20261012：需求是"多步推理 + 检索"时，Anthropic 的建议仍是"从最简单的方案开始，只在灵活性收益大于延迟和成本时才增加复杂度"，先单 agent + tool use，不是靠训练解决。

三、黄金组合：RAG + 微调 embedding

这是 7 本书的最强共识——黄佳《RAG实战课》§3.7、Denis《RAG-Driven AI》第 9 章、宁星星《RAG权威指南》第 3 章都提到：

做法：拿 RAG 系统在生产中遇到的 bad case（query → 正确文档对），用 contrastive learning 微调 bge-base 模型。效果：
- 不需要动 LLM
- 只需要 1000-5000 条标注对
- 召回率提升 10-20%
- 推理时还是原来的 bge-m3，成本不变

四、什么时候选 Agentic RAG 而不是微调

如果需求是"多步推理 + 检索"（如"比较产品 A 和 B 的价格并做表"），不是微调能解决的，需要 Agentic RAG（郑天民第 7-8 章）——让 LLM 自己决定何时检索、检索几次、如何组合。
