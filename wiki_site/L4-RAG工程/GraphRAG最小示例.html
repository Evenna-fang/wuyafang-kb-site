WHY：用关系与全局题收益抵偿图索引成本

业务目标与退出条件

2

图谱值得投入的业务目标是把“证据散在多处”变成可追溯的关系链，或把“全库共同主题”变成有依据的归纳；不是让单条款查询多绕一层工具。没有这些题型仍建全量图，后果是抽取、消歧、存储与更新开销增加，却没有相应验收收益。

来源：图谱行业调研与知识组织对标 Q1分别说明社区摘要与实体邻域检索。适用于真实多跳/全局题已有 supporting evidence 的试点；不适用于上游解析已缺失证据、单点事实为主或没有费用上限的全库实验。质量合同是多跳/全局有净收益、简单事实不退化、边能回原文、索引与查询费用分别记录，未达到就停。

原文版本、星数、维护状态、单价与“几分钱/1000 倍”等保留为 2026-10-15 核实或估算快照，本次未重新联网或计费验证；不能用它们承诺今天的服务状态，也不能把估算倍率外推到任意数据量。

核心论点

2

GraphRAG 的本质不是"更好的检索"，而是用逐 chunk 的 LLM 实体抽取换多跳与全库归纳能力，这笔账必须先算清：微软官方口径是完整 GraphRAG 索引成本约向量 RAG 的 1000 倍，token 约原文 ×10~15，而 LightRAG 只做抽取（×3~6）就把学习/落地成本压到最低。三条路线的分野在于维护状态而非功能多少——microsoft/graphrag 是方法论标杆但已明示 maintenance mode，nano-graphrag 十个月未更，2026 年要跑起来就选 LightRAG。边界由问题形态决定：多跳关系和全库主题归纳才值得付图索引成本，单点事实查询上 GraphRAG 是负优化（自然语言问题 90% 是单点时尤甚）；语料 <千篇、有领域 schema、要可解释时，零 LLM 抽取的人工审校轻量图谱反而完胜。判断口诀：纯向量 RAG 输在必须跨 chunk 拼答案，GraphRAG 输在一次性索引投入 + 每次查询变贵。

结论先行：三条开源路线里，2026 年的学习/落地首选是 LightRAG（v1.5.7，港大 HKUDS，4 万 star，活跃维护、单次抽取成本最低、pip 一装即用）；microsoft/graphrag 是方法论标杆但官方 README 已明确标注 maintenance mode（仅修 bug 不加新功能）；nano-graphrag 适合"读懂 GraphRAG 源码"但已 10 个月未更新，不建议作为生产依赖。索引成本的大头是逐 chunk 的 LLM 实体抽取，量级约等于"原始文本 token 数 × 3~15 倍"（视框架与模型而定）。如果你只是想回答"多跳关系类问题"，先试 LightRAG 或自建轻量图谱；只有当问题确实是"全库级主题归纳"时，才值得为社区摘要（community reports）付 GraphRAG 的索引成本。

五、何时值得上 GraphRAG，何时是过度设计

2
你的问题长这样 该用什么
"A 公司和 B 公司什么关系？""X 的上游供应商是谁？"（多跳关系，答案分散在多个 chunk，向量检索召不全） 值得上：LightRAG 或自建轻量图谱
"这批文档最主要的五个主题是什么？"（全库归纳，没有任何单 chunk 能回答） 值得上：graphrag global / LightRAG mix
"XX 条款写了什么？"（单点事实，答案就在某个 chunk 里） 过度设计。纯向量 RAG + rerank 又快又便宜
FAQ 客服、规章查询、检索准确率问题 过度设计。先排查 chunk 切分和 embedding（见 RAG检索不准怎么排查）
文档每天大量更新 GraphRAG 重索引成本不可接受；考虑 LazyGraphRAG 思路或自建轻量方案

判断口诀：纯向量 RAG 输在"必须跨 chunk 拼答案"，GraphRAG 输在"一次性索引投入 + 每次查询变贵"。 拿 20 个真实业务问题问自己：如果 80% 是单点查询，就别上。企业降本增效场景（库主的目标岗位）尤其要警惕：客户看到"每 MB 索引贵 10 倍、每次查询多花 5 倍 token"的账单，而问题 90% 是单点查询时，GraphRAG 就是负优化。

WHYT：图、原文与检索器怎样协同，怎样选路线

本库：ontology 三元组 + wiki 标签/术语 → entities/relations
                                    → 实体命中/沿边展开 → 关联 chunk
外部：原文 → LLM 抽取/实体消歧 → 图 +（可选）社区摘要

组件选择有三个独立轴：抽取是否依赖 LLM、查询要实体邻域还是全局摘要、存储是否需多用户并发。人工审校 JSON 图省抽取费用但受覆盖率约束，LightRAG 的实体/关系双层检索与 Microsoft 的社区报告不是同一机制。文件数更少不等于边更正确，答得更长不等于全局综合更好。

数据契约需有实体唯一标识/别名、边端点/关系、来源定位与关联 chunk；社区摘要是派生证据，应能下钻原文。本库配置 retrieval.graph_slot_mode 的 2026-11-03 值为 after_top1，它是排序策略，不是“已实现完整 GraphRAG”的证明。知识组织对标把 schema 与存储解耦，正是先验证轻量图、再决定外部框架的依据。

是什么（定义与边界）

2

定义：GraphRAG = 用 LLM 从文档抽实体/关系建图（+ 可选社区摘要），查询时沿图做多跳推理或全库归纳的检索增强方法。本篇是其成本核算与选型指南：三条开源路线对比（microsoft/graphrag / LightRAG / nano-graphrag）、最小可运行示例（LightRAG 接 OpenAI 兼容端点）、成本量级推导、何时值得上/何时过度设计、自建轻量图谱对照。

边界：
- ✅ 管：GraphRAG 的成本量级、三路线选型、最小可运行代码、适用边界判断、自建方案对照。
- ❌ 不管：GraphRAG 的行业标准与验证（RAG知识图谱标准与验证）、Agentic RAG 范式（Agentic-RAG与多模态RAG调研）、检索流水线（RRF融合加重排）。
- ⚠️ 成本表是推导估算（标注"估"），不是实际计费实测——用前建议用自己的账单复核一次（见"附：核实记录"）。
- ⚠️ "多跳/全局才值得上、单点事实是过度设计"是本篇的边界核心——先统计真实 query 的多跳占比再决定，别拍脑袋（见"怎么用"节）。

一、先搞清 GraphRAG 到底多花了什么钱2 个重点▾ 点开看本章重点
本章重点
  • 3. 社区摘要（microsoft/graphrag 独有）：对每个社区再调 LLM 写"报告"，供 global 查询做 map-reduce——这是官方版贵 1~2 个数量级的主因
  • 微软研究院官方博客（LazyGraphRAG 一文）给出的量化：完整 GraphRAG 索引成本约为向量 RAG 的 1000 倍（LazyGraphRAG 把索引成本压回 0.1%）
2

纯向量 RAG 的索引 = chunk + embedding，几乎零 LLM 成本。GraphRAG 在此之上追加了一条 LLM 抽取管线：

  1. 实体/关系抽取：每个 chunk 调一次 LLM，输出结构化三元组——这是所有人都要付的固定成本；
  2. 图构建（社区发现/聚簇）：纯算法（Leiden 等），不花钱；
  3. 社区摘要（microsoft/graphrag 独有）：对每个社区再调 LLM 写"报告"，供 global 查询做 map-reduce——这是官方版贵 1~2 个数量级的主因。

微软研究院官方博客（LazyGraphRAG 一文）给出的量化：完整 GraphRAG 索引成本约为向量 RAG 的 1000 倍（LazyGraphRAG 把索引成本压回 0.1%）。这条曲线决定了下面的所有选型。

没有公开的"每 MB 官方报价"，以下按管线推导（可自行代入你的单价复算）：

推导基准：1MB 英文 ≈ 25 万 token；1MB 中文（UTF-8）约 30~40 万 token。按 chunk=1200 token 切约 200~300 个 chunk，每个 chunk 一次抽取调用（输入 = chunk + 提示词 ≈ 2k token，输出 = 结构化三元组 ≈ 1~2k token）。

方案 每 MB 索引总 token（估） GPT-4o 级单价下 国产低价模型（约 ¥1~2/百万token）
纯向量 RAG ≈ 原文 ×1（仅 embedding，可忽略） < ¥0.5 ≈ ¥0.1
LightRAG ≈ 原文 ×3~6（仅实体关系抽取） ≈ $1~4 ≈ ¥2~8
microsoft/graphrag 全量 ≈ 原文 ×10~15（抽取 + 描述摘要 + 社区报告） ≈ $5~15 ≈ ¥10~30

三个可以背下来的锚点：

  1. 微软官方口径：完整 GraphRAG 索引成本 ≈ 向量 RAG 的 1000 倍（LazyGraphRAG 博客）；
  2. 索引是一次性沉没成本，查询才持续发生：graphrag global 查询每次要对几十上百个社区摘要做 map-reduce（单次查询可达几十次 LLM 调用）；LightRAG mix 单次查询仅个位数调用；
  3. 知识库只读、更新频率低 → 索引贵点可摊薄；文档天天变 → GraphRAG 全量重建是灾难（LightRAG 支持增量 insert，官方版重建成本极高）。

用 MiMo/DeepSeek 这类低价端点跑 LightRAG，10KB 示例文档一次索引大约几万 token、几分钱——学习阶段成本可忽略，放心跑。

六、自建轻量图谱方案（build_wiki_graph.py）vs 开源方案

2

库主已有的自建方案：实体 + 共现 + 语义边，人工审校三元组 + tag 共现构图，零 LLM 抽取成本。对照：

维度 自建轻量方案 LightRAG microsoft/graphrag
构图成本 零 LLM 调用，只有人工审校时间 每 chunk 1 次抽取调用 每 chunk 多次调用 + 社区报告
边质量 人工审校，精度高、召回受限（只覆盖你定义的 schema） LLM 自动抽取，召回高但噪声需清洗 同左，且提示词调优门槛高
规模上限 受人工产能约束，适合百~千级文档的领域知识库 百 MB 级 同左但成本更高
多跳查询 共现边能撑 1~2 跳；语义边补长程关联 2~4 跳，图遍历自动 global 模式做全库归纳最强
保鲜/增量 改一篇文档只需重跑该篇，人工审校天然增量 支持 insert 增量 基本要重建
可控性/交付 完全可控，能给客户讲清每条边怎么来的（企业交付加分项） 依赖抽取质量，黑盒程度中等 黑盒程度高

适用边界（建议写进你的方案话术）：

  • 客户语料规模可控（< 千篇）、有明确领域 schema、且要可解释可审计 → 自建轻量方案完胜：零索引 API 成本、增量友好、边可人工背书。这正是"企业 AI 降本增效"叙事里最好卖的部分。
  • 客户语料量大、杂、无人审校、问题以多跳关系为主 → 自建产能不够，上 LightRAG（国产低价模型抽取，成本可控）。
  • 只在"全库主题归纳"是刚需且预算充足时才考虑 graphrag 全家桶；或直接用 LazyGraphRAG 思路（NLP 抽名词短语替代 LLM 抽取，索引成本 ≈ 向量 RAG）把索引成本问题绕过去。

三者不互斥，成熟做法是自建图谱做高置信主干 + LightRAG 做自动补充，Layered 混合检索。

自建图谱的三条加固（据[一手源]：RAG知识组织对标-一手源-20261016 落地建议 1–3、5）：
1. 纵向边用“合法边矩阵”表达：仿 LlamaIndex kg_validation_schema，规定哪类实体可连哪些关系（如 框架:[PART_OF, USES]、API:[IMPLEMENTS, PART_OF]），先补 5–8 条纵向边打样再批量抽；谓词与实体类型一律大写下划线（PART_OF / IMPLEMENTS / USES / DEPENDS_ON / IS_A，TECH_STACK / FRAMEWORK / MODULE / API / IMPLEMENTATION）。
2. 纵向层次双轨：显式谓词 + 二级社区聚类摘要（塔尖 = L1–L9 域摘要，塔基 = wiki 篇）。GraphRAG 的层次主要靠社区而非谓词，所以 53 条三元组硬凑 part-of 边不如建二级社区 + 逐层摘要。
3. 关系边带 strength（0–10 数值），检索时按强度加权，替代平级无权重。
以上 OC 的“对我们的启示”是工程化推断；R@5 能抬多少该源明确标【待验证】，以 baseline_items.json 重测为准。

本库当前谓词状态（据[一手源]：RAG知识组织一手源对标-20261022 §二，2026-11-02 复测）：ontology-triples.csv 谓词仍碎片化（complementary 20 / alternative 15 / orthogonal 5 / PART_OF 5 / part-of 4 / IS_A 4 …），PART_OF 与 part-of 命名分裂未归一；该调研 10-22 记录 graph/ 目录不存在，今日复测 rag/graph/ 已存在（含 entities.json、entity_chunk_links.json、graphml 等），当时缺失的原因未查明，使用前仍应 ls rag/graph 实测。

LightRAG 的 openai_complete_if_cache / openai_embed 都接受 base_url + api_key，所以接 MiMo 这类 OpenAI 兼容端点不需要任何 hack，直接传参即可：

# min_graphrag.py —— LightRAG v1.5.7 最小示例
import os
from functools import partial
from lightrag import LightRAG, QueryParam
from lightrag.llm.openai import openai_complete_if_cache, openai_embed
from lightrag.utils import EmbeddingFunc

WORKING_DIR = "./rag_data"
os.makedirs(WORKING_DIR, exist_ok=True)

# ===== OpenAI 兼容端点（小米 MiMo）=====
# base_url 和模型名以你 MiMo 控制台里给出的为准；密钥别写进代码，走环境变量
LLM_BASE_URL = os.getenv("LLM_BASE_URL", "https://<MiMo接入地址>/v1")
LLM_API_KEY  = os.getenv("LLM_API_KEY")
LLM_MODEL    = os.getenv("LLM_MODEL", "<你的对话模型名>")
EMB_MODEL    = os.getenv("EMB_MODEL", "<你的embedding模型名>")

rag = LightRAG(
    working_dir=WORKING_DIR,
    llm_model_func=partial(
        openai_complete_if_cache,
        model=LLM_MODEL,
        base_url=LLM_BASE_URL,
        api_key=LLM_API_KEY,
    ),
    embedding_func=EmbeddingFunc(
        embedding_dim=1024,   # 关键坑：必须与 embedding 模型真实输出维度一致
        max_token_size=8192,
        func=partial(
            openai_embed,
            model=EMB_MODEL,
            base_url=LLM_BASE_URL,
            api_key=LLM_API_KEY,
        ),
    ),
)

# 1) 索引：insert 内部完成 chunk -> LLM 实体关系抽取 -> 图+向量库落盘
with open("sample.txt", encoding="utf-8") as f:
    rag.insert(f.read())

# 2) 查询：同一个问题，对比 5 种模式
q = "文中提到的实体之间有哪些具体关系？"
for mode in ["naive", "local", "global", "hybrid", "mix"]:
    print(f"\n===== {mode} =====")
    print(rag.query(q, param=QueryParam(mode=mode)))

export LLM_BASE_URL="https://<MiMo接入地址>/v1"

关键坑（README/官方文档核实）

3
  • embedding_dim 不匹配是最常见报错，先单独调一次 embedding 确认维度再填。
  • 抽取阶段用非思考（non-thinking）模型：官方明确建议，思考型模型又慢又贵还容易超时；EXTRACT_LLM_TIMEOUT 的实际超时是配置值的 2 倍。
  • 抽取模型太慢（<50 token/s）会导致大 chunk 超时：调 OPENAI_LLM_MAX_TOKENS 限制输出。
  • 默认存储是内存+本地文件，官方原话"仅适合小规模测试评估，不适合生产"。
  • 官方仅保证 lightrag_openai_demo.py 和 lightrag_openai_compatible_demo.py 两个示例的可用性，本节代码即按后者裁剪。
