WHY：阻止旧事实继续影响回答，同时保留审计和恢复能力

业务价值、边界与不治理的后果

2

业务要避免的是“答案有引用，但引用已经不成立”。相关性分数不会自动判断 API、价格、政策和版本的有效期；不治理时，旧证据越多越容易挤掉新事实。保鲜的价值是把过期检测、确定性过滤与人工复核拆开，让系统既能停止传播失效事实，又不丢历史和追责线索。

本篇 sources 的落地验证明确区分自动到期标记与人工归档，正文的论文攻击数字保留原样本范围，不外推为本库错误率。适用于带版本或时间敏感性的知识；永恒原理不因文件修改时间旧而判无效，历史问题也不应被“只取最新”误删证据。医疗/法律等高风险事实仍需业务审批，TTL 不提供正确性保证。

质量合同是到期能发现、失效不误用、缺字段能暴露、复核后能恢复检索；误报与漏报分开报告。updated 仅表明编辑，不能自动当事实已验证，所以本轮只更新编辑日期，不顺手改 last_verified，也不把三段补齐冒充全文事实复审。

核心论点

2

知识库的退化不是"内容变少"，而是"过期内容还在投票"——保鲜治理的对象是检索权重，不只是文件生命周期。 单条过期文档就能把 83 道医学题里 74 道从对翻成错（arXiv:2609.31342），说明 TTL/复审/降权不是锦上添花而是防"越建越错"的底线机制。判定寿命要看内容性质（版本号/价格/日期 → 快速档，纯原理 → 永久档）而不是一刀切；落地路径是"入库标 TTL → 到期降权不删除 → 人审复核"三步，并用过期投毒率等四个指标量化效果。

本章重点

WHYT：分清文档复审、入库寿命和查询过滤的三种时钟

三种时钟与协同关系

2 
frontmatter ttl_days + last_verified → check_ttl.py → WARN/ERROR/缺字段
frontmatter ttl + captured_at        → ingest metadata → 查询墓碑过滤
source date + config expiry_days     → 查询中的过期提醒
                                      ↓
                        人审确认 → 更新事实/续期 → 授权增量入库

这三条链相关但不等价。rag/check_ttl.py 以 last_verified 计算复审年龄：超过 ttl_days 是 WARN，超过两倍是 ERROR，缺字段或 eternal 跳过。查询 _is_tombstoned() 则读 metadata 的 ttl 与 captured_at；来源日期加 ttl.expiry_days 产生提醒，又是另一口径。只把 Markdown 的 last_verified 改新，不证明旧向量 metadata 的 captured_at 同步刷新。

选型对标按本篇资料：dbt 式双阈值提供可阻断的健康检查，元数据驱动分档优于按目录粗分，自动墓碑过滤优于继续让旧值投票；物理删除不是 TTL 的自动动作。衰减公式、owner 分工和 cron 是治理设计，不等于每个索引都已实现。本库具体能力以当前脚本和实际记录为准，不能因为旧表写“已实现”就宣称生产全覆盖。

数据契约至少要让复审负责人能定位 source、寿命策略、上次事实核验与有效时间。更新 ttl/ttl_days 前先解释两者如何对应；ingest 的已知 ttl 字符串以 parse_ttl 实现为准，不自行猜测 90d 等任意字符串都被支持。文件索引和图派生边还需分别回溯源版本，续期文档不会自动修复过期关系。

硬证据：顶级模型（GPT-5.5 级）无检索时答对率 0.92–1.00，但单条过期文档就能把 83 道医学题里的 74 道从对翻成错（arXiv:2609.31342 实测）。

据[一手源]：RAG保鲜落地验证-20261009.md —— 同一篇论文在开源模型上的翻错率：单条过期文档让 Llama 翻错 30%、Qwen 翻错 37%；提示里带"follow instructions"时翻错率升到 66–75%。结论是"过期文档留在索引里本身就危险"，不是"提醒一下就行"。另据该源：行业数据称 60% 的 RAG PoC 失败原因是无法在规模上维持数据新鲜度，而不是检索质量。

是什么（定义与边界）

2

定义：知识库保鲜 = 让知识库内容"不因过期而误导检索/生成"的治理机制，含 TTL 分档（按内容性质定寿命：快速档 7-30 天 / 中等档 6 个月 / 永久档不碰）、过期检测、复审流程、新内容增量入库。核心原则："过期≠删除，过期只是'该复审了'"。

边界：
- ✅ 管：内容生命周期（TTL 分档）、过期提醒、复审决策流程、新内容自动入库闭环。
- ❌ 不管：检索算法本身（RRF融合加重排）、评估指标（RAG评估怎么跑）、语料组织（整本书与整套课件怎么入库）。
- ⚠️ 自动动作的红线：系统绝不自动物理删除——误删踩坑的教训是"宁可多提醒，不可自动删"；删除/归档/续期永远是人工决策。据[一手源]：RAG保鲜落地验证-20261009.md：到期后的"墓碑标记（status: expired）+ 检索过滤"可以自动做，这与上文"绝不自动降权"的旧表述不同，以本条为准（_is_tombstoned() 已按此实现）。

据[一手源]：RAG保鲜落地验证-20261009.md —— 两条校准：

  1. 按目录自动判 TTL 没有业界先例。Oracle WebCenter 的 retention category 由管理员按元数据建，不看文件路径；ServiceNow（5000 篇、默认 1 年审查期）按篇由 Document Owner 设置；Dynamics 365 的 expiration date 由 content reviewer 设，系统不自动推断；ARMA 说保留期依文档价值赋值。结论：入库时显式写 ttl: eternal|180d|30d|7d，目录路径只能当默认值提示，不能当唯一判据。本库 _DIR_TTL_DEFAULTS 正是"目录默认 + frontmatter 覆盖"的做法，frontmatter 写错（见下文 ttl_days 坑）才会让目录默认静默顶上。
  2. "80% 是永久档"是启发式假设，没有实证。源里没找到任何公开研究统计知识库中永久/临时内容的比例；能引的锚点是 97% 的学术论文 half-life 超过 1 年（按下载量算，不是按 RAG 有用性算）。模型版本、价格类内容的半衰期远短于论文，要单独估算。做法：入库满 3 个月后，统计实际被检索到的文档里永久档与临时档的比例，用真实数据修正。

RAG 专用保鲜（与通用 KM 的差异）

2

业界 RAG 大部分只盯 Recall@k / MRR（检索准不准），不盯 新鲜度（内容新不新）—— 这是行业缺口，也是本库差异化的点：

  1. 检索时加分：新文档加权、过期文档降权或直接过滤
  2. 生成时提醒：引用"到期前 N 天"的文档时，输出里附一句"此信息可能已过期，请核对"
  3. 基准测试：拿 Stale-Document Poisoning benchmark 当回归集定期跑，投毒率升了说明保鲜失效

自动化最佳实践

2
  • 入库时就标 TTL：不让"没标 TTL 的内容"进向量库（铁律候选）
  • 到期自动降级不自动删：先从检索候选移出（降权），进复审队列，人审后决定更新/归档/删除
  • 快照先行：任何批量动库操作前先打快照，出错可回滚
  • 负例入库：已知过期的"反面例子"也要进库，带 [STALE] 标记，防止模型重新踩坑

据[一手源]：RAG保鲜落地验证-20261009.md —— 到期后自动转状态（墓碑/降级）、人审只管续期或归档的业界对照（该源 §② 原标题为"系统绝不自动降权/删除"，验证后判此旧设计"过于保守"，改为自动转状态 + 人审后续；"不物理删除"是本库自己的补充约束，非该源原句）：

来源 做法
