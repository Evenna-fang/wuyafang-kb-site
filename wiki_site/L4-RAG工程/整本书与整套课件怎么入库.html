WHY：把整套材料变成不重复、可追溯的独立证据

为什么“文件都灌进去”不等于知识完整

2

业务目标是既能找准一个段落，又能还原整章语境，并避免同一课多期副本占满 top-k。不治理的后果不只是存储贵：多个近重复旧版本会把新事实淹没，整本超长块会稀释定位信号，激进去重又会吞掉独有代码与演进差异。

本篇 sources 的整本书调研与格式处理方案支持“先判断知识载体，再解析组织，再建索引”。适用于有章节/文档边界、需要多期追溯的书籍与课件；损坏 PDF、扫描图缺 OCR、纯构建产物不应靠后续去重补救。验收是独有信息不丢、来源可回溯、重复不挤占候选，不是文件数降得越多越好。

原文“不合并、打标、取最新”与来源中的“归并同知识点”代表不同组织政策：保留原件追溯，与检索只给一个融合表示可以同时成立。本轮仅保留并标清这些选项，不擅自合并材料、删除版本或更改入库排除策略。遇到技术事实冲突，应在融合稿标来源与条件，而非用更新时间盲选胜者。

核心论点

2

整本书/多期课件入库的难点是语料组织而不是切分技术——重复内容互相打架才是质量杀手。 同一本书多版本、同一课件多期各存一份，会让 RAG 检索到互相矛盾的旧版本答案；解法是双层去重（文件级 sha256 + chunk 级正文指纹）加章节级组织（按知识域而不是按来源文件挂载）。操作顺序有硬性依赖：先清重复、再归类挂图谱、再提炼成"这个问题最好的答案"式知识点文档，最后才 ingest——跳过提炼直接灌库，RAG 只能查到书摘碎片。合并多期材料时保留各期增量与硬数字、冲突标判断，旧原件用 RAG_EXCLUDE_PREFIX 排除而不是删文件。

WHYT：解析、父子分块、去重与版本组织怎样协同

分层数据契约与选型依据

2 
源文/版本 → 格式解析 → 标题与表格保护 → child 检索表示
                    └─────────────→ parent 完整语境
文档 hash / chunk 指纹 → 精确去重 → 来源优先级 → registry/索引
查询 → 候选融合/精排 → 近重复与版本治理 → 引用原段落

契约至少包含 source、heading_path、文件版本/hash、parent 关联与内容粒度。字节精确匹配应以 hash/逐字一致判断；原文把 MinHash-LSH/SimHash 放在 byte-exact 一行是概念混用，它们用于近似相似候选，不证明字节相等。当前正文指纹去重也不等于已做 embedding 聚类，更不等于所有来源的语义去重。

参数要以真实实现解释：本库 384/80 与 800/100 默认按字符，不是 token；legacy Markdown 的 800/100 细切独立于普通 RAG_CHUNK_SIZE。表格可能为完整性保留长块；仅改环境参数而源文 hash 不变时，registry 可能跳过文件，所以参数实验需要完整且独立的索引版本，不是重复跑增量就一定重切。

业内对标沿用源文：固定/递归作为基线，父子索引负责定位与语境解耦，RAPTOR 服务跨章摘要，Contextual 解决块脱离上下文。不同来源里的 49/67% 是特定 top-20 失败率降幅，不能借给本库规则前缀；原有 599/47、29547/15000 等为历史台账或估算，不是本轮实际规模。

整本书、整套多期课件入库，难点不在"切多大"，而在"怎么组织一套语料而不互相打架"。 一句话方法：

  1. 结构用「章节级 parent + 段落级 child」两层——child（256–512 token）负责精确检索，parent（≤1024 token）负责给 LLM 完整上下文；句子级不单独入库。
  2. 去重做双层——入库前做 byte 级 + semantic 级去重（让候选集干净），检索时再做 near-dup 过滤（阈值 cosine ≈ 0.95，让 LLM 不收到同一观点的 N 个版本）。两层都不能省。
  3. 多期课件不合并、要打标——v1/v2/v3 全部保留（保留演进信息），但给 chunk 打 course_tier / updated_at，同主题召回时只留最新期或最高分那一条。
  4. 技术选型看场景——横向对比型课件库首选 Contextual Retrieval + Parent-Child + 去重；Late Chunking / RAPTOR 对"几百篇横评"场景不是 P0。

切片 token 参数本身（本库 384/800）已落在业内推荐区间（child 256–512 / parent 512–1024），不是主要矛盾。真正的差距在上下文富集和多期去重。

是什么（定义与边界）

2

定义：本文解决"整本书/整套多期课件入库"的语料组织问题，核心方法 = 「章节级 parent + 段落级 child」两层粒度 + 双层去重（入库前 byte/semantic 级 + 检索时 near-dup 过滤）+ 多期课件打标不合并。

边界：
- ✅ 管：语料入库时的组织结构、去重、多期版本处理。
- ❌ 不管：切分 token 参数本身的选优（Chunk大小怎么选）、检索算法（RRF融合加重排）、内容保鲜（知识库保鲜与TTL治理）。
- ⚠️ 「多期课件不合并、打标取最新」与"跨期取并集合成完整版"是两种口径——本文保留多版本打标路线；若要合并各期独有内容，走语义比对合成流程（见 ragged-knowledge-pipeline 技能），两者择一，勿混用。

两条反直觉的实测证据（用来反驳"语义切块一定更好"）：

  • Vectara NAACL 2025 同行评审（25 配置 × 48 模型）：fixed-size 在三个评估任务上都赢了 semantic chunking，"更贵的方法更好"是幻觉。

据[一手源]：整本书入库最佳实践-20261014.md —— 业内推荐参数区间与本库（384/800）逐项对照：

参数 业内推荐 本库 判断

parent 512–1024 token 800 区间内，合理
child overlap 10–20%（512 token 配 50–100） 未显式配 建议显式写 38 token（10%）

二、双层去重（整套课件的核心动作）

2
第一层：入库前 dedup（offline，越彻底越好）3 个重点▾ 点开看本节重点
本节重点
  • 1. Byte-exact 去重：MinHash-LSH / SimHash，毫秒级去完全相同的 chunk；Milvus 2025 原生支持 MinHash-LSH 索引
  • 2. Semantic 去重：embedding 聚类（NVIDIA NeMo Curator 用 k-means + 簇内代表性保留），识别"换个说法讲同一件事"
  • 3. 文档级 + chunk 级两层都做：先文档级砍整篇近重复（简单但漏局部），再 chunk 级清内部冗余（彻底但贵）

  1. Byte-exact 去重：MinHash-LSH / SimHash，毫秒级去完全相同的 chunk；Milvus 2025 原生支持 MinHash-LSH 索引。
  2. Semantic 去重：embedding 聚类（NVIDIA NeMo Curator 用 k-means + 簇内代表性保留），识别"换个说法讲同一件事"。

据[一手源]：整本书入库最佳实践-20261014.md —— 入库前去重的收益与代价（源文估算，未实施前不当实测）：599 篇课件里独立信息可能只有约 200 篇；chunk 总数预计从 29547 降到约 15000，raw 层噪音减半，wiki/ontology 提炼层不再被淹没。工作量：检索时 near-dup 过滤约 2 小时，入库前 semantic 聚类约 2 天（CPU 上跑 bge-m3 编码慢，要放后台任务）。

据[一手源]：各类格式进RAG处理方案-20261021.md —— 去重之前先判"该不该进"。进库口径：真知识（有人写的、可被引用的教程/笔记/方法论/案例/规范/调研）进；构建产物（向量存储、rerank 缓存、registry）、纯数据集、测试桩、依赖清单、纯链接跳转、重复副本不进。该源在课件库 234 个 txt 里实测出的重复组：小说章节 12 份、DeepSeek 介绍 6 份、公司规章制度 6 份，各留 1 份即可（sha256 或正文相似度去重）；docx 与 pdf 版规章同内容，也只留一份。

第二层：检索时 near-dup 过滤（query-time，2 小时就能上线）

3

top-K（如 top-30）召回后，按 cosine 相似度把 near-dup 折叠成一条，只留最高分。阈值经验：

阈值 行为 适用
0.99 只去几乎相同的 多样化知识库
0.95 默认 多期课件场景
0.85 激进 高度重叠文档集
0.70 最狠 极度重复语料

为什么必须做：多期同主题课件全部原样入库时，一个问题会召回 3 个讲同一件事、版本略有出入的 chunk，LLM 拿到的是"3 个版本的加权平均"而不是 3 个独立证据——这是错误来源，也是 raw 层淹没提炼层的直接原因。业内共识：80% 的生产 RAG 准确性问题来自重复/矛盾源，不做去重，加 rerank、加 query 改写都是治标。

三、多期课件怎么处理（不合并、打标、取最新）3 个重点▾ 点开看本章重点
本章重点
  • 不要把 v1/v2/v3 合并成 1 篇（会丢掉技术演进）
  • 1. 入库时给每个 chunk 打 「course_tier」（v1/v2/v3）和 「updated_at」，从路径/文件名解析期数
  • 2. 检索时同主题 near-dup 只保留最新期或最高分那一条
2

不要把 v1/v2/v3 合并成 1 篇（会丢掉技术演进）。正确做法：

  1. 入库时给每个 chunk 打 course_tier（v1/v2/v3）和 updated_at，从路径/文件名解析期数。
  2. 检索时同主题 near-dup 只保留最新期或最高分那一条。
  3. 演进信息放到提炼层（wiki/ontology）显式做"演进对比"，而不是让 raw 多期版本在召回阶段互相打架。

生成本地（可选）：给 LLM 的 prompt 显式标注"以下 N 条来自不同年份的同一主题课件"，让模型做时间加权（新的优先）而不是平均。

技术 核心做法 适用 对横评型课件库

配置（评测指标 1−recall@20，4 个域，top-20） 失败率 相对基线降幅
基线：纯 embedding 5.7% —
+ Contextual Embeddings（每 chunk 前拼 50–100 token 的 Claude 上下文） 3.7% 35%

成本口径：800-token chunk、8k-token 文档、100-token 上下文，开 prompt caching 后一次性约 $1.02 / 百万文档 token（不开缓存要高一个量级）。选型口诀：Anthropic 原话称"给 chunk 加通用文档摘要"实验收益 very limited、summary-based indexing 表现差，原因是每个 chunk 拿到的上下文雷同、区分度差；要拿这三档数字，必须用 LLM 逐 chunk 生成它在文档里的定位，规则拼接标题/路径前缀不能直接套用这三档数字，只能以本库自己的 A/B 为准。
