RAG 系统架构与生产落地

核心结论：生产级 RAG 不是“向量库 + 大模型”，而是一套有数据契约、有证据门禁、有版本边界、有评测回归的知识系统。最优主线是：先把文档变成可定位的证据，再用混合召回与重排找到证据，证据不足就拒答，答案逐句可追溯，最后用同一把尺子持续回归。 Contextual Retrieval、Agentic RAG、GraphRAG、LightRAG 都只是这条主线上的条件分支，不是替代数据治理和评测的捷径。

本文定位：融合课件的理论骨架、实战书籍的工程经验、2026 年前沿路线与本库当前实现，形成从 WHY、WHYT 到 HOW 的单一主线。新资产挂总地图 N2（知识与方案规划）、N4（工程落地）、N5（验收与证据）。

1. 业务价值来自“外部知识可控地进入决策”

3

大模型参数中的知识有截止时间，也不天然包含企业制度、项目文档、产品手册和内部术语。RAG 把知识放在模型外部，在查询时取回证据再生成，因此知识更新主要变成数据和索引问题，不必每次重新训练模型。它尤其适合：知识频繁变化、回答必须给来源、不同用户权限不同、错误回答有明确业务成本 的场景。【行业调研】

但“能回答”不等于“可上线”。营销头脑风暴中的幻觉可能只是体验问题；合同条款、信用备忘、临床记录中的无依据陈述则可能成为事故。生产的分水岭不是回答是否流畅，而是系统能否做到：

  • 可检索：正确证据能进入候选并排到前面；
  • 可拒答：库内没有依据、证据不足或用户无权访问时，不硬答；
  • 可验证：答案声明能回指具体文档、章节或页码，实验可复现，版本可回滚。

这三项也是后续所有架构选择的统一验收语言。

3. 解析与分块：先保住证据结构，再谈向量质量

3

3.1 解析必须按文档类型验收

Markdown、HTML、Word、文本型 PDF、扫描 PDF、表格和图片不是同一种输入。纯文本解析器遇到扫描件可能得到空字符串；版面复杂的 PDF 可能出现双栏错序、页眉页脚重复、表格行列被打散。生产验收必须抽样对照原页，至少检查：

  • 正文是否缺段、乱码、错序；
  • 标题层级是否保留；
  • 表格的表头、单位、行列对应是否完整；
  • 图片文字和图注是否遗漏；
  • 页码与来源是否还能回溯。

对表格，不应先粗暴切成普通句子再试图补救。可以保留原始表格为生成证据，同时为其生成摘要或检索描述；摘要是检索入口，原始表格才是事实依据。图片也一样：VLM 描述方便接入文本检索，但可能漏掉细节，关键数字仍需回看原图或结构化抽取结果。【行业调研】

3.2 分块没有通用最优值

固定长度实现简单，递归分块利用分隔符层级，结构分块优先保留标题、段落、列表和表格边界，语义分块按内容变化切分。选择顺序应是 结构完整性 → 问题形态 → Embedding 输入限制 → token 与延迟预算，而不是背一个 512 或 384 的“最佳值”。

  • 短事实、编号、API 参数：较小且自洽的块更容易精确命中；
  • 长论证、制度条件、跨段步骤：需要父块、邻接扩展或更大块；
  • 表格与代码：按结构保护，不宜按字符硬切；
  • overlap 只缓解边界问题，不能修复错误解析，也不是越大越好。

变更 chunk 规则会改变证据 ID、向量与 golden 标签，因此不是一次普通参数调整，而是一次索引版本变更。

3.3 Contextual Retrieval 补的是“全局定位”

【一手源】Anthropic 的方法是在入库时让 LLM 根据整篇文档为每个 chunk 生成简短定位，再做 contextual embeddings 与 contextual BM25。官方报告中的 35%/49%/67% 分别是不同组合下 top-20 检索失败率的相对降幅，不是 Recall 提升，也不能全归给 Contextual 单独作用；49% 对应加入 hybrid，67% 对应再加入 rerank。Prompt caching 降低重复读取整篇文档的成本，不是另一个准确率版本。

本库同时存在规则前缀与 LLM 前缀入口：规则版用文件路径和标题补定位，成本低；LLM 版能描述 chunk 在全文中的作用，但产生入库调用成本。二者不可共享官方数字。正确决策不是“规则版等于官方版”，而是用同一批文档和同一 golden 集做 A/B，比较收益、失败率与成本。

4.1 dense 与 sparse 互补

dense 向量擅长同义表达和语义相近，sparse/BM25 擅长产品名、编号、缩写和专有术语。用户说“怎么防止检索不到正确资料”可能靠 dense；问 bge-reranker-v2-m3 的精确型号则不能只靠语义相似。混合检索的目的不是让管线看起来高级，而是覆盖不同失败模式。【行业调研】

4.2 RRF 融合排名，不混算距离

不同检索器的 cosine 距离、BM25 分数、稀疏点积不在同一尺度，直接相加通常没有稳定含义。RRF 使用排名：

[
RRF(d)=\sum_i w_i/(k+rank_i(d))
]

k 平滑头部名次差异，w_i 控制检索路权重。同一文档必须按稳定 chunk_id 合并，否则去重与融合都会失真。RRF 的结果仍是候选排序分数，不能直接当作“答案可信度”或拒答概率。

4.3 Cross-Encoder 重排做精排

第一阶段追求候选覆盖，第二阶段把 query 与每个候选一起输入 Cross-Encoder，细粒度判断相关性。典型折中是“较大的候选池 → rerank top N → 少量证据进生成”。候选池太小会结构性排除正确答案，太大则增加重排延迟；top_k 也不是越大越好，过多证据会增加噪声与成本。【行业调研】

4.5 门禁必须绑定具体分数和链路状态

rerank 分数、dense 距离、RRF 分数不可共用阈值。启用 rerank 时用校准后的 rerank 门禁；rerank 被禁用或故障降级时，走独立校准的 dense 兜底门禁，并显式记录“本次是降级回答”。不能把主链路阈值直接搬到降级链路。

门禁至少分三种结果：

  • 通过：证据充分，可以生成；
  • 重试：查询表达或候选质量可能可修，允许有限次改写重检；
  • 拒答：达到重试预算仍无可靠证据，或明确越权/不在服务范围。

拒答不是失败装饰，而是生产功能；但阈值过高会误拒正确问题，所以正样本与负样本必须一起校准。

5. 查询路由与 CRAG：让复杂度受控地进入系统

3

课件把 Advanced RAG 分为预检索和后检索：查询重写、扩展、分解属于前者，重排、压缩和过滤属于后者。【行业调研】工程上还需增加路由，因为不同问题不应支付同样成本：

  • 简单事实：一次混合检索与精排通常足够；
  • 复杂综合：可能需要多查询、更多候选和跨文档证据；
  • 多跳关系：可进入图上下文或迭代检索；
  • 结构化统计：优先 SQL/表查询，而不是把数字表完全交给向量检索。

CRAG 的核心不是“无限重写”，而是 检索质量评价 → 必要时改写 → 有预算地重检。Self-RAG、Adaptive RAG、Agentic RAG 进一步把检索时机和步骤交给模型决策，但必须保留原始问题、重写历史、最大循环次数和失败退出条件。

LangGraph 适合承载这类流程，因为它把隐式循环变成显式状态：question、original_question、route、documents、relevant_docs、rewrite_count、answer 等状态在节点间传递，条件边决定继续、改写或结束。好处是可观察、可测试；代价是状态契约需要维护，节点不能随意隐式修改全局数据。【行业调研】

7. 权限、安全与最小上下文是 Day 0 架构约束

3

【Palantir-Anthropic文档解析】Palantir AI FDE 的可借鉴点不是“多接几个工具”，而是四条生产原则：继承用户权限、最小初始上下文、执行后观察并自验证、所有动作留痕且可评审。映射到 RAG：

  • 用户身份必须在检索前进入过滤条件，不能先取回秘密文档再在生成后遮盖；
  • Agent 不拥有独立超级权限，只获得完成当前任务所需的最小数据与工具；

4.1 RRF 最小实现

以下逻辑与本库当前 rrf_fuse 一致：排名从 1 开始，同一稳定 ID 累加各路得分。【一手源】

def rrf_fuse(rank_lists, k=60, weights=None):
    scores, sources = {}, {}
    weights = weights or [1.0] * len(rank_lists)
    for i, rank_list in enumerate(rank_lists):
        weight = weights[i] if i < len(weights) else 1.0
        for rank, hit in enumerate(rank_list, start=1):
            hit_id = hit.get("_id") or (hit["source"], hit["chunk"])
            scores[hit_id] = scores.get(hit_id, 0.0) + weight / (k + rank)
            sources.setdefault(hit_id, hit)
    merged = []
    for hit_id, score in sorted(scores.items(), key=lambda x: x[1], reverse=True):
        hit = dict(sources[hit_id])
        hit["rrf_score"] = score
        merged.append(hit)
    return merged

单元测试至少覆盖：同 chunk 在两路出现能合并；不同 chunk 不错误合并；空列表不报错；权重长度不足有默认行为；排名并列时结果可复现。

from typing import TypedDict
from langgraph.graph import StateGraph, END

class State(TypedDict):
    question: str
    original_question: str
    documents: list
    rewrite_count: int
    answer: str

def retrieve(state: State) -> dict:
    return {"documents": retrieve_evidence(state["question"])}

def grade(state: State) -> dict:
    # 真实项目在这里做相关性评分，不伪造默认通过。
    return {"documents": grade_evidence(state["question"], state["documents"])}

def should_rewrite(state: State) -> str:
    if state["documents"]:
        return "generate"
    if state["rewrite_count"] < 2:
        return "rewrite"
    return "refuse"

def rewrite(state: State) -> dict:
    return {
        "question": rewrite_query(state["original_question"], state["question"]),
        "rewrite_count": state["rewrite_count"] + 1,
    }

def generate(state: State) -> dict:
    return {"answer": generate_with_citations(state["original_question"], state["documents"])}

def refuse(state: State) -> dict:
    return {"answer": "根据当前已授权知识库，无法确认该问题。"}

builder = StateGraph(State)
for name, fn in [("retrieve", retrieve), ("grade", grade),
                 ("rewrite", rewrite), ("generate", generate), ("refuse", refuse)]:
    builder.add_node(name, fn)
builder.set_entry_point("retrieve")
builder.add_edge("retrieve", "grade")
builder.add_conditional_edges("grade", should_rewrite, {
    "rewrite": "rewrite", "generate": "generate", "refuse": "refuse",
})
builder.add_edge("rewrite", "retrieve")
builder.add_edge("generate", END)
builder.add_edge("refuse", END)
app = builder.compile()

其中 retrieve_evidence、grade_evidence、rewrite_query、generate_with_citations 是需要项目自行实现的函数，示例没有伪装成现成 API。生产还应补超时、异常降级、每节点 trace、token/调用预算和最大总步数；只限制 rewrite 次数并不能限制其他所有循环。

本库当前图结构为 router → retrieve → grade → (rewrite → grade | rerank) → gate → generate，重写次数来自 CRAG 配置。【一手源】路由分支最终仍要进入统一证据门禁，不能让 multi-hop 或图谱分支绕过引用与拒答。

3. 解析与分块：先保住证据结构，再谈向量质量

3

3.1 解析必须按文档类型验收

Markdown、HTML、Word、文本型 PDF、扫描 PDF、表格和图片不是同一种输入。纯文本解析器遇到扫描件可能得到空字符串；版面复杂的 PDF 可能出现双栏错序、页眉页脚重复、表格行列被打散。生产验收必须抽样对照原页，至少检查：

  • 正文是否缺段、乱码、错序；
  • 标题层级是否保留；
  • 表格的表头、单位、行列对应是否完整；
  • 图片文字和图注是否遗漏；
  • 页码与来源是否还能回溯。

对表格，不应先粗暴切成普通句子再试图补救。可以保留原始表格为生成证据，同时为其生成摘要或检索描述；摘要是检索入口，原始表格才是事实依据。图片也一样：VLM 描述方便接入文本检索，但可能漏掉细节，关键数字仍需回看原图或结构化抽取结果。【行业调研】

3.2 分块没有通用最优值

固定长度实现简单，递归分块利用分隔符层级，结构分块优先保留标题、段落、列表和表格边界，语义分块按内容变化切分。选择顺序应是 结构完整性 → 问题形态 → Embedding 输入限制 → token 与延迟预算，而不是背一个 512 或 384 的“最佳值”。

  • 短事实、编号、API 参数：较小且自洽的块更容易精确命中；
  • 长论证、制度条件、跨段步骤：需要父块、邻接扩展或更大块；
  • 表格与代码：按结构保护，不宜按字符硬切；
  • overlap 只缓解边界问题，不能修复错误解析，也不是越大越好。

变更 chunk 规则会改变证据 ID、向量与 golden 标签，因此不是一次普通参数调整，而是一次索引版本变更。

3.3 Contextual Retrieval 补的是“全局定位”

【一手源】Anthropic 的方法是在入库时让 LLM 根据整篇文档为每个 chunk 生成简短定位，再做 contextual embeddings 与 contextual BM25。官方报告中的 35%/49%/67% 分别是不同组合下 top-20 检索失败率的相对降幅，不是 Recall 提升，也不能全归给 Contextual 单独作用；49% 对应加入 hybrid，67% 对应再加入 rerank。Prompt caching 降低重复读取整篇文档的成本，不是另一个准确率版本。

本库同时存在规则前缀与 LLM 前缀入口：规则版用文件路径和标题补定位，成本低；LLM 版能描述 chunk 在全文中的作用，但产生入库调用成本。二者不可共享官方数字。正确决策不是“规则版等于官方版”，而是用同一批文档和同一 golden 集做 A/B，比较收益、失败率与成本。

4.1 dense 与 sparse 互补

dense 向量擅长同义表达和语义相近，sparse/BM25 擅长产品名、编号、缩写和专有术语。用户说“怎么防止检索不到正确资料”可能靠 dense；问 bge-reranker-v2-m3 的精确型号则不能只靠语义相似。混合检索的目的不是让管线看起来高级，而是覆盖不同失败模式。【行业调研】

4.2 RRF 融合排名，不混算距离

不同检索器的 cosine 距离、BM25 分数、稀疏点积不在同一尺度，直接相加通常没有稳定含义。RRF 使用排名：

[
RRF(d)=\sum_i w_i/(k+rank_i(d))
]

k 平滑头部名次差异，w_i 控制检索路权重。同一文档必须按稳定 chunk_id 合并，否则去重与融合都会失真。RRF 的结果仍是候选排序分数，不能直接当作“答案可信度”或拒答概率。

4.3 Cross-Encoder 重排做精排

第一阶段追求候选覆盖，第二阶段把 query 与每个候选一起输入 Cross-Encoder，细粒度判断相关性。典型折中是“较大的候选池 → rerank top N → 少量证据进生成”。候选池太小会结构性排除正确答案，太大则增加重排延迟；top_k 也不是越大越好，过多证据会增加噪声与成本。【行业调研】

4.5 门禁必须绑定具体分数和链路状态

rerank 分数、dense 距离、RRF 分数不可共用阈值。启用 rerank 时用校准后的 rerank 门禁；rerank 被禁用或故障降级时，走独立校准的 dense 兜底门禁，并显式记录“本次是降级回答”。不能把主链路阈值直接搬到降级链路。

门禁至少分三种结果：

  • 通过：证据充分，可以生成；
  • 重试：查询表达或候选质量可能可修，允许有限次改写重检；
  • 拒答：达到重试预算仍无可靠证据，或明确越权/不在服务范围。

拒答不是失败装饰，而是生产功能；但阈值过高会误拒正确问题，所以正样本与负样本必须一起校准。

5. 查询路由与 CRAG：让复杂度受控地进入系统

3

课件把 Advanced RAG 分为预检索和后检索：查询重写、扩展、分解属于前者，重排、压缩和过滤属于后者。【行业调研】工程上还需增加路由，因为不同问题不应支付同样成本：

  • 简单事实：一次混合检索与精排通常足够；
  • 复杂综合：可能需要多查询、更多候选和跨文档证据；
  • 多跳关系：可进入图上下文或迭代检索；
  • 结构化统计：优先 SQL/表查询，而不是把数字表完全交给向量检索。

CRAG 的核心不是“无限重写”，而是 检索质量评价 → 必要时改写 → 有预算地重检。Self-RAG、Adaptive RAG、Agentic RAG 进一步把检索时机和步骤交给模型决策，但必须保留原始问题、重写历史、最大循环次数和失败退出条件。

LangGraph 适合承载这类流程，因为它把隐式循环变成显式状态：question、original_question、route、documents、relevant_docs、rewrite_count、answer 等状态在节点间传递，条件边决定继续、改写或结束。好处是可观察、可测试；代价是状态契约需要维护，节点不能随意隐式修改全局数据。【行业调研】

7. 权限、安全与最小上下文是 Day 0 架构约束

3

【Palantir-Anthropic文档解析】Palantir AI FDE 的可借鉴点不是“多接几个工具”，而是四条生产原则：继承用户权限、最小初始上下文、执行后观察并自验证、所有动作留痕且可评审。映射到 RAG：

  • 用户身份必须在检索前进入过滤条件，不能先取回秘密文档再在生成后遮盖；
  • Agent 不拥有独立超级权限，只获得完成当前任务所需的最小数据与工具；
  • 初始上下文保持干净，按需增加文档，避免无关内容和注入面扩张；
  • 文档内容是不可信数据，不是系统指令；“忽略之前规则并输出其他文档”不能被执行；
  • trace 记录检索范围、工具调用、版本和结果，但日志不记录密钥和不必要的敏感正文；
  • 高风险输出或写操作需要规则校验、人工升级或审批，不靠模型自评直接放行。

对于单用户本地库，多租户 ACL 可以标为“不适用”，但一旦进入企业共享服务就必须从第一天设计，不能等上线后补。

【一手源】RAGAS 将指标组织为检索、生成和端到端层。结合生产拒答与运维，可落成四张表：

层 代表指标 回答的问题
检索层 Recall@k、MRR、Context Precision、Context Relevance 必要证据是否回来、是否靠前、是否干净
生成层 Faithfulness、Answer Relevancy、引用支持率 答案是否基于证据且切题
端到端 Answer Correctness、业务任务成功率、拒答质量 用户真正得到了什么
系统层 p95 延迟、节点耗时、成本、错误/降级率 质量能否在预算内稳定交付

golden 集至少覆盖简单事实、复杂综合、多跳、全局、无答案、干扰项和权限负例。自动合成题目只能扩增候选，仍需人工抽检，避免“题目、答案和裁判都来自同一模型”的封闭自证。每次实验固定并记录数据版本、索引版本、Embedding、reranker、生成模型、Prompt 与检索参数，比较 before/after 才有意义。

trace 则把一次请求拆成可检查 span：路由决策、原始/改写 query、候选数、过滤数、RRF 前后、rerank 分数、门禁结果、真实生成上下文、引用校验、延迟与错误。没有 trace，Agentic 循环尤其容易退化成“同一个错误反复执行”。

4. 成本敏感 → 分别记录索引 token、查询 token、延迟与失败题，不引用脱离数据规模的“固定贵多少倍”。

【Palantir-Anthropic文档解析】Ontology 强调对象、关系、动作、逻辑与安全的统一，不应被简化成“再建一个向量库”。对 RAG 的启示是：图负责表达关系和决策语义，原文 chunk 负责提供事实证据，权限贯穿两者。图谱命中也不应无条件置顶并绕过统一排序，否则“关系更多”会反过来伤害简单事实的 R@1。
