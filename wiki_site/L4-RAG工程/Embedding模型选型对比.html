核心论点

3

通用语料上的 benchmark 排名对生产选型只有参考价值，真正的决策变量是"你的场景 × 部署约束 × 语言"三者的交集。 中文为主、要私有化、要 dense+sparse 一体输出时 bge-m3 是无需争论的默认解；英文极致质量才轮到 OpenAI 3-large，窄领域必须用 (query, relevant_doc) badcase 微调而非换通用模型。比选型本身更硬的规则是三条工程约束：换模型必须重建索引（向量空间不兼容）、维度不是越高越好（3072 维成本 3 倍收益约 3%）、改 embedding 前先用 100 条领域 query 实测 Recall@5 而不是看 MTEB 榜。

是什么（定义与边界）

3

定义：embedding 模型 = 把文本映射为定长向量、使语义相近的文本在向量空间中距离相近的编码器；RAG 用它把 query 和 chunk 编码到同一空间做相似度检索。选型维度：语言覆盖、维度、最大上下文、dense/sparse 是否一体输出、开源 vs API、价格。

边界：
- ✅ 管：检索第一轮的召回质量（"能不能把正确文档召回来"）。
- ❌ 不管：排序精度（cross-encoder rerank 的活）、生成质量（LLM 的活）、语料覆盖（知识库内容的活）。
- ⚠️ "微调 embedding"与"微调 LLM"是两回事：本文的微调指用 (query, relevant_doc) badcase 对微调编码器（提升召回 10-20%），不涉及生成模型——见 RAG和微调到底选哪个。

二、选型决策树

你的场景？
├─ 中文为主？
│  ├─ 需要开源/私有部署？ → bge-m3 ✅
│  └─ 可以用付费 API？ → OpenAI text-embedding-3-large（中文质量略高于 bge-m3）
├─ 英文为主？
│  ├─ 追求极致质量？ → OpenAI voyage-2
│  └─ 成本优先？ → text-embedding-3-small
├─ 法律/医疗/金融窄领域？
│  └─ 通用模型召回差 → 用 bge-base 做领域微调（黄佳 §3.7）
└─ 多语言混合？
   └─ bge-m3 或 Cohere embed v3

三、关键陷阱

  1. 不要用只在英文上训练的模型跑中文：all-MiniLM 在中文上召回率会掉一半
  2. 向量维度不是越高越好：3072 维存储和计算成本是 1024 维的 3 倍，质量提升可能只有 3%
  3. 换 embedding 模型必须重建索引：不同模型的向量空间不兼容，不能混用
  4. bge-m3 的 sparse 输出要单独启用：默认只输出 dense，用 return_sparse=True 才能拿到 BM25 风格的稀疏向量
  5. 微调 embedding 比换生成模型收益更大：黄佳《RAG实战课》第 3.7 节专门讲微调 embedding，1438 人划线——领域内微调通常能把 Recall@5 提升 10-20%
  6. 据[一手源]：RAG优化-外部调研-20260929（StackAI fix-order playbook）：召回差时换 embedding 排在最后一位——顺序是 chunking + metadata → hybrid → candidate size → 才换模型；换模型前先证明前三步已做满。
  7. 据[一手源]：RAG进阶调研-6方向-Top3落地方案-20260928（2026 开源横评，tier2）：Qwen3-Embedding-8B（2026 初）MTEB v2 开源第一，约 75%；BGE-M3 仍是 HF 下载量第一（568M 参数、1024 维、100+ 语言、8192 context），且单模型同时输出 dense / sparse / ColBERT multi-vector 三种；BEIR 上三模式混合比单模式 nDCG@10 高 2–5 点。本库 bge-m3 目前只用 dense + sparse，ColBERT multi-vector 能力未启用，是"免费的升级空间"。长文档（> 2048 token）子集可备 Qwen3-Embedding-0.6B/4B（32K context）；8GB 笔记本本地跑 BGE-M3 或 Nomic v2。中文场景 BGE-M3 与 Qwen3 谁更好，必须在自建 query eval set 上实测，不凭榜单直接切。
  8. 据[一手源]：多模态RAG图片处理两路线-飞书-20261020：图片进 RAG 时 embedding 有两种选法——路线一用多模态 Embedding（图片直接转向量，查询时每次要调多模态模型，需与文本向量双路融合）；路线二用 VLM 生成描述 + 文本 Embedding（沿用本篇的文本模型如 bge-m3，产出直接并入现有 dense+sparse 检索）。本库图片多为课件截图，沿用文本 embedding 的路线二不用换模型。

我们库当前的落地点

3

我们已经选了 bge-m3——这是中文开源场景的最优解，理由：
- dense (1024维) + sparse 一体输出，天然支持 hybrid 检索，不需要单独跑 BM25
- 8K 上下文窗口，能吃下整个段落
- 免费开源，私有化部署无 API 成本

下一步优化：
1. 在我们自己的 100 条 query 上跑 Recall@5 基线，确认 bge-m3 在我们的文档域上表现是否达标
2. 如果某些领域（如法律合同）召回差，用领域数据微调 bge-base
3. 考虑加 Cohere Rerank（cross-encoder 精排），这一步的收益通常比换 embedding 模型更大

本库真实落地（源码核对，2026-11-04）

  • 本库选的是 bge-m3，理由是「一个模型同时出 dense 和 sparse」——本次实跑验证了这一点（rag/.venv，2026-11-04）：
    [m3] bge-m3统一模型已加载(dense+sparse共用): /home/wuyafang/models/bge-m3 [m3] sparse 头来源(非随机初始化): /home/wuyafang/models/bge-m3/sparse_linear.pt (3516B sha256=45c93804d2142b8f) local_dense dim=1024 head=[-0.0071, 0.0166, -0.0302, -0.0003] load+encode=224.7s sparse tokens=15 head=[('19071', 0.11032017320394516), ('30094', 0.2633190155029297), ...] enc=0.3s
  • 选型里最容易被忽略的一条：同一个模型名不等于同样输出（rag/config.yaml L17-19，本次读源码）：
    yaml # [2026-10-14 澄清] eval_mode=true 仅让 *dense* 编码走 Ollama(省内存), # 不再影响 sparse —— query_sparse() 已改为独立加载本地模型(_get_sparse_model)。 # Ollama 的 bge-m3 只输出 dense 1024 维, 没有 lexical_weights, 无法提供 sparse。
    Ollama 里的 bge-m3 只能给 dense，要 sparse 必须本地 FlagEmbedding 加载带 sparse_linear.pt 的权重——混用会得到「dense 变了、sparse 没变」而不报错。
  • 加载器还有一道自检：_get_m3_model()（L256）在加载前检查 sparse 头文件，不可用就拒绝加载（拒绝加载(避免随机初始化)），而不是带病运行。随机初始化的 sparse 头会让检索结果看起来「能用」但毫无意义。
  • 和课件讲法的差异：课件对比 embedding 多比 MTEB 分数与维度；本库的决策变量是「能否同时提供 dense+sparse、能否本地离线跑、加载耗时」。224.7 秒的冷加载是真实成本，选型时必须计入。
  • 本库暂无：没有对本库语料做的 embedding 横向评测（bge-m3 vs 其他模型在同一套 golden 问题上的 R@k），选型依据来自通用榜单 + 本地可跑性。

来源与三源融合落点

来自哪些书的哪些观点

3
  • 黄佳《RAG实战课》：第 3 章完整对比 OpenAI / Jina / Cohere / Voyage，明确推荐"根据任务选模型，不要盲目追最大"。重点：稀疏嵌入、密集嵌入和 BM25 是三种不同的编码范式（§3.4），不是越新越好。
  • 郑天民《从零实现RAG与Agent系统》：强调 embedding 是 RAG 的"基础设施"，1052 人划线——"Embeddings 模型可将文本信息转化为数字表示形式，便于进行语义搜索"。
  • 凌峰《构建智能生成系统》：242 人划线——"向量检索利用嵌入模型将文本语义信息保存在向量中，从而能够匹配语义上相关的内容，而不仅仅是字面相似的内容"。
  • Denis Rothman《RAG-Driven Generative AI》：第 9 章专门讲 fine-tuning RAG embedding 数据——把检索到的 bad case 做成 (query, relevant_doc) 对来微调 embedding 模型。

冲突点：黄佳建议多模型对比测评（MTEB + 自己的领域数据），Denis 建议直接微调。两者结合：先用 MTEB 选 2-3 个候选，在自己的 100 条 domain query 上实测，不行再微调。
