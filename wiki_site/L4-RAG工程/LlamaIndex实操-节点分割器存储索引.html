核心论点

3

LlamaIndex 的数据模型是"文档 → 节点 → 三种存储"：Node 是检索的最小单位，docstore 存节点原文，vector_store 存向量，index_store 存索引结构，三者可以分别换后端。 课件 day04 的主线就是把这三者拆开演示：先造节点（01–04），再分别持久化文档（05–06）、向量（07–08）、索引（09），最后混搭（10：文档和索引放 Redis，向量放 Chroma）。最容易踩的坑也出在这个拆分上：用 Chroma 这类自带存文本的向量库时，docstore 默认是空的，依赖 docstore 的功能（节点关系遍历、父子回溯）会静默失效，需要显式打开 store_nodes_override=True。

本库自研栈（rag/ingest.py + rag/query.py）更适合生产，LlamaIndex 在这里的价值是读懂框架、读懂别人的项目，以及 rag/query_llamaindex.py 这类对照实现。

一、节点（Node）

3

1.1 认识节点：Reader + SentenceSplitter（01-认识节点.py）

# 来源：2605期 day04/源码/01-认识节点.py
from llama_index.core.node_parser import SentenceSplitter
from llama_index.core import SimpleDirectoryReader

documents = SimpleDirectoryReader(input_files=['../data_file/公司规章制度.txt']).load_data()
nodes = SentenceSplitter().get_nodes_from_documents(documents)
print(repr(nodes[1]))

三步固定套路：SimpleDirectoryReader 读成 Document → NodeParser 切成 Node → 后续存储/建索引。课件笔记里叫"分割孤岛"问题：切完的块不能丢掉出处，每个节点要知道三件事：来自哪个文档、上一个节点是谁、下一个节点是谁。LlamaIndex 把这三件事放在 node.relationships 里。

[实测] SentenceSplitter 切出的节点自带三条关系：SOURCE（来源文档）、PREVIOUS、NEXT（首尾节点各缺一条）；node_id 是 UUID。默认参数 chunk_size=1024, chunk_overlap=200（01 讲没传参，用的就是这组）。

1.2 手动创建节点并连关系（02-创建节点.py）

# 来源：2605期 day04/源码/02-创建节点.py
from llama_index.core.schema import TextNode, NodeRelationship, RelatedNodeInfo

def link_bidirectional(a: TextNode, b: TextNode, a_note: str, b_note: str):
    a.relationships[NodeRelationship.NEXT] = RelatedNodeInfo(
        node_id=b.node_id, metadata={"desc": a_note})
    b.relationships[NodeRelationship.PREVIOUS] = RelatedNodeInfo(
        node_id=a.node_id, metadata={"desc": b_note})

node1 = TextNode(text="deepseek")
node2 = TextNode(text="chatgpt")
link_bidirectional(node1, node2, a_note="这是节点2", b_note="这是节点1")

用途：不走分割器、自己从结构化数据（QA 对、制度条款）直接造节点。双向链接要两头都写（NEXT 和 PREVIOUS 分别设），只写一头遍历时会断。RelatedNodeInfo.metadata 可挂关系描述，方便追溯。

2.1 SentenceSplitter 的长度单位是 token（03-分割器.py、test.py）

# 来源：2605期 day04/源码/03-分割器.py
splitter = SentenceSplitter(
    chunk_size=100,    # 单位是 token，不是字符数
    chunk_overlap=5,   # 同样是 token
)
nodes = splitter.get_nodes_from_documents(documents)
for node in nodes:
    print(repr(node)); print(len(node.text))   # 对比字符数和 chunk_size

课件 test.py 专门用来证明这一点：

from llama_index.core import get_tokenizer
bb = '这些人，都如此刻薄势力吗？或许是因为三年前他们曾经在自己面前露出过最谦卑的笑容'
print(len(bb), len(get_tokenizer()(bb)))

[实测] 这句 39 个字符 = 50 个 token（默认 tokenizer）。对照本库 ingest.py 的 800/100 是字符单位（LangChain RecursiveCharacterTextSplitter），两边数字不能直接比：LlamaIndex 的 chunk_size=512 对应的中文字数明显少于 512（本机两组样本约 0.78 与 0.9 字/token，随内容变化），不是 512 字。

笔记里记的分句逻辑：SentenceSplitter 先按段落（多个换行）分，再用 nltk 按句号切，保证不在句子中间断开；小于 chunk_size 的段落不产生重叠块（课件注释："如果分割完之后小于长度，不会有重叠块"）。

2.2 选尺寸的方法（笔记.md）

课件笔记给的是一套流程，比"512 最好"更有用：

  1. 分析业务：先问知识库是什么（HR 制度库、产品 QA 库……）。
  2. 分析文档结构：员工手册这类按条款组织的，结构单元比固定长度重要。
  3. 找知识单元：QA 对用"问题+答案"整体做一个块；企业制度按条款（如"第 3.2 条 迟到处理"）切。
  4. 候选尺寸：384 / 512 / 768 / 1024，重叠取 10%–20%。
  5. 测试：准备约 100 个问题，只改切分尺寸，对比准确率、召回率、token 消耗、耗时。
  6. 上线。

向量模型维度/上限只是约束（笔记提到上限 8000 但"文本太长语义不够健壮"），不是目标。这条流程与 Chunk大小怎么选 的"同一把评测尺子"一致。

2.3 其他 NodeParser：HTML / JSON / Markdown（04-html解析器.py）

课件把三个解析器写在同一个文件里，只有 Markdown 这段没被注释：

# 来源：2605期 day04/源码/04-html解析器.py（HTML、JSON 两段在课件里是注释状态）
from llama_index.core.node_parser import HTMLNodeParser, JSONNodeParser, MarkdownNodeParser
from llama_index.readers.file import FlatReader
from pathlib import Path

# HTML：只取指定标签的内容做节点（需 pip install beautifulsoup4）
html_docs = FlatReader().load_data(Path("../data_file/index.html"))
nodes = HTMLNodeParser(tags=["p", "h1", "li"]).get_nodes_from_documents(html_docs)

# JSON
json_docs = FlatReader().load_data(Path("../data_file/request.json"))
nodes = JSONNodeParser().get_nodes_from_documents(json_docs)

# Markdown：按标题层级切
md_docs = FlatReader().load_data(Path("../data_file/test.md"))
nodes = MarkdownNodeParser().get_nodes_from_documents(md_docs)
  • FlatReader 把文件原样读成一个 Document（不做格式解析），解析交给后面的 NodeParser。[仅课件] HTML/JSON 两段本机缺 readers-file，未跑。
  • [实测] MarkdownNodeParser 在课件 test.md（含 Markdown 表格 + HTML <table> + 多级标题）上切出 3 个节点，metadata 里只有 header_path；一个节点的 header_path 是它所在的父标题路径，不含自己的标题（"标题三"节点的 header_path 是 /标题二/，顶层标题节点是 /）。表格没有被拆开，整张留在所属标题节点里。
  • 课件配的测试数据 厦门.md 是年报（MinerU 转出的 Markdown），test.md 里的 <table rowspan colspan> 就是这类转换产物：说明 Markdown 路线的表格会带 HTML 标签，进库前要决定是否转文本，见 各类格式进RAG处理方案。

3.1 文档存储：本地持久化与 Mongo（05、06）

# 来源：2605期 day04/源码/05-文档存储.py
from llama_index.core.storage.docstore import SimpleDocumentStore
from llama_index.core import StorageContext

doc_store = SimpleDocumentStore()
doc_store.add_documents(nodes)                       # 默认存内存
storage_context = StorageContext.from_defaults(docstore=doc_store)
storage_context.persist("./documents")               # 落盘

new_ctx = StorageContext.from_defaults(persist_dir="./documents")   # 重新加载
print(new_ctx.docstore.docs)

# 来源：2605期 day04/源码/06-mongo存储.py  [仅课件]
from llama_index.storage.docstore.mongodb import MongoDocumentStore

docstore = MongoDocumentStore.from_uri(
    uri="mongodb://localhost:27017",
    db_name="llama_index1",
    namespace="novel",        # 命名空间：多个知识库共用一个库时做隔离
)
storage_context = StorageContext.from_defaults(docstore=docstore)
storage_context.docstore.add_documents(nodes)   # 课件里这行是注释，首次运行要打开

[实测] persist() 即使只传了 docstore，也会写出 5 个文件：docstore.json、index_store.json、default__vector_store.json、image__vector_store.json、graph_store.json；重新加载后 docstore.docs 完整还原。

坑：05、06 两个文件把"写入"那几行注释掉了，只留"读取"。直接运行会因为 ./documents 不存在或 Mongo 里没数据而报错/空；先开着写入跑一遍，再注释掉。

3.2 向量存储：内存版与 Chroma（07、08）

# 来源：2605期 day04/源码/07-向量存储.py
from llama_index.core.vector_stores import SimpleVectorStore
vector_store = SimpleVectorStore()
storage_context = StorageContext.from_defaults(vector_store=vector_store)
nodes = SentenceSplitter().get_nodes_from_documents(documents)
for node in nodes:
    node.embedding = embed_model.get_text_embedding(node.text)   # 手动逐个算向量
storage_context.vector_store.add(nodes)
storage_context.docstore.add_documents(nodes)
storage_context.persist('./vector_store')

07 是"手工档"：自己给每个 node 填 node.embedding，再 vector_store.add(nodes)。它展示的是向量库内部在做什么，生产里不会这么写（逐条调 embedding，没有批量）。

# 来源：2605期 day04/源码/08-向量数据库存储.py
import chromadb
from llama_index.core import VectorStoreIndex, StorageContext
from llama_index.vector_stores.chroma import ChromaVectorStore

chroma_client = chromadb.PersistentClient("./chroma_db")      # 本地持久化；EphemeralClient 是内存版
chroma_collection = chroma_client.get_or_create_collection("quickstart")
vector_store = ChromaVectorStore(chroma_collection=chroma_collection)
storage_context = StorageContext.from_defaults(vector_store=vector_store)

index = VectorStoreIndex.from_documents(
    documents, storage_context=storage_context, embed_model=embed_model)
print(chroma_collection.count())
print(index.as_retriever().retrieve('萧炎的妹妹是谁？'))

# 之后复用已有 Chroma 库，不重新写入：
vector_store_new = ChromaVectorStore(chroma_collection=chroma_client.get_collection("quickstart"))
index_new = VectorStoreIndex.from_vector_store(
    vector_store=vector_store_new, embed_model=embed_model)   # embed_model 必须与建库时一致

[实测] 用 MockEmbedding 跑通：from_documents 写入 Chroma 后 collection.count() 等于节点数；换一个新进程用 from_vector_store 重载，retrieve 能返回带原文的节点。

[实测] 重要：Chroma 自带存文本，LlamaIndex 因此不再往 docstore 写节点。上面这套流程跑完，index.docstore.docs 是空的，chroma_db/ 目录里也没有 docstore.json。只做向量检索不受影响，但任何依赖 docstore 的功能（按 node_id 取节点、NEXT/PREVIOUS 遍历、父子回溯）都拿不到数据。解法见 §3.4。

3.3 索引存储：整体持久化（09-索引存储.py）

# 来源：2605期 day04/源码/09-索引存储.py
from llama_index.core import StorageContext, load_index_from_storage, VectorStoreIndex

index = VectorStoreIndex.from_documents(documents, embed_model=embed_model)
index.storage_context.persist("./vector_store_index")

new_ctx = StorageContext.from_defaults(persist_dir="./vector_store_index")
new_index = load_index_from_storage(new_ctx, embed_model=embed_model)
print(new_index.as_retriever().retrieve('古河是谁?'))

这是最省事的路径：默认内存三件套（docstore + 内存向量 + index_store）一起 persist，再用 load_index_from_storage 整体恢复。[实测] 恢复后检索正常，且因为用的是内存向量库，docstore 里有全部节点（对比 §3.2 的 Chroma 情形）。代价：向量存在 JSON 里，数据量大了加载慢，只适合小库和教学。

3.4 混搭存储：Redis + Chroma（10-文档数据存储.py）

# 来源：2605期 day04/源码/10-文档数据存储.py  [Redis 仅课件]
from llama_index.storage.index_store.redis import RedisIndexStore
from llama_index.storage.docstore.redis import RedisDocumentStore

# 文档存 Redis，向量存 Chroma，索引存 Redis
storage_context = StorageContext.from_defaults(
    index_store=RedisIndexStore.from_host_and_port(
        host="127.0.0.1", port=6379, namespace="novel_index"),
    docstore=RedisDocumentStore.from_host_and_port(
        host="127.0.0.1", port=6379, namespace="novel_docs"),
    vector_store=ChromaVectorStore(chroma_collection=chroma_collection),
)
index = VectorStoreIndex(nodes, storage_context=storage_context, embed_model=embed_model)
print(index.as_retriever(similarity_top_k=5).retrieve("小说中古河是个什么样的人？"))
print(index.as_query_engine(llm=llm).query("小说中古河是个什么样的人？"))   # 检索+生成
  • 两个 Redis 存储用不同的 namespace（novel_index / novel_docs），同一个 Redis 实例里互不干扰。
  • as_retriever 只检索返回节点；as_query_engine(llm=llm).query(...) 才会再调 LLM 生成答案。
  • [实测，推断到 Redis] 因为向量库是 Chroma，按 §3.2 的机制，这段代码里 RedisDocumentStore 不会收到节点，课件示例看起来"混搭了三个后端"，实际 docstore 是空的。要让节点真的进 Redis docstore，构造索引时加 store_nodes_override=True。本机实测（Chroma + 默认 docstore）：不加该参数 docstore=0 个节点，加了=20 个节点（与节点总数一致）；Redis 后端本机未装，没有直接跑。
index = VectorStoreIndex(nodes, storage_context=storage_context,
                         embed_model=embed_model, store_nodes_override=True)
