核心论点

3

Contextual Retrieval 的收益来自"给每个 chunk 补一句全局定位"这一动作本身，而收益大小取决于前缀是 LLM 生成还是规则拼接——两者不可混为一谈。 官方数字（top-20 检索失败率 5.7%→3.7%→2.9%→1.9%）全部出自 LLM 生成版 + hybrid + rerank 的组合，且官方明确否定启发式摘要（"very limited gains"）；本库 build_context_prefix() 的规则拼接版只是零成本的近似，不能引用官方降幅数字。到 2026 年这套方法已是成熟标配基线而非前沿，升级决策只应比较"规则版 vs LLM 版的实际 A/B 差距"，不值得再争论要不要做。

  • 动机（WHY）：chunk 是从整篇文档里切出来的碎片，脱离了文档级的全局语境——单独看一个 200 token 的片段，embedding 模型不知道它讲的是"哪本书的哪一章"。查询里带的词（书名/章节名/术语）常常只出现在文档别处，结果 chunk 的向量与 query 的向量天然错位，检索不到真正该命中的段落。Contextual Retrieval 的动机就是把"chunk 在全文中的位置"这一全局信息在入库时就补进每个 chunk，让 embedding 时的语义与 query 对齐。
  • 代价与权衡：补全局语境有两条路——LLM 给每个 chunk 生成一句"它在全文中的定位"（官方做法，准确但要花钱花时间），或用规则拼 source+heading 前缀（零成本但信息量少）。官方实测规则拼接/启发式摘要收益"very limited"，真正有效的是 LLM 生成版——代价是一次性入库成本约 $1.02/每百万 document tokens（靠 prompt caching 才压下来）。所以决策不是"要不要做"（2026 年已是标配基线），而是"规则版够不够用、要不要花钱升 LLM 版"。

是什么（定义与边界）3 个重点▾ 点开看本节重点
本节重点
  • 核心动作是"补全局定位"，前缀生成方式（LLM vs 规则）决定收益量级
  • ⚠️ 引用红线：35%/49%/67% 是 top-20 检索失败率的相对降幅，且全部出自 LLM 生成版——规则拼接版不许引用这些数字（见下文"官方数字"节）
  • ❌ 不管：排序质量（那是 rerank 的活）、召回上限（那是 hybrid 的活）——官方数字是三者叠加（Contextual → +hybrid → +rerank）才到 1.9%，不能把 67% 全归给 Contextual 本身
3

定义：Contextual Retrieval = 入库时给每个 chunk 追加一句 LLM 生成的"该 chunk 在全文中的位置与主题"前缀，再把带前缀的 chunk 送进 embedding，使向量携带全局定位信息。核心动作是"补全局定位"，前缀生成方式（LLM vs 规则）决定收益量级。

边界（本方法管什么、不管什么）：
- ✅ 管：解决"chunk 碎片化导致语义与 query 错位"的检索失败。
- ❌ 不管：排序质量（那是 rerank 的活）、召回上限（那是 hybrid 的活）——官方数字是三者叠加（Contextual → +hybrid → +rerank）才到 1.9%，不能把 67% 全归给 Contextual 本身。
- ❌ 不管：内容本身的准确性/过期治理（那是保鲜层的活）。
- ⚠️ 引用红线：35%/49%/67% 是 top-20 检索失败率的相对降幅，且全部出自 LLM 生成版——规则拼接版不许引用这些数字（见下文"官方数字"节）。

基线 = 纯 embeddings 的 top-20 检索失败率 5.7%（跨 codebase/fiction/arXiv/science 四类语料）：

方案 top-20 检索失败率 相对降幅
Baseline（纯 embeddings） 5.7% —
+ Contextual Embeddings 3.7% −35%
+ Hybrid（embeddings+BM25） 2.9% −49%
+ Hybrid + Cohere rerank 1.9% −67%

三条引用红线：
1. 35% / 49% / 67% 全是"top-20 检索失败率的相对降幅"（基线5.7%），不是整体查询错误率、不是 Recall 目标值。
2. 35% 是 Contextual Embeddings 单独、49% 是 hybrid、67% 是 hybrid+rerank —— 不是笼统的"Contextual 降35%"。
3. 官方否定启发式摘要：文档级通用摘要"very limited gains"、summary-based indexing"low performance" —— 所以规则拼接（source+heading拼接）不是官方方法，官方是 LLM 生成。

成本

3

一次性入库 $1.02 / 每百万 document tokens（假设 800-token chunks / 8k文档 / 每chunk约100 tokens前缀）。prompt caching 把整篇文档缓存一次（1.25x），每 chunk 读缓存（0.1x，90%折扣）—— 这是成本机制不是准确率变体。

与二手实测的对照（冷启动取舍）

据[一手源]：RAG优化-外部调研-20260929（方向 6，tier2）：该源转述 Anthropic 提出的做法是 indexing 时给每个 chunk 加 2–3 句上下文前缀（prompt 为 "Here is the full document: {doc}. Here is a chunk: {chunk}. Give a short context to situate this chunk"），并引 arXiv 2604.01733 实测为"consistent moderate gains，一次性成本"；其落地清单把前缀也列了"调用一次 LLM，或规则生成 本文档 = {filename}，所属决策 = {heading}"两条路，理由是 800 token chunk 切小后会失去上下文，前缀补回，对 162 chunk 冷启动友好。冲突裁决：规则前缀可作冷启动起点，但官方一手明确否定启发式摘要（very limited gains），按"一手官方 > 二手总结"的真值层级，规则版的收益只能说"补回了 source/heading 定位"，不能套用官方 35%/49%/67% 降幅；是否值得花钱升 LLM 版，仍以本库规则版 vs LLM 版的小批 A/B 为准。

2026 定位

3

Contextual Retrieval 到 2026 已是成熟标配基线（AWS Bedrock KBs 产品化、LlamaIndex cookbook 落地），不是前沿。前沿已转向：agentic/iterative RAG、训练型 contextual embeddings（arXiv 2505.24782）、late chunking（arXiv 2409.04701）。

怎么用

    bash source ~/ai-stack/bin/activate cd /mnt/c/MyData/Documents/wuyafang-l/rag/eval python3 ab_contextual_test.py # 规则版 vs LLM 版对照（参考报告 rag/Contextual-Retrieval-LLM-AB验证报告-20261026.md）

本库真实落地

2

2026-11-04 源码核对：路径 os.path.exists 全绿，代码块逐字摘自源文件（可 grep 复核）。行号以 rag/ingest.py 1594 行版本为准。

  • 本库真的有两条实现，不是一个概念：规则版 build_context_prefix()（rag/ingest.py L809）与 LLM 版 build_context_prefix_llm()（L825），由 CONTEXTUAL_MODE 切换，默认 rule：
    python # RAG_CONTEXTUAL_MODE=llm 启用LLM版, 默认 rule (规则版) CONTEXTUAL_MODE = os.environ.get("RAG_CONTEXTUAL_MODE", "rule") # rule | llm
  • 规则版前缀就是一句话模板（rag/ingest.py L822）：
    python return f"本文来自{source_name},主要讲{h}。"
    它不是官方方法——官方要的是「这个 chunk 在全文档里处在什么位置、起什么作用」，这是两回事，本库把它显式叫「规则版」就是承认这一点（rag/contextual_llm.py 文件头："规则版: 仅用文件路径+标题生成前缀, 零LLM成本但信息量有限"）。
  • LLM 版的前缀生成在 rag/contextual_llm.py：走 SiliconFlow（deepseek-ai/DeepSeek-V3，可用 RAG_CONTEXTUAL_MODEL 覆盖），带 data/contextual_cache.jsonl 缓存；失败降级为规则版，保证 ingest 不挂。
  • A/B 证据在本库，不在论文里：rag/eval/ab_contextual_test.py（对比 build_context_prefix vs generate_contextual_prefix_llm，指标 Recall@5）与报告 rag/Contextual-Retrieval-LLM-AB验证报告-20261026.md（成本口径 ¥7.75/15k chunks）。
  • 重要边界：ingest.py 里送 embed 的是 indexed = prefix + c，但写进 metadata 的 text 是 e["raw"]（不带前缀）。也就是说前缀只影响检索向量，不会进生成上下文——想知道「答案里为什么没有那段上下文」，看这里。

  • 和课件讲法的差异：课件把 contextual retrieval 讲成一个开关；本库的真实代价是「全库需要重灌一次 embedding」——前缀变了向量就变，registry 的 bge_version 就是用来防这类重灌风暴的。

  • 本库暂无：没有在 RAG_CHUNK_MODE=atomic + LLM 前缀的叠加组合上做过对照实验；A/B 报告的成本数字是估算口径，未按真实 token 账单核对。
