2.1 为什么是"混合检索"，而不是单路 dense

dense 擅长"意思相近但用词不同"（问"拒答机制"能召回"门禁"），但对专有名词、型号、ID 类查询很弱；sparse（关键词权重）正好相反。两路结果量纲完全不同（dense 是 1-dist ∈ [0,1]，sparse 是未归一的词权重、实测可 >1），直接加权求和必翻车——我们 10-14 就踩过：无关课件的 sparse 原始分 2.35 直接碾压 wiki 层霸榜 top1。所以用 RRF 只吃"排名"不吃"分数"，天然同量纲：

# rag/query.py::rrf_fuse —— 实测输出（可直接跑，见下方命令）
# dense 路: a#0 第1名, b#1 第2名；sparse 路: b#1 第1名, c#2 第2名；k=60
# b#1 = 1/(60+2) + 1/(60+1) = 0.032522  ← 两路都出现，稳居第 1
# a#0 = 1/(60+1) = 0.016393              ← 只有 dense 路
# c#2 = 1/(60+2) = 0.016129              ← 只有 sparse 路

cd /mnt/c/MyData/Documents/wuyafang-l && /home/wuyafang/ai-stack/bin/python - <<'PY'
import sys; sys.path.insert(0, '/mnt/c/MyData/Documents/wuyafang-l/rag')
from query import rrf_fuse
dense=[{"_id":"a#0","source":"wiki/x.md","chunk":0},{"_id":"b#1","source":"raw/y.md","chunk":1}]
sparse=[{"_id":"b#1","source":"raw/y.md","chunk":1},{"_id":"c#2","source":"wiki/z.md","chunk":2}]
for h in rrf_fuse([dense, sparse], k=60):
    print(h["_id"], round(h["rrf_score"], 6))
PY
# 预期输出: b#1 0.032522 / a#0 0.016393 / c#2 0.016129

代价：RRF 丢弃了分数的绝对大小，k=60 是压制头部排名影响的经验值（Cormack 2009 实验结论，本项目沿用）。要"分数敏感"的场景只能换加权归一融合，那需要先做分位数归一，我们没做，因为 RRF 已够用。

2.2 为什么 dense 和 sparse 必须共用一个 bge-m3 实例

历史方案是 dense 走 sentence_transformers、sparse 走 FlagEmbedding.BGEM3FlagModel，两个加载器在同进程抢同一份 snapshot 权重，后加载的那个 encode 出空——日志会从 dense top-0 + sparse top-100 变成镜像的 dense top-1000 + sparse top-0。2026-10-16 修复成 _get_m3_model() 单实例：一个 BGEM3FlagModel 同时吐 dense_vecs 和 lexical_weights，查询侧与索引侧（ingest.py 的 get_bge_model()）严格同源，向量空间与 token id 才对得上。

为什么不用 Ollama 提供 embedding：embedding.eval_mode: true 时 dense 走 localhost:11434，但实测 Ollama 里只有 qwen3 没有 bge-m3，服务 inactive → Connection refused → dense 路空。本地 snapshot 是唯一确定可用的路径（~/.cache/huggingface/hub/models--BAAI--bge-m3/snapshots/5617a9f61b028005a4858fdac845db406aefb181，已验证含 colbert_linear.pt 与 sparse_linear.pt）。

2.3 为什么必须 rerank，且为什么 simple_fact 也不能跳过

双塔（bi-encoder）检索为了快，query 和文档分开编码，精度有天花板；cross-encoder（reranker）把"问题+整段"拼在一起过模型，慢但准。实测区分度极高：域外问题 0.0021 vs 正样本 0.9924，这个 0.45 阈值就是我们的门禁主路径。

10-15 之前 simple_fact 路由跳过 rerank，只剩 dist_threshold=0.60 兜底，而 bge-m3 给域外问题的 dense dist 实测只有 0.37~0.43，永远 < 0.60 → 门禁形同虚设，答非所问。现在三条路由统一过 rerank（simple_fact_top_n: 10）。

代价：rerank 一次 top_n=10 成对打分，CPU 上约 0.5~2s，且首次加载 reranker 模型约 1 分钟；所以配了 data/rerank_cache/（md5 缓存）和 timeout: 60.0 熔断——超时返回 None，回退 RRF 排序而不是崩。

2.4 为什么先建评估、再动检索（Fix-Order）

调参最贵的成本是"不知道这次改动是变好还是变坏"。我们踩过三次：golden 集因 wiki 目录重组腐烂两次（10-09 扁平→子目录 55/76 引用失效；10-14 合并 10 条死标签），第三版才加 --check-golden 守卫。顺序永远是：评估口径 → 检索 → 生成，反过来就是凭感觉调。RAGAS 四指标 + golden-q 56 题就是这把尺子。

2.6 为什么用"小块检索、父块回灌"，而不是拿大块直接检索

检索希望块小：块越小，这段话的语义越集中，dense 向量被无关内容稀释得越少，
Recall@k 越容易做高。生成希望块大：大模型只看 100 字的碎片，很容易断章取义，
拼出来的上下文缺前后条件。两头都要，就拆成两层——检索用小块（本项目 Markdown
标题切出的 163~506 字符段，实测见步骤 4），生成时用 parent_text 回灌父块
（split_parent_chunks() 的 chunk_size=PARENT_CHUNK_SIZE、chunk_overlap=PARENT_CHUNK_OVERLAP）。

在代码里的落点是两处，缺一处就退化：

    for h in hits:
        h["_rerank_text"] = h.get("parent_text") or h["text"]

rag/ingest.py::find_parent_chunk(chunk_text, parent_chunks)
    # 用块首 120 字符在父块列表里回溯，命中返回父块全文，找不到退化为第一个父块

代价：chunks.jsonl 每条要多存一份 parent_text，当前文件 38761631 字节
（约 37MB，18599 条），内存里做内容指纹去重时也要一起读；换来的是生成端上下文完整。
为什么不干脆全用 800 字符块检索：同样召回 4 条，800 字符块给模型的是 3200 字符
噪声，200~300 字符块给的是 800~1200 字符高密度证据，rerank 的成对打分也更准——
这也是 Chunk大小怎么选 的结论来源。

这个域是什么

RAG（Retrieval-Augmented Generation，检索增强生成）解决一个非常具体的问题：大模型（LLM）不知道你私有文档里的内容，而且会一本正经地编。做法是先把你本地的 Markdown/PDF 文档切成小块、转成向量存进向量库；用户提问时，先去库里捞最相关的几段，再把这几段塞进提示词（prompt）让模型"照着材料回答"。

一句话记住它的边界：RAG 改善的是"模型手里有没有这份材料"，不是"模型聪不聪明"。

需要先会什么（缺哪块补哪块，不要全学完才动手）

  1. Bash 基础：会 cd、ls、grep -n、cat，会看退出码（echo $?）。
  2. Python 虚拟环境：会 source <venv>/bin/activate 或直接用绝对路径 <venv>/bin/python。本项目所有命令必须用 /home/wuyafang/ai-stack/bin/python（Python 3.14.4）——系统 python3 没装 chromadb，直接跑会 ModuleNotFoundError: No module named 'chromadb'（本文实测过）。
  3. 编辑 YAML：rag/config.yaml 是全管线唯一配置入口，缩进用空格、不能用 Tab。
  4. SQLite 基本查询：Chroma 的数据落在 rag/index/chroma.sqlite3，验收经常要直接查表。
  5. 不用先会的：分布式、GPU 推理、微调——本方案全程 CPU 本地跑，bge-m3 加载约 1.6GB 内存。

定义

企业级 RAG = 一条带反馈回路的流水线，而不是一个"向量搜索函数"。 它的完整生命周期在我们库里对应这些物理文件：

阶段 落地文件 干什么
数据准备 raw/（16842 chunk）、wiki/（1706）、ontology/（51） 三层语料：外部知识 / 人读权威条目 / 术语对齐
分块 rag/ingest.py 的 split_file() Markdown 标题切 + >800 字符段 RecursiveCharacter 细切（chunk_size=800, chunk_overlap=100）
嵌入 rag/ingest.py 的 encode_with_sparse() bge-m3 一次 encode 同时出 dense(1024) + sparse(lexical_weights)
建库 rag/index/chroma.sqlite3 Chroma collection wuyafang_kb，hnsw:space=cosine，当前 18599 条
检索 rag/query.py 的 retrieve_hybrid() dense top-1000 + sparse top-100 → RRF(k=60) 融合

进了 Chroma 之后 metadata 还会多出 sparse_vec（sparse 权重的 JSON 串，检索时
在 Python 里点积打分）、chars、bge_version、chroma:document（正文本体）等 key。
查询这些字段必须查 embedding_metadata 表（列是 id/key/string_value/int_value/float_value/bool_value），

解决什么

  1. 可溯源回答：答案后面能挂 source + chunk 编号，用户可以点回原文。
  2. 拒答：库里没有的内容明说"未检索到相关片段"，而不是编（gate_node 就是干这个的）。
  3. 私有知识上桌：18599 个 chunk 全在本地磁盘，不外传原文。
  4. 可评估：换任何参数都能用同一把尺子（golden-q.jsonl 56 题）量出变好还是变坏。

不解决什么（越界即返工）

  • 不解决"模型推理能力"：问题需要多步计算、长链推理时，换更强的 LLM 才是正解，调检索没用。
  • 不解决"原始资料质量"：PDF 乱码、表格切散（我们 102/119 篇含表格且 ingest.py 无表格逻辑，属 P1 缺口）、OCR 错字，进库前就得修。
  • 不解决"权限与多租户"：Chroma 无行级权限，谁能查库就能查全部内容。

  • 预期输出：ss 打出一行 LISTEN 0 2048 127.0.0.1:8770 0.0.0.0:*（本文实测）；server 侧访问日志出现 client=<名> tool=search_knowledge query=<前40字> hits=<n> ms=<耗时>——验收以 server 日志为准，不采信客户端自报。首查慢是正常的（首次加载模型 1-2 分钟，实测一次 search_knowledge 109s），验收 timeout 给足 ≥300s。
  • 常见错误：照 MCP 1.x 记忆写 FastMCP → 2.x 里已改名 mcp.server.mcpserver.MCPServer，import 直接失败；客户端 streamablehttp_client 这个名字不存在（正确是 streamable_http_client）。
