核心论点

3

检索短板不能靠换 embedding 硬扛，要靠"并行检索→RRF 融合→cross-encoder 重排"的流水线补齐——arXiv 2604.01733 实测 hybrid+rerank 的 Recall@5 达 0.816，比纯向量检索高 39%。RRF 只做排名融合、回避了不同检索器分数不可校准的难题；比"再调一次模型"收益更大的是 chunk 元数据（heading path / source file）与 256-512 token 的递归分块。

  • 两阶段流水线：BM25 + dense 并行检索 → RRF 融合 → cross-encoder rerank。RRF 用排名而非原始分数融合，天然免疫稠密分与 BM25 分不可比的问题。
  • 分块策略：256-512 tokens 递归字符切分（RecursiveCharacterSplitter）为主流；hierarchical chunking 解决"检索要小块、生成要大上下文"的矛盾。
  • 据[一手源]：RAG优化-外部调研-20260929（arXiv 2604.01733 基准，23,088 queries / 7,318 docs，10 种检索策略）：Recall@5 三档对照为 dense-only 0.587 → hybrid-only 0.695 → hybrid+rerank 0.816，即 rerank 在 hybrid 上再 +17.4%、整条链比 dense-only +39%；MRR@3 从 0.433 升到 0.605。补召回（hybrid）和精排（rerank）两步各自都有独立收益，不能只上一步。
  • 据[一手源]：RAG优化-外部调研-20260929（StackAI fix-order playbook，调优顺序口诀）：召回差时按 chunking + metadata（heading / section path / version / date）→ hybrid → candidate size → 最后才换 embedding 模型 的顺序排查；元数据优先于换模型是确定性收益。
  • 据[一手源]：RAG进阶调研-6方向-Top3落地方案-20260928（混合检索数据，tier2 博客实测）：纯向量 recall@10 约 78%，纯 BM25 约 65%，RRF 混合后约 91%，且无需任何分数归一化；纯向量在精确匹配/缩写/产品 ID 类 query 上 miss 30–40%。公式 RRF_score(d) = Σ 1/(k + rank(d,r))，k=60（LangChain EnsembleRetriever 默认硬编码）；不能直接相加 cosine（0–1）与 BM25（0–30+）分数；默认权重 0.7 向量 / 0.3 BM25；混合只加 10–30ms，远低于 rerank 的 50–150ms。bge-m3 的 sparse 输出可直接当"学习版 BM25"，省掉一个 ES 索引，比单独建 BM25 索引工程量小一半。
  • 据[一手源]：RAG进阶调研-6方向-Top3落地方案-20260928（重排选型与门控）：标准链路 = 召回 top-30 shortlist → bge-reranker-v2-m3 交叉编码 → 取 top-4/5，硬 query 上 recall@5 +5–15 点、延迟 +50–150ms。模型取舍：bge-reranker-v2-m3（568M，MIT，MTEB Rerank 60.4，多语言默认，RTX4090 上 100 对约 90ms）；要质量用 v2-Gemma（9B，64.5 但约 1050ms）；要延迟用 Jina v2 base（28ms）或 mxbai-base（24ms）。chunk 控制在 512 token 内保持延迟可预测；可用已有阈值门控——dense top-1 过线的 query 跳过 rerank，低置信才触发，省算力。
  • 据[一手源]：RAG进阶调研-6方向-Top3落地方案-20260928（查询改写层）：默认组合"对话式改写 + HyDE"约加 150ms TTFT，覆盖大部分失败模式；生成 3–6 个 rewrite（同义词扩展 + 意图分解 + 改写，叙事文档加 HyDE）。路由口诀：factoid 短 query 上 HyDE（桥接问题-答案语义鸿沟）；多面/多跳 query 才走子问题分解并行检索；raw query 相似度已高于阈值就跳过 HyDE。多 query 合并时每个 rewrite 取 top-5~10，按 chunk hash 去重并记录哪个 rewrite 命中；k 别拉到 50，那是 index/chunking 的锅。
  • 据[一手源]：RAG进阶调研-6方向-Top3落地方案-20260928（分块实测）：recursive 400 token 时检索 recall 85–89.5%；semantic chunking 检索 recall 91–92%（+2–3 点）但每句都要 embedding、ingestion 成本高；另一口径是端到端答案准确率（FloTorch/Vecta benchmark），recursive@512 为 69%、semantic chunking 为 54%（平均切出 43 token 碎片），两组指标不同，不可直接对比；先做 recursive@512 + 10% overlap 的 A/B 再考虑 semantic。分析型/多跳问题用 512–1024，factoid 用 256–512，PDF 分页文档用 page-level，代码用语言特定 splitter。
  • 元数据优先于模型：每个 chunk 带 heading path / source file / 层级元数据，收益大于换 embedding 模型。
  • 知识库单元设计（FDE 场景）：以带上下文的完整决策记录（发票+采购单+合同条款这类成套材料）为检索单元，输出附引用、强制暴露歧义点；MIT 数据 95% 企业 AI 试点失败源于未固化工作流逻辑与监控层。
  • 工具分工：Chroma 适合百万级向量内本地开发；DeepEval 做 PR 拦截测试，RAGAS 负责生产监控；纯向量适合企业文档搜索，Graph RAG 在法律/合规类关系推理场景占优。

是什么（定义与边界）

3

定义：混合检索流水线 = "并行检索（BM25 + dense）→ RRF 融合 → cross-encoder 重排"的两阶段检索架构；RRF（Reciprocal Rank Fusion）用排名倒数融合多路检索结果，回避不同检索器分数不可校准的问题。本篇是其方法论笔记：机制拆解、为什么成立、最小流水线代码与阈值。

边界：
- ✅ 管：多路检索融合（RRF）、重排（cross-encoder）、分块与元数据的协同原则、评测三件套分工。
- ❌ 不管：embedding 选型（Embedding模型选型对比）、chunk 大小参数（Chunk大小怎么选）、图谱路线（GraphRAG最小示例）。
- ⚠️ RRF 只解决"多路分数不可比"的融合问题，不提升单路召回质量——单路召回差（如 sparse 没启用）时 RRF 救不回来，先补召回再融合。

最小流水线（LangChain + Chroma/Qdrant）：

from langchain.retrievers import EnsembleRetriever
from langchain_community.retrievers import BM25Retriever
# 1) BM25 + dense 并行
ensemble = EnsembleRetriever(retrievers=[bm25, dense], weights=[0.4, 0.6])
# 2) cross-encoder 精排（top-20 → 取 top-4 送生成）
reranker = CohereRerank(model="rerank-v3.5", top_n=4)  # 或 bge-reranker-v2-m3 本地
  • 分块：RecursiveCharacterSplitter(chunk_size=256~512 tokens, overlap≈15%)，每个 chunk 注入 heading_path/source_file 元数据。
  • 检索进位：hybrid 取 top-20 → rerank 收敛到 top-3~5 上下文。
  • 据[一手源]：RAG进阶调研-6方向-Top3落地方案-20260928（权重口径差异）：上面示例的 weights=[0.4, 0.6] 是 EnsembleRetriever 的加权写法，该源的默认口径是 RRF k=60、向量 0.7 / 稀疏 0.3；两者都是起点，权重要用自己的 golden query 集校准，不要照搬。进阶调研给出的最小落地序是"bge-m3 开 sparse 输出 + RRF（预期 recall@10 约 78% → 约 91%，+10–30ms）→ 加 rerank 短路径（硬 query recall@5 +5–15 点）→ 低置信 query 才触发改写"，按投入产出比排序。
  • 据[一手源]：RAG进阶调研-6方向-Top3落地方案-20260928（方向 6，术语表代替 ontology）：同一实体多种叫法（别名/缩写/英文名）是中文个人库最常见的召回盲区；轻量解法是建"规范名 → 别名/同义词"术语表，在 query 侧做术语扩展后再 embedding，可与查询改写合并成一个节点。归一化会轻微打乱 cross-encoder 排序，rerank 时要用原始文本而非归一化文本。上 GraphRAG/ontology 之前先做 ingestion 清洗审计（去 tab/空白/页眉页脚）——SEC 10-K 实验里图抽取近零的真因是文本被污染，ontology 救不了上游坏掉的实体抽取。
  • 评测三件套：DeepEval（PR 阶段拦截）+ RAGAS faithfulness（生产监控）+ Langfuse（trace 与成本）。
  • 据[一手源]：RAG优化-外部调研-20260929（方向 4，生产评测 pattern，genai.qa 2026）：Langfuse 捕获全部生产 trace（question / retrieved context / answer / metadata）→ RAGAS CronJob 每小时采样 1–5% trace 算 faithfulness + context precision + answer relevance 并回写 Langfuse → DeepEval 在 CI 拦 golden-question 回归 → Grafana 看 7 天滚动平均，faithfulness < 0.80 触发告警。口诀："DeepEval 在 PR 时抓回归，RAGAS 随时间监控漂移"。faithfulness 是 reference-free（claim 分解，不需要标准答案），适合个人库冷启动；起步只需 20 条 golden question + RAGAS 离线算 baseline，约半天。
  • 据[一手源]：RAG优化-外部调研-20260929（方向 1 & 6，内容侧）：每个 chunk 带 source_file / heading_path / date / chunk_type(decision|error|note|diary) / decision_id，让"找 9 月 15 日的决策"从模糊匹配变精确过滤；agentic chunking（LLM 定边界）质量最高但贵 10–50×，个人库不值得；chunking 不是一次性配置，按生产 query log 每季度回顾一次。
  • 不要一上来上 Graph RAG：关系推理明确（法律/合规/合同）才用，普通文档搜索纯向量+hybrid 足够。

本库真实落地（源码核对，2026-11-04）

  • 本库的 RRF 实现只有 20 行，公式与课件一致（rag/query.py L428，本次读源码）：
    python def rrf_fuse(rank_lists, k=None, weights=None): """Reciprocal Rank Fusion""" k = k or CONFIG["retrieval"]["rrf_k"] ... for rank_idx, h in enumerate(rank_list, start=1): hid = h.get("_id") or (h["source"], h["chunk"]) scores[hid] = scores.get(hid, 0.0) + w / (k + rank_idx)
    k 取配置 rrf_k: 60（config L64）；_id 是 source#chunk，融合单位是 chunk 不是文档。
  • 本库的流水线比课件多两个环节（本次实跑日志可见）：
    | 环节 | 位置 | 本次证据 |
    |---|---|---|
    | 三路召回（dense + sparse + 图谱实体直取） | _do_retrieve / _linked_chunk_hits | merged top-435 |
    | RRF 融合 | rrf_fuse | top_rrf=0.0164 |
    | 层权重（wiki/×2.0、ontology/×1.8） | weight_by_tier + config L151-156 | top1=wiki/A2A协议调研-... |
    | rerank（熔断后回退） | rerank() | [rerank] 熔断: 回退排序 top-3 |
  • 一个反直觉的调参结论（config L96-104 注释）：图谱命中「无条件置顶」会让 R@1 从 45.1% 掉到 19.6%（51 条正样本），所以改成 graph_slot_mode: after_top1——融合之后还有一步「怎么放」，放错位置比不放更糟。
  • 和课件讲法的差异：课件讲 RRF 只讲融合公式；本库的经验是 RRF 只解决「谁排前面」，解决不了「层之间的权重」与「特殊片段的落位」，后两者要靠单独机制。
  • 本库暂无：没有对「RRF k 值」做过扫描实验（固定 60，沿用文献默认）；融合权重 weights 参数已实现但当前调用未使用。
