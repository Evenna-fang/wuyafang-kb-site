需求访谈与问题定义：从“想要一个AI”走到可验证的业务契约

阅读定位：承接方法论全景，输出供交付门禁和技术选型使用的问题契约。文中访谈节奏、样本安排、表格与案例均为本文建议；书籍依据限于实际取得的目录与划线，不伪装成全书总结。数字示例不代表行业基准。

WHY

2

为什么需求访谈不是确认功能清单

3

客户提出的往往是已经想象好的解决办法，例如“做一个聊天机器人”“给系统加一个导出按钮”“让智能体自动审批”。这些请求可能合理，却没有告诉我们原先的任务是什么、问题出在哪里、失败代价有多大。如果工程团队直接把请求翻译成待办清单，就会过早锁定技术方案；后续即使实现完全正确，也可能解决了不值得解决的问题。

《持续交付2.0》的本地划线把正确需求与客户真正的问题关联起来，而非等同于客户提出的方案；《FDE：AI落地实战指南》的划线提醒，封闭问题容易只验证工程师原有假设。[书1][书2] 本文将这两点转为访谈纪律：先问具体事件，再问解释和期望；先观察现状，再展示方案；先寻找可能推翻假设的材料，再寻找支持材料。访谈的成果是降低决策不确定性，不是让客户同意我们的演示。

以报表助手为例，“写 SQL 很慢”可能只是表面。真正耗时的也许是确认收入是否含退款、哪张表覆盖最新组织结构、谁能批准跨部门口径。若没有识别这些问题，再好的语言转 SQL 也只会更快地产生争议结果。课件中从表结构生成联合查询的实操帮助我们理解“输入是什么”，但实际需求还要定义“哪个业务口径才算正确”。[课1，本文扩展]

访谈也不是让客户替团队写产品规格。用户擅长描述自己的工作和困扰，不一定能准确估计未来采用率或技术可行性。工程师应主动承担证据整理、因果假设和方案比较，同时尊重用户对工作情境的知识。好的访谈既不把客户的话当作不可质疑指令，也不因为团队懂技术就认为更懂业务；双方分别贡献材料，在可验证的问题上形成共识。

WHAT

2

分清请求、需要、事实、假设与约束

3
2.1 五类信息不能混写3 个重点▾ 点开看本节重点
本节重点
  • 请求是受访者希望获得的功能，例如“自动生成周报”
  • 需要是请求背后的工作目的，例如“在会议前判断哪些订单可能延期”
  • 事实是有具体证据支撑的描述，例如“在某次订单复盘中，需要切换三个系统核对承诺日期”
3

请求是受访者希望获得的功能，例如“自动生成周报”。需要是请求背后的工作目的，例如“在会议前判断哪些订单可能延期”。事实是有具体证据支撑的描述，例如“在某次订单复盘中，需要切换三个系统核对承诺日期”。假设是待验证解释，例如“系统切换是主要延迟来源”。约束是当前不允许改变的边界，例如“客户合同数据不得进入未经批准的外部服务”。

记录时给每条信息单独分类。一句“销售都不看周报，因为内容不准”至少包含覆盖全体的泛化、原因解释和质量判断，不能直接标成事实。应追问谁、哪份周报、哪次决策、哪些内容不准、造成了什么后果。无法补足的信息不必删除，但要保留为观察或假设。这样做不是挑剔措辞，而是避免把一句情绪化评价变成昂贵的架构决定。

2.2 问题定义的最小单位是业务事件

3

不要只写抽象角色“运营人员”，应写清角色在什么触发条件下，要对什么对象采取什么动作。例如“运营人员在接到客户催单后，核对订单、库存与物流状态，决定继续承诺还是升级异常”。事件有开始和结束，才能界定时长；对象有状态和标识，才能对齐数据；动作有权限和后果，才能讨论自动化边界。

Palantir 的 Ontology 文档用对象、属性、关系和动作连接数字资产与现实组织。[业2] 本文将这个思路用于访谈笔记：出现一个业务名词，追问它的标识、状态与来源；出现一个动作，追问触发条件、执行权与结果。这里并不要求现场建设本体平台，而是用对象意识防止“同名不同义”和“看得到就能修改”的误解。

2.3 需求是可修改的契约，不是一次签字后的永久真理3 个重点▾ 点开看本节重点
本节重点
  • 问题契约应包含受影响人群、任务情境、现状证据、目标结果、约束、范围、非目标、验收方法和开放问题
  • 它比需求清单多了“为什么”，比愿景口号多了“如何证伪”
  • 客户确认后，团队仍然可以依据新证据修改，但必须记录修改原因和受影响决定；不能一边口头扩大范围，一边沿用原来的成本与成功承诺
3

问题契约应包含受影响人群、任务情境、现状证据、目标结果、约束、范围、非目标、验收方法和开放问题。它比需求清单多了“为什么”，比愿景口号多了“如何证伪”。客户确认后，团队仍然可以依据新证据修改，但必须记录修改原因和受影响决定；不能一边口头扩大范围，一边沿用原来的成本与成功承诺。

一个合格的问题陈述可以按此形式书写：某类人员在某情境下，为完成某任务，因已观察到的障碍承受某损失；拟在约束内验证某种改进，使用某口径判断是否有效。若损失尚无可靠数据，应写“基线待测”，并安排补测动作，而不是为了让文档显得完整填上推测数字。未知是需要管理的状态，不是应当隐藏的缺陷。

HOW

2

第一步：访谈前把研究问题和招募逻辑写清楚

3

3.1 用决策倒推需要知道什么

首先列出访谈之后必须做出的决定。例如是否值得投入验证、先做哪个流程切片、是否需要真实写入、数据能否合法取得。再为每个决定列出当前最大未知与可改变决定的证据。这样可以避免在一小时里讨论大量有趣细节，却没有回答任何影响方案的关键问题。研究问题是团队要弄清的事，不能原封不动变成对用户的抽象考题。

例如团队的研究问题是“自动化的主要风险来自何处”，用户问题可以是“请带我看最近一次需要退回重做的订单”“当时谁发现问题，后来如何修正”。如果研究问题是“生成答案是否必须可追溯”，可以问“上次有人质疑结论时，你需要拿出什么材料”。具体事件比“你重视可解释性吗”更容易产生可用证据。

3.2 按差异招募，不只找最支持项目的人

至少覆盖日常操作者、流程负责人、数据维护者、风险或权限负责人。若角色存在关键差异，还要覆盖新手与熟手、不同班次、不同地区或不同工作负荷。本文不规定“访谈五个人就够”，因为覆盖需求取决于差异结构。判断是否继续，应看新增访谈是否仍改变问题、约束或例外清单，而不是机械凑固定人数。

赞助人可以介绍流程，但不能替代实际使用者。熟练人员可能记住了文档中没有的捷径，新手则能暴露概念和界面障碍；管理者看到的平均情况可能掩盖峰值压力。还应允许负面意见独立表达，避免上下级同时在场让受访者只说“流程没有问题”。样本结构和招募偏差应在结论中显式说明。

3.3 准备材料与同意机制

GOV.UK 的深度访谈指南要求围绕研究问题设计讨论提纲，采用开放、中性的问法，关注真实故事，并取得知情同意与安全保存研究数据。[业1] 本文据此建议在邀请中说明研究目的、参与方式、是否录音、谁能接触记录和保留期限。没有录音授权就使用笔记，不以“方便整理”为由默认记录一切，更不要把敏感原始材料提交给未经批准的外部模型。

准备一份脱敏任务样本、当前流程草图和待核对术语表即可，不必带完整方案演示。若需要屏幕观察，应请参与者使用批准的测试或脱敏环境，并允许随时暂停。数据无法展示时，可以先看结构、字段说明或合成样例，但要标清它们与真实分布的差距。证据需求不构成扩大访问权限的理由。

第二步：沿着最近一次真实事件追到边界

3

4.1 开场建立安全感，不先推销方案

可用这样的开场：“今天主要理解你怎样完成这类任务，不考核个人表现，也不要求你接受任何工具。请以最近一次实际发生的事情为例，可以跳过敏感内容。”随后请对方说明职责与任务背景。不要在开场用“我们准备给你省一半时间”制造期待；这类承诺会改变后续回答，也可能让参与者把研究看成项目验收。

访谈建议按情境、事件、动作、例外、代价、约束、成功定义逐步展开。时间安排应服从任务复杂度，不照搬某个固定时长。若对方带出关键异常，可以深入，不必为覆盖全部问题而强行打断。提纲是研究的一致性工具，不是问卷；若没有真正理解一个事件，问完所有题也不算取得证据。

4.2 把“通常”还原成一次过程

当受访者说“通常要查很多资料”，追问“请看最近一次，你先打开什么，接着依据什么决定下一步”。逐步记录输入、操作、系统、等待、判断与输出。特别留意从一个系统复制到另一个系统、离开系统找人确认、重新录入相同字段等动作，因为它们往往暴露接口或口径缺口。不要立刻把每个手工动作都认定为浪费，某些复核正是风险控制。

可用“你刚才为什么停在这里”“如果没有这项资料会怎样”“另一个人会用同样方法吗”来追问判断依据。对方说“凭经验”时，继续问最近一次反例、最早看到的信号和可能改变判断的条件。目标是把隐性知识转为条件化规则，而不是强迫专家把所有经验变成绝对判断。无法解释的部分可以保留为需要人工负责的环节。

4.3 用反例检查解释，不用封闭问题取悦自己

“如果加一个 AI，你会用吗”通常只能得到礼貌态度，不能证明采用。可以改为“你现在用什么替代办法”“哪种情况你宁愿自己做”“上次引入新工具时卡在哪里”。“是不是因为系统慢”会把原因塞进问题，应改为“哪一步最难推进，最近一次发生了什么”。书摘关于封闭问题的提醒，在这里具体体现为不提前提供答案。[书1，第5章划线]

也要追问没有发生问题的事件。若同类任务有的快速完成、有的反复返工，差异可能来自资料完整度、熟练程度或审批条件。只研究失败会夸大问题频率，只研究明星用户会掩盖真实门槛。正反事件共同帮助建立适用范围：什么情况下需要助手，什么情况下现有方式足够，以及什么时候必须拒绝自动化。

4.4 发现业务代价与实际优先级

对“很痛”的问题，追问频率、单次损失、涉及人数、错误后果和替代成本。注意让受访者区分估计与记录。例如“每天十几次”是回忆，不等于系统日志计数；“浪费两小时”可能包含并行等待，不等于可回收劳动时间。可以请对方指出现有记录入口，之后由授权人员核对，而不是在访谈现场把估计写成商业论证的硬数字。

优先级不只由频率决定。低频但后果严重的错误，可能必须先通过规则、权限或人工控制解决；高频但影响小的问题，也可能不值得增加复杂系统。建议综合考虑价值、可干预性、证据可得性和风险，不机械相乘出一个看似精确的排名。若多个部门利益冲突，应交由明确的业务裁决人协调，不能让技术评分掩盖组织决策。

第三步：把流程、数据、权限与例外一起建模

3

5.1 一张事件表胜过抽象流程口号

观察维度 要记录的内容 要继续追问的问题
触发与结束 什么开始任务，什么算完成 是系统完成还是用户真正得到结果
对象与口径 订单、客户、日期、状态等定义 相同字段在不同部门是否同义
判断与动作 人怎样选择下一步 谁允许执行，什么条件必须升级
时间与等待 处理时间、排队、返工 哪些步骤并行，哪里是瓶颈
数据与来源 原始系统、版本、更新责任 谁能解释缺失、冲突和过期
例外与后果 少见但重要的异常 如何发现、接管、恢复与追责

这张表并不是要求受访者填写全部字段，而是研究人员在访谈后整理。遇到无法核实的部分，标出待访谈角色与需取得的材料。数据来源与业务口径要并排记录：同一指标可能在数据库里能查到，却仍然没有业务共识。技术可访问性与语义正确性是两个独立问题，不能只靠数据库连接成功宣布需求已清楚。

5.2 需求数据不等于索取客户整库

对于 SQL 场景，可以先取得经批准的表结构、字段释义、脱敏样本和典型问题。课件里的生成器依赖表结构作为上下文，但生产发现还需要了解主键、关联关系、时间口径、逻辑删除、租户过滤与数据更新频率。[课1，本文扩展] 若这些信息缺失，应写“数据语义待验证”，不能把字段名称相似当作业务等价。

对于知识问答，应核对资料版本、发布流程、撤回机制、角色可见范围与答案争议由谁裁决。对于工具代理，应列出可读与可写系统、业务参数、授权链与重复执行后果。不要在首次访谈中索要密码或密钥；需求资料只记录访问方式和责任人，由既有安全流程提供凭据。权限问题本身就是需求，不是开发阶段顺便补的配置。

5.3 合规问题先定用途，不凭行业标签猜义务

应询问服务面向谁、在哪里使用、处理哪些数据、是否影响个人权益、数据是否跨域或跨境，以及谁负责合规确认。不能因为“金融行业”就断言所有数据都不得外发，也不能因为“企业内部”就断言一切豁免。具体适用规则需要授权法务或合规负责人核验正式法规与合同。本文只提供提问框架，不将旧碎片中的备案周期、罚款数字或量化门槛当现行法律建议。

当业务需要与现有权限冲突，例如希望查询跨部门资料而未获授权，应把冲突写入约束清单并暂停相关样本收集。可以在不接触敏感内容的条件下继续流程观察、合成数据验证和方案比较。访谈方法的专业性包括知道哪里不能继续，不是为了尽快出方案而绕过组织边界。

第四步：从材料形成可反驳的问题陈述

3

6.1 事实、解释、决定分层整理

给原始记录分配事件编号，形成“事实—出处—解释—待验证”四列。事实保留原情境，解释可以多种并存，决定则引用所依据的事实。比如三次查询结果被退回是事实，“术语定义不一致”是解释，“先建立指标口径表”是决定。若后续发现退回其实是数据过期，保留事实而修订解释与决定，不必把整段历史重写成团队一开始就知道答案。

采用跨角色复核时，不把所有访谈细节公开给所有参与者。可以共享脱敏流程和问题摘要，请各角色纠正与自身职责有关的部分。个人抱怨、敏感评价和身份线索应控制传播范围。研究需要组织信任；一次不当转发可能使后续参与者不再愿意谈真实困难，进而破坏整个项目的证据质量。

6.2 建立基线与目标，但不捏造精度

首先定义统计单位：一次咨询、一个案件还是一名用户一周。再定义起止点：从任务创建到首次可用结果，还是从打开界面到提交答案。记录样本选择、时间窗口、被排除的任务以及缺失数据。若样本仅覆盖白天常见任务，应明确不能代表夜班和高风险异常。不同口径的前后数字不可直接比较，尤其不能用平均时长掩盖长尾等待。

目标应同时包含主要收益、质量护栏和运营护栏。例如希望缩短资料核对时间，同时保持错误升级可追踪、不增加权限泄露和专家复核负担。具体阈值由现场基线和风险承受度确定。主观质量可以用带例子的评分量规；确定性边界则用明确通过失败规则。它们在第三篇转成门禁，而不应在访谈时被模糊合并成“满意度达到很高”。

贯穿案例：报表需求如何从功能请求变成验证任务

3

以下为构造案例，不引用客户实绩。部门提出“用 AI 自动写经营分析 SQL”。首次访谈只问想要哪些图表，团队得到几十条功能；第二次改为复盘最近一次经营会议，发现争议集中在收入是否扣退款、组织调整后客户归谁、何时算订单完成。问题从“不会写查询”转成“查询与经营口径无法稳定对应”。

团队分别观察分析师、业务负责人和数据维护人员。分析师抱怨字段难找，业务负责人关注会议中结果不一致，数据维护者指出历史表更新滞后。三种叙述没有互相否定，而是构成同一价值流的不同层。团队保留“自然语言能降低查询门槛”的假设，同时新增“必须先明确指标与时间口径”的约束，不再把所有问题归因于提示词不够详细。

首个验证切片限定为一类经过批准的经营指标，只读查询、固定租户过滤、输出可复核依据、不自动形成对外承诺。对照组不是另一个更强模型，而是已有 SQL 模板和口径说明。验证一方面检查结果语义，另一方面记录业务人员能否识别适用范围和异常。若模板已覆盖全部高频需求，团队应允许结论是“先建设指标契约，不需要开放式代理”。

三源在这个决定里承担不同职责：课件给出表结构与问题组合的实现路径；书籍提供从真实问题出发和避免局部优化的提醒；GOV.UK 的访谈原则促使团队用实际事件和中性追问收集证据；Palantir 的对象语义帮助梳理指标、组织与动作关系。[课1][书1][书2][业1][业2] 最终的问题契约不是多段摘抄，而是一个可以拒绝无效技术投入的明确判断。

常见失败、纠偏与交接标准

3

只访谈经理的失败信号是流程描述过于整齐、没有真实异常；补充一线观察。访谈一开始展示 Demo 的失败信号是后续意见都围绕界面功能；另开不带演示的发现访谈。只收愿望的失败信号是出现大量“将来应该”，没有过去事件；追问最近一次。为赶工虚构基线的失败信号是数据来源无人能指出；撤销数字并安排测量。

“所有用户都需要”的失败信号是没有群体差异，“必须用大模型”的失败信号是没有非 AI 对照，“方案确定只差数据”的失败信号是数据可得性恰好决定方案可行性。纠偏时不只补一句免责声明，要重新检查受到影响的预算、时间和承诺。发现一个根本假设错误，应修改问题契约并通知相关决定的负责人。

访谈收口应交出一份问题契约、带出处的现状流程、关键术语表、证据缺口、风险清单和最小验证计划。接收团队应能回答：为什么值得做，哪些仍然未知，数据和权限由谁提供，什么结果会让我们停止，如何知道方案优于现状。答不出其中任一项，继续加功能不会自动补足发现工作的欠账。

最后让业务方用自己的话复述问题与非目标，让工程方说明需要哪些证据才能选择方案，再让风险责任人确认不能越过的边界。三方说的是同一件事，才具备进入设计的条件。真正的问题定义不是文档被签过，而是团队面对新需求或失败样本时，仍能共同判断它是否属于正在解决的问题。

冲突处理与从访谈到评测的最后一公里

3

不同角色对同一问题的叙述冲突时，先检查他们是否在描述同一类任务、同一时间窗口和同一“完成”定义。经理说平均处理很快，操作员说经常等待，可能一个只统计系统操作时间，一个统计端到端耗时；两者都可能准确。应建立口径对照，而不是用职位高低决定事实真假。无法通过记录核对的部分，保留为待验证差异，并设计下一轮观察。

把访谈转成评测样本时，每个样本要能回溯到任务情境、输入、允许依据、预期动作和不可接受结果。例如受访者说“遇到旧版手册必须找专家”，可以形成一条资料版本冲突的负例，预期是提示冲突并升级，而非挑一份看似相关的回答。这样访谈不仅产生功能需求，还直接产生以后判断系统是否学会正确边界的测试。

还要防止把用户原话当作标准答案。受访者可能沿用已经失效的习惯，或者与正式流程不一致。研究人员应分别保留“现实怎样做”和“制度允许怎样做”，让相应责任人裁决是否需要改变制度、系统或培训。需求发现的目标不是自动化所有现有行为，而是在理解真实情境后，选择值得保留、需要修正和不能交给系统的部分。
