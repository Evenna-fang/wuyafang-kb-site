技术选型决策框架：在业务约束下比较方案，而不是追逐工具榜单

阅读定位：以前两篇的问题与范围为输入，以交付门禁中的可验条件为输出。本文讨论选择方法，不提供未经实时评测的模型排名、价格表或“2026标准栈”。评分、算例、决策记录与实验流程属于本文综合设计；书籍依据限于本地可读材料。

WHY

2

为什么功能对比表经常选不出可交付方案

3

技术选型不是寻找功能最多或排行榜最高的产品，而是在确定目的、约束和资源下选择一个可以验证、运行、维护和退出的方案。相同模型用于离线草稿和自动业务执行，风险结构不同；相同向量库服务于个人资料与跨租户知识，权限要求不同；相同框架用于教学演示与长期运行，观测和升级成本不同。脱离场景谈“最佳”，实际上省略了决定答案的条件。

选型失误常见于三种替代：用产品名替代问题，用厂商基准替代本地实验，用免费单价替代总成本。团队可能因为已经会某个框架，就把所有任务改写成该框架擅长的形式；也可能因为一张演示效果好，就忽略数据清洗、失败接管与迁移。正确的顺序应是先写问题契约和硬约束，再比较最小架构，最后决定具体产品和实现。

课件的 SQL、Agent 与 Dify 示例提供三种实现入口：直接模型调用、动态工具循环与平台化部署。[课1][课2][课3] 它们帮助理解怎样动手，却不构成“所有生产项目都应采用”的证据。《FDE：AI落地实战指南》的划线将成本、效果与延迟放进同一讨论；《持续交付2.0》提醒抵抗局部优化并尽早验证。[书1][书2] 三源融合的选型必须同时回答“能做吗”“值不值”“养得起吗”。

WHAT

2

将选型写成带约束的决策问题

3
2.1 先区分硬约束、目标与偏好3 个重点▾ 点开看本节重点

3

硬约束是不满足就不能进入候选集的条件，例如未经批准不得外发特定数据、必须接入现有身份体系、必须在批准环境运行、某些动作必须人工确认。目标是可优化的结果，例如任务成功、响应速度、运维负担和单位业务成本。偏好是团队熟悉度、界面习惯、语言生态等选择倾向，它们有价值，但不能被偷偷包装成不可讨论的硬约束。

每条硬约束都要有来源和裁决人。客户说“必须私有化”，应进一步确认禁止外发什么、哪些环境被批准、更新与支持如何进行。可能真正要求的是数据驻留，也可能是合同约束或无网现场；不同原因导向不同架构。不能为了方便改写客户边界，也不能把模糊担忧扩大成全系统永久离线。无法澄清时，把它作为待决条件而不是假装已经确定。

2.2 以端到端任务为单位，不以组件分数为单位

3

模型单题得分、向量库每秒查询数、平台节点数量，都只是局部属性。业务关心的是在给定权限和工作负荷下，任务能否完成以及失败后如何恢复。比如生成 SQL 的语法正确率很高，仍可能用错金额口径；检索召回很高，仍可能返回无权访问的资料；代理工具调用成功，仍可能重复写入。候选方案必须用同一业务任务契约比较。

可以将一个候选方案描述为“数据准备、检索、推理、工具、权限、界面、观测与运维”的组合，而不是只有模型名。升级一个组件可能改变其他组件的行为，尤其是上下文长度、结构化输出、流式事件和错误处理。因此实验应记录完整组合与版本，不能把旧索引、新提示词和不同模型混在一组结果里，再把差异归因给单个产品。

候选集中应保留现状、流程调整、规则或搜索等非 AI 方案。它们不是故意设置的弱对照，而是现实机会成本。若通过统一指标口径和改善搜索入口就能解决主要问题，再引入复杂代理可能只增加故障点。对于证据不足的场景，可以选择维持人工、仅做小范围辅助或先补数据治理；延迟不可逆决策有时比尽快选一个产品更有价值。

HOW

2

第一步：按能力阶梯选择最小架构

3

Anthropic 的 Building effective agents 区分了固定代码路径编排的工作流与由模型动态决定路径的代理，并主张从满足需求的简单结构开始。[业1] 本文据此提出下列阶梯。它是方案搜索顺序，不是必须逐级升级的成熟度排名；低一级能稳定满足目标，就没有义务追求高一级。

任务条件 首先验证的结构 升级前需要的证据
规则清楚、数据结构稳定 普通代码、规则、SQL模板 规则维护成本或覆盖缺口确实阻碍业务
需要语言理解或生成、资料已在输入 单次模型调用与结构校验 单次调用无法达到任务要求
需要可更新的私有知识 检索或检索增强生成 直接上下文、过滤搜索不足以解决问题
步骤固定、调用外部工具 显式工作流或状态机 固定路径确有大量不可预见分支
路径随现场反馈变化 有界单代理 动态规划收益超过成本与风险
存在独立子任务或权限隔离需求 受控多代理 并行或分工在同尺子上有可测净收益

选择检索增强生成时，先问知识是否可获得、可更新、可授权访问与可解释，再讨论向量库。选择微调时，先区分需要改变行为还是需要补充经常变化的事实；知识缺失未必适合靠参数更新解决。选择代理时，先问动作是否可逆、失败是否可检测、工具接口是否足够清楚。架构类别选错，后面比较产品功能通常救不回来。

课件《Agent智能体》把规划、记忆与工具循环组织在一起，适合学习这些能力的相互关系。[课2] 生产方案可以只取其中一部分：任务只有查询和摘要，就不必增加长期记忆与自动写入；任务路径明确，就不必让模型反复规划。课程中的“具备某能力”是学习对象，不是每个项目的必备清单。

第二步：建立候选档案与来源证据

3

4.1 候选档案至少覆盖六个维度

AWS Well-Architected 的公开介绍强调在安全、可靠性、效率、成本、可持续性与运行实践等方面理解架构决策的利弊，并明确架构评审是一种建设性讨论，不等同于审计。[业2] 本文借鉴这种多维取舍，而不是要求使用 AWS。候选档案应覆盖业务适配、数据与安全、运行可靠性、性能与容量、工程维护和总成本；任何维度没有证据，都标为未知。

业务适配看任务与失败模式，不看宣传案例数量。安全看身份、权限、数据流、密钥、日志和许可证边界。可靠性看故障恢复、备份一致性和依赖中断。性能看真实负载下的尾部延迟、吞吐与资源；维护看调试透明度、升级、可测试性和团队能力。总成本看开发、运维、评测、支持和迁移，而不仅是 API 计费。

4.2 给每条能力声明注明证据等级

产品官方文档证明公开支持范围；发布说明证明某版变化；维护者问题单提供缺陷和限制线索；论文证明特定实验条件下的结果；本地复现实验证明本环境表现。它们不能互相替代。一个问题单不证明所有用户都会遇到，一篇论文的提升比例也不证明中文客户语料能复现。记录能力时并列写版本、来源日期、适用条件和本地核验状态。

原有信息源体系的价值在于区分官方文档、研究、工程经验和社区线索，这个分类保留；“某站永远可直连”“某代理永远可用”等环境断言不作为长期事实。可达性需要在实际网络环境测试；不能为了取得资料上传本地配置或使用未经批准的凭据。若来源不可读，写明未取得，不用二手文章冒充已读原文。

4.3 把变更源纳入选型，而不是上线后才关注

候选档案应指向其维护方式、弃用公告、许可证与兼容性信息。频繁改接口的组件不是一定不能用，但要计算跟随升级、锁版与适配测试的工作量。关键依赖如果没有明确维护人，免费也可能很贵。旧稿里的前沿新闻与论文月报应当作为历史线索，不应直接成为选型理由；只有回溯原文、明确场景并通过实验，新闻才转化为可用决策证据。

第三步：先做淘汰，再做权衡，避免评分伪精确

3

5.1 硬约束不能被平均分抵消

先对每个候选执行通过、失败、未知三态筛选。失败就淘汰或改变明确获批的约束；未知则安排验证，不给一个中间分掩盖。比如不支持所需租户隔离的方案，不能因为便宜和速度快获得总分第一。许可证是否允许目标用途、数据是否进入批准边界、关键动作是否可控，都不应进入普通加权平均。

留下的方案再做多维比较。权重应在看实验结果之前由相关负责人确认，避免为偏爱产品调权。评分锚点必须有具体解释，例如维护性高意味着现有团队可定位故障、可导出配置、升级有测试，而不是“看起来生态好”。资料不足时给出区间与置信程度，不能给精确到小数点的主观分数制造客观感。

5.2 用敏感性检查发现脆弱结论

若权重略变、流量略涨或复核成本稍高，排序就翻转，说明结论依赖不稳假设，需要补证据或选择更容易退出的方案。可以分别看低、中、高负载以及严格、一般风险场景，不必编造一个能概括未来的唯一分数。条件变化时谁胜出，往往比当前谁多两分更有决策价值。

也要检查支配关系。如果方案甲在所有关键目标都不差，并且退出成本更低，方案乙没有清晰额外价值，就不值得仅因品牌偏好保留。若不存在全面占优者，记录被接受的代价：例如选择平台换取更快交付，同时接受较弱可移植性；选择自建换取可控性，同时承担持续运维。没有代价说明的决定，通常隐藏了未讨论的成本。

第四步：用最小实验回答最大不确定性

3

6.1 实验不是再做一遍产品演示

先写最可能改变决定的未知，例如权限过滤是否有效、资料更新是否及时、复杂任务是否需要动态规划、离线环境能否完整启动。然后设计能推翻它的实验。一个精致 UI 不能回答隔离问题，普通问题的高分不能回答多跳价值，单用户冒烟也不能回答并发容量。实验应优先验证架构类别与风险，不先耗费时间比较微小参数。

样本应按真实任务分层，包含高频普通任务、低频高风险任务、无答案、脏数据、过期资料、越权与依赖故障。建立开发集和独立验收集，避免候选方案反复针对同一组题优化。共享相同任务、同样的预处理与评判口径；确实必须为某候选使用特殊适配时，把适配成本和条件写入结果，不假装比较完全同质。

6.2 记录完整实验链，允许结果否定方案

至少记录问题版本、数据与样本版本、候选组合、配置、负载、预热方式、重复次数、结果及失败明细。对不稳定输出，可重复运行并报告波动，不能只取最好一轮。对性能，明确是否包含网络、检索、排队、生成和人工复核；冷启动与常驻状态分别看。对代理，记录轮数、工具次数、终止原因与副作用，而非只看最终答案。

如果简单方案已经达到约定目标，复杂方案必须证明新增净收益；如果所有方案都失败，应检查问题定义、数据质量和评价口径，不急着不断换模型。最小实验的成功可能是“发现不值得做”，也可能是“确定只需固定流程”。不要将选型变成必须选出某种 AI 产品的竞赛。

6.3 针对离线与迁移做专门实验

私有化验证要覆盖完整依赖：模型与分词资源、数据库、前端静态资源、身份服务、日志、更新、备份与恢复。应在获准隔离环境中阻断出站后走完主路径，核对是否还有联网依赖；不能仅设置一个离线变量就宣布成功。本地部署也不自动意味着更便宜，闲置硬件、值班、能源、驱动维护和模型更新都需要计入。

迁移验证则应实际导出少量文档、元数据、权限和评测样本，验证能否在另一实现中恢复主要能力。向量维度相同不代表语义空间相同，模型或编码方式变化可能需要重新生成索引；不要只按存储文件大小估算迁移时间。这里是需要在候选环境验证的工程风险提示，不是本篇对某个具体数据库已做过迁移的声明。

第五步：计算总成本、质量代价与退出成本

3

7.1 从每次调用成本改成每个有效业务结果成本

可使用以下教学口径：有效任务成本等于模型、检索、存储、计算、运维、人工复核、失败处理等成本之和，再除以真正完成的范围内任务数。拒答任务的处理成本不能消失，重复重试也不能按一次计费；高质量结果如果需要大量专家修订，不能仅用模型单价宣称经济。各成本项的现金支出和人员机会成本应分开，避免重复计算。

构造算例：方案甲每月基础支出四千元，处理一千个任务，其中七百个达到业务标准，暂不计其他费用时约每个有效任务五点七一元。方案乙每月六千元，九百五十个达到标准，约六点三二元。仅看这部分甲便宜；如果甲剩余任务显著增加人工处理，结论可能反转。此例只展示分母与遗漏成本的重要性，不是现实报价或性能数据。

7.2 建立低、中、高三种场景

对请求量、输入长度、检索上下文、代理轮数、缓存命中、复核比例和运维工时分别给假设范围。把最影响总成本的变量找出来，再决定是否值得花实验预算。若成本主要由人工复核决定，就不该只优化 token；若主要由闲置算力决定，就不该只比较满载吞吐。模型价格、配额与供应商承诺具有时效性，正式采购前应重新核对官方页面和合同。

同样，延迟要与工作方式匹配。交互咨询的等待、后台批处理的完成窗口、自动操作的超时和重试，不能用一个响应时间指标混合。缓存会改善速度与费用，却可能引入过期资料或跨用户泄露风险，必须连同失效和权限策略一起测。每个优化都应说清改善什么、可能伤害什么、怎样验证没有把代价转移到别处。

7.3 把退出路径当作候选能力

退出成本包括数据导出、格式转换、重新标注、索引重建、流程改写、权限重建、用户培训和双跑时间。能导出文档不代表能导出整套能力；提示词、工具契约、工作流、版本记录和评测集同样重要。为高不确定组件保留适配层和回退方案是合理投资，但不应为了假想可替换性抽象所有细节，反而让系统无人理解。

第六步：用ADR记录理由、代价与重评条件

3

Michael Nygard 的原始文章建议用短小的架构决策记录保存重要决定的背景、决定、状态与后果，并保留被替代记录的历史。[业3] 本文在其基础上增加证据和重评条件，便于 AI 项目在模型与数据变化时更新。ADR 的作用不是证明当初永远正确，而是让后来者知道当时条件下为什么那样选。

ADR编号、日期与状态：提议/接受/被替代
关联问题契约与范围：
背景：业务、数据、权限、团队与时间条件
硬约束及其来源：
候选：现状/非AI方案/最小AI方案/复杂方案
证据：官方能力声明、本地实验、未解决未知
决定：选择什么、仅在哪个范围内生效
取舍：收益、负担、限制与残余风险
成本与退出：假设、敏感变量、导出与恢复
实施和验收：负责人、产物、门禁
重评触发：范围、流量、规则、版本或成本改变
替代关系：旧记录不删除，注明新记录

ADR 不需要堆满所有调研材料，可以链接证据并保留关键比较。若决定来自业务负责人对风险的取舍，要写明谁批准，不能伪装为纯技术最优。若证据仍弱，应标记试验性接受和限制范围；若旧决定已失效，创建替代记录，而不是悄悄改掉理由让历史看起来没有错误。

旧碎片的“每周扫描”在此转为责任化的重评机制：指定维护人、关注实际依赖、记录重要变更、评估受影响契约、用同尺子回归。不是每条新闻都需要重构，也不是永远锁住版本就没有风险。真正的触发条件是现有决定的前提发生变化，而不是发布标题足够吸引眼球。

贯穿案例：售后知识助手如何选择而不被技术绑架

3

以下为构造案例。问题契约要求某产品线人员查找有效处理依据，资料不得进入未经批准的服务，关键建议必须带可复核来源，不允许自动修改设备。候选先列现有搜索、带版本过滤的搜索、检索增强生成和动态代理。权限与数据流先筛选，无法验证边界的候选保持未知，不因演示效果好直接入围。

最小实验发现，版本过滤能解决一批旧资料误用，生成摘要能减少部分阅读，但动态规划并未增加可验证收益。团队据此选择过滤检索加受控摘要，暂不增加写入工具。课程提供上下文与模型调用的实现路径，[课1] 书摘提醒真实流程和成本效果取舍，[书1] Anthropic 的结构区分帮助限制代理复杂度，[业1] 多维架构视角要求补上恢复与维护证据。[业2]

随后记录 ADR：只覆盖批准文档与指定用户；若引入跨系统诊断、任务路径明显变化或新风险，重新评估结构；若资料更新责任无法落实，不扩大范围。客户维护人员演示更新与撤销，验证导出样本在替代实现中可读。这一选择不是“某模型全球最好”，而是“在已知约束和证据下，这个组合最值得有限投入”。

决策收口检查

3

最终评审可问：候选是否含现状与非 AI，硬约束是否有出处，比较是否同任务同分母，是否看过失败和尾部，成本是否包含人工与维护，能否恢复与退出，谁负责前提变化后的重评。任何一个问题没有答案，都应记录待办与影响，而不是通过增加表格分数制造确定性。选型质量体现为可解释、可验证、可修订，不体现为选了最时髦的名字。

框架与平台选型的额外检查

3

当候选差异主要来自编排框架或低代码平台，不要只比较是否提供某个节点。应让同一名维护者完成一个实际变更，例如替换模型、增加权限判断、恢复失败任务或导出应用，再观察要改哪里、如何测试、怎样定位错误。平台内置能力可能缩短开发时间，也可能把隐含状态藏起来；代码框架可能更透明，也可能增加团队维护负担。二者都需要本场景证据。

课程中的 Dify 部署链可以成为动手起点，但“平台已经安装”不证明团队能承担升级、备份与运行；Agent 示例能够调用工具，也不证明复杂任务能在预算内稳定终止。[课2][课3] 书籍的整体优化提醒我们将业务、开发和运营放在同一条价值流上。[书2] 因此选型评审应邀请真正负责维护的人，而不是只由做演示的人决定未来支持成本。

可以为每个候选设计一次“离开原作者”的测试：由另一个具备基本背景的人，依据文档重现配置、定位一个失败并说明恢复方法。如果需要原作者不断补充口头解释，这些隐性知识要计入风险和交接工作。该测试不是要求任何新手都能维护复杂系统，而是检查候选所需能力是否与已承诺的团队资源匹配。

最终决定还应标注时间有效性。原则层的取舍可以长期存在，产品层的价格、限额、兼容矩阵和许可证应定期或按事件重核；本地实验也会因数据分布、负载和权限改变而过期。不要因为 ADR 保留了历史就继续使用失效结论，应由重评触发明确连接到下一次实验和发布门禁。这样选型成为可持续决策能力，而不是一次采购文件。

在采购沟通中也应保持同样口径：供应商演示可以证明某条路径存在，服务承诺需要合同确认，现场集成需要本地验证。应要求对方解释限制、失败恢复与数据导出，而不只展示顺畅路径。若关键能力只能由销售口头承诺，应在候选档案中保持未验证，并写入试用或合同条件；不能为了按计划完成选型而把口头承诺提升为已具备能力。

另一个停止信号是选型调研无限延长。为每个未知设定决策价值和验证成本，先验证最可能改变结果的部分；当候选都满足硬约束、主要差异已可解释、剩余未知不改变有限试点决定时，就应形成具名记录并进入受控验证。继续追求所有维度最优，会让调研本身成为无法结束的项目。
