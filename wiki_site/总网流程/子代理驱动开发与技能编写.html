两套方法解决同一个问题——把"判断"从"执行"里切出来，让每一步都可被独立验证。

  • 子代理驱动开发（SDD）：一个任务派一个全新子代理执行，每任务后做规格 + 质量双验收，最后再做一次全分支终审。公式：fresh subagent per task + task review + broad final review = 高质量快速迭代。
  • 技能编写（Skill Authoring）：把可复用的"怎么做"写成 SKILL.md（薄决策层）+ scripts/（确定性）+ references/（按需查阅），判断交给人/Agent，流程交给脚本。

一句话判据："没被独立验证的产出 = 未完成"——这是 SDD 的验收底线，也是技能里为何要把确定性逻辑抽出成可复现脚本的同一动机。

A. 子代理驱动开发（SDD）3 个重点▾ 点开看本节重点
本节重点
  • A0. 何时用（判断标准）
  • 与并行会话版的核心差异：同会话零切换、每任务换新子代理（无上下文污染）、每任务后即验收、任务间无人在环（更快）
  • 每任务评审是任务级闸门：规格合规 AND 任务质量两个结论都必需，缺任一即不算报告完整
3

A0. 何时用（判断标准）

按序问三个问题：① 有实施计划吗？ 无 → 先脑暴/手工执行。② 任务大多独立吗？ 否（强耦合）→ 不适用。③ 在同一会话内推进吗？ 是 → SDD；否（并行会话）→ 走 executing-plans。与并行会话版的核心差异：同会话零切换、每任务换新子代理（无上下文污染）、每任务后即验收、任务间无人在环（更快）。

A1. 任务怎么切给子代理（派发五要素）

一个派发 prompt 只描述一个任务，且只装五样东西：

  1. 一行交代"这个任务在项目里的位置"；
  2. 任务简报路径（scripts/task-brief 生成的独立文件），措辞为"先读这个——它是你的需求，含要原样使用的确切取值"；
  3. 简报无法知道的、来自前序任务的接口与决策；
  4. 你对简报中歧义的裁决；
  5. 报告文件路径 + 报告契约。

铁律：确切取值（数字、魔法串、签名、测试用例）只出现在简报里；绝不把累积的历史塞进派发（真实案例中一份派发 prompt 达 42k 字符，99% 是粘贴的历史）；绝不让子代理读整个计划文件。小而同形的批量改动（同一处一行修正、常量替换、字段新增重复到多文件）合成一个派发，不要一任务一代理；一任务一代理只留给需要独立判断/独立测试/独立验收面的活。

边界怎么定：派发里带 no-subagents 契约——实现者永不再派子代理（包括"帮手"，更包括自查评审）。真实会话里执行者自派的评审每次都重复了控制器的任务评审，等于每任务白多一个评审位。多个实现子代理绝不并行派发（会冲突）。若早先任务在本任务区域留有 finding，派发里带上指向该台账条目的指针。

A2. 进度怎么记（台账 Ledger）

对话记忆不跨压缩存活——控制器丢状态后重派已完成的整段任务是实测中最贵的失败。因此进度写进台账文件（<workspace>/progress.md），首行写身份 # SDD ledger — plan: <计划路径>：

  • 有 Task <N>: complete 行的任务即 DONE，不重派，从第一个没有该行的任务续跑；
  • 压缩后信台账与 git log，不信自己的记忆；
  • 修补轮次、裁决、驻留的 finding 全部落台账；单个计划一个 workspace，别的计划的目录不读不写。

A3. 验收怎么做（三层门，缺一不算过）

  • 每任务评审是任务级闸门：规格合规 AND 任务质量两个结论都必需，缺任一即不算报告完整。实现者自查永不替代任务评审——两者都要。
  • 评审输入三条路径：同一份简报、报告文件、评审包（review-package PLAN_FILE BASE HEAD 产出的单文件 diff）；外加绑定该任务的全局约束（逐字抄自计划的 Global Constraints / 规格：确切取值、确切格式、组件间关系）。全局约束块是评审者的注意力透镜。
  • 不预判 finding：绝不指示评审者"忽略某问题""别当缺陷""至多 Minor""计划就是选的"——出现这类话说明你在预判，通常是想省一轮评审。若确信是误报，让评审者提出、在评审环里裁决。
  • 重建 BASE：派发实现者前记下 BASE=git rev-parse HEAD；评审包用该 BASE，绝不用 HEAD~1（会静默截断多提交任务的中间提交）。
  • 评审可能报 ⚠️ 无法从 diff 验证（要求落在未改动代码或跨任务处）：不阻断其余评审，但控制器必须逐条自行解决（你持有计划与跨任务上下文）——确认是真缺口，就按规格失败进修补环。

A4. 修补环（Fix Loop）与"断路器"

触发条件：规格 ❌、任一 Critical/Important finding、或你确认为真缺口的 ⚠️ 项。每任务最多 5 轮（一轮 = 一次修补派发 + 一次限定范围的复审）：

  • 第 1–3 轮：续用原实现者（上下文完整），把未决 finding 原样发给它；
  • 第 4–5 轮：换新实现者 + 至少升一档模型，说"此前已尝试 N 次，现在归你，先读报告文件看试过什么"——撑过三次续跑的环，通常意味着实现者看不见自己的问题，换眼睛与升能力一步到位；
  • 复审是限定的：只对每条 finding 判 ADDRESSED / NOT ADDRESSED，并只在修补 diff 内标记新破坏；范围外观察记为延后 minor，绝不延长环。
  • Minor 不进环：逐条记台账（Task <N>: minor (deferred): …），终审时统一分诊。plan-mandated 的 finding 归你裁决（以规格为约束权威），不得因"计划要求的"就丢弃。
  • 断路器（第 5 轮仍不收敛）：停止派发，逐条自行裁决——评审者错/可争辩 → 驻留；真但无人依赖 → 驻留；真且承重（后续任务依赖它 / 暴露计划缺陷）→ 裁最小改动解锁下游，记 Ruling: 并带入下一任务派发。只在触顶时裁决，提前裁决=换个名字的预判；每次裁决必落台账，禁止静默丢弃。
  • 控制器绝不自己动手修：保持上下文干净，且控制器直接修会跳过评审。

A5. 终审与收尾

全分支终审用最强模型，把评审包（MERGE_BASE…HEAD）、台账里的 deferred-minor 与驻留行一起给它分诊。有 finding → 只派一次修补（不是一 finding 一修，真实会话里逐 finding 修的代价超过全部任务之和），再做恰好一次限定复审，残余按断路器方式裁决；没有第二轮修补。收尾时把台账里所有含 Ruling: 的行按发生顺序汇总进最终消息——"随 workspace 一起消失的裁决 = 秘密决策"。全绿后删除本计划 workspace（git 历史即记录）。

A6. 模型选择（判断标准）

用能胜任该角色的最弱模型省钱提速。显式指定模型——省略会继承你（通常最贵）的会话模型，静默破坏本节。关键校准：轮数比 token 单价更重要——最便宜的模型常在多步活上多花 2–3× 轮数，总体更贵，故评审者与"读散文式描述干活"的实现者以中档为底；计划文本已含完整待写代码时，实现=抄写+测试，用最便宜档。任务信号：单/双文件且规格完整 → 便宜档；多文件带集成关注 → 标准档；需设计判断或广域理解 → 最强档。修补环 4–5 轮升档。

A7. 为什么必须 verification-before-completion

  • 没有评审的环只是"未经验证的瞎忙"——评审是环的刹车与方向盘。
  • "规格差不多就行"= 没完成：评审查到规格缺口就得修，或触顶后裁决，别无出口。
  • 未评审的修补正是回归落地的方式：每轮都以限定复审收尾，无例外。
  • "实现者自派了评审，白得一层保险"= 缺陷：那是对同一 diff 的重复评审位，任务评审才是闸门。
  • "我自己修，派发是开销"：控制器修污染自己上下文且跳过评审。

配套的持续推进纪律：任务间不停下来请示，把全部任务跑完；计划不停下来等人。冲突/歧义/计划缺陷由你裁决而非停滞（记 Ruling: <决定> — <理由> — <错了的代价> 后继续）。只有四类事才停：不可逆或破坏性操作、安全敏感动作、工作树外需先问的副作用（合并/推共享分支/发布）、计划烂到每条路都是猜。

B. 技能编写（Skill Authoring）

3

B1. 三条核心原则

  1. 拆成 Agent：复杂技能 = 纯编排者 + 专职子代理；子代理单一职责，编排者只委派/协调/汇报，绝不自己干活。
  2. 并行优先：相互独立的子代理在同一条 Task 消息里一起启动（3 个目录 → 3 个并行代理 ≈ 1× 延迟而非 3×，只在有依赖时才串）。
  3. 脚本优先（确定性）：技能价值若能用确定性脚本表达，先写脚本，再用 SKILL.md 包住它——脚本可测、可在 Claude 外运行、让 SKILL.md 变薄。Agent 管判断，脚本管流程。

其余：精简（上下文是共享资源，逐段问"值这个 token 吗"）；渐进披露（SKILL.md 是概览，正文 < 500 行，引用文件按需加载）；自由度匹配脆性（灵活任务给文字指引、脆性操作给确切脚本、判断密集型给专职 Agent）。

B2. 怎么写才可复用：结构约定

Frontmatter 只允许三类字段：name（kebab-case，≤64 字符）、description（≤1024 字符，第三人称 + 单行双引号）、metadata.version（semver）。不要 author/date/tags/allowed-tools/category，也不要顶层 version；description: | 块标量会触发 VS Code linter 报错。

description 写法（Claude 靠它从 100+ 技能里选你）：第三人称；同时含"做什么"与"何时用"；带编号触发条件 Use when: (1)…(2)…(3)…；写具体症状、报错、框架名。

目录布局与"什么放哪"：

your-skill/
├── SKILL.md        # 必需：决策工作流、when-to-use、关键规则
├── scripts/         # 可选：可执行自动化（前/后处理）
└── references/      # 可选：按需加载的查阅材料
.claude/agents/      # Agent 定义放这里（跨技能复用），不放技能内
内容类型 放哪 为什么
决策流、触发条件、常用命令、编排模式 SKILL.md 每次都加载
Agent 定义 .claude/agents/ 标准位置、可复用
查表、字段参考、代码示例、案例 references/ 偶尔查阅，避免稀释 SKILL.md
可执行流程 scripts/ 可预测、可测、可复用

引用规则：距 SKILL.md 只一层（references 不再链 references）；文件名有描述性（api-field-reference.md 而非 ref1.md）；>100 行加目录。

脚本抽取判断：检查/校验/检测（过期、同步、覆盖）、含错误处理（缺依赖/错目录/非法参数）、同段代码出现在多技能、可与其它脚本或 CI/hooks 组合、用户可能在技能外单独运行——命中任一即抽 scripts/。脚本要求：必备 --help、运行前校验输入、有意义的退出码（0 成功/1 错误/2 用法）、适用时提供 --fix、chmod +x、#!/usr/bin/env bash。

B3. 三个"Do I need it"判断表

  • 拆解评估：N 个独立项 → 按项 fan-out；N 个独立关注点 → 按维度 fan-out；阶段内可并行 → 脚本→并行代理→脚本；纯串行 → 不需要编排者。
  • 脚本优先评估：完全确定性 → 先写脚本、SKILL.md 做薄壳；大部分确定 + 少量判断 → 脚本管确定、Agent 管判断；纯决策指引 → 散文优先、无需脚本。
  • 进度追踪评估：3+ 顺序阶段或多工作流 → 加 scripts/task-manifest.sh（每个工作流一个 case 分支，输出 subject/activeForm/description）；1–2 个快阶段 → 跳过。

创建 vs 更新：无相关 → 新建；同触发+同修法 → 更新（minor 升版）；同触发+不同根因 → 新建并双向 See Also；同域+不同触发 → 更新加变体小节；已陈旧/错误 → Notes 弃用并建替代。

B4. 反模式（照抄避坑）

  • 能并行却顺序执行（无依赖就该同一条消息发）· 单体代理（一个干五件事）· 编排者亲自干活 · 缺结构化输出（返回散文迫使编排者猜）。
  • 啰嗦解释（跳过"PDF 是什么"这类常识）· 选项过多（给默认 + 逃生口，不是五个方案）· 深层嵌套引用（SKILL.md→ref→detail 导致只读到一半）。
  • 时间敏感信息（"2025 年 8 月后用 X"会腐烂，改用"当前方法/遗留"分节）· 术语不一致（统一用 endpoint，别混 URL/route/path）· 非标准 frontmatter（author/date/tags 白烧 token）。
  • Agent 里 CLI 模板不全（gh issue/pr create 要写全 --label/--assignee/--milestone，否则 Agent 用似是而非的值瞎填）。
  • 长流程静默（3+ 阶段不建任务清单，用户盯着转圈；子代理 >30s 就该看到哪个任务 in_progress）。
  • 未测脚本当"完成"：过得了代码评审却在真实数据上失败——发布前必须对当前项目用 2–3 个变化输入做 dry-run（bug 成簇，一个启发式错往往意味着别的也错）。
  • 一次性并行却上 Teams：Teams 有开销（共享任务表、消息路由）；独立 fan-out 用子代理更快更省。

优化既有技能（超 500 行/结构差/慢）：审计可并行点 → 拆单体 Agent → 抽 scripts/ → 抽 references/ → 内联改链接（See **[references/x.md]**…）→ 校验交叉引用都存在 → 修失效引用 → 升版（重组=minor，Agent 架构变更=major）。
