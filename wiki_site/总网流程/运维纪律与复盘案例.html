二、什么必须先备份——命中任一先落可回滚副本

3
  • 活配置／活库：state.db + -wal、agent sqlite、.env／secrets.env、key-map.json／model-map.json。
  • 在途产物：写入中的 log、cache/delegation/live/*——先停写再动。
  • 手改文件：AGENTS.md、SOUL.md、config.yaml——手改即先 cp。
  • 备份类本身：*.bak*、*-backups/*——可删，但先 tar 归档。

四、批量操作上限——防超时也防误伤

3
  • 逐条 terminal() 调用，禁止在 execute_code 里循环批量 rm／du：实测循环会撞 300s 超时，且失败点难定位。
  • 批量删除前先只读扫描 → 出清单 → 确认 → 执行；清单对齐类任务走零删除只读模式：不 chmod、不改名、只写一个产出文件，原始 find／grep 行必须贴进产出（不许只给结论）。
  • 敏感点先分级再进表：活库禁删（专项走 key 轮换或登记接受）、历史文档需讨论（脱敏 vs 留证）、备份类先 tar、在途产物先停写。

六、三个必查 pitfall——漏一个清单就错

3
  • find 根是 symlink → 假阴性：默认不跟命令行 symlink，计数恒为 0；先 stat -c '%N' <根> 验证，扫 777 必须 find -H。
  • /mnt/c 是 9p／drvfs 无 metadata → 全文件假 777：chmod 不持久；判权限问题前先 grep ' /mnt/c ' /proc/self/mounts，命中 9p 且无 metadata 记"不适用"，别当真 777 报。
  • MCP filesystem 读不了 /tmp：/tmp 下的清单文件要用 read_file 读。

顺序铁律：先"收口绿"再"清场"——[7] 收口通过后才执行 [8] 清场；清场清单写入收口单（删了什么／归位核验／备份登记／进程清点），清场本身可被验收。

七、复盘案例一：API 防废专项（2026-09-24）3 个重点▾ 点开看本节重点
本节重点
  • 现象：单日 API 浪费估算达全天消耗的 1/4 ~ 1/3
  • 四类具体表现：渠道超时空烧 5 次（单次 420–1500s）；大卡跑偏 2 次（940s／1500s）；死锁返工——同一任务 declare 11 次（每次冷启重读材料）；换 key 断供（402）导致 4 线齐挂、全量重发
  • 当晚另补 5 项：⑥ S1 amend 一键（消掉 5 步手工循环）；⑦ 改派续会话落用（消冷启）；⑧ OC 并发 ≤ 1；⑨ Claude 单 timeout ≥ 600s + 发前快测渠道；⑩ R6 闸——在途 > 3 时新任务只入队不落地

现象：单日 API 浪费估算达全天消耗的 1/4 ~ 1/3。四类具体表现：渠道超时空烧 5 次（单次 420–1500s）；大卡跑偏 2 次（940s／1500s）；死锁返工——同一任务 declare 11 次（每次冷启重读材料）；换 key 断供（402）导致 4 线齐挂、全量重发。

根因：① background 单未带 timeout → 一旦卡住就是无限烧（无它止血）；② 大卡不拆 → 跑偏／超时，渠道未快测就发长任务；③ 改派 = 开新会话 → 每次冷启重读材料，重复烧；④ 402 断供无预案 → 集中重发；⑤ 并发未限 → 3 单挤兑互相超时。

纠正（已落地防废五件套）：① timeout 前置（所有 background 单带 timeout）；② 拆小卡 + 白名单；③ 材料内嵌／引用分界；④ 绿即停 + 轮次 ≤ 2；⑤ 改派 = 续会话。当晚另补 5 项：⑥ S1 amend 一键（消掉 5 步手工循环）；⑦ 改派续会话落用（消冷启）；⑧ OC 并发 ≤ 1；⑨ Claude 单 timeout ≥ 600s + 发前快测渠道；⑩ R6 闸——在途 > 3 时新任务只入队不落地。

预防动作（可复用清单）：任何长任务默认带 timeout，超时即止；发长任务前先快测渠道，单渠道故障先查再发、不全量重发；改派优先续会话不新开；同一任务连续失败 ≤ 2 轮即回边重审、不硬闯；在途闸并发 ≤ 1。仍欠：精确 token 计量（现靠 budget 档位 + 人工对账，双轨有风险）；Claude 长任务首响卡根因未深挖（现象有、根因无）。

八、复盘案例二：记忆未同步配置变化（2026-09-30）

3

现象：09-30 12:39 用户把某 provider 从 fallback 链拿掉（配置 6 跳 → 5 跳）。下午查"还能用吗"时，记忆里仍写"fallback 6 跳含它"，据此把"文件是 5 跳"误判为"配置被无痕回退"，反向派单要把它插回去——方向完全错，被用户当场纠正。

根因：① 记忆是异步自动抽取的滞后快照，记的是"当时说过的话"、不记"后来配置又改了"，新改动无新条目覆盖旧的；② 把记忆当真源而非线索——默认"记忆 = 正确状态"，于是"文件与记忆不符"被读成"文件被破坏"，正确顺序应是 文件／配置 > 记忆快照；③ 没先 diff 文件与备份——backup 里有 6 跳版本这一证据没先看就下了结论；④ 没问一句就派单——只要问"12:39 是你让改的吗"即可避免。

纠正（判定铁律）：真源是配置文件，记忆只是历史快照；冲突时文件为准、记忆默认过时；拿不准先 diff 文件 + 备份，再问用户，绝不据此派写单。

预防动作：① 记忆每日整理（按官方 pruning workflow：list → 聚类 → invalidate），清理过时 + 重复条目，每条带 When 时间锚（不带锚最易被当永久事实）；② 工具先读说明书——用任何 API 前先读官方文档再操作、禁瞎试（尤其 DELETE／写）。本次整理记忆时想直接试 DELETE，读文档才发现该用 PATCH invalidate（可逆）；③ 环境类事实（模型版本／兜底链）属易漂移项，定期重验而非长期外推。

通用教训：过时记忆 + 没核实 + 没确认 = 反向操作。 三个环节任缺一个都会放大错误。
