阶段 我们的做法 业内最佳实践 差距定性
1. 分流定档 判断任务类型/风险等级/是否人审，路由+粗粒度分诊 Anthropic Routing 模式；OpenAI Input Guardrail（入口跑一次：越权/参数/能力边界检查）；高风险任务 Voting（并行 2-3 路执行取共识） 已达标（Routing 是我们与业内同构项）；缺 Input Guardrail 与高风险 Voting 规则，需补
2. 拆图画全景 直接拆成子任务、列依赖图，plan 在"脑子里" Cursor Plan Mode / Claude Code：先 Clarify 反问 3-5 个问题再出 plan.md；plan 是结构化一等数据 steps[{task, depends_on, acceptance_cmd, model_size}]；planner 用强模型、executor 用便宜模型（LangChain 经验） 需补：缺 Clarify Loop、plan 数据结构化、planner/executor 模型分离
3. 逐项派单 子任务丢给执行 agent，单向派单 Anthropic Orchestrator-Workers；OpenAI Handoff=工具（on_handoff 钩子授权检查 + input_filter 接单方先过滤）；Tool Guardrail（每次工具调用前后都跑轻量检查）；Checkpoint（每 N 个子任务/30-60 分钟暂停，用户决定 continue/rewind/replan） 已达标（Orchestrator-Workers 同构）；缺 Tool Guardrail、Handoff 输入自检、checkpoint 中断，需补
4. 验收 Check 做完后一次性 LLM 检查"看起来对" 两层验收：先确定性检查（单测/schema/grep），再 LLM-judge；结构化 rubric（3-5 维度×1-5分×few-shot、judge 温度 0.2、关键 judge 跑 3 次查一致性）；Evaluator-Optimizer 闭环（不通过→反馈喂回改→至少 1 轮再判死） 落后最多：模糊单轮判断 vs 业内多维 rubric + 重试闭环 + 一致性自检 + 确定性优先
5. 收口打扫 清理临时文件、写记忆、汇报，偏轻 状态三件套 tasks.md/requirements.md/session.md（开场先读 state 防失忆）；Handoff 交接笔记（做了什么/下一步/关键决策，给下一个无上下文 agent）；Reflexion verbal reflection ≤200 字入 episodic memory（上限 1-3 条防 context 爆） 部分领先：写记忆/落账意识已有（152 台账+error-ledger 技能可直连）；缺 session state 协议与固定 handoff 产出，需补

各阶段"同构已达标"的判定依据：Anthropic 五种 workflow 模式中 Routing↔阶段1、Orchestrator-Workers↔阶段3、Evaluator-Optimizer↔阶段4（雏形）、Prompt Chaining/Parallelization↔派单，全部有对应物；CrewAI Hierarchical（manager 派单+复审）恰覆盖我们阶段 3+4。

P0（最高 ROI，直接决定验收质量）：
1. 验收标准前置：派单那一刻就把"完成判据 + 可执行验证命令"写进派单单，不要拆完才想怎么算完（Anthropic：define acceptance criteria before code）。
2. 两层验收：第一层命令行/单测/JSON schema 确定性检查，能过的不占 judge token；第二层才上 LLM-judge。
3. 结构化 rubric + 一致性自检：3-5 维度（事实性/完整性/格式/是否越界改动）×1-5 分 ×few-shot 正反例；judge 温度锁 0.2，关键 judge 同输入跑 3 次，分歧 >1 分升级人审。

P1（补执行中回路，防线性跑完才发现错）：
4. Replan Loop（LangGraph 三节点图的关键）：子任务验收失败不直接报错回退，而是让 planner 重写剩余 plan 再继续派单；plan 必须先数据结构化才可被 replan 改写。
5. Tool Guardrail per 子任务：派单前+回报后各跑一次轻量检查（范围/schema/敏感词），对应 OpenAI Tool guardrail"每次调用前后都跑"。
6. Checkpoint 中断：每 N 个子任务或 30-60 分钟强制暂停汇报，用户决定 continue/rewind/re-plan。

P2（补入口与协作纪律）：
7. Input Guardrail + 高风险 Voting：入口跑一次越权/参数/能力边界检查；金额或不可逆操作自动升级为并行 2-3 路执行，一致性低于阈值则升级人审。
8. Clarify Loop：拆图前 planner 先反问 3-5 个澄清问题，用户答完再出 plan（Cursor Plan Mode 做法）。
9. Handoff 输入过滤：子 agent 接单先自检"这任务是不是我的"，不匹配就 raise 而不是硬做（OpenAI input_filter）。
10. Planner/Executor 模型分离：拆图用强模型、执行用便宜模型，写进分流定档规则。

P3（收口协议化）：
11. Handoff 笔记 + session.md：任务结束固定产出交接文档与状态文件，下次开场第一件事读它。
12. 失败 lesson 入台账：≤200 字 verbal reflection 进 error-ledger（我们已有该技能，直接接上），保留 1-3 条防 context 爆。

反面警示（业内已知坑）：CrewAI manager agent 实际不 delegate 是常见 bug——多智能体动态派发并不省心，必须显式测试；LLM-as-Judge 要防位置偏置（换序）、长度偏置、同模型自我偏好。

对标后确认的 2 个真差距（区别于阶段内细节）：
1. 冲突源头真值层级规则（已补进总地图 N6）：多源冲突时（SOP 写 30 天 vs 帮助中心 14 天）AI 挑先检索到的引用=错。业内要求 source-of-truth hierarchy 裁决权，落地为五级：实测命令输出 > 一手官方文档 > 台账已验证坑 > 技能库规则 > 二手总结。
2. 渐进式披露"触发词-加载"（挂账）：我们把规则全塞 system prompt 导致 context 爆炸；Anthropic 规范是 L1 约 100 token 常时注入、L2 完整手册触发才加载。因要动 guard 脚本+system prompt 结构，不在本轮做。

"记台账≠完事"的行业答案（Google SRE）：Design systems that prevent errors——设计层堵死，下次想犯都犯不了；action item 必须单一 owner + 可客观验证 + 进工程 backlog，不能停在文档里；agent 记忆三件套：启动注入相关 lessons、失败反思写回、写前校验+定期过期清理。

挂账防过度工程：9 字段分层、渐进式披露、durable execution（崩溃从断点恢复而非重跑）、KG 推理核心层，均不在本轮做。

  1. 验收前置 + 两层验收（P0-1/2）：派单单强制含"完成判据+验证命令"；验收第一层先用单测/schema/grep，第二层才上 LLM-judge。改动最小（只改派单与验收两个动作的定义），直接消灭"做完才发现错"和"模糊验收"两大痛点。
