AGENTS.md 是六员协作的协议总纲，其可复用内核是一组把"判断权"与"执行权"切开的纪律：主链固定为"七步 + 两条回边"；任务按爆炸半径分三档（80% 直出、15% 派单、5% 重流程）；下判断前必须先过 G-PROBE 五道门禁；新知识进库前必须先落对分层；角色权限按"最小必要集"分配且审查与执行强制分离。目标只有一个——让"自报即作数""单次探测即定论""看到就写"这三类失真无处发生。

主链七步：①进件分诊 → ②P1 权威信息 → ③计划＋审 → ④拆卡派单 → ⑤执行 → ⑥验收四门 → ⑦收口回流。

两条回边——停手／失败／变更走回边 A（回③重新计划）；验收不通过走回边 B（回⑤返工）。回边是这套流程的核心：不走回边直接往下冲，等于带着已知错误继续投入。

关键约束：
- 审查链：OpenClaw 方案 → DSH 可行性 → Claude 工程，有分歧升用户；同一议题轮次 ≤ 2，超 2 轮直接报用户；执行期一旦改计划，强制回③重审、并在⑦补记。
- 白名单：派单卡写死"只做这 N 件"，卡外一律不做。
- 拆卡：大任务拆小卡，单卡单目标 + 六要素投影；DSH 批量吞吐 N=5。
- 凭据：密钥／凭据不进卡、不落盘、不复述，走 key 同步链路注入。
- 停手：撞到新门停手报告；同一错误第 3 次停手报用户。
- 绿即停：验收四门全绿立即收手——① 自报不采信 ② 预埋 check 复跑 ③ 正例＋负例 ≥ 5 ④ receipt verify G0–G9。

二、任务三档分流：按爆炸半径决定要不要派单

3

80% 的日常任务应直接出结果，不该派单。判据是爆炸半径（影响面）而非任务大小。

档 占比 触发 做法
A 直出 80% 只读查询，或新文件 < 20 行且不在例外清单 直接干，不派单不审，干完报结果
B 派单 15% 命中例外清单／写 ~/.hermes 配置／改 key／跨 2+ Agent 出方案 → 派 1 个子智能体执行 → 验证
C 重流程 5% 架构决策／新功能／可能搞崩系统 方案 → OC 审 → 执行 → E2E + receipt verify

例外清单（即便 < 20 行也升 B 档）：~/.hermes/ 下任何文件、.env 类、依赖文件（pyproject.toml／package.json／requirements.txt）、docker／systemd／/etc/、多 Agent 共享文件（key-map／keyring／fallbacks）、export HERMES_* 类环境变量。

B 档验证三件套（缺一不算过）：① grep 实测改动已落盘；② 配置重载 + 真实 list／最小调用（不接受"grep 到文本就算过"）；③ 下游受影响 Agent 逐个 validate／ping——改了共享配置必须验下游，不只验自己侧（历史事故：自己侧 grep OK，下游 OpenClaw/Codex 读时炸）。

铁律：A 档干完直接报、不等确认；B 档不接受子智能体自报完成；只有 C 档才写 plan 文件、才走 receipt。

三、探测纪律 G-PROBE：五门禁治"单次探测下结论"2 个重点▾ 点开看本节重点
本节重点
  • 只要要写"可用／不可用／已挂／已生效／未生效／是死代码"这类判断，先过五道门；五条全过才能下结论，否则只能写"未确认"
  • 强制细则：多 IP 时逐 IP 全探（DNS 解析出多个 IP，全通才算过）；多端点变体全测（路径／版本／region 变体逐一验）；探测前先跑 30 秒探针确认网络正常，避免把超时当不可用；禁止"单次失败成结论 + 反复引用"——任何被复用的结论都必须可追溯到 G1+G2 的实测输出

只要要写"可用／不可用／已挂／已生效／未生效／是死代码"这类判断，先过五道门；五条全过才能下结论，否则只能写"未确认"。

门 规则 不通过
G1 双样本 附 ≥ 2 次独立探测的实测输出（状态码／响应／日志）；只贴一次 = 无效证据 改写"未确认"
G2 跨维度 这 ≥ 2 次需跨 ≥ 2 个维度：不同 IP／端点／参数，或引入已知正常的对照组 降级"疑似"
G3 加载路径 判"某配置是否生效"必须查产品实际加载路径（进程环境变量、被 import 的代码、真实调用打点），不接受只 grep 表面配置文件 改写"未确认"
G4 禁间接推断 禁用体积／mtime／条目数等间接指标推内容，必须实查（API／SQL／读文件） 改写"未确认"
G5 纠错闭环 因新证据改口后的新结论同样要过 G1–G4；撤回旧结论必须显式报告，禁静默改口 改写"未确认"

强制细则：多 IP 时逐 IP 全探（DNS 解析出多个 IP，全通才算过）；多端点变体全测（路径／版本／region 变体逐一验）；探测前先跑 30 秒探针确认网络正常，避免把超时当不可用；禁止"单次失败成结论 + 反复引用"——任何被复用的结论都必须可追溯到 G1+G2 的实测输出。

正／负例对照（2026-09-29 实测）：

负例 正例
单次 curl 返回 000 → 断言"魔搭不可用" 逐 IP 重探：一 IP 000、另一 IP 200 → 结论"可用，双 IP 中一个不通"
单次 000 → 断言"端点配错了" 重测返 200 + 官方文档证实端点本就正确 → "此前 000 为瞬时抖动"
单次 000 → 断言"火山不可用" 全变体复测：/api/v3/ 401（鉴权正常）、/api/plan/v3/ 200 → "可用"
grep 废弃的 secrets.env → 断言"没接进配置" 查实际加载路径 ~/.hermes/hindsight/config.json → "早已接管生效"
du -sh 见 65M → 断言"空壳没记忆" 实查 API：fact_count=481 且持续写入 → "有记忆"

四、六角色权限契约：权限 = 职责的最小必要集

3

派子智能体前先定角色，权限只给职责需要的最小集。

角色 职责 工具权限 承担者
研究 探索代码库、分析实现 只读（file／search／web） Hermes／DSH
规划 需求分解为结构化任务 只读，无写入 Hermes 独占
执行 实现单个具体任务 限定范围读写 DSH（完整单整单自主）／Codex
审查 审计成果、标记问题 只读 + 标记（禁用 terminal） Claude Code／OpenClaw
调试 修复审查发现的问题 限定范围修复 Claude Code
清理 对抗熵积累、清低质产物 读写（先建清单再删） Hermes 定期任务

铁律——审查者与执行者分离：改动 > 3 个文件必须由独立上下文的审查角色复审；审查角色 context 只给产物路径、不给执行过程；审查角色只能读，发现问题标记出来、交调试角色修。

权限陷阱：terminal 能写文件（>、rm、sed -i），execute_code 能调 terminal → 审查／研究角色必须同时禁用 terminal 与 execute_code，否则"只读"形同虚设。

权限四级：只读级（file+search+web）→ 研究、审查；轻写级（file+search）→ 只改文件；执行级（file+terminal+search）→ 执行、调试、清理；完全级（不加限制）→ 仅总调度 Agent。

沉淀三问（receipt declare 后、任务收尾前自动跑，全否即收尾）：Q1 有新链接／来源吗 → 有就落 raw/ 采集层；Q2 踩过坑／报错了吗 → 有就写 error-ledger 回流层；Q3 流程有可优化点吗 → 有就提 Gap 到人。

三问命中后，新知识不能"看到就写、写完就生效"，必须先判落对哪一层、再过对应门：

落地层 载体 准入门 状态标记
协议层 AGENTS.md 必须 OpenClaw 审通过才能写入 直接生效（OC 已把关）
记忆层 LEARNING-INDEX.md Hermes 自审：是否与现有规则冲突？触发词是否重叠？ 新条目默认"候选"，实战触发 ≥ 3 次后由周复盘 cron 升"已验证"
技能层 技能 references/ Hermes 自审 + 标注来源（哪个 error-ledger 条目触发） 新条目"候选"，触发 3 次后转正

顺序：三问命中 → 判分层 → 走门 → 再写盘，禁止跳过门直接生效。冲突处理：自审发现新条目与现有规则冲突时不写，在原位置追加 ⚠️冲突: <现有规则#>，等下次周复盘 cron 一并提案。

六、派单卡的工程硬约束（5 条踩坑修正）

3

来自 2026-09-29 实测，每次派 delegate_task 前自检：

  1. 派单卡必须标注"子智能体执行"：否则 write-guard 正则会把主对话的写操作误杀（连 open("/etc/passwd") 这类读操作都被拦）。
  2. 派单卡长度 ≤ 2000 字：超长会被 message_sanitization 替换成空对象，子智能体收不到 context。长任务拆多卡，或把长 context 丢文件、卡里只留路径。
  3. 派单卡禁含 ${VAR_NAME} 字面量：含 shell 变量插值字面量会被上游 API 直接拒绝；需描述变量时改用文字（如"环境变量 X"）。
  4. 查进程占用用 fuser <file> 或 lsof <path>：禁止遍历 /proc/*/fd，安全网关会 BLOCKED 整批遍历。
  5. verifier 警告 ≠ 没改成：看到"file not modified／lint warning"类警告，先实测（grep、python 读配置、真实 list 调用）再下结论，不要因警告直接回滚——警告可能由 lint 误配置引起。
